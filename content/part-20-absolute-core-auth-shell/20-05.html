2. login() ทีละส่วน

Future<AuthSession> login(String employeeId, String password) async {
  // Shared WMS auth (Identity / AspNetUsers) — not a PDA-specific endpoint.
  final json = await _api.post('/api/Authenticate/login', {          // ①
    'Username': employeeId,
    'Password': password,
  }, absolute: true);

  final roles = (json['roles'] as List<dynamic>? ?? const [])       // ②
      .map((value) => value.toString())
      .where((value) => value.isNotEmpty)
      .toList(growable: false);

  final session = AuthSession(
    token: json['token'] as String,                                  // ③
    username: json['username']?.toString().trim().isNotEmpty == true  // ④
        ? json['username'].toString().trim()
        : employeeId,
    roles: roles,
    access: PdaAccess.fromJson(json['permissions']),                 // ⑤
    expiration: DateTime.tryParse(json['expiration']?.toString() ?? ''),  // ⑥
  );

  _api.authToken = session.token;                                    // ⑦
  _session = session;
  return session;
}

① absolute: true

ปกติ post() จะเติม /api/WMS ให้ — ล็อกอินไม่ใช่เส้นทางของพีดีเอ จึงต้องบอกให้ใช้เส้นทางตามที่เขียน

ปกติ       → http://host:6191/api/WMS/mobile_xxx
absolute   → http://host:6191/api/Authenticate/login

คอมเมนต์บอกว่านี่คือระบบยืนยันตัวตนของ WMS ที่เว็บใช้ร่วมกัน — ผู้ใช้คนเดียวกัน รหัสผ่านเดียวกัน ล็อกอินได้ทั้งเว็บและพีดีเอ

② อ่าน roles แบบไม่ยอมล้ม

(json['roles'] as List<dynamic>? ?? const [])
    .map((value) => value.toString())
    .where((value) => value.isNotEmpty)
    .toList(growable: false);
ส่วนกันอะไร
as List<dynamic>?ไม่มีฟิลด์ หรือเป็น null
?? const []ได้รายการว่างแทนที่จะล้ม
.toString()ถ้าเซิร์ฟเวอร์ส่งตัวเลขมาก็ยังใช้ได้
.where(isNotEmpty)ทิ้งสตริงว่าง

③ token เป็นที่เดียวที่ยอมล้ม

token: json['token'] as String,     // ไม่มี ? ไม่มี ??

ถ้าไม่มี token จะโยน TypeError

นี่เป็นการเลือกที่ถูก ไม่ใช่การลืม
ทุกฟิลด์อื่นมีทางถอย เพราะขาดไปแล้วยังทำงานต่อได้
แต่ session ที่ไม่มี token คือ session ที่ยิงอะไรไม่ได้เลย — การสร้างมันขึ้นมาแล้วให้ผู้ใช้เข้าไปเจอ 401 ทุกจอ แย่กว่าการบอกว่าล็อกอินไม่สำเร็จตั้งแต่แรก
กฎ: ยอมล้มตรงที่ล้มแล้วรู้เรื่อง ดีกว่าไปล้มไกล ๆ ที่ไม่รู้ว่าเพราะอะไร

ข้อควรปรับปรุงเล็ก ๆ คือ TypeError ที่หลุดออกไปจะไม่ใช่ ApiException จอล็อกอินจึงเห็นเป็นข้อผิดพลาดคนละชนิด — จะกลับมาที่บทที่ 7

④ ชื่อผู้ใช้ที่มีทางถอย

username: json['username']?.toString().trim().isNotEmpty == true
    ? json['username'].toString().trim()
    : employeeId,

ถ้าเซิร์ฟเวอร์ไม่ส่งชื่อกลับมา ก็ใช้รหัสพนักงานที่พิมพ์เข้าไปแทน — แถบสถานะจะไม่ว่าง

สังเกตรูปแบบ == true ที่ท้าย: ?. ทำให้ผลเป็น bool? ซึ่งใส่ใน ? : ตรง ๆ ไม่ได้ การเทียบกับ true จึงแปลง null ให้เป็น false

สิ่งที่มีสิ่งที่ไม่มี

คอมเมนต์บอกว่ามาจากไหนfromJson

ไม่มี fromJson ทำไม

เพราะการแปลงอยู่ใน AuthRepository.login() ซึ่งเป็นที่เดียวที่มี JSON ก้อนนี้

ทางเลือกเหมาะเมื่อ
ใส่ fromJson ในโมเดลโมเดลถูกแปลงจากหลายที่ / มีเทสต์ยิงที่ตัวแปลงตรง ๆ
แปลงในตัวที่เรียกแปลงที่เดียว และตัวแปลงต้องรู้บริบท

ที่นี่เข้าเงื่อนไขที่สอง — สังเกตว่าตัวถอยของ username ใช้ employeeId ซึ่งเป็นพารามิเตอร์ของ login() ไม่ได้อยู่ใน JSON

username: ... : employeeId,     // ← ค่าจากนอก JSON

ถ้าย้ายไปเป็น AuthSession.fromJson(json) จะทำแบบนี้ไม่ได้ ต้องกลายเป็น AuthSession.fromJson(json, fallbackUsername: employeeId) ซึ่งไม่ได้ดีขึ้น

ไม่มี toJson ทำไม

เพราะ session ไม่เคยถูกบันทึกลงดิสก์ — ปิดแอปแล้วต้องล็อกอินใหม่ทุกครั้ง

เป็นการเลือกที่เหมาะกับพีดีเอในคลัง
  • เครื่องใช้ร่วมกันหลายคนต่อกะ — การจำผู้ใช้ไว้คือความเสี่ยงว่าคนถัดไปทำงานในนามคนก่อน
  • การบันทึกงานต้องผูกกับคนที่ทำจริง
บนแอปผู้บริโภคจะตรงข้าม — การบังคับล็อกอินทุกครั้งคือความรำคาญ
คำตอบมาจากรูปแบบการใช้งาน ไม่ใช่จากหลักการทั่วไป

6. ข้อผิดพลาดที่พบบ่อย

ผิดอาการถูก
สร้าง client แยกต่อฟีเจอร์ต้องส่ง token ต่อกันทุกที่ใช้ตัวเดียว แชร์ผ่าน getter
เก็บ session ลงดิสก์บนเครื่องที่ใช้ร่วมกันทำงานในนามคนอื่นอยู่ในหน่วยความจำ
อ่าน token แบบมีทางถอยเข้าแอปแล้วเจอ 401 ทุกจอปล่อยให้ล้มตั้งแต่ล็อกอิน
เก็บ expiration แต่ไม่ใช้token หมดอายุกลางกะโดยไม่บอกเช็คก่อนยิง แล้วพากลับไปล็อกอิน
ตรวจชื่อบทบาทในแอปเพิ่มบทบาทฝั่งเซิร์ฟเวอร์แล้วต้อง build ใหม่ให้เซิร์ฟเวอร์ส่งสิทธิ์ที่คำนวณแล้วมา

7. แบบฝึกหัด

  1. เขียนเทสต์ที่พิสูจน์ว่าเมื่อ username เป็นสตริงว่าง session จะใช้รหัสพนักงานแทน
  2. ออกแบบวิธีใช้ expiration ให้เกิดประโยชน์ โดยแก้ให้น้อยที่สุด

จังหวะทำไมพอ
ตอนกลับมาจากพักหน้าจอมี didChangeAppLifecycleState อยู่แล้ว (20.14) และเป็นจังหวะที่หมดอายุบ่อยที่สุด
เมื่อได้ 401เป็นตาข่ายรับกรณีที่เซิร์ฟเวอร์เพิกถอน token ก่อนเวลา
ทำไมไม่ตรวจใน ApiClient.post() ทุกครั้ง
ApiClient อยู่ใน core/ ซึ่งไม่รู้จัก AuthSession — การให้มันรู้จักคือการลากธุรกิจเข้าไปในชั้นที่ตั้งใจให้สะอาด
และการตรวจ 401 ทำงานอยู่แล้วโดยไม่ต้องพึ่งนาฬิกาของเครื่อง ซึ่งบนพีดีเออาจตั้งเวลาไม่ตรง
ประเด็นสุดท้ายสำคัญ — เวลาเครื่องเพี้ยนแล้วการเช็ค isExpired จะเด้งคนออกทั้งที่ token ยังดี ตัวจริงที่เชื่อได้คือ 401 จากเซิร์ฟเวอร์

สรุปว่า 401 คือกลไกหลัก และ expiration เป็นแค่ตัวช่วยให้ข้อความอ่านรู้เรื่อง — ต่างจากที่เดาไว้ตอนแรกว่าจะใช้มันเป็นตัวตัดสิน

8. สรุป

  • AuthRepository 46 บรรทัด — ไม่รู้จักหน้าจอเลย
  • ล็อกอินยิง /api/Authenticate/login ด้วย absolute: true ใช้ระบบเดียวกับเว็บ
  • ทุกฟิลด์มีทางถอย ยกเว้น token ที่ยอมล้ม — ล้มตรงที่รู้เรื่องดีกว่าล้มไกล
  • client getter ทำให้ทุกชั้น API ใช้ ApiClient ตัวเดียวกัน ล็อกอิน/ออกครั้งเดียวมีผลทั้งแอป
  • AuthSession ไม่มี fromJson เพราะแปลงที่เดียวและต้องใช้ค่าจากนอก JSON
  • ไม่มี toJson เพราะพีดีเอใช้ร่วมกันหลายคน ไม่ควรจำผู้ใช้
  • expiration ถูกอ่านมาแต่ไม่มีใครใช้ — และตัวที่เชื่อได้จริงคือ 401 ไม่ใช่นาฬิกาเครื่อง
