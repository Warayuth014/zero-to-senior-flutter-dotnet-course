2. _isHealthPayload

bool _isHealthPayload(String body) {
  try {
    final json = jsonDecode(body);
    return json is Map && json['service'] == 'WMS' && json['ok'] == true;
  } catch (_) {
    return false; // HTML, or anything else that is not our health payload
  }
}

สามเงื่อนไขที่ต้องผ่านพร้อมกัน

เงื่อนไขตัดอะไรออก
json is MapJSON ที่เป็นอาร์เรย์หรือตัวเลข
json['service'] == 'WMS'API อื่นที่บังเอิญตอบ JSON
json['ok'] == trueWMS ที่ตอบว่าตัวเองไม่พร้อม

และ catch จับ HTML ที่ jsonDecode แปลงไม่ได้

เงื่อนไขที่สองคือหัวใจ
ในเครือข่ายองค์กร ที่อยู่หนึ่งอาจเป็น API ของระบบอื่นที่รันอยู่พอร์ตใกล้กัน
การถามว่า “คุณคือ WMS ใช่ไหม” ตรง ๆ แม่นกว่าการเดาจากรูปแบบคำตอบ
หลักที่ใช้ได้ทั่วไป: ให้ตัวตรวจถามสิ่งที่มีแต่ระบบที่ถูกตัวเท่านั้นที่ตอบได้

สังเกตว่าตัวเปรียบเทียบใช้ == true ไม่ใช่ as bool

json['ok'] == true      // ถ้าเป็น null, "true", 1 → ได้ false ไม่ล้ม
json['ok'] as bool      // ถ้าเป็น null → TypeError

ในฟังก์ชันที่ต้องไม่ล้มไม่ว่าจะได้อะไรมา แบบแรกถูก

5. ตรวจ URL ก่อนยิง

Uri uri;
try {
  uri = Uri.parse('$baseUrl/api/WMS/mobile_health');
  if (!uri.hasScheme || uri.host.isEmpty) throw const FormatException();
} on FormatException {
  ...
  message: tr('The address is not a valid URL', 'ที่อยู่เซิร์ฟเวอร์ไม่ถูกต้อง'),
}

Uri.parse ใจกว้างกว่าที่คิด — สตริงหลายอย่างที่ไม่ใช่ URL ก็แปลงผ่าน

ใส่Uri.parseผ่านการตรวจเพิ่ม
http://host:6191/...ผ่านผ่าน
hello/api/WMS/mobile_healthผ่าน (เป็นเส้นทางสัมพัทธ์)ไม่ผ่าน — ไม่มี scheme
http:///api/...ผ่านไม่ผ่าน — host ว่าง

สองเงื่อนไขที่เติมเข้าไปจึงจำเป็น — และการโยน FormatException เองแล้วให้ catch เดียวกันจัดการ ทำให้ไม่ต้องเขียนเส้นทางออกสองแบบ

6. สี่ catch ที่แยกกันชัด

ข้อยกเว้นข้อความผู้ใช้ต้องทำ
TimeoutExceptionไม่ตอบใน 8 วินาที — ตรวจ IP และพอร์ตตรวจตัวเลข
HandshakeExceptionใบรับรอง HTTPS ไม่ผ่าน — ลองใช้ HTTPสลับช่อง Protocol
SocketExceptionติดต่อที่อยู่นี้ไม่ได้ — ตรวจสัญญาณและเครื่องตรวจ Wi-Fi / เครื่องเปิดไหม
http.ClientExceptionเชื่อมต่อไม่สำเร็จ + ข้อความจริงอ่านรายละเอียด
ทุกข้อความบอกการกระทำถัดไป — หลักเดียวกับข้อความตรวจฟอร์มใน 20.10
โดยเฉพาะ HandshakeException ที่บอกตรง ๆ ว่า “ลองใช้ HTTP”
คนที่เจอปัญหาใบรับรองในเครือข่ายภายในมักไม่มีสิทธิ์แก้ใบรับรอง — ทางออกจริงคือใช้ HTTP ซึ่งข้อความนี้พูดออกมาแทนที่จะให้ผู้ใช้เดา

9. ข้อผิดพลาดที่พบบ่อย

ผิดอาการถูก
ตรวจสุขภาพด้วยรหัส 200 อย่างเดียวเขียวทั้งที่ตั้งค่าผิดอ่านตัว body ด้วย
ตรวจผ่าน client ที่ผูกกับที่อยู่ปัจจุบันทดสอบค่าที่กำลังพิมพ์ไม่ได้รับ baseUrl เป็นพารามิเตอร์
ปิด client ที่ยืมมาเทสต์ล้มในการเรียกครั้งที่สองปิดเฉพาะที่สร้างเอง
เชื่อ Uri.parse ว่าจะโยนเมื่อ URL ผิดยิงไปยัง URL ที่ไม่มีความหมายตรวจ hasScheme และ host
ใช้ timeout เดียวกับคำขอปกติผู้ใช้นั่งรอ 15 วินาทีสั้นกว่าเมื่อคนกำลังรอดู
โยนข้อยกเว้นจากตัวตรวจผู้เรียกต้อง try/catch เพื่อรับคำตอบปกติคืนวัตถุผลลัพธ์
as bool กับค่าจาก JSONล้มเมื่อได้ null== true

    baseUrl: 'http://host:6191',

คำตอบสั้น: ควร แต่ไม่ใช่ด้วยการก๊อป _isHealthPayload ไปวาง

ให้แต่ละชั้นตรวจให้เข้มเท่าที่ความรู้ของมันอนุญาต — ไม่ใช่คัดลอกการตรวจของชั้นที่รู้มากกว่าไปใช้ในชั้นที่รู้น้อยกว่า
การก๊อปตรง ๆ จะทำให้ทุกคำขอที่ไม่มีฟิลด์ service ล้มทันที ซึ่งคือทุกคำขอในแอป

และนี่เป็นตัวอย่างของสิ่งที่ 19.15 เตือนไว้จากอีกมุม — การเห็นโค้ดคล้ายกันสองที่แล้วรีบรวม ไม่ได้ดีกว่าเสมอไป ต้องดูก่อนว่ามันตอบคำถามเดียวกันจริงหรือไม่

11. สรุป

  • Blazor ที่มี MapFallbackToPage ตอบ 200 ให้ทุกเส้นทางที่ไม่รู้จัก — รหัสสถานะจึงพิสูจน์อะไรไม่ได้
  • _isHealthPayload ตรวจ service == 'WMS' และ ok == true จากตัว body
  • ใช้ == true ไม่ใช่ as bool เพราะฟังก์ชันนี้ต้องไม่ล้ม
  • ไม่ผ่าน ApiClient เพราะต้องทดสอบที่อยู่ที่ยังพิมพ์อยู่ในฟอร์ม
  • owned — ปิดเฉพาะ client ที่สร้างเอง
  • ตรวจ hasScheme และ host เพิ่ม เพราะ Uri.parse ใจกว้างเกินไป
  • สี่ catch ที่ทุกข้อความบอกการกระทำถัดไป
  • คืน ConnectionTestResult ไม่โยน เพราะการต่อไม่ติดคือคำตอบ ไม่ใช่ข้อผิดพลาด
  • timeout 8 วินาทีเพราะผู้ใช้นั่งรอดู
  • ไม่มีเทสต์สำหรับไฟล์นี้ ทั้งที่ออกแบบมาให้ทดสอบได้ครบ
