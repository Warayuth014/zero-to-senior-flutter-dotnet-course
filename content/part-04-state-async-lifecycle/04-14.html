UI idempotencyทำให้ eventซ้ำให้ผลเหมือนครั้งเดียวภายใน client session ด้วย guard, command identity และ state transition แต่ความถูกต้องสุดท้ายของ mutationต้องมี server idempotency/unique constraintด้วย

1. Guard by state

Future<void> confirmPick() async {
  if (state is! ReadyToConfirm) return;
  final ready = state as ReadyToConfirm;
  state = Submitting(ready.draft);
  notifyListeners();
  // eventที่สองเห็น Submittingและ return
}

State machine guardแข็งแรงกว่า boolกระจัดกระจายเพราะบอก actionที่อนุญาต

2. Operation key

สร้าง UUIDตอนเริ่ม business operationและเก็บคู่ pending state Retry requestเดิม reuse key; userเริ่ม operationใหม่จึงสร้าง keyใหม่ ส่ง header/bodyให้ .NET endpointเก็บผล/unique keyตาม user+operation

3. Disable UI ไม่พอ

Enter, scanner, hardware button, deep callbackและ double tapอาจเข้าก่อน rebuild ต้อง guard synchronousใน command และ serverตรวจอีกชั้น Disabled widgetเป็น feedback/accessibilityไม่ใช่ lockหลัก

4. Duplicate domain value

Idempotency keyต่างจาก barcode duplicate รหัสเดิมอาจเป็น operationใหม่ที่ถูกต้อง หรือ scanซ้ำผิด ต้องมี domain ruleแยก เช่น serial unique, product barcodeเพิ่ม qty, retry confirmใช้ operationเดิม

5. Timeout unknown outcome

อย่าปลด stateเป็น Readyแล้วสร้าง keyใหม่ทันที เพราะ serverอาจ commitแล้ว เปลี่ยนเป็น Unknown/Reconcile, query statusด้วย key หรือ retry same keyจนได้ deterministic result

6. Tests

เรียก commandสองครั้งก่อน Futureแรกจบ assert repositoryหนึ่ง call; timeoutแล้ว retry assert keyเดิม; successแล้ว eventซ้ำไม่ call; reset/new draftจึง keyใหม่ ใช้ Completerกับ fake UUID generator

7. แบบฝึกหัด

ผู้ใช้กด Confirm, timeout, ปิดหน้าแล้วกลับมา ต้องเก็บอะไรเพื่อ retryปลอดภัย?

8. จุดพลาด

Debounce 500msไม่ใช่ idempotency Requestอาจใช้ 5s, app retryหรือสอง deviceยังซ้ำ ต้องออกแบบ command stateและ backend contractร่วมกัน
