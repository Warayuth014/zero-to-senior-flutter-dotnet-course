ระดับ: กลาง–สูงใช้เวลา: 40–50 นาทีลงมือทำ: ทำให้กดซ้ำ ส่งซ้ำ แล้วผลยังเหมือนกดครั้งเดียว
ต้องผ่านอะไรมาก่อน: 4.13 (การย้อนกลับและกรณีไม่รู้ผล) และ 3.9 (การกันสแกนซ้ำ)
จบบทนี้แล้วจะทำได้: ออกแบบคำสั่งที่ส่งซ้ำได้อย่างปลอดภัย และรู้ว่าฝั่งแอปทำได้แค่ไหน ฝั่งเซิร์ฟเวอร์ต้องทำอะไร

1. ปัญหาที่บทนี้แก้

ปัญหาที่เจอจริงในคลัง — ใบรับเข้าใบเดียวกันถูกบันทึกสองครั้ง สต๊อกเกินไป 240 ชิ้น

ไล่ย้อนกลับไปดูจะพบว่าไม่มีใครทำอะไรผิดเลย

0.0s  ผู้ใช้กดยืนยัน → ยิงคำขอไป
5.0s  ยังไม่มีอะไรเกิดขึ้นบนจอ (สัญญาณ Wi-Fi แถวแร็คแย่)
6.0s  ผู้ใช้กดยืนยันอีกครั้ง เพราะคิดว่ากดไม่ติด
7.0s  คำขอแรกถึง server → บันทึก
9.0s  คำขอที่สองถึง server → บันทึกอีกใบ

เซิร์ฟเวอร์ทำถูกต้องทุกอย่าง — ได้รับคำขอสองครั้ง ก็บันทึกสองครั้ง ปัญหาคือ ไม่มีใครบอกมันว่าสองคำขอนี้คือเจตนาเดียวกัน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
idempotentทำกี่ครั้งก็ได้ผลเท่ากับทำครั้งเดียว
command id / idempotency keyรหัสประจำเจตนาหนึ่งครั้งของผู้ใช้
guardเงื่อนไขที่ปฏิเสธคำสั่งซ้ำก่อนที่จะทำอะไร
unique constraintกติกาในฐานข้อมูลที่ห้ามข้อมูลซ้ำ
at-least-onceรับประกันว่าถึงอย่างน้อยหนึ่งครั้ง แต่อาจมากกว่า

3. Mental model: แยก “การกด” ออกจาก “เจตนา”

เจตนา: "ปิดงานบรรทัด L-3"       ← มีครั้งเดียว
  ├─ กดครั้งที่ 1 → คำขอ
  ├─ กดครั้งที่ 2 → คำขอ           ทั้งหมดนี้คือเจตนาเดียวกัน
  └─ ลองใหม่อัตโนมัติ → คำขอ

เจตนาใหม่: "ปิดงานบรรทัด L-3 อีกครั้งหลังแก้ปัญหาแล้ว"  ← คนละครั้ง
ประโยคเดียวที่ต้องจำ: รหัสคำสั่งไม่ได้ระบุ “คำขอ” แต่ระบุ “เจตนา” — คำขอหลายครั้งที่มาจากเจตนาเดียวกัน ต้องพกรหัสเดียวกันไป

สิ่งที่ต้องระวังคือ การปิดปุ่มไม่ใช่การกัน

ปุ่มจะกลายเป็นสีเทาก็ต่อเมื่อ notifyListeners() ทำงานและ Flutter วาดใหม่เสร็จ ซึ่งเกิดหลังจากที่ผู้ใช้กดไปแล้ว บน PDA ที่ใช้ปุ่มสแกนแบบกดค้าง หรือเครื่องสแกนที่ยิง Enter รัว ๆ เหตุการณ์สองครั้งอาจเข้ามาก่อนที่จอจะทันวาดด้วยซ้ำ

5. ด่านที่สอง: รหัสคำสั่ง

ด่านแรกอยู่ในหน่วยความจำของแอป จึงหายไปทุกครั้งที่ปิดแอป และไม่มีทางรู้เรื่องของ PDA เครื่องอื่น ด่านที่สองคือการติดรหัสไปกับคำขอ

final Map<String, String> _pendingCommandIds = <String, String>{};

final commandId = _pendingCommandIds.putIfAbsent(lineId, _createCommandId);

putIfAbsent ทำสองอย่างในบรรทัดเดียว

สถานการณ์ผลลัพธ์
ยังไม่มีรหัสค้างอยู่สร้างรหัสใหม่แล้วเก็บไว้
มีรหัสค้างอยู่แล้วใช้รหัสเดิม

แล้วส่งไปกับคำขอ

await repository.markDone(lineId, commandId: commandId);

ฝั่งเซิร์ฟเวอร์จะเห็นว่าคำขอที่สองพกรหัสเดียวกับคำขอแรก จึงตอบผลเดิมกลับมาแทนที่จะบันทึกซ้ำ — รายละเอียดฝั่ง .NET อยู่ในหัวข้อ 8

6. กฎที่ตัดสินว่าเมื่อไหร่ใช้รหัสเดิม

นี่คือส่วนที่คิดยากที่สุดของบทนี้ และเป็นจุดที่คนเขียนผิดบ่อยที่สุด

คำถามคือ เมื่อคำสั่งล้มเหลวแล้วผู้ใช้กดใหม่ ควรใช้รหัสเดิมหรือรหัสใหม่

คำตอบไม่ใช่ “เดิมเสมอ” และไม่ใช่ “ใหม่เสมอ” แต่ขึ้นกับว่า เรารู้ผลของครั้งก่อนหรือเปล่า

ผลของครั้งก่อนครั้งใหม่คือรหัสเพราะ
ไม่รู้ผล เช่นหมดเวลารอการส่งซ้ำของเจตนาเดิมเดิมเซิร์ฟเวอร์อาจบันทึกไปแล้ว รหัสเดิมทำให้ไม่ซ้ำ
รู้แน่ว่าถูกปฏิเสธเจตนาใหม่ใหม่ครั้งก่อนไม่มีอะไรถูกบันทึก และเงื่อนไขอาจเปลี่ยนไปแล้ว
สำเร็จ—ล้างทิ้งเจตนานั้นจบแล้ว

ดูว่าโค้ดบังคับกฎนี้อย่างไร

try {
  await repository.markDone(lineId, commandId: commandId);
  _pendingCommandIds.remove(lineId);       // สำเร็จ → ล้าง
} on PickException catch (error) {
  if (error.outcomeUnknown) {
    ...
    await load();
    return;                                 // ไม่ลบ → ครั้งหน้าได้รหัสเดิม
  }
  _rollback(lineId, before);
  _pendingCommandIds.remove(lineId);       // ล้มเหลวแน่นอน → ล้าง → รหัสใหม่
  _errorMessage = error.message;
}

ทั้งหมดตัดสินด้วยการ ลบหรือไม่ลบ รายการออกจาก map เท่านั้น

ทำไมกรณี “ถูกปฏิเสธ” ถึงต้องใช้รหัสใหม่ — ลองนึกภาพว่าเซิร์ฟเวอร์ปฏิเสธเพราะบรรทัดนั้นถูกล็อกโดยคนอื่นอยู่ พอคนนั้นทำเสร็จ ผู้ใช้กดใหม่ ถ้ายังส่งรหัสเดิมไป เซิร์ฟเวอร์ที่จำผลเดิมไว้จะตอบ “ถูกปฏิเสธ” กลับมาอีกทั้งที่ตอนนี้ทำได้แล้ว

7. เทสต์ที่ตรึงกฎทั้งสองข้อไว้

กฎในหัวข้อ 6 เป็นข้อตกลงที่มองไม่เห็นจากตัวโค้ด ถ้าไม่มีเทสต์ตรึงไว้ วันหนึ่งจะมีคนย้าย _pendingCommandIds.remove() ไปไว้ใน finally เพราะดูสะอาดกว่า แล้วกฎครึ่งหนึ่งจะหายไปเงียบ ๆ

สิ่งที่ทำให้ทดสอบได้คือ store รับตัวสร้างรหัสเข้ามาได้

PickStore({required this.repository, String Function()? createCommandId})
  : _createCommandId = createCommandId ??
        (() => DateTime.now().microsecondsSinceEpoch.toString());
// ในเทสต์ ใช้ตัวสร้างที่คาดเดาได้
var counter = 0;
store = PickStore(
  repository: repository,
  createCommandId: () => 'cmd-${counter++}',
);
test('ไม่รู้ผลแล้วลองใหม่ ต้องใช้รหัสคำสั่งเดิม เพื่อไม่ให้บันทึกซ้ำ', () async {
  repository.failWith = const PickException('หมดเวลารอ', outcomeUnknown: true);
  await store.markDone('L-1');

  repository.failWith = null;
  await store.markDone('L-1');

  expect(repository.commandIds, ['cmd-0', 'cmd-0']);
});

test('รู้แน่ว่าล้มเหลว การลองใหม่คือเจตนาใหม่ จึงใช้รหัสใหม่', () async {
  repository.failWith = const PickException('บรรทัดนี้ถูกยกเลิกแล้ว');
  await store.markDone('L-1');

  repository.failWith = null;
  await store.markDone('L-1');

  expect(repository.commandIds, ['cmd-0', 'cmd-1']);
});

สองเทสต์นี้ตรึงคนละครึ่งของกฎเดียวกัน และถ้าเขียนแค่ตัวเดียวจะได้ระบบที่ผิดคนละแบบ

ถ้ามีแต่เทสต์แรกถ้ามีแต่เทสต์ที่สอง
อาจเขียนให้ใช้รหัสเดิมตลอด → ลองใหม่หลังถูกปฏิเสธแล้วโดนปฏิเสธซ้ำตลอดกาลอาจเขียนให้สร้างรหัสใหม่ตลอด → ข้อมูลซ้ำเมื่อหมดเวลารอ
ลองเอง: ย้าย _pendingCommandIds.remove(lineId) ทั้งสองที่ไปรวมไว้ใน finally แล้วรัน flutter test --no-pub — เทสต์แรกจะแดงทันที นี่คือตัวอย่างของเทสต์ที่ปกป้องการตัดสินใจเชิงออกแบบ ไม่ใช่แค่ปกป้องโค้ด

8. ฝั่งแอปทำได้แค่ครึ่งเดียว

ต้องพูดให้ชัด — ทุกอย่างในบทนี้ไม่มีความหมายเลยถ้าเซิร์ฟเวอร์ไม่ทำหน้าที่ของมัน

ฝั่งแอปรับผิดชอบฝั่งเซิร์ฟเวอร์รับผิดชอบ
สร้างรหัสประจำเจตนาจำว่ารหัสไหนเคยทำไปแล้ว
ส่งรหัสเดิมไปเมื่อส่งซ้ำตอบผลเดิมแทนการทำซ้ำ
กันการกดรัวในเครื่องกันคำขอจากหลายเครื่องพร้อมกัน

เหตุผลที่ฝั่งแอปทำเองไม่ได้ เพราะมีอย่างน้อยสามช่องที่แอปมองไม่เห็น

ช่องโหว่ทำไมแอปกันไม่ได้
ปิดแอปแล้วเปิดใหม่ข้อมูลในหน่วยความจำหายหมด
PDA สองเครื่องทำบรรทัดเดียวกันแต่ละเครื่องไม่รู้จักกัน
ชั้นเครือข่ายส่งซ้ำเองเกิดใต้ระดับที่โค้ดเรามองเห็น

ฝั่ง .NET จะเก็บรหัสไว้แล้วตอบผลเดิมเมื่อเจอซ้ำ

// ฝั่ง server (แนวคิด — รายละเอียดอยู่ในคอร์ส .NET)
var existing = await _db.Commands.FindAsync(commandId);
if (existing is not null) return Ok(existing.Result);   // ตอบผลเดิม ไม่ทำซ้ำ

และควรมี unique constraint ในฐานข้อมูลเป็นด่านสุดท้าย เพราะสองคำขอที่มาถึงพร้อมกันจริง ๆ อาจอ่านตารางเจอว่า “ยังไม่มี” พร้อมกันทั้งคู่

เรื่องการออกแบบ endpoint และการเก็บผลฝั่งเซิร์ฟเวอร์อยู่ใน zero-to-senior-dotnet8-course ส่วนการส่งรหัสผ่าน header และการอ่านคำตอบจะทำจริงใน Part 8

ก่อนเริ่มเขียนฟีเจอร์ที่เปลี่ยนสต๊อก ต้องคุยกับฝั่งหลังบ้านก่อนว่ารหัสคำสั่งส่งไปทางไหนและเซิร์ฟเวอร์ตอบอะไรเมื่อเจอซ้ำ — ถ้าตกลงกันทีหลัง มักจะได้ข้อตกลงที่ไม่ครอบคลุมกรณีหมดเวลารอ ซึ่งเป็นกรณีที่สำคัญที่สุด

9. รหัสคำสั่ง กับ การสแกนซ้ำ ไม่ใช่เรื่องเดียวกัน

ใน 3.9 เราเคยกันการสแกนบาร์โค้ดซ้ำมาแล้ว แต่คนละเรื่องกับบทนี้

กันสแกนซ้ำ (3.9)รหัสคำสั่ง (บทนี้)
ถามว่า“รหัสของนี้เคยสแกนในรอบนี้ไหม”“เจตนานี้เคยถูกส่งไปแล้วไหม”
เป็นกติกาของธุรกิจระบบ
ค่าเดิมซ้ำได้ไหมแล้วแต่กติกาไม่มีทางซ้ำ เพราะสร้างใหม่ทุกเจตนา

และกติกาธุรกิจก็ไม่เหมือนกันในแต่ละกรณี

สแกนของเดิมซ้ำควรทำอย่างไร
เลข serial ที่ต้องไม่ซ้ำปฏิเสธ ของชิ้นนั้นมีชิ้นเดียว
บาร์โค้ดสินค้าทั่วไปเพิ่มจำนวน เพราะหยิบมาสองชิ้นจริง
รหัสพาเลทปลายทางยอมรับ ค่าเดิมคือค่าเดิม

อย่าใช้รหัสคำสั่งไปแก้ปัญหาการสแกนซ้ำ และอย่าใช้การกันสแกนซ้ำไปแก้ปัญหาการส่งซ้ำ

10. debounce ไม่ใช่ idempotency

ทางลัดที่เห็นบ่อย

// "แก้แล้ว" — ยังไม่ได้แก้
if (DateTime.now().difference(_lastTap) < const Duration(milliseconds: 500)) {
  return;
}
สถานการณ์debounce 500msรหัสคำสั่ง
กดรัวใน 0.2 วินาทีกันได้กันได้
กดอีกครั้งหลังรอ 5 วินาทีกันไม่ได้กันได้
ปิดแอปแล้วเปิดใหม่กดกันไม่ได้กันได้ ถ้าเก็บรหัสลงเครื่อง
เครือข่ายส่งซ้ำเองกันไม่ได้กันได้

debounce แก้เรื่องนิ้วสั่น ส่วน idempotency แก้เรื่องความถูกต้องของข้อมูล — ใช้แทนกันไม่ได้

11. เมื่อต้องข้ามการปิดแอป

ถ้าคำสั่งนั้นสำคัญพอ รหัสต้องอยู่รอดแม้แอปถูกปิด

ก่อนยิงคำขอ  → บันทึกรหัสลงเครื่อง
ยิงคำขอ
สำเร็จ       → ลบรหัสออก
ปิดแอปกลางคัน → รหัสยังอยู่

ตอนเปิดแอปกลับมาแล้วเจอรหัสค้าง มีสองทางเลือก

ทางเลือกเหมาะเมื่อ
ถามเซิร์ฟเวอร์ก่อนว่ารหัสนี้ผลเป็นอย่างไรเซิร์ฟเวอร์มี endpoint ให้ถาม
ส่งซ้ำด้วยรหัสเดิมเซิร์ฟเวอร์รองรับรหัสซ้ำแล้ว — ปลอดภัยเท่ากัน

ทั้งสองทางต้องอาศัยฝั่งเซิร์ฟเวอร์ที่ทำหน้าที่ตามหัวข้อ 8 ไว้แล้ว

สิ่งที่ห้ามทำคือลบรหัสทิ้งตอนเปิดแอปเพราะดูรก — เท่ากับลืมว่าเคยส่งอะไรไป แล้วคำสั่งถัดไปจะกลายเป็นการบันทึกซ้ำ

การเก็บข้อมูลลงเครื่องจะทำจริงใน Part 12

12. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ข้อมูลซ้ำเมื่อเน็ตช้าไม่มีรหัสคำสั่งส่งรหัสไปกับคำขอ
ปิดปุ่มแล้วยังซ้ำเหตุการณ์เข้ามาก่อนจอวาดใหม่กันในโค้ดด้วยธง ไม่ใช่กันด้วยหน้าตา
ลองใหม่หลังหมดเวลารอแล้วได้สองรายการสร้างรหัสใหม่ทุกครั้งใช้รหัสเดิมเมื่อไม่รู้ผล
ลองใหม่หลังถูกปฏิเสธแล้วโดนปฏิเสธซ้ำตลอดใช้รหัสเดิมตลอดล้างรหัสเมื่อรู้แน่ว่าล้มเหลว
เทสต์ผ่านหมด แต่ยังซ้ำที่หน้างานเซิร์ฟเวอร์ไม่ได้ตรวจรหัสตกลงข้อตกลงกับหลังบ้านให้ครบ
ใช้ debounce แล้วคิดว่าจบเข้าใจผิดว่าเป็นเรื่องเดียวกันทำทั้งสองอย่าง
สแกนของสองชิ้นแล้วนับได้ชิ้นเดียวเอาการกันคำสั่งซ้ำไปใช้กับการสแกนแยกกติกาธุรกิจออกจากกลไกระบบ

13. แบบฝึกหัด

ผู้ใช้กดยืนยันรับเข้า แล้วเกิดหมดเวลารอ จากนั้นกดปุ่มย้อนกลับออกจากหน้าจอ ปิดแอป แล้วเปิดกลับเข้ามาที่ใบเดิม

  1. ระบุว่าตอนเปิดกลับมา ความจริงมีกี่แบบที่เป็นไปได้
  2. บอกว่าต้องเก็บอะไรไว้บ้างเพื่อให้กดใหม่ได้อย่างปลอดภัย
  3. อธิบายว่าถ้าไม่เก็บอะไรเลย จะเกิดอะไรขึ้นและเสียหายแค่ไหน
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ความจริงที่เป็นไปได้

#ความจริงควรทำอะไร
1คำขอไปไม่ถึงเลยส่งใหม่ได้
2ถึงแล้ว บันทึกสำเร็จ แต่คำตอบหายห้ามส่งใหม่แบบไม่มีรหัส
3ถึงแล้ว กำลังประมวลผลอยู่รอหรือถามสถานะ
4ถึงแล้ว แต่ถูกปฏิเสธส่งใหม่เป็นเจตนาใหม่

จุดสำคัญคือ ฝั่งแอปแยกทั้งสี่แบบนี้ไม่ออกเลย — สิ่งที่เห็นเหมือนกันหมดคือ “ไม่ได้คำตอบ” จึงห้ามเดา

ข้อ 2 — ต้องเก็บอะไร

เก็บใช้ทำอะไร
รหัสคำสั่งส่งซ้ำได้โดยไม่บันทึกซ้ำ — สำคัญที่สุด
รหัสใบที่ทำอยู่รู้ว่ารหัสคำสั่งนั้นเป็นของใบไหน
สถานะว่า “ส่งไปแล้วแต่ไม่รู้ผล”ตอนเปิดมาจะได้รู้ว่าต้องตรวจสอบก่อน ไม่ใช่เริ่มใหม่
เวลาที่ส่งใช้บอกผู้ใช้ และตัดสินว่าเก่าเกินจะสนใจหรือยัง

ลำดับที่ควรทำเมื่อเปิดกลับมา

เปิดแอป → เจอคำสั่งค้าง
  → แสดงว่า "มีการยืนยันค้างอยู่ กำลังตรวจสอบ"   ← อย่าให้เริ่มใหม่เงียบ ๆ
  → ถามเซิร์ฟเวอร์ด้วยรหัสคำสั่งนั้น
      ├─ สำเร็จไปแล้ว → แสดงผล ลบรหัส จบ
      ├─ ไม่เคยได้รับ → ให้ผู้ใช้กดส่งด้วยรหัสเดิม
      └─ ถูกปฏิเสธ   → แสดงเหตุผล ลบรหัส เริ่มเจตนาใหม่ได้

ถ้าเซิร์ฟเวอร์ไม่มี endpoint ให้ถาม ก็ส่งซ้ำด้วยรหัสเดิมได้เลย ซึ่งปลอดภัยเท่ากันตราบใดที่เซิร์ฟเวอร์ตรวจรหัส

ข้อ 3 — ถ้าไม่เก็บอะไรเลย

ตอนเปิดกลับมา แอปจะไม่รู้ว่าเคยมีอะไรเกิดขึ้น หน้าจอจะแสดงใบเดิมในสภาพ “ยังไม่ได้ยืนยัน” เพราะข้อมูลที่โหลดมายังไม่ทันอัปเดต หรือเพราะโหลดมาก่อนที่เซิร์ฟเวอร์จะบันทึกเสร็จ

ผู้ใช้เห็นว่ายังไม่ยืนยัน → กดยืนยัน → รหัสใหม่ → บันทึกอีกใบ

ความเสียหายเรียงจากเบาไปหนัก

ระดับสิ่งที่เกิด
ข้อมูลใบรับเข้าซ้ำสองใบ
สต๊อกยอดเกินจริงเท่ากับของทั้งใบ
การเงินตั้งหนี้ผู้ขายซ้ำ หรือจ่ายซ้ำ ขึ้นกับว่าระบบผูกกับอะไร
การนับสต๊อกรอบนับถัดไปพบส่วนต่าง ต้องสอบสวนย้อนหลังทั้งวัน
ความเชื่อถือคนหน้างานเลิกเชื่อตัวเลขในระบบ แล้วกลับไปจดใส่กระดาษ

แถวสุดท้ายคือความเสียหายที่แท้จริง — ระบบที่ตัวเลขเชื่อถือไม่ได้ ไม่ได้ถูกใช้งานผิด แต่ถูกเลิกใช้

ข้อสังเกตสุดท้าย: ทั้งบทนี้แก้ปัญหาที่มาจากข้อเท็จจริงเดียว — เครือข่ายรับประกันได้แค่ว่าข้อความจะถึงอย่างน้อยหนึ่งครั้ง ไม่เคยรับประกันว่าถึงครั้งเดียว เมื่อรับข้อเท็จจริงนี้แล้ว รหัสคำสั่งจะไม่ใช่ของแถม แต่เป็นส่วนหนึ่งของคำสั่งที่ขาดไม่ได้

ลองต่อ: เขียนเทสต์ที่จำลองข้อ 1 กรณีที่ 2 — ให้ repository ปลอมโยน outcomeUnknown แต่บันทึกลง list ภายในว่าทำสำเร็จแล้ว จากนั้นส่งซ้ำด้วยรหัสเดิมแล้วให้ repository ตรวจรหัสและตอบผลเดิม แล้วยืนยันว่ารายการที่บันทึกมีแค่หนึ่ง

14. สรุปท้ายบท

  • เครือข่ายรับประกันแค่ “ถึงอย่างน้อยหนึ่งครั้ง” ไม่เคยรับประกันว่าครั้งเดียว
  • รหัสคำสั่งระบุเจตนา ไม่ใช่ระบุคำขอ
  • การปิดปุ่มคือการบอกผู้ใช้ ส่วนธงในโค้ดคือการกันจริง ต้องมีทั้งคู่
  • ไม่รู้ผล → ใช้รหัสเดิม / รู้ว่าล้มเหลว → ใช้รหัสใหม่ / สำเร็จ → ล้างทิ้ง
  • กฎนี้มองไม่เห็นจากโค้ด จึงต้องมีเทสต์ตรึงไว้ทั้งสองข้าง
  • ฝั่งแอปทำได้แค่ครึ่งเดียว เซิร์ฟเวอร์ต้องจำรหัสและตอบผลเดิม
  • ควรมี unique constraint เป็นด่านสุดท้ายในฐานข้อมูล
  • debounce ไม่ใช่ idempotency และการกันสแกนซ้ำก็คนละเรื่อง
  • คำสั่งที่สำคัญ ต้องเก็บรหัสให้อยู่รอดข้ามการปิดแอป
