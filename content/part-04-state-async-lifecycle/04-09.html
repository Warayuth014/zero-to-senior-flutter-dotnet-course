หลัง await UI ownerอาจถูก dispose การตรวจ mounted ป้องกันใช้ State/BuildContextที่หมดอายุ แต่ไม่ป้องกัน responseเก่าหรือ business stateเปลี่ยน ต้องตรวจ lifecycleและ operation identityแยกกัน

1. State.mounted

final result = await repository.login(credentials);
if (!mounted) return;
Navigator.of(context).pushReplacement(/* ... */);

ใช้ใน State methodก่อน setState, Navigator, ScaffoldMessengerหรือ FocusNodeหลัง async gap

2. context.mounted

ใน callbackที่มี local BuildContextใช้ if (!context.mounted) return และตรวจ contextตัวที่จะใช้จริง Dialog contextที่ popแล้วไม่เหมือน page contextที่ยังอยู่

3. Store ไม่ควรพึ่ง mounted

ChangeNotifier/repositoryไม่ควรรับ BuildContextเพื่อเช็ค lifecycle Storeมี ownership/disposed/cancellationของตนและ publish state; UI listenerที่ยัง mountedจึง render/effect WarehouseStoreอยู่ใต้ shellและ shell dispose storeพร้อมกัน

4. finally เมื่อ unmounted

อย่า returnก่อน cleanupที่จำเป็น วาง resource/store cleanupใน finallyแล้วตรวจ mountedเฉพาะ UI update ถ้า Stateหาย busy fieldของมันไม่สำคัญ แต่ timer/request/clientที่ ownerถือยังต้องจัดการ

5. Focus/dialog

หลัง await dialog/APIตรวจ mountedก่อนคืน focus wmsappและ Absoluteทำเช่นนี้หลายจุด ป้องกัน FocusNodeถูก disposeเมื่อ userกดย้อนระหว่าง request

6. Analyzer lint

use_build_context_synchronously ชี้จุด contextข้าม async gap แก้ด้วย reorderให้ใช้ก่อน await, ตรวจ mounted, หรือย้าย navigation/effectออกจาก service ไม่ปิด lintทั้งโปรเจกต์เพราะรำคาญ

7. แบบฝึกหัด

Store fetchเสร็จหลังหน้า Aปิดแต่หน้า Bยังใช้ storeเดียวกัน ควรทิ้ง resultเพราะ A unmountedไหม?

เฉลย

ไม่ควรผูก resultกับ Aถ้า storeเป็น shared owner ให้ store applyตาม operation identityและ notify B ส่วน Aเพียงหยุดใช้ context/effects หาก requestเป็นของ Aโดยเฉพาะค่อย cancel/ignoreเมื่อ owner dispose

8. จุดพลาด

Mounted trueไม่ได้แปลว่า task/entityยังเดิม และ mounted falseไม่ได้แปลว่าควรยกเลิก domain operationเสมอ แยก UI lifetimeจากงานธุรกิจให้ชัด
