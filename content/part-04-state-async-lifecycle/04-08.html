Async actionที่แข็งแรงต้อง guard concurrent call, publish loading, map error, cleanupใน finally และรักษา state consistency ไม่ว่า success, exception, navigation หรือ disposeจะเกิด

1. try/finally pattern

Future<void> confirm() async {
  if (_submitting) return;
  _submitting = true; _error = null; notifyListeners();
  try {
    final receipt = await repository.confirm(draft);
    _receipt = receipt;
  } on ApiException catch (e) {
    _error = e.message;
  } finally {
    _submitting = false;
    notifyListeners();
  }
}

2. Catch เฉพาะที่จัดการได้

แปลง known transport/domain exceptionเป็น state แต่ programming errorไม่ควรถูกกลืนเป็น “เกิดข้อผิดพลาด”แล้วเดินต่อผิด invariant ใช้ logging+rethrow/zoneตาม policy และให้ repositoryแปลง HTTPรายละเอียดเป็น typed failures

3. Future.wait

WarehouseStore loadAll โหลดหลาย resourceขนานด้วย Future.wait ลดเวลารวม แต่ค่า default errorทำ Futureรวม failเมื่อหนึ่งงาน fail แม้งานอื่นยังวิ่ง แต่ละ loaderจับ errorตนเองจึงเหมาะกับ partial success งานที่ต้อง all-or-nothingต้องออกแบบ transaction/result aggregationชัด

4. unawaited อย่างตั้งใจ

ใช้ unawaited เมื่อ fire-and-forgetจริง เช่น refresh badge/historyหลัง success แต่ futureต้องจัดการ errorภายใน ไม่ปล่อย unhandled exception และไม่ใช้เมื่อขั้นถัดไปต้องผลลัพธ์

5. Snapshot input

อ่าน draft/entity IDใส่ localก่อน await ถ้า mutable fieldsเปลี่ยนระหว่างทาง resultต้อง applyเฉพาะ operationเดิม ใช้ generation/session token ไม่อ่าน current fieldหลัง awaitแล้วสมมติว่าเหมือนเดิม

6. Cleanup location

Busyใน storeปลดใน finallyและ notify ส่วน UI setStateต้องตรวจ mounted แยก Resource cleanupไม่ควรถูกข้ามเพราะ UIหาย หาก commandถูกยกเลิกใช้ cancellation resultเฉพาะไม่เหมารวม error

7. แบบฝึกหัด

โหลด tasksและsummaryพร้อมกัน Summary failแต่ tasksต้องแสดง จะใช้ Future.waitตรงไหน?

เฉลย

ให้ loadTasks/loadSummaryจับและ publish stateตนเอง แล้ว Future.waitเพื่อรอ completionทั้งหมด หรือใช้ record Results aggregate ไม่ปล่อย summary exceptionทำ global load error หาก summaryเป็น optional ส่วน critical dependenciesค่อย failทั้งหน้า

8. จุดพลาด

ห้าม set loading=falseเฉพาะ success/catchหลายทางเพราะ return/exceptionใหม่ทำค้าง ใช้ finally และอย่า notify successก่อน serverตอบเพียงเพื่อให้ UIเร็ว หากต้อง optimisticให้มี rollbackชัด
