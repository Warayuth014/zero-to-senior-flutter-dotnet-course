ListenableBuilder rebuild builderเมื่อ notifierส่งสัญญาณ ขอบเขต builderควรครอบ consumersที่ต้องอ่าน snapshotเดียวกัน แต่ไม่ครอบ subtreeคงที่หรือ unrelated featureโดยไม่จำเป็น

1. Builder พื้นฐาน

ListenableBuilder(
  listenable: store,
  child: const WarehouseLogo(),
  builder: (context, child) => Column(
    children: [
      child!,
      Text('${store.pendingCount} งาน'),
      Expanded(child: TaskList(tasks: store.tasks)),
    ],
  ),
)

2. ขอบเขตจากโปรเจกต์จริง

Absolute shellแยก ListenableBuilderของ bodyและ bottom navigationแม้ฟัง storeเดียวกัน ทำ responsibilityชัด แต่ ChangeNotifier notifyยังเรียกทั้งสอง builder หากต้องลดกว่านั้นต้องแยก notifier/sliceหรือ selector ไม่ใช่แค่เพิ่ม nested builder

3. child optimization

ส่ง subtreeที่ไม่ขึ้นกับ stateผ่าน childเพื่อสร้าง configurationครั้งเดียว เช่น logo/static frame แต่ถ้า childอ่าน notifierผ่าน global/contextก็ไม่คงจริงและอาจ stale ให้ dependency explicit

4. Rebuild ไม่เท่ากับ repaint

Builderทำ buildใหม่แต่ Element/renderอาจ reuse การ optimizeต้อง profile DevToolsก่อน การแตก builderเล็กมากจำนวนมากเพิ่ม complexity ถ้า widgetราคาถูกและ notifyไม่ถี่อาจไม่คุ้ม

5. Selector concept

เมื่อ consumerสนเพียง pendingCount ให้ listenค่า sliceที่มี equality เช่น ValueListenable/Selector หรือแยก TaskSummaryNotifier จาก TaskDetailNotifier Snapshotควร immutableเพื่อเทียบได้ ไม่ให้ mutable listเปลี่ยนแต่ referenceเดิม

6. Side effect ไม่อยู่ builder

ห้าม showDialog, Navigator, sound หรือ APIใน builderเพราะ notify/buildซ้ำได้ ใช้ listener/effect channelที่ consume eventครั้งเดียว หรือ callbackจาก command owner ส่วน builder render stateเท่านั้น

7. แบบฝึกหัด

Connection dotเปลี่ยนทุก probeแต่ MaterialAppทั้งต้นไม้ rebuild ควรทำอย่างไร?

เฉลย

วาง ListenableBuilderเฉพาะ header dot/connection menuที่อ่าน controller ไม่ครอบ MaterialApp หาก base URL/profileกระทบ dependencyระดับ app ให้แยก config snapshotจาก status heartbeatเพื่อไม่ rebuildกว้างจาก dot

8. จุดพลาด

การวาง builderต่ำเกินจนแต่ละลูกอ่าน stateคนละช่วง notificationอาจเพิ่ม boilerplateและ snapshotไม่ atomic เลือก boundaryตาม consistencyและcost ไม่ใช่ “เล็กที่สุดเสมอ”
