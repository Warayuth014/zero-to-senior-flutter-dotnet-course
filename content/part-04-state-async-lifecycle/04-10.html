Stale responseเกิดเมื่อ requestเก่ากลับหลัง request/selectionใหม่และทับ stateล่าสุด วิธีง่ายที่ testได้คือ generation/session token: captureเลขตอนเริ่มและ applyเฉพาะเมื่อยังตรง current generation

1. Race ตัวอย่าง

A: load pallet P1 ─────────────── returns last
B: load pallet P2 ───── returns first → UI shows P2
A result applies                         → UI wrongly shows P1

2. Generation token

int _loadGeneration = 0;

Future<void> load(String id) async {
  final generation = ++_loadGeneration;
  _state = Loading(id); notifyListeners();
  final result = await repository.fetch(id);
  if (generation != _loadGeneration) return;
  _state = Data(result); notifyListeners();
}

void clear() {
  _loadGeneration++;
  _state = const Initial();
  notifyListeners();
}

3. Receive session จริง

WarehouseStoreเก็บ _receiveSession captureก่อน validate/confirm แล้วเปรียบเทียบหลัง await หากผู้ใช้ออกจาก flow sessionเพิ่มจึงไม่ restore UIเก่า แม้ backendอาจ commitแล้วก็ refresh receivingเพื่อ reconcile

4. Token vs cancellation

Tokenไม่หยุด network/batteryแต่กัน applyผิด; cancellationหยุดงานถ้า clientรองรับแต่ยังต้อง tokenเพราะ cancelอาจแข่ง completion ใช้ทั้งคู่ตาม cost และให้ repositoryรับ cancellation signalเมื่อเหมาะ

5. Per-key concurrency

Global generationทำ requestคนละ entityยกเลิกกันหมด หากโหลด detailหลายรายการพร้อมกันใช้ Map<ID,generation>, cache per keyหรือ immutable query key ตรวจ responseตรง request key/current selection

6. Busy flags และ stale finally

Requestเก่าไม่ควร set loading=falseของ requestใหม่ ใน finallyตรวจ generationก่อน publish หรือเก็บ in-flight count/tokenใน state มิฉะนั้น spinnerหายขณะ Bยังวิ่ง
