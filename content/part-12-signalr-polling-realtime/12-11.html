Fallback pollingเป็น degraded mode: เริ่มเมื่อ realtime disconnected/unsynchronized, หยุดเมื่อ reconnect+reconcileสำเร็จ และใช้ backoff/jitterเพื่อไม่ถล่ม server

1. Poll loop ไม่ overlap

Future<void> pollOnce() async {
  if (_polling || disposed || !needsFallback) return;
  _polling = true;
  try { await refresh(); _attempt = 0; }
  catch (_) { _attempt++; }
  finally { _polling = false; scheduleNext(); }
}

2. Backoff

successใช้ intervalปกติ เช่น 15s; failureเพิ่ม 2^attemptถึง maxและ jitter ถ้า businessต้อง 5sระบุ SLA/โหลด ไม่ใช้ Timer.periodicยิงซ้อนเมื่อ requestนานกว่า interval

3. Screen-aware

pollเฉพาะ dataที่ visible/จำเป็น ลด WarehouseStore timerที่เรียกหลาย endpointพร้อมกันทุกช่วง และ pauseตอน background/logout/server switch

4. Realtime recovery

เมื่อ hub reconnectให้หยุด fallbackหลัง HTTP reconcileสำเร็จ ไม่หยุดทันทีที่ socket connectedเพราะ stateอาจยังพลาด events

5. Manual refresh

user pull-to-refreshควรร่วม single-flightกับ pollและแสดง feedbackต่างกัน ไม่เปิด requestคู่ที่ responseแข่งกัน

6. Staleness

เก็บ lastSuccessfulSyncและแสดง stale/offlineเมื่อเกิน threshold Green realtime dotไม่แทน data freshnessถ้า refresh/parseล้ม

7. แบบฝึกหัด

poll interval 5sแต่ APIใช้ 8s จะเกิดอะไรกับ Timer.periodic?

เฉลย

request overlapและ response race ใช้ non-overlap self-scheduling/single-flightแล้ว scheduleหลัง requestจบ

8. Tests

fake clockตรวจ interval/backoff/jitter cap, no overlap, pause/resume, reconnect reconcileและ timer cancelเมื่อ dispose
