ระดับ: เริ่มต้น–กลางใช้เวลา: 30–40 นาทีลงมือทำ: ทำให้เนื้อหาที่ยาวเกินจอเลื่อนได้
ต้องผ่านอะไรมาก่อน: 2.1 (unbounded) และ 2.3 (Expanded)
จบบทนี้แล้วจะทำได้: เลือกระหว่าง SingleChildScrollView กับ ListView ได้ถูก และแก้ปัญหาพื้นที่เลื่อนซ้อนกันที่คนใหม่เจอกันทุกคน

1. ปัญหาที่บทนี้แก้

เมื่อเนื้อหายาวเกินจอ Flutter ไม่ได้ทำให้เลื่อนได้อัตโนมัติเหมือนหน้าเว็บ — มันแสดงแถบสีเหลืองดำแทน เราต้องบอกเองว่าส่วนไหนเลื่อนได้

ทางเลือกมีสองตัวหลัก และการเลือกผิดไม่ได้ทำให้หน้าจอพัง แต่ทำให้แอปช้าลงมากบน PDA โดยที่บนเครื่องพัฒนาไม่รู้สึกอะไรเลย

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
viewportช่องหน้าต่างที่มองเห็น ส่วนเนื้อหาเลื่อนอยู่ข้างหลัง
lazyสร้างเฉพาะที่มองเห็น ไม่สร้างทั้งหมด
shrinkWrapให้รายการหดตามเนื้อหาแทนที่จะกินพื้นที่เต็ม
ScrollControllerตัวควบคุมที่อ่านและสั่งตำแหน่งการเลื่อนได้
viewInsetsพื้นที่ที่ถูกระบบบัง เช่นแป้นพิมพ์

นี่คือรูปแบบที่ใช้ได้กับเกือบทุกหน้าจอในแอปคลัง: ส่วนหัวตรึง ส่วนกลางเลื่อน ซึ่งดีกว่าการให้ทั้งหน้าเลื่อน เพราะพนักงานยังเห็นยอดสรุปตลอดเวลาขณะไล่ดูรายการ

ทบทวนจาก 2.1 ว่าทำไมต้องมี Expanded: พื้นที่ที่เลื่อนได้ต้องรู้ว่าตัวเอง สูงเท่าไร ถึงจะรู้ว่าต้องแสดงกี่แถว ถ้าอยู่ใน Column เฉย ๆ มันจะไม่มีขอบเขตและพัง

5. กับดักใหญ่: พื้นที่เลื่อนซ้อนกัน

// ผิด — เลื่อนแนวตั้งซ้อนแนวตั้ง
SingleChildScrollView(
  child: Column(
    children: [
      const Header(),
      ListView.builder(...),    // พัง หรือต้องใส่ shrinkWrap ซึ่งเสียประโยชน์
    ],
  ),
)

คนใหม่มักเจอ error แล้วค้นเจอทางแก้ว่าให้ใส่ shrinkWrap: true กับ physics: NeverScrollableScrollPhysics() ซึ่งทำให้ error หายจริง แต่มีราคาที่ต้องจ่าย

ผลของ shrinkWrap: trueทำไมเป็นปัญหา
รายการต้องวัดลูกทุกตัวเพื่อรู้ความสูงรวมเสียประโยชน์ของ lazy ไปทั้งหมด — กลับไปสร้างครบทุกแถวเหมือน Column
ทุกครั้งที่ข้อมูลเปลี่ยนต้องวัดใหม่ทั้งหมดยิ่งรายการยาว ยิ่งหน่วง

ทางแก้ที่ถูกมีสองทาง

  1. ให้มีพื้นที่เลื่อนชั้นเดียว — ใช้ Column + Expanded ตามแบบใน lab ส่วนหัวตรึงไว้
  2. ถ้าส่วนหัวต้องเลื่อนไปด้วย — ใช้ CustomScrollView ที่รวมทุกอย่างไว้ในพื้นที่เลื่อนเดียว (เรื่องของ 2.8)

ใช้ shrinkWrap ได้เมื่อรายการสั้นและมีเพดานแน่นอนทางธุรกิจ เช่น “สินค้าที่แนบมากับพาเลทนี้ไม่เกิน 5 รายการ” ไม่ใช่ใช้เป็นทางหนี error

6. แป้นพิมพ์กับฟอร์ม

เมื่อแป้นพิมพ์ขึ้นมา Scaffold จะย่อพื้นที่ของเนื้อหาลงให้อัตโนมัติ ถ้าเนื้อหาอยู่ใน SingleChildScrollView อยู่แล้ว ช่องที่กำลังพิมพ์จะถูกเลื่อนขึ้นมาให้เห็นเอง

นี่คือเหตุผลหลักที่ฟอร์มควรอยู่ในพื้นที่เลื่อนได้เสมอ แม้จะดูพอดีจอบนเครื่องพัฒนา — เพราะบน PDA จอเตี้ยกว่า และเมื่อแป้นพิมพ์กินไปครึ่งจอ ฟอร์มที่เคยพอดีจะล้นทันที

อย่าคำนวณระยะเผื่อแป้นพิมพ์เองด้วยตัวเลขคงที่ เพราะความสูงของแป้นพิมพ์ต่างกันไปตามอุปกรณ์ ภาษา และว่าผู้ใช้เปิดแถบคำแนะนำไว้หรือไม่ — ปล่อยให้ Scaffold กับพื้นที่เลื่อนจัดการ

7. ScrollController

ใช้เมื่อต้องอ่านหรือสั่งตำแหน่งการเลื่อน เช่นเลื่อนกลับไปบนสุดหลังสแกนสำเร็จ

class _ScanListState extends State<ScanList> {
  final _controller = ScrollController();

  @override
  void dispose() {
    _controller.dispose();      // ของที่เราสร้าง เราคืน (1.6)
    super.dispose();
  }

  void _scrollToTop() {
    _controller.animateTo(
      0,
      duration: const Duration(milliseconds: 250),
      curve: Curves.easeOut,
    );
  }

  @override
  Widget build(BuildContext context) => ListView.builder(
    controller: _controller,
    ...
  );
}

เป็นการใช้กฎ “ใครสร้างต้องคืน” จาก 1.6 อีกครั้ง — และห้ามสร้างใน build ตามกฎใน 1.9 เพราะตำแหน่งการเลื่อนจะรีเซ็ตทุกครั้งที่หน้าจอวาดใหม่

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Vertical viewport was given unbounded heightพื้นที่เลื่อนอยู่ใน Column โดยไม่มีขอบเขตครอบด้วย Expanded
รายการเลื่อนไม่ได้ ทั้งที่ใช้ ListViewใส่ NeverScrollableScrollPhysicsตรวจว่าตั้งใจหรือลอกมาโดยไม่รู้ตัว
เลื่อนแล้วกระตุกมากเมื่อข้อมูลเยอะใช้ SingleChildScrollView + Column กับรายการยาวเปลี่ยนเป็น ListView.builder
ใส่ shrinkWrap แล้วแอปช้าลงเสียประโยชน์ของ lazyจัดโครงให้มีพื้นที่เลื่อนชั้นเดียว
ตำแหน่งเลื่อนรีเซ็ตเองตลอดสร้าง ScrollController ใน buildย้ายไปเป็น field ของ State
ช่องกรอกถูกแป้นพิมพ์บังฟอร์มไม่ได้อยู่ในพื้นที่เลื่อนได้ครอบด้วย SingleChildScrollView
เลื่อนแล้วสองชั้นขยับพร้อมกันงง ๆมีพื้นที่เลื่อนซ้อนกันในแกนเดียวเหลือชั้นเดียว

9. แบบฝึกหัด

หน้าจอรับเข้าสินค้าประกอบด้วย

  • หัวข้อและยอดสรุป
  • ฟอร์มสแกน 4 ช่อง
  • รายการที่รับเข้าแล้ว ซึ่งมาจาก API และอาจมีถึง 800 แถว
  • ปุ่มยืนยันที่ต้องอยู่ล่างสุดเสมอ กดได้ตลอดเวลา
  1. จัดโครงอย่างไร ถ้ายอดสรุปควรเห็นตลอด
  2. จัดอย่างไร ถ้าลูกค้าขอให้ยอดสรุปเลื่อนหายไปด้วยเพื่อให้เห็นรายการมากขึ้น
  3. อธิบายว่าทำไมห้ามใช้ SingleChildScrollView ครอบทั้งหมดในทั้งสองกรณี
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ยอดสรุปเห็นตลอด

Column(
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: [
    const SummaryHeader(),                       // ตรึง
    const ScanForm(),                            // ตรึง
    Expanded(                                    // เลื่อนเฉพาะส่วนนี้
      child: ListView.builder(
        itemCount: lines.length,
        itemBuilder: (context, index) => LineCard(
          key: ValueKey<String>(lines[index].palletCode),
          line: lines[index],
        ),
      ),
    ),
    const SafeArea(top: false, child: ConfirmBar()),   // ตรึงล่างสุด
  ],
)

ข้อ 2 — ยอดสรุปเลื่อนไปด้วย

Column(
  children: [
    Expanded(
      child: CustomScrollView(          // พื้นที่เลื่อนเดียว รวมทุกอย่าง
        slivers: [
          const SliverToBoxAdapter(child: SummaryHeader()),
          const SliverToBoxAdapter(child: ScanForm()),
          SliverList.builder(           // ยังคง lazy อยู่
            itemCount: lines.length,
            itemBuilder: (context, index) => LineCard(
              key: ValueKey<String>(lines[index].palletCode),
              line: lines[index],
            ),
          ),
        ],
      ),
    ),
    const SafeArea(top: false, child: ConfirmBar()),   // ยังตรึงอยู่นอก
  ],
)

จุดสำคัญคือปุ่มยืนยัน อยู่นอกพื้นที่เลื่อนทั้งสองกรณี เพราะโจทย์บอกว่าต้องกดได้ตลอดเวลา ถ้าเอาไปไว้ข้างในผู้ใช้ต้องเลื่อนลงไปสุดก่อนถึงจะกดได้ ซึ่งบนหน้าจอที่มี 800 แถวคือฝันร้าย

ข้อ 3 — ทำไมห้ามครอบทั้งหมด

สองเหตุผล เหตุผลแรกคือถ้าครอบด้วย SingleChildScrollView แล้วใส่ ListView ข้างใน จะได้พื้นที่เลื่อนซ้อนกันตามหัวข้อ 5 และต้องพึ่ง shrinkWrap ซึ่งทำให้ 800 แถวถูกสร้างครบทันที

เหตุผลที่สองซึ่งสำคัญกว่าคือ ปุ่มยืนยันจะเลื่อนหายไปด้วย ผู้ใช้ที่เพิ่งสแกนเสร็จต้องเลื่อนผ่าน 800 แถวเพื่อไปหาปุ่ม ในคลังจริงที่ต้องทำงานเร็ว นี่คือปัญหาการใช้งานที่ร้ายแรงกว่าเรื่องประสิทธิภาพเสียอีก

ข้อสังเกตเรื่อง SafeArea(top: false): ใส่ที่ปุ่มล่างเพื่อกันไม่ให้ปุ่มไปอยู่ใต้แถบนำทางของระบบ และปิด top เพราะด้านบนมีคนจัดการแล้ว — รายละเอียดใน 2.9

ลองต่อ: ใน lab ให้เปลี่ยน ListView.builder เป็น SingleChildScrollView + Column แล้วเพิ่มข้อมูลจำลองเป็น 2,000 แถว จับเวลาตอนเปิดหน้าจอเทียบกัน — ความต่างจะชัดเจนมากบนอุปกรณ์จริง

10. สรุปท้ายบท

  • SingleChildScrollView สร้างลูกทั้งหมดทันที เหมาะกับฟอร์มและเนื้อหาที่นับได้
  • ListView.builder สร้างเฉพาะที่มองเห็น เหมาะกับรายการที่โตได้
  • ถามว่าจำนวนรายการมาจากไหน ถ้ามาจาก API ให้ใช้ตัวหลังเสมอ
  • พื้นที่เลื่อนต้องมีขอบเขต — ครอบด้วย Expanded
  • อย่าให้มีพื้นที่เลื่อนซ้อนกันในแกนเดียว
  • shrinkWrap ทำให้ error หายแต่เสียประโยชน์ของ lazy
  • ฟอร์มควรอยู่ในพื้นที่เลื่อนได้เสมอ เพราะแป้นพิมพ์กินพื้นที่
  • ปุ่มสำคัญควรอยู่นอกพื้นที่เลื่อน

บทถัดไป: 2.7 จะลงรายละเอียดการใช้ ListView และ GridView ให้ถูกวิธี ทั้งเรื่องตัวคั่น สถานะว่าง และการเลือกจำนวนคอลัมน์ตามขนาดจอ
