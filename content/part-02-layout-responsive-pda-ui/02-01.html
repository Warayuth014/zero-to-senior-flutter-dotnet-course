1. ปัญหาที่บทนี้แก้

ใน Part 1 เราไม่เคยกำหนดขนาดอะไรเลย ปล่อยให้ Flutter จัดการ พอเริ่มทำหน้าจอจริงจะเจอสองอาการทันที

  • แถบสีเหลืองดำพาดหน้าจอพร้อมข้อความ RenderFlex overflowed by 42 pixels
  • ข้อความว่า Vertical viewport was given unbounded height

ทั้งสองมาจากกฎเดียวกัน และเมื่อเข้าใจกฎนี้แล้ว ปัญหา layout ทั้งหมดใน Part นี้จะกลายเป็นเรื่องที่วิเคราะห์ได้ ไม่ใช่เรื่องที่ต้องเดา

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
constraintข้อจำกัดที่แม่บอกลูกว่า “เธอมีขนาดได้ในช่วงนี้”
sizeขนาดที่ลูกเลือกจริง
tightช่วงที่บีบจนเหลือค่าเดียว — ลูกไม่มีทางเลือก
looseช่วงที่ยังเลือกได้ — ลูกจะเล็กกว่าก็ได้
unboundedไม่มีขีดจำกัดด้านนั้น เช่นในพื้นที่ที่เลื่อนได้
overflowลูกใหญ่เกินพื้นที่ที่แม่มีให้

3. Mental model: กฎสามข้อที่อธิบายทุกอย่าง

จำสามประโยคนี้ให้ขึ้นใจ
  1. ข้อจำกัดไหลลง — แม่บอกลูกว่ามีพื้นที่ได้เท่าไร
  2. ขนาดไหลขึ้น — ลูกเลือกขนาดของตัวเองแล้วบอกกลับ
  3. แม่เป็นคนวางตำแหน่ง — ลูกไม่มีสิทธิ์เลือกว่าตัวเองอยู่ตรงไหน

เปรียบเทียบกับการจัดของในคลัง: หัวหน้าบอกว่า “ชั้นนี้กว้างไม่เกิน 2 เมตร” (ข้อจำกัดไหลลง) พนักงานจัดของแล้วรายงานว่าใช้ไป 1.5 เมตร (ขนาดไหลขึ้น) จากนั้นหัวหน้าตัดสินว่าจะวางกองนี้ชิดซ้ายหรือกลาง (แม่วางตำแหน่ง)

ผลที่ตามมาซึ่งสำคัญมาก: widget ไม่มีทางรู้ว่าตัวเองอยู่ตรงไหนบนหน้าจอ และไม่มีทางบังคับให้ตัวเองใหญ่เกินที่แม่อนุญาต ถ้าอยากเปลี่ยนขนาด ต้องไปแก้ที่แม่ ไม่ใช่ที่ตัวมันเอง

4. tight กับ loose

BoxConstraints(
  minWidth: 0,     maxWidth: 360,     // loose — เลือกได้ 0 ถึง 360
  minHeight: 100,  maxHeight: 100,    // tight — ต้องเป็น 100 เท่านั้น
)
widgetส่งข้อจำกัดแบบไหนให้ลูก
SizedBox(width: 48, height: 48)tight ทั้งสองด้าน — ลูกต้องเป็น 48×48
Centerloose — ลูกจะเล็กแค่ไหนก็ได้ แล้วจัดกลางให้
Expandedtight ตามพื้นที่ที่เหลือ
Paddingส่งต่อของแม่ แต่หักระยะขอบออก
ConstrainedBoxเพิ่มข้อจำกัดของตัวเองเข้าไปผสม

นี่อธิบายเรื่องที่คนใหม่งงบ่อยที่สุด — ทำไมใส่ width ให้ Container แล้วบางทีไม่มีผล คำตอบคือถ้าแม่ส่ง tight constraint มา Container ไม่มีสิทธิ์เลือกขนาดเอง ค่าที่เราใส่จึงถูกละเลย

5. unbounded: ที่มาของ error ที่งงที่สุด

พื้นที่ที่เลื่อนได้ (เช่น ListView) ส่งข้อจำกัดแบบ “ไม่จำกัด” ในทิศที่เลื่อน เพราะเนื้อหาจะยาวเท่าไรก็ได้

SingleChildScrollView(
  child: Column(
    children: [
      Expanded(child: Text('...')),   // พังทันที
    ],
  ),
)

เหตุผล: Expanded แปลว่า “ขอพื้นที่ที่เหลือทั้งหมด” แต่ในพื้นที่ที่เลื่อนได้ ความสูงไม่มีปลายทาง จึงไม่มี “ที่เหลือ” ให้คำนวณ Flutter จึงโยน error แทนที่จะเดาให้

ข้อความ errorแปลว่า
Vertical viewport was given unbounded heightเอาสิ่งที่เลื่อนได้ไปใส่ในที่ที่ความสูงไม่จำกัด
RenderFlex children have non-zero flex but incoming height constraints are unboundedใช้ Expanded ในที่ที่ไม่มีขอบเขต

ทางแก้คือทำให้มีขอบเขต — ครอบด้วย Expanded หรือ SizedBox ที่ระบุความสูง หรือใช้ ListView ตัวเดียวแทนการซ้อนกัน

6. ดูของจริงใน lab

Set-Location .\labs\flutter_wms_companion

เปิด lib/layout_basics/layout_basics_app.dart แล้วดูโครงหลัก

Column(
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: [
    SummaryBar(...),                    // สูงเท่าที่เนื้อหาต้องการ
    const SizedBox(height: 12),         // ระยะห่างคงที่
    Expanded(                           // กินพื้นที่ที่เหลือทั้งหมด
      child: ListView.builder(...),
    ),
  ],
)

อ่านตามกฎสามข้อ: Column วัดลูกสองตัวแรกก่อน (แถบสรุปกับช่องว่าง) แล้วจึงรู้ว่าเหลือพื้นที่เท่าไร จากนั้นส่ง tight constraint ตามพื้นที่ที่เหลือให้ Expanded — ซึ่งทำให้ ListView ได้ความสูงที่แน่นอนและเลื่อนภายในตัวเองได้

ถ้าลบ Expanded ออก จะได้ error unbounded height ทันที เพราะ Column ในทิศแนวตั้งไม่ได้จำกัดความสูงให้ลูกโดยอัตโนมัติ ลองทำดูเพื่อเห็นด้วยตา

7. วิธีไล่หาสาเหตุอย่างเป็นระบบ

  1. อ่านชื่อ widget ในข้อความ error — Flutter บอกตัวที่มีปัญหาและตัวที่เกี่ยวข้องมาให้
  2. ถามว่าใครเป็นคนกำหนดขนาด ไล่ขึ้นไปตามสายแม่จนเจอตัวที่ตัดสิน
  3. ถามว่าอะไรควรตรึง อะไรควรยืด อะไรควรเลื่อน ตอบสามข้อนี้ก่อนแล้วค่อยเลือก widget
  4. ทดสอบบนขนาดที่แคบที่สุดที่ต้องรองรับ ไม่ใช่บนหน้าต่างเบราว์เซอร์กว้าง ๆ
สิ่งที่ไม่ควรทำเป็นทางแก้แรก: ครอบทุกอย่างด้วย SingleChildScrollView เพื่อให้แถบเหลืองหายไป — มันซ่อนปัญหาว่าใครควรเป็นเจ้าของพื้นที่ และทำให้เกิดพื้นที่เลื่อนซ้อนกันซึ่งใช้งานยากมากบน PDA

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
RenderFlex overflowed by N pixelsผลรวมลูกใหญ่กว่าพื้นที่ให้ลูกที่ยืดได้ห่อด้วย Expanded (2.3)
Vertical viewport was given unbounded heightที่เลื่อนได้อยู่ในที่ที่ไม่มีขอบเขตครอบด้วย Expanded หรือกำหนดความสูง
ใส่ width ให้ Container แล้วไม่มีผลแม่ส่ง tight constraint มาไปแก้ที่แม่ หรือใช้ Align/Center คั่น
CrossAxisAlignment.stretch แล้วไม่ยืดไม่มีขอบเขตในแกนขวางทำให้แกนขวางมีขอบเขตก่อน
ทำงานดีบนเบราว์เซอร์ แต่ล้นบน PDAทดสอบบนจอกว้างอย่างเดียวทดสอบที่ความกว้าง 320–360 เสมอ

9. แบบฝึกหัด

หน้าจอหนึ่งต้องมีสามส่วนเรียงจากบนลงล่าง

  • หัวข้อ สูงตามเนื้อหา
  • รายการที่เลื่อนได้ กินพื้นที่ที่เหลือทั้งหมด
  • แถบปุ่มด้านล่าง สูง 56 ตรึงอยู่กับที่เสมอ
  1. เขียนโครงโค้ด
  2. อธิบายว่าทำไมไม่ควรคำนวณความสูงเองด้วยการเอาความสูงจอมาลบ
  3. ถ้าเปลี่ยนรายการเป็น Column ธรรมดาแทน ListView จะเกิดอะไรขึ้น
ดูแนวคำตอบและเหตุผล
Column(
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: [
    const ScreenHeader(),                  // สูงตามเนื้อหา
    Expanded(                              // กินที่เหลือ
      child: ListView.builder(
        itemCount: lines.length,
        itemBuilder: (context, index) => LineCard(line: lines[index]),
      ),
    ),
    const SizedBox(
      height: 56,
      child: ActionBar(),                  // ตรึงความสูง
    ),
  ],
)

ข้อ 2 — ทำไมไม่คำนวณเอง

วิธีที่คนใหม่มักทำคือ height: MediaQuery.of(context).size.height - 72 - 56 ซึ่งดูเหมือนได้ผล แต่จะพังทันทีเมื่อ

  • แป้นพิมพ์ขึ้นมาบังจอ — พื้นที่จริงเล็กลงแต่ตัวเลขไม่เปลี่ยน
  • อุปกรณ์มีรอยบากหรือแถบล่างของระบบ
  • ผู้ใช้ตั้งขนาดตัวอักษรใหญ่ขึ้น หัวข้อจึงสูงกว่า 72
  • หน้าจอนี้ถูกเอาไปใส่ในแท็บบางส่วนของจอ ไม่ได้เต็มจอ

ส่วน Expanded ถามพื้นที่จริงที่ได้รับมาตามกฎข้อ 1 จึงถูกต้องเสมอในทุกกรณีข้างต้นโดยไม่ต้องแก้อะไร — นี่คือความหมายของการทำงานร่วมกับระบบ constraint แทนที่จะสู้กับมัน

ข้อ 3 — ถ้าใช้ Column แทน ListView

จะเกิดสองปัญหา ปัญหาแรกคือเมื่อรายการยาวเกินพื้นที่จะเกิด RenderFlex overflowed เพราะ Column เลื่อนไม่ได้ ปัญหาที่สองที่ร้ายกว่าคือ Column สร้างลูกทุกตัวพร้อมกัน ถ้ามีห้าพันรายการก็สร้างครบห้าพันชิ้นทันที ในขณะที่ ListView.builder สร้างเฉพาะที่มองเห็น — เรื่องนี้จะลงลึกใน 2.6 และ 2.7

ลองต่อ: ใน lab ให้ลบ Expanded ที่ครอบ ListView ออก แล้วรัน อ่านข้อความ error ให้ครบทั้งย่อหน้า จะเห็นว่า Flutter บอกทั้งชื่อ widget ที่มีปัญหาและแนะนำทางแก้มาให้ — การอ่าน error ให้จบเป็นทักษะที่ประหยัดเวลาได้มากที่สุดใน Part นี้

10. สรุปท้ายบท

  • ข้อจำกัดไหลลง ขนาดไหลขึ้น แม่เป็นคนวางตำแหน่ง
  • widget ไม่มีทางบังคับให้ตัวเองใหญ่เกินที่แม่อนุญาต
  • tight คือไม่มีทางเลือก loose คือเลือกได้
  • ที่เลื่อนได้ส่งขอบเขตแบบไม่จำกัดในทิศที่เลื่อน
  • Expanded ต้องอยู่ในที่ที่มีขอบเขต ไม่งั้นพัง
  • อย่าคำนวณความสูงเองจากขนาดจอ ให้ใช้ Expanded
  • ตอบให้ได้ว่าอะไรตรึง อะไรยืด อะไรเลื่อน ก่อนเลือก widget
