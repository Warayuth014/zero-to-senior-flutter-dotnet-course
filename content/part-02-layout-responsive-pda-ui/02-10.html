ระดับ: กลางใช้เวลา: 35–45 นาทีลงมือทำ: ทำหน้าจอเดียวให้ใช้ได้ทั้ง PDA และแท็บเล็ต
ต้องผ่านอะไรมาก่อน: 2.1 (ข้อจำกัดไหลลง) และ 2.9 (MediaQuery)
จบบทนี้แล้วจะทำได้: แยกได้ว่าเมื่อไหร่ใช้ LayoutBuilder เมื่อไหร่ใช้ MediaQuery และวางจุดตัดขนาดจอที่มีเหตุผลรองรับ

1. ปัญหาที่บทนี้แก้

ใน 2.9 เราเจอประโยคว่า MediaQuery บอกเรื่องหน้าต่างทั้งบาน ส่วน LayoutBuilder บอกเรื่องพื้นที่ที่ widget ได้รับจริง บทนี้จะทำให้ความต่างนั้นเป็นเรื่องที่ใช้ตัดสินใจได้

ความต่างนี้สำคัญเพราะหน้าจอเดียวกันอาจถูกเอาไปวางในที่ที่แคบกว่าจอ เช่นแผงด้านข้างบนแท็บเล็ต ถ้าเราตัดสินใจจากขนาดจอทั้งเครื่อง เราจะได้ layout ที่ผิด

5. เปลี่ยนโครง ไม่ใช่ย่อทุกอย่าง

ความผิดพลาดที่พบบ่อยคือพอจอแคบก็ลดขนาดตัวอักษรและปุ่มลงให้พอดี ซึ่งทำให้อ่านยากและกดไม่โดน โดยเฉพาะบน PDA ที่ผู้ใช้ใส่ถุงมือ

ลำดับที่ควรทำเมื่อพื้นที่ไม่พอ

  1. เปลี่ยนทิศการเรียง — จาก Row เป็น Column เหมือนที่แถบสรุปใน lab ทำ
  2. ลดจำนวนคอลัมน์ — จาก 3 เหลือ 2
  3. ซ่อนข้อมูลรอง — เอาคำอธิบายออก เก็บรหัสและจำนวนไว้
  4. ลดจำนวนบรรทัด — จาก 2 บรรทัดเหลือ 1 พร้อมจุดไข่ปลา
  5. ลดขนาดตัวอักษร — ทางเลือกสุดท้าย และต้องมีขั้นต่ำที่ยังอ่านออก
ห้ามลดขนาดปุ่มลงต่ำกว่า 48 ไม่ว่าจอจะแคบแค่ไหน — ถ้าพื้นที่ไม่พอสำหรับปุ่มสามปุ่ม ให้เหลือสองปุ่มแล้วย้ายที่เหลือไปเมนู ไม่ใช่ย่อทั้งสามปุ่มให้เล็กลง เหตุผลเต็ม ๆ อยู่ใน 2.13

6. ตัวเลข breakpoint มาจากไหน

อย่าคัดตัวเลขจากบทความออกแบบเว็บมาใช้ตรง ๆ ให้คำนวณจากเนื้อหาจริง

ความกว้างขั้นต่ำที่ช่องหนึ่งใช้ได้จริง   = 160
ช่องว่างระหว่างช่อง                     =  12
ระยะขอบซ้ายขวา                        =  12 × 2

สองคอลัมน์ต้องการ = 160×2 + 12 + 24 = 356
→ ต่ำกว่า 356 ต้องเหลือคอลัมน์เดียว

ใน lab เราตั้ง Breakpoints.compact = 480 ซึ่งเป็นค่าที่เผื่อไว้สำหรับข้อความไทยที่ยาวกว่าอังกฤษและผู้ใช้ที่ตั้งตัวอักษรใหญ่

สิ่งที่สำคัญกว่าตัวเลขคือ ตัวเลขนั้นมีชื่อและมีเหตุผลกำกับ ตามที่ทำใน 2.4 — เมื่อวันหนึ่งต้องปรับ จะมีคนกล้าแก้เพราะรู้ว่าค่านี้มาจากไหน

7. อย่าให้ breakpoint กระจายทั่วโปรเจกต์

// แย่ — เลข 480 โผล่ในสิบไฟล์ และบางไฟล์ใช้ 460
if (MediaQuery.sizeOf(context).width < 480) { ... }

// ดี — มีที่เดียว มีชื่อ มีเหตุผล
if (constraints.maxWidth < Breakpoints.compact) { ... }

เมื่อโปรเจกต์โตขึ้น อาจรวมการตัดสินใจทั้งชุดไว้ในที่เดียว

class WarehouseLayout {
  const WarehouseLayout({
    required this.columns,
    required this.stacked,
    required this.titleMaxLines,
  });

  factory WarehouseLayout.fromWidth(double width) {
    if (width < Breakpoints.compact) {
      return const WarehouseLayout(columns: 1, stacked: true, titleMaxLines: 1);
    }
    return const WarehouseLayout(columns: 2, stacked: false, titleMaxLines: 2);
  }

  final int columns;
  final bool stacked;
  final int titleMaxLines;
}

ข้อดีคือการตัดสินใจทั้งหมดอยู่ที่เดียว อ่านรวดเดียวจบ และทดสอบได้โดยไม่ต้องประกอบหน้าจอ — เพราะมันเป็นแค่ฟังก์ชันธรรมดาตามหลักใน D1.20

8. ข้อมูลต้องไม่หายเมื่อเปลี่ยนโครง

เมื่อผู้ใช้หมุนจอกลางคัน layout เปลี่ยน แต่สิ่งที่พิมพ์ไว้ต้องไม่หาย

// อันตราย — สลับ widget คนละชนิดตามขนาด
if (isCompact) {
  return CompactForm(...);      // State คนละตัวกับด้านล่าง
} else {
  return WideForm(...);         // สลับแล้วข้อมูลหาย
}

// ปลอดภัย — widget ตัวเดียว รับค่าบอกโหมด
return ScanForm(compact: isCompact);

เหตุผลตรงกับ 1.3: เมื่อชนิดของ widget เปลี่ยน Flutter ทิ้ง Element เดิมทั้งกิ่ง และข้อมูลที่อยู่กับ Element นั้นก็หายไปด้วย

ถ้าจำเป็นต้องสลับโครงจริง ๆ ให้ย้ายข้อมูลขึ้นไปเก็บที่แม่ซึ่งอยู่เหนือจุดที่สลับ ตามหลักใน 1.5

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
การ์ดล้นเมื่อเอาไปวางในแผงแคบใช้ MediaQuery อ่านขนาดจอทั้งเครื่องเปลี่ยนเป็น LayoutBuilder
ข้อความที่พิมพ์หายเมื่อหมุนจอสลับเป็น widget คนละชนิดใช้ widget ตัวเดียวแล้วส่งค่าบอกโหมด
เลข breakpoint ไม่ตรงกันในแต่ละไฟล์ไม่มีที่รวมตั้งชื่อไว้ที่เดียว
จอแคบแล้วปุ่มเล็กจนกดไม่โดนย่อทุกอย่างแทนที่จะเปลี่ยนโครงทำตามลำดับในหัวข้อ 5
ทำงานดีบนจอเดียว แต่พังที่ค่าใกล้จุดตัดไม่ได้ทดสอบที่ขอบทดสอบที่ 479 และ 481
ยิง API ใหม่เมื่อหมุนจอโครงที่สลับไปสร้าง State ใหม่ย้ายข้อมูลขึ้นเหนือจุดสลับ

10. แบบฝึกหัด

แดชบอร์ดหนึ่งใช้โค้ดนี้ และทำงานถูกต้องเมื่อเปิดเต็มจอบนแท็บเล็ตกว้าง 900

final width = MediaQuery.sizeOf(context).width;
final columns = width < 420 ? 2 : (width < 840 ? 3 : 4);
return WarehouseGrid(columns: columns);

วันหนึ่งทีมเอาแดชบอร์ดนี้ไปวางในแผงซ้ายของหน้าจอแบบรายการ-รายละเอียด ซึ่งแผงกว้างแค่ 340 แล้วเกิดแถบสีเหลืองดำ

  1. อธิบายว่าทำไมถึงล้น
  2. แก้ให้ถูก
  3. อธิบายว่าส่วนไหนของหน้าจอที่ยังควรใช้ MediaQuery อยู่
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ทำไมล้น

MediaQuery.sizeOf(context).width คืนความกว้างของ หน้าต่างทั้งบาน ซึ่งยังเป็น 900 แม้แดชบอร์ดจะถูกวางในแผงกว้าง 340 โค้ดจึงคำนวณได้ 4 คอลัมน์ แล้วพยายามยัดสี่ช่องลงในพื้นที่ 340 ซึ่งไม่พอ

สิ่งที่ทำให้บั๊กนี้อันตรายคือ โค้ดไม่ได้เปลี่ยนเลย — มันเคยถูกและยังดูถูกอยู่ แต่ผิดเพราะบริบทที่ถูกใช้เปลี่ยนไป

ข้อ 2 — แก้ให้ถูก

LayoutBuilder(
  builder: (context, constraints) {
    final width = constraints.maxWidth;      // พื้นที่ที่ได้รับจริง
    final columns = width < 420 ? 2 : (width < 840 ? 3 : 4);
    return WarehouseGrid(columns: columns);
  },
)

เปลี่ยนแค่แหล่งที่มาของตัวเลข ตรรกะเดิมทั้งหมดยังใช้ได้ — ตอนนี้แผง 340 จะได้ 2 คอลัมน์ และเมื่อเปิดเต็มจอ 900 ก็ยังได้ 4 เหมือนเดิม

ข้อ 3 — ส่วนที่ยังควรใช้ MediaQuery

เรื่องใช้อะไรเหตุผล
จำนวนคอลัมน์LayoutBuilderขึ้นกับพื้นที่ที่ได้รับ
ระยะหลบรอยบากและแถบระบบMediaQuery ผ่าน SafeAreaเป็นเรื่องของอุปกรณ์ ไม่ใช่ของแผง
ระยะเผื่อแป้นพิมพ์MediaQuery.viewInsetsOfแป้นพิมพ์บังทั้งหน้าต่าง
ขนาดตัวอักษรที่ผู้ใช้ตั้งMediaQueryเป็นการตั้งค่าระดับระบบ

ข้อสังเกตที่สำคัญที่สุด: ทั้งสองอย่างใช้ร่วมกันในหน้าจอเดียวได้และควรใช้ด้วย — ไม่ใช่เลือกอย่างใดอย่างหนึ่งไปทั้งแอป โดยวาง SafeArea ไว้ระดับหน้าจอ และวาง LayoutBuilder ไว้ตรงที่ต้องตัดสินใจเรื่องโครง เหมือนที่ lab ทำ

บทเรียนที่ใช้ได้ต่อไป: เวลาเขียน widget ที่จะถูกเอาไปใช้ซ้ำ ให้ถามเสมอว่า “ถ้ามีคนเอาฉันไปวางในที่แคบกว่านี้ ฉันยังทำงานถูกไหม” — ถ้าคำตอบขึ้นกับขนาดจอทั้งเครื่อง แปลว่ายังผูกกับบริบทมากเกินไป

ลองต่อ: เขียนเทสต์ที่ครอบแดชบอร์ดด้วย SizedBox(width: 340) แล้วตรวจว่าได้ 2 คอลัมน์ — ทำได้โดยไม่ต้องจำลองขนาดจอเลย ซึ่งเป็นข้อดีอีกอย่างของ LayoutBuilder

11. สรุปท้ายบท

  • ตัดสินใจเรื่อง layout ใช้ LayoutBuilder เรื่องอุปกรณ์ใช้ MediaQuery
  • MediaQuery ยังบอกความกว้างจอเต็มแม้ widget จะอยู่ในแผงแคบ
  • เมื่อพื้นที่ไม่พอ ให้เปลี่ยนโครงก่อน ลดขนาดตัวอักษรเป็นทางสุดท้าย
  • ห้ามลดขนาดปุ่มต่ำกว่า 48
  • คำนวณ breakpoint จากเนื้อหาจริง และตั้งชื่อไว้ที่เดียว
  • อย่าสลับเป็น widget คนละชนิด เพราะข้อมูลจะหาย
  • ทดสอบที่ค่าใกล้จุดตัดทั้งสองฝั่ง
