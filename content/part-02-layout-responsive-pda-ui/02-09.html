ระดับ: เริ่มต้น–กลางใช้เวลา: 30–40 นาทีลงมือทำ: หลบรอยบาก แถบระบบ และแป้นพิมพ์
ต้องผ่านอะไรมาก่อน: 1.7 (.of(context)) และ 2.6 (แป้นพิมพ์กับพื้นที่เลื่อน)
จบบทนี้แล้วจะทำได้: ใช้ SafeArea และ MediaQuery ได้ถูกที่ และเข้าใจว่าทำไมหน้าจอที่ดูดีบนเครื่องหนึ่งกลับผิดบนอีกเครื่อง

1. ปัญหาที่บทนี้แก้

พื้นที่หน้าจอที่เราใช้ได้จริง ไม่เท่ากับขนาดจอทั้งหมด เพราะระบบปฏิบัติการกินไปบางส่วน

  • รอยบากหรือกล้องหน้าด้านบน
  • แถบนำทางหรือเส้นลากด้านล่าง
  • แป้นพิมพ์ที่ขึ้นมาบังครึ่งจอ

ที่ทำให้ปัญหานี้ยากคือ เครื่องพัฒนามักไม่มีสิ่งเหล่านี้ โค้ดจึงดูถูกต้องจนกว่าจะเอาไปลงบน PDA จริง

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
MediaQueryข้อมูลของหน้าต่างทั้งบาน เช่นขนาด ระยะที่ระบบกิน
SafeAreawidget ที่หลบพื้นที่ที่ระบบกินให้อัตโนมัติ
paddingระยะที่ระบบบังอยู่ตอนนี้
viewInsetsระยะที่ถูกบังเต็ม เช่นแป้นพิมพ์
textScalerตัวคูณขนาดตัวอักษรที่ผู้ใช้ตั้งไว้

3. Mental model: ขนาดจอ ไม่เท่ากับพื้นที่ที่เราได้

┌─────────────────────┐  ← ขนาดจอทั้งหมด (MediaQuery.size)
│ ▓▓▓ รอยบาก ▓▓▓▓▓▓▓ │  ← padding.top
├─────────────────────┤
│                     │
│   พื้นที่ที่เราได้จริง   │  ← SafeArea ให้ส่วนนี้
│                     │
├─────────────────────┤
│ ▓▓ แถบนำทาง ▓▓▓▓▓ │  ← padding.bottom
└─────────────────────┘
ประโยคเดียวที่ต้องจำ: MediaQuery บอกเรื่องของ หน้าต่างทั้งบาน ส่วน LayoutBuilder (บทหน้า) บอกเรื่องของ พื้นที่ที่ widget ตัวนี้ได้รับจริง — สองอย่างนี้ต่างกัน และเลือกผิดจะพังเมื่อหน้าจอถูกเอาไปวางในแผงย่อย

4. SafeArea: ใช้ให้ถูกที่

Scaffold(
  appBar: AppBar(title: const Text('รับเข้าสินค้า')),
  body: SafeArea(
    child: ...,
  ),
)

ใน lab เราใส่ SafeArea ครอบเนื้อหาของ Scaffold ไว้ ซึ่งเป็นตำแหน่งที่ถูก

เลือกด้านได้ ซึ่งจำเป็นบ่อยกว่าที่คิด

SafeArea(
  top: false,        // AppBar จัดการด้านบนให้แล้ว ไม่ต้องเผื่อซ้ำ
  child: ActionBar(),
)
สถานการณ์ตั้งอย่างไร
มี AppBar อยู่แล้วtop: false
แถบปุ่มด้านล่างtop: false เผื่อเฉพาะล่าง
หน้าจอเต็มจอไม่มี AppBarใช้ค่าเริ่มต้น เผื่อทุกด้าน
อยากมีระยะขอบขั้นต่ำแม้ไม่มีรอยบากใส่ minimum: EdgeInsets.symmetric(horizontal: 12)
การซ้อน SafeArea หลายชั้นไม่ทำให้ระยะทบกัน เพราะชั้นในรู้ว่าชั้นนอกเผื่อไปแล้ว — แต่ถ้าเราไปบวก MediaQuery.paddingOf(context).bottom เองด้วยมือ จะทบกันจริง ทำให้เกิดช่องว่างใหญ่ผิดปกติที่หาสาเหตุยาก

5. แป้นพิมพ์: viewInsets

เมื่อแป้นพิมพ์ขึ้น Scaffold จะย่อพื้นที่ให้อัตโนมัติอยู่แล้ว จึงไม่ต้องทำอะไรเพิ่มในกรณีปกติ

กรณีที่ต้องจัดการเองคือแผ่นเลื่อนขึ้นจากด้านล่าง ซึ่งไม่ได้อยู่ใน Scaffold

final insets = MediaQuery.viewInsetsOf(context);

return AnimatedPadding(
  duration: const Duration(milliseconds: 180),
  padding: EdgeInsets.only(bottom: insets.bottom),   // ยกขึ้นเหนือแป้นพิมพ์
  child: const ScanForm(),
);
ค่าบอกอะไรลดลงเมื่อแป้นพิมพ์ขึ้นไหม
paddingระยะที่ระบบบังตอนนี้ลด (เพราะแป้นพิมพ์บังแทน)
viewPaddingระยะที่ระบบบังโดยพื้นฐานไม่ลด
viewInsetsระยะที่ถูกบังเต็มเพิ่มขึ้นตามความสูงแป้นพิมพ์

ความต่างสามข้อนี้อธิบายอาการที่งงบ่อย: ทำไมพอแป้นพิมพ์ขึ้น ปุ่มที่เผื่อระยะไว้ด้วย padding.bottom ถึงขยับผิดที่ — เพราะ padding.bottom กลายเป็น 0 ไปแล้ว

6. อ่านเฉพาะค่าที่ต้องใช้

// ดี — ผูกกับค่าเดียว
final size = MediaQuery.sizeOf(context);
final insets = MediaQuery.viewInsetsOf(context);

// ไม่ดี — ผูกกับทุกค่า
final media = MediaQuery.of(context);

ทบทวนจาก 1.14: การเรียก .of(context) คือการสมัครรับข่าว ถ้าเรียก MediaQuery.of ทั้งก้อน widget จะถูกวาดใหม่ทุกครั้งที่ อะไรก็ตาม ใน MediaQuery เปลี่ยน รวมถึงแป้นพิมพ์ที่กำลังเลื่อนขึ้นทีละพิกเซล

การใช้ sizeOf จะวาดใหม่เฉพาะเมื่อขนาดเปลี่ยนจริง ซึ่งลดงานลงมากบน PDA

7. ขนาดตัวอักษรที่ผู้ใช้ตั้งเอง

MediaQuery ยังบอกด้วยว่าผู้ใช้ตั้งขนาดตัวอักษรไว้เท่าไร ซึ่งเป็นเรื่องที่มักถูกลืมและทำให้หน้าจอพังบนอุปกรณ์ของผู้ใช้จริง

พนักงานคลังที่อายุมากมักตั้งขนาดตัวอักษรไว้ 130–150% ซึ่งทำให้

  • ช่องที่ล็อกความสูงไว้เกิดแถบสีเหลืองดำ (ตามที่เตือนใน 2.7)
  • ปุ่มที่มีข้อความยาวถูกตัด
  • รายการที่คำนวณจำนวนแถวไว้แสดงได้น้อยลง
อย่าปิดการปรับขนาดตัวอักษร ด้วยการบังคับตัวคูณเป็น 1.0 เพื่อให้หน้าจอไม่พัง — นั่นคือการแก้ปัญหาด้วยการทำให้ผู้ใช้ที่ต้องการตัวอักษรใหญ่ใช้งานไม่ได้ ให้แก้ที่ layout ให้ยืดหยุ่นแทน

วิธีทดสอบคือตั้งขนาดตัวอักษรในระบบให้ใหญ่สุด แล้วเปิดแอปดูทุกหน้าจอ — ควรทำก่อนส่งมอบทุกครั้ง

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
หัวข้อโดนรอยบากบังไม่มี SafeAreaครอบเนื้อหาของ Scaffold
ปุ่มล่างโดนแถบนำทางบังปุ่มอยู่นอก SafeAreaครอบเฉพาะปุ่มด้วย SafeArea(top: false)
มีช่องว่างใหญ่ด้านบนผิดปกติมี SafeArea แล้วยังบวก padding.top เองอีกเลือกอย่างใดอย่างหนึ่ง
เผื่อระยะด้วย padding.bottom แล้วเพี้ยนตอนแป้นพิมพ์ขึ้นpadding ลดลงเมื่อแป้นพิมพ์บังแทนใช้ viewPadding หรือ SafeArea
แผ่นเลื่อนขึ้นถูกแป้นพิมพ์บังไม่ได้เผื่อ viewInsets.bottomใส่ระยะล่างตามค่านั้น
หน้าจอวาดใหม่รัวขณะแป้นพิมพ์เลื่อนขึ้นใช้ MediaQuery.of ทั้งก้อนใช้ sizeOf หรือ paddingOf
เนื้อหาล้นเมื่อผู้ใช้ตั้งตัวอักษรใหญ่ล็อกความสูงตายตัวทำให้ยืดหยุ่น อย่าปิดการปรับขนาด

9. แบบฝึกหัด

หน้าจอรับเข้าสินค้ามีโครงตามนี้ และเจอปัญหาสองอย่างบน PDA จริง

Scaffold(
  appBar: AppBar(title: const Text('รับเข้าสินค้า')),
  body: SafeArea(
    child: Column(
      children: [
        const ScanForm(),
        Expanded(child: ListView.builder(...)),
      ],
    ),
  ),
  bottomNavigationBar: const ConfirmBar(),
)
  • ปัญหาที่ 1: ปุ่มยืนยันโดนเส้นลากด้านล่างของระบบบังบางส่วน
  • ปัญหาที่ 2: เมื่อแป้นพิมพ์ขึ้น ช่องกรอกล่างสุดของฟอร์มถูกบัง
  1. อธิบายว่าทำไม SafeArea ที่มีอยู่ถึงไม่ช่วยปัญหาที่ 1
  2. แก้ปัญหาที่ 1
  3. แก้ปัญหาที่ 2
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ทำไม SafeArea ไม่ช่วย

เพราะ ConfirmBar อยู่ใน bottomNavigationBar: ซึ่งเป็นคนละที่กับ body: ที่ SafeArea ครอบอยู่ ตาม 1.7 การครอบ widget หนึ่งมีผลเฉพาะกับสิ่งที่อยู่ ใต้มัน ใน tree เท่านั้น — bottomNavigationBar เป็นพี่น้องกับ body ไม่ใช่ลูก

นี่เป็นตัวอย่างที่ดีว่าทำไมต้องเข้าใจ tree จริงตอนรัน ไม่ใช่ดูจากลำดับในไฟล์

ข้อ 2 — แก้ปัญหาปุ่มโดนบัง

bottomNavigationBar: const SafeArea(
  top: false,              // ด้านบนมี AppBar และ body จัดการแล้ว
  child: ConfirmBar(),
),

ใส่ top: false เพราะถ้าเผื่อด้านบนด้วยจะได้ช่องว่างเปล่า ๆ เหนือแถบปุ่มโดยไม่มีเหตุผล

ข้อ 3 — แก้ปัญหาแป้นพิมพ์บังช่องกรอก

body: SafeArea(
  child: Column(
    children: [
      // ให้ฟอร์มเลื่อนได้ เมื่อพื้นที่หดจากแป้นพิมพ์
      Flexible(
        child: SingleChildScrollView(child: const ScanForm()),
      ),
      Expanded(child: ListView.builder(...)),
    ],
  ),
),

เหตุผลตรงกับ 2.6 หัวข้อ 6: Scaffold ย่อพื้นที่ของ body ให้อัตโนมัติเมื่อแป้นพิมพ์ขึ้นอยู่แล้ว แต่ถ้าฟอร์มไม่ได้อยู่ในพื้นที่ที่เลื่อนได้ มันก็แค่ถูกบีบจนล้น ไม่ได้เลื่อนขึ้นมาให้เห็น

ทำไมใช้ Flexible ไม่ใช่ Expanded: ตาม 2.3 — Expanded จะบังคับให้ฟอร์มกินพื้นที่เต็มส่วนแบ่งเสมอ แม้ตอนที่ยังไม่มีแป้นพิมพ์และฟอร์มสั้น ทำให้เหลือที่ให้รายการน้อยลงโดยไม่จำเป็น ส่วน Flexible ให้ฟอร์มสูงตามเนื้อหาเมื่อพื้นที่พอ และหดลงพร้อมเลื่อนได้เมื่อพื้นที่ไม่พอ

สิ่งที่ห้ามทำในทั้งสองข้อ: เผื่อระยะด้วยตัวเลขคงที่อย่าง padding: EdgeInsets.only(bottom: 34) เพราะความสูงของเส้นลากด้านล่างและแป้นพิมพ์ต่างกันไปตามอุปกรณ์ ภาษา และการตั้งค่าของผู้ใช้ — ตัวเลขที่ถูกบนเครื่องหนึ่งจะผิดบนอีกเครื่องเสมอ

ลองต่อ: เปิดแอปบนอุปกรณ์จำลองที่มีรอยบาก แล้วสลับไปแบบไม่มีรอยบาก โดยไม่แก้โค้ดเลย — ถ้าใช้ SafeArea ถูกที่ ทั้งสองแบบจะแสดงผลถูกต้องทันที

10. สรุปท้ายบท

  • ขนาดจอไม่เท่ากับพื้นที่ที่เราได้ใช้จริง
  • SafeArea หลบรอยบากและแถบระบบให้อัตโนมัติ และเลือกด้านได้
  • SafeArea มีผลเฉพาะกับสิ่งที่อยู่ใต้มันใน tree
  • padding ลดลงเมื่อแป้นพิมพ์บังแทน ส่วน viewPadding ไม่ลด
  • viewInsets คือความสูงของแป้นพิมพ์
  • ใช้ sizeOf/paddingOf แทน of เพื่อลดการวาดใหม่
  • อย่าปิดการปรับขนาดตัวอักษร ให้แก้ layout ให้ยืดหยุ่นแทน
  • อย่าเผื่อระยะด้วยตัวเลขคงที่
