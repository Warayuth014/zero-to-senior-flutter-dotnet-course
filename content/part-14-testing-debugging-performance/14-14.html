Debug จากหลักฐาน: เริ่มจาก reproduce ที่เล็กที่สุด เก็บ state/request/timeline แล้วใช้ Inspector, Debugger, Network และ Memory ตามอาการ หลีกเลี่ยงใส่ print แบบไม่มีโครงทั่วแอป

1. Build mode

debug เหมาะ breakpoints/assert/hot reload แต่ performance ไม่แทน release; profile ใช้วัด CPU/GPU/memory ใกล้ของจริง; release ใช้ตรวจพฤติกรรมสุดท้าย ห้ามสรุป jank จาก debug mode

2. Widget Inspector

ใช้ Select Widget, Layout Explorer และ constraints ดู overflow/พื้นที่ว่าง ตรวจ parent ที่ส่ง unbounded constraint, flex/scroll nesting และ repaint boundaries ก่อนแก้ด้วย hard-coded size

3. Debugger

ตั้ง conditional breakpoint ที่ partId/step เฉพาะ, inspect call stack และ watch expression ใช้ pause on uncaught exceptions เพื่อเจอต้นทางก่อน error ถูกแปล หลีกเลี่ยง breakpoint ใน build ที่ถูกเรียกถี่จนทำ timing เปลี่ยน

4. Logging ที่สืบได้

log.info('receive.submit', {
  'operationId': operationId,
  'partId': partId,
  'step': state.step.name,
});

ใส่ correlation/operation ID และ event name แต่ไม่ log JWT, password, serial ส่วนบุคคลหรือ response body ใหญ่

5. Network

ดู method, URL, status, duration, request/response size และ waterfall เปรียบเทียบ operation ID กับ .NET logs จำลอง offline/slow/timeout และตรวจ duplicate calls หลัง rebuild ไม่อ่านเพียงข้อความ error UI

6. CPU/frames

เปิด Performance overlay/DevTools Timeline ใน profile mode บันทึกช่วง reproduce สั้น ๆ แยก UI thread/raster jank แล้วหา expensive build/layout/paint, synchronous JSON/image decode หรือ widget ที่ rebuild เกินจำเป็น

7. Memory

ถ่าย heap snapshot ก่อนเข้า flow, หลังใช้งาน และหลังออก/GC ดู retaining path ของ Store, Timer, StreamSubscription, Controller, Image และ BuildContext การที่ memory สูงครั้งเดียวไม่เท่ากับ leak—ต้องดูวัตถุที่ควรถูกปล่อยแต่ยังถูก retain

8. Debug record

บันทึก device/build/commit, ขั้น reproduce, expected/actual, timestamp, operation ID, screenshot/timeline และ test ที่เพิ่มหลังแก้ เพื่อให้ bug เดิมกลับมาแล้ว CI จับได้
