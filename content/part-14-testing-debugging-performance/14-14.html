จบบทนี้แล้วจะทำได้: หาสาเหตุของปัญหาที่เทสต์จับไม่ได้ ด้วยเครื่องมือที่มากับ Flutter

1. เมื่อเทสต์ไม่พอ

ปัญหาเทสต์จับได้ไหม
ตรรกะผิดได้ ถ้าเขียนไว้
เนื้อหาล้นได้ (14.13)
รั่วได้ (14.11)
ช้าบนเครื่องจริงไม่ได้ — เทสต์รันบนคอมที่เร็วกว่ามาก
กินหน่วยความจำจนถูกปิดไม่ได้
วาดใหม่บ่อยเกินจนกระตุกได้บางส่วน (14.15)

สามแถวล่างต้องดูจากแอปที่ทำงานจริง และ DevTools คือเครื่องมือนั้น

2. เปิดอย่างไร

# แล้วกด 'v' ใน terminal หรือเปิด URL ที่มันพิมพ์ออกมา

ต้องรันในโหมด profile หรือ debug — โหมด release ปิดเครื่องมือส่วนใหญ่ไว้ และตัวเลขประสิทธิภาพในโหมด debug ช้ากว่าของจริงมาก จึงต้องใช้ flutter run --profile เมื่อจะวัดความเร็ว

3. แท็บที่ใช้จริง

แท็บตอบคำถามว่าใช้ตอน
Flutter Inspectorต้นไม้ widget หน้าตาเป็นอย่างไรlayout ไม่เป็นอย่างที่คิด
Performanceเฟรมไหนใช้เวลานานแอปกระตุก
CPU Profilerเวลาหมดไปกับฟังก์ชันไหนช้าแต่ไม่รู้ว่าตรงไหน
Memoryอะไรกินหน่วยความจำแอปถูกปิดเอง
Networkยิงคำขออะไรไปบ้างข้อมูลไม่มา หรือยิงถี่เกิน
Loggingข้อความที่แอปพิมพ์ทั่วไป

สามแท็บแรกใช้บ่อยที่สุด และแท็บ Network มีค่ามากกับแอปที่คุยกับเซิร์ฟเวอร์ตลอดเวลาแบบนี้

5. Performance — หาเฟรมที่ช้า

Flutter ตั้งเป้าที่ 60 เฟรมต่อวินาที ซึ่งแปลว่าแต่ละเฟรมมีเวลา16 มิลลิวินาที

สีในกราฟหมายถึง
แท่งเตี้ยสีน้ำเงินปกติ
แท่งสูงเกินเส้นเฟรมนั้นใช้เกิน 16ms — ผู้ใช้เห็นเป็นการกระตุก
ส่วนสีน้ำเงินเวลาที่ใช้ใน Dart — โค้ดของเรา
ส่วนสีเขียวเวลาที่ใช้วาดจริง — มักเป็นเรื่องของ layout ที่ซับซ้อน

กดที่แท่งที่สูงผิดปกติแล้วดูว่าเวลาหมดไปกับอะไร

สาเหตุที่พบบ่อยแก้อย่างไร
วาดใหม่ทั้งจอทั้งที่เปลี่ยนนิดเดียว14.15
รูปใหญ่ถูกคลายในเฟรมนั้นcacheWidth (13.7)
สร้าง widget ทั้งลิสต์พร้อมกันListView.builder (14.16)
คำนวณหนักใน buildย้ายออกไปคำนวณครั้งเดียว

6. Memory — หาว่าอะไรไม่ถูกเก็บ

วิธีที่ได้ผลที่สุดคือเทียบสองภาพ

1. เปิดจอที่สงสัย แล้วกดปุ่มถ่ายภาพหน่วยความจำ
2. เปิดปิดจอนั้นสิบครั้ง
3. กดปุ่ม GC เพื่อบังคับให้เก็บขยะ
4. ถ่ายภาพอีกครั้ง แล้วเทียบ
สิ่งที่เห็นหมายถึง
จำนวน _TaskScreenState เพิ่มขึ้นสิบตัวรั่ว — จอเก่าไม่ถูกเก็บ (12.8)
จำนวนเท่าเดิมปกติ
ขนาดรวมโตขึ้นเรื่อย ๆอาจเป็นแคชรูป — ตรวจที่ imageCache (13.7)
การรั่วแบบนี้ fakeAsync จับได้บางส่วน (14.11) แต่การรั่วที่เกิดจากการถืออ้างอิงไว้โดยไม่ตั้งใจ ต้องดูที่นี่

7. Network — ดูว่ายิงอะไรไปบ้าง

ใช้ตรวจสิ่งที่มักพบ
ยิงถี่เกินตัวจับเวลาซ้อนกัน (12.11)
ยิงซ้ำลืมกันกดซ้ำ (4.9)
ยิงตอนอยู่พื้นหลังไม่ได้หยุดตอน paused (12.1)
คำขอที่ช้าผิดปกติendpoint ที่ต้องบอกทีมหลังบ้าน
ขนาดของคำตอบโหลดข้อมูลเกินความจำเป็น

แท็บนี้ตอบคำถามที่ 12.11 แบบฝึกหัดถามไว้ได้ตรง ๆ — “แอปยิงคำขอกี่ครั้งต่อนาที” และ “ยิงตอนที่ไม่ควรยิงหรือเปล่า”

สิ่งที่ควรทำคู่กันคือบันทึกลง log ของเราเองด้วย ตามที่ 7.17 วางไว้ เพราะ DevTools ดูได้เฉพาะตอนที่ต่ออยู่ ส่วน log ที่เก็บไว้ในเครื่องดูย้อนหลังได้จากหน้างาน

8. เครื่องมือที่ไม่ต้องเปิด DevTools

// พิมพ์ต้นไม้ widget ทั้งหมด
debugDumpApp();

// พิมพ์ต้นไม้ของการวาด — ใช้ตอน layout แปลก
debugDumpRenderTree();

// วาดเส้นขอบของทุก widget
debugPaintSizeEnabled = true;

// วาดเส้นแสดงพื้นที่กด
debugPaintPointersEnabled = true;

// พิมพ์ทุกครั้งที่มีการสร้าง widget ใหม่
debugPrintRebuildDirtyWidgets = true;
ตัวไหนใช้เมื่อทำไม
debugDumpApp()หา widget ไม่เจอในเทสต์ (14.8)
debugPaintSizeEnabledข้อความถูกตัด ไม่รู้ว่ากล่องไหนบีบ (11.4)
debugPrintRebuildDirtyWidgetsสงสัยว่าวาดใหม่บ่อยเกิน (14.15)

ตัวสุดท้ายพิมพ์ออกมาเยอะมาก แต่ใช้ได้ดีเมื่อจำกัดขอบเขต — เปิดก่อนกดปุ่มที่สงสัย แล้วปิดทันที

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ตัวเลขประสิทธิภาพแย่มากวัดในโหมด debugใช้ --profile
แท็บส่วนใหญ่ว่างเปล่ารันในโหมด releaseใช้ profile หรือ debug
วัดบน emulator แล้วเชื่อผลemulator เร็วกว่าเครื่องจริงมากวัดบน PDA จริง
เห็นการรั่วแต่หาต้นตอไม่เจอไม่ได้กด GC ก่อนถ่ายภาพกด GC ก่อน
Highlight Repaints กะพริบทั้งจอตลอดอาจเป็นเรื่องปกติของ animationดูตอนที่ไม่มี animation
ลืมปิด flag ที่เปิดไว้เขียนใน main แล้วลืมครอบด้วย if (kDebugMode)

10. แบบฝึกหัด

ผู้ใช้บอกว่า “จอรายการงานกระตุกตอนเลื่อน แต่จออื่นปกติ” ไล่หาสาเหตุอย่างเป็นระบบ

แนวคำตอบ

ห้าขั้น เรียงจากถูกที่สุดไปแพงที่สุด

ขั้นทำอะไรตัดอะไรออกได้
1รันบนเครื่องจริงในโหมด profile แล้วเลื่อนดูยืนยันว่ากระตุกจริง ไม่ใช่เฉพาะโหมด debug
2เปิด Performance ดูว่าเฟรมไหนเกิน 16msรู้ว่าเป็นเรื่องของ Dart หรือของการวาด
3เปิด Highlight Repaintsรู้ว่าส่วนไหนวาดใหม่บ่อย
4ดู Memory ตอนเลื่อนรู้ว่ามีการคลายรูปตอนเลื่อนไหม
5CPU Profilerรู้ว่าฟังก์ชันไหนกินเวลา

สาเหตุที่เป็นไปได้ เรียงตามความน่าจะเป็น

สาเหตุเห็นได้จากแก้
รูปย่อไม่มี cacheWidthMemory โตพรวดตอนเลื่อนใส่ (13.7)
ใช้ Column แทน ListView.builderเฟรมแรกช้ามาก แต่หลังจากนั้นปกติ14.16
สร้าง Future ใน buildHighlight Repaints กะพริบตอนเลื่อน13.6
คำนวณหนักใน itemBuilderCPU Profiler ชี้ฟังก์ชันนั้นคำนวณล่วงหน้า
ไม่ได้ตั้ง itemExtentเวลาไปอยู่ที่ layoutตั้งถ้าทุกแถวสูงเท่ากัน

ข้อสังเกตที่สำคัญกว่าเครื่องมือ: คำว่า “จออื่นปกติ” เป็นข้อมูลที่มีค่ามาก — มันบอกว่าปัญหาไม่ได้อยู่ที่ธีม การนำทาง หรือเครื่อง แต่อยู่ที่สิ่งที่จอนี้ทำต่างจากจออื่น

วิธีที่เร็วที่สุดบางครั้งไม่ใช่การเปิดเครื่องมือ แต่คือเปิดโค้ดของจอนี้เทียบกับจอที่ปกติ แล้วดูว่าต่างกันตรงไหน

และเมื่อเจอสาเหตุแล้ว ให้เขียนเทสต์ที่จับได้ก่อนแก้ — ซึ่ง 14.15 กับ 14.16 จะแสดงว่าทำอย่างไร

11. สรุป

  • เทสต์จับตรรกะได้ แต่จับความช้าบนเครื่องจริงไม่ได้
  • วัดในโหมด profile บนเครื่องจริงเท่านั้น
  • Highlight Repaints ให้ข้อมูลมากที่สุดต่อการกดปุ่มเดียว
  • Memory ใช้เทียบภาพก่อนและหลัง เพื่อหาการรั่ว
  • Network ตอบว่ายิงถี่เกินหรือยิงตอนไม่ควร
  • บางครั้งการเทียบโค้ดสองจอเร็วกว่าการเปิดเครื่องมือ
