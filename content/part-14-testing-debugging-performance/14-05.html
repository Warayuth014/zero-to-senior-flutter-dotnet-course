JSON test คือ executable contract: fixture ต้องสะท้อน payload .NET จริงทั้ง happy path และข้อมูลสกปรก ไม่ใช่สร้างเฉพาะ object ที่ parser รับได้แน่นอน

1. Happy-path fixture

test('parses receiving line from API contract', () {
  final json = fixture('receiving_line.json');
  final line = ReceivingLine.fromJson(jsonDecode(json));
  expect(line.partCode, 'P-001');
  expect(line.qty, 5);
});

2. Missing, null และ wrong type

ทดสอบ required field หาย, nullable field เป็น null, number มาเป็น int/double/string ตาม contract จริง และ list/object ผิดชนิด Parser ต้อง fail แบบมี path หรือใช้ fallback ที่ตัดสินใจแล้ว ไม่ cast จน error คลุมเครือ

3. Unknown fields

โดยทั่วไป client ควร ignore field ใหม่เพื่อ forward compatibility แต่ field สำคัญที่ rename/hide ต้องทำ contract versioning Test payload ที่มี extra field เพื่อกัน parser เข้มเกินเหตุ

4. Enum/status

expect(TaskStatusCodec.parse('OPEN'), TaskStatus.open);
expect(TaskStatusCodec.parse('new-server-value'), TaskStatus.unknown);

unknown status ไม่ควร crash ทั้งรายการ แต่อาจต้อง block action และส่ง telemetry

5. Date/time

ทดสอบ UTC Z, offset +07:00, fractional seconds และ invalid date ตกลงว่าชั้น model เก็บ UTC หรือ instant อย่างไร อย่าให้ timezone ของเครื่อง CI เปลี่ยน expected

6. Round-trip ไม่พอ

fromJson(toJson(object)) อาจผ่านแม้ทั้งสองฝั่งสะกด key ผิดเหมือนกัน ต้องมี golden JSON ที่มาจาก OpenAPI/.NET integration response และ assert key outbound แยกต่างหาก

7. Contract drift

เก็บ fixture พร้อม schema/version และให้ backend integration test serialize DTO เดียวกัน หรือ generate schema/OpenAPI snapshot ที่ review ได้ เมื่อ payload เปลี่ยน CI ฝั่งใดฝั่งหนึ่งต้องเตือนก่อน deploy

8. Security cases

เพิ่ม string ยาวมาก, Unicode/Thai, HTML-like text, null ใน list, duplicate IDs และเลขเกินช่วง การ parse ไม่ควรรัน code หรือเอาข้อความ server ไปเป็น trusted HTML/log โดยไม่กรอง
