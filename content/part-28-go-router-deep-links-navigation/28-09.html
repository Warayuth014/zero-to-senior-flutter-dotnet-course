Nested routes: child pathสัมพันธ์กับ parentและ page stackสะท้อน hierarchy แต่ builderยังต้องแยก dependency/data loadingอย่างมี boundary

1. Task children

/tasks
└─ :taskId
   └─ scan

child pathsไม่ขึ้น slashจึงประกอบเป็น URLเต็มโดย router

2. Parent page

เมื่อ match detail Routerอาจสร้างทั้ง parent listและ detailใน branch Navigator ขึ้นกับ route configuration จึงอย่าให้ parentยิง side effectซ้ำทุก matchโดยไม่ lifecycle guard

3. Relative context

go_routerรองรับ relative navigationบางรูปแบบแต่ named routesมักชัดกว่าเมื่อเรียกข้าม feature อย่าพึ่งตำแหน่ง widget treeโดยไม่จำเป็น

4. parentNavigatorKey

child routeเลือกขึ้น root Navigatorได้แม้อยู่ใน URL hierarchy ใช้ scanner/dialog-like pageที่ต้องคลุม shellทั้งหมด

5. Layout route

Shell builderรับ child/navigationShellและสร้าง shared scaffold อย่า duplicate app bar/nav barในทุก page

6. Deep link stack

เปิด /tasks/TASK-001 ตรงต้องได้ shellแท็บ Tasksพร้อม detail ไม่ควรต้องเข้าหน้า listด้วยมือก่อน

7. Refactor

ย้าย routeใน treeอาจเปลี่ยน URL/back stackแม้ widgetเดิม จัดเป็น product migrationและมี redirect/testsไม่ใช่ file moveธรรมดา

8. Exercise

เพิ่ม /tasks/:taskId/history ที่อยู่ใน task branchและพิสูจน์ direct link/backไป detailตาม contractที่เลือก
