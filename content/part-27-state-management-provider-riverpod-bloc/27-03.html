Provider ownership: constructor create และ .value ไม่ได้ต่างแค่ syntax แต่บอกว่า Provider เป็นเจ้าของการ dispose object หรือเพียง expose object ที่มีเจ้าของอยู่แล้ว

1. สร้างใน scope

ChangeNotifierProvider(
  create: (_) => TaskStore(repository)..load(),
  child: const ProviderTaskBody(),
)

Provider สร้างหนึ่งครั้งแบบ lazy และ dispose เมื่อ scope ถูกถอด เหมาะกับ feature route ที่ state มีอายุเท่าหน้า

2. Expose instance เดิม

ChangeNotifierProvider.value(value: existingStore) ใช้เมื่อ parent เป็นเจ้าของ instance เช่น store อยู่ app scope ห้ามสร้าง object ใหม่ใน .value เพราะ lifecycle/disposal อาจผิด

3. Scope placement

วางต่ำสุดที่ consumers ทั้งหมดเข้าถึงได้ Auth session อาจอยู่เหนือ Navigator ส่วน scan form stateอยู่ route เดียว การยกทุก provider ไป root ทำให้ state อยู่ยาวและ dependencies มองไม่เห็น

4. BuildContext timing

context อ่านได้เฉพาะ provider ที่เป็น ancestor หากสร้าง Provider และอ่านด้วย context เดิมเหนือ child จะเกิด ProviderNotFound ใช้ builder/child context ที่อยู่ใต้ scope

5. Lazy creation

create ปกติ lazy จนมี consumer ถ้าต้องเริ่ม background subscriptionทันทีอาจใช้ lazy:false แต่ควรถามก่อนว่า side effect ควรเริ่มจาก UI scope จริงหรือ composition service

6. Route replacement

เมื่อ logout/เปลี่ยน server ให้ถอด scope ที่ผูก session เพื่อ dispose stores และสร้าง dependency graph ใหม่ ไม่ใช่แก้ fields ของ singleton ทุกตัวด้วยมือ

7. Ownership test

Widget test pump Provider panel, ตรวจ load แล้ว replace widget จาก tree จากนั้น ChangeNotifier ที่ Provider สร้างไม่ควรถูกใช้อีก สามารถ instrument dispose ใน controller สำคัญได้

8. Rule

create = scope owns; .value = someone else owns เขียน owner ใน composition code ให้ reviewerเห็น ไม่พึ่งความจำว่า object มาจากไหน
