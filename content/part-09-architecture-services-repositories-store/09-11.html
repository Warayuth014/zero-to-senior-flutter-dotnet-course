2. บททดสอบ

งานจริงที่จะได้รับคือ “เพิ่มช่องหมายเหตุในพาเลท” ลองนับว่าต้องเปิดกี่โฟลเดอร์

แบ่งตามชนิดแบ่งตามฟีเจอร์
โฟลเดอร์ที่ต้องเปิด41
เวลาลบฟีเจอร์ทิ้งทั้งตัวต้องไล่ลบทีละโฟลเดอร์ และมักลืมลบโฟลเดอร์เดียว
คนใหม่ถามว่า “ฟีเจอร์รับเข้าอยู่ตรงไหน”ตอบว่า “กระจายอยู่ทั่ว”ตอบว่า features/receiving/

ด้วยเหตุนี้ โปรเจกต์ที่โตเกินสิบจอมักจบที่แบ่งตามฟีเจอร์

3. ของกลางอยู่ที่ไหน

ของที่ทุกฟีเจอร์ใช้ ไม่ควรอยู่ในฟีเจอร์ใดฟีเจอร์หนึ่ง

lib/
  core/          ← ApiClient, ตัวอ่าน JSON, การตั้งค่า, ภาษา
  widgets/       ← ปุ่ม การ์ด แถบสถานะ ที่ใช้ซ้ำทุกจอ
  features/
    auth/
    receiving/
    tasks/
กฎ: ฟีเจอร์ import จาก core ได้ แต่ core ห้าม import จากฟีเจอร์ — ถ้าวันไหน core ต้องรู้จักฟีเจอร์ แปลว่าของชิ้นนั้นไม่ใช่ของกลาง

คำถามที่ตามมาคือ “ฟีเจอร์ import ข้ามฟีเจอร์ได้ไหม” ตอบว่าได้ แต่ให้รู้ตัว — ทุกลูกศรข้ามฟีเจอร์คือการบอกว่าสองอันนี้ลบทีละอันไม่ได้แล้ว ถ้ามีเยอะจนเป็นใยแมงมุม ให้ยกของที่ใช้ร่วมกันขึ้นไปไว้ core

เป็นแบบผสม — แบ่งตามฟีเจอร์เป็นหลัก แต่ยก repository ทั้งหมดออกมาไว้ api/ ด้วยกัน

ผลที่ได้ผลที่เสีย
เปิด api/ เห็นสัญญากับหลังบ้านทั้งหมดในที่เดียวเพิ่มฟิลด์หนึ่งช่องต้องเปิดสองโฟลเดอร์
รู้ทันทีว่าแอปคุยกับ endpoint กี่กลุ่มapi/tasks_api.dart ต้อง import โมเดลจาก features/warehouse/models/ — ลูกศรชี้ย้อนเข้าไปในฟีเจอร์

แถวสุดท้ายดูได้จากหัวไฟล์จริง

import '../features/warehouse/models/task_models.dart'
    show EventView, CompletedPickHistory, CompletedTaskHistory, WmsTask;

ไม่ผิด เพราะโมเดลไม่ได้เป็นของกลางจริง ๆ มันเป็นของฟีเจอร์คลัง แต่แปลว่า api/ กับ features/warehouse/ แยกจากกันไม่ได้จริง — เป็นฟีเจอร์เดียวกันที่วางไว้สองที่

6. โครงที่แนะนำสำหรับโปรเจกต์ใหม่

lib/
  core/
    api/           ApiClient, ชนิดความล้มเหลว, การ log
    json/          ตัวอ่านค่ากลาง
    config/        การตั้งค่า, เซิร์ฟเวอร์
  features/
    <feature>/
      <feature>.dart              โมเดล
      <feature>_repository.dart   สัญญา + ตัวจริง
      <feature>_store.dart        สถานะ
      <feature>_screen.dart       จอหลัก
      widgets/                    ชิ้นส่วนที่ใช้เฉพาะฟีเจอร์นี้
  widgets/                        ชิ้นส่วนที่ใช้ทุกฟีเจอร์
  main.dart                       จุดประกอบ

สองไม่ที่สำคัญกว่ารายละเอียดโครง

  • อย่าสร้างโฟลเดอร์ล่วงหน้าให้ฟีเจอร์ที่ยังไม่มี
  • อย่ายกของขึ้นไป widgets/ ตั้งแต่มีคนใช้คนเดียว — รอให้มีคนใช้ที่สองก่อน

7. แบบฝึกหัด

ฟีเจอร์ “รับเข้า” กับ “นับสต๊อก” ต่างก็ต้องใช้ widget ช่องสแกนบาร์โค้ดที่มีปุ่มล้างและเสียงบี๊บ ตอนนี้แต่ละฟีเจอร์เขียนของตัวเอง

  1. ควรยกขึ้นไปไว้ widgets/ ไหม
  2. ถ้าฟีเจอร์รับเข้าต้องการให้ช่องสแกนโชว์จำนวนที่รับไปแล้วด้วย ควรทำอย่างไร
แนวคำตอบ

1. ควร เพราะมีผู้ใช้สองรายแล้ว และพฤติกรรมของช่องสแกน (โฟกัสกลับอัตโนมัติ ล้างหลังสแกน กันสแกนซ้ำ) เป็นเรื่องของอุปกรณ์ ไม่ใช่ของงานรับเข้าหรืองานนับ

2. อย่าใส่ตรรกะของงานรับเข้าเข้าไปใน widget กลาง ให้เปิดช่องรับเข้ามาแทน

ScanField(
  onScan: store.scanPart,
  trailing: Text('รับแล้ว ${store.receivedCount}'),   // ฟีเจอร์ส่งของตัวเองเข้าไป
)

สัญญาณอันตรายคือถ้าเริ่มเขียน if (mode == 'receiving') ใน widget กลาง — แปลว่าของกลางเริ่มรู้จักฟีเจอร์แล้ว ซึ่งเป็นการละเมิดกฎใน §3 และจะจบที่ widget เดียวที่มี if ของทุกฟีเจอร์อยู่ข้างใน

8. สรุป

  • แบ่งตามฟีเจอร์ทำให้ของที่แก้พร้อมกันอยู่ใกล้กัน
  • ฟีเจอร์ใช้ของกลางได้ ของกลางห้ามรู้จักฟีเจอร์
  • ยกของขึ้นเป็นของกลางเมื่อมีผู้ใช้รายที่สอง ไม่ใช่ตอนเขียนรายแรก
  • โครงจริงมักเป็นแบบผสม และรอยต่อของแบบผสมจะเห็นได้จากบรรทัด import
