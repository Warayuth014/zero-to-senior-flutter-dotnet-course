จบบทนี้แล้วจะทำได้: เขียน repository interface ที่ใช้คำของงาน ไม่ใช่คำของ HTTP และรู้ว่าอะไรไม่ควรอยู่ในนั้น

1. repository คืออะไร

Repository คือชั้นที่ตอบว่า “ขอข้อมูลนี้” และ “สั่งให้เกิดสิ่งนี้” โดยที่คนขอไม่ต้องรู้ว่าข้อมูลมาจากไหน — จาก HTTP, จากฐานข้อมูลในเครื่อง, หรือจากตัวปลอมในเทสต์

ชื่อมาจากคำว่า “คลังเก็บของ” เดินไปที่เคาน์เตอร์ บอกว่าอยากได้อะไร แล้วได้ของ ไม่ต้องรู้ว่าของอยู่ชั้นไหน

2. หน้าตาใน lab

abstract interface class PalletRepository {
  Future<List<Pallet>> fetchInZone(String zone);
  Future<Pallet> hold(String code, {required String commandId});
}

อ่านสามบรรทัดนี้แล้วรู้ทันทีว่าจอพาเลทต้องการอะไรจากโลกภายนอก — สองอย่าง ไม่มีมากกว่านั้น

คำที่อยู่ในนี้คำที่ไม่อยู่ในนี้
Pallet, zone, holdResponse, statusCode, json, Uri

เกณฑ์ตรวจง่าย ๆ: ถ้าอ่าน interface ให้หัวหน้าคลังฟังแล้วเขาเข้าใจ แปลว่าใช้คำถูกชั้น

3. abstract interface class คืออะไร

Dart 3 แยกคำสั่งให้ชัดขึ้น สามคำนี้ต่างกัน

เขียนแบบสืบทอด (extends)สวมสัญญา (implements)สร้างตรง ๆ
class Aได้ได้ได้
abstract class Aได้ได้ไม่ได้
interface class Aเฉพาะในไฟล์เดียวกันได้ได้
abstract interface class Aเฉพาะในไฟล์เดียวกันได้ไม่ได้

ตัวสุดท้ายคือ “สัญญาล้วน ๆ” — บังคับว่าคนที่จะใช้ต้อง implements และเขียนทุกเมธอดเอง ไม่มีทางลัดด้วยการ extends แล้วเขียนบางตัว

4. ทำไมต้องมี interface ทั้งที่มี implementation ตัวเดียว

class _ScriptedRepository implements PalletRepository {
  final List<Completer<List<Pallet>>> _fetches = [];

  @override
  Future<List<Pallet>> fetchInZone(String zone) {
    final completer = Completer<List<Pallet>>();
    _fetches.add(completer);
    return completer.future;      // ค้างไว้จนกว่าเทสต์จะสั่งให้ตอบ
  }

  void completeAt(int index, List<Pallet> pallets) =>
      _fetches[index].complete(pallets);
}

ตัวปลอมนี้ทำให้เขียนเทสต์ที่ ตอบคำขอที่สองก่อนคำขอแรก ได้ ซึ่งเป็นสถานการณ์ที่เกิดจริงบน PDA ที่สัญญาณไม่ดี แต่จำลองผ่าน HTTP ยากมาก

ไฟล์ lib/api/tasks_api.dart ยาว 665 บรรทัด แต่ 59 บรรทัดแรกคือสัญญาทั้งหมด อ่านแค่นั้นก็รู้ว่าฟีเจอร์งานขนย้ายพึ่งพาอะไรบ้าง — นี่คือประโยชน์ที่ได้แม้จะมี implementation ตัวเดียว

สังเกต required String serverId ที่โผล่ในหลายเมธอด — มาจากบทเรียนใน 8.11 ว่า session ต้องผูกกับเซิร์ฟเวอร์ที่ออกมัน

7. ข้อผิดพลาดที่พบบ่อย

อาการทำไมเป็นปัญหา
ตั้งชื่อเมธอดตาม path เช่น getMobilePallets()วันที่ path เปลี่ยน ชื่อเมธอดจะโกหก
ทำ interface ที่มีเมธอดเดียวชื่อ call(String path)ได้ interface ที่ไม่ได้บอกอะไร เท่ากับไม่มี
เขียน interface ตอนยังไม่รู้ว่าต้องการอะไรจะได้สัญญาที่สะท้อน endpoint แทนที่จะสะท้อนงาน
ใส่ทุก endpoint ของระบบไว้ใน interface เดียวตัวปลอมในเทสต์ต้องเขียนเมธอดเปล่าเป็นสิบตัว

ข้อสุดท้ายมีทางแก้: แยก interface ตามฟีเจอร์ ไม่ใช่ตามระบบ ให้ interface หนึ่งตัวเล็กพอที่ตัวปลอมจะเขียนได้ในสิบบรรทัด

8. แบบฝึกหัด

จอ “นับสต๊อกหน้าแร็ค” ต้องทำสี่อย่าง — ค้นพาเลทจากรหัส, เริ่มรอบนับ, ส่งจำนวนที่นับได้ทีละรายการ, ปิดรอบนับ เขียน interface ให้จอนี้

แนวคำตอบ
abstract interface class CycleCountRepository {
  Future<CycleCountPallet> lookupPallet(String palletCode);
  Future<CycleCountSession> start(String palletCode, CycleCountMode mode);
  Future<void> recordCount(String sessionId, String productCode, double quantity);
  Future<CycleCountResult> confirm(String sessionId);
}

จุดที่ต้องคิด

  • quantity เป็น double ไม่ใช่ int เพราะบางสินค้าเป็นน้ำหนักหรือความยาว — ตัดสินจากงาน ไม่ใช่จากชนิดที่เผอิญมีในภาษา
  • ไม่มีเมธอด getScannedItems() เพราะสิ่งที่สแกนไปแล้วในรอบนี้เป็นสถานะที่ store ถืออยู่ ไม่ต้องถามเซิร์ฟเวอร์
  • ทั้งสี่เมธอดใช้คำที่หัวหน้าคลังเข้าใจ

ของจริงเลือกต่างจากนี้ — wms_absolute_mobile/lib/api/cycle_count_api.dart มีสามเมธอด คือ lookup, start, confirm ไม่มี recordCount เพราะจำนวนที่นับได้ทั้งรอบถูกส่งไปทีเดียวตอน confirm

Future<CycleCountPallet> confirm({
  required String palletCode,
  required String user,
  required List<CycleCountResult> counts,   // ← ทั้งรอบส่งทีเดียว
  String station = 'PDA',
});

ทั้งสองแบบใช้ได้ ต่างกันตรงนี้

ส่งทีละรายการส่งทีเดียวตอนปิดรอบ
สแกนไปครึ่งทางแล้วแบตหมดของที่นับไปแล้วอยู่บนเซิร์ฟเวอร์หายหมด ต้องนับใหม่
จำนวนคำขอเท่ากับจำนวนรายการสามครั้งต่อรอบ
ทำงานตอนสัญญาณไม่ดีค้างกลางคันได้ ต้องมีกลไกส่งซ้ำสแกนตอนไม่มีเน็ตก็ได้ ติดแค่ตอนปิดรอบ

ในคลังที่ Wi-Fi ไม่ทั่วถึง แบบที่สองชนะ และนั่นคือเหตุผลที่ของจริงเลือกแบบนั้น — สัญญาที่ถูกต้องขึ้นกับหน้างาน ไม่ใช่ขึ้นกับความสวยของ interface

9. สรุป

  • interface บอกว่า “ฟีเจอร์นี้ต้องการอะไร” ด้วยคำของงาน
  • abstract interface class คือสัญญาล้วน ๆ ที่บังคับให้เขียนครบ
  • ประโยชน์ได้ทันทีสองข้อ คือมีที่ให้สวมของปลอม และมีที่เดียวที่อ่านแล้วรู้ว่าฟีเจอร์พึ่งอะไร
  • อย่าให้ HTTP, BuildContext หรือสถานะ หลุดเข้าไปใน interface
