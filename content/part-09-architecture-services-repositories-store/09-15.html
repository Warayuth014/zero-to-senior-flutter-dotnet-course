2. อาการที่รู้สึกได้

อาการสาเหตุ
แก้ตรรกะนับสต๊อก แต่ต้องอ่านผ่านโค้ดรับเข้าอยู่ไฟล์เดียวกัน
สองคนแก้คนละฟีเจอร์แล้ว merge ชนไฟล์เดียวกัน
เขียนเทสต์ของนับสต๊อก ต้องสร้าง repository ครบสี่ตัวconstructor ต้องการทั้งหมด
notifyListeners() ครั้งเดียวทำให้ทุกจอวาดใหม่ผู้ฟังทั้งหมดผูกกับ notifier ตัวเดียว
เผลอใช้ตัวแปรข้ามฟีเจอร์โดยไม่รู้ตัวทุกอย่างอยู่ในขอบเขตเดียวกัน

แถวสุดท้ายคือความเสี่ยงที่แท้จริง ไม่ใช่เรื่องความสวย — เช่นถ้ามีใครใช้ rQty ในโค้ดของงานเบิกออกโดยเข้าใจผิดว่าเป็นจำนวนทั่วไป จะได้บั๊กที่ตามยากมาก และคอมไพเลอร์ช่วยอะไรไม่ได้เลยเพราะทุกอย่างอยู่ในคลาสเดียวกัน

3. อาการที่ยังไม่ใช่ปัญหา

ก่อนแยก ต้องยอมรับข้อดีที่มีอยู่จริงก่อน ไม่งั้นจะแยกแล้วเสียของ

ข้อดีที่มีถ้าแยกผิดจะเสียไป
ไม่มีวันที่สองจอเห็นข้อมูลไม่ตรงกันแยกแล้วมี pallets สองชุดทันที
งานที่ข้ามฟีเจอร์ทำได้ตรง ๆ เช่นรับเข้าเสร็จแล้วสร้างงานขนย้ายต้องหาทางให้ store คุยกัน
screen กับขั้นตอนของงานสอดคล้องกันเสมอปุ่มย้อนกลับอาจพาไปจอที่สถานะไม่พร้อม
จุดประกอบเดียว อ่านง่ายต้องประกอบห้าตัวและตัดสินใจว่าใครถือใคร
แถวแรกสำคัญที่สุด ห้ามแก้ปัญหาไฟล์ใหญ่ด้วยการสร้างแหล่งความจริงที่สอง — ได้ไฟล์เล็กลงแต่ได้บั๊กประเภทที่แก้ยากที่สุดกลับมาแทน

4. เส้นแบ่งที่ปลอดภัย

แบ่ง ตามข้อมูลที่เป็นเจ้าของ ไม่ใช่แบ่งตามจำนวนบรรทัด

WarehouseStore              ← ของกลาง: screen, username, access, onToast
  ├─ InventoryStore         ← pallets, freeLocations, locationCount  (แหล่งเดียว)
  ├─ ReceivingStore         ← inboundOrders, rPallet, rStep, rQty
  ├─ CycleCountStore        ← cycleCountPallet, cycleCountValues
  ├─ TaskStore              ← tasks, taskId, tStep
  └─ PickingStore           ← picks, selectedPickingConveyorNo

ตัวที่ต้องคิดหนักคือ pallets เพราะมีสามฟีเจอร์ที่ใช้ ทางแก้ที่ถูกคือ ให้มีเจ้าของคนเดียว แล้วให้คนอื่นถามเอา ไม่ใช่ให้แต่ละตัวเก็บสำเนา

class ReceivingStore extends ChangeNotifier {
  ReceivingStore(this.repository, this.inventory);   // ถือ inventory ไว้ถาม

  final InventoryStore inventory;

  Future<void> confirmReceive() async {
    await repository.receive(...);
    await inventory.reload();       // บอกเจ้าของให้ไปโหลดใหม่ ไม่แก้ของเขาเอง
  }
}

5. ลำดับที่ปลอดภัย

ขั้นทำอะไรยังไม่ทำอะไร
1เขียนเทสต์ของฟีเจอร์ที่จะแยกออกก่อน โดยยังเรียกผ่าน WarehouseStore เดิมยังไม่ย้ายโค้ด
2จัดกลุ่มฟิลด์กับเมธอดของฟีเจอร์นั้นให้อยู่ติดกันในไฟล์เดิมยังไม่แยกไฟล์
3ดูว่ามีใครนอกกลุ่มใช้ฟิลด์เหล่านั้นบ้าง — รายชื่อนี้คือสิ่งที่ต้องออกแบบต่อยังไม่แยก
4ย้ายออกเป็นคลาสใหม่ ให้ WarehouseStore ถือไว้และส่งต่อชั่วคราวจอยังไม่ต้องแก้
5ค่อย ๆ เปลี่ยนจอให้ฟัง store ตัวใหม่โดยตรง แล้วลบตัวส่งต่อ—

ขั้นที่ 4 คือหัวใจ เพราะทำให้แอปยังทำงานได้ตลอดเวลาระหว่างที่ย้าย

class WarehouseStore extends ChangeNotifier {
  late final cycleCount = CycleCountStore(cycleCountRepository)
    ..addListener(notifyListeners);    // ของใหม่เปลี่ยน ของเก่าก็แจ้งต่อ

  // ตัวส่งต่อชั่วคราว — จอเดิมยังเรียกได้เหมือนไม่มีอะไรเกิดขึ้น
  @Deprecated('ใช้ cycleCount.confirm() แทน')
  Future<void> confirmCycleCount() => cycleCount.confirm();
}

..addListener(notifyListeners) ทำให้จอที่ยังฟัง WarehouseStore อยู่ ได้รับแจ้งเหมือนเดิมทุกประการ — โค้ดจอไม่ต้องแก้แม้แต่บรรทัดเดียวในขั้นนี้

6. อย่าแยกถ้า

  • ยังไม่มีเทสต์ครอบฟีเจอร์นั้น
  • กำลังจะส่งงานสัปดาห์หน้า
  • เหตุผลเดียวคือ “ไฟล์ยาว”
  • ยังตอบไม่ได้ว่า pallets จะมีเจ้าของคนไหน
  • ทีมมีคนเดียวและไม่เคย merge ชนกัน

ข้อสุดท้ายอาจฟังดูแปลก แต่ประโยชน์หลักข้อหนึ่งของการแยกคือให้หลายคนทำงานพร้อมกันได้ ถ้าไม่มีปัญหานั้น ประโยชน์ก็หายไปข้อหนึ่ง

7. ทางเลือกที่เบากว่า

ถ้าปัญหาคือ “หาโค้ดไม่เจอ” ไม่ใช่ “แก้แล้วพัง” มีทางที่ถูกกว่ามาก

ทำได้อะไรเสี่ยง
จัดกลุ่มฟิลด์และเมธอดในไฟล์เดิมให้อยู่ติดกัน พร้อมคอมเมนต์คั่นหาเจอเร็วขึ้นมากไม่มี
แยกเป็น part ไฟล์ตามฟีเจอร์ไฟล์ละฟีเจอร์ แต่ยังเป็นคลาสเดียวต่ำ
ยกงานที่ไม่แตะสถานะออกไปเป็นฟังก์ชันอิสระทดสอบชิ้นนั้นได้เดี่ยว ๆต่ำ

แถวกลางน่าสนใจ — เป็นเทคนิคเดียวกับที่ wmsapp ใช้กับ ApiService ใน 9.4 ได้ไฟล์เล็กลงโดยไม่แตะโครงสร้างอะไรเลย และไม่เสี่ยงสร้างแหล่งความจริงที่สอง

8. แบบฝึกหัด

ทีมตัดสินใจแยก CycleCountStore ออกมาก่อนเป็นตัวแรก

  1. ทำไมเลือกตัวนี้เป็นตัวแรกถึงสมเหตุสมผล
  2. มีอะไรที่ต้องตัดสินใจก่อนลงมือ
แนวคำตอบ

1. เพราะกลุ่มนี้แยกตัวได้มากที่สุด — ฟิลด์ทั้งหมดขึ้นต้นด้วย cycleCount, ใช้ repository ตัวเดียว, และไม่มีฟีเจอร์อื่นอ่านค่าเหล่านั้นเลย เป็นการซ้อมที่ความเสี่ยงต่ำสุด ก่อนไปเจอตัวที่พันกันจริงอย่างงานรับเข้ากับงานขนย้าย

2. อย่างน้อยสี่ข้อ

  • นับเสร็จแล้วต้องอัปเดต pallets ไหม ถ้าใช่ ต้องตัดสินตั้งแต่ตอนนี้ว่าใครเป็นเจ้าของ — และคำตอบต้องไม่ใช่ “เก็บไว้ทั้งสองที่”
  • ใครเรียก onToast ถ้า store ใหม่ต้องแจ้งข้อความ ต้องรับ callback เข้ามาด้วย หรือให้ตัวแม่ฟังแล้วแจ้งแทน
  • screen ยังอยู่ที่เดิมไหม ถ้า store ใหม่ต้องสั่งเปลี่ยนจอตอนนับเสร็จ แสดงว่ามันยังต้องคุยกับตัวแม่ ให้ทำผ่าน callback ไม่ใช่ให้ถือตัวแม่ไว้ ไม่งั้นจะได้การพึ่งพาที่วนกลับ
  • จอยังฟังตัวเก่าอยู่ไหม ถ้าใช่ ต้องมี ..addListener(notifyListeners) ตามขั้นที่ 4

ข้อที่มักถูกลืมคือข้อสาม และมันจะกลายเป็นการพึ่งพาที่วนกลับ (แม่ถือลูก ลูกถือแม่) ซึ่งทำให้ทดสอบลูกเดี่ยว ๆ ไม่ได้อีก — เท่ากับแยกแล้วไม่ได้อะไรเลย

9. สรุป

  • แบ่งตามข้อมูลที่เป็นเจ้าของ ไม่ใช่ตามจำนวนบรรทัด
  • ข้อมูลที่หลายฟีเจอร์ใช้ ต้องมีเจ้าของคนเดียว คนอื่นถามเอา
  • ย้ายทีละก้าวโดยให้ตัวเก่าส่งต่อชั่วคราว แอปต้องทำงานได้ตลอดทาง
  • ถ้าปัญหาคือหาโค้ดไม่เจอ ให้จัดกลุ่มหรือใช้ part ก่อน ถูกกว่าและไม่เสี่ยง
