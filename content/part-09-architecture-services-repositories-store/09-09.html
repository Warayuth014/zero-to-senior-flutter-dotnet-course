1. อาการ

ผู้ใช้ล็อกพาเลท PLT-001 ที่จอค้นหา แถวเปลี่ยนเป็น “ล็อกแล้ว” ถูกต้อง แล้วกดไปจอสรุป ตรงนั้นยังบอกว่าพาเลทใบนี้ว่างอยู่

ผู้ใช้จะรายงานว่า “แอปล็อกไม่ติด” ทั้งที่เซิร์ฟเวอร์ล็อกไปแล้วเรียบร้อย นี่คืออาการของข้อมูลชุดเดียวถูกเก็บไว้สองที่

2. หลัก

Single source of truth: ข้อมูลแต่ละอย่างมีเจ้าของที่เดียว ที่เหลืออ่านจากเจ้าของ ไม่เก็บสำเนาของตัวเอง

เหตุผลไม่ใช่เรื่องความสวยงาม แต่เป็นเรื่องคณิตศาสตร์ — ถ้าเก็บที่เดียว มันไม่มีวันไม่ตรงกัน ถ้าเก็บสองที่ ต้องมีโค้ดที่ซิงก์ให้ตรง และโค้ดนั้นจะลืมกรณีใดกรณีหนึ่งเสมอ

3. สามหน้าตาของปัญหาเดียวกัน

แบบหน้าตาเจอตอน
store สองตัวเก็บของเดียวกันจอ A กับจอ B สร้าง store คนละตัวข้อมูลไม่ตรงข้ามจอ
จอ copy ค่าจาก store มาเก็บใน State_pallets = widget.store.pallets ใน initStatestore อัปเดตแล้วจอไม่เปลี่ยน
เก็บค่าที่คำนวณได้เป็น fieldbool _hasHeldPallets เก็บแยกจากลิสต์ลืมอัปเดตในเส้นทางใดเส้นทางหนึ่ง

5. แล้วสถานะของหน้าจอล่ะ

ไม่ใช่ทุกอย่างต้องอยู่ใน store สิ่งที่เป็นของหน้าจอจริง ๆ ควรอยู่ในหน้าจอ

อยู่ในจอได้ต้องอยู่ใน store
ตำแหน่งการเลื่อนของลิสต์รายการพาเลท
ข้อความที่พิมพ์อยู่ในช่องค้นหา (ก่อนกดค้น)คำค้นที่ค้นไปแล้ว
dialog เปิดอยู่หรือไม่ผลของการยืนยันใน dialog
แท็บที่เลือกอยู่ ถ้าไม่มีผลกับข้อมูลขั้นตอนของ workflow ที่ทำค้างไว้

เกณฑ์ตัดสิน: ถ้าปิดจอแล้วเปิดใหม่ ค่านี้ควรหายไปไหม ถ้าควรหาย ให้อยู่ในจอ

แม้แต่ screen ที่บอกว่าตอนนี้อยู่จอไหน ก็อยู่ใน store ทำให้ปุ่มย้อนกลับกับขั้นตอนของงานสอดคล้องกันเสมอ

ราคาที่จ่ายคือไฟล์ 1,684 บรรทัด ซึ่งเป็นปัญหาคนละเรื่อง และ 9.15 จะพูดถึง — อย่าแก้ปัญหาไฟล์ใหญ่ด้วยการสร้างแหล่งความจริงที่สอง

7. เมื่อสองแหล่งเลี่ยงไม่ได้

บางกรณีมีข้อมูลสองที่จริง ๆ เช่น รายการที่แคชไว้ในเครื่องกับข้อมูลบนเซิร์ฟเวอร์ กรณีแบบนี้ต้องตอบสามคำถามให้ชัดตั้งแต่ออกแบบ

คำถามตัวอย่างคำตอบ
ใครถูกเมื่อไม่ตรงกันเซิร์ฟเวอร์ถูกเสมอ
ซิงก์ตอนไหนตอนเปิดจอ และตอนกลับมาจาก background
ผู้ใช้รู้ได้อย่างไรว่ากำลังดูของเก่ามีป้ายบอกเวลาที่ข้อมูลอัปเดตล่าสุด

ถ้าตอบไม่ได้ทั้งสามข้อ แปลว่ายังไม่ควรมีแคช — Part 29 จะลงรายละเอียดเรื่องนี้

8. แบบฝึกหัด

อ่านโค้ดนี้แล้วบอกว่าจะพังตอนไหน

class _SummaryViewState extends State<SummaryView> {
  late int _heldCount;

  @override
  void initState() {
    super.initState();
    _heldCount = widget.store.pallets.where((p) => p.onHold).length;
  }

  @override
  Widget build(BuildContext context) => Text('ล็อกอยู่ $_heldCount ใบ');
}
แนวคำตอบ

พังทันทีที่ store เปลี่ยน เพราะ _heldCount คำนวณครั้งเดียวตอนสร้างจอ และ build ไม่ได้ผูกกับ store ด้วย

มีบั๊กสองชั้นซ้อนกัน — ชั้นแรกคือเก็บค่าที่คำนวณได้ ชั้นสองคือไม่ได้ฟัง store แก้แล้วเหลือแบบนี้

Widget build(BuildContext context) => ListenableBuilder(
  listenable: widget.store,
  builder: (context, _) {
    final heldCount = widget.store.pallets.where((p) => p.onHold).length;
    return Text('ล็อกอยู่ $heldCount ใบ');
  },
);

ถ้ามีหลายจอต้องใช้ตัวเลขนี้ ให้ย้ายไปเป็น getter ใน store แทนที่จะเขียน where ซ้ำ

int get heldCount => _pallets.where((p) => p.onHold).length;

ยังเป็นการคำนวณ ไม่ใช่การเก็บ จึงไม่มีวันไม่ตรง

9. สรุป

  • ข้อมูลหนึ่งอย่าง มีเจ้าของที่เดียว
  • อาการที่พบบ่อยที่สุดคือจอถ่ายสำเนาจาก store มาไว้ใน State
  • สิ่งที่ควรหายเมื่อปิดจอ ให้อยู่ในจอ ที่เหลืออยู่ใน store
  • ค่าที่คำนวณได้ ให้คำนวณ อย่าเก็บ
