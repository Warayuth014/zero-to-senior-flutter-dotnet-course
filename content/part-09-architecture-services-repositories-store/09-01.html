Separation of concerns: แยกเพราะเหตุผลในการเปลี่ยนต่างกัน—not เพื่อเพิ่มจำนวนไฟล์ UI เปลี่ยนตาม UX, workflow เปลี่ยนตามธุรกิจ, transport เปลี่ยนตาม API และ persistence เปลี่ยนตามแหล่งข้อมูล

1. Four concerns

  • Presentation: render/input/navigation
  • Application: orchestration และ workflow state
  • Domain: กฎ/คำศัพท์ธุรกิจ
  • Infrastructure: HTTP, JSON, storage, SignalR

2. Change test

ถามว่า “ถ้า endpoint เปลี่ยน casing ไฟล์ UI ต้องแก้ไหม?” และ “ถ้า layout เปลี่ยน repository test พังไหม?” ถ้าพังข้ามเหตุผลแสดงว่า concerns ยังปนกัน

3. Boundary flow

Widget → Store → Repository → RemoteDataSource → .NET
       ← ViewState ← Domain model ← DTO/JSON

dependency ชี้เข้าหา abstraction/logic ไม่ให้ domain import Flutter หรือ package http

4. แยกเท่าที่จำเป็น

feature CRUD เล็กอาจใช้ Widget → Repository ได้ แต่ workflow scan หลาย step, offline/retry หรือหลาย data source ควรมี Store/application layer ห้ามสร้าง UseCase หนึ่งไฟล์ต่อ methodเพียงเพราะ diagram บอก

5. Cohesion

ของที่เปลี่ยนด้วยกันควรอยู่ใกล้กัน เช่น Receiving API + DTOs + repository อยู่ feature เดียว ส่วน generic ApiClient, auth และ connection เป็น shared core

6. Warning signs

  • widget เรียก jsonDecode
  • ApiClient เปิด dialog
  • repository ถือ BuildContext
  • model import material.dart เพื่อเลือกสี
  • ทุก featureแก้ God Store ไฟล์เดียว

7. แบบฝึกหัด

จัดวาง barcode normalization, HTTP timeout, selected row และ quantity business limit ลงชั้นที่เหมาะสม

แนวคำตอบ

normalize input ที่ application/domain boundary, timeout infrastructure, selected row presentation/store, quantity invariant domain/server

8. หลักตัดสิน

ทุก class ควรบอกได้ว่ารับผิดชอบอะไร, ไม่รับผิดชอบอะไร, dependency ใด และทดสอบโดยไม่เปิดส่วนอื่นได้อย่างไร
