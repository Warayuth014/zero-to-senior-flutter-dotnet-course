จบบทนี้แล้วจะทำได้: อ่านโค้ดที่ใช้ part กับ extension ออก และรู้ว่าเลือกใช้ตอนไหน

1. ปัญหา

wmsapp มีเมธอดเรียก endpoint 44 ตัว กระจายอยู่ใน 9 กลุ่มงาน (picking 11, receiving 6, sorting 6, checkin 5, putaway 5, packing 4, unload 3, basket 2, upload 2) ถ้าเขียนรวมในคลาสเดียวจะได้ไฟล์ราวพันบรรทัด ถ้าแยกเป็น 9 คลาส ก็ต้องหาทางแชร์โค้ดที่ใช้ร่วมกัน เช่น การหา base URL การใส่ header และการแปลงคำตอบ

ทางที่เลือกคือ คลาสเดียว แต่เขียนคนละไฟล์

2. part กับ part of

// api_service.dart
part 'api/upload_api.dart';
part 'api/receiving_api.dart';
part 'api/unload_api.dart';
...

class ApiService { ... }
// api/receiving_api.dart
part of '../api_service.dart';

extension ReceivingApi on ApiService {
  Future<ApiResult<POResponse>> getPO(String poId) async {
    final response = await _get('/receiving/po/$poId');
    if (!response.success) return ApiResult.error(response.error);
    return ApiResult.success(POResponse.fromJson(response.data!));
  }
  ...
}
part คืออะไร: Dart ปกติมองไฟล์หนึ่งไฟล์เป็นหนึ่ง library part ทำให้หลายไฟล์กลายเป็น library เดียวกัน ผลคือ ทุกไฟล์เห็นสมาชิกที่ขึ้นต้นด้วย _ ของกันและกัน และไม่ต้อง import กันเอง

3. ทำไมต้องใช้ part ตรงนี้

ดูบรรทัดนี้ในไฟล์ย่อย

final response = await _get('/receiving/po/$poId');

_get ขึ้นต้นด้วยขีดล่าง แปลว่าเป็นของส่วนตัวของ library ถ้า receiving_api.dart เป็น library ของตัวเองแล้ว import เข้ามาเฉย ๆ จะเรียก _get ไม่ได้เลย จะต้องเปลี่ยน _get เป็น get สาธารณะ ซึ่งแปลว่าจอไหนก็เรียก ApiService().get('/อะไรก็ได้') ได้

การใช้ part จึงเป็นการ แลกความเป็นไฟล์อิสระ เพื่อรักษาความเป็นส่วนตัวของเมธอดกลาง

4. extension ทำอะไร

extension ReceivingApi on ApiService {
  Future<ApiResult<POResponse>> getPO(String poId) async { ... }
}

อ่านว่า “เพิ่มเมธอด getPO ให้กับคลาส ApiService” คนใช้เรียกได้เหมือนเมธอดปกติ

final result = await ApiService().getPO('PO-2026-001');
extension ทำได้extension ทำไม่ได้
เพิ่มเมธอดเพิ่มฟิลด์ที่เก็บค่า
เพิ่ม getter/setter ที่คำนวณจากของที่มีoverride เมธอดเดิม
เพิ่มให้คลาสที่เราแก้ไม่ได้ เช่นของใน packageถูกเรียกแบบ polymorphic ผ่านตัวแปรชนิดแม่

ข้อสุดท้ายสำคัญ — extension ถูกเลือกตอนคอมไพล์จากชนิดของตัวแปร ไม่ใช่ตอนรันจากชนิดจริงของวัตถุ ถ้าตัวแปรประกาศเป็น Object จะเรียก getPO ไม่ได้แม้ข้างในจะเป็น ApiService

5. ผลของการเลือกทางนี้

ได้เสีย
ไฟล์ละกลุ่มงาน หาง่าย git ชนกันน้อยยังเป็นคลาสเดียว จอที่ต้องการแค่ getPO ได้ทุก endpoint ติดมาด้วย
เมธอดกลาง _get ยังเป็นส่วนตัวไฟล์ย่อยเปิดอ่านเดี่ยว ๆ ไม่รู้ว่า _get มาจากไหน ต้องรู้ว่ามันเป็น part
ไม่ต้องส่ง ApiService ไปมาระหว่างคลาสย่อยทำ ApiService ปลอมไม่ได้ เพราะไม่มี interface ให้ implement

แถวสุดท้ายคือสิ่งที่ต้องจ่ายจริงที่สุด ReceivingApi เป็น extension บนคลาสรูปธรรม ไม่ใช่บน interface ทำให้ในเทสต์ไม่มีอะไรให้สวมแทน — ต้องไปคุมที่ระดับ http.Client แทน ซึ่งแปลว่าเทสต์ต้องรู้ path และรูปแบบ JSON ทุกครั้ง

extension on classinterface + implementation

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุ

The name '_get' is being referenced before it is declaredลำดับ part ไม่เกี่ยว — มักเป็นเพราะสะกดชื่อไฟล์ผิด
เพิ่มฟิลด์ใน extension ไม่ได้ถูกแล้ว extension เก็บสถานะไม่ได้ ถ้าต้องเก็บ ต้องไปไว้ในคลาสหลัก
เรียกเมธอดของ extension ไม่ได้ทั้งที่ import แล้วตัวแปรประกาศเป็นชนิดที่กว้างกว่า เช่น dynamic หรือ Object

8. แบบฝึกหัด

ทีมหลังบ้านจะทำ endpoint ชุดใหม่ให้โหมด offline ที่อ่านจากฐานข้อมูลในเครื่องแทน

  1. ในโครง wmsapp ต้องแก้อะไรบ้าง
  2. ในโครง wms_absolute_mobile ต้องแก้อะไรบ้าง
แนวคำตอบ

1. ไม่มีจุดสลับ ต้องเลือกทางใดทางหนึ่ง — เพิ่ม if (offline) ในทุกเมธอดของ extension ทั้ง 60 ตัว, หรือแก้ _get/_post ให้เปลี่ยนเส้นทางไปที่ฐานข้อมูล ซึ่งทำไม่ได้จริงเพราะฐานข้อมูลไม่ได้พูด HTTP, หรือรื้อให้มี interface ก่อน

2. เขียนคลาสใหม่ OfflineTasksRepository implements TasksRepository แล้วเปลี่ยนบรรทัดเดียวตอนสร้าง WarehouseStore ใน warehouse_shell.dart โค้ดที่เหลือไม่ต้องแตะ

นี่ไม่ได้แปลว่าโครงแรกผิด ถ้าไม่เคยต้องทำ offline เลย interface ที่เขียนไว้ก็เป็นบรรทัดที่ไม่ได้ใช้ ประเด็นคือ ราคาของการเปลี่ยนใจจ่ายตอนไหน — โครงแรกจ่ายทีเดียวตอนต้องเปลี่ยน โครงหลังจ่ายทีละนิดตั้งแต่วันแรก

9. สรุป

  • part รวมหลายไฟล์เป็น library เดียว ทำให้ยังเห็นสมาชิกส่วนตัวของกันได้
  • extension เพิ่มเมธอดให้คลาสได้ แต่เพิ่มฟิลด์ไม่ได้ และถูกเลือกตอนคอมไพล์
  • extension บนคลาสรูปธรรมทำให้ไม่มีที่ให้สวมของปลอม
