ต้องผ่านอะไรมาก่อน: 1.3 (Element และการเทียบชนิด) และ 1.5 (ข้อมูลอยู่ใน State)
จบบทนี้แล้วจะทำได้: ใส่ key ให้ถูกที่ เข้าใจว่าทำไมข้อมูลถึงสลับกันเมื่อเรียงรายการใหม่ และรู้ว่าเมื่อไหร่ที่ ไม่ ควรใส่

1. ปัญหาที่บทนี้แก้

ใน 1.3 เราค้างไว้ว่า Flutter เทียบ ชนิด และ key เพื่อตัดสินว่าจะเก็บ Element เดิมไว้ไหม แล้วบอกว่า key จะอธิบายทีหลัง — ตอนนี้ถึงเวลาแล้ว

ปัญหาที่ key แก้เกิดขึ้นเมื่อมีรายการหลายแถวที่ ชนิดเดียวกันทั้งหมด เมื่อลำดับเปลี่ยน Flutter ไม่มีทางรู้ว่าแถวไหนคือแถวไหน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
keyป้ายชื่อที่ติดกับ widget เพื่อบอกว่า “ตัวนี้คือใคร”
ValueKeykey ที่ใช้ค่าหนึ่งค่าเป็นตัวระบุ เช่นรหัสงาน
UniqueKeykey ที่ต่างเสมอ ทำให้เป็นตัวใหม่ทุกครั้ง
GlobalKeykey ที่ไม่ซ้ำทั้งแอป และเข้าถึง State ได้จากข้างนอก
siblingwidget ที่อยู่ระดับเดียวกันใต้แม่คนเดียวกัน

3. Mental model: ป้ายชื่อบนกล่องที่เหมือนกันทุกใบ

ลองนึกถึงกล่องสินค้าสิบใบที่หน้าตาเหมือนกันหมดเรียงอยู่บนชั้น ถ้าเราสลับตำแหน่งกล่อง แล้วบอกให้ใครสักคนไปหยิบ “กล่องที่สาม” เขาจะได้กล่องคนละใบกับที่เราหมายถึง

ทางแก้คือติดป้ายชื่อไว้บนกล่องแต่ละใบ — นั่นคือ key

ไม่มี keyมี key
Flutter จำแถวด้วยตำแหน่งที่เท่าไรป้ายชื่อที่เราติดให้
เมื่อสลับลำดับข้อมูลติดอยู่กับตำแหน่งข้อมูลย้ายตามตัวจริง
ประโยคเดียวที่ต้องจำ: key ตอบคำถามว่า “widget ตัวนี้คือ ใคร” ไม่ใช่ “มันอยู่ ที่ไหน”

4. บั๊กที่เกิดขึ้นจริง

สมมติรายการงานสามแถว แต่ละแถวมีช่องกรอกจำนวนที่ผู้ใช้พิมพ์ไว้แล้ว

เดิม (ยังไม่ใส่ key)
  ตำแหน่ง 0: T-01  ช่องกรอกพิมพ์ไว้ "5"
  ตำแหน่ง 1: T-02  ช่องกรอกพิมพ์ไว้ "12"
  ตำแหน่ง 2: T-03  ช่องกรอกว่าง

ผู้ใช้กดเรียงตามจำนวน → T-03 ขึ้นมาบนสุด

หลังเรียงใหม่
  ตำแหน่ง 0: T-03  ช่องกรอกยังเป็น "5"   ← ผิด! ค่าของ T-01
  ตำแหน่ง 1: T-01  ช่องกรอกยังเป็น "12"  ← ผิด!
  ตำแหน่ง 2: T-02  ช่องกรอกว่าง          ← ผิด!

เหตุผลตรงกับ 1.3 ทุกประการ: ข้อความที่พิมพ์อยู่ใน State ซึ่งผูกกับ Element ที่ตำแหน่งนั้น เมื่อ widget ใหม่มาถึง Flutter เห็นว่า “ตำแหน่ง 0 เป็น TaskRow เหมือนเดิม” จึงใช้ Element เดิม พร้อมข้อความเก่าที่ติดมาด้วย

ทางแก้คือติดป้ายชื่อ

TaskRow(
  key: ValueKey<String>(task.id),   // บอกว่าแถวนี้คือ T-01
  task: task,
)

คราวนี้ Flutter จับคู่ด้วยรหัสงาน จึงย้าย Element พร้อมข้อความไปตามตัวจริง

6. เลือก key แบบไหน

แบบใช้เมื่อตัวอย่าง
ValueKey(id)มีรหัสที่ไม่ซ้ำและไม่เปลี่ยนValueKey(task.id)
ValueKey(index)เกือบไม่ควรใช้เลยเพราะ index เปลี่ยนเมื่อเรียงใหม่ — ไม่ต่างจากไม่ใส่
UniqueKey()ตั้งใจให้เป็นของใหม่ทุกครั้งบังคับเล่นอนิเมชันซ้ำ
GlobalKeyต้องสั่งงาน State จากข้างนอกสั่งฟอร์มตรวจข้อมูล (Part 3)

เกณฑ์ของ key ที่ดีมีสองข้อ: ไม่ซ้ำในกลุ่มพี่น้องเดียวกัน และ ไม่เปลี่ยนข้าม rebuild รหัสงานจากฐานข้อมูลเข้าเกณฑ์ทั้งสอง ส่วน index ไม่เข้าข้อสอง

7. เมื่อไหร่ที่ไม่ต้องใส่ key

คนใหม่มักใส่ key ทุกที่เพราะกลัวพลาด ซึ่งทำให้โค้ดรกโดยไม่ได้อะไร

สถานการณ์ต้องใส่ไหม
รายการที่เรียงใหม่ เพิ่ม หรือลบได้ใส่
รายการที่มีช่องกรอก หรือสถานะย่อยในแต่ละแถวใส่
ต้องการหาใน widget testใส่ (ช่วยได้มาก)
widget ที่อยู่ตำแหน่งเดียวตายตัว เช่นหัวข้อหน้าจอไม่ต้อง
รายการที่แสดงอย่างเดียว ไม่มีสถานะ และลำดับไม่เปลี่ยนไม่ต้อง

8. กับดักใหญ่: UniqueKey ที่ดูเหมือนแก้ปัญหาได้

// อันตราย — สร้าง key ใหม่ทุกครั้งที่ build
TaskRow(key: UniqueKey(), task: task)
เมื่อเจอบั๊กแปลก ๆ หลายคนลอง UniqueKey() แล้วพบว่า “หายแล้ว” เพราะมันบังคับให้ทุกอย่างถูกสร้างใหม่หมด — แต่นั่นคือการซ่อนปัญหา ไม่ใช่แก้ ผลข้างเคียงที่จะตามมาคือ ช่องกรอกที่พิมพ์ไว้หายทุกครั้งที่หน้าจอวาดใหม่, รายการเด้งกลับไปบนสุดขณะเลื่อน, และอนิเมชันเริ่มใหม่ไม่หยุด

ถ้าใส่ UniqueKey() แล้วอาการดีขึ้น ให้ถามต่อว่า ทำไม Element ถึงถูกจับคู่ผิดตั้งแต่แรก คำตอบที่แท้จริงมักคือ ควรใช้ ValueKey ที่มีความหมาย หรือข้อมูลถูกเก็บผิดที่ตามที่คุยไว้ใน 1.5

อีกกับดักหนึ่งคือการสร้าง GlobalKey ใน build

// ผิด — ได้ key ใหม่ทุกรอบ ทำให้ State ถูกทิ้งทุกรอบ
Widget build(BuildContext context) {
  final formKey = GlobalKey<FormState>();
  ...
}

// ถูก — สร้างครั้งเดียวใน State
final _formKey = GlobalKey<FormState>();

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เรียงรายการใหม่แล้วข้อความในช่องกรอกสลับแถวไม่มี keyใส่ ValueKey ที่ใช้รหัสจริง
ใส่ ValueKey(index) แล้วยังสลับอยู่index เปลี่ยนตามการเรียงใช้รหัสของข้อมูล ไม่ใช่ตำแหน่ง
Duplicate keys foundมี key ซ้ำในกลุ่มพี่น้องตรวจว่ารหัสที่ใช้ไม่ซ้ำจริง
ช่องกรอกล้างตัวเองทุกครั้งที่พิมพ์ใช้ UniqueKey()เปลี่ยนเป็น ValueKey หรือเอาออก
ฟอร์มตรวจข้อมูลไม่ทำงานสร้าง GlobalKey ใน buildย้ายไปเป็น field ของ State
ใส่ key แล้วบั๊กไม่หายใส่ผิดชั้น — ต้องใส่ที่ตัวที่ถูกจัดลำดับใส่ที่ widget ระดับบนสุดของแต่ละแถว

10. แบบฝึกหัด

รายการซีเรียลที่ผู้ใช้เรียงใหม่ได้ แต่ละแถวมีช่องกรอกจำนวน

  1. ควรใส่ key แบบไหน และใส่ที่ widget ตัวไหน
  2. อธิบายว่าจะเกิดอะไรถ้าใช้ ValueKey(index)
  3. อธิบายว่าจะเกิดอะไรถ้าใช้ UniqueKey()
  4. เขียนเทสต์ที่พิสูจน์ว่าข้อมูลไม่สลับหลังเรียงใหม่
ดูแนวคำตอบและเหตุผล

ข้อ 1

ListView.builder(
  itemCount: serials.length,
  itemBuilder: (context, index) {
    final serial = serials[index];
    return SerialRow(
      key: ValueKey<String>(serial.code),   // ใส่ที่ตัวบนสุดของแถว
      serial: serial,
    );
  },
)

ใช้ serial.code เพราะเป็นค่าที่ไม่ซ้ำและติดตัวข้อมูลไปตลอด ไม่เปลี่ยนเมื่อเรียงใหม่ และต้องใส่ที่ SerialRow ซึ่งเป็นตัวที่ถูกจัดลำดับ — ถ้าไปใส่ที่ช่องกรอกข้างในจะไม่ช่วย เพราะ Flutter จับคู่ที่ระดับพี่น้องใต้ ListView

ข้อ 2 — ถ้าใช้ ValueKey(index)

ไม่ต่างจากไม่ใส่เลย เพราะแถวที่อยู่ตำแหน่ง 0 จะมี key เป็น 0 เสมอไม่ว่าข้อมูลจริงจะเป็นซีเรียลใบไหน Flutter จึงยังจับคู่ตามตำแหน่งเหมือนเดิม และข้อมูลยังสลับอยู่ดี — นี่เป็นความผิดพลาดที่พบบ่อยมาก เพราะโค้ดดู “มี key แล้ว” จึงไม่มีใครสงสัย

ข้อ 3 — ถ้าใช้ UniqueKey()

ข้อมูลจะไม่สลับจริง เพราะทุกแถวถูกสร้างใหม่หมด แต่แลกมาด้วยผลข้างเคียงที่ร้ายแรงกว่า: ช่องกรอกทุกช่องถูกล้างทุกครั้งที่หน้าจอวาดใหม่ ซึ่งเกิดบ่อยมาก ผู้ใช้จะพิมพ์ตัวเลขไม่ได้เลยเพราะทุกครั้งที่พิมพ์หนึ่งตัวอักษรแล้ว rebuild ข้อความจะหายไป

ข้อ 4 — เทสต์

testWidgets('เรียงใหม่แล้วข้อมูลไม่สลับแถว', (tester) async {
  await tester.pumpWidget(const MaterialApp(home: SerialListScreen()));

  // พิมพ์ค่าลงในแถวของ SN-001
  await tester.enterText(
    find.descendant(
      of: find.byKey(const ValueKey<String>('SN-001')),
      matching: find.byType(TextField),
    ),
    '5',
  );
  await tester.pump();

  // สั่งเรียงใหม่
  await tester.tap(find.byKey(const Key('sort-button')));
  await tester.pumpAndSettle();

  // ค่า "5" ต้องยังอยู่กับ SN-001 ไม่ว่ามันจะย้ายไปตำแหน่งไหน
  final field = tester.widget<TextField>(
    find.descendant(
      of: find.byKey(const ValueKey<String>('SN-001')),
      matching: find.byType(TextField),
    ),
  );
  expect(field.controller?.text, '5');
});

จุดสำคัญของเทสต์นี้: มันค้นหาด้วย ValueKey ไม่ใช่ด้วยตำแหน่ง จึงยังหาถูกแม้แถวจะย้ายที่ — ถ้าเขียนเทสต์โดยอ้างตำแหน่งที่เท่าไร เทสต์จะผ่านทั้งที่โค้ดผิด ซึ่งอันตรายกว่าไม่มีเทสต์

ลองต่อ: ลบ key ออกแล้วรันเทสต์นี้ ควรเห็นมันล้มเหลว — นั่นคือการยืนยันว่าเทสต์จับบั๊กนี้ได้จริง

11. สรุปท้ายบท

  • key ตอบว่า widget ตัวนี้คือ “ใคร” ไม่ใช่ “อยู่ที่ไหน”
  • จำเป็นเมื่อรายการเรียงใหม่ เพิ่ม หรือลบได้ และแต่ละแถวมีสถานะ
  • ใช้ ValueKey กับรหัสจริงของข้อมูล ไม่ใช่ index
  • ใส่ที่ widget ระดับบนสุดของแต่ละแถว
  • UniqueKey() ซ่อนบั๊กและทำให้ข้อมูลที่ผู้ใช้พิมพ์หาย
  • อย่าสร้าง GlobalKey ใน build
  • ใช้ key เป็นตัวค้นหาในเทสต์ ดีกว่าค้นด้วยข้อความ
