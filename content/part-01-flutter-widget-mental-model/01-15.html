3. ขั้นที่ 2: ตอบคำถามจากโค้ด

ตอบให้ได้ทุกข้อโดยดูจากโค้ดเท่านั้น ห้ามเดา

  1. ข้อมูล “งานใบไหนเสร็จแล้ว” เก็บอยู่ที่ไหน และทำไมถึงไม่เก็บใน TaskTile
  2. เมื่อกดที่แถวหนึ่งใบ มีอะไรถูกวาดใหม่บ้าง
  3. ทำไม _tapCount ถึงไม่ใช้ setState เหมือนตัวอื่น
  4. ใครเป็นคน dispose อะไร และทำไม
  5. ถ้าลบ key: ValueKey(task.id) ออก จะเกิดอะไรขึ้นตอนนี้ และจะเกิดอะไรขึ้นถ้าเพิ่มช่องกรอกในแต่ละแถว
ดูแนวคำตอบและเหตุผล

ข้อ 1

เก็บใน _DashboardScreenState._doneIds เพราะข้อมูลนี้มีสองฝ่ายที่ต้องใช้ — TaskTile ใช้ตัดสินว่าจะขีดฆ่าหรือไม่ และ StatCard ใบ “ยังไม่เสร็จ” ใช้คำนวณตัวเลข ตามกฎใน 1.5 ข้อมูลจึงต้องอยู่ที่แม่ร่วมที่ต่ำที่สุดของทั้งสอง

ถ้าเก็บไว้ใน TaskTile เอง จะเกิดอาการที่ 1.5 เตือนไว้พอดี: กดแล้วแถวขีดฆ่าถูกต้อง แต่ตัวเลขด้านบนไม่ลด เพราะไม่มีใครบอกมัน

ข้อ 2

เมื่อกด _toggleDone ทำสองอย่างที่มีขอบเขตต่างกัน

คำสั่งผลกระทบ
setStatebuild ของ DashboardScreen ทำงานใหม่ทั้งหมด — การ์ดสองใบและรายการทั้งหมดถูกสร้างคำอธิบายใหม่
_tapCount.value++เฉพาะ Text ข้างใน ValueListenableBuilder

แต่ตามที่เรียนใน 1.3 การสร้างคำอธิบายใหม่ไม่ได้แปลว่าสร้างของจริงใหม่ — Element และ RenderObject ของแถวที่ไม่เปลี่ยนถูกใช้ซ้ำ

ข้อ 3

เพราะจำนวนครั้งที่กดถูกใช้ที่เดียวคือข้อความบรรทัดนั้น การใช้ setState จะทำให้รายการทั้งหมดถูกวาดใหม่โดยไม่จำเป็น ซึ่งเป็นการสาธิตหลักใน 1.10 และ 1.13 ว่าเลือกเครื่องมือตาม ขอบเขตที่ข้อมูลกระทบ

ข้อ 4

_DashboardScreenState เป็นคน dispose เฉพาะ _tapCount เพราะมันสร้างเอง ส่วน _doneIds เป็น Set ธรรมดาที่ไม่ต้องคืนอะไร และ _allTasks เป็น const จึงไม่มีเจ้าของให้คืน — ตรงกับกฎความเป็นเจ้าของใน 1.6

ข้อ 5

ตอนนี้: ไม่เกิดอะไรเลย เพราะรายการไม่เคยเรียงใหม่และแต่ละแถวไม่มีสถานะภายใน

ถ้าเพิ่มช่องกรอก: เมื่อรายการเรียงใหม่หรือมีการลบแถว ข้อความที่ผู้ใช้พิมพ์จะติดอยู่กับตำแหน่งแทนที่จะติดกับงาน — คือบั๊กที่อธิบายไว้ใน 1.8 หัวข้อ 4 ทุกประการ

นี่เป็นบทเรียนสำคัญ: key ที่ “ยังไม่จำเป็นตอนนี้” เป็นการเตรียมไว้สำหรับสิ่งที่จะเกิดแน่นอนเมื่อหน้าจอโตขึ้น

4. ขั้นที่ 3: ทดลองแล้วสังเกต

ทำทีละข้อ รันดูจริง แล้วบันทึกสิ่งที่เห็น อย่าอ่านแล้วเชื่อ

การทดลองสิ่งที่ควรสังเกต
ใส่ print('build screen') ต้น build ของ _DashboardScreenState แล้วกดแถวถูกเรียกทุกครั้ง
ใส่ print('build tile') ใน TaskTile.build แล้วกดแถวถูกเรียกทุกแถว ไม่ใช่แค่แถวที่กด
เปลี่ยน _tapCount.value++ ให้เกิดอย่างเดียวโดยไม่มี setStateข้อความเปลี่ยน แต่ไม่มี print ใดถูกเรียกเลย
เปลี่ยนสีหลักใน ThemeDataทั้งแอปเปลี่ยนโดยไม่แตะโค้ดหน้าจอ
ลบ _tapCount.dispose() แล้วเข้าออกหน้าจอซ้ำ ๆยังไม่เห็นอาการทันที — เป็นเหตุผลว่าทำไมต้องมีเทสต์

ผลจากแถวที่สองคือหลักฐานตรง ๆ ของ 1.13: setState ทำให้ทั้ง build ทำงาน จึงต้องมีเครื่องมือจำกัดขอบเขตเมื่อจำเป็น

5. ขั้นที่ 4: แก้โค้ดจริง

ทำทั้งสามข้อ โดยรัน flutter analyze --no-pub และ flutter test --no-pub ทุกครั้งหลังแก้

  1. เพิ่มการ์ดใบที่สาม แสดง “เสร็จแล้ว” โดยห้ามเพิ่ม field ใหม่ใน State
  2. เพิ่มปุ่มล้างทั้งหมด ที่คืนทุกงานเป็นยังไม่เสร็จ และต้องกดไม่ได้เมื่อยังไม่มีงานไหนเสร็จ
  3. เพิ่มจำนวนรวมทุกงาน แสดงต่อท้ายข้อความนับจำนวนครั้ง โดยห้ามให้มันวาดใหม่เมื่อจำนวนครั้งเปลี่ยน
ดูแนวคำตอบและเหตุผล

ข้อ 1

// ใน _DashboardScreenState — เป็น getter ไม่ใช่ field (1.4, D1.7)
int get _doneCount => _doneIds.length;

// ใน build
Expanded(
  child: StatCard(
    key: const Key('stat-done'),
    label: 'เสร็จแล้ว',
    value: '$_doneCount',
  ),
),

ห้ามเพิ่ม field เพราะค่านี้คำนวณจาก _doneIds ได้ — ถ้าเก็บแยก วันหนึ่งจะมี method ที่ลืมอัปเดตแล้วตัวเลขสามใบไม่ตรงกัน

ข้อ 2

bool get _hasDone => _doneIds.isNotEmpty;

void _clearAll() {
  if (!_hasDone) return;              // กันที่ตรรกะด้วย ไม่ใช่แค่ที่ปุ่ม (1.5)
  setState(_doneIds.clear);
}

// ใน build
TextButton(
  key: const Key('clear-all'),
  onPressed: _hasDone ? null : null,  // <- ผิด! ดูคำอธิบายด้านล่าง
  child: const Text('ล้างทั้งหมด'),
),

บรรทัดนั้นเขียนผิดโดยตั้งใจ เพื่อชี้จุดที่คนพลาดบ่อย — เงื่อนไขต้องกลับด้าน

onPressed: _hasDone ? _clearAll : null,   // มีงานเสร็จ -> กดได้

จำหลักจาก 1.5: null แปลว่า “ไม่มีอะไรให้ทำ” ปุ่มจึงจางและกดไม่ได้เอง

ข้อ 3

ValueListenableBuilder<int>(
  valueListenable: _tapCount,
  // ส่วนนี้ไม่ขึ้นกับ _tapCount จึงสร้างครั้งเดียวแล้วใช้ซ้ำ (1.13 หัวข้อ 6)
  child: Text('ทั้งหมด ${_allTasks.length} งาน'),
  builder: (context, count, child) => Row(
    mainAxisAlignment: MainAxisAlignment.center,
    children: [
      Text('กดไปแล้ว $count ครั้ง', key: const Key('tap-count')),
      const SizedBox(width: 12),
      child!,
    ],
  ),
),

ข้อนี้คือการใช้ child ตามที่อธิบายไว้ใน 1.13 — ส่วนที่ไม่ขึ้นกับค่าที่ฟังอยู่ถูกสร้างครั้งเดียวและส่งเข้ามาใช้ซ้ำ ไม่ถูกสร้างใหม่ทุกครั้งที่ตัวนับเปลี่ยน

6. ขั้นที่ 5: เขียนเทสต์พิสูจน์

เพิ่มเทสต์ในไฟล์ test/widget_basics_test.dart อย่างน้อยสองข้อสำหรับสิ่งที่แก้ในขั้นที่ 5

ดูแนวคำตอบและเหตุผล
testWidgets('การ์ดเสร็จแล้วนับตามงานที่กด', (tester) async {
  await tester.pumpWidget(const WidgetBasicsApp());

  expect(
    tester.widget<StatCard>(find.byKey(const Key('stat-done'))).value,
    '0',
  );

  await tester.tap(find.text('จัดเก็บ PAL-1001'));
  await tester.pump();

  expect(
    tester.widget<StatCard>(find.byKey(const Key('stat-done'))).value,
    '1',
  );
});

testWidgets('ปุ่มล้างทั้งหมดกดไม่ได้เมื่อยังไม่มีงานเสร็จ', (tester) async {
  await tester.pumpWidget(const WidgetBasicsApp());

  final before = tester.widget<TextButton>(find.byKey(const Key('clear-all')));
  expect(before.onPressed, isNull);          // ปิดอยู่

  await tester.tap(find.text('จัดเก็บ PAL-1001'));
  await tester.pump();

  final after = tester.widget<TextButton>(find.byKey(const Key('clear-all')));
  expect(after.onPressed, isNotNull);        // เปิดแล้ว

  await tester.tap(find.byKey(const Key('clear-all')));
  await tester.pump();

  expect(
    tester.widget<StatCard>(find.byKey(const Key('stat-done'))).value,
    '0',
  );
});

ทำไมตรวจ onPressed แทนที่จะลองกดดู: เพราะการกดปุ่มที่ปิดอยู่ไม่ทำให้เทสต์ล้มเหลว มันแค่ไม่เกิดอะไรขึ้น ถ้าเราตรวจแค่ผลลัพธ์ เทสต์จะผ่านทั้งที่ปุ่มอาจกดได้ตอนที่ไม่ควร — การตรวจ onPressed ว่าเป็น null จึงพิสูจน์เจตนาได้ตรงกว่า

ทำไมใช้ find.byKey แทนข้อความ: ตามที่เรียนใน 1.8 หัวข้อ 5 — ข้อความอาจเปลี่ยนเมื่อรองรับหลายภาษา แต่ key ไม่เปลี่ยน

ทำไมต้อง await tester.pump() หลังกด: เพราะ setState เพียงทำเครื่องหมายว่าต้องวาดใหม่ การวาดจริงเกิดในรอบถัดไป ตามที่อธิบายใน 1.5 หัวข้อ 5 — ถ้าไม่ pump เราจะตรวจสถานะก่อนวาดใหม่และเทสต์จะล้มเหลวโดยที่โค้ดถูกต้อง

8. แบบทดสอบตัวเองก่อนไป Part 2

คุณพร้อมไปต่อเมื่อทำสิ่งเหล่านี้ได้โดยไม่เปิดดูเฉลย

  • อธิบายความต่างของ Widget, Element และ RenderObject ด้วยภาษาของตัวเอง
  • บอกได้ว่าข้อมูลชิ้นหนึ่งควรอยู่ที่ widget ไหน และให้เหตุผลได้
  • เลือกระหว่าง StatelessWidget กับ StatefulWidget ได้ถูก
  • เขียนคู่ initState/dispose ให้ครบทุกทรัพยากร
  • แก้ปัญหา context ที่หาของไม่เจอได้สองวิธี
  • บอกได้ว่าเมื่อไหร่ต้องใส่ key และเมื่อไหร่ไม่ต้อง
  • ชี้ได้ว่าโค้ดชิ้นไหนไม่ควรอยู่ใน build และควรย้ายไปไหน
  • จำกัดขอบเขต rebuild ด้วย ValueNotifier ได้
  • เขียน widget test ที่พิสูจน์พฤติกรรม ไม่ใช่แค่ตรวจว่ามีข้อความ

ข้อไหนยังไม่มั่นใจ ให้กลับไปทำแบบฝึกหัดของบทนั้นซ้ำ — การอ่านซ้ำช่วยได้น้อยกว่าการลองแก้แล้วรัน

9. สรุปปิด Part 1

  • Flutter รับคำอธิบายจากเรา แล้วจัดการของจริงให้เอง
  • สร้าง widget ใหม่บ่อยไม่ใช่ปัญหา — สิ่งที่เป็นปัญหาคือทำงานหนักผิดที่
  • คำถามสำคัญที่สุดของทุกหน้าจอคือ “ข้อมูลนี้เป็นของใคร”
  • ข้อมูลไหลลงผ่าน constructor เหตุการณ์ไหลขึ้นผ่าน callback
  • ทุกอย่างที่เริ่มไว้ต้องมีคนคืน
  • ขอบเขตของ rebuild สำคัญกว่ารายละเอียดปลีกย่อยเรื่องประสิทธิภาพ
  • โค้ดที่แตกดีคือโค้ดที่ทดสอบทีละชิ้นได้

ต่อจากนี้: Part 2 จะตอบคำถามที่เราหลบมาตลอด — Flutter ตัดสินใจอย่างไรว่า widget แต่ละตัวควรมีขนาดเท่าไรและอยู่ตรงไหน ซึ่งเป็นที่มาของแถบสีเหลืองดำที่คุณจะได้เจอแน่นอน
