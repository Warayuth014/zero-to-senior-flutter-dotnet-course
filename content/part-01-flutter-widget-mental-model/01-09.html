build() ต้องเป็นการแปลง current configuration/state/context → widgets ที่ทำซ้ำได้ ปราศจาก side effect ที่ต้องเกิดครั้งเดียว เพราะ framework เรียก buildเมื่อไรก็ได้ตาม dependency/frame scheduling

1. สิ่งที่ทำใน buildได้

  • คำนวณ derived valuesเร็ว ๆ
  • เลือก widgetจาก enum/state
  • สร้าง callbacksที่เรียก commandภายหลัง
  • อ่าน Theme/MediaQuery/Localizations
  • ประกอบ widgets/collections

2. สิ่งที่ไม่ควรทำ

@override
Widget build(BuildContext context) {
  repository.loadTasks(); // ผิด: ทุก rebuild ยิงใหม่
  timer = Timer(...);     // ผิด: resource ซ้ำ
  store.addListener(...); // ผิด: listener ทวีคูณ
  return const SizedBox();
}

ย้ายครั้งแรกไป initState/store load command; dependencyเปลี่ยนใช้ didUpdateWidget/didChangeDependencies; user actionไป callback

3. Build อาจรันบ่อยเพราะอะไร

setState, parent update, Listenable builder, inherited dependency, animation และ hot reload ล้วนเรียก buildได้ โค้ดที่ “ตอนนี้เห็นรันครั้งเดียว” ไม่มีสัญญาว่าจะเป็นเช่นนั้น

4. API load pattern

State ownerถือ loading/data/error แล้วเริ่ม loadครั้งเดียวตาม lifecycle หรือ event; buildอ่าน snapshotและเลือก Loading/Error/Empty/Data อย่าสร้าง Futureใหม่ทุก buildให้ FutureBuilder ถ้าจะใช้ให้ cache Futureใน Stateและเปลี่ยนเมื่อ inputเปลี่ยน

5. ตัวอย่าง absolute shell

Shell สร้าง storeและ unawaited(store.loadAll()) ใน initState จากนั้น buildใช้ ListenableBuilderอ่าน store ส่วน _body() เป็น pure switchคืน screenตาม store.screen นี่แยก side effectจาก renderingชัด

6. Derived work ที่แพง

Filter/sort listใหญ่มากใน buildอาจ pureแต่ช้า ให้ derive/cachingใน state layerตาม input revisionหรือใช้ memoizationที่ correct ก่อน optimizeต้อง profile อย่า cache widget/contextแบบทำให้ข้อมูลเก่า

7. แบบฝึกหัด

หน้า Task ต้องโหลดเมื่อ taskIdเปลี่ยน ออกแบบ lifecycleโดยไม่ยิงใน build

เฉลย

เริ่ม loadใน initStateจาก initial widget.taskId; ใน didUpdateWidgetเทียบ old/new idแล้ว loadใหม่/cancelหรือ generation token; set state/storeตามผล; buildแสดง snapshotเท่านั้น

8. จุดพลาด

การห่อ side effectด้วย Future.microtask หรือ post-frame callbackจาก buildไม่ได้ทำให้ถูก ถ้า buildซ้ำก็ scheduleซ้ำ ต้องมี owner/event/lifecycle invariantที่ชัด
