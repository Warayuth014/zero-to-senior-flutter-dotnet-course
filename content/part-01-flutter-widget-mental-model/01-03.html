จบบทนี้แล้วจะทำได้: อธิบายได้ว่า Flutter เก็บอะไรไว้ที่ไหน และตอบคำถามที่คนใหม่สงสัยมากที่สุดว่า “สร้าง widget ใหม่ทุกครั้ง ทำไมไม่ช้า”

1. ปัญหาที่บทนี้แก้

ในบทหน้า ๆ เราจะเจอคำว่า “rebuild” ตลอดเวลา และจะเห็นว่าเมื่อข้อมูลเปลี่ยนหนึ่งค่า Flutter จะเรียกฟังก์ชันที่สร้าง widget ทั้งหน้าจอใหม่หมด

คำถามที่ตามมาทันทีคือ “สร้างทุกอย่างใหม่ทุกครั้งแบบนี้ แอปจะไม่ช้าเหรอ” — คำตอบคือไม่ช้า และเหตุผลอยู่ในบทนี้ ถ้าเข้าใจตรงนี้ บทที่เหลือทั้ง Part จะง่ายขึ้นมาก

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
Widgetคำอธิบายว่าอยากได้อะไร — เบามาก สร้างทิ้งได้
Elementตัวจริงที่อยู่ในหน้าจอ จำได้ว่าตัวเองอยู่ตำแหน่งไหน
RenderObjectตัวที่คำนวณขนาด ตำแหน่ง และวาดจริง — หนักที่สุด
rebuildการเรียกฟังก์ชัน build เพื่อสร้างคำอธิบายชุดใหม่
immutableสร้างแล้วแก้ไม่ได้ (จาก D1.3)
reconcileการเทียบของใหม่กับของเก่าเพื่อหาว่าอะไรเปลี่ยนจริง

3. Mental model: ใบสั่งงาน ช่าง และของจริง

ให้คิดถึงการสั่งจัดชั้นวางของในคลัง

ในคลังใน Flutterราคาในการสร้างใหม่
ใบสั่งงาน ที่เขียนว่า “ชั้นนี้ป้าย A-01 สินค้า 12 ชิ้น”Widgetถูกมาก — แค่กระดาษหนึ่งใบ
ช่างประจำชั้นนั้น ที่รู้ว่าตัวเองดูแลชั้นไหนElementแพง — ไม่สร้างใหม่ถ้าไม่จำเป็น
ชั้นวางจริง ที่ตั้งอยู่ในคลังRenderObjectแพงมาก — ยิ่งไม่สร้างใหม่

เมื่อจำนวนสินค้าเปลี่ยนจาก 12 เป็น 13 เราไม่ได้รื้อชั้นทิ้งแล้วสร้างใหม่ เราแค่เขียนใบสั่งงานใบใหม่ส่งให้ช่างคนเดิม แล้วช่างไปเปลี่ยนป้ายตัวเลข

ประโยคเดียวที่ต้องจำ: เราสร้าง ใบสั่งงาน ใหม่ทุกครั้ง แต่ Flutter ไม่ได้สร้าง ของจริง ใหม่ — นี่คือเหตุผลทั้งหมดว่าทำไม rebuild ถึงไม่แพง

4. Widget ถูกทิ้งได้เพราะมันเบา

Text('$_itemCount รายการ')

บรรทัดนี้สร้าง object ใหม่ทุกครั้งที่หน้าจอวาดใหม่ ซึ่งฟังดูน่ากลัว แต่ object นี้เก็บแค่ข้อความหนึ่งชุดกับรูปแบบตัวอักษร — พอ ๆ กับการสร้างตัวแปรธรรมดา ไม่ได้แตะหน้าจอเลย

ทบทวนจาก D1.3: widget ทุกตัวมี field เป็น final ทั้งหมด สร้างแล้วแก้ไม่ได้ นั่นคือเหตุผลที่มันปลอดภัยจะทิ้งแล้วสร้างใหม่ เพราะไม่มีใครถือสถานะอะไรไว้ในนั้น

5. Element ตัดสินใจว่าจะเก็บหรือทิ้ง

เมื่อได้ใบสั่งงานใหม่มา Flutter เทียบกับใบเดิมด้วยคำถามสองข้อ

คำถามถ้าตอบว่า “เหมือน”ถ้าตอบว่า “ต่าง”
เป็น widget ชนิดเดียวกัน ไหมเก็บ Element เดิมไว้ทิ้งของเดิมทั้งกิ่ง สร้างใหม่
มี key ตรงกันไหม (ถ้ามี)เก็บ Element เดิมไว้ทิ้งของเดิมทั้งกิ่ง สร้างใหม่
เดิม:  Text('12 รายการ')
ใหม่:  Text('13 รายการ')
       → ชนิดเดียวกัน (Text) → ใช้ Element เดิม แค่เปลี่ยนข้อความ

เดิม:  Text('12 รายการ')
ใหม่:  Icon(Icons.check)
       → คนละชนิด → ทิ้งของเดิม สร้างใหม่

เรื่อง key จะอธิบายเต็ม ๆ ใน 1.8 ตอนนี้แค่รู้ว่ามันคือวิธีบอก Flutter ว่า “ถึงจะย้ายที่ ก็ยังเป็นตัวเดิมนะ”

6. State ผูกกับ Element ไม่ใช่ Widget

นี่คือข้อที่สำคัญที่สุดในบทนี้ และเป็นรากของบั๊กที่งงที่สุดใน Flutter

เมื่อหน้าจอมีข้อมูลที่เปลี่ยนได้ เช่นจำนวนที่นับได้ในแอป lab ข้อมูลนั้นไม่ได้เก็บไว้ใน widget (ซึ่งถูกทิ้งทุกรอบ) แต่เก็บไว้กับ Element ซึ่งอยู่ยาว

Widget ถูกสร้างใหม่:   ครั้งที่ 1 → ครั้งที่ 2 → ครั้งที่ 3 ...
Element อยู่ตัวเดิม:   ────────────────────────────────→
ข้อมูล _itemCount:     อยู่กับ Element จึงไม่หายไปตอน rebuild

ผลที่ตามมาคือ ถ้า Element ถูกทิ้ง ข้อมูลจะหายไปด้วย ซึ่งเป็นสาเหตุของอาการอย่าง “ตัวเลขที่นับไว้รีเซ็ตเป็นศูนย์เอง” หรือ “ข้อความที่พิมพ์ในช่องกรอกหายไป” เมื่อสลับหน้าจอ — เราจะเจอตัวอย่างจริงและวิธีป้องกันใน 1.8

7. build ไม่เท่ากับวาด

คำที่คนมักใช้ปนกันคือ “build”, “layout” และ “paint” ซึ่งเป็นคนละขั้นตอนและแก้ปัญหาคนละแบบ

ขั้นตอนทำอะไรปัญหาที่เกี่ยวข้องเรียนใน
buildสร้างใบสั่งงานชุดใหม่ทำงานหนักผิดที่ใน build1.9
layoutคำนวณว่าแต่ละชิ้นใหญ่แค่ไหน อยู่ตรงไหนเนื้อหาล้นจอ แถบสีเหลืองดำPart 2
paintวาดสีและเส้นลงจริงอนิเมชันกระตุกPart 14

เวลาเจออาการช้า อย่ารีบสรุปว่า “Flutter ช้า” ให้ถามก่อนว่าช้าที่ขั้นไหน เพราะทางแก้ต่างกันสิ้นเชิง

8. ข้อผิดพลาดที่พบบ่อย

ความเข้าใจผิดความจริง
“ต้องเลี่ยง rebuild ให้ได้มากที่สุด”rebuild เป็นเรื่องปกติและถูก — สิ่งที่ต้องเลี่ยงคือทำงานหนักใน build
“สร้าง widget ใหม่ = สร้างหน้าจอใหม่”สร้างแค่คำอธิบาย ส่วนของจริงถูกใช้ซ้ำ
“ข้อมูลเก็บไว้ใน widget”เก็บกับ Element — widget ถูกทิ้งทุกรอบ
“ใส่ const เยอะ ๆ แล้วแอปจะเร็ว”ช่วยได้บ้าง แต่ตัวชี้ขาดคือ ขอบเขต ของ rebuild (1.10)
“แอปกระตุก แปลว่า rebuild เยอะ”อาจเป็น layout หรือ paint ก็ได้ — ต้องวัดก่อน

9. แบบฝึกหัด

เปิด lab แล้วรัน

Set-Location .\labs\flutter_wms_companion
flutter run -d chrome -t lib/beginner_main.dart
  1. กดปุ่ม “เพิ่มสินค้า” หลายครั้ง แล้วอธิบายว่าเกิดอะไรขึ้นกับ Widget, Element และ RenderObject ในแต่ละครั้ง
  2. ตอบว่าทำไมค่าที่นับไว้ถึงไม่รีเซ็ตทุกครั้งที่กด ทั้งที่ build ถูกเรียกใหม่ทั้งหมด
  3. คาดเดาว่าถ้าเปลี่ยน Text ที่แสดงจำนวนให้กลายเป็น Icon เมื่อจำนวนเกิน 5 จะเกิดอะไรขึ้นกับ Element ตัวนั้น
ดูแนวคำตอบและเหตุผล

ข้อ 1 — แต่ละครั้งที่กด

ชั้นเกิดอะไรขึ้น
Widgetสร้างใหม่ทั้งหน้าจอ — Scaffold, Column, Text, ปุ่มทุกตัว เป็น object ชุดใหม่หมด
Elementไม่มีตัวไหนถูกทิ้งเลย เพราะชนิดของ widget ทุกตัวเหมือนเดิมทุกตำแหน่ง
RenderObjectเกือบทั้งหมดอยู่เฉย ๆ มีเฉพาะตัวที่วาดข้อความจำนวนที่ถูกสั่งให้วาดใหม่ เพราะข้อความเปลี่ยนจริง

ข้อ 2 — ทำไมค่าไม่รีเซ็ต

เพราะ _itemCount ไม่ได้อยู่ใน widget แต่อยู่กับ Element ซึ่งไม่ถูกทิ้ง — widget ที่ถูกสร้างใหม่เป็นเพียงคำอธิบายว่า “ให้แสดงตัวเลขที่ Element ถืออยู่ตอนนี้” ถ้าค่าอยู่ใน widget จริง มันจะรีเซ็ตเป็นศูนย์ทุกครั้งที่กด และแอปนี้จะใช้งานไม่ได้เลย

ข้อ 3 — เปลี่ยนชนิด widget

เมื่อ Text กลายเป็น Icon ในตำแหน่งเดิม Flutter เห็นว่าชนิดไม่ตรง จึง ทิ้ง Element เดิมทั้งกิ่งแล้วสร้างใหม่ ในกรณีนี้ไม่มีผลเสียอะไร เพราะ Text ไม่ได้ถือข้อมูลอะไรไว้

แต่ถ้าตำแหน่งนั้นเป็นช่องกรอกข้อความที่ผู้ใช้พิมพ์ไว้แล้ว หรือรายการที่เลื่อนไปครึ่งทาง การสลับชนิดจะทำให้ข้อมูลเหล่านั้นหายทันที — นี่คือเหตุผลที่ต้องเข้าใจ Element ก่อนจะไปเรียนเรื่อง key ใน 1.8

ลองพิสูจน์ด้วยตัวเอง: เพิ่ม print('build ทำงาน') ไว้บรรทัดแรกของ build ใน _WarehouseCounterScreenState แล้วดู console ตอนกดปุ่ม — จะเห็นว่ามันถูกเรียกทุกครั้ง แต่หน้าจอยังลื่นและค่าไม่หาย

10. สรุปท้ายบท

  • Widget = คำอธิบาย เบามาก สร้างทิ้งได้ตลอด
  • Element = ตัวจริงในหน้าจอ อยู่ยาว และถือข้อมูลไว้
  • RenderObject = ตัวคำนวณขนาดและวาด แพงที่สุด
  • Flutter เทียบชนิดและ key เพื่อตัดสินว่าจะเก็บ Element เดิมไว้ไหม
  • ข้อมูลอยู่กับ Element — ถ้า Element ถูกทิ้ง ข้อมูลหายด้วย
  • build, layout, paint เป็นคนละขั้น และแก้ปัญหาคนละแบบ
