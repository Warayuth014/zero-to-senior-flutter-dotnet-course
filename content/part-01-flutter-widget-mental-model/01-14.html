ระดับ: กลางใช้เวลา: 30–40 นาทีลงมือทำ: ส่งข้อมูลลงไปหลายชั้นโดยไม่ผ่าน constructor
ต้องผ่านอะไรมาก่อน: 1.7 (BuildContext และการเดินขึ้นหา ancestor) และ 1.12 (ส่งข้อมูลผ่าน constructor)
จบบทนี้แล้วจะทำได้: อธิบายได้ว่า Theme.of(context) ทำงานอย่างไร และตัดสินได้ว่าเมื่อไหร่ควรส่งผ่าน constructor เมื่อไหร่ควรใช้กลไกนี้

1. ปัญหาที่บทนี้แก้

ใน 1.12 เราส่งข้อมูลจากแม่ลงลูกผ่าน constructor ซึ่งใช้ได้ดีเมื่อห่างกันชั้นเดียว แต่ถ้าข้อมูลต้องเดินทางลึกลงไปหลายชั้นล่ะ

หน้าจอ (มีข้อมูลผู้ใช้)
└── Column
    └── Card
        └── Padding
            └── Row
                └── ชื่อผู้ใช้   ← ต้องใช้ข้อมูล

ถ้าส่งผ่าน constructor ทุกชั้น widget กลาง ๆ ทั้งสี่ตัวต้องรับข้อมูลที่ตัวเองไม่ได้ใช้ เพียงเพื่อส่งต่อ — เรียกว่าปัญหา “ส่งของผ่านมือ”

Flutter แก้ปัญหานี้ด้วยกลไกที่เราใช้มาตลอดโดยไม่รู้ตัว: Theme.of(context)

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
InheritedWidgetwidget ที่วางข้อมูลไว้ให้ลูกหลานทุกชั้นหยิบใช้ได้
scopeขอบเขตที่ข้อมูลนั้นมีผล คือทุกอย่างที่อยู่ใต้มัน
dependentwidget ที่ลงทะเบียนไว้ว่าใช้ข้อมูลนั้น
updateShouldNotifymethod ที่ตัดสินว่าค่าใหม่ต่างพอที่จะแจ้งไหม

3. Mental model: ป้ายที่ติดผนังห้อง

ทบทวนจาก 1.7: .of(context) คือการ เดินขึ้นไปตามต้นไม้เพื่อหาของ

MaterialApp          ← ติดป้าย "ธีม" ไว้ที่นี่
└── Scaffold
    └── Card
        └── Text     ← เดินขึ้นไปอ่านป้าย เจอที่ MaterialApp

ความพิเศษที่มากกว่าการอ่านเฉย ๆ คือ มันจดชื่อคนที่มาอ่านไว้ด้วย เมื่อป้ายเปลี่ยน คนที่เคยอ่านจะถูกเรียกให้มาวาดใหม่ ส่วนคนที่ไม่เคยอ่านจะไม่ถูกรบกวนเลย

ประโยคเดียวที่ต้องจำ: การเรียก .of(context) ไม่ใช่แค่การอ่านค่า แต่เป็นการ สมัครรับข่าว — นี่คือเหตุผลที่เปลี่ยนธีมแล้วทั้งแอปเปลี่ยนตามได้เองโดยไม่มีใครเขียนโค้ดสั่ง

4. สิ่งที่ใช้กลไกนี้อยู่แล้ว

เรียกอย่างไรให้อะไรใช้มาตั้งแต่
Theme.of(context)ชุดสีและตัวอักษร1.2
MediaQuery.of(context)ขนาดหน้าจอ ระยะปลอดภัยPart 2
Navigator.of(context)ตัวจัดการหน้าจอPart 5
ScaffoldMessenger.of(context)ตัวแสดงข้อความแจ้งเตือน1.7

ทั้งหมดนี้ทำงานแบบเดียวกัน — และปัญหา “หา Scaffold ไม่เจอ” ใน 1.7 ก็คือกรณีที่เดินขึ้นไปแล้วไม่พบป้าย เพราะป้ายอยู่ข้างล่าง

5. เขียนของตัวเอง

class SessionScope extends InheritedWidget {
  const SessionScope({
    super.key,
    required this.userName,
    required super.child,
  });

  final String userName;

  // ทางเข้ามาตรฐานที่คนอื่นเรียกใช้
  static SessionScope of(BuildContext context) {
    final scope = context.dependOnInheritedWidgetOfExactType<SessionScope>();
    assert(scope != null, 'ต้องมี SessionScope อยู่เหนือขึ้นไป');
    return scope!;
  }

  // ค่าใหม่ต่างจากเดิมพอที่จะแจ้งไหม
  @override
  bool updateShouldNotify(SessionScope oldWidget) =>
      oldWidget.userName != userName;
}
// วางไว้ชั้นบน
SessionScope(
  userName: 'สมชาย',
  child: const DashboardScreen(),
)

// ลูกหลานชั้นไหนก็หยิบใช้ได้ โดยชั้นกลางไม่ต้องรู้เรื่อง
Text(SessionScope.of(context).userName)

updateShouldNotify คือจุดที่ควบคุมประสิทธิภาพ — ถ้าคืน true เสมอ ทุกคนที่อ่านจะวาดใหม่ทุกครั้งแม้ค่าจะเท่าเดิม ถ้าเทียบไม่ครบ บางคนจะแสดงค่าเก่า

6. ตัวมันเองเปลี่ยนค่าไม่ได้

InheritedWidget เป็น widget จึง immutable ตามกฎใน 1.4 — มันแค่ ส่งต่อ ข้อมูล ไม่ใช่ เจ้าของ ข้อมูล

StatefulWidget          ← เจ้าของข้อมูลจริง เปลี่ยนค่าด้วย setState
└── SessionScope        ← ตัวส่งต่อ สร้างใหม่ทุกครั้งที่ค่าเปลี่ยน
    └── ลูกหลานทั้งหมด    ← หยิบใช้

ดังนั้นการใช้งานจริงต้องมีสองส่วนเสมอ: ส่วนที่เก็บข้อมูล (ตามที่เรียนใน 1.5 และ 1.13) กับส่วนที่กระจายข้อมูล ซึ่งเป็นบทนี้

ในโปรเจกต์จริงเรามักไม่เขียน InheritedWidget เองเพราะต้องเขียนสองส่วนนี้ทุกครั้ง แต่ใช้เครื่องมือสำเร็จรูปที่ห่อทั้งสองส่วนไว้ให้แล้ว ซึ่งจะเรียนใน Part 27 — สิ่งสำคัญคือรู้ว่าข้างในมันคือกลไกนี้

7. constructor หรือ scope — เลือกอย่างไร

สถานการณ์ใช้เหตุผล
ห่างกันหนึ่งถึงสองชั้นconstructorเห็นชัดว่าใครใช้อะไร
ข้อมูลเฉพาะของ widget นั้นconstructorไม่มีใครอื่นต้องใช้
ลูกหลานจำนวนมากข้ามหลายชั้นต้องใช้scopeชั้นกลางไม่ต้องรับของที่ไม่ใช้
เป็นค่าระดับแอปหรือระดับส่วนงาน เช่น ธีม ผู้ใช้ ภาษาscopeเป็นนโยบายของทั้งขอบเขต
อย่าใช้ scope เพียงเพื่อลด parameter สองชั้น เพราะข้อเสียคือ dependency หายไปจากสายตา — เมื่ออ่าน constructor ของ widget เราจะไม่รู้อีกต่อไปว่ามันต้องใช้อะไรบ้าง ต้องไล่อ่านทั้ง build ผลคือทดสอบยากขึ้นเพราะต้องรู้ว่าต้องเตรียม scope อะไรครอบไว้

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เรียก of(context) แล้วได้ null หรือ assert ล้มเหลวcontext อยู่เหนือ scopeใช้ Builder หรือแยก widget ย่อย (1.7)
ค่าเปลี่ยนแล้วหน้าจอไม่อัปเดตupdateShouldNotify คืน false ผิดเทียบให้ครบทุก field ที่มีคนใช้
ทั้งแอปวาดใหม่ทุกครั้งที่ค่าเล็ก ๆ เปลี่ยนupdateShouldNotify คืน true เสมอเทียบค่าจริง หรือแยกเป็นหลาย scope
เทสต์ล้มเหลวเพราะหา scope ไม่เจอลืมครอบ scope ในเทสต์ครอบให้ครบ หรือเปลี่ยนมาส่งผ่าน constructor
ไม่รู้ว่า widget ต้องใช้อะไรบ้างใช้ scope มากเกินไปส่งผ่าน constructor เมื่อใกล้กัน

9. แบบฝึกหัด

แอปมีข้อมูลสามชุด จงเลือกวิธีส่งให้แต่ละชุดพร้อมเหตุผล

  1. ชื่อและสิทธิ์ของผู้ใช้ที่ล็อกอิน — ใช้ในเกือบทุกหน้าจอ ลึกหลายชั้น
  2. ข้อมูลงานหนึ่งใบที่ส่งให้แถวในรายการ
  3. โหมดมืด/สว่าง ที่ผู้ใช้สลับได้

แล้วอธิบายว่าถ้าเลือกผิด จะเกิดปัญหาอะไร

ดูแนวคำตอบและเหตุผล
ข้อวิธีเหตุผล
1scopeลูกหลานจำนวนมากข้ามหลายชั้นต้องใช้ และเป็นค่าระดับ session
2constructorแถวนั้นใช้คนเดียว ห่างชั้นเดียว และต้องเห็นชัดว่าแถวนี้แสดงงานใบไหน
3scope (ใช้ของที่มีอยู่แล้ว)เป็นนโยบายทั้งแอป และ Theme.of(context) ทำให้อยู่แล้ว

ถ้าข้อ 1 เลือกผิดเป็น constructor

widget กลางทางทุกตัวต้องรับ user เข้ามาแล้วส่งต่อ ทั้งที่ตัวเองไม่ได้ใช้ พอเพิ่ม field ใหม่ในข้อมูลผู้ใช้ ต้องไล่แก้ทุกชั้น และเมื่ออ่าน Padding(user: user, ...) คนอ่านจะสับสนว่าทำไม Padding ต้องรู้จักผู้ใช้

ถ้าข้อ 2 เลือกผิดเป็น scope

จะพังทันที เพราะ scope ให้ค่าเดียวกับทุกคนที่อยู่ใต้มัน แต่รายการมีร้อยแถวที่ต้องแสดงงานคนละใบ — ถ้าจะทำจริงต้องสร้าง scope หนึ่งอันต่อแถว ซึ่งซับซ้อนกว่าการส่งผ่าน constructor มาก และไม่ได้อะไรกลับมาเลย

บทเรียนจากข้อ 2: scope เหมาะกับข้อมูลที่ เหมือนกันทั้งขอบเขต ไม่ใช่ข้อมูลที่ต่างกันไปตามแต่ละชิ้น — นี่คือเกณฑ์ที่ใช้ตัดสินได้เร็วที่สุด

ถ้าข้อ 3 เลือกผิดเป็น constructor

ทุก widget ที่ต้องใช้สีจะต้องรับสีเข้ามา และเมื่อผู้ใช้สลับโหมด เราต้องไล่ส่งค่าใหม่ลงไปทุกชั้นด้วยตัวเอง ซึ่งเป็นงานที่ Flutter ทำให้อยู่แล้วผ่าน Theme — การเขียนเองใหม่จึงเป็นการทำงานซ้ำและมีโอกาสลืมบางจุด

ลองต่อ: เขียน SessionScope ตามหัวข้อ 5 แล้วลองเรียก SessionScope.of(context) จาก build ของ widget ที่อยู่ เหนือ scope — จะเห็น assert ล้มเหลว ซึ่งเป็นอาการเดียวกับ “หา Scaffold ไม่เจอ” ใน 1.7 เพราะเป็นกลไกเดียวกัน

10. สรุปท้ายบท

  • InheritedWidget วางข้อมูลไว้ให้ลูกหลานทุกชั้นหยิบใช้
  • .of(context) ไม่ใช่แค่อ่านค่า แต่เป็นการสมัครรับข่าวด้วย
  • Theme, MediaQuery, Navigator ล้วนใช้กลไกนี้
  • ตัวมันเองเปลี่ยนค่าไม่ได้ — ต้องมีเจ้าของข้อมูลอยู่เหนือขึ้นไป
  • updateShouldNotify เป็นตัวควบคุมว่าใครต้องวาดใหม่
  • ใช้ scope กับข้อมูลที่เหมือนกันทั้งขอบเขต ใช้ constructor กับข้อมูลที่ต่างกันไปตามชิ้น
  • ใช้ scope มากเกินไปทำให้ dependency หายไปจากสายตาและทดสอบยาก
