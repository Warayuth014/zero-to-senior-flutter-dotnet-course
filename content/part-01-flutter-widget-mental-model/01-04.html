ระดับ: เริ่มต้นใช้เวลา: 30–40 นาทีลงมือทำ: เขียน widget ตัวแรกของตัวเอง
ต้องผ่านอะไรมาก่อน: 1.1–1.3 (widget tree และความต่างระหว่าง Widget กับ Element) และ D1.6–D1.8 (class, constructor, extends, @override)
จบบทนี้แล้วจะทำได้: สร้าง widget ของตัวเองด้วย StatelessWidget รับข้อมูลผ่าน constructor และเข้าใจว่าคำว่า “stateless” หมายถึงอะไรจริง ๆ

1. ปัญหาที่บทนี้แก้

จนถึงตอนนี้เราใช้แต่ widget สำเร็จรูปของ Flutter อย่าง Text และ Center แต่หน้าจอจริงมีชิ้นส่วนที่ซ้ำกัน เช่นการ์ดแสดงตัวเลขสถิติที่มีสามใบเรียงกัน ถ้าเขียนซ้ำสามรอบ พอต้องแก้รูปแบบก็ต้องแก้สามที่

ทางออกคือสร้าง widget ของเราเอง ซึ่งก็คือการเขียน class ธรรมดาที่สืบทอดจาก StatelessWidget — ทุกอย่างที่เรียนใน D1.8 ใช้ได้ตรง ๆ

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
StatelessWidgetwidget ที่ไม่ถือข้อมูลที่เปลี่ยนได้ของตัวเอง
buildmethod ที่คืนว่าหน้าตาควรเป็นอย่างไร
BuildContextข้อมูลว่า widget นี้อยู่ตรงไหนของ tree (เต็ม ๆ ใน 1.7)
super.keyส่ง key ต่อให้แม่ (เต็ม ๆ ใน 1.8)
derived valueค่าที่คำนวณจากค่าอื่นได้ ไม่ต้องเก็บซ้ำ (จาก D1.7)

3. Mental model: ฟังก์ชันที่คืนหน้าตา

ให้คิดว่า StatelessWidget คือ ฟังก์ชันที่รับข้อมูลแล้วคืนหน้าตา

ข้อมูลเข้า  →  [ StatelessWidget ]  →  หน้าตาที่ควรเป็น
(label, value)                        (การ์ดหนึ่งใบ)

คุณสมบัติที่สำคัญคือ ข้อมูลเข้าชุดเดิม ต้องได้หน้าตาชุดเดิมเสมอ ซึ่งแปลว่ามันไม่มีความจำ ไม่มีอารมณ์ ไม่ขึ้นกับว่าถูกเรียกเป็นครั้งที่เท่าไร

เข้าใจผิดที่พบบ่อยที่สุด: คำว่า “stateless” ไม่ได้แปลว่า “สร้างครั้งเดียวแล้วไม่เปลี่ยนอีก” — มันแปลว่า “ไม่ถือข้อมูลที่เปลี่ยนได้ของตัวเอง” widget แบบนี้ถูก build ใหม่บ่อยมาก และควรถูก build ใหม่ด้วย เพราะนั่นคือวิธีที่มันแสดงข้อมูลใหม่

4. เขียน widget ตัวแรก

เปิด lib/widget_basics/widget_basics_app.dart ใน lab แล้วดู StatCard

class StatCard extends StatelessWidget {
  const StatCard({super.key, required this.label, required this.value});

  final String label;
  final String value;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.symmetric(vertical: 16, horizontal: 12),
        child: Column(
          children: [
            Text(value, style: Theme.of(context).textTheme.headlineMedium),
            const SizedBox(height: 4),
            Text(label, style: Theme.of(context).textTheme.bodySmall),
          ],
        ),
      ),
    );
  }
}

อ่านทีละส่วน — ทุกอย่างคือ Dart ที่เรียนมาแล้ว

ส่วนคืออะไรเรียนมาจาก
extends StatelessWidgetสืบทอดเพื่อรับสัญญาว่าต้องมี buildD1.8
const StatCard({...})constructor แบบ named parameterD1.4, D1.6
required this.labelทางลัดรับค่าแล้วเก็บลง fieldD1.6
final String labelfield ที่ตั้งครั้งเดียวแล้วห้ามเปลี่ยนD1.3
@override Widget buildเขียนทับ method ที่แม่บังคับไว้D1.8

ใช้งานเหมือนเรียก widget สำเร็จรูปทุกประการ

StatCard(label: 'งานทั้งหมด', value: '3')

5. ทำไม field ต้องเป็น final ทั้งหมด

ทบทวนจาก 1.3: widget ถูกทิ้งและสร้างใหม่ตลอดเวลา ถ้าเราแอบเปลี่ยนค่าใน field ของมัน

  • ไม่มีใครรู้ว่าค่าเปลี่ยน หน้าจอจึงไม่อัปเดต
  • รอบถัดไปที่ widget ถูกสร้างใหม่ ค่านั้นหายไปทันที

Flutter จึงบังคับให้ทุก field เป็น final ตั้งแต่ตอน compile ซึ่งเป็นการป้องกันที่ดี ไม่ใช่ข้อจำกัดที่น่ารำคาญ

ถ้าคุณรู้สึกอยากเปลี่ยนค่าใน StatelessWidget แสดงว่าข้อมูลนั้นควรอยู่ที่อื่น — คำตอบว่าที่ไหนอยู่ในบทหน้า

6. ค่าที่คำนวณได้ อย่าเก็บซ้ำ

// ดี — คำนวณตอน build
@override
Widget build(BuildContext context) {
  final isEmpty = value == '0';
  return Card(
    color: isEmpty ? Colors.grey.shade200 : null,
    ...
  );
}

// แย่ — เก็บเป็น field ที่ต้องคอยอัปเดตให้ตรง
final bool isEmpty;   // วันหนึ่งจะไม่ตรงกับ value

หลักการเดียวกับ getter ใน D1.7: ถ้าคำนวณจากค่าอื่นได้ อย่าเก็บซ้ำ เพราะข้อมูลสองชุดที่ต้อง “ตรงกัน” จะมีวันที่ไม่ตรงกันเสมอ

ตัวอย่างค่าที่ควรคำนวณใน build ไม่ใช่เก็บไว้: สีตามสถานะ, ข้อความจาก enum, ป้ายแจ้งเตือนจากจำนวนที่มากกว่าศูนย์

7. เมื่อไหร่ที่ StatelessWidget ถูก build ใหม่

สาเหตุตัวอย่าง
widget แม่ถูก build ใหม่หน้าจอเปลี่ยนจำนวนที่นับได้
ธีมเปลี่ยนผู้ใช้สลับโหมดมืด
ขนาดหน้าจอเปลี่ยนหมุนอุปกรณ์
ภาษาเปลี่ยนผู้ใช้เปลี่ยนเป็นภาษาอังกฤษ
เพราะ build ถูกเรียกได้บ่อยและคาดเดาเวลาไม่ได้ จึง ห้ามทำงานที่มีผลข้างเคียงใน build เช่นยิง API บันทึกข้อมูล หรือเริ่มจับเวลา — เหตุผลเต็ม ๆ และตัวอย่างจริงอยู่ใน 1.9

8. แตก widget ย่อยเมื่อไหร่

เกณฑ์ที่ใช้ได้จริงมีสามข้อ ถ้าเข้าข้อใดข้อหนึ่งก็ควรแตก

  1. ใช้ซ้ำ — ชิ้นส่วนเดียวกันปรากฏมากกว่าหนึ่งที่ เช่น StatCard ที่ใช้สองใบ
  2. ตั้งชื่อได้ — ถ้าเรียกส่วนนั้นด้วยคำเดียวได้ เช่น “แถวงาน” แปลว่ามันเป็นสิ่งของหนึ่งชิ้น
  3. อ่านยาก — build ยาวจนต้องเลื่อนจอเพื่อดูให้จบ

ข้อดีที่ตามมาซึ่งคนมักไม่คาดคิด: widget ที่แตกออกมาแล้ว ทดสอบแยกได้ ดูตัวอย่างจากเทสต์ของ lab

await tester.pumpWidget(
  MaterialApp(
    home: Scaffold(
      body: TaskTile(
        task: const DashboardTask(id: 'T-99', title: 'งานทดสอบ', quantity: 7),
        done: true,
        onToggle: () => toggled++,
      ),
    ),
  ),
);

เราทดสอบ TaskTile ใบเดียวได้โดยไม่ต้องเปิดแดชบอร์ดทั้งหน้า เพราะมันรับทุกอย่างที่ต้องใช้ผ่าน constructor ไม่ได้ไปหยิบข้อมูลมาเอง

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้

10. แบบฝึกหัด

สร้าง StatelessWidget ชื่อ StockBadge ที่

  1. รับจำนวนคงเหลือ (int) และจำนวนขั้นต่ำ (int ค่าเริ่มต้น 10)
  2. แสดงข้อความ เหลือ N ชิ้น
  3. ถ้าจำนวนต่ำกว่าขั้นต่ำ ให้พื้นหลังเป็นสีเตือน ถ้าไม่ใช่ให้ใช้สีปกติ
  4. ถ้าจำนวนเป็นศูนย์ ให้แสดงข้อความ ของหมด แทน
  5. ห้ามเก็บสีหรือข้อความเป็น field
ดูแนวคำตอบและเหตุผล
class StockBadge extends StatelessWidget {
  const StockBadge({super.key, required this.quantity, this.minimum = 10});

  final int quantity;
  final int minimum;

  @override
  Widget build(BuildContext context) {
    final scheme = Theme.of(context).colorScheme;
    final isOut = quantity == 0;
    final isLow = quantity < minimum;

    final label = isOut ? 'ของหมด' : 'เหลือ $quantity ชิ้น';
    final background = isOut
        ? scheme.errorContainer
        : isLow
            ? scheme.tertiaryContainer
            : scheme.surfaceContainerHighest;

    return Container(
      padding: const EdgeInsets.symmetric(horizontal: 12, vertical: 6),
      decoration: BoxDecoration(
        color: background,
        borderRadius: BorderRadius.circular(999),
      ),
      child: Text(label),
    );
  }
}

ทำไม label และ background ถึงเป็นตัวแปรใน build ไม่ใช่ field: เพราะทั้งคู่คำนวณได้จาก quantity และ minimum ทั้งหมด ถ้าเก็บเป็น field เราต้องรับประกันเองว่ามันตรงกับ quantity เสมอ ซึ่งวันหนึ่งจะไม่ตรง — เป็นหลักเดียวกับ remaining ในแบบฝึกหัด D1.7

ทำไม minimum มีค่าเริ่มต้นแทนที่จะ required: เพราะ 10 เป็นค่าที่ใช้ได้ในกรณีส่วนใหญ่ การบังคับให้ทุกจุดเรียกส่งค่านี้ทำให้โค้ดยาวโดยไม่ได้อะไร — ตรงกับกฎการเลือกรูปแบบ parameter ใน D1.4

ทำไมใช้สีจากธีม: ถ้าเขียน Colors.red ตรง ๆ พอทำโหมดมืดสีจะแสบตาและตัวอักษรอาจอ่านไม่ออก การใช้ colorScheme.errorContainer ได้สีที่คู่กับตัวอักษรอย่างถูกต้องในทุกโหมด (ทบทวน 1.2)

จุดที่คนมักพลาด: การเขียน if (isOut) return Container(...) แล้ว if (isLow) return Container(...) เป็นสามชุดแยกกัน ซึ่งได้ผลถูกต้องแต่โครงสร้างซ้ำสามรอบ พอต้องแก้ระยะขอบก็ต้องแก้สามที่ — ให้แยกเฉพาะ ค่า ที่ต่างกัน แล้วใช้โครงเดียว

ลองต่อ: เพิ่มไอคอนหน้าข้อความที่เปลี่ยนตามสถานะ แล้วสังเกตว่าคุณเพิ่มตัวแปรอีกหนึ่งตัวใน build ไม่ใช่ field อีกหนึ่งตัว

11. สรุปท้ายบท

  • StatelessWidget คือฟังก์ชันที่รับข้อมูลแล้วคืนหน้าตา
  • “stateless” แปลว่าไม่ถือข้อมูลที่เปลี่ยนได้ ไม่ได้แปลว่าไม่ถูก build ใหม่
  • field ทุกตัวต้องเป็น final — Flutter บังคับ และเป็นการป้องกันที่ดี
  • ค่าที่คำนวณได้ ให้คำนวณใน build อย่าเก็บเป็น field
  • ห้ามทำงานที่มีผลข้างเคียงใน build
  • แตก widget เมื่อใช้ซ้ำ ตั้งชื่อได้ หรืออ่านยาก — และได้ผลพลอยได้คือทดสอบแยกได้

บทถัดไป: 1.5 จะตอบคำถามที่ค้างไว้ว่า ถ้า widget ถือข้อมูลที่เปลี่ยนได้ไม่ได้ แล้วจำนวนที่นับได้ในแอป lab เก็บอยู่ที่ไหน
