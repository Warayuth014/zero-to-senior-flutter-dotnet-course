ระดับ: เริ่มต้น–กลางใช้เวลา: 25–35 นาทีลงมือทำ: เข้าใจว่าอะไรทำให้แอปลื่นจริง
ต้องผ่านอะไรมาก่อน: 1.3 (Widget/Element/RenderObject), 1.9 (build ต้องเบา) และ D1.3 (const)
จบบทนี้แล้วจะทำได้: ใส่ const ได้ถูกที่และรู้ว่ามันช่วยอะไรจริง ๆ พร้อมรู้ว่าอะไรคือตัวชี้ขาดของประสิทธิภาพที่สำคัญกว่ามาก

1. ปัญหาที่บทนี้แก้

ตั้งแต่ 1.1 เราบอกให้ “เติม const ทุกครั้งที่ analyzer แนะนำ” โดยยังไม่อธิบายเหตุผล และหลายคนพอรู้ว่ามันเกี่ยวกับความเร็วก็เริ่มใส่ทุกที่ด้วยความเชื่อว่ายิ่งเยอะยิ่งเร็ว

ความจริงคือ const ช่วยได้จริงแต่เป็นเรื่องเล็ก ส่วนสิ่งที่ทำให้แอปช้าหรือลื่นจริง ๆ เป็นคนละเรื่อง บทนี้จะจัดลำดับความสำคัญให้ถูก

2. คำศัพท์ที่ต้องรู้ก่อน

rebuild scopeขอบเขตว่าเมื่อข้อมูลเปลี่ยน ส่วนไหนของหน้าจอถูกวาดใหม่บ้าง
frameภาพหนึ่งภาพ — แอปลื่นคือวาดได้ 60 ภาพต่อวินาที

3. Mental model: const คือคำสัญญา ไม่ใช่ยาวิเศษ

ทบทวนจาก D1.3: const แปลว่า “ค่านี้รู้ได้ตั้งแต่ยังไม่รันโปรแกรม” เมื่อใช้กับ widget มันให้ผลสองอย่าง

  1. Flutter สร้าง object นั้นชิ้นเดียวแล้วใช้ซ้ำ ทุกครั้งที่ build ทำงาน
  2. เมื่อ Flutter เห็นว่า widget ตัวเดิมเป๊ะ ๆ (ชิ้นเดียวกัน) มันข้ามการตรวจกิ่งนั้นได้
const SizedBox(height: 12)     // ทั้งแอปใช้ object ชิ้นเดียวกัน
SizedBox(height: 12)           // สร้างใหม่ทุกครั้งที่ build
ประโยคเดียวที่ต้องจำ: const บอกว่า “ชิ้นนี้ไม่ขึ้นกับข้อมูลอะไรเลย” — ประโยชน์ด้านความเร็วเป็นของแถม ส่วนประโยชน์หลักคือ สื่อสารกับคนอ่าน ว่าตรงนี้ไม่มีอะไรเปลี่ยน

4. ใส่ได้เมื่อไหร่

const SizedBox(height: 12)              // ได้ — ตัวเลขตายตัว
const Icon(Icons.inventory_2_outlined)  // ได้
const EdgeInsets.all(16)                // ได้
const Text('เพิ่มสินค้า')                 // ได้ — ข้อความตายตัว

Text('$_itemCount รายการ')               // ไม่ได้ — ค่ามาจากตัวแปร
Text(task.title)                        // ไม่ได้
Icon(done ? Icons.check : Icons.close)  // ไม่ได้ — ขึ้นกับเงื่อนไข

กฎเดียวกับ D1.3: ทุก argument ต้องเป็นค่าคงที่หมด ถ้ามีตัวใดตัวหนึ่งมาจากตัวแปร ทั้งก้อนก็เป็น const ไม่ได้ — และตัวที่ครอบมันก็เป็นไม่ได้ตามไปด้วย

ข้อดีที่สังเกตได้ทันที: analyzer จะขีดเส้นแนะนำให้เอง ไม่ต้องเดา ถ้ามันไม่แนะนำแปลว่าใส่ไม่ได้

5. สิ่งที่ const ไม่ได้ทำ

เข้าใจผิดว่าความจริง
ทำให้ widget ไม่ถูกวาดใหม่เลยยังถูกจัดวางและวาดใหม่ได้ถ้าขนาดหน้าจอเปลี่ยน
ทำให้ API ที่เรียกผิดที่ไม่ถูกเรียกซ้ำไม่เกี่ยวกันเลย — นั่นคือเรื่องของ 1.9
แก้ปัญหารายการยาวที่กระตุกต้องใช้รายการแบบสร้างทีละแถวแทน
ยิ่งใส่เยอะยิ่งเร็วผลตอบแทนน้อยมากเมื่อเทียบกับการจำกัดขอบเขต rebuild

ตัวอย่างที่ชัด: const Text('WMS') ยังต้องถูกจัดวางใหม่เมื่อหมุนอุปกรณ์ เพราะแม้คำอธิบายจะเหมือนเดิม แต่พื้นที่ที่มันต้องอยู่เปลี่ยนไป — const ล็อกที่ระดับ Widget ไม่ได้ล็อกที่ระดับ RenderObject (ทบทวน 1.3)

6. สิ่งที่สำคัญกว่ามาก: ขอบเขตของการ rebuild

คำถามที่ให้ผลตอบแทนสูงกว่า const หลายเท่าคือ “เมื่อข้อมูลชิ้นนี้เปลี่ยน มีอะไรถูกวาดใหม่บ้าง”

// แบบที่ 1 — ทั้งหน้าจอวาดใหม่เมื่อตัวนับเปลี่ยน
setState(() => _tapCount++);

// แบบที่ 2 — เฉพาะข้อความบรรทัดเดียววาดใหม่
_tapCount.value++;   // ValueNotifier

ดูของจริงใน lab widget_basics_app.dart

// ส่วนนี้เท่านั้นที่ rebuild เมื่อ _tapCount เปลี่ยน
ValueListenableBuilder<int>(
  valueListenable: _tapCount,
  builder: (context, count, child) {
    return Text('กดไปแล้ว $count ครั้ง', key: const Key('tap-count'));
  },
),

เทียบกันตรง ๆ: การใส่ const ให้ SizedBox สิบตัวช่วยประหยัดการสร้าง object สิบชิ้นที่เบามาก ส่วนการจำกัดขอบเขต rebuild อาจช่วยไม่ให้ทั้งรายการร้อยแถวถูกวาดใหม่ — ต่างกันคนละระดับ

เครื่องมือสำหรับจำกัดขอบเขตจะเรียนใน 1.13 และเต็มรูปแบบใน Part 4

7. ลำดับที่ควรทำเมื่อแอปช้า

  1. วัดก่อน — อย่าเดา ใช้เครื่องมือดูว่าเวลาหมดไปกับอะไร
  2. ดูว่าอะไรถูกวาดใหม่โดยไม่จำเป็น แล้วจำกัดขอบเขต
  3. ดูว่ามีงานหนักอยู่ใน build ไหม (1.9)
  4. ใช้รายการแบบสร้างทีละแถว แทนการสร้างทุกแถวพร้อมกัน
  5. ลดปริมาณข้อมูล ที่ต้องประมวลผล (D1.17)
  6. ค่อยมาดู const เป็นลำดับท้าย ๆ
ที่จัด const ไว้ท้ายสุดไม่ได้แปลว่าไม่ต้องใส่ — ให้ใส่ตั้งแต่แรกทุกครั้งที่ analyzer แนะนำ เพราะมันฟรีและช่วยสื่อความหมาย แต่เมื่อแอปช้าจริง อย่าเสียเวลาไล่เติม const เป็นทางแก้แรก เพราะจะไม่ได้อะไรกลับมา

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Invalid constant valueใส่ const กับสิ่งที่มีค่ามาจากตัวแปรเอาออก — ให้ analyzer เป็นคนบอกว่าตรงไหนใส่ได้
ใส่ const เต็มไปหมดแล้วแอปยังกระตุกต้นเหตุจริงอยู่ที่ขอบเขต rebuild หรืองานใน buildทำตามลำดับในหัวข้อ 7
เติม const ที่ตัวนอกไม่ได้เพราะตัวในมีตัวแปรconst ต้องเป็นตลอดสายแยกส่วนที่คงที่ออกมาเป็น widget ของตัวเอง แล้วใส่ const เฉพาะส่วนนั้น
รายการยาวกระตุกทั้งที่ใส่ const ครบสร้างทุกแถวพร้อมกันใช้ ListView.builder (Part 2)
แตก widget ย่อยเยอะมากเพื่อให้ใส่ const ได้ปรับตามคะแนน lint แทนที่จะปรับตามความหมายแตกตามเกณฑ์ใน 1.4 และ 1.11 เท่านั้น

9. แบบฝึกหัด

ดูโค้ดนี้แล้วตอบสามข้อ

Widget build(BuildContext context) {
  return Column(
    children: [
      Padding(
        padding: EdgeInsets.all(16),
        child: Row(
          children: [
            Icon(Icons.inventory_2_outlined),
            SizedBox(width: 8),
            Text('รายการสินค้า'),
          ],
        ),
      ),
      SizedBox(height: 12),
      Text('พบ $count รายการ'),
    ],
  );
}
  1. บรรทัดไหนใส่ const ได้บ้าง
  2. ทำไม Column ตัวนอกสุดถึงใส่ const ไม่ได้
  3. ถ้าอยากให้ส่วนหัว (Padding ทั้งก้อน) เป็น const ได้ ควรทำอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1

return Column(
  children: [
    const Padding(                          // ← ได้ทั้งก้อน
      padding: EdgeInsets.all(16),
      child: Row(
        children: [
          Icon(Icons.inventory_2_outlined),
          SizedBox(width: 8),
          Text('รายการสินค้า'),
        ],
      ),
    ),
    const SizedBox(height: 12),             // ← ได้
    Text('พบ $count รายการ'),                // ← ไม่ได้
  ],
);

สังเกตว่าเมื่อใส่ const ที่ Padding ตัวนอกแล้ว ตัวข้างในทั้งหมดไม่ต้องใส่ซ้ำ เพราะอยู่ในบริบทที่เป็น const อยู่แล้ว — การใส่ซ้ำไม่ผิด แต่รกโดยไม่จำเป็น

ข้อ 2

เพราะลูกคนสุดท้ายคือ Text('พบ $count รายการ') ซึ่งใช้ค่าจากตัวแปร เมื่อลูกตัวใดตัวหนึ่งไม่เป็น const แม่ก็เป็นไม่ได้ — เหมือนกฎใน D1.3 ที่ว่า const ต้องเป็นตลอดสายลงไปถึงข้างใน

ข้อ 3

ก้อนนั้น เป็น const ได้อยู่แล้วตามข้อ 1 เพราะข้างในไม่มีอะไรมาจากตัวแปรเลย ประเด็นที่แท้จริงของคำถามนี้คือ ถ้าวันหนึ่งส่วนหัวต้องแสดงชื่อคลังที่มาจากข้อมูล เราจะทำอย่างไร คำตอบคือ แยกเฉพาะส่วนที่เปลี่ยนออกมา ไม่ใช่ยอมให้ทั้งก้อนหลุดจาก const

// แยกส่วนหัวที่คงที่ออกมาเป็น widget ของตัวเอง
class _ListHeader extends StatelessWidget {
  const _ListHeader();

  @override
  Widget build(BuildContext context) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Row(
        children: [
          Icon(Icons.inventory_2_outlined),
          SizedBox(width: 8),
          Text('รายการสินค้า'),
        ],
      ),
    );
  }
}

// เรียกใช้
const _ListHeader(),

ประโยชน์ที่แท้จริงของการแยกแบบนี้: ไม่ใช่แค่ได้ const แต่คือหัวข้อนี้กลายเป็นสิ่งของที่มีชื่อ อ่านง่ายขึ้น และถ้าวันหน้าต้องใช้ในหน้าจออื่นก็หยิบไปใช้ได้ทันที — ตรงกับเกณฑ์การแตก widget ใน 1.4

สิ่งที่ต้องระวัง: อย่าแตก widget ย่อยเพียงเพื่อให้ตัวเลข const ในโปรเจกต์สูงขึ้น ถ้าแยกออกมาแล้วตั้งชื่อไม่ได้ว่ามันคืออะไร แสดงว่ายังไม่ควรแยก

ลองต่อ: เพิ่ม print ใน build ของ _ListHeader แล้วกดปุ่มที่เปลี่ยน count — จะเห็นว่ามันยังถูกเรียกอยู่ เพราะ const ไม่ได้หยุด build ของแม่ ประเด็นนี้คือหัวใจของหัวข้อ 5 และเป็นเหตุผลว่าทำไมขอบเขต rebuild ถึงสำคัญกว่า

10. สรุปท้ายบท

  • const บอกว่าชิ้นนี้ไม่ขึ้นกับข้อมูลใด ๆ และให้ Flutter ใช้ object ซ้ำได้
  • ใส่ทุกครั้งที่ analyzer แนะนำ — ฟรีและช่วยสื่อความหมาย
  • ทุก argument ต้องคงที่หมด และต้องเป็น const ตลอดสาย
  • const ไม่ได้หยุดการ build ของแม่ และไม่ได้หยุดการจัดวางใหม่
  • ตัวชี้ขาดของความลื่นคือ ขอบเขตของ rebuild ไม่ใช่จำนวน const
  • เมื่อแอปช้า ให้วัดก่อนเสมอ แล้วไล่แก้ตามลำดับความสำคัญ

บทถัดไป: 1.11 จะลงลึกเรื่องการแตก widget ที่เราแตะไว้ใน 1.4 — เกณฑ์ที่ใช้ตัดสินจริงในโปรเจกต์ และกับดักของการแตกมากเกินไป
