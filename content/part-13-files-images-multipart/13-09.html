1. หลักข้อเดียวที่ต้องจำ

การตรวจฝั่งแอปคือความสะดวก การตรวจฝั่งเซิร์ฟเวอร์คือความปลอดภัย — และทั้งสองอย่างต้องมี
/// การตรวจฝั่งแอปคือความสะดวก ไม่ใช่ความปลอดภัย — เซิร์ฟเวอร์ต้องตรวจซ้ำ
/// เสมอ เพราะใครก็ยิงเข้า endpoint ตรง ๆ ได้โดยไม่ผ่านแอปนี้
ImageCheck checkImage(PickedImage image, {ImagePolicy policy = const ImagePolicy()})
ฝั่งแอปตรวจเพื่อฝั่งเซิร์ฟเวอร์ตรวจเพื่อ
ไม่ให้ผู้ใช้เสียเวลารอส่งไฟล์ที่จะถูกปฏิเสธไม่ให้ข้อมูลเสียเข้าระบบ
ไม่ให้เสียเน็ตไปเปล่า ๆไม่ให้ถูกโจมตี
บอกทางแก้ทันทีตอนที่ผู้ใช้ยังอยู่ตรงนั้นรักษาความจริงของข้อมูล

เป็นหลักเดียวกับ 9.1 แบบฝึกหัดข้อ 4 ที่ว่า “ถ้าสองที่ไม่ตรงกัน เซิร์ฟเวอร์ถูกเสมอ”

2. สิ่งที่ตรวจได้ฝั่งแอป

    this.maxBytes = 5 * 1024 * 1024,
    this.minBytes = 5 * 1024,
    this.allowedMimeTypes = const {'image/jpeg', 'image/png', 'image/webp'},
    this.minWidth = 480,
    this.minHeight = 480,
  });

ตรวจจับอะไร
ชนิดไฟล์ผู้ใช้เลือกไฟล์ที่ไม่ใช่รูป
ขนาดสูงสุดรูปที่จะถูกปฏิเสธด้วย 413
ขนาดต่ำสุดไฟล์เสียหรือถ่ายพลาด
ขนาดพิกเซลรูปที่เล็กจนอ่านฉลากไม่ออก
ลายเซ็นในไฟล์ไฟล์ที่เปลี่ยนนามสกุลมาหลอก
maxBytes ต้องตรงกับที่เซิร์ฟเวอร์ตั้งไว้ — ถ้าแอปยอมให้ 5 MB แต่เซิร์ฟเวอร์รับแค่ 2 MB ผู้ใช้จะเสียเวลาอัปโหลดสามสิบวินาทีแล้วถูกปฏิเสธ ซึ่งแย่กว่าการถูกห้ามตั้งแต่ต้น

3. ลายเซ็นในไฟล์

ทุกรูปแบบไฟล์มีไบต์เฉพาะที่ต้นไฟล์ เรียกว่า magic number

/// ตรวจว่าไบต์ต้นไฟล์ตรงกับชนิดที่อ้างไหม
bool _looksLike(Uint8List bytes, String mimeType) {
  if (bytes.length < 12) return false;

  return switch (mimeType) {
    // JPEG ขึ้นต้นด้วย FF D8 FF เสมอ
    'image/jpeg' => bytes[0] == 0xFF && bytes[1] == 0xD8 && bytes[2] == 0xFF,
    // PNG ขึ้นต้นด้วย 89 P N G
    'image/png' =>
      bytes[0] == 0x89 && bytes[1] == 0x50 && bytes[2] == 0x4E && bytes[3] == 0x47,
    // WebP คือ RIFF....WEBP
    'image/webp' => ...,
    _ => false,
  };
}
สิ่งที่โกหกได้สิ่งที่โกหกยากกว่า
นามสกุลในชื่อไฟล์ไบต์ต้นไฟล์
mimeType ที่ระบบบอกมา—

สังเกตคำว่า “ยากกว่า” ไม่ใช่ “ไม่ได้” — ไฟล์ที่ขึ้นต้นด้วยลายเซ็น JPEG แล้วตามด้วยอะไรก็ได้ ก็ยังผ่านการตรวจนี้ ซึ่งเป็นเหตุผลที่เซิร์ฟเวอร์ต้องตรวจจริงจังกว่านี้

test('เนื้อไฟล์ไม่ตรงกับชนิดที่อ้าง ถูกจับได้', () {
  // ไฟล์ PNG ที่ถูกเปลี่ยนนามสกุลและ mimeType เป็น jpeg
  final result = checkImage(image(bytes: pngBytes(), mimeType: 'image/jpeg'));
  expect(result, isA<ImageRejected>());
  expect((result as ImageRejected).message, contains('เนื้อไฟล์'));
});

กรณีห้ามหรือเตือนเพราะ

test('รูปเล็กกว่าที่แนะนำ ได้คำเตือน ไม่ใช่ถูกห้าม', () {
  // ห้ามเฉพาะสิ่งที่ผิดแน่นอน รูปเบลอยังใช้เป็นหลักฐานได้ถ้าผู้ใช้ยืนยัน

});

รูปแบบไม่ถูกต้องรองรับเฉพาะไฟล์ JPG, PNG, WebP แต่ไฟล์นี้เป็น HEIC

เกณฑ์เดียวกับ 10.7 §2 — อ่านแล้วรู้ไหมว่าต้องทำอะไรต่อ

test('ไฟล์ใหญ่เกินถูกปฏิเสธ พร้อมบอกขนาดจริง', () {
  final result = checkImage(image(bytes: jpegBytes(size: 8 * 1024 * 1024)));
  // บอกทั้งขนาดที่ได้และขนาดที่รับได้ ผู้ใช้จะได้รู้ว่าต้องลดแค่ไหน
  expect((result as ImageRejected).message, contains('8.0 MB'));
  expect(result.message, contains('5 MB'));
});

เรื่อง HEIC เป็นกรณีจริงที่เจอบ่อย — iPhone ถ่ายเป็น HEIC โดยปริยาย และผู้ใช้ไม่มีทางรู้ว่าไฟล์ที่ตัวเองเลือกคือรูปแบบอะไร ข้อความที่บอกชื่อรูปแบบทำให้เขาไปหาวิธีเปลี่ยนได้

6. ชื่อไฟล์คือข้อมูลที่ไม่น่าเชื่อถือ

/// อย่าเชื่อชื่อที่ได้จากอุปกรณ์โดยตรง — ผู้ใช้ตั้งชื่อไฟล์เป็นอะไรก็ได้
/// รวมถึงชื่อที่มี `../` ซึ่งฝั่งเซิร์ฟเวอร์ที่เขียนไม่ระวังจะเขียนไฟล์
/// ออกนอกโฟลเดอร์ที่ตั้งใจ
final String fileName;
String safeFileName(String raw, {required String extension}) {
  final base = raw.split(RegExp(r'[/\\]')).last;          // ตัดเส้นทางทิ้ง
  final withoutExt = base.contains('.')
      ? base.substring(0, base.lastIndexOf('.'))
      : base;
  final cleaned = withoutExt.replaceAll(RegExp(r'[^A-Za-z0-9_-]'), '_');
  final trimmed = cleaned.isEmpty ? 'image' : cleaned;
  final limited = trimmed.length > 60 ? trimmed.substring(0, 60) : trimmed;
  return '$limited.$extension';
}

แถวสุดท้ายในตารางแรกสำคัญ — นามสกุลมาจาก mimeType ที่ตรวจเนื้อไฟล์แล้ว ไม่ใช่จากชื่อเดิม ทำให้ไฟล์ที่พยายามหลอกด้วยนามสกุล ถูกเปลี่ยนเป็นนามสกุลที่ตรงกับเนื้อจริง

แต่ต้องย้ำอีกครั้ง — นี่คือการช่วยฝั่งเซิร์ฟเวอร์ ไม่ใช่การป้องกัน เพราะใครก็ยิงคำขอที่มีชื่อไฟล์เป็นอะไรก็ได้เข้า endpoint ตรง ๆ โดยไม่ผ่านแอปนี้

7. สิ่งที่ฝั่งเซิร์ฟเวอร์ต้องทำ

ตรวจทำไมแอปทำแทนไม่ได้
ขนาดและชนิดซ้ำคำขออาจไม่ได้มาจากแอปนี้
ตั้งชื่อไฟล์ใหม่เองทั้งหมดชื่อที่แอปส่งมาเชื่อไม่ได้
เก็บนอก web rootไม่งั้นไฟล์ที่อัปโหลดอาจถูกเรียกให้ทำงาน
ตรวจว่าผู้ใช้มีสิทธิ์กับสินค้าตัวนั้นแอปซ่อนปุ่มได้ แต่นั่นไม่ใช่การป้องกัน (8.9)
จำกัดจำนวนต่อผู้ใช้ต่อช่วงเวลากันการยิงถล่ม

รายละเอียดฝั่ง .NET อยู่ใน zero-to-senior-dotnet8-course — สิ่งที่ฝั่งแอปต้องทำคือถามให้แน่ใจว่าทีมหลังบ้านทำครบ ไม่ใช่สมมติว่าทำแล้ว

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ตรวจผ่านฝั่งแอปแต่ถูกปฏิเสธที่เซิร์ฟเวอร์ขีดจำกัดสองฝั่งไม่ตรงกันถามค่าจริงแล้วตั้งให้ตรง
ผู้ใช้ iPhone ใช้ฟีเจอร์ไม่ได้HEIC ไม่อยู่ในรายการที่รองรับรองรับ หรือบอกวิธีเปลี่ยนตั้งค่ากล้อง
เครื่องกล้องความละเอียดต่ำใช้ไม่ได้ห้ามแทนที่จะเตือนแยกห้ามกับเตือน
ไฟล์ที่ไม่ใช่รูปหลุดเข้าระบบเชื่อนามสกุลอย่างเดียวตรวจลายเซ็นในไฟล์
คิดว่าตรวจฝั่งแอปแล้วปลอดภัยเข้าใจผิดเรื่องบทบาทเซิร์ฟเวอร์ต้องตรวจซ้ำเสมอ

9. แบบฝึกหัด

ทีมพบว่ามีคนอัปโหลดไฟล์ PDF เข้ามาในช่องที่ควรเป็นรูปสินค้า ผ่านการยิง API ตรง ๆ

  1. ฝั่งแอปควรทำอะไรเพิ่ม
  2. ควรบอกทีมหลังบ้านอย่างไร
แนวคำตอบ

1. ไม่ต้องทำอะไรเพิ่ม และนี่คือคำตอบที่สำคัญที่สุดของบทนี้

คนที่ยิง API ตรง ๆ ไม่ได้ผ่านแอปเลย การเพิ่มการตรวจฝั่งแอปจึงไม่มีผลกับเขาแม้แต่น้อย — เหมือนกับที่ 8.9 สรุปว่าการซ่อนปุ่มตาม role ไม่ใช่การป้องกัน

สิ่งที่ควรตรวจสอบคือการตรวจที่มีอยู่ตรงกับที่เซิร์ฟเวอร์ต้องการไหม เพราะถ้าเซิร์ฟเวอร์เพิ่มการตรวจใหม่ แอปควรตรวจแบบเดียวกันเพื่อไม่ให้ผู้ใช้เสียเวลา

2. บอกด้วยข้อเท็จจริงและเสนอสิ่งที่ตรวจสอบได้

# สิ่งที่ควรตรวจฝั่งเซิร์ฟเวอร์ พร้อมสิ่งที่ฝั่งแอปตรวจอยู่แล้ว
- ลายเซ็นในไฟล์ (แอปตรวจ FF D8 FF สำหรับ JPEG)
- ขนาดสูงสุด (แอปตั้งไว้ 5 MB — ยืนยันว่าตรงกับฝั่งเซิร์ฟเวอร์ไหม)
- ตั้งชื่อไฟล์ใหม่ ไม่ใช้ชื่อที่แอปส่งมา
- เก็บนอก web root
- ตรวจสิทธิ์ว่าผู้ใช้แก้สินค้าตัวนั้นได้จริง

สิ่งที่ฝั่งแอปทำได้และมีค่ามาก คือเขียนเทสต์ที่ยิงเข้าเซิร์ฟเวอร์จริงด้วยไฟล์ที่ไม่ควรผ่าน แล้วยืนยันว่าถูกปฏิเสธ (Part 14)

10. สรุป

  • ฝั่งแอปตรวจเพื่อความสะดวก เซิร์ฟเวอร์ตรวจเพื่อความปลอดภัย
  • ขีดจำกัดสองฝั่งต้องตรงกัน ไม่งั้นผู้ใช้เสียเวลาเปล่า
  • ตรวจลายเซ็นในไฟล์ เพราะนามสกุลและ mimeType โกหกได้
  • ห้ามเฉพาะสิ่งที่ผิดแน่นอน ที่น่าสงสัยให้เตือน
  • ข้อความต้องบอกทั้งค่าที่ได้และค่าที่รับได้
  • ชื่อไฟล์จากอุปกรณ์เชื่อไม่ได้ และการทำให้ปลอดภัยฝั่งแอปคือการช่วย ไม่ใช่การป้องกัน
