ระดับ: กลางใช้เวลา: 40–50 นาทีลงมือทำ: เพิ่มช่องข้อมูลแล้วดูว่า body เปลี่ยนอย่างไร
ต้องผ่านอะไรมาก่อน: 13.3, 7.13 (Idempotency-Key)
จบบทนี้แล้วจะทำได้: ส่งข้อมูลประกอบไปกับไฟล์ และรู้ว่าอะไรควรอยู่ใน header กับอะไรควรอยู่ในช่อง

1. ไฟล์อย่างเดียวไม่พอ

เซิร์ฟเวอร์ที่ได้รับไฟล์รูปมาเปล่า ๆ ทำอะไรไม่ได้เลย มันต้องรู้ว่า

คำถามตอบด้วย
รูปนี้ของสินค้าตัวไหนช่อง partId
ใครถ่ายtoken ใน header
ถ่ายจากเครื่องไหนช่อง station
เป็นคำสั่งเดิมที่ส่งซ้ำหรือคำสั่งใหม่Idempotency-Key ใน header

สองแถวบนอยู่ในช่อง สองแถวล่างอยู่ใน header และเส้นแบ่งนี้มีเหตุผล

2. ช่องหรือ header

ใส่ใน header เมื่อใส่ในช่องเมื่อ
เป็นเรื่องของคำขอ ไม่ใช่เรื่องของข้อมูลเป็นเรื่องของข้อมูลที่จะถูกบันทึก
ใช้เหมือนกันทุก endpointต่างกันตาม endpoint
ตัวกลางในเครือข่ายอาจต้องอ่านเฉพาะแอปปลายทางเท่านั้นที่สนใจ
ตัวอย่าง: token, รหัสคำสั่ง, ภาษาตัวอย่าง: รหัสสินค้า จำนวน หมายเหตุ
..headers.addAll({
  if (authToken != null) 'Authorization': 'Bearer $authToken',
  // ส่งซ้ำเพราะเน็ตหลุด ต้องไม่ได้รูปสองใบ (7.13)
  'Idempotency-Key': commandId,
})
..fields.addAll(fields)      // partId, station, note
ข้อควรระวังของ header — ค่าต้องเป็น ASCII เท่านั้น ถ้าใส่ข้อความไทยลงไปจะได้ข้อผิดพลาดตอนส่ง หมายเหตุที่ผู้ใช้พิมพ์จึงต้องอยู่ในช่องเสมอ

3. รหัสคำสั่งกับการอัปโหลด

7.13 อธิบายว่าคำสั่งที่ไม่รู้ผลต้องมีรหัสกำกับ การอัปโหลดเป็นกรณีที่ชัดเจนที่สุด

ผู้ใช้กดส่ง → ส่งไป 80% → เน็ตหลุด
  → ไม่รู้ว่าเซิร์ฟเวอร์ได้ครบหรือยัง
    → กดส่งซ้ำ
      → ถ้าไม่มีรหัส เซิร์ฟเวอร์อาจเก็บรูปสองใบ

รูปซ้ำไม่ได้ทำให้ข้อมูลผิด แต่ทำให้พื้นที่เก็บโตเรื่อย ๆ และทำให้หน้าจอที่แสดงรูปของสินค้ามีรูปเดียวกันซ้อนกันหลายใบ

กฎที่สำคัญที่สุดคือ รหัสต้องเป็นของรอบนั้น ไม่ใช่ของครั้งนั้น

/// รหัสคำสั่งของรอบนี้ สร้างครั้งเดียวตอนเลือกรูป
///
/// **ไม่สร้างใหม่ตอนลองใหม่** — การส่งซ้ำไฟล์เดิมต้องใช้รหัสเดิม
/// ไม่งั้นเซิร์ฟเวอร์จะเก็บรูปสองใบ
String? _commandId;
test('ส่งซ้ำหลังล้มเหลว ต้องใช้รหัสคำสั่งเดิม', () async {
  await store.pick(PickSource.camera);
  await store.upload(path: '/upload');       // ล้มเหลว
  await store.upload(path: '/upload');       // ลองใหม่

  // รหัสเดิมทั้งสองครั้ง ไม่งั้นเซิร์ฟเวอร์จะเก็บรูปสองใบ
  expect(commandIds[0], commandIds[1]);
});

test('เลือกรูปใหม่ ต้องได้รหัสคำสั่งใหม่', () async {
  ...
  expect(commandIds[0], isNot(commandIds[1]));
});

สองเทสต์นี้ต้องมีคู่กัน — ข้อแรกอย่างเดียวจะผ่านได้ด้วยการใช้รหัสคงที่ตลอดกาล ซึ่งจะทำให้รูปใบที่สองไม่ถูกเก็บเลย

4. ค่าที่ควรส่งไปด้วยเสมอ

ค่าทำไม
รหัสของสิ่งที่รูปนี้เกี่ยวข้องไม่มีก็เก็บไม่ได้
เวลาที่ถ่ายเวลาที่เซิร์ฟเวอร์ได้รับอาจช้ากว่าหลายชั่วโมงถ้าเก็บไว้ส่งทีหลัง
รหัสเครื่องหรือชื่อสถานีตามหาต้นตอเมื่อรูปมีปัญหา
ชนิดของรูป“หลักฐานความเสียหาย” ต่างจาก “รูปประกอบสินค้า”

แถวที่สองสำคัญและมักถูกลืม — ถ้าไม่ส่งเวลาที่ถ่ายไปด้วย เซิร์ฟเวอร์จะบันทึกเวลาที่ได้รับ ซึ่งผิดทันทีที่มีฟีเจอร์เก็บไว้ส่งทีหลัง (Part 29)

fields: {
  'partId': part.id,
  'station': settings.stationName,
  'capturedAt': capturedAt.toUtc().toIso8601String(),   // UTC เสมอ (6.9)
  'kind': 'damage',
},

5. ชื่อไฟล์ก็เป็นข้อมูลที่ส่งไป

http.MultipartFile.fromBytes(
  'file',
  image.bytes,
  filename: safeFileName(image.fileName, extension: image.extension),
)

ชื่อไฟล์ที่ได้จากอุปกรณ์เชื่อไม่ได้ และ 13.9 จะพูดถึงเหตุผลเต็ม ๆ ตอนนี้แค่รู้ว่าต้องทำให้ปลอดภัยก่อนส่ง

test('ชื่อไฟล์ที่ส่งไปถูกทำให้ปลอดภัยแล้ว', () async {
  await client.uploadImage(
    path: '/upload',
    image: image(fileName: '../../evil.jpg'),
    commandId: 'cmd-1',
  );

  expect(body, isNot(contains('..')));
  expect(body, contains('evil.jpg'));
});

อีกทางที่ปลอดภัยกว่าคือไม่ส่งชื่อเดิมเลย แล้วตั้งชื่อจากข้อมูลที่เรารู้แน่

filename: '${part.id}-$commandId.${image.extension}',
ส่งชื่อเดิมตั้งชื่อใหม่
ผู้ใช้จำได้ว่าไฟล์ไหนคือไฟล์ไหนชื่อสื่อความหมายกับระบบมากกว่า
ต้องทำให้ปลอดภัยก่อนปลอดภัยโดยธรรมชาติ

สำหรับรูปที่ถ่ายจากกล้อง ชื่อเดิมคือ IMG_0001.jpg ซึ่งไม่มีความหมายอยู่แล้ว การตั้งชื่อใหม่จึงชนะชัดเจน — ส่วนไฟล์ที่ผู้ใช้เลือกจากเอกสารที่ตั้งชื่อเอง เก็บชื่อเดิมไว้มีประโยชน์

6. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ส่งไม่ได้เมื่อหมายเหตุเป็นภาษาไทยใส่ค่าไทยใน headerย้ายไปเป็นช่อง
ได้รูปซ้ำในระบบสร้างรหัสคำสั่งใหม่ทุกครั้งที่กดส่งสร้างตอนเลือกรูป ไม่ใช่ตอนส่ง
รูปใบที่สองไม่ถูกเก็บใช้รหัสคงที่สร้างใหม่เมื่อเลือกรูปใหม่
เวลาในระบบผิดใช้เวลาที่เซิร์ฟเวอร์ได้รับส่งเวลาที่ถ่ายไปด้วย
เซิร์ฟเวอร์บอกว่าขาดช่องสะกดชื่อช่องไม่ตรงเขียนเทสต์ตรวจ body

7. แบบฝึกหัด

ผู้ใช้ถ่ายรูปตอนอยู่ในห้องเย็นที่ไม่มีสัญญาณ แล้วเดินออกมาส่งข้างนอกสิบนาทีต่อมา

  1. ข้อมูลอะไรที่จะผิดถ้าไม่ระวัง
  2. ต้องส่งอะไรเพิ่ม
แนวคำตอบ

1. สามอย่าง

ข้อมูลถ้าไม่ระวังจะเป็นที่ถูกคือ
เวลาเวลาที่เซิร์ฟเวอร์ได้รับเวลาที่กดถ่าย
ตำแหน่งที่ที่ยืนตอนส่งที่ที่ถ่าย
ผู้ถ่ายคนที่ล็อกอินอยู่ตอนส่งคนที่ถ่าย

แถวสุดท้ายเกิดจริงบน PDA ที่เปลี่ยนมือทุกกะ — ถ่ายไว้ตอนกะเช้า ส่งตอนกะบ่ายที่เป็นคนละคน แล้วรูปจะถูกบันทึกว่าเป็นของคนที่ไม่ได้ถ่าย ซึ่งเป็นปัญหาทันทีถ้ารูปนั้นเป็นหลักฐานประกอบการเคลม

2. ส่งบริบทของตอนถ่ายไปด้วย ไม่ใช่ให้เซิร์ฟเวอร์เดาจากตอนได้รับ

fields: {
  'partId': part.id,
  'capturedAt': capturedAt.toUtc().toIso8601String(),
  'capturedBy': capturedByUsername,     // เก็บไว้ตอนถ่าย ไม่ใช่อ่านตอนส่ง
  'station': stationAtCapture,
},

แต่มีเรื่องที่ต้องคิดต่อ — ข้อมูลที่แอปส่งมา เซิร์ฟเวอร์เชื่อได้แค่ไหน

ค่าเซิร์ฟเวอร์ควรเชื่อไหม
capturedAtเชื่อได้พอสมควร แต่ควรบันทึกเวลาที่ได้รับไว้คู่กัน เพราะนาฬิกาเครื่องอาจเพี้ยน (8.3)
capturedByไม่ควรเชื่อเป็นตัวยืนยันตัวตน — ใครก็ส่งชื่อใครก็ได้ ให้ถือเป็นข้อมูลประกอบ ส่วนตัวตนจริงมาจาก token (8.9)

ทางที่ถูกคือเก็บทั้งสองอย่าง — สิ่งที่แอปอ้าง กับสิ่งที่เซิร์ฟเวอร์รู้ — แล้วถ้าไม่ตรงกัน ให้บันทึกไว้ให้คนตรวจสอบได้ ไม่ใช่ทิ้งอย่างใดอย่างหนึ่ง

ซึ่งเป็นหลักเดียวกับที่ 13.9 จะสรุปเรื่องการตรวจ — ฝั่งแอปตรวจเพื่อความสะดวก เซิร์ฟเวอร์ตรวจเพื่อความจริง

8. สรุป

  • header สำหรับเรื่องของคำขอ ช่องสำหรับเรื่องของข้อมูล
  • header รับ ASCII เท่านั้น ข้อความไทยต้องอยู่ในช่อง
  • รหัสคำสั่งสร้างตอนเลือกรูป และใช้เดิมตลอดการลองใหม่
  • ส่งเวลาที่ถ่ายไปด้วย ไม่ใช่ให้เซิร์ฟเวอร์ใช้เวลาที่ได้รับ
  • ตั้งชื่อไฟล์ใหม่จากข้อมูลที่เรารู้แน่ ปลอดภัยกว่าส่งชื่อเดิม
