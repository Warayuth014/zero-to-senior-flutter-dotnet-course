ระดับ: กลางใช้เวลา: 50–65 นาทีลงมือทำ: อ่าน body ของ multipart จริงในเทสต์
ต้องผ่านอะไรมาก่อน: 13.2, Part 7 (HTTP)
จบบทนี้แล้วจะทำได้: ส่งไฟล์ด้วย multipart ให้ถูก และรู้ว่าอะไรที่ห้ามแตะ

1. ทำไมไฟล์ส่งเป็น JSON ไม่ได้

คำขอ JSON ที่ใช้มาทั้งคอร์ส เป็นข้อความล้วน

Content-Type: application/json

{"partId": "P-100", "quantity": 5}

แต่ไฟล์รูปเป็นไบต์ดิบที่ไม่ใช่ข้อความ ทางเลือกมีสองทาง

ทางวิธีปัญหา
แปลงเป็นข้อความ (base64)ใส่ในฟิลด์ JSON ธรรมดาขนาดโตขึ้น 33% และต้องอ่านทั้งไฟล์เข้าหน่วยความจำสองรอบ
multipartส่งไบต์ดิบพร้อมข้อมูลอื่นในคำขอเดียวโครงคำขอซับซ้อนกว่า
base64 ใช้ได้กับไฟล์เล็กมาก เช่นลายเซ็นที่วาดบนหน้าจอ แต่กับรูปถ่าย การโตขึ้นหนึ่งในสามแปลว่ารูป 300 KB กลายเป็น 400 KB ซึ่งเสียเปล่าทุกครั้ง

2. multipart หน้าตาเป็นอย่างไร

POST /api/WMS/mobile_upload HTTP/1.1
Content-Type: multipart/form-data; boundary=dart-http-boundary-Xk7Qm

--dart-http-boundary-Xk7Qm
content-disposition: form-data; name="partId"

P-100
--dart-http-boundary-Xk7Qm
content-disposition: form-data; name="station"

PDA
--dart-http-boundary-Xk7Qm
content-disposition: form-data; name="file"; filename="IMG_0001.jpg"
content-type: application/octet-stream

...ไบต์ดิบของรูป...
--dart-http-boundary-Xk7Qm--
ส่วนหน้าที่
boundaryข้อความสุ่มที่ใช้คั่นแต่ละส่วน ต้องไม่ปรากฏในเนื้อข้อมูลเลย
name="partId"ชื่อช่องที่ฝั่งเซิร์ฟเวอร์ใช้อ่าน
filename="..."บอกว่าส่วนนี้เป็นไฟล์ ไม่ใช่ค่าข้อความ
บรรทัดว่างคั่นระหว่างส่วนหัวกับเนื้อหา
--boundary-- ปิดท้ายบอกว่าจบแล้ว ขาดไม่ได้

3. กฎเหล็กข้อเดียว

ห้ามตั้ง Content-Type เอง
// อย่าเขียนแบบนี้
request.headers['Content-Type'] = 'multipart/form-data';   // ← ไม่มี boundary

ถ้าตั้งเอง จะทับ boundary ที่ MultipartRequest สุ่มมา แล้วเซิร์ฟเวอร์จะแยกส่วนไม่ออก ผลคือ 400 ที่บอกว่า “ไม่พบไฟล์” ทั้งที่เราส่งไปแล้ว

..headers.addAll({
  // ห้ามตั้ง Content-Type เอง — MultipartRequest ต้องใส่ boundary
  // ที่มันสุ่มมาเอง ถ้าเราทับ เซิร์ฟเวอร์จะแยกส่วนของไฟล์ไม่ออก
  if (authToken != null) 'Authorization': 'Bearer $authToken',
  'Idempotency-Key': commandId,
})

กับดักนี้เกิดง่ายเมื่อคัดลอกโค้ดตั้ง header มาจากคำขอ JSON ปกติ ซึ่งมี Content-Type: application/json อยู่แล้ว

test('ส่งเป็น multipart พร้อมช่องและไฟล์', () async {
  ...
  // boundary ถูกสร้างโดย MultipartRequest ห้ามตั้ง Content-Type เอง
  expect(contentType, contains('multipart/form-data'));
  expect(contentType, contains('boundary='));
});

4. โค้ดที่ส่งจริง

final request = http.MultipartRequest('POST', Uri.parse('$baseUrl$path'))
  ..headers.addAll({ ... })
  ..fields.addAll(fields)
  ..files.add(
    http.MultipartFile.fromBytes(
      'file',
      image.bytes,
      filename: safeFileName(image.fileName, extension: image.extension),
    ),
  );

final streamed = await _client.send(request);
final response = await http.Response.fromStream(streamed);
บรรทัดเหตุผล
send() ไม่ใช่ post()MultipartRequest เป็น BaseRequest ไม่ใช่ Request ธรรมดา
ได้ StreamedResponseคำตอบมาเป็น stream ต้องรวบเป็น Response ก่อนอ่าน
fromBytes ไม่ใช่ fromPathทำงานได้ทุกแพลตฟอร์ม (13.2)

โค้ดจริงของ wmsapp ใช้ fromPath ซึ่งเป็นทางที่สั้นกว่าถ้าลงเฉพาะมือถือ

request.files.add(await http.MultipartFile.fromPath('file', file.path));

สังเกต await — fromPath ต้องอ่านขนาดไฟล์ก่อน จึงเป็น async ส่วน fromBytes รู้ขนาดอยู่แล้วจึงไม่ต้อง

5. อ่าน multipart ในเทสต์

ตอนเขียนเทสต์แรกจะเจอข้อผิดพลาดนี้

FormatException: Invalid UTF-8 byte (at offset 445)

เพราะ request.body พยายามถอดรหัสทั้งก้อนเป็น UTF-8 แต่ในนั้นมีไบต์ดิบของรูปปนอยู่ ซึ่งไม่ใช่ข้อความ

/// อ่าน body ของ multipart เป็นข้อความ
///
/// ใช้ latin1 ไม่ใช่ utf8 เพราะ body มีไบต์ดิบของรูปปนอยู่ ซึ่งไม่ใช่ UTF-8
/// ที่ถูกต้อง — `request.body` จะโยน FormatException ทันที
/// latin1 แปลงทีละไบต์เป็นตัวอักษร จึงค้นข้อความ ASCII ในนั้นได้
String multipartText(http.Request request) => latin1.decode(request.bodyBytes);

latin1 แปลงทุกไบต์ตั้งแต่ 0 ถึง 255 เป็นตัวอักษรได้เสมอ จึงไม่มีทางโยน — เหมาะกับการค้นหาข้อความ ASCII ในก้อนที่มีไบต์ดิบปน

expect(body, contains('name="partId"'));
expect(body, contains('P-100'));
expect(body, contains('name="file"'));
expect(body, contains('filename='));
เทสต์แบบนี้มีค่ามาก เพราะมันตรวจสิ่งที่เซิร์ฟเวอร์จะเห็นจริง ไม่ใช่แค่ว่าโค้ดของเราไม่โยน — และจับกรณีที่ชื่อช่องผิดได้ก่อนถึงมือใคร

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
400 บอกว่าไม่พบไฟล์ ทั้งที่ส่งไปแล้วตั้ง Content-Type เองทับ boundaryอย่าตั้ง
เซิร์ฟเวอร์อ่านช่องไม่เจอชื่อช่องไม่ตรงตกลงชื่อกับฝั่ง .NET แล้วเขียนเทสต์คุมไว้
เทสต์โยน Invalid UTF-8 byteอ่าน request.bodyใช้ latin1 กับ bodyBytes
413 Payload Too Largeเกินขีดของเซิร์ฟเวอร์หรือ proxyย่อรูป และถามขีดจริงจากทีมหลังบ้าน
อัปโหลดสำเร็จแต่ไฟล์เสียส่งไบต์ที่ถูกแปลงเป็นข้อความไปแล้วส่ง Uint8List ตรง ๆ อย่าแปลง
ใช้ post() แล้วคอมไพล์ไม่ผ่านMultipartRequest ต้องใช้ send()เปลี่ยนเป็น send()

8. แบบฝึกหัด

ทีมหลังบ้านจะทำ endpoint ใหม่ที่รับรูปได้หลายใบพร้อมกัน สำหรับการรับของที่ต้องถ่ายหลายมุม

  1. ฝั่งแอปต้องเปลี่ยนอะไร
  2. ควรส่งหลายใบในคำขอเดียว หรือส่งทีละใบ
แนวคำตอบ

1. multipart รองรับหลายไฟล์อยู่แล้ว เพิ่มเข้า files หลายตัวได้

for (final image in images) {
  request.files.add(http.MultipartFile.fromBytes(
    'files',                     // ชื่อเดียวกันทุกใบ
    image.bytes,
    filename: safeFileName(image.fileName, extension: image.extension),
  ));
}

ฝั่ง .NET รับด้วย [FromForm] List<IFormFile> files — สังเกตว่าชื่อช่องเป็นพหูพจน์และซ้ำกันทุกใบ ซึ่งเป็นข้อตกลงที่ต้องคุยกันให้ชัด เพราะบางระบบคาดหวัง files[0], files[1] แทน

2. เทียบสองทาง

คำขอเดียวหลายใบทีละใบ
ล้มเหลวกลางทางเสียทั้งชุด ต้องส่งใหม่หมดเสียเฉพาะใบนั้น
ความคืบหน้าบอกได้แค่รวมบอกได้ว่าใบไหนเสร็จแล้ว
จำนวนคำขอหนึ่งเท่าจำนวนใบ
ความสอดคล้องฝั่งเซิร์ฟเวอร์บันทึกพร้อมกันได้ในธุรกรรมเดียวอาจได้บางใบ ต้องมีวิธีจัดการ

บน PDA ในคลัง ทีละใบชนะ เพราะแถวแรกคือสิ่งที่เกิดบ่อยที่สุด — เน็ตหลุดกลางทางแล้วต้องส่งรูปห้าใบใหม่ทั้งหมด เสียเวลาและเสียใจ ส่วนการส่งทีละใบ ใบที่ผ่านไปแล้วก็ผ่านเลย

ที่ต้องจัดการเพิ่มคือแถวสุดท้าย — ถ้าส่งได้สามจากห้าใบแล้วผู้ใช้ปิดแอป เซิร์ฟเวอร์จะมีรูปสามใบที่ไม่ครบชุด ทางแก้คือให้ทุกใบผูกกับรหัสการรับของเดียวกัน แล้วให้ฝั่งเซิร์ฟเวอร์ถือว่าชุดนั้นสมบูรณ์เมื่อผู้ใช้กดยืนยันการรับ ไม่ใช่เมื่อรูปครบ

ซึ่งกลับไปที่หลักใน 13.1 — อย่าให้รูปบล็อกงานหลัก

9. สรุป

  • multipart ส่งไบต์ดิบพร้อมข้อมูลอื่นในคำขอเดียว โดยไม่โตขึ้นเหมือน base64
  • ห้ามตั้ง Content-Type เอง เพราะจะทับ boundary
  • ใช้ send() ไม่ใช่ post()
  • ชื่อช่องต้องตรงกับฝั่ง .NET เป๊ะ ๆ
  • เทสต์อ่าน body ด้วย latin1 เพื่อตรวจสิ่งที่เซิร์ฟเวอร์จะเห็นจริง
  • หลายใบให้ส่งทีละใบ เพราะเน็ตหลุดกลางทางเป็นเรื่องปกติ
