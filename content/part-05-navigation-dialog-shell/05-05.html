ระดับ: กลางใช้เวลา: 30–40 นาทีลงมือทำ: กันงานที่ทำค้างไว้ไม่ให้หายเพราะกดย้อนกลับ
ต้องผ่านอะไรมาก่อน: 5.1 (ปุ่มย้อนกลับคือ pop) และ 5.3 (ผลลัพธ์ที่ส่งกลับ)
จบบทนี้แล้วจะทำได้: ใช้ PopScope ถามยืนยันก่อนปิดหน้าที่มีของค้าง โดยไม่ทำให้เกิดวงวนหรือปิดสองรอบ

3. Mental model: บอกล่วงหน้า ไม่ใช่ห้ามทีหลัง

จุดที่ทำให้หลายคนเขียน PopScope ผิด คือคิดว่ามันทำงานแบบ “ดักตอนกด แล้วยกเลิก”

สิ่งที่คิด:  ผู้ใช้กด → เราดัก → ยกเลิกการปิด
สิ่งที่จริง:  เราประกาศไว้ล่วงหน้าว่าปิดได้ไหม → ระบบทำตามนั้น
ประโยคเดียวที่ต้องจำ: canPop ต้องสะท้อนความจริง ตลอดเวลา ไม่ใช่เฉพาะตอนที่ผู้ใช้กด — เพราะ Android ต้องรู้ล่วงหน้าเพื่อจะวาดตัวอย่างหน้าถัดไปให้เห็นระหว่างปัด

นี่คือเหตุผลที่ PopScope รับ canPop เป็นค่า ไม่ใช่เป็นฟังก์ชันที่ถามตอนกด

4. โครงพื้นฐาน

เปิด lib/nav_basics/task_detail_screen.dart

@override
Widget build(BuildContext context) => PopScope(
  // ปล่อยให้ปิดได้เองเมื่อไม่มีอะไรค้าง
  canPop: !_isDirty,
  onPopInvokedWithResult: (didPop, result) async {
    // ปิดไปแล้ว ห้ามสั่งปิดซ้ำ
    if (didPop) return;
    final discard = await showDiscardDialog(context);
    if (!discard || !context.mounted) return;
    Navigator.of(context).pop(const TaskCancelled());
  },
  child: Scaffold(...),
);

ไล่ดูสองเส้นทาง

_isDirtycanPopกดย้อนกลับแล้วเกิดอะไร
falsetrueปิดทันที แล้ว callback ถูกเรียกด้วย didPop == true
truefalseไม่ปิด แล้ว callback ถูกเรียกด้วย didPop == false

สังเกตว่า callback ถูกเรียก ทั้งสองกรณี — ซึ่งเป็นที่มาของบั๊กที่พบบ่อยที่สุดในบทนี้

5. บรรทัด if (didPop) return; คือหัวใจ

ถ้าลืมบรรทัดนี้

onPopInvokedWithResult: (didPop, result) async {
  // ลืมตรวจ didPop
  final discard = await showDiscardDialog(context);
  if (discard) Navigator.of(context).pop();
}

ผลที่ได้เมื่อ _isDirty เป็น false

ผู้ใช้กดย้อนกลับ
  → canPop เป็น true → หน้าถูกปิดไปแล้ว
  → callback ทำงาน → เปิดกล่องถามบนหน้าที่ปิดไปแล้ว
  → ผู้ใช้กดทิ้งไป → pop() อีกครั้ง → ปิดหน้าที่อยู่ข้างล่างไปด้วย

อาการที่เห็นคือ “กดย้อนกลับหนึ่งครั้ง แต่ถอยไปสองหน้า” ซึ่งเกิดเป็นครั้งคราวและอธิบายยากถ้าไม่รู้สาเหตุ

กฎที่ใช้ได้ทุกครั้ง — onPopInvokedWithResult ต้องขึ้นต้นด้วย if (didPop) return; เสมอ ยกเว้นจะรู้แน่ว่ากำลังทำอะไรอยู่

6. canPop ต้องคำนวณ ไม่ใช่เก็บ

เปิดดูว่า _isDirty มาจากไหน

/// มีอะไรที่แก้ไว้แล้วยังไม่ได้ส่งกลับหรือไม่
bool get _isDirty =>
    _quantity != widget.task.quantity ||
    _palletCode != widget.task.palletCode ||
    _noteController.text != widget.task.note;

เป็น getter ที่เทียบกับค่าตั้งต้น ไม่ใช่ bool _isDirty = false; ที่ตั้งเป็น true ทุกครั้งที่มีการแก้

เก็บเป็น fieldคำนวณจากค่าจริง
แก้แล้วแก้กลับเป็นค่าเดิมยังบอกว่า dirty — ถามทั้งที่ไม่มีอะไรเปลี่ยนบอกว่าไม่ dirty ถูกต้อง
ลืมตั้งค่าในบางเส้นทางเป็นไปได้เป็นไปไม่ได้

เป็นหลักการเดียวกับ 4.2 — อย่าเก็บสิ่งที่คำนวณได้

และเพราะ _isDirty อ่านจาก _noteController.text หน้าจอจึงต้องวาดใหม่เมื่อผู้ใช้พิมพ์ ไม่งั้น canPop จะยังเป็นค่าเก่า

_noteController.addListener(_onNoteChanged);
...
void _onNoteChanged() => setState(() {});

ตรงนี้คือเหตุผลที่ต้องฟัง controller ตาม 3.4 — ไม่ใช่แค่เพื่อเปิดปิดปุ่มบันทึก แต่เพื่อให้ canPop ตรงกับความจริงตลอดเวลาตามที่หัวข้อ 3 บอกไว้

7. ปุ่มที่เราทำเองก็ต้องผ่านด่านเดียวกัน

ปัญหาที่โผล่ทันทีที่มีปุ่มย้อนกลับของตัวเอง

// ผิด — ข้าม PopScope ไปเลย
IconButton(
  icon: const Icon(Icons.close),
  onPressed: () => Navigator.of(context).pop(),
)
// ถูก — ขอปิด แล้วให้ PopScope ตัดสิน
IconButton(
  icon: const Icon(Icons.close),
  onPressed: () => Navigator.of(context).maybePop(),
)
pop()maybePop()
เคารพ PopScopeไม่ใช่
ใช้เมื่อตัดสินใจแล้วว่าจะปิดจริงผู้ใช้ขอปิด แต่ยังต้องผ่านการตรวจ

ใน lab ปุ่มบันทึกและปุ่มพักไว้ก่อนใช้ pop() ตรง ๆ ซึ่งถูกต้อง เพราะทั้งสองเป็นการตัดสินใจที่ชัดเจนแล้ว ไม่ใช่การ “ขอออก”

ถ้ามีหลายทางออกจากหน้าเดียวกัน ต้องทำให้ทุกทางที่แปลว่า “ขอออกโดยยังไม่ตัดสินใจ” ไปรวมที่ maybePop() ทางเดียว ไม่งั้นจะมีทางที่หลุดการตรวจ

8. ใช้ย้อนขั้นตอนภายในหน้าเดียวกัน

เมื่อหน้าจอมีหลายขั้นตอน (4.15) ปุ่มย้อนกลับควรถอยทีละขั้น ไม่ใช่ออกจากงานทั้งหมด

PopScope(
  // อยู่ขั้นแรกถึงจะออกจากหน้าได้
  canPop: _state is ScanPallet,
  onPopInvokedWithResult: (didPop, result) {
    if (didPop) return;
    // ยังไม่ใช่ขั้นแรก — ถอยหนึ่งขั้นแทนการปิดหน้า
    _goToPreviousStep();
  },
  child: ...,
)

ผู้ใช้จึงกดย้อนกลับได้ตามสัญชาตญาณ และมันทำสิ่งที่เขาคาดหวังคือ “ถอยหนึ่งก้าว” ไม่ใช่ “ทิ้งงานทั้งหมด”

สังเกตว่าเมื่อถอยจนถึงขั้นแรก canPop จะกลายเป็น true เอง แล้วการกดครั้งถัดไปจึงออกจากหน้าจริง — โดยไม่ต้องเขียนเงื่อนไขพิเศษอะไรเพิ่ม

9. บางครั้งไม่ควรถาม แต่ควรเก็บให้เลย

PopScope ที่ถามยืนยันไม่ใช่คำตอบของทุกงาน

ลักษณะงานควรทำ
แก้ไม่กี่ช่อง เสียหายน้อยถ้าหายถามยืนยัน
สแกนมาแล้วหลายสิบบรรทัดเก็บเป็นร่างอัตโนมัติ แล้วให้กลับมาทำต่อได้
กำลังส่งข้อมูลอยู่ห้ามปิด และบอกว่ากำลังส่ง

แถวกลางสำคัญ — ถ้างานที่หายมีมูลค่าสูงพอ การถามว่า “จะทิ้งไหม” ก็ยังเป็นการออกแบบที่ไม่ดี เพราะผู้ใช้อาจกดผิดอีกรอบ ทางที่ดีกว่าคือทำให้มันไม่หายตั้งแต่แรก

และแถวล่างคือกรณีที่ต้องใช้ canPop: false จริง ๆ ระหว่างที่คำสั่งยังไม่จบ ตามที่ทำใน 4.14

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
กดย้อนกลับหนึ่งครั้ง ถอยไปสองหน้าลืม if (didPop) return;ใส่บรรทัดแรกเสมอ
ถามยืนยันทั้งที่ไม่ได้แก้อะไรเก็บ dirty เป็น field แล้วตั้งค่าไม่ตรงคำนวณจากค่าจริง
ปัดย้อนกลับบน Android แล้วภาพกระตุกcanPop ไม่ตรงกับความจริง ณ ขณะนั้นทำให้หน้าจอวาดใหม่เมื่อค่าที่เกี่ยวข้องเปลี่ยน
ปุ่มปิดที่ทำเองข้ามการตรวจไปเลยใช้ pop() แทน maybePop()เปลี่ยนเป็น maybePop()
กล่องยืนยันเด้งซ้อนกันหลายอันกดย้อนกลับรัว ๆ ระหว่างที่กล่องเปิดอยู่ธงกันซ้ำ หรือปิดการโต้ตอบระหว่างถาม
ปิดหน้าไปทั้งที่ยังส่งข้อมูลไม่เสร็จไม่ได้ตั้ง canPop: false ระหว่างส่งรวมสถานะกำลังส่งเข้าไปในเงื่อนไข

11. แบบฝึกหัด

หน้าสแกนรับเข้าหนึ่งหน้า มีสามสถานะ

สถานะคำอธิบาย
ยังไม่ได้สแกนอะไรรายการว่าง
สแกนไปแล้วบางส่วนมี 1 บรรทัดขึ้นไป ยังไม่ได้ส่ง
กำลังส่งขึ้นเซิร์ฟเวอร์กดยืนยันแล้ว รอผลอยู่
  1. เขียน canPop ให้ครบทั้งสามสถานะ
  2. เขียน onPopInvokedWithResult ที่ทำต่างกันตามสถานะ
  3. ตอบว่าถ้าสแกนไปแล้ว 40 บรรทัด การถามว่า “จะทิ้งไหม” เพียงพอหรือไม่
ดูแนวคำตอบและเหตุผล

ข้อ 1 และ 2 — โค้ด

bool get _hasScannedLines => _lines.isNotEmpty;

@override
Widget build(BuildContext context) => PopScope(
  // ปิดได้เฉพาะตอนที่ไม่มีอะไรค้างและไม่ได้กำลังส่ง
  canPop: !_hasScannedLines && !_submitting,
  onPopInvokedWithResult: (didPop, result) async {
    if (didPop) return;

    // กำลังส่งอยู่ — ห้ามออก และบอกว่าทำไม
    if (_submitting) {
      showResultBanner(
        ScaffoldMessenger.of(context),
        'กำลังส่งข้อมูล กรุณารอสักครู่',
      );
      return;
    }

    // มีของค้าง — ให้เลือกสามทาง ไม่ใช่สองทาง
    final choice = await showExitChoiceDialog(context, lineCount: _lines.length);
    if (!context.mounted) return;
    switch (choice) {
      case ExitChoice.keepScanning:
        return;                                  // ไม่ทำอะไร
      case ExitChoice.saveDraft:
        await _saveDraft();
        if (!context.mounted) return;
        Navigator.of(context).pop(const ReceivePaused());
      case ExitChoice.discard:
        Navigator.of(context).pop(const ReceiveCancelled());
      case null:
        return;                                  // ปิดกล่องเฉย ๆ
    }
  },
  child: ...,
);

สังเกตว่ากล่องถามคืน enum สามค่า ไม่ใช่ bool — เป็นเหตุผลเดียวกับ 5.3 คือมีสามทางที่ต้องทำต่างกัน

ข้อ 3 — 40 บรรทัด การถามว่าจะทิ้งไหม พอไหม

ไม่พอ และเหตุผลลึกกว่าที่คิด

เหตุผลที่หนึ่ง — กล่องยืนยันกันได้แค่การกดผิดครั้งเดียว

นิ้วโดนปุ่มย้อนกลับ → กล่องเด้ง → นิ้วยังอยู่ที่เดิม → โดนปุ่ม "ทิ้งไป" พอดี

บน PDA ที่ถือด้วยมือเดียวและใส่ถุงมือ เหตุการณ์นี้เกิดจริง

เหตุผลที่สอง — คำถามนั้นตอบยากเกินไป

“จะทิ้งไหม” บังคับให้ผู้ใช้เลือกระหว่างเสียงาน 40 บรรทัด กับติดอยู่ในหน้านั้นต่อ ทั้งที่สิ่งที่เขาต้องการจริง ๆ อาจเป็น “ขอไปดูอย่างอื่นแป๊บหนึ่ง แล้วจะกลับมา”

เหตุผลที่สาม — งานสำคัญไม่ควรอยู่ในที่ที่หายได้

ทางเลือกงานหายเมื่อ
เก็บใน State อย่างเดียว + ถามก่อนปิดกดผิด, แอปถูกระบบปิด, แบตหมด, เครื่องค้าง
เก็บลงเครื่องทุกครั้งที่สแกนแทบไม่มี

สิ่งที่ควรทำจริง

สแกนแต่ละบรรทัด → เก็บลงเครื่องทันที
กดย้อนกลับ      → ไม่ต้องถามว่าจะทิ้งไหม
                   ถามว่า "เก็บไว้ทำต่อ" หรือ "ยกเลิกใบนี้"
เปิดกลับเข้ามา   → เจอ 40 บรรทัดเดิมรออยู่

เมื่อทำแบบนี้แล้ว PopScope ยังมีประโยชน์อยู่ แต่หน้าที่ของมันเปลี่ยนไป — จากการ กันไม่ให้งานหาย กลายเป็นการ ถามว่าจบใบนี้อย่างไร ซึ่งเป็นคำถามที่ตอบง่ายกว่ามาก

หลักที่ได้: PopScope เหมาะกับงานที่หายแล้วเสียดายนิดหน่อย ส่วนงานที่หายแล้วต้องทำใหม่ทั้งหมด ต้องแก้ด้วยการทำให้มันไม่หาย ไม่ใช่ด้วยการถาม — การเก็บข้อมูลลงเครื่องจะทำจริงใน Part 12

12. สรุปท้ายบท

  • PopScope ประกาศล่วงหน้าว่าปิดได้ไหม ไม่ใช่ดักตอนกด
  • canPop ต้องตรงกับความจริงตลอดเวลา จึงต้องวาดใหม่เมื่อค่าที่เกี่ยวข้องเปลี่ยน
  • onPopInvokedWithResult ถูกเรียกทั้งตอนที่ปิดได้และปิดไม่ได้
  • ขึ้นต้น callback ด้วย if (didPop) return; เสมอ
  • คำนวณ dirty จากค่าจริง อย่าเก็บเป็น field
  • ทางออกที่แปลว่า “ขอออก” ต้องผ่าน maybePop() ทุกทาง
  • ใช้ย้อนขั้นตอนภายในหน้าเดียวกันได้ ไม่ใช่แค่ปิดหน้า
  • งานที่หายแล้วต้องทำใหม่ทั้งหมด ต้องแก้ด้วยการเก็บ ไม่ใช่ด้วยการถาม
