ระดับ: กลางใช้เวลา: 35–45 นาทีลงมือทำ: เข้าและออกจากระบบโดยไม่เหลือหน้าเก่าค้าง
ต้องผ่านอะไรมาก่อน: 5.1 (stack ของหน้าจอ) และ 4.12 (การเก็บกวาดทรัพยากร)
จบบทนี้แล้วจะทำได้: เลือกใช้ pushReplacement กับ pushAndRemoveUntil ได้ถูกจังหวะ และรู้ว่าการล้างหน้าจอไม่เท่ากับการออกจากระบบ

1. ปัญหาที่บทนี้แก้

ลองนึกภาพว่าใช้ push ธรรมดากับการเข้าสู่ระบบ

┌──────────────────┐
│ หน้าหลัก          │  ← ผู้ใช้อยู่ตรงนี้
├──────────────────┤
│ เข้าสู่ระบบ       │  ← ยังค้างอยู่ข้างล่าง
└──────────────────┘

กดปุ่มย้อนกลับหนึ่งครั้ง แล้วจะกลับไปหน้าเข้าสู่ระบบทั้งที่ล็อกอินอยู่ — สับสนทันที

และปัญหาฝั่งตรงข้ามที่ร้ายแรงกว่า — ออกจากระบบขณะอยู่ลึก ๆ ในแอป แล้วปุ่มย้อนกลับพากลับเข้าไปดูข้อมูลของคนที่ออกไปแล้ว

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
pushReplacementวางหน้าใหม่แทนหน้าบนสุด
pushAndRemoveUntilวางหน้าใหม่แล้วเอาหน้าที่เหลือออกตามเงื่อนไข
predicateฟังก์ชันที่ตอบว่าจะเก็บหน้านั้นไว้ไหม
sessionข้อมูลของผู้ใช้ที่ล็อกอินอยู่
tokenบัตรผ่านที่ใช้คุยกับเซิร์ฟเวอร์

3. Mental model: เข้าคือแทนที่ ออกคือล้างทั้งกอง

เข้าสู่ระบบ   [เข้าสู่ระบบ]  →  [หน้าหลัก]
              แทนที่ใบเดียว เพราะตอนนั้นมีใบเดียว

ออกจากระบบ   [เข้าสู่ระบบ]  ←  [หน้าหลัก][รายละเอียด][ยืนยัน]
              ต้องล้างทุกใบ ไม่ใช่แทนแค่ใบบนสุด
ประโยคเดียวที่ต้องจำ: ตอนเข้าสู่ระบบเรารู้ว่ามีกี่ใบ ตอนออกจากระบบเราไม่รู้ — จึงต้องใช้เมธอดที่ไม่ต้องรู้

4. เข้าสู่ระบบ: pushReplacement

เปิด lib/nav_basics/nav_basics_app.dart

void _signIn(BuildContext context) {
  session.signIn('somchai');
  // pushReplacement แทนหน้าเข้าสู่ระบบด้วยหน้าหลัก
  // ถ้าใช้ push เฉย ๆ ปุ่มย้อนกลับจะพากลับเข้าหน้าเข้าสู่ระบบเดิม
  Navigator.of(context).pushReplacement(
    MaterialPageRoute<void>(builder: (_) => HomeShell(session: session)),
  );
}

เทสต์ที่ยืนยันว่าทำถูก

expect(tester.state<NavigatorState>(find.byType(Navigator)).canPop(), isFalse);

canPop() เป็น false แปลว่าเหลือหน้าเดียวในกอง — หน้าเข้าสู่ระบบถูกเอาออกไปแล้วจริง

5. ออกจากระบบ: pushReplacement ไม่พอ

ตอนสร้าง lab นี้ ผมเขียนวิธีที่ดูสวยกว่าไว้ก่อน — ให้แอปสลับระหว่างหน้าเข้าสู่ระบบกับหน้าหลักตามสถานะของ session

// วิธีที่ผมเขียนไว้ตอนแรก และมันผิด
MaterialApp(
  home: ListenableBuilder(
    listenable: session,
    builder: (context, child) => session.authenticated
        ? HomeShell(session: session)
        : LoginScreen(session: session),
  ),
)

ดูสมเหตุสมผล — พอ signOut() ถูกเรียก สถานะเปลี่ยน หน้าจอก็สลับกลับไปหน้าเข้าสู่ระบบเอง โดยไม่ต้องไล่ pop

เทสต์จับได้ทันทีว่าไม่จริง

await openFirstTask(tester);       // push หน้ารายละเอียดขึ้นมา
session.signOut();
await tester.pumpAndSettle();

expect(find.text('งาน T-001'), findsNothing);   // ล้มเหลว — ยังเจออยู่

สาเหตุคือ home เป็นแค่ หน้าแรกในกอง ไม่ใช่ทั้งกอง

┌──────────────────┐
│ รายละเอียดงาน     │  ← push ขึ้นมา ไม่เกี่ยวกับ home
├──────────────────┤
│ home             │  ← เปลี่ยนได้ แต่เปลี่ยนแค่ใบนี้
└──────────────────┘

การเปลี่ยน home ทำให้ใบล่างสุดกลายเป็นหน้าเข้าสู่ระบบ แต่หน้ารายละเอียดยังทับอยู่ข้างบนเหมือนเดิม ผู้ใช้จึงยังเห็นข้อมูลงานอยู่ทั้งที่ออกจากระบบไปแล้ว

บทเรียนที่ได้ — การเปลี่ยนสิ่งที่หน้าจอแสดง กับการเปลี่ยนสิ่งที่อยู่ในกอง เป็นคนละเรื่อง ตราบใดที่ยังใช้ Navigator แบบ stack การล้างกองต้องสั่งอย่างชัดเจน

6. ทางที่ถูก: pushAndRemoveUntil

void _signOut() {
  widget.session.signOut();
  Navigator.of(context).pushAndRemoveUntil(
    MaterialPageRoute<void>(
      builder: (_) => LoginScreen(session: widget.session),
    ),
    (route) => false,        // ไม่เก็บ route ไหนไว้เลย
  );
}

พารามิเตอร์ตัวที่สองคือเงื่อนไขว่า จะหยุดลบเมื่อไหร่

เงื่อนไขผลลัพธ์ใช้เมื่อ
(route) => falseลบทั้งหมดออกจากระบบ
(route) => route.isFirstเก็บใบล่างสุดไว้กลับไปหน้าแรกของแอป
(route) => route.settings.name == '/home'ลบจนถึงหน้าที่ระบุจบ workflow แล้วกลับหน้าหลัก

สังเกตว่ามันอ่านกลับหัวจากที่คิด — คืน false แปลว่า “ยังไม่ใช่ ลบต่อ” ไม่ใช่ “ห้ามลบ”

เทสต์ที่ตรึงพฤติกรรมนี้

testWidgets('ออกจากระบบตอนอยู่ลึกในแอป ต้องไม่มีหน้าเก่าค้างอยู่', (tester) async {
  ...
  expect(session.authenticated, isFalse);
  expect(find.byKey(const Key('bottom-nav')), findsNothing);
  // ล้าง stack หมดแล้ว จึงย้อนกลับเข้าหน้าหลักไม่ได้อีก
  expect(tester.state<NavigatorState>(find.byType(Navigator)).canPop(), isFalse);
});

7. ล้างหน้าจอ ไม่เท่ากับ ออกจากระบบ

นี่เป็นจุดที่สำคัญกว่าเรื่อง Navigator ทั้งหมดในบทนี้

Navigator.pushAndRemoveUntil(...)   ← ทำให้ผู้ใช้ "มองไม่เห็น" ข้อมูลเก่า
                                       ไม่ได้ทำให้เขา "เข้าถึงไม่ได้"
ต้องล้างอะไรบ้างถ้าลืม
token ที่เก็บไว้ในเครื่องเปิดแอปใหม่แล้วเข้าได้เลยโดยไม่ต้องล็อกอิน
ข้อมูลใน store ที่ยังอยู่ในหน่วยความจำล็อกอินคนใหม่แล้วเห็นงานของคนเก่า
ตัวจับเวลาที่ยังเดินอยู่ (4.11)ยังยิงคำขอด้วย token เก่าเรื่อย ๆ
คำขอที่ยังค้างอยู่ (4.10)ผลกลับมาแล้วเขียนลง store ของ session ที่จบไปแล้ว
ไฟล์หรือฐานข้อมูลที่เก็บไว้ในเครื่องคนถัดไปที่ถือ PDA เครื่องนั้นเปิดดูได้

แถวสุดท้ายสำคัญเป็นพิเศษกับ PDA เพราะ เครื่องหนึ่งใช้กันทั้งกะ และเปลี่ยนมือทุกวัน — ไม่เหมือนโทรศัพท์ส่วนตัวที่คนเดียวใช้

และต่อให้ล้างทุกอย่างในเครื่องแล้ว ก็ยังไม่พอ — เซิร์ฟเวอร์ต้องปฏิเสธ token ที่ออกจากระบบไปแล้วด้วย เพราะฝั่งแอปเป็นแค่ด่านแรก ไม่ใช่ด่านจริง เป็นหลักเดียวกับ 4.14 หัวข้อ 8

8. ลำดับสำคัญ

// ลำดับที่ถูก
1. ล้าง token และข้อมูลในเครื่อง
2. หยุดตัวจับเวลาและงานที่ยังค้าง
3. แล้วค่อยเปลี่ยนหน้าจอ

ถ้าเปลี่ยนหน้าจอก่อน จะมีช่วงหนึ่งที่หน้าเข้าสู่ระบบขึ้นมาแล้วแต่ตัวจับเวลายังยิงคำขออยู่เบื้องหลัง

ใน lab ลำดับนี้ปรากฏชัดในสองบรรทัด

widget.session.signOut();        // ล้างสถานะก่อน
Navigator.of(context).pushAndRemoveUntil(...);   // แล้วค่อยเปลี่ยนหน้า

ในแอปจริงขั้นแรกมักเป็น await เพราะต้องลบข้อมูลในเครื่อง ซึ่งแปลว่ามี async gap และต้องตรวจ mounted ตาม 4.9

Future<void> _signOut() async {
  await authRepository.signOut();     // ลบ token จริง
  if (!context.mounted) return;
  Navigator.of(context).pushAndRemoveUntil(..., (route) => false);
}

9. ใครควรเป็นคนสั่งเปลี่ยนหน้า

สังเกตว่าใน lab แผ่นตั้งค่าไม่ได้เรียก Navigator เอง

// ใน SettingsSheet
Navigator.of(context).pop();      // ปิดแผ่นก่อน
widget.onSignOut();               // แล้วให้เจ้าของหน้าจอจัดการเส้นทาง
/// แผ่นนี้ไม่รู้จักเส้นทางของแอป จึงบอกได้แค่ว่า "ผู้ใช้ขอออกจากระบบ"
/// แล้วให้เจ้าของหน้าจอเป็นคนตัดสินว่าต้องล้าง stack อย่างไร
final VoidCallback onSignOut;
เหตุผลผลที่ได้
แผ่นตั้งค่าอาจถูกเปิดจากหลายที่แต่ละที่ล้าง stack ไม่เหมือนกันได้
แผ่นไม่ต้องรู้ว่าหน้าเข้าสู่ระบบชื่ออะไรไม่ต้อง import กันไปมา
ทดสอบแผ่นได้โดยไม่ต้องมีเส้นทางจริงส่ง callback ปลอมเข้าไปแล้วตรวจว่าถูกเรียก

หลักนี้ใช้กับทุกชั้นที่อยู่ลึก — ชั้นที่รู้เรื่องเส้นทางน้อยที่สุด ควรตัดสินใจเรื่องเส้นทางน้อยที่สุด โดยเฉพาะ repository และ store ซึ่งไม่ควรแตะ Navigator เลย เพราะจะทำให้ทดสอบไม่ได้และผูกกับ BuildContext ตาม 4.9 หัวข้อ 8

10. เมื่อเซิร์ฟเวอร์บอกว่าหมดอายุ

กรณีที่ผู้ใช้ไม่ได้กดออกเอง แต่ token หมดอายุระหว่างทำงาน

คำขอที่ 1 → 401
คำขอที่ 2 → 401     สามคำขอที่วิ่งพร้อมกัน
คำขอที่ 3 → 401     ต่างคนต่างสั่งเปลี่ยนหน้า

ผลคือหน้าเข้าสู่ระบบถูกเปิดซ้อนกันสามชั้น กดย้อนกลับก็เจออีกหน้า

ต้องทำเหตุผล
ให้จุดเดียวเป็นคนตัดสินไม่ให้แต่ละคำขอสั่งเปลี่ยนหน้าเอง
ทำครั้งเดียว แม้ได้ 401 มาสิบครั้งธงกันซ้ำแบบเดียวกับ 4.14
บอกผู้ใช้ว่าทำไมถึงหลุดไม่งั้นเขาจะคิดว่าแอปพัง
เก็บงานที่ทำค้างไว้อย่างปลอดภัย ถ้าทำได้อย่าทิ้งงานของผู้ใช้เงียบ ๆ

รายละเอียดของการดักรหัส 401 อยู่ใน Part 8

11. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ล็อกอินแล้วกดย้อนกลับ กลับไปหน้าเข้าสู่ระบบใช้ push แทน pushReplacementเปลี่ยนเป็น pushReplacement
ออกจากระบบแล้วกดย้อนกลับ กลับเข้าหน้าหลักใช้ pushReplacement ตอนอยู่ลึกpushAndRemoveUntil พร้อม (route) => false
เปลี่ยน home แล้วหน้าเก่ายังอยู่home เป็นแค่ใบล่างสุดสั่งล้างกองอย่างชัดเจน
เปิดแอปใหม่แล้วเข้าได้โดยไม่ต้องล็อกอินล้างหน้าจอแต่ไม่ได้ล้าง tokenล้างข้อมูลในเครื่องด้วย
ล็อกอินคนใหม่แล้วเห็นงานของคนเก่าstore เก่ายังอยู่ในหน่วยความจำทำลาย store พร้อม session
หน้าเข้าสู่ระบบซ้อนกันหลายชั้นหลายคำขอได้ 401 พร้อมกันให้จุดเดียวตัดสิน + ธงกันซ้ำ
ยังมีคำขอยิงออกไปหลังออกจากระบบไม่ได้หยุดตัวจับเวลาหยุดก่อนเปลี่ยนหน้า (4.11)

12. แบบฝึกหัด

แอปคลังหนึ่งมีเส้นทางแบบนี้

เข้าสู่ระบบ → หน้าหลัก → รายการรับเข้า → ใบรับเข้า → ยืนยัน

ผู้ใช้ยืนอยู่ที่หน้ายืนยัน มีรายการที่สแกนไว้แล้ว 18 บรรทัดที่ยังไม่ได้ส่ง แล้ว token หมดอายุ

  1. เขียนลำดับสิ่งที่ต้องทำ ตั้งแต่รู้ว่า token หมดอายุจนถึงหน้าเข้าสู่ระบบ
  2. ตัดสินว่าจะทำอย่างไรกับ 18 บรรทัดนั้น
  3. ตอบว่าถ้าผู้ใช้ล็อกอินกลับเข้ามาเป็นคนเดิม กับเป็นคนละคน ควรทำต่างกันไหม
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ลำดับที่ต้องทำ

1. คำขอแรกได้ 401
2. ตัวจัดการกลางตรวจว่ากำลังจัดการอยู่แล้วหรือยัง
   ถ้ายัง → ตั้งธงว่ากำลังจัดการ  (คำขออื่นที่ได้ 401 ตามมาจะไม่ทำซ้ำ)
3. หยุดตัวจับเวลาและงานเบื้องหลังทั้งหมด
4. เก็บงานที่ทำค้างไว้ลงเครื่อง            ← ข้อ 2
5. ล้าง token และข้อมูลที่อ่อนไหวในเครื่อง
6. ทำลาย store ของ session นี้
7. เปลี่ยนหน้าด้วย pushAndRemoveUntil((route) => false)
8. แสดงข้อความว่า "เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่"

จุดที่คนมักสลับลำดับคือข้อ 4 กับ 5 — ต้องเก็บงานก่อนล้างข้อมูล ไม่งั้นจะล้างงานของผู้ใช้ไปด้วย

และข้อ 3 ต้องมาก่อนข้อ 5 เสมอ ไม่งั้นตัวจับเวลาจะยิงคำขอด้วย token ที่เพิ่งลบไป แล้วได้ 401 กลับมาอีกรอบ

ข้อ 2 — จะทำอย่างไรกับ 18 บรรทัด

ต้องเก็บไว้ ไม่ใช่ทิ้ง

ทางเลือกผลที่ตามมา
ทิ้งไปเลยผู้ใช้เดินสแกนของ 18 บรรทัดใหม่ทั้งหมด
ส่งขึ้นเซิร์ฟเวอร์ก่อนออกทำไม่ได้ — token หมดอายุแล้ว จึงส่งไม่ผ่าน
เก็บลงเครื่องเป็นร่างล็อกอินกลับมาแล้วทำต่อได้

สิ่งที่ต้องเก็บคือ ข้อมูลของงาน ไม่ใช่ข้อมูลของผู้ใช้ — เก็บรหัสสินค้า จำนวน รหัสพาเลท และรหัสคำสั่งที่สร้างไว้แล้ว (4.14) แต่ไม่เก็บ token ไม่เก็บชื่อผู้ใช้

ข้อ 3 — คนเดิมกับคนละคน

ต้องทำต่างกัน และนี่คือประเด็นที่มักถูกมองข้ามจนกลายเป็นปัญหาจริง

ร่างที่ค้างไว้เสนอให้ทำต่อห้ามเสนอ
เหตุผลเป็นงานของเขาเองเป็นงานของคนอื่น

ทำไมถึงสำคัญ — บนคลังจริง PDA เครื่องเดียวเปลี่ยนมือทั้งวัน ถ้าคนกะดึกเปิดแอปแล้วเจอ “มีงานรับเข้าค้างอยู่ 18 บรรทัด ทำต่อไหม” ซึ่งเป็นงานของคนกะบ่าย เขาอาจกดทำต่อโดยไม่รู้ แล้วของ 18 บรรทัดนั้นถูกบันทึกในชื่อคนผิด

วิธีทำให้ถูก — ผูกร่างไว้กับผู้ใช้ที่สร้างมัน

// ตอนเก็บ
await draftStorage.save(userId: session.userId, draft: draft);

// ตอนล็อกอินกลับมา
final draft = await draftStorage.load(userId: session.userId);
if (draft != null) {
  // เสนอให้ทำต่อ เฉพาะเจ้าของเท่านั้น
}

และร่างของคนอื่นที่ยังค้างอยู่ ไม่ควรลบทิ้งเงียบ ๆ เพราะเจ้าของอาจกลับมาที่เครื่องนี้ — แต่ควรมีนโยบายว่าเก็บไว้กี่วัน และควรแจ้งหัวหน้าถ้ามีงานค้างข้ามกะ

ข้อสังเกตสุดท้าย: ทั้งบทนี้มีสองชั้นที่ต้องแยกให้ออก — ชั้นหน้าจอ ทำให้มองไม่เห็น และ ชั้นข้อมูล ทำให้เข้าถึงไม่ได้ การทำแค่ชั้นแรกแล้วคิดว่าปลอดภัย คือความผิดพลาดที่พบบ่อยที่สุดในเรื่องนี้

13. สรุปท้ายบท

  • เข้าสู่ระบบใช้ pushReplacement เพราะรู้ว่าแทนใบไหน
  • ออกจากระบบใช้ pushAndRemoveUntil เพราะไม่รู้ว่าผู้ใช้อยู่ลึกแค่ไหน
  • เงื่อนไข (route) => false แปลว่าลบทั้งหมด
  • เปลี่ยน home ไม่ได้ล้างหน้าที่ push ทับอยู่
  • ล้างหน้าจอไม่เท่ากับออกจากระบบ — ต้องล้าง token, store, ตัวจับเวลา และข้อมูลในเครื่อง
  • ล้างข้อมูลก่อน แล้วค่อยเปลี่ยนหน้า
  • ชั้นที่รู้เรื่องเส้นทางน้อยที่สุด ควรตัดสินใจเรื่องเส้นทางน้อยที่สุด
  • เมื่อ token หมดอายุ ให้จุดเดียวตัดสิน และทำครั้งเดียว
