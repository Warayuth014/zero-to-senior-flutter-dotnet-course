ระดับ: กลางใช้เวลา: 30–40 นาทีลงมือทำ: ส่งข้อมูลให้หน้าใหม่โดยไม่สร้างปัญหาทีหลัง
ต้องผ่านอะไรมาก่อน: 5.1 (push/pop) และ 4.12 (ใครสร้าง คนนั้นทำลาย)
จบบทนี้แล้วจะทำได้: ตัดสินได้ว่าหน้าใหม่ควรได้รับ id หรือได้รับข้อมูลทั้งก้อน และรู้ว่าใครต้องทำลายอะไร

1. ปัญหาที่บทนี้แก้

ตอนเปิดหน้าใหม่ เราต้องส่งของให้มันเสมอ — และวิธีส่งที่เลือกจะตามหลอกไปอีกนาน

TaskDetailScreen(task: task)        // ส่งข้อมูลทั้งก้อน
TaskDetailScreen(taskId: task.id)   // ส่งแค่รหัส แล้วให้มันโหลดเอง

ทั้งสองแบบใช้ได้ แต่ให้พฤติกรรมต่างกันในสถานการณ์ที่สำคัญ และเลือกผิดจะเจอ “ข้อมูลบนสองหน้าไม่ตรงกัน” ซึ่งไล่หาสาเหตุยาก

3. Mental model: route คือใบสั่งงาน ไม่ใช่หน้าจอ

MaterialPageRoute(builder: (_) => TaskDetailScreen(task: task))
       │                    │
       │                    └─ ยังไม่ได้สร้าง widget ตอนนี้
       └─ เป็นแค่คำอธิบายว่า "ถ้าจะสร้างหน้านี้ ให้ทำแบบนี้"
ประโยคเดียวที่ต้องจำ: builder ถูกเรียกเมื่อ Navigator ต้องการวาดหน้านั้นจริง ๆ ไม่ใช่ตอนที่เราเขียนบรรทัดนั้น

ผลตามมาที่ต้องรู้ — ค่าที่อ่านไว้ ก่อน เขียน MaterialPageRoute จะถูกจับไว้ในตัวมัน ส่วนค่าที่อ่าน ใน builder จะเป็นค่า ณ ตอนที่หน้าถูกสร้าง

4. ส่งของผ่าน constructor

MaterialPageRoute<TaskOutcome>(

สังเกตว่า builder รับ context มาแต่ไม่ได้ใช้ จึงเขียนเป็น _

วิธีส่งของควรใช้ไหมเพราะ
ผ่าน constructorใช่compiler ตรวจให้ว่าครบและถูกชนิด

// เลี่ยง — ผิดแล้วรู้ตอนรัน

// ดีกว่า — ผิดแล้วรู้ตอน compile

RouteSettings ยังมีประโยชน์สำหรับตั้งชื่อ route ไว้ดูใน log หรือส่งให้ระบบเก็บสถิติ แต่ไม่ควรใช้เป็นทางหลักในการส่งข้อมูล

5. ส่ง id หรือส่งข้อมูลทั้งก้อน

นี่คือการตัดสินใจหลักของบทนี้

ส่งข้อมูลทั้งก้อนส่งแค่ id
หน้าใหม่แสดงได้ทันทีได้ต้องรอโหลดก่อน
ข้อมูลสดแค่ไหนเท่าที่เห็นตอนกดสดที่สุด ณ ตอนเปิด
ต้องมีสถานะโหลด/ผิดพลาดไหมไม่ต้องต้องมีครบ (4.7)
เหมาะกับข้อมูลที่เห็นบนรายการก็พอแล้วข้อมูลที่คนอื่นแก้ได้ หรือมีรายละเอียดมากกว่าในรายการ

ใน lab เลือกส่งทั้งก้อน เพราะหน้ารายละเอียดต้องการแค่สิ่งที่แสดงอยู่ในรายการอยู่แล้ว และการทำให้หน้าจอเปิดขึ้นมาพร้อมใช้ทันทีสำคัญกว่าบน PDA

แต่ถ้าเป็นงานที่คนอื่นแย่งทำได้ ควรส่ง id แล้วโหลดใหม่ เพราะข้อมูลบนรายการอาจเก่าไปหลายนาทีแล้ว

มีทางสายกลางที่ใช้ได้ดีในหลายกรณี — ส่งทั้งก้อนเพื่อให้แสดงได้ทันที แล้วโหลดใหม่เบื้องหลังเพื่อยืนยัน ซึ่งเป็นรูปแบบเดียวกับ 4.7 หัวข้อ 8 เรื่องโหลดครั้งแรกกับโหลดซ้ำ

6. ห้ามส่งของที่แก้ได้ให้สองหน้าถือร่วมกัน

อันตรายที่สุดคือส่งวัตถุที่แก้ค่าในตัวเองได้

// อันตราย ถ้า NavTask แก้ค่าในตัวเองได้

// → หน้ารายการเปลี่ยนตามทันที ทั้งที่ผู้ใช้ยังไม่ได้กดบันทึก
// → กดยกเลิกก็ย้อนไม่ได้แล้ว

NavTask ใน lab จึงเป็นวัตถุที่แก้ไม่ได้ ทุก field เป็น final และเปลี่ยนค่าด้วย copyWith เท่านั้น

NavTask get _draft => widget.task.copyWith(

ผลคือหน้ารายละเอียดถือ สำเนาของตัวเอง และไม่มีทางไปแตะข้อมูลของหน้ารายการได้เลย ทางเดียวที่ผลจะกลับไปคือผ่านค่าที่ pop ออกไป

เป็นหลักการเดียวกับ 4.13 หัวข้อ 5 — ถ้าวัตถุแก้ได้ สำเนาก็ไม่มีความหมาย

7. ใครสร้าง คนนั้นทำลาย

เมื่อหน้าใหม่ต้องใช้ store หรือ controller คำถามเดิมจาก 4.12 กลับมาอีกครั้ง

สร้างที่ไหนใครทำลาย
หน้าใหม่สร้างเองใน initStateหน้านั้น ใน dispose
ส่งเข้ามาทาง constructorห้ามทำลาย — คนที่สร้างเป็นคนทำลาย
// ใน TaskDetailScreen — controller ตัวนี้เป็นของหน้านี้
@override
void initState() {
  super.initState();
  _noteController = TextEditingController(text: widget.task.note);
  _noteController.addListener(_onNoteChanged);
}

@override
void dispose() {
  _noteController
    ..removeListener(_onNoteChanged)   // คู่ตรงข้าม (4.12)
    ..dispose();
  super.dispose();
}

ส่วน AppSession ที่ส่งต่อกันลงมาหลายชั้น — ไม่มีหน้าไหนทำลายมันเลย เพราะมันมีอายุยาวกว่าทุกหน้าจอ

อย่าสร้างของที่ควรใช้ร่วมกัน เช่น client ที่คุยกับ API ขึ้นมาใหม่ในทุก route — จะได้การตั้งค่าและ token คนละชุด แล้วเกิดอาการ “บางหน้าใช้ได้ บางหน้าไม่ได้”

ไม่ต้องตั้งค่าอะไรทั้งนั้น ไม่ต้องมีเซิร์ฟเวอร์ ไม่ต้องล็อกอิน — เพราะทุกอย่างที่หน้านี้ต้องใช้ถูกประกาศไว้ใน constructor แล้ว

ถ้าหน้าจอไปหยิบของจากตัวแปร global เอง จะทดสอบไม่ได้เลยจนกว่าจะจำลองสภาพแวดล้อมทั้งแอป

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แก้ในหน้ารายละเอียดแล้วหน้ารายการเปลี่ยนตามทันทีส่งวัตถุที่แก้ได้ไปใช้วัตถุที่แก้ไม่ได้ + copyWith
type 'Null' is not a subtype of type 'String' ตอนเปิดหน้าใช้ arguments แล้ว cast ผิดส่งผ่าน constructor
ข้อมูลบนหน้ารายละเอียดเก่ากว่าความจริงส่ง snapshot ทั้งที่ข้อมูลแข่งกันส่ง id แล้วโหลดใหม่
A ChangeNotifier was used after being disposedทำลายของที่รับมาทาง constructorใครสร้าง คนนั้นทำลาย
บางหน้าเรียก API ไม่ผ่านสร้าง client ใหม่ทุก routeสร้างที่เดียวแล้วส่งต่อ
ทดสอบหน้าจอไม่ได้ ต้องรันทั้งแอปหน้าจอหยิบของจาก global เองรับทุกอย่างผ่าน constructor

11. แบบฝึกหัด

หน้าจอเลือกช่องเก็บสินค้า ต้องใช้สามอย่าง

สิ่งที่ต้องใช้รายละเอียด
รหัสพาเลทที่กำลังจะเก็บมาจากหน้าก่อนหน้า
ตัวโหลดรายการช่องว่างใช้ร่วมกันทั้งแอป
คำค้นที่ผู้ใช้พิมพ์เกิดในหน้านี้เท่านั้น
  1. ตัดสินว่าแต่ละอย่างควรมาจากไหน
  2. เขียน constructor และ initState/dispose ให้ครบ
  3. ตอบว่าถ้าผู้ใช้เปิดหน้านี้ ค้างไว้ห้านาที แล้วค่อยเลือก จะมีปัญหาอะไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — แต่ละอย่างมาจากไหน

สิ่งที่ต้องใช้มาจากใครทำลาย
รหัสพาเลทconstructor — เป็น String ที่แก้ไม่ได้อยู่แล้วไม่ต้องทำลาย
ตัวโหลดรายการช่องว่างconstructor — สร้างที่เดียวระดับแอปไม่ใช่หน้านี้
คำค้นสร้างเองใน initStateหน้านี้ ใน dispose

ข้อ 2 — โค้ด

class LocationPickerScreen extends StatefulWidget {
  const LocationPickerScreen({
    super.key,
    required this.palletCode,        // ข้อมูลจากหน้าก่อน
    required this.repository,        // ของใช้ร่วม รับมา ไม่ได้สร้าง
  });

  final String palletCode;
  final LocationRepository repository;

  @override
  State<LocationPickerScreen> createState() => _LocationPickerScreenState();
}

class _LocationPickerScreenState extends State<LocationPickerScreen> {
  late final TextEditingController _searchController;   // ของหน้านี้เอง
  late final LocationStore _store;                      // ของหน้านี้เอง

  @override
  void initState() {
    super.initState();
    _searchController = TextEditingController();
    _searchController.addListener(_onSearchChanged);
    // store เป็นของหน้านี้ แต่ repository ที่มันใช้เป็นของคนอื่น
    _store = LocationStore(repository: widget.repository);
    _store.load();
  }

  @override
  void dispose() {
    _searchController
      ..removeListener(_onSearchChanged)
      ..dispose();
    _store.dispose();          // ทำลายเฉพาะที่สร้างเอง
    // ไม่แตะ widget.repository เด็ดขาด
    super.dispose();
  }
  ...
}

จุดที่ต้องระวังคือ _store — หน้านี้สร้างเอง จึงต้องทำลายเอง แต่ repository ข้างในมันเป็นของคนอื่น การ dispose store ต้องไม่ไปทำลาย repository ตามไปด้วย

ข้อ 3 — เปิดค้างไว้ห้านาที

รายการช่องว่างที่โหลดมาตอนเปิดหน้า จะเก่าไปห้านาที และในคลังจริงช่องว่างเปลี่ยนเร็วมาก

สิ่งที่จะเกิดความเสียหาย
ช่องที่เลือกเต็มไปแล้วถูกปฏิเสธตอนยืนยัน ต้องเลือกใหม่
มีช่องว่างใหม่ที่ดีกว่าแต่ไม่เห็นเดินไกลกว่าที่จำเป็น
ผู้ใช้เชื่อว่าสิ่งที่เห็นคือของจริงเสียเวลาเดินไปแล้วพบว่าใช้ไม่ได้

ทางรับมือ เรียงจากถูกสุดไปแพงสุด

วิธีต้นทุนได้อะไร
แสดงเวลาที่โหลดล่าสุด + ปุ่มรีเฟรชต่ำผู้ใช้ตัดสินเองได้ (4.7)
รีเฟรชเมื่อกลับมาที่แอปต่ำครอบกรณีวางเครื่องไว้ (4.11)
polling ทุก 30 วินาทีกลางสดตลอด แต่กินแบต (4.11)
ให้เซิร์ฟเวอร์ตรวจตอนยืนยันและตอบว่าเต็มแล้วต้องคุยกับหลังบ้านจำเป็นเสมอ ไม่ว่าจะทำข้ออื่นหรือไม่

แถวสุดท้ายสำคัญที่สุดและมักถูกลืม — ต่อให้รีเฟรชถี่แค่ไหน ก็ยังมีช่องว่างระหว่างที่ผู้ใช้เห็นกับตอนที่กดยืนยัน จึงต้องมีการตรวจที่ปลายทางเสมอ และแอปต้องรับมือกับคำตอบว่า “ช่องนี้เต็มแล้ว” ให้ดี ซึ่งเป็นเรื่องที่ออกแบบไว้ใน 4.15 แบบฝึกหัดข้อ 3 พอดี

นี่คือหลักเดียวกับ 4.14 — ฝั่งแอปทำได้แค่ลดโอกาส ความถูกต้องต้องมาจากปลายทาง

12. สรุปท้ายบท

  • MaterialPageRoute เป็นคำอธิบายวิธีสร้างหน้า ไม่ใช่ตัวหน้าเอง
  • builder ทำงานเมื่อ Navigator ต้องการวาดหน้านั้น
  • ส่งของผ่าน constructor เพื่อให้ compiler ตรวจให้
  • อย่าใช้ arguments เป็นทางหลัก เพราะ cast ผิดแล้วรู้ตอนรัน
  • ส่งทั้งก้อนเมื่อข้อมูลบนรายการพอแล้ว ส่ง id เมื่อข้อมูลแข่งกัน
  • วัตถุที่ส่งต้องแก้ไม่ได้ ไม่งั้นสองหน้าจะแก้ข้อมูลชุดเดียวกัน
  • ใครสร้าง คนนั้นทำลาย — ของที่รับมาห้ามทำลาย
  • หน้าที่รับของครบผ่าน constructor คือหน้าที่ทดสอบได้

บทถัดไป: 5.3 จะกลับมาที่ค่าที่ pop ส่งกลับ — ทำไม bool ไม่พอ และทำไมต้องแยก “ยกเลิก” ออกจาก “กดย้อนกลับเฉย ๆ”
