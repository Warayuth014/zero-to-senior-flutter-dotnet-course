ปัญหาจริง: mounted guardป้องกัน setStateหลัง dispose แต่ไม่ป้องกัน responseเก่าทับ stateใหม่; absoluteมี receive-session generationบาง flowแต่ pollingบางเส้นยัง overlapได้

1. Race taxonomy

  • lifecycle: widget/storeถูก dispose
  • identity: ผู้ใช้สแกน palletใหม่ก่อนผลเก่ากลับ
  • ordering: requestเก่าจบหลัง requestใหม่
  • duplication: tap/scanส่ง commandซ้ำ
  • uncertainty: timeoutหลัง server commit

2. mountedแก้เพียง lifecycle

wmsappตรวจ mountedหลายจุดซึ่งจำเป็น แต่ถ้าหน้ายัง mountedและ inputเปลี่ยน ผล requestเก่ายัง commitได้ ต้อง snapshot identityหรือ generationก่อน awaitแล้วตรวจอีกครั้ง

3. Generation token

final generation = ++_generation;
final key = currentPallet;
final result = await repository.lookup(key);
if (_disposed || generation != _generation || key != currentPallet) return;
commit(result);

เหมาะกับ latest-wins lookupและ receive session

4. Single-flight และ exhaust

commandที่ห้ามซ้ำใช้ in-flight key/disableและ ignoreเหตุการณ์ใหม่จนจบ ต่างจาก searchที่ควร latest-wins ส่วน pollingใช้ single-flightพร้อม pending refresh flagเพื่อไม่ให้ command-triggered reloadถูก guardกลืน

5. Cancellation

Futureทั่วไป cancelไม่ได้ การ cancel subscription/timer/http clientอาจหยุด resourceแต่ server commandอาจเดินต่อ Generationจึงยังต้องกัน commit local และ mutation endpointต้อง idempotent/reconcile

6. Response version

client generationกันลำดับภายใน process แต่หลาย operatorต้องใช้ server version/ETag/current status compare-and-set เช่น STAGED→DISPATCHED ผู้แพ้ reload current truth ไม่ retryโดยเดา

7. Test deterministic

ใช้ controllable Completersให้ request Bจบก่อน A, fake clockขยับ timerและ simulate timeout-after-commit Assertว่า latest identityชนะ, duplicate commandหนึ่งครั้งและ disposeไม่ notify

8. Strategy matrix

เลือก semanticsต่อ operation: search=latest wins, submit=exhaust+idempotency, refresh=single-flight/coalesce, stream=subscription cancel+reconcile อย่าใช้ boolean loadingเดียวแก้ทุก race
