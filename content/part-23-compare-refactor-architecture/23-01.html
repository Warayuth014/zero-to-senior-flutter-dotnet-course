กรณีศึกษา: wmsapp เก็บ flowส่วนใหญ่ใน StatefulWidget ขณะที่ wms_absolute_mobile ให้ WarehouseStoreถือ state/commands แล้ว shellส่ง storeลง views

1. สอง architecture ที่พบจริง

Screen-centricStore-centric
Widgetถือ state, API call, navigationStoreถือ domain state/commands
flowอยู่ใกล้ UI อ่านหน้าเดียวจบหลาย viewแชร์ stateและ resumeได้
widget testต้องขับหน้าจอมากstore testแยกจาก renderingได้

2. wmsapp ไม่ได้ “ผิด”

flowอย่าง Packingอยู่ใน screenทำให้ event→API→setStateมองเห็นใกล้กัน เหมาะกับ featureเล็กและทีมที่ส่งงานเร็ว ปัญหาเริ่มเมื่อไฟล์โตเกิน 2,000 บรรทัด มีหลาย scanner/controller/dialogและ business transitionถูกผูกกับ widget lifecycle

3. absolute ไม่ได้ “ดีกว่าทุกอย่าง”

WarehouseStoreทำให้ task/receiving/pickingแชร์ stateและ fake repositoryได้ แต่รวมหลาย bounded contextsกว่า 1,600 บรรทัด, busy flagsข้าม featureและ timerกลาง จึงย้ายความซับซ้อนจาก giant screenไป God Storeบางส่วน

4. เลือกจาก lifetime

stateที่อยู่แค่ text field, expansionหรือ dialogควรอยู่ widget ส่วน stateที่ต้องข้ามหน้า, survive navigation, reconcileกับ pollingหรือเป็น business invariantควรอยู่ feature controller/store ไม่ใช่ย้ายทุก booleanขึ้น global

5. Trace ownership

User scan
→ local input/focus: Widget
→ validate/transition: Feature controller
→ HTTP/domain mapping: Repository
→ server truth: .NET/WMS
→ render snapshot: Widget

6. Decision signals

ย้ายออกจาก screenเมื่อ logicถูกใช้หลาย widget, ต้องทดสอบโดยไม่ render, มี async race, ต้อง resumeข้าม routeหรือแก้ UIแล้วเสี่ยง business flow อย่าสร้าง storeเพียงเพราะไฟล์ยาวถ้าส่วนยาวเป็น pure presentationที่ extract widgetได้

7. Target ที่เหมาะกับสองโปรเจกต์

wmsappควรเริ่ม feature controllerเฉพาะ Packing/Receiving/Picking ส่วน absoluteควรแยก WarehouseStoreเป็น receiving/task/picking/cycle-count stores และมี shell coordinatorบางๆ โดยยังเก็บ transient view stateใน widget

8. Exercise

เลือกหนึ่ง flowแล้วทำ state inventory: ชื่อ state, ownerปัจจุบัน, lifetime, source of truth, consumersและเหตุผลว่าจะคง/ย้าย ระบุ testที่ต้องผ่านก่อนย้าย ห้ามสรุปจากจำนวนบรรทัดอย่างเดียว
