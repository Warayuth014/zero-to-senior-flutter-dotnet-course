ADR: บันทึกว่าเลือกอะไรเพราะ constraintใด ไม่ใช่เอกสารสวยหลังตัดสินใจแล้ว Partนี้จบด้วย ADRที่ทำให้ทีมอนาคตไม่ย้อน debateโดยไร้บริบท

1. เมื่อใดควรเขียน

เขียนเมื่อ decisionมีผลข้าม feature/ทีม, revertแพงหรือมี trade-offจริง เช่น Result vs exception, repository boundary, store split, token persistenceและ polling strategy ไม่ต้องเขียน ADRสำหรับ rename widgetเล็กๆ

2. โครงขั้นต่ำ

Title / Status / Date
Context & constraints
Decision
Alternatives considered
Consequences (+/-)
Migration / rollback
Validation metrics
Links

3. Context ต้องเฉพาะระบบ

ระบุว่า wmsappมี giant screens/testน้อย, absoluteมี repository seamsแต่ God Store, PDAอาจ offline, .NET contract deployแยกและ mutationsเสี่ยงซ้ำ ไม่เขียนเพียง “clean architecture scales better”

4. ตัวอย่าง decision

“Adopt feature stores incrementally behind WarehouseStore façade; keep local UI state in widgets; repositories remain domain boundaries” พร้อมเหตุผลเรื่อง shared snapshot, fake testsและ deployทีละ feature

5. Consequences ซื่อสัตย์

ข้อดี: dependencies/test/lifetimeชัด ข้อเสีย: wiring/adapters/filesเพิ่ม, transition periodมีสอง APIและทีมต้องเรียนรู้ ระบุ operational cost ไม่ขาย decisionเหมือนไม่มี downside

6. Status lifecycle

ใช้ Proposed→Accepted→Superseded/Deprecated ไม่แก้ ADRเก่าให้เหมือนประวัติไม่เคยเกิด สร้าง ADRใหม่ supersedeและ linkกลับเพื่อรักษาเหตุผลตามเวลา

7. Validation

ผูก decisionกับ metrics/tests เช่น duplicate mutations, stale-response incidents, store test duration, direct ApiService call sitesและ crash-free sessions พร้อมวันที่ทบทวน มิฉะนั้น ADRเป็น opinion archive

8. Capstone Part 23

เขียน ADRหนึ่งฉบับเลือก migrationของ flowจริง ระบุ alternativeอย่างน้อยสองแบบ, security/race/test impact, rolloutและrollback ผู้เรียนต้องอธิบายได้ว่าทำไม architectureใหม่เหมาะ constraintนี้—not เพราะเป็น patternยอดนิยม
