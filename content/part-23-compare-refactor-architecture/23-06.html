ข้อเท็จจริง: ทั้งสองแอปมี typed modelsจำนวนมาก แต่ transport/adaptersยังเริ่มจาก Map<String,dynamic>; ประเด็นคือหยุด dynamicที่ boundary ไม่ใช่ห้าม JSON dynamicทั้งหมด

1. Dynamicจำเป็นตรง wire

jsonDecodeให้ dynamicและ backendบาง endpoint casing/shapeไม่สม่ำเสมอ Adapterต้องตรวจ runtimeก่อนแปลง แต่ Mapไม่ควรไหลถึง widgetหรือ storeเพราะ typo/castจะพังช้าใน production

2. Typed model value

wmsapp receiving/picking/packing modelsและ absolute inbound/task/inventory modelsให้ compilerช่วยเรื่อง field/nullabilityและรวม fromJson logic สิ่งนี้ลด knowledgeของ JSON keysที่กระจายตาม screens

3. Typed ไม่แปลว่าปลอดภัยอัตโนมัติ

json['token'] as String, direct int castsและ list castsยัง throwเมื่อ contractเปลี่ยน ต้องตัดสิน field required/optional, coercionที่ยอมรับ, unknown enumและ error messageที่บอก pathได้

4. แยก DTO กับ domainเมื่อจำเป็น

API DTOอาจมี nullable/casing/legacy statuses ส่วน domain modelต้องรักษา invariant ใช้ mapperแปลง TaskDto → WmsTaskเมื่อ wire shapeไม่ตรงภาษาธุรกิจ ไม่ต้อง duplicate modelถ้ารูปร่างตรงและเสถียร

5. Unknown values

server deployก่อน clientได้ Enum parserต้องมี unknown/raw valueและ UI fail-soft ไม่ map statusใหม่เป็น executing/availableโดยปริยายหากอาจเปิด actionผิด ความปลอดภัยของ warehouseสำคัญกว่า cardสวย

6. Contract test

fixtureจริง/anonymous → DTO parser
missing required → typed ParseFailure
optional absent → documented default
unknown enum → Unknown(raw)
serialize command → exact .NET property names

7. Code generation trade-off

freezed/json_serializableลด boilerplateและเพิ่ม equality/copyWith แต่มี generated files/build_runner cost Manual parserเหมาะ modelน้อยหรือ contractแปลก ไม่ควร migrateทั้ง repoเพียงเพื่อ style consistencyโดยไม่มี test benefit

8. Boundary rule

อนุญาต dynamicภายใน decode adapterช่วงสั้นๆ แล้วคืน typed success/failureออกมา Searchหา Map<String,dynamic>ใน widgets/storesเพื่อจัดลำดับ refactorจาก mutation-critical flowsก่อน
