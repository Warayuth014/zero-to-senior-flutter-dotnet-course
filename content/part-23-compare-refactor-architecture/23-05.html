โค้ดจริง: wmsappใช้ singleton ApiService/SignalRService; absoluteใช้ singletonเฉพาะ app-wide language/connection แต่สร้าง ApiClient/Auth/Storeและ repositoriesผ่าน composition

1. Singletonเหมาะเมื่อใด

process-wide policyที่มีหนึ่ง identityจริง เช่น active languageหรือ connection profileอาจใช้ singletonง่ายและทุก listenerเห็นค่าเดียว แต่ยังต้องมี reset/test hooksและชัดว่า lifetimeเท่ากับ app

2. Hidden dependency

final _api = ApiService()ใน screenดูสะดวกแต่ constructorไม่บอกว่า screenต้องใช้ network Testsแทน implementationไม่ได้และ global cached base/headerอาจรั่วข้าม testหรือ session

3. Constructor injection

WarehouseShellประกอบ Api implementationsจาก authenticated clientแล้วส่งเข้า WarehouseStore Dependenciesเห็นใน signature, fakeได้และ lifetimeผูก login shell ข้อเสียคือ wiringมากขึ้นแต่เป็น complexityที่มองเห็น

4. Composition root

main/app shell:
client → auth → repositories → feature stores → widgets

สร้าง graphที่จุดเดียว ไม่ให้ leaf widget new serviceเอง และอย่าใช้ service locatorซ่อน globalไว้ใต้ชื่อ DI

5. Scope สำคัญกว่าคำว่า singleton

ApiClientใน absoluteอยู่ตลอด authenticated sessionเพื่อถือ bearer token แต่ไม่จำเป็นต้อง globalทั้ง process WarehouseStoreอยู่เท่า shellและ dispose timerตอน logout นี่คือ scoped singletonที่ควบคุม lifecycleได้

6. SignalR lifecycle

หนึ่ง connectionร่วมอาจคุ้ม แต่ subscribersต้อง unsubscribeและ resetเมื่อ session/serverเปลี่ยน Singletonที่ถือ callbacksเก่าทำให้ duplicate eventหรือ user dataรั่ว จึงต้องมี explicit connect/disconnect ownership

7. Migration seam

เพิ่ม optional constructor parameterที่ defaultเป็น ApiServiceเดิมก่อน แล้ว composition rootส่ง adapterใน productionและ fakeใน tests จากนั้นค่อยถอด default/globalหลัง call sitesย้ายครบ

8. Decision checklist

ระบุ identity, owner, creation, disposal, session reset, test isolationและ concurrency ถ้าตอบไม่ได้อย่าใช้ global singleton; ถ้าข้อมูล app-wideจริงก็ไม่ต้องสร้าง providerซับซ้อนเพียงเพื่อหลีกคำว่า singleton
