ไฟล์หลัก: startSelectedConveyorPick, startPick และ mobile_start_pick — handoff จาก arrived conveyor ไป active picking

1. Preconditions

ต้องมี destination, C1/C2ที่ arrived, waiting pickที่ palletตรงกันและ valid server task ID ก่อนเปิด scan dialog เงื่อนไขเหล่านี้กันการเริ่มจาก card staleหรือข้อมูลไม่ครบ

2. Scan เป็น proof of presence

ผู้ปฏิบัติงานสแกน palletจริงที่ lane ไม่ใช่แค่กด card การเทียบ exactหลัง normalizeยืนยันว่ากำลังหยิบ palletที่ backendคาดไว้

3. ปิด dialog ก่อน refresh

implementationรอให้ scan dialog disposeเสร็จก่อนเรียก API/refresh เพื่อหลีกเลี่ยง Flutter Web inherited-widget lifecycle assertion หลักคืออย่า update ancestor stateขณะที่ route/dialog descendantกำลัง teardown

4. Start command

POST mobile_start_pick(taskId)
→ backend WAITING → active
→ reload picks
→ reload destination queues
→ lane becomes Available

serverเป็นผู้เปลี่ยนสถานะ; clientไม่ปลอม activeจาก local flag

5. แยก start กับ find

หลัง start storeยังไม่ตั้ง selectedActivePick การบังคับ Find Picking Taskด้วยการสแกนอีกครั้งทำหน้าที่ handoff/ยืนยัน palletที่ย้ายจาก conveyorเข้าสู่พื้นที่หยิบจริง

6. Concurrent operator

สองเครื่องอาจเห็น arrivedเดียวกันและกด startพร้อมกัน Backendต้อง compare current status atomically เครื่องที่แพ้ควร reloadแล้วเห็น active/available ไม่แสดง generic errorที่ชวน retryซ้ำ

7. Start success แต่ refresh fail

commandอาจสำเร็จแต่ reloadล้มเหลว UIต้องไม่เสนอ Startซ้ำโดยไร้คำเตือน ทางเลือกคือ invalidate snapshot, แสดง “started—refresh pending” และให้ manual refreshที่ reconcileจาก server

8. Start-flow tests

ครอบคลุม wrong pallet, missing task ID, double operator conflict, start timeout-after-commit, queue/pick refresh partial failure และ lifecycleตอนปิด dialog โดย assertว่า commandถูกเรียกสูงสุดหนึ่งครั้งต่อ interaction
