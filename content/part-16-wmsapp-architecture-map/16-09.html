รายละเอียดทำไมสำคัญบท
onPressed: loading ? null : onPressedป้องกันการกดซ้ำโดยไม่ต้องเขียนที่ผู้เรียก4.9
AnimatedSwitcher + ValueKeyไม่มี key แล้ว Flutter จะคิดว่าเป็น widget เดิม ไม่เกิดแอนิเมชัน1.12
Flexible + ellipsis รอบ Textข้อความยาวไม่ทำให้ล้น2.9

แถวแรกคือประโยชน์ที่ใหญ่ที่สุด — 4.9 สอนว่าปุ่มที่ยิงคำขอต้องปิดตัวเองระหว่างรอ ถ้าให้แต่ละจอเขียนเอง จะมีจอที่ลืม แต่พอฝังไว้ในปุ่มกลาง ทุกจอที่ใช้ปุ่มนี้ได้ไปฟรี

สังเกตความต่าง: DangerButton ก็มี loading แต่ไม่มี AnimatedSwitcher และ WarningButton ไม่มี loading เลย — ปุ่มที่ต้องระวังจึงกดซ้ำได้ระหว่างที่กำลังทำงาน
ถ้าจะแก้ที่เดียวให้ครบ ควรทำ WarningButton ให้มี loading เหมือนอีกสองตัว

3. StatusBadge — ตารางแปลงสถานะเป็นสี

Color get _color => switch (status.toUpperCase()) {
  'FG' => AppTheme.success,
  'PW' => AppTheme.warning,
  'DAMAGED' => AppTheme.danger,
  'RECEIVED' => AppTheme.primary,
  'PARTIAL' => AppTheme.warning,
  'PENDING' => const Color(0xFF78909C),
  'CONFIRMED' => AppTheme.success,
  ...
  'OPERATOR' => AppTheme.primary,
  'SUPERVISOR' => AppTheme.purple,
  _ => const Color(0xFF78909C),
};

17 สถานะจากทุกโดเมนรวมอยู่ในตารางเดียว ผู้เรียกส่งสถานะเข้ามาแล้วได้ป้ายสีที่ถูกต้อง

StatusBadge(_role ?? '')          // ใน HomeScreen
StatusBadge(item.status)          // ในจอรายการ
ข้อดีข้อควรระวัง
สีของสถานะเดียวกันตรงกันทุกจอสถานะจากคนละโดเมนปนกัน — 'PENDING' ของ receiving กับของ picking ได้สีเดียวกันเสมอ
toUpperCase() กันเรื่องตัวพิมพ์สถานะใหม่ที่ยังไม่ได้เพิ่มจะได้สีเทาเงียบ ๆ
_ => กันพังไม่มีอะไรเตือนว่าลืมเพิ่ม

ข้อควรระวังข้อสุดท้ายเจอได้จริง — ฝั่ง .NET เพิ่มสถานะ 'HOLD' แล้วป้ายขึ้นสีเทาเหมือนสถานะที่ไม่รู้จัก ผู้ใช้ตีความว่าไม่สำคัญ ทั้งที่เป็นสถานะที่ต้องรีบจัดการ

ทำให้เห็นได้ด้วยการแยกสีของ “ไม่รู้จัก” ออกจากสีของสถานะจริง

_ => AppTheme.purple,     // สีที่ไม่มีสถานะไหนใช้ → เห็นทันทีว่ามีอะไรใหม่

หรือถ้าอยากให้จับได้ตั้งแต่ตอนพัฒนา

_ => () {
  assert(false, 'StatusBadge: ไม่รู้จักสถานะ "$status"');
  return const Color(0xFF78909C);
}(),

assert ถูกตัดออกใน release ตามที่ 15.1 อธิบาย — แอปที่ผู้ใช้ใช้จะไม่พัง แต่คนพัฒนาจะเจอทันทีที่รัน

สั่นเบาผ่าน สแกนชิ้นถัดไปได้
สั่นแรงต้องหยุดมอง

สิ่งที่ยังขาดคือแถบสำหรับความล้มเหลว — ตอนนี้มีแค่สำเร็จกับเตือน ส่วนความผิดพลาดจริงต้องใช้ showErrorDialog ที่ขวางทั้งจอและต้องกดปิด

ระดับวิธีแสดงผู้ใช้ต้องกด

6. LoadingOverlay — ม่านที่ต้องระวัง

return Stack(
  children: [
    child,
    if (loading)
      Container(
        color: Colors.black.withValues(alpha: 0.35),
        child: Center(child: ...),
      ),
  ],
);

ทำงานถูกต้อง — ม่านทับทั้งจอ กดอะไรข้างหลังไม่ได้ และมีข้อความบอกได้ว่ากำลังทำอะไร

สิ่งที่ต้องระวังคือผู้ใช้ยกเลิกไม่ได้ ถ้าคำขอค้าง 10 วินาทีตาม timeout ของ _get ผู้ใช้จะมองม่านดำอยู่ 10 วินาทีโดยทำอะไรไม่ได้เลย

บน PDA ที่ทำงานเป็นจังหวะเร็ว 10 วินาทีคือนานมาก — 15.11 จัดว่าเป็นอาการ “กดแล้วค้าง” ในสายตาผู้ใช้

ถ้าจะให้ดีขึ้นโดยไม่แก้เยอะ ให้ม่านแสดงเวลาที่ผ่านไปหลังจากผ่านไปสักพัก

// หลัง 3 วินาที เปลี่ยนข้อความให้ผู้ใช้รู้ว่ายังไม่ค้าง
if (elapsed > const Duration(seconds: 3))
  Text('กำลังรอเซิร์ฟเวอร์... ${elapsed.inSeconds} วินาที')

ผู้ใช้ที่เห็นตัวเลขเดินจะรอต่อ ผู้ใช้ที่เห็นวงกลมหมุนนิ่ง ๆ จะปิดแอป

7. ผลกระทบเมื่อแก้ไฟล์นี้

แก้อะไรกระทบต้องตรวจอะไร
ความสูงของ PrimaryButtonทุกจอที่มีปุ่มหลักจอที่มีปุ่มหลายปุ่มเรียงกันจะล้นไหม
สีใน StatusBadgeทุกจอที่แสดงสถานะสถานะที่เคยต่างสีกันยังต่างอยู่ไหม
ความกว้าง 110 ของ InfoRowทุกจอที่แสดงรายละเอียดป้ายกำกับที่ยาวจะตัดไหม
เพิ่ม field ที่ requiredคอมไพล์ไม่ผ่านทุกที่ที่เรียกให้มีค่าเริ่มต้นแทน
showConfirmDialogทุกที่ที่ถามยืนยันค่าที่คืนตอนกดนอกกล่องยังเป็น false ไหม

แถวสุดท้ายมีรายละเอียดที่ทำถูกไว้แล้ว

final result = await showDialog<bool>(...);
return result ?? false;

ผู้ใช้กดนอกกล่องหรือกดปุ่มย้อนกลับ → showDialog คืน null → แปลงเป็น false แปลว่า “ไม่ยืนยัน”

ถ้าเขียนเป็น result ?? true การกดพลาดออกนอกกล่องจะกลายเป็นการยืนยัน ซึ่งเป็นบั๊กที่อันตรายมากเพราะกล่องนี้ถูกใช้ยืนยันการลบด้วย

9. แบบฝึกหัด

ทีมอยากให้ทุกจอมีปุ่ม “ลองใหม่” เมื่อโหลดข้อมูลไม่สำเร็จ ตอนนี้แต่ละจอเขียนเอง หน้าตาไม่เหมือนกัน บางจอไม่มีเลย

  1. ควรเพิ่มอะไรในไฟล์นี้
  2. เขียนโค้ดให้ครบ
  3. ต้องระวังอะไรบ้างเมื่อเอาไปใช้จริง
แนวคำตอบ

ข้อ 1

EmptyState มี onRetry อยู่แล้ว แต่ชื่อและไอคอนเป็นของ “ไม่มีข้อมูล” ซึ่งคนละความหมายกับ “โหลดไม่สำเร็จ”

สถานการณ์ผู้ใช้ต้องเข้าใจว่า
ไม่มีข้อมูลถามสำเร็จ คำตอบคือไม่มี — ไปทำอย่างอื่น
โหลดไม่สำเร็จยังไม่รู้ว่ามีหรือไม่มี — ลองใหม่

ต้องเป็นคนละ widget ไม่ใช่ตัวเดียวกัน — เป็นเรื่องเดียวกับที่ 16.7 ข้อ 3 สรุปไว้ว่ารายการว่างกับความล้มเหลวต้องแยกกัน

ข้อ 2

// =============================================
// ErrorState — โหลดไม่สำเร็จ (คนละเรื่องกับ EmptyState)
// =============================================
class ErrorState extends StatelessWidget {
  final String message;
  final VoidCallback? onRetry;
  final bool retrying;

  const ErrorState({
    super.key,
    required this.message,
    this.onRetry,
    this.retrying = false,
  });

  @override
  Widget build(BuildContext context) {
    return Center(
      child: Padding(
        padding: const EdgeInsets.all(32),
        child: Column(
          mainAxisSize: MainAxisSize.min,
          children: [
            Container(
              padding: const EdgeInsets.all(20),
              decoration: BoxDecoration(
                color: AppTheme.danger.withValues(alpha: 0.08),
                shape: BoxShape.circle,
              ),
              child: const Icon(Icons.cloud_off_rounded,
                  color: AppTheme.danger, size: 40),
            ),
            const SizedBox(height: 16),
            Text(
              message,
              textAlign: TextAlign.center,
              style: TextStyle(
                fontSize: 14,
                height: 1.5,               // ภาษาไทยมีสระบนล่าง ต้องเผื่อ
                color: AppTheme.textGrey(context),
              ),
            ),
            if (onRetry != null) ...[
              const SizedBox(height: 20),
              SizedBox(
                width: 200,
                child: PrimaryButton(
                  label: 'ลองใหม่',
                  icon: Icons.refresh_rounded,
                  loading: retrying,       // กดซ้ำระหว่างลองใหม่ไม่ได้
                  onPressed: onRetry,
                ),
              ),
            ],
          ],
        ),
      ),
    );
  }
}

ใช้ PrimaryButton ที่มีอยู่แล้วแทนที่จะสร้างปุ่มใหม่ — ได้พฤติกรรมกันกดซ้ำมาฟรี และถ้าวันหนึ่งเปลี่ยนหน้าตาปุ่มหลัก ปุ่มนี้เปลี่ยนตาม

SizedBox(width: 200) จำเป็นเพราะ PrimaryButton ตั้ง minimumSize: Size(double.infinity, ...) ไว้ ถ้าไม่ครอบ ปุ่มจะกว้างเต็มจอซึ่งดูแปลกกลางหน้าว่าง

ข้อ 3 — ต้องระวังอะไร

เรื่องทำไม
ข้อความต้องมาจาก ApiResult.error ไม่ใช่เขียนตายตัว“ไม่มีสัญญาณ” กับ “เซิร์ฟเวอร์ไม่ตอบ” ต้องบอกคนละอย่าง (7.9)
ห้ามใช้กับความล้มเหลวของคำสั่งที่เปลี่ยนข้อมูล“ลองใหม่” กับคำสั่งที่อาจไปถึงแล้ว = ข้อมูลซ้ำ (7.10)
ต้องไม่ล้างข้อมูลเดิมที่เคยโหลดสำเร็จข้อมูลเก่าที่มีเวลากำกับ ดีกว่าหน้าว่าง (10.12)
ปุ่มต้องปิดตัวเองระหว่างลองใหม่ไม่งั้นผู้ใช้รัวปุ่มตอนรอ

แถวที่สองสำคัญที่สุด — widget นี้เหมาะกับการโหลดข้อมูลเท่านั้น ถ้าเอาไปใช้กับหน้าจอที่ยืนยันการรับสินค้าไม่สำเร็จ จะกลายเป็นการชวนผู้ใช้สร้างรายการซ้ำ

ทางที่ถูกสำหรับคำสั่งที่เปลี่ยนข้อมูลคือแสดงข้อความที่บอกว่าให้ตรวจก่อนส่งซ้ำ ตามที่ 15.11 สรุปไว้

  • DangerButton มี loading แต่ WarningButton ไม่มี
  • StatusBadge รวม 17 สถานะจากทุกโดเมนไว้ตารางเดียว ที่ไม่รู้จักได้สีเทาเงียบ ๆ
  • ScanTextField รับทั้งเครื่องสแกนและการพิมพ์เอง แต่ไม่ล้างช่อง/คืนโฟกัสให้
  • แถบข้อความสั่นต่างกันสองระดับ เพราะผู้ใช้ไม่ได้มองหน้าจอตลอด
  • LoadingOverlay ยกเลิกไม่ได้ ผู้ใช้อาจต้องรอถึง 10 วินาที
  • showConfirmDialog คืน false เมื่อกดนอกกล่อง ซึ่งเป็นค่าที่ถูกต้อง
