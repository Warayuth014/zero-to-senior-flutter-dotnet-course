3. AuthSessionService — 27 บรรทัดทั้งไฟล์

class AuthSession {
  final String? userId;
  final String? fullName;
  final String? role;

  const AuthSession({
    required this.userId,
    required this.fullName,
    required this.role,
  });

  bool get isLoggedIn => userId != null;
}

class AuthSessionService {
  const AuthSessionService();

  Future<AuthSession> loadSession() async {
    final prefs = await SharedPreferences.getInstance();
    return AuthSession(
      userId: prefs.getString('userId'),
      fullName: prefs.getString('fullName'),
      role: prefs.getString('role'),
    );
  }

  Future<void> clearSession() async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.clear();
  }
}

มีเรื่องที่ทำถูกและเรื่องที่เป็นบั๊ก

ทำถูกทำไม
เป็น const constructorไม่มี state ในตัวเอง สร้างกี่ครั้งก็เหมือนเดิม
คืน AuthSession แทนสาม Stringค่าที่มาด้วยกันเดินทางไปด้วยกัน
มี isLoggedInตั้งชื่อความหมายให้เงื่อนไข

แก้ได้ด้วยการลบเฉพาะที่เป็นของตัวเอง

Future<void> clearSession() async {
  final prefs = await SharedPreferences.getInstance();
  await prefs.remove('userId');
  await prefs.remove('fullName');
  await prefs.remove('role');
}
บทเรียนที่ใหญ่กว่าบั๊กนี้: SharedPreferences เป็นพื้นที่ที่ทุกคนใช้ร่วมกัน แต่ไม่มีอะไรบอกว่าคีย์ไหนเป็นของใคร prefs.clear() จึงเป็นคำสั่งที่แตะของคนอื่นเสมอ
อย่าใช้ clear() ในโค้ดของฟีเจอร์ใดฟีเจอร์หนึ่ง — ลบเฉพาะคีย์ที่ตัวเองเขียน

6. ถ้าจะต่อของจริงต้องทำอะไร

ลำดับงานไฟล์
1เพิ่ม login() ที่ยิง POST /Authenticate/loginไฟล์ใหม่ services/api/auth_api.dart
2เก็บ token ลง SharedPreferencesauth_session_service.dart
3ให้ _headers อ่าน token ทุกครั้งที่ยิงapi_service.dart
4รับมือ 401 → ล้างเซสชัน → พากลับไปล็อกอินapi_service.dart + จุดกลาง
5เปลี่ยนจอล็อกอินจากรายการผู้ใช้เป็นช่องกรอกชื่อผู้ใช้login_screen.dart
6เลิกส่ง operatorId ใน body ให้เซิร์ฟเวอร์อ่านจาก token แทนทุกไฟล์ใน services/api/ + ฝั่ง .NET

ข้อ 3 มีอุปสรรคเฉพาะของโปรเจกต์นี้

final _headers = {'Content-Type': 'application/json'};

_headers เป็น final ที่สร้างครั้งเดียวตอนสร้าง ApiService ซึ่งเป็น singleton — ถ้าใส่ token ลงไปตอนล็อกอิน แล้วผู้ใช้ออกจากระบบและล็อกอินใหม่เป็นคนอื่น token เก่าจะค้างอยู่ ต้องเปลี่ยนเป็นสร้างใหม่ทุกคำขอตามที่ 8.4 สอน

Map<String, String> _buildHeaders() => {
  'Content-Type': 'application/json',
  if (_token != null) 'Authorization': 'Bearer $_token',
};

ข้อ 4 ยากที่สุด เพราะตอนนี้ไม่มีที่กลางที่รู้เรื่องการนำทาง — ApiService ไม่มี context และไม่มีตัวจัดการ state กลางที่จอทุกจอฟังอยู่ ทางที่ทำได้คือให้ ApiResult พก statusCode ไปถึงจอ แล้วให้จอตัดสินใจ — ซึ่งแปลว่าต้องเขียนซ้ำทุกจอ และ 16.7 จะแสดงว่าตอนนี้ statusCode หายระหว่างทางด้วยซ้ำ

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
ล็อกอินสำเร็จแปลว่าเซิร์ฟเวอร์ยอมรับแล้วไม่มีการติดต่อเซิร์ฟเวอร์เลย
ล็อกอินได้แปลว่าเชื่อมต่อเซิร์ฟเวอร์ได้คนละเรื่องกันสิ้นเชิง
prefs.clear() ลบแค่ของเซสชันลบทุกคีย์ รวมที่อยู่เซิร์ฟเวอร์
role ควบคุมสิทธิ์อยู่ถูกแสดงอย่างเดียว
เพิ่ม token แล้วจบต้องแก้ทั้งหกข้อในตารางข้างบน

แถวที่สองอธิบายอาการที่สับสนที่สุดในคลัง — ผู้ใช้ล็อกอินผ่านสวย ๆ แล้วกดเมนูปุ๊บขึ้น “ไม่สามารถเชื่อมต่อ server ได้” เพราะการล็อกอินไม่เคยแตะเครือข่าย

8. แบบฝึกหัด

ผู้ใช้แจ้งว่า “เมื่อวานใช้ได้ วันนี้ล็อกอินได้แต่กดรับสินค้าแล้วขึ้นว่าต่อเซิร์ฟเวอร์ไม่ได้” เครื่องอื่นในคลังใช้ได้ปกติ

  1. เรียงสมมติฐานตามความน่าจะเป็น
  2. คำถามแรกที่ควรถามผู้ใช้คืออะไร
  3. ถ้ายืนยันว่าเป็นสาเหตุจากบทนี้ จะแก้ระยะสั้นและระยะยาวอย่างไร
แนวคำตอบ

ข้อ 1

ลำดับสมมติฐานทำไมอยู่ตรงนี้
1มีคนกดออกจากระบบบนเครื่องนี้ → apiHost ถูกลบอธิบายได้ครบว่าทำไมเครื่องเดียวและทำไมล็อกอินยังผ่าน
2เครื่องนี้ต่อ Wi-Fi คนละวงเป็นไปได้ แต่ปกติจะกระทบทั้งจุดนั้น
3มีคนเข้าไปแก้ IP ในหน้า Settingsเป็นไปได้ แต่ต้องตั้งใจทำ
4เซิร์ฟเวอร์มีปัญหาตัดทิ้งได้ เพราะเครื่องอื่นใช้ได้

สมมติฐานที่ 1 ชนะเพราะอธิบายทุกข้อสังเกตพร้อมกัน — ล็อกอินผ่าน (ไม่ต้องใช้เครือข่าย) แต่ยิง API ไม่ได้ (ไม่มีที่อยู่) และเกิดเครื่องเดียว (คนอื่นไม่ได้กดออกจากระบบ)

ข้อ 2 — คำถามแรก

“เมื่อวานหรือเช้านี้มีใครกดออกจากระบบบนเครื่องนี้ไหม”

ถ้าตอบว่าใช่ ยืนยันได้ทันทีโดยไม่ต้องต่อเครื่องมือใด ๆ

คำถามที่ไม่ควรถามก่อนคือ “ต่อ Wi-Fi อยู่ไหม” — เพราะผู้ใช้เห็นสัญญาณเต็มก็จะตอบว่าต่ออยู่ ซึ่งจริงและไม่ช่วยอะไร

วิธียืนยันแบบไม่ต้องถาม: ให้ผู้ใช้เปิดหน้า Settings แล้วดูว่าช่อง IP ว่างหรือไม่

ข้อ 3 — แก้อย่างไร

ระยะทำอะไร
ทันทีให้ผู้ใช้ตั้ง IP ใหม่ในหน้า Settings
สั้นแก้ clearSession() ให้ลบเฉพาะสามคีย์ของตัวเอง
กลางย้ายชื่อคีย์ทั้งหมดไปเป็นค่าคงที่ในที่เดียว
ยาวเพิ่มการตรวจในหน้าหลัก ว่าถ้ายังไม่ตั้งที่อยู่เซิร์ฟเวอร์ ให้บอกก่อนที่ผู้ใช้จะกดเมนู

ข้อสุดท้ายสำคัญที่สุด เพราะแก้ที่อาการที่ผู้ใช้เจอ ไม่ใช่แค่ที่สาเหตุอันเดียว — ยังมีทางอื่นที่ทำให้ที่อยู่เซิร์ฟเวอร์หายหรือผิด เช่นย้ายคลังแล้วเปลี่ยนวงเครือข่าย

// ใน HomeScreen — ตรวจก่อนที่ผู้ใช้จะเจอ error ตอนกดเมนู
final base = await const ApiConfigService().getCustomBase();
if (base == null && mounted) {
  showWarningSnackbar(context, 'ยังไม่ได้ตั้งค่าเซิร์ฟเวอร์ — กดไอคอนตั้งค่ามุมขวาบน');
}

ข้อความนี้ต่างจาก “ไม่สามารถเชื่อมต่อ server ได้” ตรงที่บอกว่าต้องทำอะไรต่อ ซึ่งเป็นหลักเดียวกับที่ 10.7 และ 15.11 ย้ำมาตลอด

9. สรุป

  • การล็อกอินของ wmsapp เป็นของจำลอง — ผู้ใช้สามคนฝังในโค้ด รหัส 1234 ไม่แตะเครือข่าย
  • มีคอมเมนต์และข้อความบนจอบอกไว้ชัด ซึ่งเป็นวิธีทำ mock ที่ถูกต้อง
  • ล็อกอินสำเร็จ ≠ ต่อเซิร์ฟเวอร์ได้
  • operatorId ถูกส่งไปกับ body และเซิร์ฟเวอร์เชื่อโดยไม่ตรวจ
  • clearSession() เรียก prefs.clear() ซึ่งลบที่อยู่เซิร์ฟเวอร์ไปด้วย — บั๊กจริงที่ทำให้เครื่องใช้งานไม่ได้หลังออกจากระบบ
  • อย่าใช้ prefs.clear() ในโค้ดของฟีเจอร์เดียว ลบเฉพาะคีย์ของตัวเอง
  • การต่อการยืนยันตัวตนจริงมีหกงาน ไม่ใช่แค่เพิ่ม token

บทหน้า: หน้า Settings และ ApiConfigService — ส่วนที่ทำได้ดีที่สุดในโปรเจกต์นี้
