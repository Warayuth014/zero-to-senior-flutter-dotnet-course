Order detail เชื่อม demand กับ source pallets: ต้องแยกยอดระดับ order, ยอดที่ allocate บนแต่ละ pallet และยอดที่หยิบแล้ว ไม่เช่นนั้น progress จะดูถูกแต่ inventory ผิด

1. Model topology

PickOrderDetailFull
├─ pallets[] → pallet parts[]
└─ parts[]   → required/reserved/remaining

สองมุมมองตอบคนละคำถาม: ของอยู่ที่ pallet ใด และ order ยังต้องการ part เท่าไร

2. List item model

PickOrderListItem เป็น summary สำหรับหน้าแรก ส่วน PickOrderDetailFull มีข้อมูลเต็ม อย่าใช้ summary ต่อในหน้าทำงานเพราะอาจ stale และไม่มี line detail

3. Pallet status

PickOrderPalletInfo มี palletStatus, stationId/name, partCount, totalQty และ parts โดย part status เป็น PENDING/PARTIAL/PICKED UI ใช้แสดงตำแหน่งและ progress ก่อน scan

4. Order part totals

PickOrderPartInfo แยก requiredQty, reservedQty และ remainingQty คำว่า reserved ไม่เท่ากับ picked; UI และ backend ต้องนิยามว่าการยกเลิก/คืน pallet ปลด reservation เมื่อใด

5. Scan membership guard

detail screen ตรวจ local ว่า palletId อยู่ใน detail.pallets ก่อนเรียก assign ลด request ผิด แต่ server ต้องตรวจ order membership/version ซ้ำเพราะ snapshot อาจเปลี่ยน

6. Assign response

AssignPickStationResponse คืน station, source pallet, pick order, palletItems และ pickOrderItems เป็น working snapshot สำหรับ PickItemsScreen จึงเป็น boundary เริ่ม picking session ใน client

7. Parser risks

วันที่ผิด fallback เป็น now และหลาย required field cast ตรง; unknown status ถูกเก็บ String การ fallback วันที่ทำให้ order เก่าดูใหม่ ควรใช้ nullable/parse failure และ typed enum ที่รองรับ unknown

8. Detail tests

fixture order หลาย pallets, part ซ้ำหลาย pallet, partial/picked, station null, invalid date และ concurrent unassignment; widget test ต้องพิสูจน์ local reject, server conflict และ refresh หลังกลับจาก PickItemsScreen
