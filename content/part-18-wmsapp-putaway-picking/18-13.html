2. ข้อดีและข้อเสียของการให้ widget โหลดเอง

ข้อดีข้อเสีย
จอไม่ต้องรู้เรื่องนี้เลย — เพิ่มการ์ดแล้วจบจอควบคุมไม่ได้ว่าจะโหลดเมื่อไร
โหลดเฉพาะเมื่อการ์ดถูกแสดงจริงทดสอบจอต้องมีเซิร์ฟเวอร์
สถานะการโหลดอยู่ในการ์ด ไม่ปนกับจอโหลดใหม่จากภายนอกไม่ได้

ข้อดีข้อสองสำคัญที่นี่ — การ์ดนี้แสดงเฉพาะในสถานะ scanDest

_PickState.scanDest => _buildScanDest(),

ผู้ใช้ที่ไม่เคยเข้าสถานะนั้น (เพราะรู้พาเลทปลายทางแล้ว) จะไม่ยิงคำขอนี้เลย

ถ้าจอโหลดให้ ต้องตัดสินใจว่าโหลดตอน initState (เสียเปล่าถ้าไม่ใช้) หรือตอนเปลี่ยนสถานะ (ซับซ้อนขึ้น)

ข้อเสียข้อสามเป็นสิ่งที่ต้องรู้

Future<void> _loadSuggested() async { ... }     // private ไม่มีใครเรียกจากข้างนอกได้
สถานการณ์เกิดอะไร
ผู้ใช้ยืนยันหยิบ → กลับมา scanDest อีกครั้งการ์ดถูกสร้างใหม่ → โหลดใหม่เอง ✓
ผู้ใช้อยู่ใน scanDest นานแล้วพาเลทที่แนะนำถูกคนอื่นใช้ไม่มีทางโหลดใหม่

แถวที่สองไม่เสียหายมาก เพราะการแนะนำเป็นแค่ตัวช่วย — ผู้ใช้สแกนใบอื่นได้เสมอ และเซิร์ฟเวอร์จะปฏิเสธถ้าใช้ไม่ได้

หลักที่ใช้ตัดสิน: ให้ widget โหลดเองได้เมื่อข้อมูลนั้นเป็นของ widget ตัวนั้นคนเดียว และไม่ต้องซิงก์กับอะไร
ที่นี่ครบทั้งสองข้อ — คำแนะนำพาเลทใช้เฉพาะในการ์ดนี้ และผิดก็ไม่เสียหาย
ถ้าเป็นข้อมูลที่จอต้องใช้ด้วย หรือต้องโหลดใหม่พร้อมกับอย่างอื่น ต้องให้จอโหลด

ฝั่ง API อธิบายไว้ในคอมเมนต์

/// แนะนำ pallet ปลายทาง — ถ้า order นี้กำลังใช้ pallet เดิมอยู่ → ส่ง pallet เดิม
/// ไม่งั้นส่ง pallet ว่างถัดไป (Type=NULL + AVAILABLE)
/// คืน (palletId, continued) — continued=true แปลว่าเป็น pallet เดิมที่ pick ก่อนหน้าไว้

continuedหมายถึงผู้ใช้ควรรู้ว่า
trueพาเลทที่งานนี้ใช้อยู่แล้วใส่ต่อจากของเดิม
falseพาเลทว่างใบถัดไปเริ่มพาเลทใหม่

ความต่างนี้สำคัญ — ผู้ใช้ที่คิดว่าเป็นพาเลทใหม่แต่ที่จริงมีของอยู่แล้ว จะนับของผิด

ชนิดที่ API คืนน่าสนใจ

ApiResult<({String palletId, bool continued})?>
ค่าหมายถึง
success + recordมีพาเลทแนะนำ
success + nullถามสำเร็จ แต่ไม่มีพาเลทว่าง
errorถามไม่ได้

ตรวจอย่างเดียวว่าไม่ใช่พาเลทต้นทาง — ที่เหลือให้เซิร์ฟเวอร์ตัดสิน

การตรวจนี้จำเป็นเพราะเป็นความผิดพลาดที่เกิดได้ง่ายและเสียหายมาก
ผู้ใช้ที่ยิงพาเลทต้นทางซ้ำ (เพราะมันวางอยู่ตรงหน้า) จะกลายเป็นการหยิบของออกจากพาเลทแล้วใส่กลับที่เดิม — ระบบบันทึกว่าหยิบแล้ว แต่ของไม่ได้ขยับ

สังเกตว่า _destPalletId ถูกตั้งค่านอก setState อีกครั้ง

await _confirmPick(destId);

ทำงานได้เพราะ _confirmPick มี setState ข้างใน — แต่เป็นรูปแบบเดียวกับที่ 18.12 ชี้ว่าควรเลี่ยง

และไม่มีการตรวจว่าช่องว่างก่อนหน้านี้แล้วคืนโฟกัส

if (destId.isEmpty) return;      // ← เงียบ ไม่บอกอะไร

ผู้ใช้ที่กดปุ่มโดยยังไม่สแกนจะไม่เห็นอะไรเลย — จุดที่ return; เงียบอีกจุด

เข้าใจผิดที่จริง

8. แบบฝึกหัด

ทีมอยากให้จอ scanDest เตือนเมื่อผู้ใช้สแกนพาเลทที่มีของของงานอื่นอยู่

  1. ข้อมูลที่ต้องใช้มีอยู่แล้วไหม
  2. ควรตรวจฝั่งแอปหรือฝั่งเซิร์ฟเวอร์
  3. ออกแบบการเตือนที่ไม่ขวางผู้ใช้ที่ทำถูก
แนวคำตอบ

ข้อ 1 — ข้อมูลที่มีอยู่

ข้อมูลมีไหม
พาเลทที่แนะนำ + continuedมี — จาก getSuggestedDestPallet
พาเลทที่ผู้ใช้สแกนมีของงานอื่นไหมไม่มี

continued บอกได้แค่ว่าพาเลทที่แนะนำเป็นใบเดิมของงานนี้ไหม — ไม่ได้บอกอะไรเกี่ยวกับใบที่ผู้ใช้สแกนเอง

ต้องมีข้อมูลใหม่ ซึ่งแปลว่าต้องยิงคำขอเพิ่มหรือขอให้เซิร์ฟเวอร์ส่งมา

ข้อ 2 — ตรวจที่ไหน

ฝั่งแอป (ยิง preview)ฝั่งเซิร์ฟเวอร์ (ตรวจตอน confirm)
ผู้ใช้รู้ก่อนกดยืนยันไหมรู้ไม่รู้ — รู้หลังกดแล้ว
ยิงคำขอเพิ่มทุกครั้งที่สแกนไม่เพิ่ม
ป้องกันได้จริงไหมไม่ — ข้อมูลอาจเก่า (18.10)ได้

คำตอบคือทั้งสอง — เซิร์ฟเวอร์ต้องเป็นผู้ตัดสินคนสุดท้าย ส่วนแอปเตือนล่วงหน้าเพื่อให้ผู้ใช้ไม่เสียเวลา

แต่ที่นี่ต่างจาก 18.9 ตรงที่ไม่ควรบล็อก

กรณีควรทำ
พาเลทมีของงานอื่นเตือน แต่ยังยืนยันได้
พาเลทเป็นใบต้นทางห้าม — ไม่มีเหตุผลที่จะทำ

เพราะการใส่ของหลายงานลงพาเลทเดียวอาจเป็นสิ่งที่ทำได้จริงในบางกรณี — ต้องถามฝ่ายคลังก่อนว่าห้ามหรือแค่ไม่แนะนำ

9. สรุป

  • PickingDestScanCard เป็น widget ย่อยตัวเดียวในโดเมนนี้ที่ยิง API เอง
  • ทำได้เพราะข้อมูลเป็นของ widget นั้นคนเดียวและผิดก็ไม่เสียหาย
  • แต่โหลดใหม่จากข้างนอกไม่ได้ — คำแนะนำอาจล้าสมัยถ้าอยู่นาน
  • continued แยก “ใส่ต่อจากเดิม” จาก “เริ่มพาเลทใหม่”
  • การ์ดยุบ “ไม่มีพาเลทว่าง” กับ “ถามไม่ได้” เป็นกรณีเดียวกัน
  • แตะชิปแล้วเติมช่อง ไม่ยืนยันทันที — ปลอดภัยกว่าสำหรับคำสั่งที่ทำให้ของเคลื่อนที่
  • ตรวจอย่างเดียวว่าปลายทางไม่ใช่ต้นทาง ซึ่งเป็นความผิดพลาดที่เสียหายมาก
  • _confirmPick วนจาก palletItems และข้ามของที่ไม่ได้หยิบ
  • ไม่คัดลอกรายการ S/N ก่อนส่ง — ปลอดภัยตามลำดับที่เขียน ไม่ใช่ตามโครงสร้าง
