จบบทนี้แล้วจะทำได้: เขียน health check ที่บอกได้ว่าปลายทางเป็นเซิร์ฟเวอร์ที่ต้องการจริง และแปลผลให้ผู้ใช้แก้ปัญหาต่อได้

1. health endpoint คืออะไร

เส้นทางเล็ก ๆ ที่มีไว้ตอบคำถามเดียวคือ “ยังอยู่ไหม” โดยไม่ต้องเข้าสู่ระบบและไม่แตะฐานข้อมูล
GET /api/WMS/mobile_health

200 OK
{"service": "WMS", "ok": true, "version": "3.1.0"}
คุณสมบัติที่ต้องมีเพราะ
เรียกได้โดยไม่ต้องล็อกอินต้องทดสอบที่อยู่ได้ก่อนมีบัญชี
เร็วและเบาถ้าเส้นนี้ช้า แปลว่าตรวจแล้วรอนาน
ตอบข้อมูลที่ระบุตัวเองได้เพื่อแยกว่า “ใครตอบ” ไม่ใช่แค่ “มีคนตอบ”
ไม่บอกข้อมูลภายในมากเกินเส้นทางเปิด ใครก็เรียกได้

แถวที่สามคือหัวใจของบทนี้ และเป็นสิ่งที่คนมองข้ามบ่อยที่สุด

2. ทำไมรหัสตอบกลับไม่พอ

วิธีที่คนเขียนกันเป็นแบบนี้

// ไม่พอ
final response = await client.get(uri);
final ok = response.statusCode >= 200 && response.statusCode < 300;

ปัญหาคือ 200 แปลว่า “มีอะไรบางอย่างตอบ” ไม่ได้แปลว่า “สิ่งที่เราต้องการตอบ” สิ่งที่อาจตอบ 200 กลับมาได้

ใครตอบเกิดตอนไหน
เว็บหน้าแรกของเซิร์ฟเวอร์เดียวกันBase Path ผิด (10.10)
Wi-Fi ของโรงแรมหรือสนามบินยังไม่ได้กดยอมรับเงื่อนไข
reverse proxy ที่ตอบหน้า error สวย ๆเซิร์ฟเวอร์ปลายทางล่ม
เซิร์ฟเวอร์อื่นที่บังเอิญอยู่ IP นั้นผู้ใช้พิมพ์ IP ผิดหนึ่งตัว

ทั้งสี่กรณีผู้ใช้จะเห็นจุดเขียว แล้วสรุปว่าตั้งค่าถูกแล้ว จากนั้นทุกอย่างที่เหลือจะพังโดยไม่มีใครรู้ว่าทำไม

3. อ่านเนื้อหา ไม่ใช่แค่รหัส

/// จริงเฉพาะกับ JSON ที่ `mobile_health` ตอบจริง ๆ
bool isHealthPayload(String body) {
  try {
    final json = jsonDecode(body);
    return json is Map && json['service'] == 'WMS' && json['ok'] == true;
  } catch (_) {
    return false;   // HTML หรืออะไรก็ตามที่ไม่ใช่คำตอบของเรา
  }
}

ตรวจสามอย่างซ้อนกัน

ตรวจกันอะไร
แปลงเป็น JSON ได้HTML, ข้อความเปล่า, หน้า error
เป็น objectJSON ที่เป็น array หรือตัวเลขเดี่ยว
service == 'WMS' และ ok == trueAPI อื่นที่บังเอิญตอบ JSON

สังเกต catch (_) ที่กว้างผิดปกติ ตรงนี้ยอมรับได้เพราะเป้าหมายของฟังก์ชันคือตอบว่าจริงหรือเท็จ และทุกความล้มเหลวแปลว่า “ไม่ใช่คำตอบของเรา” เหมือนกันหมด — ต่างจากกรณีใน 9.13 ที่การกลืนข้อผิดพลาดทำให้ข้อมูลหาย

4. สามผลลัพธ์ ไม่ใช่สอง

final code = response.statusCode;
final answered = code >= 200 && code < 300;
final isWms = answered && isHealthPayload(response.body);

return ProbeResult(
  ok: isWms,
  statusCode: code,
  message: isWms
      ? 'เชื่อมต่อสำเร็จ · ${watch.elapsedMilliseconds} ms'
      : answered
      ? 'เซิร์ฟเวอร์ตอบกลับ แต่ไม่ใช่ WMS API — ตรวจ Base Path'
      : 'ตอบกลับ HTTP $code — ไม่ใช่เซิร์ฟเวอร์ WMS',
);
สถานการณ์ผู้ใช้ต้องทำอะไรต่อ
สำเร็จไม่ต้องทำอะไร
มีคนตอบ แต่ไม่ใช่ WMSตรวจ Base Path — IP กับพอร์ตน่าจะถูกแล้ว
ไม่มีใครตอบเลยตรวจ IP และพอร์ต

สองแถวล่างพาไปคนละช่องในฟอร์ม ซึ่งคือทั้งหมดที่ผู้ใช้ต้องการรู้ ถ้ายุบเป็น “เชื่อมต่อไม่สำเร็จ” อย่างเดียว ผู้ใช้จะไล่แก้ทุกช่องแบบสุ่ม

5. แปลความล้มเหลวแต่ละชนิดให้ต่างกัน

on TimeoutException => 'ไม่ตอบใน ${timeout.inSeconds} วินาที — ตรวจ IP และพอร์ต'
on HandshakeException => 'ใบรับรอง HTTPS ไม่ผ่าน — ลองใช้ HTTP หรือแก้ใบรับรอง'
on SocketException => 'ติดต่อที่อยู่นี้ไม่ได้ — ตรวจสัญญาณและเครื่องเซิร์ฟเวอร์'

HandshakeException คุ้มค่ามากที่จะแยกออกมา เพราะเซิร์ฟเวอร์ในองค์กรมักใช้ใบรับรองที่เครื่องไม่รู้จัก อาการที่ผู้ใช้เจอคือ “เลือก HTTPS แล้วต่อไม่ติด แต่ HTTP ติด” ซึ่งถ้าไม่บอก ผู้ใช้จะสรุปว่า HTTPS ใช้ไม่ได้และเลิกใช้ไปเลย

6. ตรวจก่อนยิง

Uri uri;
try {
  uri = Uri.parse('$baseUrl/api/WMS/mobile_health');
  if (!uri.hasScheme || uri.host.isEmpty) throw const FormatException();
} on FormatException {
  if (owned) httpClient.close();
  return const ProbeResult(ok: false, message: 'ที่อยู่เซิร์ฟเวอร์ไม่ถูกต้อง');
}

Uri.parse ใจกว้างกว่าที่คิด — Uri.parse('ไม่ใช่ url') ไม่โยน แต่คืน Uri ที่ไม่มี scheme และไม่มี host การเช็คสองอย่างนี้เองจึงจำเป็น

test('ที่อยู่ที่แปลงเป็น URL ไม่ได้ ต้องบอกก่อนยิง', () async {
  var called = false;
  final result = await probeServer(
    baseUrl: 'ไม่ใช่ url',
    client: MockClient((_) async { called = true; return http.Response('{}', 200); }),
  );
  expect(result.ok, isFalse);
  expect(called, isFalse, reason: 'ไม่ควรยิงคำขอเลย');
});

7. ทำไมไม่ใช้ ApiClient

/// ใช้ [http.Client] ตรง ๆ ไม่ผ่าน ApiClient โดยตั้งใจ — ApiClient ยิงไปที่
/// profile ที่ใช้งานอยู่เสมอ แต่ปุ่ม "ทดสอบการเชื่อมต่อ" ต้องลองที่อยู่ที่
/// พิมพ์อยู่ในฟอร์ม โดยไม่ไปรบกวนที่อยู่ที่ทั้งแอปกำลังใช้

นี่เป็นข้อยกเว้นของกฎใน 9.1 ที่ว่าทุกอย่างควรผ่านชั้นที่กำหนดไว้ และเหตุผลที่ยกเว้นชัดเจนคือ สิ่งที่ทดสอบยังไม่ใช่ของที่แอปใช้

เวลาจะยกเว้นกฎสถาปัตยกรรม ให้เขียนเหตุผลไว้ในโค้ดตรงนั้นเสมอ — คนที่มาเห็นทีหลังจะได้ไม่ “แก้ให้ถูกต้อง” แล้วทำฟีเจอร์พัง

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
จุดเขียวแต่ยิงคำขอไม่เข้าเชื่อรหัสตอบกลับอย่างเดียวอ่านเนื้อหา
ทดสอบผ่านแต่ใช้จริงไม่ได้ทดสอบคนละที่อยู่กับที่ใช้จริงให้ทั้งสองอย่างมาจากแหล่งเดียว (10.2)
ปุ่มทดสอบทำให้ทั้งแอปเปลี่ยนเซิร์ฟเวอร์ทดสอบโดยเปลี่ยน profile ที่ใช้งานอยู่ยิงตรงด้วย client ของตัวเอง
รอนานมากกว่าจะรู้ผลไม่ได้ตั้ง timeout หรือตั้งนานเกิน8 วินาทีก็เกินพอสำหรับเน็ตในองค์กร
ผู้ใช้บอกว่า HTTPS ใช้ไม่ได้ไม่แยก HandshakeExceptionแยกและบอกทางแก้

9. แบบฝึกหัด

ทีมหลังบ้านเสนอให้ health endpoint ตอบข้อมูลเพิ่ม เพื่อช่วยวินิจฉัย

{
  "service": "WMS",
  "ok": true,
  "version": "3.1.0",
  "database": "Server=10.0.0.5;Database=db_wms_pallet;User Id=sa;...",
  "pendingTasks": 47,
  "serverTime": "2026-08-21T09:15:00Z"
}

ควรรับข้อมูลไหนบ้าง

แนวคำตอบ
ฟิลด์รับเหตุผล
versionควรตอบคำถาม “PDA รุ่นนี้ใช้กับเซิร์ฟเวอร์รุ่นนี้ได้ไหม” และเป็นข้อมูลแรกที่ทีมถามเวลามีปัญหา
serverTimeควรเทียบกับเวลาบนเครื่องแล้วเตือนได้เมื่อนาฬิกาเพี้ยน ซึ่งทำให้ token หมดอายุผิดจังหวะ (8.3)
pendingTasksไม่เป็นข้อมูลธุรกิจ ไม่ใช่ข้อมูลสุขภาพ ทำให้ endpoint ต้องแตะฐานข้อมูล ซึ่งขัดกับข้อกำหนดว่าต้องเบา และวันที่ฐานข้อมูลช้า การตรวจก็จะช้าตาม
databaseห้ามเด็ดขาดเป็น connection string ที่มีรหัสผ่าน บนเส้นทางที่เรียกได้โดยไม่ต้องล็อกอิน — ใครก็ตามที่อยู่ในเครือข่ายเดียวกันจะได้สิทธิ์เข้าฐานข้อมูลทันที

ถ้าอยากรู้ว่าฐานข้อมูลต่อได้ไหมจริง ๆ ให้ตอบเป็น "database": "ok" หรือ "degraded" — บอกสถานะ ไม่บอกรายละเอียด

หลักที่ใช้ตัดสิน: health endpoint เปิดให้ทุกคนเรียกได้ ทุกฟิลด์ที่ใส่ลงไปคือข้อมูลที่ยอมให้คนนอกเห็น ถ้าลังเลแม้แต่นิดเดียว อย่าใส่

10. สรุป

  • health endpoint ต้องระบุตัวเองได้ ไม่ใช่แค่ตอบ 200
  • อ่านเนื้อหาเสมอ เพราะหลายอย่างตอบ 200 ได้
  • แยกผลเป็นสามแบบ เพื่อพาผู้ใช้ไปแก้ให้ถูกช่อง
  • แยก HandshakeException ออกมา เพราะใบรับรองในองค์กรมีปัญหาบ่อย
  • ยกเว้นกฎสถาปัตยกรรมได้ แต่ต้องเขียนเหตุผลไว้ในโค้ด
  • อย่าใส่ข้อมูลอ่อนไหวในเส้นทางที่ไม่ต้องล็อกอิน
