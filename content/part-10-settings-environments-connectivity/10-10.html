ระดับ: สูงใช้เวลา: 45–60 นาทีลงมือทำ: จำลองกับดักแล้วดูว่าเทสต์จับได้อย่างไร
ต้องผ่านอะไรมาก่อน: 10.9
จบบทนี้แล้วจะทำได้: รู้จักกับดักชนิด “200 ที่ไม่ใช่ของเรา” และหาเจอในระบบอื่นได้ด้วย

1. เรื่องที่เกิดขึ้นจริง

ผู้ใช้ตั้งค่า profile ใหม่สำหรับเซิร์ฟเวอร์ที่อยู่หลัง reverse proxy

Protocol: HTTPS
Host: wms.company.com
Port: 443
Base Path: /api          ← ตรงนี้

กด “ทดสอบการเชื่อมต่อ” แล้วขึ้นว่า เชื่อมต่อสำเร็จ · 84 ms จุดกลายเป็นสีเขียว ผู้ใช้กดบันทึกแล้วสลับไปใช้

จากนั้นทุกอย่างในแอปพัง ทุกหน้าจอขึ้นว่าโหลดไม่สำเร็จ

2. เกิดอะไรขึ้น

เซิร์ฟเวอร์ WMS ฝั่ง .NET เป็นเว็บ Blazor ที่ตั้งค่าไว้แบบนี้

// Program.cs ฝั่ง .NET
app.MapControllers();
app.MapBlazorHub();
app.MapFallbackToPage("/_Host");    // ← ต้นเหตุ
MapFallbackToPage บอกว่า “เส้นทางไหนที่ไม่ตรงกับอะไรเลย ให้ตอบหน้าเว็บหลักไป” มีไว้เพื่อให้เว็บที่ทำงานฝั่งเบราว์เซอร์ refresh หน้าใดก็ได้แล้วยังใช้ได้

ผลคือเซิร์ฟเวอร์นี้ ตอบ 200 ให้กับทุกเส้นทางที่ไม่รู้จัก

ยิงไปที่ได้
/api/WMS/mobile_health200 + JSON ที่ถูกต้อง
/api/api/WMS/mobile_health200 + HTML ของหน้าเว็บ
/อะไรก็ได้ที่ไม่มีจริง200 + HTML ของหน้าเว็บ

Base Path ที่ใส่ /api ทำให้ทุกคำขอกลายเป็น /api/api/WMS/... ซึ่งไม่ตรงกับ controller ไหน จึงตกไปที่หน้าเว็บ และได้ 200 กลับมาทุกครั้ง

3. ทำไมถึงหลอกได้แนบเนียน

สิ่งที่ตรวจผลที่ได้ดูเหมือน
ต่อ socket ได้ไหมได้ปกติ
DNS แปลชื่อได้ไหมได้ปกติ
ใบรับรอง HTTPS ผ่านไหมผ่านปกติ
รหัสตอบกลับ200ปกติ
เวลาตอบ84 msเร็วดี
เนื้อหา<!DOCTYPE html>...ผิด

ห้าข้อแรกผ่านหมด เพราะมันผ่านจริง — เซิร์ฟเวอร์ตัวนั้นมีอยู่จริงและทำงานปกติ สิ่งที่ผิดคือเส้นทาง ซึ่งเป็นสิ่งเดียวที่ต้องอ่านเนื้อหาถึงจะรู้

4. เทสต์ที่บังคับไว้

test('200 พร้อม HTML ของหน้าเว็บ ต้องไม่ถือว่าสำเร็จ', () async {
  // กับดัก Blazor: MapFallbackToPage ตอบ 200 ให้ทุกเส้นทางที่ไม่รู้จัก
  // ถ้าเชื่อแค่รหัสตอบกลับ Base Path ที่ผิดจะดูเหมือนใช้ได้
  final result = await probeServer(
    baseUrl: 'http://10.0.0.1:6191',
    client: respond('<!DOCTYPE html><html><body>WMS</body></html>', 200),
  );
  expect(result.ok, isFalse);
  expect(result.statusCode, 200);          // ← ยืนยันว่ามันตอบ 200 จริง
  expect(result.message, contains('Base Path'));
});

บรรทัด expect(result.statusCode, 200) มีไว้เพื่อบอกคนอ่านว่า นี่ไม่ใช่กรณีที่เซิร์ฟเวอร์ล่ม — ถ้าไม่มีบรรทัดนี้ คนที่มาอ่านเทสต์ทีหลังอาจคิดว่าเป็นเทสต์ซ้ำกับกรณีต่อไม่ติด

5. กันไว้สองชั้น

ชั้นแรกคือดักตั้งแต่ในฟอร์ม ไม่ให้ใส่ /api ได้เลย

if (normalizeBasePath(raw).toLowerCase().startsWith('/api')) {
  return 'ปล่อยว่างไว้ — แอปเติม /api ให้เองอยู่แล้ว '
      'ถ้าใส่ตรงนี้จะกลายเป็น /api/.../api/... แล้วยิงไม่เข้าสักเส้น';
}

ข้อความนี้ยาวกว่าข้อความผิดพลาดทั่วไปมาก และตั้งใจ เพราะผู้ใช้ที่ใส่ /api ลงไปไม่ได้ทำผิดโดยไม่มีเหตุผล — ช่องนี้หน้าตาเหมือนที่ที่ API root ควรอยู่ ถ้าบอกแค่ว่า “ห้ามใส่ /api” เขาจะสงสัยว่าแล้วต้องใส่ที่ไหน

ชั้นที่สองคือการตรวจเนื้อหาใน probe ซึ่งจับกรณีที่ชั้นแรกดักไม่ได้ เช่นเส้นทางที่ผิดด้วยเหตุอื่น หรือ proxy ที่กำหนดค่าผิด

สังเกตว่าเทสต์บังคับให้ดักได้ทุกรูปแบบที่พิมพ์

for (final raw in ['api', '/api', 'api/', '/API/wms']) {
  expect(validateDraft(draft(basePath: raw)).basePath, isNotNull);
}

/API/wms อยู่ในรายการเพราะ URL บางส่วนไม่สนตัวพิมพ์ใหญ่เล็ก และผู้ใช้ที่พิมพ์ตัวใหญ่ก็ตั้งใจอย่างเดียวกัน

6. กับดักเดียวกันในที่อื่น

รูปแบบนี้ไม่ได้มีแค่ Blazor ให้ระวังเมื่อเจอ

ระบบตอบ 200 ให้เส้นทางที่ไม่รู้จัก เพราะ
SPA ทุกชนิด (React, Angular, Vue)ต้องให้ refresh หน้าไหนก็ได้
Wi-Fi สาธารณะดักทุกคำขอไปหน้าล็อกอิน
ISP บางรายดัก DNS ที่หาไม่เจอไปหน้าค้นหา
reverse proxy ที่ตั้งค่าผิดตกไปที่ default server block
CDNตอบหน้า error ของตัวเองด้วย 200
กฎที่ใช้ได้ทั่วไป: เมื่อจะตรวจว่า “ต่อกับสิ่งที่ต้องการได้ไหม” ต้องมีอะไรบางอย่างในคำตอบที่เฉพาะเจาะจงกับระบบของเรา ไม่ใช่แค่รหัสตอบกลับ

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ทดสอบผ่านแต่ใช้จริงไม่ได้เชื่อรหัสตอบกลับตรวจเนื้อหา
jsonDecode โยนตอนได้ HTMLไม่ได้ครอบ tryครอบแล้วคืน false
ตรวจแค่ว่ามีคำว่า WMS ในเนื้อหาหน้าเว็บก็มีคำว่า WMSตรวจโครงสร้าง JSON
ผู้ใช้ใส่ /api ซ้ำแล้วซ้ำอีกข้อความบอกแค่ว่าห้ามบอกว่าทำไมและจะเกิดอะไร

8. แบบฝึกหัด

ทีมจะเพิ่มการตรวจว่ารุ่นของเซิร์ฟเวอร์ใช้กับ PDA รุ่นนี้ได้ไหม โดยอ่าน version จาก health payload

  1. ถ้าเซิร์ฟเวอร์เก่ากว่าที่รองรับ ควรทำอย่างไร
  2. ถ้า health payload ไม่มี version เลย ควรทำอย่างไร
แนวคำตอบ

1. ขึ้นกับว่าเข้ากันไม่ได้แค่ไหน และควรแยกเป็นสองระดับ

ระดับทำอะไร
เก่ากว่าที่รองรับ แต่ยังใช้ได้บางส่วนเตือน แล้วให้ใช้ต่อได้ — ผู้ใช้ที่หน้างานต้องทำงานให้เสร็จ
เก่าจนสัญญาไม่ตรงกันเลยห้ามใช้ พร้อมบอกรุ่นที่ต้องการ — ถ้าปล่อยไป จะได้ ContractException ทุกจอ ซึ่งผู้ใช้เข้าใจน้อยกว่า

สิ่งที่ต้องมีคู่กันคือข้อความที่บอกทั้งรุ่นที่เจอและรุ่นที่ต้องการ เพราะคนที่แก้ปัญหานี้ได้คือทีมไอที ไม่ใช่ผู้ใช้ และเขาต้องเอาข้อความนี้ไปบอกต่อ

2. ต้องยอมให้ไม่มี และถือว่าเป็นรุ่นเก่าที่สุดที่ยังรองรับ เหตุผลคือเซิร์ฟเวอร์ที่ยังไม่ได้อัปเดตคือเซิร์ฟเวอร์ที่ไม่มีฟิลด์นี้พอดี ถ้าบังคับให้ต้องมี ก็จะกันเซิร์ฟเวอร์รุ่นเก่าออกทั้งหมดตั้งแต่วันแรกที่ปล่อยฟีเจอร์นี้ ซึ่งเป็นสิ่งที่ตรงข้ามกับที่ต้องการ

นี่เป็นข้อยกเว้นของกฎใน 6.5 ที่ว่าฟิลด์ที่ขาดต้องโยน และเหตุผลชัดเจนคือ ฟิลด์นี้มีไว้ตรวจความเข้ากันได้ การไม่มีมันจึงเป็นข้อมูลอย่างหนึ่ง ไม่ใช่ความผิดพลาด

9. สรุป

  • 200 แปลว่ามีคนตอบ ไม่ได้แปลว่าคนที่เราต้องการตอบ
  • MapFallbackToPage และ SPA ทุกชนิดทำให้ทุกเส้นทางตอบ 200
  • ต้องมีอะไรในคำตอบที่เฉพาะเจาะจงกับระบบของเรา
  • ดักสองชั้น คือที่ฟอร์ม และที่การตรวจ
  • ข้อความผิดพลาดของกับดักที่หน้าตาสมเหตุสมผล ต้องอธิบายว่าทำไม
