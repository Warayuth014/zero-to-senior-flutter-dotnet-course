Sorting SignalR เป็น invalidation + fast patch: มี 6 event channels แต่หน้าหลัก subscribe เพียงบางรายการ ดังนั้น event coverage ต้องตรวจคู่กับ dashboard counters

1. Hub lifecycle

SortingSignalRService เป็น singleton/ref-count ต่อ /hubs/sorting ด้วย automatic reconnect connect/disconnect ทำงานเหมือน Putaway hub

2. Event catalog

StationCounterUpdated  StationFull
StationCleared         StationToggled
BatchQueued            BatchAssigned

payload ถูก parse เป็น Map แล้ว broadcast ไป copy ของ listener list

3. Main subscriptions

SortingScreen ฟัง counter/full/cleared/toggled/batchAssigned แต่ไม่ได้ฟัง BatchQueued ดังนั้น queuedCount อาจไม่เปลี่ยนจนมี eventอื่นหรือ manual refresh เป็น coverage gap ที่ควรแก้

4. Fast counter patch

CounterUpdated หา stationIdแล้ว copyWith current/total/full/pallet/status BUSY ลด latency แต่ไม่อัปเดต global completed/queued จึงยังต้องมี aggregate eventหรือ REST reconcile

5. Detail subscriptions

StationDetailSheet ฟัง counter/full เฉพาะ stationเดียวและเรียก GET detail ใหม่ มันไม่ connect/ref-countเองแต่พึ่ง parent screen connectionที่ยังอยู่หลัง bottom sheet

6. Reconnect gaps

connect exception ถูก log แต่ UIไม่รู้, automatic reconnectไม่มี refresh callback และไม่มี event replay ควร expose connection state แล้ว reload dashboardเมื่อ reconnected พร้อม periodic reconciliation

7. Event schema

Map casts เช่น stationId as int อาจ failถ้า JSON decoderให้ num/string และ malformed eventเงียบ ควรมี typed event parser, schema version, correlation ID และ telemetry ของ rejected payload

8. Realtime tests

fake hub ทดสอบ BatchQueued counter, queued→assigned, duplicate/out-of-order, detail+main listeners, reconnect refresh, two screens ref-count และ eventระหว่าง REST loadโดย versionล่าสุดต้องชนะ
