Sorting API แยก operations กับ test simulator: dashboard/station/toggle/clear เป็นงานจริง ส่วน available packs/create batch อยู่ใต้ test routes และไม่ควรเปิดใน production โดยไม่มี authorization

1. Operational endpoints

GET  /sorting/stations
GET  /sorting/stations/{stationId}
POST /sorting/stations/toggle
POST /sorting/stations/clear

2. Dashboard model

SortingDashboardData มี stations, completedCount และ queuedCount Count เป็น server aggregate ไม่ควรคำนวณ completed/queued จาก 10 cards เพราะ queue อยู่นอก station

3. Station view

SortingStationView มี stationId, enabled, status, pallet/capacity/full/disableReason และ copyWith สำหรับ realtime patch แต่ nullable parametersทำให้ set palletId กลับ null ไม่ได้ชัด ควรใช้ sentinel/copy API ที่รองรับ clear

4. Station detail

detail เพิ่ม cartons และ pendingCount; carton มี packingId, owner, weightGram, itemCount, sortedAt และ sequenceNo สำหรับตรวจลำดับ/น้ำหนักใน station

5. Test endpoints

GET  /sorting/test/available-packs
POST /sorting/test/create-batch
{ operatorId, packingIds }

response batch เป็น ASSIGNED พร้อม stationId หรือ QUEUED

6. Queue semantics

CreateSortingBatchResponse.isQueued derive จาก outcome String Batch size ต้องตรง packing IDs ที่ accepted และ partial reject policyต้อง explicitเพื่อไม่ให้ packหาย/ซ้ำใน queue

7. Parser/error debt

invalid times fallback now, statuses/outcomes เป็น String และ toggle/clear ยังคืน dynamic map ควรใช้ enum+typed result+server time/version และคง statusCode/problem details ทุก endpoint

8. API tests

ทดสอบ 10 stations, disabled/full, carton sequence, ASSIGNED/QUEUED, duplicate packing IDs, no station, clear/toggle conflict และ production policyที่ปิด test routes
