1. สามโดเมนที่เหลือ

18.16 ถามว่า “จอที่ไม่มี enum และไม่แตกไฟล์เลย ถือสถานะกี่อย่าง และอ่านอย่างไรให้ไม่หลง”

โดเมนไฟล์บรรทัดไฟล์ใหญ่สุดมี enum ไหม
packing12,1762,176มี — 5 สถานะ
checkin11,4411,441ไม่มี
sorting11,0301,030ไม่มี

ทั้งสามเป็นไฟล์เดียว ไม่มีโฟลเดอร์ widgets/ ไม่มี shared/

แต่สมมติฐานที่ว่า “ไฟล์เดียว = ไม่มีโครง” ผิดทันทีที่เปิดไฟล์แรก

// packing_screen.dart บรรทัดที่ 11
enum _PackState { scanPallet, packList, orderList, orderParts, success }
packing มี enum เหมือน PickItemsScreen — ทั้งที่ไม่แตกไฟล์เลยสักไฟล์
เป็นหลักฐานตรงที่สุดว่าการแตกไฟล์กับการจัดการสถานะเป็นคนละเรื่อง ซึ่ง 18.16 สรุปไว้

  ▼

  │

Future<void> _openStation(SortingStationView s) async {
  if (s.status == 'DISABLED') { _showDisabledMenu(s); return; }
  if (s.status == 'AVAILABLE') { _showAvailableMenu(s); return; }
  // BUSY → open detail sheet
  await showModalBottomSheet<void>(...);
}

9. แบบฝึกหัด

  1. จากตัวเลขในบทนี้ ทำนายว่าจอไหนอ่านยากที่สุด และเพราะอะไร
  2. ทำไม sorting ถึงไม่ต้องมี enum ทั้งที่มีสถานะสามแบบ
แนวคำตอบ

ข้อ 1

ถ้าดูแค่บรรทัด จะตอบว่า packing (2,176)

แต่เกณฑ์ที่ 18.16 สรุปไว้คือ “ต้องคิดถึงสถานะกี่อย่างพร้อมกัน”

จอสถานะที่ต้องคิดพร้อมกันอ่านยากแค่ไหน
packing1 (enum) + ข้อมูลของชั้นที่กำลังอยู่ยาว แต่ไม่หลง
checkin3 ฟิลด์ nullable ที่ประกอบกันเป็นโหมดหลงง่ายที่สุด
sorting0 — สถานะอยู่ที่เซิร์ฟเวอร์ง่ายที่สุด

checkin มีฟิลด์แค่ 7 ตัวแต่สามตัวเป็น nullable ที่ประกอบกันเป็นโหมด

PreviewCheckInResponse? _pendingPack;
PreviewCheckInResponse? _deliveryNotePack;
CheckInSlotDetail? _slotDetail;

ตามชนิดแล้วมีแปดชุดค่าที่เป็นไปได้ — เหมือนปัญหาที่ 17.5 พบใน ScanPartScreen

19.7 จะไล่ดูว่าชุดไหนเกิดจริงและชุดไหนไม่ควรเกิด

ข้อ 2 — ทำไม sorting ไม่ต้องมี enum

คำถามpacking/pickingsorting
ใครเป็นเจ้าของสถานะแอป — ผู้ใช้เดินผ่านขั้นตอนเซิร์ฟเวอร์ — สถานีมีสถานะของมัน
สถานะเปลี่ยนเพราะอะไรผู้ใช้กดเหตุการณ์จากที่อื่น
ถ้าปิดแอปแล้วเปิดใหม่เริ่มใหม่จากขั้นแรกเห็นสถานะเดิม

แถวสุดท้ายคือความต่างที่แท้จริง — สถานะของสถานีไม่ได้อยู่ในเครื่องผู้ใช้เลย

// จอทำแค่แสดงและอัปเดตตามที่ได้รับ
List<SortingStationView> _stations = [];
int _completedCount = 0;
int _queuedCount = 0;

สามฟิลด์นี้เป็นสำเนาของสิ่งที่เซิร์ฟเวอร์รู้ ไม่ใช่สถานะที่แอปเป็นเจ้าของ

หลักที่ใช้ตัดสินได้ทั่วไป: ต้องมีเครื่องสถานะในแอปเมื่อผู้ใช้เดินผ่านขั้นตอนที่แอปเป็นคนจำ
ถ้าสถานะทั้งหมดอยู่ที่เซิร์ฟเวอร์และแอปแค่แสดง สิ่งที่ต้องการคือการโหลดใหม่ให้ถูกจังหวะ ไม่ใช่ enum
สังเกตว่า UnloadSessionSheet (17.11) อยู่ตรงกลาง — สถานะการยืนยันอยู่ที่เซิร์ฟเวอร์ แต่ S/N ที่สแกนค้างอยู่ในเครื่อง จึงเสียงานได้เมื่อปิดแผ่น

10. สรุป

  • สามโดเมนสุดท้ายเป็นไฟล์เดียวทั้งหมด รวม 4,647 บรรทัด
  • packing มี enum ห้าสถานะทั้งที่ไม่แตกไฟล์เลย — พิสูจน์ว่าสองเรื่องนี้แยกกัน
  • checkin ไม่มี enum และมีสามฟิลด์ nullable ที่ประกอบกันเป็นโหมด
  • sorting ไม่มีสถานะของตัวเอง เพราะเซิร์ฟเวอร์เป็นเจ้าของ
  • packing เดินสี่ชั้น: พาเลท → กล่อง → ใบสั่ง → สินค้า
  • checkin ใช้ preview เป็นขั้นบังคับ ไม่ใช่ทางเลือก
  • sorting มีสามสถานะสถานีและทั้งสามแตะได้ ไม่มี return; เงียบ
  • ทั้งสิบห้า endpoint ส่ง statusCode ต่อครบ ต่างจากสี่โดเมนก่อนหน้า
  • packing_screen.dart คัดลอกโครงมาจาก pick_items_screen.dart
