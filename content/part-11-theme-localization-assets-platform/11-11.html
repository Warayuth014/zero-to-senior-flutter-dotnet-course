1. ประกาศให้ Flutter รู้จัก

เขียนแบบได้อะไร
ลงท้ายด้วย /ทุกไฟล์ในโฟลเดอร์นั้น แต่ไม่รวมโฟลเดอร์ย่อย
ชื่อไฟล์เต็มเฉพาะไฟล์นั้น

ข้อที่ทำให้เสียเวลาบ่อยคือโฟลเดอร์ย่อย — assets/images/ ไม่ครอบคลุม assets/images/products/ ต้องประกาศแยก

2. ความละเอียดหลายระดับ

จอโทรศัพท์มีความหนาแน่นพิกเซลต่างกันมาก รูปที่คมบนจอธรรมดาจะเบลอบนจอความละเอียดสูง Flutter จึงใช้กติกาชื่อโฟลเดอร์

assets/images/
  logo.png            ← 1x  (120×40)
  2.0x/
    logo.png          ← 2x  (240×80)
  3.0x/
    logo.png          ← 3x  (360×120)
// ประกาศแค่ตัว 1x ตัวอื่นถูกหยิบมาให้อัตโนมัติ
flutter:
  assets:
    - assets/images/logo.png
// เรียกด้วยชื่อเดียว Flutter เลือกไฟล์ตามจอ
Image.asset('assets/images/logo.png', width: 120)
width: 120 คือหน่วยอิสระจากพิกเซล ไม่ใช่จำนวนพิกเซลจริง บนจอ 3x จะกินพื้นที่ 360 พิกเซลจริง ซึ่งเป็นเหตุผลที่ไฟล์ 3x ต้องกว้าง 360

ถ้าไม่มีไฟล์ตรงความละเอียด Flutter จะใช้ตัวที่ใกล้ที่สุดแล้วย่อขยายให้ ซึ่งได้ผลที่ยอมรับได้แต่ไม่คมเท่า

4. รูปที่โหลดจากเน็ต ต่างกันคนละเรื่อง

Image.assetImage.network
อยู่ที่ไหนในแอปบนเซิร์ฟเวอร์
ล้มเหลวได้ไหมไม่ ถ้าประกาศถูกได้ตลอดเวลา
ต้องมีสถานะระหว่างโหลดไม่ต้อง
ต้องจัดการ errorไม่ต้อง
Image.network(
  url,
  loadingBuilder: (context, child, progress) =>
      progress == null ? child : const Center(child: CircularProgressIndicator()),
  // ขาดไม่ได้ — บน PDA ที่สัญญาณไม่ดี รูปโหลดไม่ขึ้นเป็นเรื่องปกติ
  errorBuilder: (context, error, stack) => const Icon(Icons.broken_image),
)

ถ้าไม่ใส่ errorBuilder จะได้กล่องแดงพร้อมข้อความ exception เต็มจอในโหมด debug และพื้นที่ว่างในโหมด release ซึ่งทั้งสองอย่างไม่ควรให้ผู้ใช้เห็น

5. fit ตัดสินว่าอะไรถูกตัด

BoxFitผลเหมาะกับ
containเห็นทั้งรูป มีที่ว่างเหลือโลโก้ รูปสินค้าที่ต้องเห็นครบ
coverเต็มพื้นที่ ส่วนเกินถูกตัดภาพพื้นหลัง
fillยืดให้พอดี รูปบิดเบี้ยวแทบไม่มี
fitWidth / fitHeightพอดีด้านเดียวกรณีเฉพาะ

ในงานคลัง contain เป็นค่าที่ปลอดภัยสำหรับรูปสินค้า เพราะ cover อาจตัดส่วนที่มีฉลากหรือรหัสออกไปพอดี

6. รูปกินหน่วยความจำมากกว่าขนาดไฟล์

รูป JPEG ขนาดไฟล์ 200 KB ที่มีขนาด 3000×2000 พิกเซล เมื่อถูกแสดงจะกินหน่วยความจำ

3000 × 2000 × 4 ไบต์ = 24 MB

ไม่ใช่ 200 KB เพราะรูปต้องถูกคลายการบีบอัดออกมาเป็นพิกเซลก่อนวาด ห้ารูปแบบนี้ในลิสต์เดียวคือ 120 MB ซึ่งทำให้แอปถูกระบบปิดบน PDA ที่แรมน้อย

Image.asset(
  'assets/images/product.jpg',
  width: 80,
  height: 80,
  // บอกให้คลายการบีบอัดที่ขนาดนี้ ไม่ใช่ขนาดเต็ม
  cacheWidth: 160,     // 80 × devicePixelRatio ของเครื่องเป้าหมาย
  cacheHeight: 160,
)
cacheWidth ลดหน่วยความจำได้มหาศาลและควรใส่เสมอกับรูปที่แสดงเล็กกว่าขนาดจริง — เป็นบรรทัดเดียวที่มักแก้ปัญหาแอปค้างในลิสต์รูปได้ทั้งหมด

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Unable to load assetไม่ได้ประกาศใน pubspec.yaml หรือสะกดชื่อผิดตรวจทั้งสองอย่าง ชื่อไฟล์ต้องตรงตัวพิมพ์
ประกาศแล้วยังไม่เจอhot reload ไม่โหลด asset ใหม่รันใหม่
ไฟล์ในโฟลเดอร์ย่อยไม่ถูกรวมประกาศแค่โฟลเดอร์แม่ประกาศแยกทุกโฟลเดอร์
แอปค้างเมื่อเลื่อนลิสต์ที่มีรูปรูปใหญ่กว่าที่แสดงมากใส่ cacheWidth
รูปเบลอบนบางเครื่องไม่มีไฟล์ความละเอียดสูงเพิ่ม 2x หรือใช้ SVG
รูปจากเน็ตหายเป็นพื้นที่ว่างไม่มี errorBuilderใส่เสมอ

8. แบบฝึกหัด

ฟีเจอร์ใหม่ต้องแสดงรูปสินค้าในลิสต์ รูปมาจากเซิร์ฟเวอร์ ขนาดต้นฉบับราว 2000×2000 และลิสต์แสดงรูปขนาด 64×64

  1. จะทำอย่างไร
  2. ถ้าเน็ตในคลังช้ามาก ควรทำอะไรเพิ่ม
แนวคำตอบ

1. สิ่งที่ควรทำ เรียงตามลำดับผลที่ได้

ทำได้อะไร
ขอให้เซิร์ฟเวอร์ส่งรูปย่อได้ผลมากที่สุด — โหลดเร็วขึ้นหลายสิบเท่า และประหยัดทั้งเน็ตและแรม
ใส่ cacheWidth: 128ถ้าเซิร์ฟเวอร์ส่งรูปเต็มมาแล้ว อย่างน้อยไม่กินแรม
errorBuilder และ loadingBuilderผู้ใช้รู้ว่าเกิดอะไรขึ้น
ใช้ cached_network_imageไม่โหลดซ้ำเมื่อเลื่อนกลับขึ้น

แถวแรกสำคัญที่สุดและมักถูกข้าม เพราะเป็นงานของทีมหลังบ้าน — แต่การดาวน์โหลดรูป 2000×2000 มาแสดงที่ 64×64 คือการโยนข้อมูลทิ้ง 99.9% หลังจากส่งมันข้ามเครือข่ายมาแล้ว

2. เมื่อเน็ตช้า ให้ถามคำถามที่ตรงกว่า คือ รูปนี้จำเป็นต่อการทำงานไหม

ถ้าจำเป็นถ้าไม่จำเป็น
โหลดเฉพาะแถวที่เห็นบนจอซ่อนรูปในลิสต์ แสดงเฉพาะหน้ารายละเอียด
เก็บลงเครื่องหลังโหลดครั้งแรกมีสวิตช์ให้ปิดรูป
แสดงกล่องสีเทาที่มีขนาดเท่ารูปไว้ก่อน—

ข้อสุดท้ายในคอลัมน์ซ้ายสำคัญ — ถ้าไม่จองพื้นที่ไว้ ลิสต์จะกระตุกทุกครั้งที่รูปโหลดเสร็จ และผู้ใช้ที่กำลังจะกดแถวหนึ่งจะกดโดนอีกแถว ซึ่งในงานคลังแปลว่าหยิบของผิด

คำถามที่ควรถามก่อนทั้งหมดนี้: ผู้ใช้ใช้รูปทำอะไร ถ้าใช้ยืนยันว่าหยิบของถูกใบ รูปย่อ 64×64 อาจไม่พอตั้งแต่แรก และคำตอบที่ถูกคือให้สแกนบาร์โค้ดยืนยันแทน ซึ่งเร็วกว่าและแม่นกว่ารูป

9. สรุป

  • ประกาศ asset ใน pubspec.yaml และโฟลเดอร์ย่อยต้องประกาศแยก
  • โฟลเดอร์ 2.0x และ 3.0x ถูกเลือกอัตโนมัติ ประกาศแค่ตัว 1x
  • ทำเท่าที่เครื่องจริงต้องการ
  • รูปกินแรมตามจำนวนพิกเซล ไม่ใช่ตามขนาดไฟล์ — ใส่ cacheWidth เสมอ
  • รูปจากเน็ตต้องมี errorBuilder และต้องจองพื้นที่ไว้ก่อน
