ระดับ: สูงใช้เวลา: 60–75 นาทีลงมือทำ: ตั้ง gen_l10n ในโปรเจกต์เปล่าแล้วเทียบกับที่เขียนเอง
ต้องผ่านอะไรมาก่อน: 11.7
จบบทนี้แล้วจะทำได้: ใช้เครื่องมือมาตรฐานของ Flutter เป็น และตัดสินได้ว่าโปรเจกต์ควรใช้หรือไม่

1. เครื่องมือมาตรฐาน

gen_l10n คือเครื่องมือที่มากับ Flutter อ่านไฟล์ข้อความแล้วสร้างคลาส Dart ให้อัตโนมัติ ไม่ต้องติดตั้งอะไรเพิ่ม

ไฟล์ข้อความใช้รูปแบบ ARB (Application Resource Bundle) ซึ่งเป็น JSON ที่มีกติกาเพิ่มนิดหน่อย

// lib/l10n/app_en.arb
{
  "@@locale": "en",
  "scanPallet": "Scan pallet",
  "@scanPallet": {
    "description": "ปุ่มหลักบนหน้าจอค้นพาเลท"
  },
  "palletCount": "{count, plural, =1{1 pallet} other{{count} pallets}}",
  "@palletCount": {
    "description": "จำนวนพาเลทในโซนที่เลือก",
    "placeholders": {
      "count": { "type": "int" }
    }
  }
}
// lib/l10n/app_th.arb
{
  "@@locale": "th",
  "scanPallet": "สแกนพาเลท",
  "palletCount": "พาเลท {count} ใบ"
}
ส่วนความหมาย
@@localeภาษาของไฟล์นี้
@ชื่อคีย์ข้อมูลประกอบ ใส่เฉพาะในไฟล์ภาษาหลัก
descriptionคำอธิบายให้คนแปล — สำคัญมาก คนแปลไม่เห็นหน้าจอ
placeholdersค่าที่จะแทรก พร้อมชนิด

2. ตั้งค่าและสร้าง

# l10n.yaml ที่รากโปรเจกต์
arb-dir: lib/l10n
template-arb-file: app_en.arb
output-localization-file: app_localizations.dart
flutter gen-l10n

ได้คลาสมาให้ใช้ทันที

MaterialApp(
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,
  locale: controller.locale,
)

// ในจอ
Text(AppLocalizations.of(context)!.scanPallet)
Text(AppLocalizations.of(context)!.palletCount(12))
AppLocalizations.localizationsDelegates รวมสาม delegate ของ Flutter (11.5) กับ delegate ของข้อความเราไว้ให้แล้ว จึงไม่ต้องเขียนรายการเอง

3. สิ่งที่ได้ที่เขียนเองไม่ได้

เอกพจน์–พหูพจน์ที่ถูกต้องทุกภาษา

"palletCount": "{count, plural, =1{1 pallet} other{{count} pallets}}"
ภาษาจำนวนรูปตัวอย่าง
ไทย จีน ญี่ปุ่น1ไม่เปลี่ยนตามจำนวน
อังกฤษ2one, other
รัสเซีย4one, few, many, other
อาหรับ6zero, one, two, few, many, other

โค้ดที่เขียนเองแบบ count == 1 ? ... : ... ใช้ได้กับสองภาษาแรกเท่านั้น ส่วน gen_l10n รู้กฎของทุกภาษาจากข้อมูล CLDR

เพศทางไวยากรณ์

"assignedTo": "{gender, select, male{เขาได้รับมอบหมาย} female{เธอได้รับมอบหมาย} other{ได้รับมอบหมาย}}"

การจัดรูปแบบตัวเลขและวันที่ในประโยค

"receivedAt": "รับเข้าเมื่อ {time}",
"@receivedAt": {
  "placeholders": { "time": { "type": "DateTime", "format": "Hm" } }
}

เครื่องมือแปลรองรับ ARB — ระบบจัดการงานแปลเชิงพาณิชย์ส่วนใหญ่นำเข้าและส่งออก ARB ได้ ต่างจากรายการที่เขียนเป็นโค้ด Dart ที่ต้องแปลงเอง

4. ราคาที่ต้องจ่าย

ต้นทุนรายละเอียด
ต้องสร้างโค้ดใหม่ทุกครั้งที่แก้ข้อความลืมสั่ง gen-l10n แล้วสงสัยว่าทำไมข้อความไม่เปลี่ยน
ไฟล์ที่สร้างขึ้นต้องตัดสินว่าจะ commit ไหมไม่ commit แล้ว CI ต้องสร้าง — commit แล้ว diff รกทุก PR
ต้องมี BuildContext ถึงจะอ่านข้อความได้เขียนเทสต์ตรวจข้อความโดยไม่สร้าง widget ไม่ได้
JSON แก้ยากกว่า Dartไม่มีการเติมคำอัตโนมัติ พิมพ์คีย์ผิดรู้ตอนสร้างโค้ด
AppLocalizations.of(context)! มี !ลืมห่อ MaterialApp แล้วพังตอนรัน ไม่ใช่ตอนคอมไพล์

แถวที่สามคือเหตุผลตรง ๆ ที่ lab ไม่ใช้ — เทสต์ที่ตรวจว่าข้อความทุกก้อนแปลครบ ต้องเรียกได้โดยไม่มี widget

5. เทสต์ที่ทำหน้าที่แทนเครื่องมือ

test('ทุกก้อนมีทั้งสองภาษา และไม่มีก้อนไหนว่าง', () {
  for (final message in AppText.all) {
    expect(message.en.trim(), isNotEmpty, reason: 'ภาษาอังกฤษว่าง');
    expect(message.th.trim(), isNotEmpty, reason: 'ภาษาไทยว่าง');
  }
});

เทสต์นี้พึ่งรายการ AppText.all ที่ต้องเติมด้วยมือ ซึ่งเป็นจุดอ่อนที่ต้องรู้ตัว — ถ้ามีคนเพิ่ม Message ใหม่แล้วลืมเติมลงรายการ เทสต์จะไม่จับ

gen_l10n ไม่มีปัญหานี้เพราะรายการคือไฟล์ ARB เอง

วิธีปิดช่องโหว่แรงที่ต้องลง
รีวิวโค้ดให้ตรวจว่าเติมรายการแล้วไม่มี แต่พึ่งคน
เขียนเทสต์ที่อ่านไฟล์ต้นฉบับแล้วนับ static const Message เทียบกับ all.lengthปานกลาง เชื่อถือได้
ย้ายไปใช้ gen_l10nสูง แต่หมดปัญหาถาวร

6. ทั้งสองโปรเจกต์จริงไม่ได้ใช้

โปรเจกต์ทำอย่างไรเหตุผลที่พอเข้าใจได้
wms_absolute_mobiletr(en, th)สองภาษา ทีมเล็ก ไม่มีคนแปลภายนอก
wmsappภาษาไทยเขียนตรงในโค้ดผู้ใช้ทุกคนอ่านไทย ไม่เคยต้องรองรับภาษาที่สอง

ทั้งสองทางเลือกสมเหตุสมผลในบริบทของตัวเอง แต่มีสิ่งที่ต้องรู้ล่วงหน้า

ต้นทุนของการไม่ใช้ ไม่ได้จ่ายวันนี้ แต่จ่ายวันที่มีภาษาที่สาม — และตอนนั้นข้อความจะมีเป็นพันก้อนกระจายอยู่ทั่วโปรเจกต์

7. ตัดสินใจอย่างไร

สถานการณ์ควรใช้
ภาษาเดียว ไม่มีแผนจะเพิ่มเขียนตรงในโค้ด
สองภาษา ทีมเดียวดูแล ข้อความไม่เกินร้อยก้อนรายการที่เขียนเอง
สามภาษาขึ้นไปgen_l10n
มีคนแปลที่ไม่ใช่โปรแกรมเมอร์gen_l10n
ต้องรองรับภาษาที่มีกฎพหูพจน์ซับซ้อนgen_l10n
เขียนไลบรารีให้คนอื่นใช้gen_l10n

สังเกตว่าเกณฑ์เกือบทั้งหมดไม่ใช่เรื่องเทคนิค แต่เป็นเรื่องใครเป็นคนแก้ข้อความ — ถ้าคนแก้คือโปรแกรมเมอร์ที่เปิดโปรเจกต์อยู่แล้ว รายการที่เขียนเองก็พอ

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แก้ ARB แล้วข้อความไม่เปลี่ยนยังไม่ได้สร้างโค้ดใหม่flutter gen-l10n หรือรันแอปใหม่
AppLocalizations.of(context) เป็น nullไม่มี MaterialApp เหนือขึ้นไปห่อในเทสต์ด้วย
คีย์ที่มีในไฟล์ไทยแต่ไม่มีในอังกฤษ ถูกทิ้งไฟล์ต้นแบบเป็นตัวกำหนดรายการเพิ่มในไฟล์ต้นแบบก่อนเสมอ
คนแปลแปลผิดความหมายไม่ได้ใส่ descriptionใส่ทุกคีย์ที่กำกวม
ข้อความไทยขึ้น {count} ตรง ๆไฟล์ไทยเขียน placeholder ผิดชื่อชื่อ placeholder ต้องตรงกับไฟล์ต้นแบบ

9. แบบฝึกหัด

ข้อความนี้อยู่ในหน้าจอสรุปงานประจำวัน

Text('${done.length} งานเสร็จแล้ว จาก ${all.length} งาน')
  1. เขียนเป็น ARB อย่างไร
  2. ถ้าต้องรองรับภาษาอังกฤษด้วย ต้องระวังอะไร
แนวคำตอบ

1.

// app_th.arb
"tasksProgress": "{done} งานเสร็จแล้ว จาก {total} งาน",

// app_en.arb (ไฟล์ต้นแบบ)
"tasksProgress": "{done} of {total} tasks done",
"@tasksProgress": {
  "description": "แถบสรุปบนหน้าจอหลัก แสดงความคืบหน้าของงานวันนี้",
  "placeholders": {
    "done": { "type": "int" },
    "total": { "type": "int" }
  }
}

2. สามเรื่อง

  • ลำดับของ placeholder ต่างกันได้ และนั่นคือเหตุผลที่ต้องใช้ชื่อ ไม่ใช่ตำแหน่ง — ภาษาที่เอา total ขึ้นก่อนก็เขียน "{total} งาน เสร็จแล้ว {done}" ได้โดยไม่ต้องแก้โค้ด
  • อังกฤษต้องเลือกรูปพหูพจน์ — “1 of 5 tasks done” ถูก แต่ “1 of 1 task done” ต้องใช้ task ไม่ใช่ tasks ซึ่งต้องใช้ plural ซ้อนใน placeholder
  • ระวัง 0 งาน — “0 of 0 tasks done” อ่านแล้วสับสน ควรมีข้อความแยกสำหรับกรณีที่ยังไม่มีงานเลย ซึ่งเป็นการตัดสินใจด้าน UX ที่ระบบแปลช่วยไม่ได้

ข้อสุดท้ายเป็นบทเรียนที่ใหญ่กว่าเรื่อง ARB — เครื่องมือแปลจัดการรูปแบบของภาษาได้ แต่ตัดสินใจแทนเราไม่ได้ว่าข้อความไหนควรมีอยู่

10. สรุป

  • gen_l10n มากับ Flutter อ่าน ARB แล้วสร้างคลาสให้
  • ได้กฎพหูพจน์ของทุกภาษาและรูปแบบวันที่ในประโยค ซึ่งเขียนเองยากมาก
  • แลกด้วยการต้องสร้างโค้ดใหม่ และต้องมี BuildContext ถึงจะอ่านข้อความได้
  • เกณฑ์ตัดสินคือใครเป็นคนแก้ข้อความ ไม่ใช่เรื่องเทคนิค
  • ตั้งแต่ภาษาที่สามขึ้นไป ให้ใช้เครื่องมือ

บทหน้า: ตัวเลขและวันที่ ที่ผิดแล้วไม่มีใครเห็นจนกว่าจะสายเกินไป
