2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
HTTPกติกาที่แอปกับเซิร์ฟเวอร์ใช้คุยกัน
requestคำขอที่แอปส่งไป
responseคำตอบที่เซิร์ฟเวอร์ส่งกลับ
endpointที่อยู่หนึ่งที่ของเซิร์ฟเวอร์ที่รับคำขอเรื่องหนึ่ง
clientตัวที่ทำหน้าที่ส่ง HTTP
repositoryชั้นที่รู้ว่า endpoint ไหนให้ข้อมูลอะไร

3. Mental model: ห้าชั้น ไม่ใช่สองชั้น

ผู้ใช้แตะปุ่ม
    │
    ▼  หน้าจอ           รับการกระทำ แสดงผล — ไม่รู้จัก HTTP เลย
    │
    ▼  store            คุมสถานะ กันกดซ้ำ ตัดสินใจ — ไม่รู้จัก URL
    │
    ▼  repository       รู้ว่า endpoint ไหน และแปลง JSON เป็น model
    │
    ▼  ApiClient        รู้ HTTP, header, timeout, รหัสตอบกลับ
    │
    ▼  เครือข่าย → .NET → ฐานข้อมูล
ประโยคเดียวที่ต้องจำ: แต่ละชั้นรู้เรื่องของชั้นที่อยู่ต่ำกว่าตัวเองหนึ่งชั้นเท่านั้น — หน้าจอที่รู้จัก URL คือสัญญาณว่ามีอะไรรั่วขึ้นมา

5. ทำไมต้องมี repository คั่นกลาง

คำถามที่สมเหตุสมผล — ทำไม store ไม่เรียก ApiClient ตรง ๆ

ถ้า store เรียกเองผลที่ตามมา
store ต้องรู้เส้นทาง /api/WMS/mobile_tasksเปลี่ยน endpoint ต้องแก้ store
store ต้องแปลง JSON เองตรรกะการแปลงกระจายไปทุก store
ทดสอบ store ต้องปลอม HTTPยากกว่าปลอม repository มาก
abstract interface class TaskRepository {
  Future<List<WmsTask>> fetchOpen();
  Future<TaskCompletion> complete(String id, {required String commandId});
}

เพราะ TaskRepository เป็นสัญญา ไม่ใช่คลาสจริง store จึงทดสอบได้โดยไม่ต้องมีเซิร์ฟเวอร์ — เป็นรูปแบบเดียวกับ PickRepository ใน 4.5

และมันยังทำให้เปลี่ยนแหล่งข้อมูลได้โดยไม่แตะ store เลย ซึ่งจะได้ใช้จริงใน Part 12 ตอนทำให้ทำงานได้ตอนไม่มีเน็ต

7. ไล่หาปัญหาให้ถูกชั้น

เมื่อมีคนบอกว่า “แอปโหลดงานไม่ขึ้น” ให้ไล่จากล่างขึ้นบน

ขั้นตรวจอะไรถ้าผิดตรงนี้
1เปิด URL ในเบราว์เซอร์บนเครื่องนั้นได้ไหมปัญหาเครือข่าย ไม่ใช่โค้ด (7.3)
2เซิร์ฟเวอร์ตอบรหัสอะไรปัญหาสิทธิ์หรือเส้นทาง (7.9)
3JSON ที่ได้หน้าตาตรงสัญญาไหมปัญหาสัญญา (Part 6)
4store ได้ข้อมูลแล้วแต่จอไม่เปลี่ยนไหมปัญหาการวาดใหม่ (4.6)

คนส่วนใหญ่เริ่มที่ขั้น 4 เพราะเป็นที่ที่เห็นอาการ — แต่สาเหตุมักอยู่ขั้น 1 หรือ 2 และการเริ่มผิดที่ทำให้เสียเวลาเป็นชั่วโมง

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เปลี่ยน endpoint แล้วต้องแก้หลายไฟล์เส้นทางกระจายอยู่หลายชั้นให้ repository เป็นที่เดียวที่รู้เส้นทาง
หน้าจอมี http.getข้ามชั้นทั้งหมดย้ายลงไปที่ repository
ทดสอบ store ต้องเปิดเซิร์ฟเวอร์store ผูกกับ ApiClient จริงให้ store รับสัญญา ไม่รับคลาสจริง
แก้ปัญหานานเพราะหาสาเหตุไม่เจอเริ่มไล่จากชั้นบนสุดไล่จากล่างขึ้นบน
ตรรกะแปลง JSON อยู่ใน storeไม่มี repositoryเพิ่มชั้นคั่น

9. แบบฝึกหัด

ทีมได้ความต้องการใหม่ — เพิ่มปุ่มค้นหางานด้วยรหัสพาเลท

  1. ระบุว่าต้องแก้ไฟล์ไหนบ้าง และแต่ละไฟล์แก้อะไร
  2. ตอบว่าถ้าฝั่งหลังบ้านเปลี่ยนชื่อ query จาก search เป็น keyword จะกระทบกี่ไฟล์
  3. ตอบว่าถ้าต่อไปต้องให้ค้นหาได้ตอนไม่มีเน็ต จะกระทบกี่ไฟล์
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ไฟล์ที่ต้องแก้

ไฟล์แก้อะไร
task_screen.dartเพิ่มช่องค้นหา และเรียก store.search(query)
task_store.dartเพิ่มเมธอด search พร้อมตัวนับรุ่นและ debounce (4.10)
task_repository.dartเพิ่ม fetchOpen({String? search}) และประกอบ query
api_client.dartไม่ต้องแก้

แถวสุดท้ายคือสิ่งที่บอกว่าชั้นถูกวางถูก — ApiClient รับ path มาแล้วยิง ไม่สนใจว่า path นั้นมี query อะไร

ข้อ 2 — เปลี่ยนชื่อ query

ไฟล์เดียว คือ task_repository.dart

// เดิม
'/api/WMS/mobile_tasks?search=$encoded'
// ใหม่
'/api/WMS/mobile_tasks?keyword=$encoded'

store ไม่รู้จักชื่อ query อยู่แล้ว มันรู้แค่ว่า “ค้นด้วยข้อความนี้” ส่วนหน้าจอก็ไม่รู้จักทั้งคู่

นี่คือประโยชน์ที่จับต้องได้ของการมี repository คั่น — การเปลี่ยนที่ฝั่งเซิร์ฟเวอร์หยุดอยู่ที่ชั้นเดียว

ข้อ 3 — ค้นหาได้ตอนไม่มีเน็ต

คำตอบที่คนมักให้คือ “แก้ repository” ซึ่งใกล้เคียงแต่ยังไม่ตรง

สิ่งที่ควรทำคือ เพิ่มคลาสใหม่ ไม่ใช่แก้ของเดิม

abstract interface class TaskRepository {           // สัญญาเดิม ไม่แตะ
  Future<List<WmsTask>> fetchOpen({String? search});
}

class RemoteTaskRepository implements TaskRepository { ... }   // เดิม

class OfflineFirstTaskRepository implements TaskRepository {   // ใหม่
  const OfflineFirstTaskRepository({required this.remote, required this.local});

  final TaskRepository remote;
  final TaskDatabase local;

  @override
  Future<List<WmsTask>> fetchOpen({String? search}) async {
    try {
      final tasks = await remote.fetchOpen(search: search);
      await local.save(tasks);      // เก็บไว้ใช้ตอนไม่มีเน็ต
      return tasks;
    } on ApiException catch (error) {
      if (error.kind != ApiFailureKind.network) rethrow;
      return local.search(search);  // เน็ตไม่มี ใช้ของที่เก็บไว้
    }
  }
}
ไฟล์ต้องแก้ไหม
task_screen.dartไม่
task_store.dartไม่
task_repository.dartไม่ — เพิ่มคลาสใหม่แทน
api_client.dartไม่
จุดที่ประกอบแอปตอนเริ่มใช่ — เปลี่ยนว่าจะส่ง repository ตัวไหนให้ store
// เดิม
final store = TaskStore(RemoteTaskRepository(apiClient));

// ใหม่ — store ไม่รู้ด้วยซ้ำว่าอะไรเปลี่ยน
final store = TaskStore(OfflineFirstTaskRepository(
  remote: RemoteTaskRepository(apiClient),
  local: taskDatabase,
));

ทำไมเพิ่มคลาสดีกว่าแก้ของเดิม

เหตุผลรายละเอียด
RemoteTaskRepository ยังทดสอบแยกได้เทสต์เดิมไม่ต้องแก้
ตรรกะ “ลองเน็ตก่อนแล้วค่อยใช้ของเก่า” อยู่ที่เดียวเอาไปใช้กับ repository อื่นได้
สลับกลับได้ทันทีถ้ามีปัญหาเปลี่ยนบรรทัดเดียวที่จุดประกอบ

บทเรียนที่ควรจำ: การวางชั้นที่ดีวัดได้จากคำถามว่า ความเปลี่ยนแปลงหนึ่งอย่างกระทบกี่ไฟล์ — ถ้าคำตอบคือหนึ่ง แสดงว่าวางถูก ถ้าคำตอบคือทุกไฟล์ แสดงว่ายังไม่ได้แยกชั้นจริง

10. สรุปท้ายบท

  • มีห้าชั้น ไม่ใช่แค่หน้าจอกับเซิร์ฟเวอร์
  • แต่ละชั้นรู้เรื่องของชั้นที่ต่ำกว่าหนึ่งชั้นเท่านั้น
  • หน้าจอไม่รู้จัก HTTP, store ไม่รู้จัก URL
  • repository เป็นที่เดียวที่รู้เส้นทางและรูปแบบข้อมูล
  • ApiClient รู้ HTTP แต่ไม่รู้ว่ากำลังคุยเรื่องอะไร
  • ให้ store รับสัญญา ไม่รับคลาสจริง เพื่อให้ทดสอบได้
  • ไล่หาปัญหาจากล่างขึ้นบน ไม่ใช่จากที่ที่เห็นอาการ
  • วัดว่าวางชั้นถูกไหม จากจำนวนไฟล์ที่กระทบเมื่อมีการเปลี่ยนแปลง
