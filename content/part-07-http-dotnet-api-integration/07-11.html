ProblemDetails: รูปแบบมาตรฐานของ .NET สำหรับ error มี status, title, detail, type, instance และ extensions เช่น traceId/errors/code

1. ตัวอย่าง payload

{
  "type": "https://example/errors/validation",
  "title": "Validation failed",
  "status": 400,
  "detail": "Quantity must be greater than zero",
  "code": "INVALID_QUANTITY",
  "traceId": "00-abcd..."
}

2. Dart model แบบทนทาน

รับ field มาตรฐานเป็น nullable, parse extensions ที่ทีมใช้ และเก็บ validation errors เป็น map ของ field → messages โดยไม่ assume ว่าทุก error มี detail

3. Message fallback chain

final message = problem.detail?.trim().isNotEmpty == true
    ? problem.detail!
    : problem.title?.trim().isNotEmpty == true
        ? problem.title!
        : fallbackForStatus(response.statusCode);

4. .NET endpoint

return Results.Problem(
  statusCode: StatusCodes.Status409Conflict,
  title: "Task conflict",
  detail: "Task was completed by another device",
  extensions: new Dictionary<string, object?> {
    ["code"] = "TASK_ALREADY_COMPLETED"
  });

5. ValidationProblem

กรณีหลาย field ให้ .NET คืน dictionary ของ errors; Flutter map field key ไป form control หรือสรุปด้านบน โดยมี global message เมื่อ key ไม่ตรง UI

6. Security

production ProblemDetails ไม่ควรคืน stack trace, SQL, internal host หรือ exception message ดิบ ให้ log รายละเอียดฝั่ง serverและคืน trace ID สำหรับอ้างอิง

7. แบบฝึกหัด

Error body ว่างและ status 503 ผู้ใช้ควรเห็นอะไร?

เฉลย

fallback ที่กำหนดจาก 503 เช่น “ระบบยังไม่พร้อม กรุณาลองใหม่” พร้อม trace/correlation ID ถ้ามี ไม่แสดงข้อความว่าง

8. Contract

ตกลง stable error code และ field errors ระหว่าง Flutter/.NET; title/detail เปลี่ยนภาษาได้แต่ code ต้องไม่เปลี่ยนโดยไม่ version
