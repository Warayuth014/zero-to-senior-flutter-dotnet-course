3. Mental model: รหัสคือชื่อของเจตนา

เจตนา "ปิดงาน T-001"  →  cmd-8821
    ├─ ส่งครั้งที่ 1 → cmd-8821 → server บันทึก
    ├─ ลองใหม่      → cmd-8821 → server จำได้ ตอบผลเดิม
    └─ ผู้ใช้กดซ้ำ   → cmd-8821 → server จำได้ ตอบผลเดิม
ประโยคเดียวที่ต้องจำ: รหัสถูกสร้างตอนที่ผู้ใช้ตัดสินใจ ไม่ใช่ตอนที่ยิงคำขอ — ถ้าสร้างตอนยิง ทุกครั้งที่ยิงจะได้รหัสใหม่ ซึ่งทำให้ทั้งระบบไร้ความหมาย

4. ส่งไปทาง header

เปิด lib/features/tasks/task_repository.dart

ส่งทาง headerส่งใน body

ต้องแก้สัญญาของ endpoint ไหมไม่ต้อง

เทสต์ใน lab ตรึงไว้ว่ารหัสถูกส่งจริง

expect(sent!.headers['Idempotency-Key'], 'cmd-8821');

5. รู้ได้อย่างไรว่าเป็นการทำซ้ำ

เซิร์ฟเวอร์ควรบอกกลับมาด้วยว่าครั้งนี้ทำจริงหรือตอบผลเดิม

class TaskCompletion {
  const TaskCompletion({
    required this.id,
    required this.alreadyCompleted,
    required this.correlationId,
  });

  final String id;
  final bool alreadyCompleted;
  final String correlationId;
}
alreadyCompletedแปลว่าผู้ใช้ควรเห็น
falseปิดงานสำเร็จในครั้งนี้“ปิด T-001 สำเร็จ”
trueปิดไปแล้วก่อนหน้านี้“T-001 ถูกปิดไปแล้ว (ตรวจซ้ำสำเร็จ)”

ดูของจริงใน task_store.dart

_actionMessage = result.alreadyCompleted
    ? '${task.id} ถูกปิดไปแล้ว (ตรวจซ้ำสำเร็จ)'
    : 'ปิด ${task.id} สำเร็จ · ${result.correlationId}';

ทั้งสองกรณีเป็นความสำเร็จ — ต่างกันแค่ว่าครั้งนี้ทำอะไรจริงหรือไม่

การแยกให้ผู้ใช้เห็นสำคัญ เพราะถ้าบอกว่า “ปิดสำเร็จ” ทั้งสองกรณี ผู้ใช้จะไม่รู้ว่าเมื่อกี้ที่กดไปแล้วมันติดหรือไม่

8. ตรวจว่าผลที่ได้เป็นของคำขอนี้จริง

final responseId = json['id']?.toString();
if (responseId == null ||
    responseId != id ||
    alreadyCompleted is! bool ||
    correlationId == null ||
    correlationId.isEmpty) {
  throw const ApiException('รูปแบบผล complete task ไม่ถูกต้อง');
}

บรรทัด responseId != id ตรวจสิ่งที่ดูเหมือนไม่น่าเกิด — แต่เกิดได้จริงเมื่อ

สถานการณ์ผลที่เกิด
รหัสคำสั่งชนกันโดยบังเอิญได้ผลของงานอื่นกลับมา
เซิร์ฟเวอร์มีบั๊กในการจับคู่รหัสเหมือนกัน
ตัวกลางในเครือข่ายส่งคำตอบผิดคนเหมือนกัน

ถ้าไม่ตรวจ แอปจะทำเครื่องหมายว่างานผิดตัวเสร็จแล้ว โดยที่ไม่มีอะไรบอก

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ข้อมูลซ้ำแม้มีรหัสคำสั่งสร้างรหัสใหม่ทุกครั้งที่ยิงสร้างตอนที่ผู้ใช้ตัดสินใจ
ลองใหม่แล้วได้ข้อมูลซ้ำสร้างรหัสข้างใน closure ที่ถูกลองใหม่ย้ายออกมาข้างนอก
ทุกอย่างดูปกติแต่ไม่มีการกันซ้ำรหัสไม่ถูกส่งไปจริงเทสต์ตรวจ header ที่ส่ง
ผู้ใช้ไม่รู้ว่ากดครั้งก่อนติดหรือไม่บอกว่าสำเร็จเหมือนกันทั้งสองกรณีแยกข้อความตาม alreadyCompleted
ส่งซ้ำหลังผ่านไปนานแล้วได้ข้อมูลซ้ำเซิร์ฟเวอร์เก็บรหัสไว้สั้นเกินไปตกลงระยะเวลาเก็บ
งานผิดตัวถูกทำเครื่องหมายว่าเสร็จไม่ตรวจว่าผลเป็นของคำขอนี้เทียบ id ที่ได้กลับมา

10. แบบฝึกหัด

ทีมกำลังจะทำ endpoint ยืนยันรับเข้าทั้งใบ ซึ่งมี 40 บรรทัดในคำขอเดียว

  1. ระบุว่ารหัสคำสั่งควรผูกกับอะไร — ทั้งใบ หรือแต่ละบรรทัด
  2. เขียนข้อตกลงที่ต้องคุยกับฝั่งหลังบ้านให้ครบ
  3. ตอบว่าถ้าผู้ใช้แก้จำนวนบรรทัดหนึ่งแล้วส่งใหม่ ควรใช้รหัสเดิมหรือใหม่
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ผูกกับอะไร

ผูกกับทั้งใบ เพราะขอบเขตของรหัสควรตรงกับขอบเขตของคำสั่ง

รหัสต่อใบรหัสต่อบรรทัด
ตรงกับคำขอไหมตรง — หนึ่งคำขอหนึ่งรหัสไม่ตรง — 40 รหัสในคำขอเดียว
เซิร์ฟเวอร์ตรวจอย่างไรตรวจครั้งเดียวต้องตรวจ 40 ครั้ง แล้วตัดสินว่าถ้าบางบรรทัดซ้ำจะทำอย่างไร
ส่งซ้ำแล้วเกิดอะไรตอบผลเดิมทั้งใบอาจได้ผลปนกันระหว่างบรรทัดที่ทำแล้วกับยังไม่ทำ

แถวสุดท้ายเป็นเหตุผลหลัก — ถ้าหนึ่งคำขอทำได้บางส่วน จะไม่มีทางตอบได้ว่า “ทำไปแล้วหรือยัง” ซึ่งทำลายทั้งแนวคิด

หลักคือ หนึ่งคำขอ หนึ่งรหัส และคำขอนั้นต้องสำเร็จทั้งหมดหรือไม่สำเร็จเลย

ข้อ 2 — ข้อตกลงที่ต้องคุย

ข้อตกลงรหัสคำสั่ง — endpoint ยืนยันรับเข้า

1. ส่งอย่างไร
   header ชื่อ Idempotency-Key
   ค่าเป็นข้อความไม่เกิน 64 ตัวอักษร

2. ขอบเขต
   หนึ่งรหัสต่อหนึ่งใบ ครอบทุกบรรทัดในคำขอนั้น
   คำขอต้องสำเร็จทั้งหมดหรือไม่สำเร็จเลย

3. เก็บไว้นานแค่ไหน
   อย่างน้อย 24 ชั่วโมง
   (ครอบกรณีที่ผู้ใช้ปิดแอปข้ามกะแล้วกลับมาส่งซ้ำ)

4. เจอรหัสซ้ำ ตอบอะไร
   200 พร้อมผลเดิม และ alreadyProcessed เป็น true
   ไม่ใช่ 409 เพราะไม่ใช่ความขัดแย้ง

5. รหัสเดิมแต่เนื้อหาต่าง ตอบอะไร
   409 พร้อม errorCode ว่า IDEMPOTENCY_KEY_REUSED
   (เป็นบั๊กฝั่งแอป ต้องดังให้เห็น)

6. ไม่ส่งรหัสมาเลย ตอบอะไร
   400 — เพื่อไม่ให้มีทางที่คำสั่งจะถูกส่งโดยไม่มีการกันซ้ำ

ข้อ 4 สำคัญและมักตกลงผิด — การเจอรหัสซ้ำไม่ใช่ความผิดพลาด มันคือการทำงานตามที่ออกแบบไว้ ถ้าตอบ 409 แอปจะแสดงเป็นข้อผิดพลาดทั้งที่ทุกอย่างถูกต้อง

ข้อ 6 เป็นการป้องกันที่ดี — ถ้าเซิร์ฟเวอร์ยอมรับคำขอที่ไม่มีรหัส วันหนึ่งจะมีคนเขียนโค้ดที่ลืมส่ง แล้วไม่มีใครรู้จนกว่าจะเกิดข้อมูลซ้ำ

ข้อ 3 — แก้จำนวนแล้วส่งใหม่

รหัสใหม่ — และเหตุผลอยู่ในกฎที่ตั้งไว้ตั้งแต่ 4.14

สถานการณ์รหัสเพราะ
ส่งไปแล้วไม่รู้ผล แล้วส่งซ้ำเดิมเป็นเจตนาเดิม แค่ไม่แน่ใจว่าถึงไหม
ถูกปฏิเสธ แล้วส่งใหม่โดยไม่แก้อะไรใหม่ครั้งก่อนไม่มีอะไรถูกบันทึก และเงื่อนไขอาจเปลี่ยนแล้ว
แก้ข้อมูลแล้วส่งใหม่ใหม่เป็นคนละเจตนา — เนื้อหาไม่เหมือนเดิมแล้ว

และข้อตกลงข้อ 5 ในข้อ 2 กันกรณีที่เขียนผิดไว้พอดี — ถ้าเผลอส่งรหัสเดิมพร้อมเนื้อหาใหม่ เซิร์ฟเวอร์จะปฏิเสธและบอกว่าเป็นบั๊ก

ถ้าไม่มีข้อตกลงนั้น เซิร์ฟเวอร์จะตอบผลเดิมกลับมา แล้วผู้ใช้จะเห็นว่า “บันทึกสำเร็จ” ทั้งที่จำนวนที่แก้ไปไม่ได้ถูกบันทึกเลย

ผู้ใช้แก้ 12 เป็น 15 แล้วกดส่ง
  → ส่งรหัสเดิม (ผิด)
  → server ตอบผลเดิมที่บันทึกไว้ตอน 12
  → แอปแสดงว่าสำเร็จ
  → ในระบบยังเป็น 12 อยู่ และไม่มีใครรู้

อาการนี้ร้ายเพราะไม่มีอะไรพัง และผู้ใช้เชื่อว่าแก้สำเร็จแล้ว

วิธีทำให้ถูกในโค้ด

/// ล้างรหัสเมื่อร่างถูกแก้ — การแก้คือเจตนาใหม่
void updateLineQuantity(int index, int quantity) {
  _draft = _draft.updateLine(index, quantity);
  _pendingCommandId = null;      // รหัสเดิมใช้กับเนื้อหานี้ไม่ได้แล้ว
  notifyListeners();
}

บทเรียนที่ควรจำ: รหัสคำสั่งผูกกับ เนื้อหา ของเจตนา ไม่ใช่แค่กับการกดปุ่ม — ทุกครั้งที่เนื้อหาเปลี่ยน รหัสต้องเปลี่ยนตาม และควรมีด่านที่เซิร์ฟเวอร์คอยจับถ้าเราทำผิด

11. สรุปท้ายบท

  • รหัสถูกสร้างตอนที่ผู้ใช้ตัดสินใจ ไม่ใช่ตอนยิงคำขอ
  • ส่งทาง header เพราะเป็นเรื่องของการส่ง ไม่ใช่ของธุรกิจ
  • สร้างรหัสนอกส่วนที่ถูกลองใหม่
  • เซิร์ฟเวอร์ควรบอกกลับมาว่าครั้งนี้ทำจริงหรือตอบผลเดิม
  • การเจอรหัสซ้ำไม่ใช่ความผิดพลาด
  • หนึ่งคำขอ หนึ่งรหัส และต้องสำเร็จทั้งหมดหรือไม่เลย
  • ตกลงระยะเวลาเก็บรหัสให้ครอบกรณีข้ามกะ
  • เนื้อหาเปลี่ยน รหัสต้องเปลี่ยน — และเซิร์ฟเวอร์ควรจับได้ถ้าเราลืม
  • ตรวจว่าผลที่ได้เป็นของคำขอนี้จริง
