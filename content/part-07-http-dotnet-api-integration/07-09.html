Status code ตอบว่า request จบแบบไหน: error payload ตอบรายละเอียด ห้ามพึ่งอย่างใดอย่างหนึ่งเพียงอย่างเดียว

1. กลุ่มสำคัญ

  • 400 validation/request ผิด
  • 401 token ไม่มีหรือใช้ไม่ได้
  • 403 ไม่มีสิทธิ์
  • 404 resource/route ไม่พบ
  • 409 conflict/สถานะเปลี่ยนแล้ว
  • 422 semantic validation
  • 429 rate limit
  • 500–599 server/proxy failure

2. Typed ApiException

throw ApiException(
  statusCode: response.statusCode,
  code: problem.code,
  userMessage: problem.detail ?? fallbackFor(status),
  correlationId: problem.traceId,
);

3. อ่าน body อย่างปลอดภัย

Error body อาจเป็น ProblemDetails, legacy map, plain text, HTML หรือว่าง จึง parse แบบ best effort และต้องมี fallback จาก status เสมอ

4. UI policy

409 อาจให้ refresh งาน, 401 ส่งไป login, 403 แสดงไม่มีสิทธิ์, 400 ชี้ field ที่ผิด, 500 ให้ลองใหม่พร้อม trace ID แต่ policy navigation ควรอยู่เหนือ transport layer

5. ห้ามใช้ message เป็น logic

อย่าเขียน if (message.contains('already')) ให้ server ส่ง stable machine code เช่น TASK_ALREADY_COMPLETED และ Flutter map เป็น enum/action

6. Preserve evidence

เก็บ status, safe error code, endpoint, elapsed time และ trace ID สำหรับ log โดย truncate/redact body ที่อาจมีข้อมูลสำคัญ

7. แบบฝึกหัด

404 จาก /tasks/T-1 กับ 404 จาก route พิมพ์ผิดต่างกันอย่างไร?

เฉลย

status เท่ากันแต่ error code/ProblemDetails และ contract ช่วยแยก resource missing จาก deployment/config path ผิด

8. หลักจำ

Status ขับ policy ระดับกว้าง, stable error code ขับ behavior เฉพาะ และข้อความมีไว้แสดง—not control flow
