ระดับ: กลางใช้เวลา: 25–35 นาทีลงมือทำ: ส่งข้อมูลกำกับคำขอให้ครบและไม่รั่ว
ต้องผ่านอะไรมาก่อน: 7.4 (GET และ POST)
จบบทนี้แล้วจะทำได้: ใส่ข้อมูลกำกับคำขอให้ถูก และรู้ว่าอะไรห้ามหลุดออกไปในบันทึก

1. ปัญหาที่บทนี้แก้

คำขอหนึ่งครั้งมีข้อมูลสองชุดที่เดินทางไปด้วยกัน

POST /api/WMS/mobile_tasks/T-001/complete
Content-Type: application/json          ┐
Authorization: Bearer eyJhbGci...       ├─ ข้อมูลกำกับ (header)
Idempotency-Key: cmd-8821               ┘

{"quantity": 12}                         ← เนื้อหา (body)

ความต่างคือ body เป็นเรื่องของธุรกิจ ส่วน header เป็นเรื่องของการส่ง

ถ้าเอาไปปนกันผลที่เกิด
ใส่ token ลงใน bodyทุก endpoint ต้องรับ field นี้ และมันจะไปโผล่ใน log ของธุรกิจ
ใส่จำนวนสินค้าไว้ใน headerเซิร์ฟเวอร์ต้องอ่านสองที่ และตรวจสอบยากขึ้น

2. คำศัพท์ที่ต้องรู้ก่อน

headerบอกอะไร
Content-Typebody ที่ส่งไปเป็นรูปแบบอะไร
Acceptอยากได้คำตอบเป็นรูปแบบอะไร
Authorizationบัตรผ่านที่บอกว่าเราเป็นใคร
Idempotency-Keyรหัสที่บอกว่าคำขอนี้คือเจตนาเดิม (4.14)
bearer tokenบัตรผ่านแบบที่ใครถือก็ใช้ได้

3. Mental model: ซองจดหมายกับจดหมาย

ซอง (header)     บอกว่าส่งถึงใคร ส่งจากใคร และเป็นจดหมายประเภทไหน
จดหมาย (body)    เนื้อหาที่อยากบอก
ประโยคเดียวที่ต้องจำ: ถ้าข้อมูลนั้นเปลี่ยนไปตามธุรกิจ ให้อยู่ใน body — ถ้ามันเหมือนกันทุก endpoint ให้อยู่ใน header

4. ชุดพื้นฐานใน lab

Map<String, String> _headers() => {
  'Content-Type': 'application/json',
  if (authToken != null) 'Authorization': 'Bearer $authToken',
};

สองบรรทัดนี้ทำให้ทุกที่ที่เรียก ApiClient ไม่ต้องรู้เรื่อง header เลย

สิ่งที่ได้เพราะ
ลืมใส่ token ไม่ได้ใส่ให้อัตโนมัติทุกคำขอ
เปลี่ยนรูปแบบ token ที่เดียวไม่ต้องไล่แก้ทุก repository
ปิดค่าตอนบันทึกได้ที่เดียวดูหัวข้อ 8

สังเกตว่า if อยู่ในตัว map เลย — ถ้ายังไม่ได้เข้าสู่ระบบ ก็ไม่มี header นี้ ไม่ใช่ส่งค่าว่างไป

// เลี่ยง — ส่ง "Bearer null" ไปให้ server งง
'Authorization': 'Bearer ${authToken ?? ""}',

5. Content-Type กับ Accept ไม่เหมือนกัน

Content-TypeAccept
พูดถึงสิ่งที่เราส่งไปสิ่งที่เราอยากได้กลับ
GET ต้องมีไหมไม่ต้อง เพราะไม่มี bodyใส่ได้
ถ้าผิดได้รหัส 415ได้รหัส 406 หรือได้รูปแบบที่ไม่ต้องการ

ในทางปฏิบัติ API ส่วนใหญ่ตอบเป็น JSON อยู่แล้ว การใส่ Accept จึงไม่ค่อยเปลี่ยนอะไร — แต่มีประโยชน์ในกรณีเดียวที่สำคัญ

Accept: application/json

เมื่อมีตัวกลางในเครือข่ายที่คืนหน้า HTML แทน (เช่นหน้าเข้าสู่ระบบขององค์กร) การประกาศไว้ชัดช่วยให้บางระบบตอบเป็น JSON แทน — และถ้ายังได้ HTML มาก็ยังจับได้จากการตรวจรูปแบบตาม 7.8

6. อ่าน token ตอนส่ง ไม่ใช่ตอนสร้าง

จุดที่ผิดง่ายและอาการดูเหมือนเรื่องอื่น

// เสี่ยง — จำ token ไว้ตั้งแต่ตอนสร้าง
class ApiClient {
  ApiClient({required this.token});
  final String token;              // ถ้า token เปลี่ยน ตัวนี้ยังใช้ของเก่า
}
// ที่ lab ทำ — อ่านค่าล่าสุดทุกครั้งที่ส่ง
String? authToken;

Map<String, String> _headers() => {
  ...
  if (authToken != null) 'Authorization': 'Bearer $authToken',
};
ถ้าจำ token ไว้ตั้งแต่ต้นอาการที่เห็น
ต่ออายุ token แล้วยังใช้ตัวเก่า ได้ 401 ทั้งที่เพิ่งต่ออายุ
ออกจากระบบแล้วยังยิงคำขอด้วย token เก่าได้
เข้าสู่ระบบด้วยคนใหม่ยังใช้สิทธิ์ของคนเก่า

แถวสุดท้ายอันตรายที่สุดบน PDA ที่เปลี่ยนมือทุกกะ — และเป็นเหตุผลที่ 5.4 ย้ำว่าการล้างหน้าจอไม่เท่ากับการออกจากระบบ

7. 401 กับ 403 ต้องทำคนละอย่าง

401403
แปลว่าไม่รู้ว่าคุณเป็นใครรู้ว่าเป็นใคร แต่ทำสิ่งนี้ไม่ได้
สาเหตุยังไม่ล็อกอิน หรือ token หมดอายุสิทธิ์ไม่พอ
ควรทำพาไปเข้าสู่ระบบใหม่บอกว่าไม่มีสิทธิ์ และให้ติดต่อหัวหน้า

การเหมารวมทั้งสองเป็น “ให้ล็อกอินใหม่” ทำให้เกิดอาการที่อธิบายยาก — คนหน้างานที่ไม่มีสิทธิ์ปรับยอด จะถูกเด้งออกจากระบบทุกครั้งที่กดปุ่มนั้น แล้วล็อกอินกลับเข้ามาก็เจอเหมือนเดิม

ใน lab แยกไว้แล้วตั้งแต่ชั้น ApiClient

ApiFailureKind failureKindForStatus(int statusCode) => switch (statusCode) {
  401 => ApiFailureKind.unauthorized,
  403 => ApiFailureKind.forbidden,
  ...
};

ส่วนการตัดสินใจว่าจะพาไปหน้าไหน เป็นเรื่องของชั้นบน ไม่ใช่ของ ApiClient ตามหลักใน 5.4

8. ห้ามให้ header หลุดออกไปในบันทึก

นี่คือเรื่องที่ผิดแล้วแก้ยากที่สุดในบทนี้ เพราะเมื่อ token หลุดไปอยู่ในไฟล์บันทึกแล้ว มันจะถูกคัดลอกต่อไปเรื่อย ๆ

// อันตราย — ทุก token ที่เคยใช้จะอยู่ในไฟล์นี้
logger.debug('request headers: $headers');

เปิด lib/core/api_log.dart

const Set<String> _sensitiveHeaders = {
  'authorization',
  'cookie',
  'set-cookie',
  'x-api-key',
};

Map<String, String> redactHeaders(Map<String, String> headers) => {
  for (final entry in headers.entries)
    entry.key: _sensitiveHeaders.contains(entry.key.toLowerCase())
        ? _masked
        : entry.value,
};
test('ปิดค่า header ที่อ่อนไหว ไม่สนตัวพิมพ์', () {
  final headers = redactHeaders({
    'Authorization': 'Bearer eyJhbGciOi...',
    'Content-Type': 'application/json',
  });

  expect(headers['Authorization'], 'REDACTED');
  expect(headers['Content-Type'], 'application/json');
});

สังเกตว่าเทียบด้วย toLowerCase() เพราะชื่อ header ไม่สนตัวพิมพ์ — Authorization กับ authorization คืออันเดียวกัน และการเทียบตรง ๆ จะพลาดตัวใดตัวหนึ่ง

และการปิดค่าอยู่ที่เดียวตรงนี้ ไม่ใช่ที่ทุกจุดที่บันทึก — จะได้ไม่มีทางลืม

9. header ที่ช่วยตอนมีปัญหา

headerประโยชน์
Idempotency-Keyบอกว่าคำขอนี้คือเจตนาเดิม (7.15)
traceId ที่ได้กลับมาใช้ตามหาคำขอนี้ใน log ฝั่งเซิร์ฟเวอร์
รุ่นของแอปรู้ว่าเครื่องที่มีปัญหาใช้แอปรุ่นไหน

ใน lab เห็น Idempotency-Key ได้ที่ task_repository.dart

final json = await api.postJson(
  '/api/WMS/mobile_tasks/$id/complete',
  const {},
  headers: {'Idempotency-Key': commandId},
);

สังเกตว่ามันอยู่ใน header ไม่ใช่ใน body — เพราะเป็นเรื่องของการส่ง ไม่ใช่เรื่องของธุรกิจ ตามหลักในหัวข้อ 3

ส่วน traceId เดินทางกลับมาใน ProblemDetails ซึ่งอ่านไว้แล้วใน api_failure.dart

/// รหัสที่ใช้ตามหาคำขอนี้ใน log ฝั่งเซิร์ฟเวอร์
final String? traceId;

การแสดงรหัสนี้บนหน้าจอเมื่อเกิดข้อผิดพลาด ทำให้คนหน้างานอ่านให้ทีมฟังได้ แล้วทีมตามหาใน log ได้ทันที แทนที่จะต้องเดาว่าเกิดตอนไหน

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
รหัส 415ไม่มี Content-Type หรือค่าผิดใส่ให้ครบที่ตัวกลาง
ได้ 401 ทั้งที่เพิ่งต่ออายุ tokenจำ token ไว้ตั้งแต่ตอนสร้างอ่านค่าล่าสุดตอนส่ง
ล็อกอินคนใหม่แล้วยังใช้สิทธิ์คนเก่าเหมือนข้างบนเหมือนข้างบน
ถูกเด้งออกทุกครั้งที่กดปุ่มหนึ่งเหมารวม 403 เป็น 401แยกสองรหัส
Bearer null ถูกส่งไปใส่ header เสมอแม้ไม่มี tokenใส่เฉพาะเมื่อมี
token อยู่ในไฟล์บันทึกบันทึก header ทั้งชุดปิดค่าที่ตัวกลางที่เดียว
ปิดค่าแล้วยังหลุดเทียบชื่อ header แบบสนตัวพิมพ์เทียบด้วยตัวเล็กทั้งหมด
เกิดปัญหาแล้วตามหาใน log ไม่เจอไม่ได้เก็บรหัสตามรอยแสดง traceId ให้ผู้ใช้เห็น

บทเรียนที่ควรจำ: บั๊กที่เกิดเฉพาะตอน “คนที่สองใช้ต่อจากคนแรก” ไม่มีทางเจอจากการทดสอบด้วยมือ เพราะไม่มีใครล็อกอินสองคนติดกัน — ต้องมีเทสต์ที่จำลองการเปลี่ยนมือโดยเฉพาะ

12. สรุปท้ายบท

  • header เป็นเรื่องของการส่ง ส่วน body เป็นเรื่องของธุรกิจ
  • รวม header พื้นฐานไว้ที่ตัวกลาง จะได้ไม่มีทางลืม
  • ใส่ Authorization เฉพาะเมื่อมี token จริง
  • อ่าน token ตอนส่ง ไม่ใช่จำไว้ตอนสร้าง
  • 401 พาไปล็อกอินใหม่ ส่วน 403 ห้ามแตะ session
  • ปิดค่า header ที่อ่อนไหวที่เดียว และเทียบชื่อแบบไม่สนตัวพิมพ์
  • รหัสคำสั่งอยู่ใน header ไม่ใช่ใน body
  • แสดงรหัสตามรอยให้ผู้ใช้เห็น เพื่อให้ตามหาใน log ได้
