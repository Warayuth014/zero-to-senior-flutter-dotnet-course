Flutter render UI บน main isolate งาน CPU ที่กินเวลานานทำให้ frame หลุด แม้ function จะประกาศ async การแยก isolate เหมาะกับ CPU-bound work ไม่ใช่ HTTP ที่ asynchronous อยู่แล้ว

1. CPU-bound กับ I/O-bound

งานตัวอย่างแนวทาง
I/O-boundHTTP, file wait, timerFuture/await ปกติ
CPU-boundparse JSON ใหญ่มาก, คำนวณ/บีบอัดภาพวัดก่อน แล้วใช้ isolate/compute

การย้าย request HTTP ไป isolate เพิ่ม complexity โดยแทบไม่ช่วย เพราะเวลาส่วนใหญ่คือรอ network

2. ใช้ compute สำหรับงานหนึ่งครั้ง

List<Task> parseTasks(String body) {
  final rows = jsonDecode(body) as List<Object?>;
  return rows
      .whereType<Map<String, dynamic>>()
      .map(Task.fromJson)
      .toList();
}

final tasks = await compute(parseTasks, response.body);

callback ควรเป็น top-level/static และ input-output ต้องส่งข้าม isolate ได้ อย่าส่ง BuildContext, controller, open socket หรือ object ที่ผูก native resource

3. Message passing ไม่แชร์ memory

แต่ละ isolate มี heap/event loop ของตัวเอง สื่อสารผ่าน message จึงลด shared-memory race แต่มีต้นทุน spawn/copy/transfer ข้อมูล งานเล็กหรือเรียกถี่อาจช้ากว่าทำตรง ๆ

4. Long-lived worker

ถ้างานหนักเกิดต่อเนื่อง การ spawn ทุกครั้งแพง สามารถสร้าง isolate ยาวด้วย ReceivePort/SendPort แต่ต้องออกแบบ request id, error, shutdown และ queue เอง เริ่มจาก compute และ profiling ก่อน

5. ใช้กับ WMS เมื่อใด

  • payload inventory หลายหมื่นแถวและ profiling ยืนยัน parse ทำ UI กระตุก
  • ย่อ/ประมวลผลรูปก่อน multipart upload
  • import/export/คำนวณชุดใหญ่บนอุปกรณ์

รายการ task/pallet ปกติไม่ควรรีบใส่ isolate แก้ pagination, lazy list และ payload size ก่อน

6. Web และ platform

implementation ของ concurrency ต่างตาม platform จึงต้องวัดบน target จริง โดยเฉพาะ PDA รุ่นต่ำ อย่าอ้างผลจาก desktop อย่างเดียว และแยก platform API ออกจาก pure parsing function เพื่อ test ได้

7. แบบฝึกหัด

หน้า inventory กระตุกหลัง response 5 MB จงเรียงขั้นตรวจและแก้

แนวคำตอบ
  1. ใช้ DevTools/profile build วัด network, decode, model mapping, setState และ list rendering
  2. ลด payload/pagination ที่ API
  3. ใช้ builder/lazy rendering
  4. ถ้า decode/mapping ยังเป็น CPU bottleneck ค่อยย้าย pure parser ไป compute
  5. วัด frame และ memory ซ้ำบน PDA

8. จุดพลาด

async ไม่ได้ย้ายงานไป background thread และ isolate ไม่สามารถแก้ widget rebuild มากเกินหรือ API payload ใหญ่โดยต้นเหตุได้
