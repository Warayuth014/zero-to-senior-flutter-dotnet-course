ต้องผ่านอะไรมาก่อน: D1.4 (ฟังก์ชัน), D1.9 (generic — เพราะ Future<T> คือ generic) และ D1.14 (exception)
จบบทนี้แล้วจะทำได้: อ่านและเขียน async/await ได้ถูกต้อง แยกได้ว่างานไหนควรรอต่อคิวและงานไหนควรยิงพร้อมกัน และกันไม่ให้ผู้ใช้กดปุ่มซ้ำจนเกิดรายการซ้ำ

1. ปัญหาที่บทนี้แก้

โค้ดทุกบรรทัดที่เขียนมาตั้งแต่ D1.1 ทำงานเสร็จทันที แต่งานจริงไม่เป็นแบบนั้น — การถาม server ว่าพาเลทนี้มีของกี่ชิ้นอาจใช้เวลา 300 มิลลิวินาที หรือ 5 วินาทีถ้าสัญญาณ WiFi ในคลังไม่ดี

คำถามคือระหว่างที่รอ โปรแกรมควรทำอะไร ถ้าเลือกผิด หน้าจอจะค้าง แตะไม่ได้ และผู้ใช้จะกดซ้ำจนเกิดรายการซ้ำในระบบ

4. โครงสร้างพื้นฐาน

Future<String> fetchPallet(String code) async {
  await Future<void>.delayed(const Duration(milliseconds: 300));
  return '$code โหลดเสร็จแล้ว';
}
ส่วนความหมาย
Future<String>สุดท้ายจะได้ข้อความ แต่ยังไม่ใช่ตอนนี้
asyncข้างในฟังก์ชันนี้มีการรอ
awaitหยุดฟังก์ชันนี้ไว้จนกว่างานจะเสร็จ
return '...'เขียนแค่ String ก็พอ Dart ห่อเป็น Future ให้เอง

กฎที่ต้องจำ: ใช้ await ได้เฉพาะในฟังก์ชันที่มี async เท่านั้น และเมื่อใส่ async แล้ว ชนิดที่คืนต้องเป็น Future เสมอ (ถ้าไม่คืนอะไรก็เป็น Future<void>)

5. เรียงทีละตัว หรือ ยิงพร้อมกัน

นี่คือการตัดสินใจที่ส่งผลต่อความเร็วของแอปมากที่สุดในบทนี้

// เรียงทีละตัว: ใช้เวลารวมกัน
final a = await fetchPallet('PAL-A');   // รอ 300ms
final b = await fetchPallet('PAL-B');   // แล้วรออีก 300ms
// รวม ~600ms

// ยิงพร้อมกัน: ใช้เวลาเท่าตัวที่ช้าที่สุด
final both = await Future.wait<String>([
  fetchPallet('PAL-A'),
  fetchPallet('PAL-B'),
]);
// รวม ~300ms

ผลจริงจาก lab แสดงความต่างชัดเจน

=== เรียงทีละตัว (sequential): ช้ากว่าเพราะรอต่อคิว ===
  [ 602ms] PAL-A (โหลดใน 300ms), PAL-B (โหลดใน 300ms)

=== ยิงพร้อมกัน (concurrent) ด้วย Future.wait ===
  [ 303ms] PAL-A (โหลดใน 300ms) + PAL-B (โหลดใน 300ms)

ตัวเลขบนเครื่องคุณจะไม่ตรงเป๊ะ แต่สัดส่วนจะเหมือนกันคือประมาณสองเท่า

ใช้แบบเรียงทีละตัวเมื่อใช้ Future.wait เมื่อ
ผลของงานแรกเป็นข้อมูลเข้าของงานที่สองงานทั้งสองไม่เกี่ยวข้องกัน
ลำดับมีความหมาย เช่น ตรวจสิทธิ์ก่อนบันทึกแค่ต้องการข้อมูลหลายชุดมาแสดงพร้อมกัน
มีผลข้างเคียงที่ชนกันได้เป็นการอ่านข้อมูลล้วน ๆ
อย่าใช้ Future.wait กับคำสั่งที่เปลี่ยนข้อมูล เช่นยืนยันการหยิบของหลายรายการพร้อมกัน เพราะถ้าตัวใดตัวหนึ่งล้มเหลว คุณจะไม่รู้ว่าตัวไหนสำเร็จไปแล้วบ้าง และย้อนกลับได้ยากมาก

6. จัดการข้อผิดพลาดและการหมดเวลา

try {
  await fetchPallet('PAL-BROKEN');
} on StateError catch (error) {
  print('จับได้: ${error.message}');
}

ข่าวดีคือ try/catch จาก D1.14 ใช้กับงาน async ได้เหมือนเดิมทุกประการ ขอแค่มี await อยู่ในบล็อก try

try {
  await fetchPallet('PAL-SLOW', ms: 2000)
      .timeout(const Duration(milliseconds: 400));
} on TimeoutException {
  print('เกินเวลา 400ms -> บอกผู้ใช้ว่าเครือข่ายช้า');
}
ความจริงที่ต้องเข้าใจเรื่อง timeout: การหมดเวลาแปลว่า เราเลิกรอ ไม่ได้แปลว่า server ไม่ได้ทำงาน — คำสั่งนั้นอาจสำเร็จไปแล้วก็ได้ ดังนั้นการลองใหม่อัตโนมัติกับคำสั่งที่บันทึกข้อมูลอาจสร้างรายการซ้ำ เรื่องนี้ต้องออกแบบร่วมกับฝั่ง .NET (ดูต่อใน Part 7)

7. กันการกดซ้ำ

ปัญหาที่พบทุกโปรเจกต์: ผู้ใช้กดปุ่มบันทึก ไม่เห็นอะไรเกิดขึ้นทันที เลยกดอีกสามครั้ง

class PalletLoader {
  bool _loading = false;

  Future<void> load(String code) async {
    if (_loading) {
      print('ปฏิเสธ $code เพราะกำลังโหลดอยู่');
      return;
    }
    _loading = true;
    try {
      final result = await fetchPallet(code);
      print('โหลดสำเร็จ: $result');
    } finally {
      _loading = false;   // ปลดล็อกเสมอ แม้จะพัง
    }
  }
}

สามจุดที่ต้องทำให้ครบ

  1. ตรวจสถานะ ก่อน เริ่มงาน แล้วออกไปเลยถ้ายังไม่ว่าง
  2. ตั้งสถานะเป็นไม่ว่าง ก่อน บรรทัด await แรก
  3. ปลดล็อกใน finally เพื่อไม่ให้ค้างเมื่อเกิดข้อผิดพลาด

ถ้าทำไม่ครบสามข้อ จะได้บั๊กที่ทดสอบเจอยากมาก เพราะบนเครื่องพัฒนาที่เน็ตเร็วจะไม่มีทางกดทันเลย แต่ในคลังที่สัญญาณอ่อนจะเกิดทุกวัน

8. สิ่งที่เปลี่ยนไประหว่างที่เรารอ

ความจริงที่สำคัญที่สุดของบทนี้: โค้ดหลัง await ทำงานใน “อนาคต” ซึ่งโลกอาจเปลี่ยนไปแล้ว

สิ่งที่อาจเกิดขึ้นระหว่างรอผลที่ตามมา
ผู้ใช้กดย้อนกลับออกจากหน้าจออัปเดตหน้าจอที่ไม่มีอยู่แล้ว → error
ผู้ใช้พิมพ์คำค้นใหม่ผลเก่ากลับมาทีหลังแล้วทับผลใหม่
ผู้ใช้ออกจากระบบข้อมูลของคนเก่าโผล่มาให้คนใหม่เห็น

ตอนนี้ยังไม่ต้องแก้อะไร เพราะเรายังไม่มีหน้าจอ แต่ให้จำอาการทั้งสามไว้ — Part 4 จะสอนวิธีป้องกันอย่างเป็นระบบ สิ่งที่ทำได้ตั้งแต่วันนี้คือ ตั้งคำถามทุกครั้งที่เขียน await ว่า “ถ้าตอนที่ผลกลับมา สถานการณ์เปลี่ยนไปแล้ว โค้ดบรรทัดถัดไปยังถูกต้องอยู่ไหม”

10. แบบฝึกหัด

เขียนฟังก์ชัน loadDashboard ที่

  1. โหลดข้อมูลผู้ใช้ก่อน เพราะต้องใช้รหัสคลังจากผู้ใช้ในขั้นถัดไป
  2. จากนั้นโหลด “รายการงาน” และ “จำนวนแจ้งเตือน” ซึ่งไม่เกี่ยวข้องกัน
  3. กำหนดเวลาสูงสุดรวม 2 วินาที ถ้าเกินให้แจ้งว่าเครือข่ายช้า
  4. ไม่ว่าจะสำเร็จหรือล้มเหลว ต้องพิมพ์ว่าโหลดจบแล้ว
ดูแนวคำตอบและเหตุผล
import 'dart:async';

Future<String> loadUser() async {
  await Future<void>.delayed(const Duration(milliseconds: 200));
  return 'BKK-DC';
}

Future<List<String>> loadTasks(String site) async {
  await Future<void>.delayed(const Duration(milliseconds: 300));
  return ['T-01', 'T-02'];
}

Future<int> loadAlerts(String site) async {
  await Future<void>.delayed(const Duration(milliseconds: 300));
  return 3;
}

Future<void> loadDashboard() async {
  final clock = Stopwatch()..start();
  try {
    final site = await loadUser();            // ต้องมาก่อน

    final results = await Future.wait<Object>([ // สองงานนี้ยิงพร้อมกันได้
      loadTasks(site),
      loadAlerts(site),
    ]).timeout(const Duration(seconds: 2));

    final tasks = results[0] as List<String>;
    final alerts = results[1] as int;
    print('คลัง $site: งาน ${tasks.length} รายการ, แจ้งเตือน $alerts');
  } on TimeoutException {
    print('เครือข่ายช้า กรุณาลองใหม่');
  } finally {
    print('โหลดจบใน ${clock.elapsedMilliseconds}ms');
  }
}

Future<void> main() => loadDashboard();
คลัง BKK-DC: งาน 2 รายการ, แจ้งเตือน 3
โหลดจบใน 518ms

สังเกตว่า 518ms ≈ 200 + 300 ไม่ใช่ 200 + 300 + 300

ทำไม loadUser ต้องแยกออกมา: เพราะ loadTasks และ loadAlerts ต้องใช้ค่า site ที่ได้จากมัน — นี่คือกรณีที่ลำดับมีความหมายจริง ไม่ใช่แค่ความเคยชิน

ทำไมสองงานหลังใช้ Future.wait: เพราะไม่เกี่ยวข้องกันและเป็นการอ่านข้อมูลล้วน ๆ ถ้าเขียน await เรียงกันจะใช้เวลา 800ms แทนที่จะเป็น 500ms — ต่างกัน 300ms ซึ่งผู้ใช้รู้สึกได้

จุดที่ต้องระวังในคำตอบนี้: Future.wait<Object> ทำให้ต้อง cast ผลลัพธ์กลับเอง ซึ่งเป็นจุดที่พลาดได้ ในโค้ดจริงมักใช้ record จาก D1.12 แทน

final (tasks, alerts) = await (loadTasks(site), loadAlerts(site)).wait;

เขียนแบบนี้ได้ทั้งความเร็วและชนิดที่ถูกต้อง โดยไม่ต้อง cast เลย — เป็นตัวอย่างที่ดีว่าความรู้จากบทก่อน ๆ มาบรรจบกันอย่างไร

ลองต่อ: เปลี่ยน loadAlerts ให้ใช้เวลา 3 วินาที แล้วสังเกตว่า timeout ทำงาน และ finally ยังพิมพ์ออกมาตามปกติ

11. สรุปท้ายบท

  • Future<T> คือใบรับของ ไม่ใช่ตัวข้อมูล
  • async ทำให้ฟังก์ชันคืน Future ส่วน await รอเอาค่าออกมา
  • async ไม่ได้สร้าง thread ใหม่และไม่ได้ทำให้เร็วขึ้น
  • ใช้ Future.wait เมื่องานไม่เกี่ยวข้องกันและเป็นการอ่านข้อมูล
  • timeout แปลว่าเราเลิกรอ ไม่ได้แปลว่า server ไม่ได้ทำงาน
  • กันการกดซ้ำด้วยธง 3 ขั้น: ตรวจก่อน ตั้งก่อน await ปลดใน finally
  • โลกอาจเปลี่ยนไปแล้วเมื่อโค้ดหลัง await ทำงาน
