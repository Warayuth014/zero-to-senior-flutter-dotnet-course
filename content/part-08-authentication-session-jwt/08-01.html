2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย

สองคำแรกมักถูกใช้สลับกัน แต่ตอบคนละคำถาม และ 7.5 แสดงให้เห็นแล้วว่าการสับสนสองอย่างนี้ทำให้ผู้ใช้ถูกเด้งออกจากระบบทุกครั้งที่กดปุ่มที่ไม่มีสิทธิ์

3. Mental model: แลกรหัสผ่านเป็นบัตรผ่าน

รหัสผ่าน  →  ใช้ครั้งเดียวตอนเข้าสู่ระบบ  →  ไม่เก็บไว้ที่ไหนเลย
token     →  ใช้ทุกคำขอหลังจากนั้น        →  เก็บไว้ แต่มีวันหมดอายุ
ประโยคเดียวที่ต้องจำ: รหัสผ่านผ่านแอปแค่ครั้งเดียวแล้วหายไป — ถ้าเจอรหัสผ่านถูกเก็บไว้ที่ไหน แปลว่ามีอะไรผิด

4. เส้นทางทั้งหมด

ผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่าน

    ▼  ตรวจว่ากรอกครบไหม                        ← ในเครื่อง ไม่ยิงคำขอ
    │
    ▼  POST /api/Authenticate/login             ← 7.4
    │      {"username": "...", "password": "..."}
    │
    ▼  .NET ตรวจกับฐานข้อมูลผู้ใช้

    │
    ▼  เก็บลงเครื่อง                             ← 8.5
    │

สังเกตลำดับสองขั้นก่อนสุดท้าย — เก็บลงเครื่องก่อน แล้วค่อยประกาศว่าเข้าสู่ระบบแล้ว ซึ่งเป็นการตัดสินใจที่จะอธิบายใน 8.5

6. ห้าอย่างที่ล้มเหลวได้ และต้องแยกกัน

สิ่งที่เกิดผู้ใช้ควรทำชนิดใน lab
ยังไม่ได้กรอกชื่อผู้ใช้กรอกให้ครบไม่ยิงคำขอเลย

บัญชีถูกระงับติดต่อหัวหน้าAccountNotAllowed
เน็ตหลุดตรวจสัญญาณแล้วลองใหม่LoginFailed ที่ลองใหม่ได้
คำตอบผิดรูปแบบแจ้งทีมโยน ApiException

เปิด lib/auth/auth_repository.dart

} on ApiException catch (error) {
  return switch (error.kind) {
    ApiFailureKind.unauthorized => const InvalidCredentials(),
    ApiFailureKind.forbidden => AccountNotAllowed(error.userMessage),
    _ => LoginFailed(error.kind, error.userMessage),
  };
}

สังเกตว่าใช้ kind ที่ 7.9 ทำไว้ — ไม่ได้อ่านข้อความหรือดูรหัสตัวเลขเอง

และสังเกตว่า ความล้มเหลวที่ผิดสัญญายังโยนออกไป ไม่ได้แปลงเป็นค่า เพราะเป็นเรื่องที่ทีมต้องแก้ ไม่ใช่เรื่องที่ผู้ใช้ทำอะไรได้ ตามหลักใน 7.10

7. ทำไมคืนค่าแทนการโยน

/// ผลของการพยายามเข้าสู่ระบบ
///
/// คืนค่าแทนการโยน เพราะ "รหัสผ่านผิด" เป็นเรื่องปกติที่เกิดทุกวัน
/// ไม่ใช่ข้อยกเว้น (7.10)
sealed class LoginOutcome {
  const LoginOutcome();
}
ถ้าโยนถ้าคืนค่า
ต้องจำว่าโยนอะไรได้บ้างเห็นจากชนิดว่ามีผลลัพธ์อะไรบ้าง
ลืมดักแล้วแอปพังswitch ต้องครบ
“รหัสผ่านผิด” กลายเป็นความผิดพลาดเป็นผลลัพธ์ปกติ

แถวสุดท้ายสำคัญที่สุด — คนหน้างานพิมพ์รหัสผ่านผิดทุกวัน การทำให้มันเป็น exception ทำให้หน้าจอแสดงเป็นสีแดงพร้อมคำว่า “เกิดข้อผิดพลาด” ทั้งที่ระบบทำงานถูกต้องทุกอย่าง

8. อย่าบอกว่าผิดตรงไหน

/// ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง
///
/// ไม่แยกว่าอันไหนผิด เพราะการบอกว่า "ไม่มีผู้ใช้นี้" ทำให้เดาชื่อผู้ใช้ได้
class InvalidCredentials extends LoginOutcome {
  const InvalidCredentials();
}
ถ้าบอกว่าคนที่ไม่ควรรู้ได้อะไร
“ไม่พบผู้ใช้นี้”รู้ว่าชื่อผู้ใช้ไหนมีอยู่จริง
“รหัสผ่านไม่ถูกต้อง”รู้ว่าเดาชื่อผู้ใช้ถูกแล้ว เหลือแค่รหัสผ่าน

ข้อความเดียวกันสำหรับทั้งสองกรณี ทำให้ไม่มีข้อมูลรั่วออกไป — และไม่ได้ทำให้ผู้ใช้จริงลำบาก เพราะเขารู้ชื่อผู้ใช้ของตัวเองอยู่แล้ว

เรื่องนี้ต้องตกลงกับฝั่งหลังบ้านด้วย เพราะถ้าเซิร์ฟเวอร์ส่งข้อความที่แยกสองกรณีมา แอปก็ไม่ควรเอามาแสดง

9. รหัสผ่านต้องไม่ไปโผล่ที่ไหน

ที่ที่รหัสผ่านห้ามไปอยู่เพราะ
ไฟล์บันทึกถูกส่งต่อได้ (7.17)
ที่เก็บข้อมูลในเครื่องไม่มีเหตุผลต้องเก็บ — token ทำหน้าที่แทนแล้ว
ข้อความผิดพลาดไปโผล่บนจอและใน log
query ใน URLไปโผล่ใน log ของทุกตัวกลาง

ใน lab รหัสผ่านปรากฏแค่สองที่

// 1. พารามิเตอร์ของเมธอด
Future<LoginOutcome> login({
  required String username,
  required String password,
  required String serverId,
});

// 2. body ของคำขอเดียว
final json = await api.postJson('/api/Authenticate/login', {
  'username': username,
  'password': password,
});

หลังจากนั้นไม่มีที่ไหนเก็บไว้อีกเลย — และเพราะ 7.17 ไม่บันทึก body มันจึงไม่ไปโผล่ในไฟล์บันทึกด้วย

ระวังการเก็บ TextEditingController ของช่องรหัสผ่านไว้นานเกินจำเป็น — ควร dispose เมื่อออกจากหน้าเข้าสู่ระบบตาม 3.12 ไม่ใช่เก็บไว้ที่ระดับแอป

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
รหัสผ่านผิดแสดงเป็นหน้าจอผิดพลาดสีแดงโยนแทนคืนค่าทำเป็นผลลัพธ์ปกติ
ข้อความบอกว่าไม่พบผู้ใช้แยกสองกรณีใช้ข้อความเดียวกัน
เน็ตหลุดแล้วบอกว่ารหัสผ่านผิดเหมารวมทุกความล้มเหลวแยกด้วย kind
รหัสผ่านอยู่ในไฟล์บันทึกบันทึก bodyไม่บันทึก body (7.17)
กดเข้าสู่ระบบรัว ๆ ได้หลายคำขอไม่กันการกดซ้ำธงกันซ้ำ (8.2)
คำตอบผิดรูปแบบแล้วแอปพังแบบอธิบายไม่ได้ไม่ตรวจสัญญาตรวจเหมือน endpoint อื่น

11. แบบฝึกหัด

ทีมได้สัญญาของ endpoint เข้าสู่ระบบมาจากฝั่งหลังบ้าน

POST /api/Authenticate/login
{"username": "somchai", "password": "..."}

// สำเร็จ
200 {"token": "eyJ...", "expiration": "2026-08-15T10:00:00Z"}

// รหัสผ่านผิด
401 {"title": "Unauthorized", "status": 401,
     "detail": "ไม่พบผู้ใช้ somchai ในระบบ"}

// บัญชีถูกระงับ
403 {"title": "Forbidden", "status": 403,
     "detail": "บัญชีนี้ถูกระงับ กรุณาติดต่อผู้ดูแล"}
  1. ระบุปัญหาของสัญญานี้
  2. เขียนสิ่งที่จะขอให้ฝั่งหลังบ้านแก้ พร้อมเหตุผล
  3. ตอบว่าระหว่างที่ยังไม่แก้ ฝั่งแอปควรทำอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ปัญหา

#ปัญหาความเสี่ยง
1detail ของ 401 บอกว่าไม่พบผู้ใช้ชื่อนั้นเดาชื่อผู้ใช้ที่มีอยู่จริงได้
2ไม่มี errorCode ที่ไม่เปลี่ยนต้องอ่านข้อความเพื่อแยกกรณี (7.9)
3ไม่มีชื่อผู้ใช้และ role ในคำตอบต้องแกะจาก token ซึ่งผูกกับชื่อ claim (8.3)

ปัญหาข้อ 1 ร้ายที่สุด และเป็นสิ่งที่คนเขียนฝั่งหลังบ้านมักทำด้วยความหวังดี — อยากให้ผู้ใช้รู้ว่าผิดตรงไหน

วิธีที่คนไม่หวังดีใช้ประโยชน์

ลองชื่อผู้ใช้ทีละชื่อ ด้วยรหัสผ่านมั่ว ๆ
  "ไม่พบผู้ใช้ somchai"     → ไม่มีคนนี้
  "ไม่พบผู้ใช้ somsri"      → ไม่มีคนนี้
  "รหัสผ่านไม่ถูกต้อง"       → มีคนนี้อยู่จริง ← ได้ข้อมูลแล้ว

พอรู้ว่ามีชื่อไหนอยู่จริง ก็เหลือแค่เดารหัสผ่านของชื่อนั้น ซึ่งง่ายกว่าเดาทั้งสองอย่างพร้อมกันมาก

  "username": "somchai",

เหตุผลที่จะอธิบาย

ขอเหตุผล
401 ใช้ข้อความเดียวไม่ให้เดาชื่อผู้ใช้ที่มีอยู่จริงได้
403 บอกรายละเอียดได้ผ่านการยืนยันตัวตนแล้ว จึงไม่ใช่การรั่วข้อมูล
มี errorCodeให้แอปตัดสินใจโดยไม่ต้องอ่านข้อความ (7.9)
ส่ง username และ rolesไม่ต้องผูกกับชื่อ claim ใน token

ความต่างระหว่าง 401 กับ 403 ในข้อนี้น่าสนใจ — 403 บอกรายละเอียดได้เพราะผู้ใช้พิสูจน์ตัวตนสำเร็จแล้ว การบอกว่าบัญชีถูกระงับจึงไม่ได้ให้ข้อมูลกับใครที่ไม่ควรรู้

ข้อ 3 — ระหว่างที่ยังไม่แก้

ฝั่งแอปทำได้สองอย่าง

อย่างที่หนึ่ง — ไม่เอาข้อความของ 401 มาแสดง

ApiFailureKind.unauthorized => const InvalidCredentials(),

สังเกตว่า lab ทิ้ง error.userMessage ไปเลยในกรณีนี้ ต่างจาก 403 ที่เอามาใช้

ApiFailureKind.forbidden => AccountNotAllowed(error.userMessage),

แล้วให้หน้าจอแสดงข้อความของเราเอง

case InvalidCredentials():
  _errorMessage = 'ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง';

อย่างที่สอง — อ่านข้อมูลผู้ใช้จาก token ไปก่อน

username: _readText(json['username']) ?? payload?.username ?? username_,
roles: _readRoles(json['roles']) ?? payload?.roles ?? const {},

อ่านจากคำตอบก่อน ถ้าไม่มีค่อยแกะจาก token — พอฝั่งหลังบ้านเพิ่ม field มาให้ โค้ดนี้จะใช้ค่าใหม่เองโดยไม่ต้องแก้

สิ่งที่ฝั่งแอปทำแทนไม่ได้

เรื่องทำไมแทนไม่ได้
การรั่วข้อมูลชื่อผู้ใช้เกิดที่เซิร์ฟเวอร์แล้ว — คนที่ยิงคำขอตรงก็เห็นข้อความนั้นอยู่ดี

การที่แอปไม่แสดงข้อความนั้น ช่วยเฉพาะกับคนที่ใช้แอปเท่านั้น — ใครที่ยิงคำขอด้วยเครื่องมืออื่นยังได้ข้อมูลไปเหมือนเดิม

นี่คือเหตุผลที่ต้องแก้ที่ต้นทาง และเป็นหลักเดียวกับ 6.12 — การตรวจฝั่งแอปคือประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย

12. สรุปท้ายบท

  • รหัสผ่านผ่านแอปครั้งเดียวแล้วหายไป ส่วน token อยู่ต่อจนหมดอายุ
  • คำตอบของการเข้าสู่ระบบต้องตรวจเหมือน JSON อื่นทุกประการ
  • คืนค่าแทนการโยน เพราะรหัสผ่านผิดเป็นเรื่องปกติ
  • แต่ความล้มเหลวที่ผิดสัญญายังต้องโยน
  • ใช้ kind จาก 7.9 แยกกรณี ไม่ใช่อ่านข้อความ
  • 401 ใช้ข้อความเดียว ส่วน 403 บอกรายละเอียดได้
  • รหัสผ่านต้องไม่ไปอยู่ในบันทึก ในที่เก็บ หรือใน URL
  • สิ่งที่รั่วที่เซิร์ฟเวอร์ ฝั่งแอปปิดให้ไม่ได้

บทถัดไป: 8.2 จะจัดโครงของชั้นที่ทำเรื่องนี้ และตอบว่าใครควรเป็นเจ้าของ token
