ระดับ: กลาง–สูงใช้เวลา: 25–35 นาทีลงมือทำ: รับมือกับการสลับเซิร์ฟเวอร์
ต้องผ่านอะไรมาก่อน: 8.6 (การเปิดแอป) และ 7.3 (ที่อยู่เซิร์ฟเวอร์)
จบบทนี้แล้วจะทำได้: ผูก session กับเซิร์ฟเวอร์ที่ออกมันมา และรู้ว่าทำไมการไม่ผูกทำให้เกิดอาการที่อธิบายไม่ได้

1. ปัญหาที่บทนี้แก้

ในแอปคลังจริง ที่อยู่เซิร์ฟเวอร์เปลี่ยนได้ ตามที่ 7.3 และ 5.11 ออกแบบไว้

เมื่อไหร่ที่เปลี่ยน
ทีมติดตั้งย้ายเครื่องไปสาขาอื่น
สลับระหว่างเซิร์ฟเวอร์ทดสอบกับของจริง
สาขาย้ายไปเซิร์ฟเวอร์ใหม่

ปัญหาคือ token ที่เก็บไว้เป็นของเซิร์ฟเวอร์เก่า แต่ถ้าไม่ได้บันทึกไว้ว่าเป็นของใคร แอปจะไม่รู้

เข้าสู่ระบบที่สาขา ก → เก็บ token ไว้
เปลี่ยนที่อยู่เป็นสาขา ข → เปิดแอป
  → อ่าน token เดิม → คิดว่ายังเข้าสู่ระบบอยู่
  → ยิงคำขอไปสาขา ข ด้วย token ของสาขา ก
  → ได้ 401 ทุกคำขอ
  → ผู้ใช้เห็น "เซสชันหมดอายุ" ทั้งที่เพิ่งเข้าสู่ระบบเมื่อเช้า

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
server profileชุดการตั้งค่าของเซิร์ฟเวอร์หนึ่งตัว
bindingการผูกของสองอย่างเข้าด้วยกัน
issuerผู้ออก token

3. Mental model: token เป็นของเซิร์ฟเวอร์ที่ออกมัน

token ของสาขา ก  →  ใช้ได้กับสาขา ก เท่านั้น
                  →  สาขา ข ไม่รู้จักและปฏิเสธ
ประโยคเดียวที่ต้องจำ: เก็บ token โดยไม่เก็บว่าเป็นของใคร ก็เหมือนเก็บกุญแจโดยไม่รู้ว่าเป็นกุญแจบ้านไหน

เปิด lib/auth/auth_session.dart

/// ของอีกสาขาได้ และ token ของสาขาหนึ่งใช้กับอีกสาขาไม่ได้ (8.11)
class AuthSession {
  ...
  /// ระบุว่า token นี้เป็นของเซิร์ฟเวอร์ไหน
  final String serverId;

และเพราะเป็น required ใน constructor จึงลืมใส่ไม่ได้

Future<LoginOutcome> login({
  required String username,
  required String password,

เป็นการแก้ปัญหาด้วยชนิดข้อมูล แทนที่จะแก้ด้วยวินัย — คนเขียนโค้ดใหม่จะถูกบังคับให้คิดเรื่องนี้ตั้งแต่บรรทัดแรก

5. ตรวจตอนเปิดแอป

เปิด lib/auth/session_store.dart

/// เก็บไว้ แปลว่ามีคนสลับเซิร์ฟเวอร์ และ token เก่าใช้ไม่ได้ (8.11)
Future<void> restore({required String currentServerId}) async {

  if (stored.serverId != currentServerId) {
    await _clearTo(AuthStatus.signedOut, reason: SignOutReason.serverChanged);

8.6 อธิบายแล้วว่าทำไมตรวจข้อนี้ก่อนตรวจอายุ — เพื่อให้ได้ข้อความที่ถูกต้อง

test('สลับเซิร์ฟเวอร์แล้ว token เก่าใช้ไม่ได้', () async {
  await saveSession(serverId: 'wh-01');
  final store = storeWithClock(now);

  await store.restore(currentServerId: 'wh-02');

  expect(store.status, AuthStatus.signedOut);
  expect(store.lastSignOutReason, SignOutReason.serverChanged);
  // token ของสาขาเก่าต้องไม่ถูกส่งต่อไปให้ ApiClient เลยแม้แต่ครั้งเดียว
  expect(tokens, [null]);
});

บรรทัดสุดท้ายสำคัญ — token ของเซิร์ฟเวอร์เก่าต้องไม่ถูกตั้งค่าแม้แต่ชั่วขณะ เพราะถ้าตั้งแล้วค่อยล้าง อาจมีคำขอยิงออกไปในช่วงนั้น

6. สลับระหว่างที่ใช้งานอยู่

การตรวจตอนเปิดแอปยังไม่พอ — ผู้ใช้สลับเซิร์ฟเวอร์ได้จากหน้าตั้งค่าตาม 5.11

Future<void> changeServer(ConnectionProfile next) async {
  // ออกจากระบบก่อน แล้วค่อยเปลี่ยนที่อยู่
  await sessionStore.signOut(reason: SignOutReason.serverChanged);

  apiClient.baseUrl = next.baseUrl;
  await profileStorage.save(next);
}
ลำดับเหตุผล
ออกจากระบบก่อนล้าง token และ store ทั้งหมด (8.8)
แล้วค่อยเปลี่ยนที่อยู่ไม่ให้มีช่วงที่ token เก่าคู่กับที่อยู่ใหม่

ถ้าสลับลำดับ จะเกิดช่วงสั้น ๆ ที่อันตราย

เปลี่ยนที่อยู่ก่อน → token เก่ายังอยู่
  → polling ที่ยังไม่ถูกหยุด ยิงไปเซิร์ฟเวอร์ใหม่ด้วย token เก่า
  → ได้ 401 → เรียก handleUnauthorized
  → ผู้ใช้เห็น "เซสชันหมดอายุ" แทนที่จะเป็น "เปลี่ยนเซิร์ฟเวอร์แล้ว"

ข้อความผิดทำให้ผู้ใช้ไม่รู้ว่าตัวเองเป็นคนทำให้เกิด

การสลับเซิร์ฟเวอร์ทำให้ออกจากระบบเสมอ ซึ่งเป็นผลข้างเคียงที่ผู้ใช้อาจไม่รู้

ตามหลักใน 5.8 — ถามเมื่อย้อนกลับไม่ได้ และบอกผลที่จะเกิดขึ้น

บรรทัดที่สองสำคัญเพราะมันตอบคำถามที่ผู้ใช้กำลังกังวลอยู่พอดี

8. เลือก serverId ให้ดี

ใช้อะไรเป็น serverIdปัญหา
ที่อยู่เต็ม เช่น http://192.168.1.50:5000เปลี่ยน IP แล้วถือว่าเป็นคนละเซิร์ฟเวอร์
ชื่อที่ผู้ใช้ตั้งเองตั้งซ้ำกันได้
รหัสที่ฝั่งหลังบ้านกำหนดดีที่สุด แต่ต้องขอ

แถวแรกเป็นสิ่งที่คนทำก่อนเพราะง่ายที่สุด — และมีปัญหาที่เจอจริง

เซิร์ฟเวอร์สาขาเดิม แต่ IP เปลี่ยนจาก DHCP (7.3)
  → serverId ไม่ตรง → บังคับให้ล็อกอินใหม่
  → ทั้งที่เป็นเซิร์ฟเวอร์เดียวกัน

ทางแก้คือขอให้ฝั่งหลังบ้านส่งรหัสประจำเซิร์ฟเวอร์มาในคำตอบของการเข้าสู่ระบบ

{
  "token": "eyJ...",
  "expiration": "2026-08-15T10:00:00Z",
  "serverId": "wh-bangna-prod"
}

หรืออ่านจาก claim iss ใน token ซึ่งบอกอยู่แล้วว่าใครเป็นคนออก

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ได้ 401 ทุกคำขอหลังย้ายสาขาไม่ผูก session กับเซิร์ฟเวอร์เก็บ serverId
บอกว่าหมดอายุทั้งที่เปลี่ยนเซิร์ฟเวอร์ตรวจอายุก่อนตรวจเซิร์ฟเวอร์สลับลำดับ (8.6)
สลับเซิร์ฟเวอร์แล้วยังยิงด้วย token เก่าเปลี่ยนที่อยู่ก่อนออกจากระบบออกก่อน แล้วค่อยเปลี่ยน
ผู้ใช้ไม่รู้ว่าสลับแล้วจะหลุดไม่ถามก่อนถามพร้อมบอกผล
ถูกบังคับให้ล็อกอินใหม่ทั้งที่ไม่ได้เปลี่ยนอะไรใช้ IP เป็นตัวระบุขอรหัสประจำเซิร์ฟเวอร์
ข้อมูลของสาขาเก่าโผล่มาไม่ล้าง store ตอนสลับออกจากระบบเต็มรูปแบบ (8.8)

10. แบบฝึกหัด

ทีมใช้ที่อยู่เต็มเป็น serverId แล้วได้รายงานสามอย่าง

#อาการ
1สาขาหนึ่งบ่นว่าต้องล็อกอินใหม่ทุกเช้าวันจันทร์
2ทีมทดสอบสลับระหว่างเซิร์ฟเวอร์ทดสอบกับของจริง แล้วเห็นข้อมูลปนกัน
3เครื่องที่ย้ายจากสาขา ก ไป ข ใช้งานไม่ได้เลยจนกว่าจะติดตั้งแอปใหม่
  1. อธิบายสาเหตุของแต่ละข้อ
  2. ระบุว่าข้อไหนแก้ได้ด้วยการเปลี่ยน serverId และข้อไหนไม่ใช่
  3. เขียนวิธีแก้ทั้งหมด
ดูแนวคำตอบและเหตุผล

ข้อ 1 — สาเหตุ

#สาเหตุ
1เซิร์ฟเวอร์ได้ IP ใหม่จากเราเตอร์หลังปิดสุดสัปดาห์ → serverId ไม่ตรง
2ไม่ใช่เรื่อง serverId — ดูข้อ 2
3มีอะไรที่ไม่ถูกล้างตอนสลับ และไม่ได้ผูกกับเซิร์ฟเวอร์

ข้อ 1 ตรงกับที่ 7.3 เตือนไว้ — คอมพิวเตอร์ที่รับ IP จากเราเตอร์จะได้ IP ใหม่ และวันจันทร์เช้าคือหลังจากปิดเครื่องมาสองวัน

ข้อ 2 — ข้อไหนแก้ได้ด้วย serverId

#แก้ด้วย serverId ได้ไหมเพราะ
1ได้ใช้รหัสที่ไม่เปลี่ยนตาม IP
2ไม่ได้เป็นเรื่องการล้าง store ไม่ใช่การระบุเซิร์ฟเวอร์
3ไม่ได้ทั้งหมดต้องดูว่าอะไรค้าง

ทำไมข้อ 2 ไม่ใช่

ถ้า serverId ทำงานถูกต้อง การสลับเซิร์ฟเวอร์จะทำให้ออกจากระบบและล้าง session — แต่ ข้อมูลที่โหลดมาแล้วอยู่ใน store ซึ่งเป็นคนละเรื่อง

สลับเซิร์ฟเวอร์ → session ถูกล้าง (serverId ทำงานถูก)
  → แต่ TaskStore ยังถือรายการงานของเซิร์ฟเวอร์เก่า
  → ล็อกอินที่เซิร์ฟเวอร์ใหม่ → เห็นรายการเก่าจนกว่าจะโหลดทับ

ซึ่งเป็นปัญหาเดียวกับ 8.8 แบบฝึกหัด — store ที่มีอายุยาวกว่า session

ข้อ 3 — วิธีแก้ทั้งหมด

แก้ข้อ 1

// ขอรหัสประจำเซิร์ฟเวอร์จากฝั่งหลังบ้าน
{
  "token": "eyJ...",
  "expiration": "...",
  "serverId": "wh-bangna-prod"     // ไม่เปลี่ยนตาม IP
}

และถ้าฝั่งหลังบ้านยังไม่พร้อม ใช้ค่าที่ทีมติดตั้งกรอกเองไปก่อนได้

class ConnectionProfile {
  final String id;          // ทีมติดตั้งตั้ง เช่น "bangna"
  final String baseUrl;     // เปลี่ยนได้โดยไม่กระทบ id
}

แยก ตัวระบุ ออกจาก ที่อยู่ ทำให้เปลี่ยน IP ได้โดยไม่ถือว่าเป็นคนละเซิร์ฟเวอร์ — และตรงกับที่ 7.3 แนะนำว่าควรตั้ง IP คงที่อยู่แล้ว

แก้ข้อ 2

Future<void> changeServer(ConnectionProfile next) async {
  await sessionStore.signOut(reason: SignOutReason.serverChanged);
  // signOut ทำลาย SignedInScope ทั้งหมด รวม TaskStore (8.8)

  apiClient.baseUrl = next.baseUrl;
  await profileStorage.save(next);
}

ต้องมั่นใจว่า signOut ทำลาย store ทุกตัวที่ถือข้อมูล ไม่ใช่แค่ล้าง token

แก้ข้อ 3

อาการ “ต้องติดตั้งแอปใหม่” แปลว่ามีอะไรที่ล้างด้วยวิธีปกติไม่ได้

สิ่งที่น่าจะค้างทำไมล้างไม่ได้
ที่อยู่เซิร์ฟเวอร์เก่าไม่มีทางแก้ในแอปถ้าหน้าตั้งค่าเข้าไม่ถึง
ร่างงานของสาขาเก่าผูกกับผู้ใช้ แต่ไม่ผูกกับเซิร์ฟเวอร์
รูปที่รอส่ง (8.10)เหมือนกัน

แถวแรกน่าจะเป็นสาเหตุหลัก — ถ้าแอปเข้าหน้าตั้งค่าได้เฉพาะหลังล็อกอิน และล็อกอินไม่ได้เพราะที่อยู่ผิด ก็ติดวน

// ทางแก้ — ให้เข้าหน้าตั้งค่าได้จากหน้าเข้าสู่ระบบ
LoginScreen(
  actions: [
    TextButton(
      onPressed: _openServerSettings,     // เข้าได้โดยไม่ต้องล็อกอิน
      child: const Text('ตั้งค่าเซิร์ฟเวอร์'),
    ),
  ],
)

และแถวที่สองกับสามแก้ด้วยการผูกกับเซิร์ฟเวอร์ด้วย ไม่ใช่แค่ผูกกับผู้ใช้

await draftStorage.save(
  serverId: session.serverId,      // เพิ่มเข้าไป
  userId: session.username,
  draft: draft,
);

บทเรียนที่ควรจำ: อาการที่ต้อง “ติดตั้งแอปใหม่” ถึงจะหาย เกือบทุกครั้งแปลว่ามีสถานะที่ผู้ใช้แก้เองไม่ได้ — และทางแก้มักไม่ใช่การเพิ่มปุ่มล้างข้อมูล แต่คือการทำให้เข้าถึงหน้าที่แก้ได้ตั้งแต่ก่อนล็อกอิน

11. สรุปท้ายบท

  • token เป็นของเซิร์ฟเวอร์ที่ออกมัน ต้องเก็บว่าเป็นของใคร
  • ทำให้ serverId เป็น required จะได้ลืมไม่ได้
  • ตรวจตอนเปิดแอป ก่อนตรวจอายุ
  • token ของเซิร์ฟเวอร์เก่าต้องไม่ถูกตั้งค่าแม้แต่ชั่วขณะ
  • สลับระหว่างใช้งาน ต้องออกจากระบบก่อนเปลี่ยนที่อยู่
  • ถามผู้ใช้ก่อน และบอกว่าจะเกิดอะไร
  • อย่าใช้ที่อยู่เป็นตัวระบุ เพราะ IP เปลี่ยนได้
  • แยกตัวระบุออกจากที่อยู่
