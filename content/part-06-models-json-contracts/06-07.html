ระดับ: กลางใช้เวลา: 25–35 นาทีลงมือทำ: รองรับชื่อคีย์สองแบบโดยไม่ให้ลามทั้งโปรเจกต์
ต้องผ่านอะไรมาก่อน: 6.2 (ตัวช่วยอ่านค่ากลาง) และ 6.4 (การแยกไม่มีคีย์ออกจากค่า null)
จบบทนี้แล้วจะทำได้: รองรับ endpoint ที่ตั้งชื่อคีย์คนละแบบ โดยเก็บความยุ่งไว้ที่เดียวและถอดออกได้ในภายหลัง

1. ปัญหาที่บทนี้แก้

ระบบที่มีอายุมักมี endpoint สองรุ่นอยู่พร้อมกัน

// endpoint ใหม่
{"id": "T-001", "palletCode": "PAL-0101"}

// endpoint เก่าที่ยังมีคนใช้อยู่
{"Id": "T-001", "PalletCode": "PAL-0101"}

ทางแก้ที่คนทำก่อนคือเขียนสองทางไว้ในทุก model

id: (json['id'] ?? json['Id']) as String,
palletCode: (json['palletCode'] ?? json['PalletCode']) as String,
quantity: (json['quantity'] ?? json['Quantity']) as int,
ปัญหาที่ตามมา
ต้องเขียนซ้ำในทุก field ของทุก model
ลืมสักที่หนึ่งแล้วพังเฉพาะ endpoint เก่า ซึ่งอาจไม่มีใครทดสอบ
วันที่เซิร์ฟเวอร์เลิกส่งแบบเก่าแล้ว ไม่มีใครกล้าลบ เพราะไม่รู้ว่าลบได้หรือยัง

4. รวมไว้ในตัวอ่านกลาง

เปิด lib/json_basics/json_read.dart

/// อ่านค่าดิบ โดยลองทั้ง camelCase และ PascalCase
///
/// ASP.NET รุ่นใหม่ส่ง camelCase แต่ระบบเก่าอาจส่ง PascalCase
/// การรองรับทั้งสองแบบไว้ที่เดียวทำให้ model ทุกตัวไม่ต้องรู้เรื่องนี้
Object? _raw(Map<String, dynamic> json, String key) {
  if (json.containsKey(key)) return json[key];
  final pascal = key[0].toUpperCase() + key.substring(1);
  if (json.containsKey(pascal)) return json[pascal];
  return _absent;
}

ผลคือ model ทุกตัวเขียนเหมือนเดิมทุกอย่าง

id: requireString(json, 'id', path: path),          // ได้ทั้ง id และ Id
palletCode: requireString(json, 'palletCode', path: path),

และเทสต์ยืนยันว่าไฟล์ตัวอย่างที่เป็น PascalCase ทั้งก้อน อ่านได้เหมือนกัน

test('รับ PascalCase จากระบบเก่าได้ด้วย', () {

5. ลำดับสำคัญ: ชื่อที่ต้องการต้องชนะ

{"note": null, "Note": "ของแตก"}
วิธีได้อะไรถูกไหม

กรณีนี้ฟังดูแปลก แต่เกิดจริงตอนที่ฝั่งเซิร์ฟเวอร์กำลังย้ายระบบและส่งทั้งสองคีย์มาชั่วคราว — ถ้าค่าไม่ตรงกัน คีย์ใหม่คือคีย์ที่ควรเชื่อ เพราะเป็นตัวที่กำลังจะอยู่ต่อ

และควรบันทึก log ไว้เมื่อเจอทั้งสองคีย์ที่มีค่าต่างกัน เพราะนั่นแปลว่าฝั่งเซิร์ฟเวอร์มีปัญหาที่ต้องแก้

6. อย่าไล่หาแบบไม่สนตัวพิมพ์

// เลี่ยง
Object? findIgnoreCase(Map<String, dynamic> json, String key) {
  for (final entry in json.entries) {
    if (entry.key.toLowerCase() == key.toLowerCase()) return entry.value;
  }
  return null;
}
ปัญหารายละเอียด
ช้าต้องวนทุกคีย์ในทุก field ของทุกแถว
ซ่อนคำสะกดผิดถ้าเซิร์ฟเวอร์ส่ง "palletcode" มาโดยผิด จะผ่านไปเงียบ ๆ
ไม่รู้ว่ารองรับอะไรอยู่อ่านโค้ดแล้วไม่เห็นว่ารับชื่อแบบไหนได้บ้าง

การรองรับสองแบบที่ระบุชัด ดีกว่าการรองรับทุกแบบที่ไม่ระบุ — เพราะสิ่งที่ไม่ได้ตั้งใจรองรับ ควรพัง

7. ทางที่ดีกว่าคือแก้ที่ต้นทาง

การรองรับสองชื่อเป็นทางผ่าน ไม่ใช่ปลายทาง

ฝั่ง .NET กำหนดกติกาการตั้งชื่อได้ที่เดียวทั้งโปรเจกต์

// ฝั่ง server (แนวคิด — รายละเอียดอยู่ในคอร์ส .NET)
builder.Services.ConfigureHttpJsonOptions(options =>
{
    options.SerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
});

เมื่อทุก endpoint ใช้กติกาเดียวกันแล้ว ฝั่งแอปก็ถอดตัวสำรองออกได้

ขั้นตอนการถอด
1. บันทึก log ทุกครั้งที่ต้องใช้ชื่อแบบเก่า
2. ดูว่ายังมี endpoint ไหนเหลืออยู่
3. ตามไปแก้ฝั่งเซิร์ฟเวอร์ทีละตัว
4. เมื่อไม่มี log มาแล้วสักระยะ จึงลบตัวสำรองออก

ถ้าไม่มีขั้นที่หนึ่ง จะไม่มีวันถึงขั้นที่สี่ — เพราะไม่มีใครกล้าลบสิ่งที่ไม่รู้ว่ายังมีคนใช้หรือเปล่า

การรองรับสองชื่อโดยไม่มีแผนถอด จะกลายเป็นหนี้ถาวร และวันหนึ่งจะมีคนเพิ่มชื่อที่สามเข้ามาเพราะ “ก็มีสองชื่ออยู่แล้วนี่”

8. เมื่อชื่อต่างกันมากกว่าตัวพิมพ์

บางครั้งชื่อคีย์เปลี่ยนไปเลย ไม่ใช่แค่ตัวพิมพ์

// เก่า
{"qty": 12, "loc": "A-01"}

// ใหม่
{"quantity": 12, "locationCode": "A-01"}

กรณีนี้ใส่ในตัวอ่านกลางไม่ได้ เพราะเดาไม่ได้ — ต้องระบุที่ model

/// รองรับชื่อคีย์เก่าของ endpoint /api/v1/tasks
///
/// endpoint v2 ใช้ชื่อเต็มแล้ว — ลบเมื่อ v1 ถูกปิด (คาดว่า Q4 2026)
int _readQuantity(Map<String, dynamic> json, String path) {
  if (hasKey(json, 'quantity')) return requireInt(json, 'quantity', path: path);
  return requireInt(json, 'qty', path: path);
}

สิ่งที่ทำให้แบบนี้ยอมรับได้

ต้องมีเพราะ
อยู่ใน model ที่เกี่ยวข้องเท่านั้นไม่ลามไป model อื่นที่ไม่มีปัญหานี้
เขียนว่าเป็นของ endpoint ไหนรู้ว่าจะลบได้เมื่อไหร่
เขียนว่าคาดว่าจะลบเมื่อไหร่มีวันหมดอายุ

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
พังเฉพาะ endpoint เก่าลืมใส่ทางสำรองบาง fieldรวมไว้ในตัวอ่านกลาง
ค่าที่ตั้งใจล้าง กลับได้ค่าเก่าใช้ ?? แทน containsKeyเช็กการมีอยู่ของคีย์
คำสะกดผิดของเซิร์ฟเวอร์ผ่านไปได้ไล่หาแบบไม่สนตัวพิมพ์ระบุชื่อที่รองรับให้ชัด
แอปช้าลงเมื่อรายการยาววนหาคีย์ทุกครั้งใช้ containsKey ที่เร็วกว่า
ทางสำรองอยู่มาสามปีแล้วไม่มีใครกล้าลบไม่มี log ว่ายังใช้อยู่ไหมบันทึกทุกครั้งที่ใช้
มีชื่อที่สามและสี่โผล่มาเรื่อย ๆไม่มีแผนถอดแก้ที่ต้นทาง

10. แบบฝึกหัด

แอปต้องต่อกับ endpoint สองตัวที่ให้ข้อมูลพาเลทเหมือนกัน

// /api/v2/pallets — ตัวใหม่
{"palletCode": "PAL-0101", "locationCode": "A-01", "totalWeight": 245.5}

// /api/v1/pallets — ตัวเก่าที่ยังมีสองสาขาใช้อยู่
{"PalletCode": "PAL-0101", "Loc": "A-01", "Weight": 245.5}
  1. แยกว่าความต่างข้อไหนแก้ได้ที่ตัวอ่านกลาง และข้อไหนต้องแก้ที่ model
  2. เขียนโค้ดสำหรับส่วนที่ต้องแก้ที่ model
  3. ตอบว่าจะรู้ได้อย่างไรว่าลบทางสำรองได้แล้ว
ดูแนวคำตอบและเหตุผล

ข้อ 1 — แยกสองประเภท

ความต่างประเภทแก้ที่
palletCode ↔ PalletCodeแค่ตัวพิมพ์ตัวอ่านกลาง — ทำอยู่แล้ว
locationCode ↔ Locคนละชื่อmodel
totalWeight ↔ Weightคนละชื่อmodel

เกณฑ์แยกคือ เดาชื่ออีกแบบได้จากชื่อที่มีหรือไม่ — PalletCode เดาได้จาก palletCode ด้วยกฎเดียว แต่ Loc เดาจาก locationCode ไม่ได้

ข้อ 2 — โค้ดฝั่ง model

class PalletDto {
  const PalletDto({
    required this.palletCode,
    required this.locationCode,
    required this.totalWeight,
  });

  factory PalletDto.fromJson(Map<String, dynamic> json, {String path = ''}) =>
      PalletDto(
        // ตัวพิมพ์ต่างกัน — ตัวอ่านกลางจัดการให้แล้ว
        palletCode: requireString(json, 'palletCode', path: path),
        locationCode: _readLocationCode(json, path),
        totalWeight: _readTotalWeight(json, path),
      );

  final String palletCode;
  final String locationCode;
  final double totalWeight;

  /// v1 ใช้ชื่อ Loc — ลบเมื่อสาขาที่เหลือย้ายไป v2 หมดแล้ว
  static String _readLocationCode(Map<String, dynamic> json, String path) {
    if (hasKey(json, 'locationCode')) {
      return requireString(json, 'locationCode', path: path);
    }
    _logLegacyKey('pallets', 'Loc');
    return requireString(json, 'loc', path: path);
  }

  /// v1 ใช้ชื่อ Weight — ลบพร้อมกับ Loc
  static double _readTotalWeight(Map<String, dynamic> json, String path) {
    if (hasKey(json, 'totalWeight')) {
      return requireDouble(json, 'totalWeight', path: path);
    }
    _logLegacyKey('pallets', 'Weight');
    return requireDouble(json, 'weight', path: path);
  }
}

สังเกตว่าเรียก requireString(json, 'loc', ...) ด้วยตัวเล็ก — เพราะตัวอ่านกลางจะลอง Loc ให้เองอยู่แล้ว ไม่ต้องเขียนสองชื่อซ้ำอีก

และเรียก _logLegacyKey ก่อนอ่านทุกครั้ง ซึ่งเป็นคำตอบของข้อ 3

ข้อ 3 — จะรู้ได้อย่างไรว่าลบได้แล้ว

คำตอบที่หลายคนให้คือ “ถามทีมหลังบ้าน” ซึ่งไม่พอ เพราะทีมหลังบ้านรู้ว่า endpoint ไหนยังเปิดอยู่ แต่ไม่รู้ว่ายังมีเครื่องไหนเรียกอยู่

สิ่งที่ต้องมีคือข้อมูลจากของจริง

void _logLegacyKey(String endpoint, String key) {
  // ส่งเป็นเหตุการณ์นับจำนวน ไม่ใช่ log ทุกครั้งที่อ่าน
  // ไม่งั้นรายการ 200 แถวจะสร้าง log 200 บรรทัด
  telemetry.count('json.legacy_key', tags: {
    'endpoint': endpoint,
    'key': key,
    'appVersion': appVersion,
  });
}

ดูอะไรบอกอะไร

มาจากรุ่นแอปไหนถ้ามาจากรุ่นเก่าอย่างเดียว รอให้อัปเดตแล้วลบได้

เงื่อนไขเหตุผล
ไม่มีเหตุการณ์นี้เลยติดต่อกันนานพอนานพอต้องครอบรอบการทำงานที่ยาวที่สุด เช่นงานปิดบัญชีรายเดือน
ยืนยันกับหลังบ้านว่า v1 ถูกปิดแล้วกันกรณีที่มีคนเรียกนาน ๆ ครั้ง
แอปรุ่นที่ยังใช้ทางสำรอง หมดอายุแล้วPDA บางเครื่องไม่ได้อัปเดตนานมาก

ข้อสุดท้ายสำคัญเป็นพิเศษกับ PDA — เครื่องที่อยู่ในคลังอาจไม่ได้อัปเดตแอปเป็นปี ต่างจากโทรศัพท์ที่อัปเดตเอง

ข้อสังเกตสุดท้าย: ทางสำรองที่ไม่มีวิธีวัดว่ายังถูกใช้อยู่หรือไม่ จะอยู่ตลอดไป — การเพิ่มทางสำรองกับการเพิ่มวิธีวัด ต้องทำพร้อมกันเสมอ ไม่ใช่ทำอันแรกแล้วบอกว่าเดี๋ยวค่อยทำอันหลัง

11. สรุปท้ายบท

  • ความรู้เรื่องชื่อคีย์ควรอยู่ที่ตัวอ่านกลาง ไม่กระจายไปทุก model
  • ความต่างที่เดาได้จากกฎเดียว แก้ที่ตัวอ่านกลาง
  • ความต่างที่เดาไม่ได้ ต้องระบุที่ model ของ endpoint นั้น
  • ใช้ containsKey ไม่ใช่ ?? เพื่อไม่ให้ค่าที่ตั้งใจเป็น null ถูกแทน
  • ชื่อที่ต้องการต้องชนะเสมอเมื่อมีทั้งสองคีย์
  • อย่าไล่หาแบบไม่สนตัวพิมพ์ เพราะซ่อนคำสะกดผิดและช้า
  • ทางที่ดีที่สุดคือแก้กติกาการตั้งชื่อที่ฝั่งเซิร์ฟเวอร์
  • ทางสำรองต้องมาพร้อมวิธีวัดว่ายังถูกใช้อยู่หรือไม่ ไม่งั้นจะลบไม่ได้ตลอดไป
