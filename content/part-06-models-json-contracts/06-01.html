DTO สะท้อน wire contract, domain model สะท้อนกฎธุรกิจ, UI model สะท้อนสิ่งที่หน้าจอต้อง render การแยกชั้นช่วยไม่ให้ชื่อ JSON/null จาก API แพร่ทั่วแอป

1. DTO

รับ field ตาม API แม้ nullable/ชื่อไม่สวย และ parseอย่าง defensive

2. Domain

ใช้ชนิดที่รักษา invariant เช่น TaskId, Quantity, TaskStatus และไม่มี BuildContext

3. UI model

รวม title, badge, enabled ที่ deriveแล้ว แต่ไม่ทำ HTTP

4. Mapping

Task toDomain(TaskDto d) => Task(id: d.id, status: parseStatus(d.status));

5. เมื่อไม่ต้องแยก

CRUDเล็ก contractเสถียรอาจใช้ modelเดียว แต่บันทึก trade-off

6. WMS

Repositoryควรแปลง API DTOก่อนส่ง WarehouseStore ไม่ให้ UIรู้ PascalCase/fallback keys

7. แบบฝึกหัด

DTO qty nullableแต่ domainห้าม null ทำที่ไหน?

เฉลย

Mapper validate/rejectหรือใช้ defaultที่ contractรับรอง ไม่ซ่อน nullเป็น 0โดยเดา

8. จุดพลาด

อย่าสร้าง God modelหนึ่งตัวมี JSON, mutable UI stateและbusiness methodsทั้งหมด
