1. ปัญหาที่บทนี้แก้

โค้ดที่ดูปลอดภัยแล้ว

quantity: json['quantity'] as int,

พังในสามกรณีที่เกิดจริงทั้งหมด

เซิร์ฟเวอร์ส่งเกิดอะไรทำไมเซิร์ฟเวอร์ส่งแบบนั้น
12ผ่านปกติ
12.0พังฝั่ง .NET ประกาศเป็น decimal หรือ double

สองแถวล่างเป็นเรื่องปกติมากในระบบที่ต่อกับของเดิม และไม่ใช่ความผิดของใคร — เป็นแค่ความจริงที่ต้องรับมือ

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย

invariant cultureรูปแบบตัวเลขมาตรฐานที่ใช้จุดเป็นทศนิยม
precisionความละเอียดของตัวเลขที่เก็บได้

3. Mental model: JSON ไม่รู้จัก int กับ double

ใน JSON มีแค่ "number" ชนิดเดียว

{"quantity": 12}     ← Dart อ่านได้เป็น int
{"quantity": 12.0}   ← Dart อ่านได้เป็น double
                       แต่ในสายตา JSON มันคือเลขเดียวกัน
ประโยคเดียวที่ต้องจำ: ชนิดที่ Dart อ่านได้ ขึ้นกับว่าเซิร์ฟเวอร์เขียนจุดทศนิยมมาหรือเปล่า ซึ่งเป็นเรื่องที่เราควบคุมไม่ได้ — จึงต้องรับได้ทั้งสองแบบเสมอ

และตัวที่ทำให้ยากขึ้นอีกชั้นคือ as ไม่ได้แปลงค่า มันแค่ตรวจ

final value = 12.0;
value as int;      // พัง — ไม่ได้แปลงให้ แค่บอกว่าไม่ใช่

5. จำนวนเต็มต้องเข้มกว่า

/// จำนวนชิ้นต้องเป็นจำนวนเต็ม
///
/// รับ 5 และ 5.0 เพราะเป็นจำนวนเต็มเท่ากัน แต่ปฏิเสธ 1.9
/// การปัดเศษเงียบ ๆ ในงานคลังคือของหายหรือของเกิน
int requireInt(Map<String, dynamic> json, String key, {String path = ''}) {
  final value = _require(json, key, path);
  final parsed = _toDouble(value);
  if (parsed == null) {
    throw ContractException(
      _at(path, key),
      'ต้องเป็นตัวเลข แต่ได้ ${value.runtimeType} ($value)',
    );
  }
  if (parsed != parsed.roundToDouble()) {
    throw ContractException(_at(path, key), 'ต้องเป็นจำนวนเต็ม แต่ได้ $value');
  }
  return parsed.toInt();
}

บรรทัด parsed != parsed.roundToDouble() คือหัวใจ — มันแยก “เขียนคนละแบบ” ออกจาก “เป็นคนละค่า”

ค่าที่ได้ผลลัพธ์เหตุผล
12ผ่าน → 12จำนวนเต็มอยู่แล้ว
12.0ผ่าน → 12ค่าเดียวกัน เขียนคนละแบบ
"12"ผ่าน → 12ค่าเดียวกัน เขียนคนละแบบ
1.9ปฏิเสธไม่ใช่จำนวนเต็ม — ไม่รู้ว่าที่ถูกคือ 1 หรือ 2

ไล่หาสาเหตุย้อนหลังเป็นสัปดาห์รู้ทันทีว่างานไหน field ไหน

7. เลขที่เป็นรหัส ต้องเป็นข้อความเสมอ

{"barcode": 0012345678}    ← อันตราย
ปัญหาผลที่เกิด
ศูนย์นำหน้าหาย0012345678 กลายเป็น 12345678 — สแกนไม่เจอ
เลขยาวเกินบาร์โค้ด 18 หลักเกินความละเอียดที่เก็บได้แม่น
ถูกเอาไปคำนวณบวกลบรหัสสินค้าไม่มีความหมาย แต่โค้ดทำได้

เกณฑ์ที่ใช้ตัดสิน — ถามว่า เอาไปบวกลบแล้วมีความหมายไหม

ข้อมูลบวกลบมีความหมายควรเป็น
จำนวนชิ้นมีตัวเลข
น้ำหนักมีตัวเลข
รหัสพาเลทไม่มีข้อความ
บาร์โค้ดไม่มีข้อความ
เลขที่ใบรับเข้าไม่มีข้อความ

ถ้าเซิร์ฟเวอร์ส่งรหัสมาเป็นตัวเลขอยู่แล้ว ให้แปลงเป็นข้อความที่ขอบทันที และคุยกับฝั่งหลังบ้านให้เปลี่ยนในระยะยาว

8. เงินและหน่วยที่ต้องแม่น

double เก็บทศนิยมฐานสองไม่ได้แม่นทุกค่า

0.1 + 0.2 == 0.3     // false ใน Dart และแทบทุกภาษา

สำหรับจำนวนชิ้นไม่มีปัญหา เพราะเป็นจำนวนเต็ม แต่สำหรับเงินหรือหน่วยที่มีทศนิยม จะสะสมความคลาดเคลื่อน

ทางแก้วิธีข้อแลก
เก็บเป็นหน่วยย่อยที่สุดเก็บเป็นสตางค์ หรือกรัม เป็น intต้องแปลงตอนแสดงผล
เก็บเป็นข้อความแล้วใช้ไลบรารีทศนิยมตรงกับ decimal ฝั่ง .NETต้องเพิ่มไลบรารี
ใช้ double ต่อไป—ยอมรับความคลาดเคลื่อนได้เฉพาะงานที่ไม่แม่นก็ได้

สิ่งที่ต้องทำแน่ ๆ คือ ตกลงกับฝั่งหลังบ้านว่าใช้หน่วยอะไรและกี่ตำแหน่ง — ถ้าฝั่ง .NET ใช้ decimal แล้วฝั่งแอปใช้ double ตัวเลขจะไม่ตรงกันในบางค่า และจะเถียงกันว่าฝั่งไหนผิด

9. รูปแบบตัวเลขต้องเป็นแบบเดียวเสมอ

"245.5"     ← รับได้ — จุดเป็นทศนิยม
"245,5"     ← ปฏิเสธ — บางประเทศใช้จุลภาคเป็นทศนิยม
"1,245.50"  ← ปฏิเสธ — มีตัวคั่นหลักพัน

double.tryParse รับเฉพาะแบบแรก ซึ่งถูกต้องแล้ว — รูปแบบบนสายต้องเป็นแบบมาตรฐานเสมอ ไม่ขึ้นกับภาษาของผู้ใช้

บนสายบนหน้าจอ
รูปแบบมาตรฐานเดียว จุดเป็นทศนิยมตามภาษาและถิ่นของผู้ใช้
ใครแปลง—ชั้นแสดงผลเท่านั้น

การเผลอใช้รูปแบบตามภาษาตอนแปลงจาก JSON คือบั๊กที่โผล่เฉพาะเมื่อเปลี่ยนภาษาเครื่อง — หาเจอยากมาก

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
type 'double' is not a subtype of type 'int'as int กับค่า 12.0อ่านผ่านตัวแปลงกลาง
ยอดขาดไปเศษหนึ่งปัดเศษเงียบ ๆปฏิเสธค่าที่ไม่ใช่จำนวนเต็ม
สแกนบาร์โค้ดแล้วไม่เจอรหัสถูกเก็บเป็นตัวเลข ศูนย์นำหน้าหายเก็บรหัสเป็นข้อความ
ยอดเงินต่างกันสตางค์เดียวฝั่งหนึ่งใช้ decimal อีกฝั่งใช้ doubleตกลงหน่วยและความละเอียด
ตัวเลขอ่านไม่ได้เมื่อเปลี่ยนภาษาเครื่องแปลงตามภาษาผู้ใช้ใช้รูปแบบมาตรฐานบนสาย
ค่าผิดกลายเป็น 0 แล้วสร้างรายการผิดใช้ ?? 0 เมื่อแปลงไม่ได้แยก “ไม่มี” จาก “แปลงไม่ได้” จาก “เป็นศูนย์จริง”

11. แบบฝึกหัด

เซิร์ฟเวอร์ส่งบรรทัดสินค้ามาแบบนี้

{
  "productCode": 1001,
  "quantity": 24.0,
  "unitWeight": "1.25",
  "lotNumber": 20260815,
  "discountPercent": 7.5
}
  1. ระบุว่า field ไหนควรอ่านด้วยตัวช่วยตัวไหน และ field ไหนมีปัญหาเชิงออกแบบ
  2. เขียน fromJson
  3. ตอบว่าถ้า quantity ส่งมาเป็น 24.3 ควรทำอย่างไร และคำตอบจะเปลี่ยนไหมถ้าสินค้าขายเป็นกิโลกรัม
ดูแนวคำตอบและเหตุผล

ข้อ 1 — แต่ละ field

fieldอ่านด้วยปัญหาเชิงออกแบบ
productCodeต้องเป็นข้อความมี — เป็นรหัส แต่ส่งมาเป็นตัวเลข
quantityrequireIntไม่มี — 24.0 คือ 24
unitWeightrequireDoubleไม่มี — ข้อความที่แปลงได้
lotNumberต้องเป็นข้อความมี — เป็นรหัส แต่ส่งมาเป็นตัวเลข
discountPercentrequireDoubleไม่มี

สอง field ที่มีปัญหาเป็นเรื่องเดียวกัน — รหัสที่ถูกส่งมาเป็นตัวเลข

"productCode": 1001      → ถ้ารหัสจริงคือ "0001001" ศูนย์นำหน้าหายไปแล้ว
"lotNumber": 20260815    → ถ้าล็อตชื่อ "20260815A" จะส่งมาแบบนี้ไม่ได้

เรื่องนี้ต้องแก้ที่ต้นทาง แต่ระหว่างที่ยังแก้ไม่ได้ ต้องรับไว้และแปลงเป็นข้อความที่ขอบ

/// รับรหัสที่เซิร์ฟเวอร์เผลอส่งมาเป็นตัวเลข แล้วแปลงเป็นข้อความ
///
/// เป็นทางผ่านชั่วคราวจนกว่าฝั่งหลังบ้านจะเปลี่ยนเป็นข้อความ
/// กันไม่ได้ถ้ารหัสจริงมีศูนย์นำหน้า — จึงต้องตามไปแก้ที่ต้นทาง
String requireCode(Map<String, dynamic> json, String key, {String path = ''}) {
  final value = _require(json, key, path);
  return switch (value) {
    String s when s.trim().isNotEmpty => s.trim(),
    int i => i.toString(),
    _ => throw ContractException(
      _at(path, key),
      'รหัสต้องเป็นข้อความหรือจำนวนเต็ม แต่ได้ ${value.runtimeType}',
    ),
  };
}

รับเฉพาะ int ไม่รับ double — เพราะ 1001.0 แปลงเป็นข้อความจะได้ "1001.0" ซึ่งไม่ใช่รหัสที่ต้องการ

ข้อ 2 — fromJson

factory OrderLineDto.fromJson(Map<String, dynamic> json, {String path = ''}) =>
    OrderLineDto(
      productCode: requireCode(json, 'productCode', path: path),
      quantity: requireInt(json, 'quantity', path: path),
      unitWeight: requireDouble(json, 'unitWeight', path: path),
      lotNumber: requireCode(json, 'lotNumber', path: path),
      discountPercent: requireDouble(json, 'discountPercent', path: path),
    );

ข้อ 3 — quantity เป็น 24.3

คำตอบขึ้นกับ หน่วยของสินค้า และนี่คือประเด็นของข้อนี้

สินค้าขายเป็น24.3 แปลว่าควรทำ
ชิ้น / ลัง / พาเลทค่าที่เป็นไปไม่ได้ปฏิเสธ
กิโลกรัม / เมตร / ลิตรค่าปกติรับ

แปลว่า requireInt ไม่ใช่คำตอบที่ถูกเสมอ — มันถูกเฉพาะกับสินค้าที่นับเป็นชิ้น

สิ่งที่บอกว่าออกแบบยังไม่เสร็จ

ถ้า field เดียวกันบางครั้งต้องเป็นจำนวนเต็ม บางครั้งไม่ต้อง แปลว่าสัญญายังขาดข้อมูลหนึ่งชิ้น — หน่วย

{
  "productCode": "1001",
  "quantity": 24.3,
  "unitOfMeasure": "KG"     ← ที่ขาดไป
}
enum UnitOfMeasure { piece, box, pallet, kilogram, meter, liter, unknown }

/// หน่วยที่นับเป็นชิ้น จะมีเศษไม่ได้
bool get mustBeWhole => switch (this) {
  UnitOfMeasure.piece || UnitOfMeasure.box || UnitOfMeasure.pallet => true,
  _ => false,

// ตรวจตอนแปลงเป็นชนิดของธุรกิจ ซึ่งเป็นที่ที่รู้จักหน่วยแล้ว (6.1)
OrderLine toOrderLine(OrderLineDto dto, {String path = ''}) {
  final unit = parseUnitOfMeasure(dto.unitOfMeasure);
  if (unit.mustBeWhole && dto.quantity != dto.quantity.roundToDouble()) {

      'สินค้าหน่วย ${dto.unitOfMeasure} ต้องเป็นจำนวนเต็ม แต่ได้ ${dto.quantity}',

  }

สังเกตว่าการตรวจย้ายจากชั้น DTO ไปชั้นธุรกิจ — เพราะ กฎนี้ต้องรู้เรื่องหน่วยก่อนถึงจะตัดสินได้ และชั้น DTO ไม่ควรรู้เรื่องกฎธุรกิจ

บทเรียนที่ควรจำ: เมื่อพบว่าตอบคำถาม “ค่านี้ถูกต้องไหม” ไม่ได้ ให้ดูก่อนว่าขาดข้อมูลอะไรในสัญญา — บ่อยครั้งคำตอบไม่ใช่การเลือกกฎที่เข้มหรือหลวมกว่า แต่คือการขอ field ที่หายไปจากฝั่งหลังบ้าน

12. สรุปท้ายบท

  • JSON มี number ชนิดเดียว — Dart จะได้ int หรือ double ขึ้นกับว่ามีจุดหรือไม่
  • as ไม่ได้แปลงค่า มันแค่ตรวจแล้วพัง
  • ใช้ num ครอบทั้ง int และ double ในตัวแปลงกลาง
  • รับ 12, 12.0, "12" ได้ เพราะเป็นค่าเดียวกันที่เขียนคนละแบบ
  • ปฏิเสธ 1.9 เมื่อคาดว่าเป็นจำนวนเต็ม เพราะเป็นคนละค่า
  • การปัดเศษเงียบ ๆ ในงานคลังคือของหายหรือของเกิน
  • รหัสต้องเป็นข้อความเสมอ — เกณฑ์คือเอาไปบวกลบแล้วมีความหมายไหม
  • เงินและหน่วยที่ต้องแม่น ให้เก็บเป็นหน่วยย่อยที่สุดหรือใช้ทศนิยมที่แม่นจริง
  • รูปแบบตัวเลขบนสายต้องเป็นแบบมาตรฐาน ไม่ขึ้นกับภาษาผู้ใช้
