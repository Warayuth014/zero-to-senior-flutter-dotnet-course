ระดับ: กลางใช้เวลา: 30–40 นาทีลงมือทำ: กัก dynamic ไว้ที่ขอบ ไม่ให้หลุดเข้าแอป
ต้องผ่านอะไรมาก่อน: 6.2 (ตัวช่วยอ่านค่า) และ D1.19 (dynamic และ cast)
จบบทนี้แล้วจะทำได้: รู้ว่า as ทำอะไรจริง ๆ และแยกความผิดพลาดสามชนิดที่มักถูกยุบรวมกัน

1. ปัญหาที่บทนี้แก้

ทุกอย่างที่ผ่านมาในบทนี้เริ่มจากบรรทัดเดียว

final decoded = jsonDecode(responseBody);

decoded มีชนิดเป็น dynamic ซึ่งแปลว่า compiler เลิกช่วยตั้งแต่จุดนี้

decoded.items.first.quantity + 1     // คอมไพล์ผ่าน
decoded.thisMethodDoesNotExist()     // คอมไพล์ผ่านเหมือนกัน
decoded['items'][0]['qty'] * 2       // ผ่านอีก

ทั้งสามบรรทัดจะพังตอนรัน และพังคนละแบบ โดยที่ไม่มีอะไรเตือนตอนเขียน

สิ่งที่ทำให้เรื่องนี้ร้ายกว่าที่คิดคือ dynamic แพร่ต่อได้ — ถ้าปล่อยให้มันหลุดออกจากชั้นที่แปลงข้อมูล มันจะไหลไปถึงหน้าจอ และทุกจุดที่แตะมันจะกลายเป็นจุดที่พังได้ตอนรัน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
dynamicชนิดที่แปลว่า “อะไรก็ได้” — compiler ไม่ตรวจอะไรเลย
Object?ชนิดที่แปลว่า “อะไรก็ได้ แต่ต้องตรวจก่อนใช้”
asยืนยันว่าเป็นชนิดนี้ — ถ้าไม่ใช่จะพัง
isถามว่าเป็นชนิดนี้ไหม — คืน true หรือ false
type promotioncompiler เลื่อนชนิดให้เองหลังจากตรวจด้วย is

3. Mental model: dynamic คือการปิดสวิตช์ความปลอดภัย

dynamic value = ...;
value.anything();      // compiler: "ได้เลย ไม่ตรวจ"

Object? value = ...;
value.anything();      // compiler: "ไม่ได้ ต้องตรวจก่อน"
ประโยคเดียวที่ต้องจำ: ใช้ Object? แทน dynamic ทุกที่ที่ทำได้ — ทั้งคู่รับค่าอะไรก็ได้เหมือนกัน แต่ Object? บังคับให้ตรวจก่อนใช้ ส่วน dynamic ปล่อยผ่าน

สังเกตว่าตัวช่วยใน lab รับ Object? ไม่ใช่ dynamic

Map<String, dynamic> requireMap(Object? value, String path) {
  if (value is Map<String, dynamic>) return value;
  throw ContractException(path, 'ต้องเป็น object แต่ได้ ${value.runtimeType}');
}

4. as ไม่ได้แปลงค่า

ความเข้าใจผิดที่พบบ่อยที่สุดเรื่องนี้

final value = 12.0;
value as int;      // พัง — ไม่ได้แปลงให้ แค่ตรวจแล้วบอกว่าไม่ใช่
คำสั่งทำอะไร
value as intยืนยันว่าเป็น int อยู่แล้ว ถ้าไม่ใช่ก็พัง
value.toInt()แปลงจริง

ตัวที่ทำให้สับสนคือบางครั้ง as ก็ผ่าน

final Object value = 12;
value as num;      // ผ่าน — int เป็นลูกของ num
value as int;      // ผ่าน — เป็น int จริง
value as double;   // พัง — int ไม่ใช่ double

ซึ่งอธิบายว่าทำไม json['quantity'] as int ถึงผ่านบ้างพังบ้าง โดยขึ้นกับว่าเซิร์ฟเวอร์เขียนจุดทศนิยมมาหรือไม่ ตามที่เจอใน 6.3

5. ตรวจด้วย is แล้ว compiler จะช่วยต่อ

if (value is Map<String, dynamic>) return value;
//                                        └─ ตรงนี้ value มีชนิดเป็น Map แล้ว
//                                           ไม่ต้องเขียน as อีก

นี่คือ type promotion ที่เคยเจอใน D1.13 — พอตรวจด้วย is แล้ว compiler รู้เองว่าในบล็อกนั้นค่ามีชนิดอะไร

ใช้กับ switch ได้ด้วย ซึ่งอ่านง่ายกว่าเมื่อมีหลายกรณี

double? _toDouble(Object? value) => switch (value) {
  num n => n.toDouble(),                 // n มีชนิด num
  String s => double.tryParse(s.trim()), // s มีชนิด String
  _ => null,
};
asis / switch
ถ้าชนิดไม่ตรงพังทันทีไปทางอื่นได้
ควบคุมข้อความผิดพลาดไม่ได้ได้
เขียนสั้นกว่าใช่ยาวกว่าเล็กน้อย

6. ตรวจก้อนนอกสุดก่อนเสมอ

final decoded = jsonDecode(body);
if (decoded is! Map<String, dynamic>) {
  throw const ContractException('', 'ก้อนนอกสุดต้องเป็น object');
}
final page = TaskPageDto.fromJson(decoded);

ทำไมต้องตรวจ ทั้งที่รู้ว่าเซิร์ฟเวอร์ส่ง object มา

สิ่งที่อาจได้แทนเกิดเมื่อ
Listบาง endpoint คืน array ตรง ๆ
Stringเซิร์ฟเวอร์ตอบข้อความผิดพลาดกลับมาเป็นข้อความล้วน
nullตอบ 204 แล้ว body ว่าง
โยน FormatExceptionได้หน้า HTML แทน JSON เพราะ proxy หรือหน้า login

แถวสุดท้ายเจอบ่อยในคลังที่มีระบบเครือข่ายภายใน — พอ session หมดอายุ proxy จะตอบหน้า login กลับมา แล้ว jsonDecode ก็โยน FormatException ที่หน้าตาไม่เกี่ยวอะไรกับเรื่องจริงเลย

7. แยกความผิดพลาดสามชนิด

สิ่งที่มักถูกยุบรวมกันจนไล่หาสาเหตุไม่ได้

ชนิดแปลว่าควรทำ
ข้อความไม่ใช่ JSONได้ HTML หรือข้อความเปล่าตรวจว่าที่อยู่ถูกไหม หรือ session หมดอายุ
เป็น JSON แต่โครงผิดสัญญาไม่ตรงกันแจ้งทีมหลังบ้าน
โครงถูก แต่ค่าผิดกฎธุรกิจข้อมูลในระบบมีปัญหาแจ้งพร้อมระบุรายการ
Map<String, dynamic> decodeJsonObject(String body) {
  final Object? decoded;
  try {
    decoded = jsonDecode(body);
  } on FormatException catch (error) {
    // ไม่ใช่ JSON เลย — คนละปัญหากับ JSON ที่โครงผิด
    throw ContractException('', 'ข้อมูลที่ได้ไม่ใช่ JSON: ${error.message}');
  }
  return requireMap(decoded, '');
}

ทั้งสามชนิดควรแยกจาก ปัญหาเครือข่าย ด้วย — เน็ตหลุดกับข้อมูลผิดสัญญาต้องรับมือคนละแบบ ตาม 4.8 และจะทำเต็มรูปแบบใน Part 8

8. กัก dynamic ไว้ที่ชั้นเดียว

HTTP → jsonDecode → dynamic ─┐
                             │  ← dynamic อยู่ได้แค่ในกรอบนี้
    DTO.fromJson ────────────┘
         ↓
    Task (domain)  ← ไม่มี dynamic แล้ว
         ↓
    store, หน้าจอ  ← ไม่มี dynamic เลย

เกณฑ์ที่ตรวจได้ง่าย — ค้นคำว่า dynamic ในโปรเจกต์ ถ้าเจอนอกโฟลเดอร์ที่แปลงข้อมูล แปลว่ามีอะไรรั่ว

// สัญญาณอันตราย
class TaskStore extends ChangeNotifier {
  List<dynamic> _rawTasks = [];        // dynamic หลุดเข้ามาถึง store แล้ว
}
ถ้า dynamic หลุดเข้ามาผลที่ตามมา
หน้าจอเขียน task['quantity']พิมพ์ชื่อคีย์ผิดแล้วรู้ตอนใช้งานจริง
ทุกจุดที่แตะข้อมูลกลายเป็นจุดเสี่ยงเปลี่ยนสัญญาแล้วไม่มีอะไรบอกว่าต้องแก้ตรงไหน
เขียนเทสต์ยากต้องสร้าง map ปลอมแทนที่จะสร้างวัตถุ

สังเกตว่า Map<String, dynamic> ยังอยู่ในลายเซ็นของ fromJson ซึ่งไม่เป็นไร เพราะ dynamic ตรงนั้นคือค่าที่ยังไม่ได้ตรวจ และมันจะถูกตรวจในบรรทัดถัดไปทันที

9. บันทึกให้พอไล่หาสาเหตุ แต่ไม่มากเกินไป

ควรบันทึกห้ามบันทึก
ที่อยู่ของ endpointtoken หรือรหัสผ่าน
รหัสตอบกลับข้อมูลส่วนบุคคล
path ที่พังเนื้อหาทั้งก้อน
ชนิดที่ได้รับจริงค่าที่อ่อนไหว
// พอไล่หาได้ โดยไม่หลุดข้อมูลอ่อนไหว
logger.warn('contract violation', {
  'endpoint': '/api/v2/tasks',
  'path': error.path,
  'message': error.message,
});

เหตุผลที่ไม่ควรบันทึกทั้งก้อน — payload ของงานคลังมีทั้งชื่อลูกค้า ที่อยู่ และราคา ซึ่งไม่ควรอยู่ในไฟล์ log ที่หลายคนเข้าถึงได้

ส่วน path กับ message ที่ออกแบบไว้ตั้งแต่ 6.2 พอสำหรับไล่หาสาเหตุแล้วโดยไม่ต้องเปิด payload

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
พิมพ์ชื่อเมธอดผิดแล้วคอมไพล์ผ่านค่าเป็น dynamicใช้ Object? แทน
type 'double' is not a subtype of type 'int'คิดว่า as แปลงค่าให้ใช้ตัวแปลงจริง
FormatException: Unexpected characterได้ HTML แทน JSONตรวจว่าที่อยู่ถูกและ session ยังอยู่
ทุกปัญหาขึ้นข้อความเดียวกันไม่แยกชนิดความผิดพลาดแยกสามชนิดตามหัวข้อ 7
หน้าจอเขียน task['quantity']dynamic รั่วออกจากชั้นแปลงคืน DTO ที่มีชนิดชัดเจน
log เต็มไปด้วยข้อมูลลูกค้าบันทึก payload ทั้งก้อนบันทึกเฉพาะ path และชนิด
แก้ด้วยการเปลี่ยนทุกอย่างเป็น dynamicอยากให้คอมไพล์ผ่านเร็ว ๆแก้ที่ชนิดจริง

11. แบบฝึกหัด

โค้ดนี้อยู่ในชั้นที่คุยกับเซิร์ฟเวอร์

Future<List<dynamic>> fetchTasks() async {
  final response = await client.get('/api/v2/tasks');
  final decoded = jsonDecode(response.body);
  return decoded['items'] as List<dynamic>;
}

และหน้าจอใช้แบบนี้

final tasks = await repository.fetchTasks();
Text('${tasks[index]['palletCode']} · ${tasks[index]['quantity']} ชิ้น')
  1. ระบุจุดที่จะพังตอนรัน และแต่ละจุดพังเพราะอะไร
  2. เขียนใหม่ให้ dynamic ไม่หลุดออกจากชั้นนี้
  3. ตอบว่าถ้าเซิร์ฟเวอร์เปลี่ยนชื่อ palletCode เป็น palletNo โค้ดสองแบบจะให้ประสบการณ์ต่างกันอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — จุดที่จะพัง

#จุดพังเพราะ
1jsonDecode(response.body)ได้ HTML แทน JSON เมื่อ session หมดอายุ
2decoded['items']ถ้า decoded เป็น List หรือ null จะพัง
3as List<dynamic>ถ้า items ไม่ใช่ array
4tasks[index]['palletCode']พิมพ์ชื่อคีย์ผิดได้โดยไม่มีอะไรเตือน
5['quantity'] ใน Textถ้าเป็น null จะแสดงคำว่า "null" บนจอ

จุดที่ 5 อันตรายที่สุดในทางปฏิบัติ เพราะ มันไม่พัง — คนหน้างานจะเห็น “PAL-0101 · null ชิ้น” แล้วไม่รู้ว่าควรหยิบกี่ชิ้น

และจุดที่ 4 พังไกลจากต้นเหตุมาก — ข้อความผิดพลาดจะชี้ไปที่ไฟล์หน้าจอ ทั้งที่ปัญหาอยู่ที่สัญญากับเซิร์ฟเวอร์

ข้อ 2 — เขียนใหม่

Future<List<Task>> fetchTasks() async {
  final response = await client.get('/api/v2/tasks');

  final Object? decoded;
  try {
    decoded = jsonDecode(response.body);
  } on FormatException catch (error) {
    throw ContractException('', 'ข้อมูลที่ได้ไม่ใช่ JSON: ${error.message}');
  }

  final page = TaskPageDto.fromJson(requireMap(decoded, ''));

  // แปลงเป็นชนิดของธุรกิจก่อนส่งออกจากชั้นนี้ (6.1)
  return [
    for (var index = 0; index < page.items.length; index++)
      toTask(page.items[index], path: 'items[$index]'),
  ];
}
// หน้าจอได้ชนิดที่ชัดเจน
Text('${task.palletCode} · ${task.quantity} ชิ้น')

สิ่งที่เปลี่ยนไป

เดิมใหม่
คืน List<dynamic>คืน List<Task>
หน้าจออ่านด้วยชื่อคีย์หน้าจออ่านด้วยชื่อ field
jsonDecode พังแบบไม่มีบริบทแยกเป็น ContractException
ไม่รู้ว่าแถวไหนพังมี path บอก

ข้อ 3 — เมื่อเซิร์ฟเวอร์เปลี่ยนชื่อคีย์

นี่คือคำถามที่แสดงคุณค่าจริงของทั้งบทนี้

แบบเดิม (dynamic)แบบใหม่ (typed)
รู้ตอนไหนตอนผู้ใช้เปิดหน้าจอที่หน้างานตอนแรกที่ยิงคำขอ ในการทดสอบ
เห็นอะไร“PAL-0101 · null ชิ้น” หรือ “null · 12 ชิ้น”ข้อความผิดพลาดพร้อม path
ข้อความบอกอะไรไม่มีข้อความ — มันไม่พัง“ที่ items[0].palletCode: ไม่มีคีย์นี้”
ใครเจอก่อนคนหน้างานเทสต์ในเครื่องพัฒนา
ความเสียหายหยิบของผิด เพราะจอแสดงข้อมูลไม่ครบไม่มี — แก้ก่อนปล่อย

ทำไมแบบเดิมถึงไม่พัง

tasks[index]['palletCode']    // คีย์ไม่มี → คืน null
'${null} · 12 ชิ้น'           // กลายเป็นข้อความ "null"

Dart แปลงอะไรก็ได้เป็นข้อความใน string interpolation รวมถึง null ด้วย — จึงไม่มีอะไรพัง มีแต่ข้อมูลที่ผิด

บทเรียนที่ควรจำ: dynamic ไม่ได้ทำให้บั๊กเยอะขึ้น แต่ทำให้บั๊ก เจอช้าลง และ เจอไกลจากต้นเหตุ — ในงานคลังนั้นแปลว่าคนหน้างานเป็นคนเจอ แทนที่จะเป็นเทสต์

12. สรุปท้ายบท

  • jsonDecode คืน dynamic ซึ่งแปลว่า compiler เลิกช่วย
  • ใช้ Object? แทน dynamic เพราะบังคับให้ตรวจก่อนใช้
  • as ไม่ได้แปลงค่า แค่ตรวจแล้วพัง
  • ตรวจด้วย is หรือ switch แล้ว compiler จะเลื่อนชนิดให้เอง
  • ตรวจก้อนนอกสุดก่อนเสมอ เพราะอาจไม่ใช่ object
  • แยกความผิดพลาดสามชนิด — ไม่ใช่ JSON, โครงผิด, ค่าผิดกฎ
  • กัก dynamic ไว้ในชั้นที่แปลงข้อมูลเท่านั้น
  • บันทึก path และชนิด แต่ไม่บันทึก payload ทั้งก้อน
  • dynamic ทำให้บั๊กเจอช้าลงและไกลจากต้นเหตุ
