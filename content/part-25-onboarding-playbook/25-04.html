Debug order: พิสูจน์ก่อนว่า stateเปลี่ยนจริงหรือไม่ แล้วค่อยดู notification/listener/identity/build branch — อย่าใส่ setState/notifyListenersสุ่มทุกที่

1. Classify architecture

StatefulWidget: ownerคือ Stateและ setStateต้องเกิดหลัง mutation; ChangeNotifier: ownerคือ storeและ listenerต้อง subscribe objectเดียว; ValueNotifier/streamมี update semanticsต่างกัน เริ่มจาก typeจริง

2. Stateไม่เปลี่ยน

ตรวจ guard return, validation, catchที่กลืน, response generationถูก discard, mutationสำเนาคนละ objectและ async commandยังไม่จบ Breakpointก่อน/หลัง mutationพร้อม identity/hashของ owner

3. Notifyไม่เกิด

ChangeNotifier mutate public listจากภายนอกหรือ returnก่อน notify; setState mutationเกิดนอก callbackได้แต่ต้องเรียก setStateขณะ mounted ตรวจ finally/error branchesที่ลืม clear loading/notify

4. ฟังคนละ instance

composition rootสร้าง store Aแต่ widgetฟัง B, routeสร้างใหม่หรือ singleton/cacheรั่ว ตรวจ constructor graphและ debug identity ไม่แก้ด้วย global singletonเพื่อให้ “หาเจอ”

5. Buildแต่ branchเดิม

derived getterใช้ stale copy, equality/keyผิด, ListView item identityซ้ำ, child constเกินบริบทหรือ conditionให้ errorเหนือ data ใช้ Flutter inspector/rebuild trackingและ log branchที่เลือก

6. Mutable collection trap

แก้ list/mapเดิมแล้ว selector/equalityมองว่าไม่เปลี่ยน หรือ widgetถือ referenceเดิม ใช้ immutable snapshot/replace listและ unmodifiable public view

7. Async ordering

UIอัปเดตแล้ว responseเก่ามาทับจึงดูเหมือนไม่ rebuild ตรวจ request generation/version, overlapping pollingและ optimistic rollback ใส่ request IDใน logs/test out-of-order

8. Regression test

เขียน store/widget testทำให้ bugเกิด: action→state→notification→visible UI Assert behaviorไม่ assertจำนวน notifyตายตัว เว้นแต่จำนวนเป็น performance contract
