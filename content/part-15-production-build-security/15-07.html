จบบทนี้แล้วจะทำได้: เลือกรูปแบบไฟล์ที่ตรงกับวิธีแจก และลดขนาดแอปได้

1. สองรูปแบบ

APKApp Bundle (.aab)
คำสั่งflutter build apkflutter build appbundle
ติดตั้งได้เลยไหมได้ไม่ได้ — ต้องผ่าน Play Store
ขนาดที่ผู้ใช้โหลดทุกสถาปัตยกรรมรวมกันเฉพาะที่เครื่องนั้นใช้
เหมาะกับแจกไฟล์เองปล่อยผ่าน Play Store
สำหรับ PDA ในคลังที่แจกไฟล์เอง คำตอบคือ APK — App Bundle ติดตั้งตรง ๆ ไม่ได้ เพราะมันเป็นรูปแบบที่ให้ Play Store ประกอบ APK ที่เหมาะกับแต่ละเครื่อง

2. ขนาดที่ต่างกัน

flutter build apk --release
# app-release.apk  ~18 MB — มีโค้ดของทุกสถาปัตยกรรม
flutter build apk --release --split-per-abi
# app-armeabi-v7a-release.apk  ~7 MB
# app-arm64-v8a-release.apk    ~7 MB
# app-x86_64-release.apk       ~7 MB
สถาปัตยกรรมใช้กับ
arm64-v8aเครื่อง Android แทบทั้งหมดตั้งแต่ปี 2017
armeabi-v7aเครื่องเก่า — PDA รุ่นเก่าบางตัวยังเป็นแบบนี้
x86_64emulator เป็นหลัก

สำหรับคลังที่รู้ว่าใช้ PDA รุ่นไหน การ build เฉพาะสถาปัตยกรรมที่ใช้จริงลดขนาดได้เกินครึ่ง

# ตรวจว่า PDA เป็นสถาปัตยกรรมอะไร
adb shell getprop ro.product.cpu.abi
# arm64-v8a
ถ้าแจกไฟล์เอง ต้องแน่ใจว่าส่งไฟล์ที่ตรงกับเครื่อง — APK ที่ผิดสถาปัตยกรรมจะติดตั้งได้แต่เปิดแล้วปิดทันที ซึ่งเป็นอาการที่หาสาเหตุยาก

ถ้าไม่แน่ใจว่าคลังมีเครื่องกี่รุ่น ให้ใช้ APK รวมไปก่อน — 18 MB ไม่ได้แพงเมื่อเทียบกับการส่งไฟล์ผิดเครื่อง

3. ลดขนาดด้วยการตัดสิ่งที่ไม่ได้ใช้

// android/app/build.gradle.kts
buildTypes {
    release {
        signingConfig = signingConfigs.getByName("release")
        isMinifyEnabled = true      // ตัดโค้ด Kotlin/Java ที่ไม่ได้ใช้
        isShrinkResources = true    // ตัด resource ที่ไม่ได้ใช้
        proguardFiles(
            getDefaultProguardFile("proguard-android-optimize.txt"),
            "proguard-rules.pro",
        )
    }
}
สิ่งที่ตัดลดได้เท่าไหร่
โค้ด Java/Kotlin ที่ไม่ได้เรียกราว 1–3 MB
resource ที่ไม่ได้อ้างถึงขึ้นกับจำนวน asset
โค้ด Dart ที่ไม่ได้ใช้Flutter ตัดให้อยู่แล้วโดยปริยาย
การย่อโค้ดทำให้ปลั๊กอินบางตัวพังตอนรัน เพราะมันหาคลาสด้วยชื่อตอนรัน ซึ่ง ProGuard เปลี่ยนชื่อไปแล้ว — ต้องทดสอบ APK ที่ย่อแล้วทุกเส้นทางหลัก ไม่ใช่แค่เปิดดูว่าเปิดได้
# proguard-rules.pro — บอกให้เก็บคลาสที่ถูกหาด้วยชื่อ
-keep class com.example.plugin.** { *; }

4. ดูว่าอะไรกินพื้นที่

flutter build apk --release --analyze-size

คำสั่งนี้สร้างไฟล์ที่เปิดใน DevTools ได้ แล้วเห็นว่าขนาดมาจากไหน

สิ่งที่มักกินพื้นที่มากที่สุดลดอย่างไร
โค้ดของ Flutter engineลดไม่ได้ — เป็นพื้นฐาน
ฟอนต์ที่ฝังไว้ใส่เฉพาะน้ำหนักที่ใช้จริง (11.4)
รูปใน assetใช้ SVG แทน PNG ที่ต้องมีหลายความละเอียด (11.10)
แพ็กเกจที่ใช้เพียงเล็กน้อยตัดออกถ้าเขียนเองได้ในไม่กี่บรรทัด
ไอคอนชุดใหญ่ทั้งชุดใช้ SVG เฉพาะตัวที่ต้องการ (11.10)

สำหรับ PDA ที่ติดตั้งครั้งเดียวผ่านสาย USB ขนาดแอปไม่ใช่ปัญหาเท่าไหร่ — สิ่งที่สำคัญกว่าคือเวลาที่ใช้ติดตั้งข้ามยี่สิบเครื่อง ซึ่งขนาดมีผลโดยตรง

5. แพ็กเกจที่ไม่ควรติดไปกับแอป

test('แพ็กเกจที่ใช้เฉพาะตอนพัฒนา อยู่ใน dependencies ต้องเตือน', () {
  final pubspec = goodPubspec.replaceAll(
    '  http: ^1.2.2',
    '  http: ^1.2.2\n  build_runner: ^2.15.1',
  );

  final findings = checkPubspec(pubspec);
  expect(findings.any((f) => f.code == 'dev-package-in-dependencies'), isTrue);
});
แพ็กเกจควรอยู่ที่
flutter_launcher_iconsdev_dependencies — ใช้ตอน build ไอคอน (11.12)
build_runnerdev_dependencies — ใช้สร้างโค้ด
flutter_lintsdev_dependencies
freezed, json_serializabledev_dependencies — ส่วน *_annotation อยู่ใน dependencies

แถวสุดท้ายเป็นจุดที่สับสนบ่อย — ตัวสร้างโค้ดอยู่ฝั่ง dev ส่วนตัว annotation ที่โค้ดที่สร้างขึ้นต้องใช้ ต้องอยู่ฝั่งปกติ

สิ่งที่ควรตรวจทำไม

รูปที่ความละเอียดสูงเกินจำเป็นกินพื้นที่โดยไม่ได้ใช้

แถวสุดท้ายเชื่อมกับ 15.6 — asset ที่ติดไปโดยไม่ตั้งใจเป็นทางหนึ่งที่ข้อมูลหลุด

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ติดตั้ง .aab ไม่ได้มันไม่ใช่ไฟล์ที่ติดตั้งได้ใช้ APK ถ้าแจกเอง
ติดตั้งได้แต่เปิดแล้วปิดทันทีAPK ผิดสถาปัตยกรรมตรวจด้วย getprop ro.product.cpu.abi
ปลั๊กอินพังเฉพาะ releaseProGuard เปลี่ยนชื่อคลาสเพิ่มกฎ -keep
แอปใหญ่กว่าที่ควรฟอนต์หรือรูปที่ไม่ได้ใช้--analyze-size
เครื่องมือสร้างโค้ดติดไปกับแอปอยู่ผิดส่วนใน pubspecย้ายไป dev_dependencies
ทดสอบ APK ที่ย่อแล้วแค่เปิดดูคิดว่าเปิดได้คือใช้ได้ทดสอบทุกเส้นทางหลัก

8. แบบฝึกหัด

คลังมี PDA สองรุ่น รุ่นเก่า 8 เครื่องเป็น armeabi-v7a รุ่นใหม่ 12 เครื่องเป็น arm64-v8a ช่างต้องเดินไปติดตั้งทีละเครื่อง

  1. ควร build อย่างไร
  2. จะลดโอกาสส่งไฟล์ผิดเครื่องอย่างไร
แนวคำตอบ

1. มีสองทางที่ใช้ได้ และคำตอบขึ้นกับว่าอะไรแพงกว่า

ทางขนาดต่อไฟล์ความเสี่ยง
APK รวมไฟล์เดียวราว 18 MBส่งผิดไม่ได้เลย
แยกตามสถาปัตยกรรมราว 7 MBส่งผิดเครื่องได้

สำหรับ 20 เครื่อง คำตอบคือไฟล์เดียว — ความต่าง 11 MB ต่อเครื่องผ่านสาย USB คือไม่กี่วินาที ส่วนการติดตั้งผิดไฟล์แล้วต้องกลับไปแก้ คือการเดินซ้ำ

การแยกไฟล์คุ้มเมื่อ

  • ส่งผ่านเครือข่ายที่ช้าหรือมีค่าใช้จ่าย
  • มีเครื่องหลักร้อยขึ้นไป
  • มีระบบจัดการอุปกรณ์ที่เลือกไฟล์ให้อัตโนมัติ

2. ถ้าเลือกแยกไฟล์ ให้ลดโอกาสผิดด้วยสามอย่าง

ทำได้อะไร
ตั้งชื่อไฟล์ให้บอกสถาปัตยกรรมชัดFlutter ทำให้อยู่แล้ว — อย่าเปลี่ยนชื่อ
เขียนสคริปต์ติดตั้งที่ตรวจเครื่องก่อนผิดไม่ได้เลย
แสดงสถาปัตยกรรมในหน้าตั้งค่าของแอปตรวจย้อนหลังได้ว่าเครื่องไหนลงอะไร
# tool/install.sh — เลือกไฟล์ตามเครื่องที่ต่ออยู่
abi=$(adb shell getprop ro.product.cpu.abi | tr -d '\r')
apk="build/app/outputs/flutter-apk/app-$abi-release.apk"

if [ ! -f "$apk" ]; then
  echo "ไม่มีไฟล์สำหรับ $abi"
  exit 1
fi

adb install -r "$apk"

สิ่งที่มีค่ากว่าทั้งสองข้อ — ถามว่าทำไมต้องเดินไปทีละเครื่อง

ทางเลือกเหมาะเมื่อ
ระบบจัดการอุปกรณ์ขององค์กรมีเครื่องเกินสิบและอัปเดตบ่อย
ให้แอปตรวจรุ่นใหม่แล้วบอกผู้ใช้ทำได้ทันทีโดยไม่ต้องมีระบบเพิ่ม
// ต่อยอดจาก health payload ที่ 10.9 ทำไว้แล้ว
if (health.minimumAppBuild > currentVersion.build) {
  // บอกให้ไปรับการอัปเดต แทนที่จะปล่อยให้ใช้รุ่นเก่าไปเรื่อย ๆ
}

ข้อหลังใช้เวลาทำไม่กี่ชั่วโมง และแก้ปัญหาที่ใหญ่กว่าเรื่องขนาดไฟล์มาก — การไม่รู้ว่าเครื่องไหนใช้รุ่นอะไรอยู่ ซึ่ง 15.2 ก็ชี้ไปที่เรื่องเดียวกัน

9. สรุป

  • แจกไฟล์เองใช้ APK ส่วน App Bundle ใช้กับ Play Store เท่านั้น
  • แยกตามสถาปัตยกรรมลดขนาดเกินครึ่ง แต่เสี่ยงส่งผิดเครื่อง
  • APK ผิดสถาปัตยกรรมติดตั้งได้แต่เปิดแล้วปิดทันที
  • การย่อโค้ดทำให้ปลั๊กอินบางตัวพัง ต้องทดสอบทุกเส้นทาง
  • เครื่องมือสร้างโค้ดต้องอยู่ใน dev_dependencies
  • ตรวจว่ามี asset อะไรติดไปกับ APK บ้าง
