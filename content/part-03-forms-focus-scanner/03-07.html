Debounce จัดการ event ต่อเนื่องตามเวลา ส่วน duplicate detection จัดการค่าซ้ำตาม identity และ business window ทั้งสองเรื่องต่างกัน และไม่แทน idempotency ของ backend

1. Debounce vs throttle vs lock

  • Debounce: รอเงียบช่วงหนึ่งแล้วใช้ event ล่าสุด เหมาะ search-as-you-type
  • Throttle: รับไม่เกินหนึ่งครั้งต่อช่วง เหมาะ telemetry/UI action
  • Busy lock: ไม่รับ commandใหม่จนงานเดิมจบ เหมาะ scan→API
  • Duplicate set/window: ปฏิเสธ canonical code ที่เคยรับใน session/ช่วงเวลา

2. Scanner ที่มี Enter ไม่ต้อง debounce text

เมื่อ wedge ส่ง terminatorชัด ให้ submitที่ onSubmitted การ debounce onChanged อาจยิงก่อนอักขระสุดท้ายบนเครื่องช้า ใช้ busy lock และ duplicate policy แทน Debounce เหมาะกับช่องค้นหา filter ที่ไม่มี commit event

3. Duplicate ใน session

final scanned = <String>{};

ScanDecision acceptSerial(String raw) {
  final serial = normalizeSerial(raw);
  if (!available.contains(serial)) return const UnknownSerial();
  if (!scanned.add(serial)) return DuplicateSerial(serial);
  return AcceptedSerial(serial);
}

wmsapp SerialSelect ตรวจ available ก่อน แล้วตรวจ _scanned.contains(sn) พร้อมคืน focus Set ช่วย lookup O(1) และ add แบบ atomicใน isolateเดียว

4. Same code อาจถูกต้อง

Product barcode อาจต้องสแกนซ้ำเพื่อเพิ่ม quantity แต่ serial ต้อง unique และ pallet scanซ้ำระหว่าง workflowอาจเป็น retry กำหนด duplicate policy ตาม entity/state: ignore, increment, warn, replace หรือ reject ไม่สร้าง global “last barcode” rule

5. Time window

เครื่องบางรุ่นส่ง Enterซ้ำหรือผู้ใช้กด triggerค้าง ใช้ last accepted canonical value + timestamp ป้องกันซ้ำใน 300–800msได้ แต่ต้อง clock injectable สำหรับ test และห้ามปฏิเสธการสแกน codeเดิมที่ธุรกิจอนุญาตหลัง window

6. Backend idempotency

Mobile lock ป้องกัน UX duplicateใน processเดียว แต่ retry/network timeout/appสองเครื่องยังทำ commitซ้ำได้ Endpoint mutation ควรรับ idempotency/operation key หรือมี unique constraint/version/invariant ฝั่ง .NET แล้วคืนผลเดิม/Conflictอย่างชัดเจน

7. แบบฝึกหัด

Serial เดียวกันถูก triggerสองครั้งห่าง 40ms และ requestแรกยังวิ่ง ต้องป้องกันที่ใดบ้าง?

แนวคำตอบ

UI busy lock ปิด submitที่สอง, local canonical Set/window ให้ feedback duplicate, requestมี operation ID และ backend unique constraint/idempotency ป้องกันข้าม retry/device เมื่อ requestจบให้คืน focusและไม่ลบ accepted stateหาก response timeoutแต่ serverอาจ commitแล้ว ต้อง reconcile

8. จุดพลาด

Timer debounce อย่างเดียวไม่รับประกันไม่ซ้ำ และ busy boolean อย่างเดียวไม่กัน retryหลัง timeout ออกแบบทั้ง event semantics, local session identity และ server transaction/idempotency ตามระดับความเสียหาย
