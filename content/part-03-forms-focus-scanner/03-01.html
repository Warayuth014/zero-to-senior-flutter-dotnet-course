1. ปัญหาที่บทนี้แก้

Part 1 และ 2 เราแสดงข้อมูลอย่างเดียว ยังไม่เคยรับอะไรจากผู้ใช้เลย แต่งานคลังทั้งหมดเริ่มจากการรับข้อมูล — ยิงบาร์โค้ด กรอกจำนวน ระบุตำแหน่ง

คำถามแรกที่ต้องตอบคือ ข้อความที่ผู้ใช้พิมพ์เก็บอยู่ที่ไหน และเราจะอ่านมันอย่างไร

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
TextFieldช่องรับข้อความ
TextEditingControllerตัวที่ถือข้อความจริง อ่านและเขียนได้จากภายนอก
onChangedcallback ที่ยิงทุกครั้งที่ตัวอักษรเปลี่ยน
onSubmittedcallback ที่ยิงเมื่อกด Enter หรือปุ่มยืนยันบนแป้นพิมพ์
InputDecorationหน้าตาของช่อง เช่นป้ายกำกับ กรอบ ข้อความแนะนำ

3. Mental model: ช่องคือหน้าจอ controller คือข้อมูล

TextField เป็น widget จึงถูกสร้างใหม่ทุกครั้งที่หน้าจอวาดใหม่ ตามที่เรียนใน 1.3 — ดังนั้นมันเก็บข้อความไว้เองไม่ได้

TextEditingController   ← ถือข้อความจริง อยู่ยาว
        ↕
    TextField           ← แค่แสดงและรับการพิมพ์ ถูกสร้างใหม่เรื่อย ๆ
ประโยคเดียวที่ต้องจำ: ถ้าอยากอ่านหรือล้างข้อความจากโค้ด ต้องมี controller — ถ้าแค่รับค่าแล้วส่งต่อทันที ใช้ onChanged อย่างเดียวก็พอ

4. ใช้งานพื้นฐาน

class _ReceiveScreenState extends State<ReceiveScreen> {
  final _barcodeController = TextEditingController();   // สร้างครั้งเดียว

  @override
  void dispose() {
    _barcodeController.dispose();                       // คืนเสมอ (1.6)
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return TextField(
      controller: _barcodeController,
      decoration: const InputDecoration(
        labelText: 'บาร์โค้ดพาเลท',
        hintText: 'PAL-1001',
        border: OutlineInputBorder(),
      ),
      onSubmitted: (_) => _handleScan(),
    );
  }
}

สิ่งที่ทำได้ผ่าน controller

คำสั่งทำอะไร
controller.textอ่านข้อความปัจจุบัน
controller.text = 'PAL-1'ตั้งค่าใหม่
controller.clear()ล้างข้อความ
TextEditingController(text: '1')กำหนดค่าเริ่มต้น

6. onChanged กับ controller เลือกอย่างไร

สถานการณ์ใช้
รับค่าแล้วส่งต่อทันที ไม่ต้องอ่านย้อนหลังonChanged อย่างเดียว
ต้องล้างช่องจากโค้ดต้องมี controller
ต้องตั้งค่าเริ่มต้นแล้วแก้ได้ต้องมี controller
อ่านค่าตอนกดปุ่มยืนยันต้องมี controller
อย่าเรียก setState ใน onChanged ทุกตัวอักษร ถ้าไม่มีอะไรบนหน้าจอที่ต้องเปลี่ยนตาม — เพราะจะทำให้ทั้งหน้าจอวาดใหม่ทุกครั้งที่พิมพ์ ซึ่งบน PDA จะรู้สึกหน่วง (ทบทวน 1.10 เรื่องขอบเขต rebuild)

ถ้าจำเป็นต้องให้บางส่วนเปลี่ยนตามการพิมพ์ เช่นปุ่มล้างที่โผล่มาเมื่อมีข้อความ ให้ใช้เทคนิคจำกัดขอบเขตจาก 1.13

7. ห้ามสร้าง controller ใน build

// ผิด — สร้างใหม่ทุกครั้งที่วาดหน้าจอ
@override
Widget build(BuildContext context) {
  final controller = TextEditingController();    // ข้อความหายทุกรอบ
  return TextField(controller: controller);
}

อาการที่จะเจอคือ พิมพ์แล้วตัวอักษรหายทันที เพราะทุกครั้งที่หน้าจอวาดใหม่ controller ตัวใหม่ที่ว่างเปล่าถูกสร้างขึ้นมาแทน

เหตุผลตรงกับกฎใน 1.9 ที่ว่าห้ามสร้างสิ่งที่ต้องคืนทรัพยากรใน build — และยังทำให้ controller ตัวเก่าไม่ถูกคืน สะสมไปเรื่อย ๆ

8. ข้อความดิบไม่ใช่ข้อมูลของระบบ

ข้อความใน controller คือสิ่งที่ผู้ใช้กำลังพิมพ์ ซึ่งอาจยังไม่สมบูรณ์ ยังไม่ผ่านการตรวจ และมีช่องว่างเกิน

'  pal-1001  '     ← ข้อความดิบใน controller
      ↓ จัดรูปแบบและตรวจ (3.6)
'PAL-1001'         ← ข้อมูลที่ระบบใช้จริง

อย่าส่งข้อความดิบเข้าไปในตรรกะธุรกิจโดยตรง — ใน lab เราส่งเข้า ScanSession.accept() ซึ่งจัดรูปแบบและตรวจให้ก่อนเสมอ นี่เป็นแนวคิดเดียวกับด่านตรวจใน D1.19

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
พิมพ์แล้วตัวอักษรหายทันทีสร้าง controller ใน buildย้ายไปเป็น field ของ State
แอปกินหน่วยความจำเพิ่มเมื่อเข้าออกหน้าจอซ้ำลืม disposeคืนใน dispose ทุกตัว
A TextEditingController was used after being disposedคืน controller ที่ยืมมาจากแม่คืนเฉพาะที่สร้างเอง (1.6)
พิมพ์แล้วหน้าจอหน่วงเรียก setState ทุกตัวอักษรอ่านค่าตอนกดยืนยันแทน
ใส่ทั้ง controller และ initialValue แล้ว errorสองตัวนี้ใช้ร่วมกันไม่ได้เลือกอย่างใดอย่างหนึ่ง
ตั้งค่าใหม่แล้วเคอร์เซอร์เด้งไปต้นบรรทัดตั้ง controller.text ระหว่างที่ผู้ใช้พิมพ์อยู่ตั้งค่าเฉพาะเมื่อจำเป็นจริง เช่นหลังยิงสำเร็จ

10. แบบฝึกหัด

สร้างหน้าจอที่มีช่องรับรหัสพาเลทหนึ่งช่อง โดย

  1. กด Enter แล้วเพิ่มรหัสลงรายการด้านล่าง
  2. ล้างช่องหลังเพิ่มสำเร็จ
  3. ถ้าช่องว่าง ไม่ต้องเพิ่มอะไร
  4. แสดงจำนวนรายการที่มี
  5. ห้ามใช้ setState ใน onChanged
ดูแนวคำตอบและเหตุผล
class _CodeListScreenState extends State<CodeListScreen> {
  final _controller = TextEditingController();
  final List<String> _codes = <String>[];

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  void _add() {
    final code = _controller.text.trim();
    if (code.isEmpty) return;              // ข้อ 3
    setState(() => _codes.add(code));      // เรียกตอนกด Enter เท่านั้น
    _controller.clear();                   // ข้อ 2
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('รับแล้ว ${_codes.length} รายการ')),
      body: Column(
        children: [
          Padding(
            padding: const EdgeInsets.all(12),
            child: TextField(
              controller: _controller,
              autofocus: true,
              decoration: const InputDecoration(
                labelText: 'รหัสพาเลท',
                border: OutlineInputBorder(),
              ),
              onSubmitted: (_) => _add(),   // ข้อ 1
            ),
          ),
          Expanded(
            child: ListView.builder(
              itemCount: _codes.length,
              itemBuilder: (context, index) => ListTile(
                key: ValueKey<String>(_codes[index]),
                title: Text(_codes[index]),
              ),
            ),
          ),
        ],
      ),
    );
  }
}

ทำไม setState อยู่ที่ _add ไม่ใช่ onChanged: เพราะสิ่งที่ต้องเปลี่ยนบนหน้าจอคือ รายการ ไม่ใช่ข้อความที่กำลังพิมพ์ ตัวช่องกรอกจัดการการแสดงข้อความของตัวเองผ่าน controller อยู่แล้ว ถ้าเรียก setState ทุกตัวอักษร รายการทั้งหมดจะถูกวาดใหม่โดยไม่มีอะไรเปลี่ยน

ทำไม _controller.clear() อยู่นอก setState: เพราะการล้าง controller ทำให้ช่องอัปเดตตัวเองอยู่แล้ว ไม่ต้องบอก Flutter ให้วาดใหม่ — ใส่ในหรือนอกก็ทำงานได้ แต่การแยกออกมาทำให้เห็นชัดว่า setState ครอบเฉพาะสิ่งที่เป็นสถานะของหน้าจอจริง ๆ

ทำไมยังมี .trim() ทั้งที่ยังไม่ถึงบทเรื่องจัดรูปแบบ: เพราะถ้าไม่ตัดช่องว่าง การกด Enter ในช่องที่มีแต่ช่องว่างจะเพิ่มรายการว่างเข้าไป — เป็นตัวอย่างเล็ก ๆ ของสิ่งที่ 3.6 จะทำอย่างเป็นระบบ

ลองต่อ: ย้าย final _controller = TextEditingController(); เข้าไปใน build แล้วรัน จะเห็นว่าพิมพ์แล้วตัวอักษรหายทันที ซึ่งยืนยันหัวข้อ 7 ด้วยตาตัวเอง

11. สรุปท้ายบท

  • TextField แสดงและรับ ส่วน TextEditingController ถือข้อความจริง
  • สร้าง controller เป็น field ของ State และคืนใน dispose เสมอ
  • ห้ามสร้างใน build เพราะข้อความจะหายทุกรอบ
  • ใช้ onChanged เมื่อไม่ต้องอ่านย้อนหลัง ใช้ controller เมื่อต้องอ่านหรือล้าง
  • อย่าเรียก setState ทุกตัวอักษรถ้าไม่มีอะไรต้องเปลี่ยน
  • ข้อความดิบต้องผ่านการจัดรูปแบบและตรวจก่อนเข้าสู่ตรรกะธุรกิจ
