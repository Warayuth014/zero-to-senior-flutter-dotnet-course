1. ปัญหาที่บทนี้แก้

เราเจอ if (!mounted) return; มาหลายบทแล้ว บทนี้จะอธิบายให้ครบว่าทำไมต้องมี และที่สำคัญกว่าคือ กรณีที่ mounted เป็น true แต่ผลลัพธ์ยังใช้ไม่ได้

3. Mental model: ระหว่างที่รอ ผู้ใช้ทำอะไรก็ได้

await api.load(code);     ← ระหว่างบรรทัดนี้ ผู้ใช้อาจ...
                             • กดย้อนกลับออกจากหน้าจอ
                             • ยิงบาร์โค้ดใบใหม่
                             • ออกจากระบบ
                             • สลับไปหน้าจออื่น
if (!mounted) return;     ← จึงต้องตรวจก่อนแตะอะไร
ประโยคเดียวที่ต้องจำ: ทุกครั้งที่เห็น await ให้ถามว่า “ถ้าตอนที่ผลกลับมา สถานการณ์เปลี่ยนไปแล้ว บรรทัดถัดไปยังถูกต้องอยู่ไหม” — คำถามนี้ยกมาจาก D1.15 หัวข้อ 8 และตอนนี้ถึงเวลาตอบแล้ว

5. mounted ไม่ได้กันผลลัพธ์เก่า

นี่คือส่วนที่สำคัญที่สุดของบทนี้ ลองดูสถานการณ์นี้

เวลา 0.0 วิ  ผู้ใช้ยิง PAL-1001  →  เริ่มโหลด (ช้า 3 วินาที)
เวลา 0.5 วิ  ผู้ใช้ยิง PAL-1002  →  เริ่มโหลด (เร็ว 0.5 วินาที)
เวลา 1.0 วิ  ผลของ PAL-1002 กลับมา  →  แสดงบนจอ  ✓
เวลา 3.0 วิ  ผลของ PAL-1001 กลับมา  →  แสดงทับ    ✗ ผิด!

หน้าจอไม่ได้หายไปไหน mounted จึงเป็น true ตลอด แต่ผลที่แสดงเป็นของพาเลทใบเก่า — พนักงานจะเห็นข้อมูลของ PAL-1001 ทั้งที่เพิ่งยิง PAL-1002

ในงานคลังนี่คือความเสียหายจริง เพราะเขาอาจยืนยันการหยิบของตามข้อมูลที่เห็น

ความต่างที่ต้องเข้าใจ

สิ่งที่ทำตรวจ mounted ไหมเพราะ
setStateตรวจแตะหน้าจอที่อาจไม่มีแล้ว
ใช้ contextตรวจcontext ผูกกับหน้าจอ
ปลดธงในตรรกะไม่ตรวจตรรกะอาจถูกใช้ต่อ ต้องอยู่ในสถานะที่ถูกต้อง
ปิดการเชื่อมต่อไม่ตรวจต้องปิดไม่ว่าหน้าจอจะอยู่หรือไม่
การเขียน if (!mounted) return; ไว้ต้น finally เป็นความผิดพลาดที่พบบ่อย — เพราะจะทำให้การเก็บกวาดทั้งหมดถูกข้ามเมื่อผู้ใช้ออกจากหน้าจอ ธงจะค้าง การเชื่อมต่อจะไม่ถูกปิด

8. อย่าใช้ mounted แก้ปัญหาที่ควรแก้ที่โครงสร้าง

ถ้าพบว่าต้องเขียน if (!mounted) return; เต็มไปหมดจนอ่านยาก ให้ถามว่างานนั้นควรอยู่ที่หน้าจอจริงหรือเปล่า

งานควรอยู่ที่ไหนเมื่อออกจากหน้าจอ
โหลดข้อมูลมาแสดงหน้าจอทิ้งผลไปได้
บันทึกข้อมูลขึ้น serverควรอยู่ที่ชั้นนอกหน้าจอต้องทำงานต่อจนจบ
อัปโหลดไฟล์ขนาดใหญ่ควรอยู่ที่ชั้นนอกหน้าจอต้องทำงานต่อจนจบ

งานสองแถวล่างไม่ควรหยุดเพียงเพราะผู้ใช้กดย้อนกลับ — ซึ่งเป็นเหตุผลที่ Part 4 และ Part 9 จะย้ายงานเหล่านี้ออกไปอยู่ชั้นที่มีอายุยาวกว่าหน้าจอ

ใน lab เราแยกไว้บางส่วนแล้ว — ScanSession ถือสถานะการทำงาน ส่วนหน้าจอถือแค่การแสดงผล

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
setState() called after dispose()ไม่ตรวจ mounted หลัง awaitตรวจก่อนเรียก
หน้าจอแสดงข้อมูลของใบเก่าmounted ไม่ได้กันผลลัพธ์เก่าเทียบว่ายังตรงกับที่ต้องการ หรือกันไม่ให้มีสองคำขอ
ธงค้าง ปุ่มกดไม่ได้อีกใส่ mounted ไว้ต้น finallyปลดธงก่อน แล้วค่อยตรวจ mounted สำหรับ setState
ข้อผิดพลาดเรื่อง context ที่หมดอายุใช้ context หลัง await โดยไม่ตรวจใช้ context.mounted
งานบันทึกหยุดกลางคันเมื่อกดย้อนกลับงานผูกกับหน้าจอย้ายไปชั้นที่อายุยาวกว่า
ใส่ mounted ทุกบรรทัดจนอ่านไม่ออกแก้ปลายเหตุทบทวนว่างานควรอยู่ที่ไหน

  2. แก้ให้ครบ
  3. เขียนเทสต์ที่พิสูจน์ว่าปัญหาเรื่องผลลัพธ์เก่าถูกแก้แล้ว

ข้อ 1 — ปัญหาที่พบ

ปัญหาอาการ
ไม่ตรวจ mountedพังเมื่อผู้ใช้กดย้อนกลับระหว่างโหลด
ไม่กันผลลัพธ์เก่ายิงเร็ว ๆ สองใบแล้วเห็นข้อมูลผิดใบ
ไม่มี try/finallyถ้าโหลดล้มเหลว _loading ค้างเป็น true ตลอดไป
ไม่ดักข้อผิดพลาดผู้ใช้ไม่เห็นอะไรเลยเมื่อเน็ตหลุด
String? _pendingCode;

Future<void> _onScan(String code) async {
  _pendingCode = code;
  setState(() {
    _loading = true;
    _error = null;
  });

  try {
    final detail = await api.loadPallet(code);
    if (!mounted) return;
    if (_pendingCode != code) return;      // มีใบใหม่แล้ว ทิ้งผลนี้

    setState(() => _detail = detail);
  } on Exception catch (error) {
    if (!mounted || _pendingCode != code) return;
    setState(() => _error = 'โหลดข้อมูลไม่สำเร็จ');
    debugPrint('loadPallet failed: $error');
  } finally {
    // ปลดสถานะเฉพาะเมื่อยังเป็นคำขอล่าสุด
    // ไม่งั้นคำขอเก่าที่จบทีหลังจะปิดตัวโหลดของคำขอใหม่
    if (mounted && _pendingCode == code) {
      setState(() => _loading = false);
    }
  }
}

จุดที่ละเอียดที่สุด — เงื่อนไขใน finally

ถ้าเขียนแค่ if (mounted) setState(() => _loading = false); จะเกิดปัญหาตามลำดับนี้

ยิงใบที่ 1  →  _loading = true
ยิงใบที่ 2  →  _loading = true
ผลใบที่ 2 กลับมา  →  แสดงข้อมูล, _loading = false   ✓
ผลใบที่ 1 กลับมา  →  ทิ้งข้อมูล แต่ finally ยังทำงาน
                     _loading = false อีกครั้ง — ไม่เสียหายในกรณีนี้

กรณีนี้ยังไม่เสียหาย แต่ถ้าสลับลำดับ — ใบที่ 1 กลับมาก่อน แล้วใบที่ 2 ยังโหลดอยู่ — finally ของใบที่ 1 จะปิดตัวโหลดทั้งที่ใบที่ 2 ยังไม่เสร็จ ผู้ใช้จะเห็นหน้าจอว่างเปล่าโดยไม่มีตัวบอกว่ากำลังโหลด

การเทียบ _pendingCode == code ใน finally จึงจำเป็น

testWidgets('ผลของใบเก่าที่มาช้าต้องไม่ทับใบใหม่', (tester) async {

ทำไมเทสต์นี้จำเป็น

เพราะปัญหาผลลัพธ์เก่า แทบไม่มีทางเจอด้วยการทดสอบด้วยมือ — บนเครื่องพัฒนาที่เน็ตเร็ว คำขอจบเรียงตามลำดับเสมอ ปัญหาจะโผล่เฉพาะในคลังที่สัญญาณ WiFi ไม่สม่ำเสมอ ซึ่งเป็นที่ที่เราไปนั่งดีบักไม่ได้

การใช้ Completer สองตัวทำให้เราควบคุมลำดับการจบได้เอง ตามรูปแบบเดียวกับที่ใช้ใน 3.8

ลองต่อ: ลบบรรทัด if (_pendingCode != code) return; ออกแล้วรันเทสต์ — จะเห็นว่าล้มเหลวเพราะหน้าจอกลับไปแสดง PAL-1001 ซึ่งยืนยันว่าเทสต์จับปัญหานี้ได้จริง

11. สรุปท้ายบท

  • ระหว่าง await ผู้ใช้ทำอะไรก็ได้ — ต้องตรวจก่อนแตะหน้าจอ
  • ใช้ mounted ใน State และ context.mounted ใน callback
  • mounted กันหน้าจอที่หายไป แต่ไม่กันผลลัพธ์เก่า
  • ผลลัพธ์เก่าที่มาช้าอาจทับผลใหม่ ต้องตรวจว่ายังตรงกับที่ต้องการ
  • ทางที่ง่ายที่สุดคือไม่ให้มีสองคำขอพร้อมกัน
  • mounted ใช้กับการแตะหน้าจอ ไม่ใช่กับการเก็บกวาดใน finally
  • ถ้าต้องใส่ mounted เต็มไปหมด ให้ทบทวนว่างานควรอยู่ที่ไหน
