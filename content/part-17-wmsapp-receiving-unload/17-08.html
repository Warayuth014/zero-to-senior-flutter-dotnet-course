Pending pallet คือ recovery queue: receipt ถูกบันทึกแล้ว แต่ยังผูก pallet ไม่สำเร็จ หน้านี้จึงต้องซ่อมเฉพาะ assignment และห้ามยิงรับสินค้าเดิมซ้ำ

1. Load pending lines

PendingPalletScreen เรียก getPendingPalletLines() ตอนเปิดหน้า เก็บ loading/error/data แยกกัน และตรวจ mounted ก่อนเปลี่ยน state หลัง await เพื่อไม่อัปเดต widget ที่ถูก dispose แล้ว

2. Group by PO

final grouped = <String, List<PendingPalletLine>>{};
for (final line in lines) {
  grouped.putIfAbsent(line.poId, () => []).add(line);
}

การจัดกลุ่มด้วย poId ช่วยให้ operator เห็นบริบทเอกสาร ไม่ปะปน line จากหลาย PO ในรายการยาว

3. Identity ที่ต้องรักษา

lineId คือ receipt line ที่ backend สร้างแล้ว ไม่ใช่ partId และไม่ใช่ PO item id การ retry ต้องส่ง lineId เดิมกลับไปเพื่อผูก pallet กับ record ที่ถูกต้อง

4. Scan pallet dialog

เมื่อเลือกบรรทัด UI เปิด dialog ให้ scan/กรอก pallet แล้ว trim ค่า ตรวจไม่ให้ว่าง และ disable ปุ่มระหว่างส่ง request ส่วน palletType ใช้ condition ของ line เป็นข้อมูลประกอบตาม contract ปัจจุบัน

5. Assignment request

POST /receiving/assign-pallet
{
  "palletId": palletId,
  "palletType": line.condition,
  "operatorId": operatorId,
  "lineIds": [line.lineId]
}

API รองรับหลาย line แต่หน้าปัจจุบันซ่อมครั้งละหนึ่ง line จึงส่ง list ขนาดหนึ่ง

6. Refresh authoritative data

หลัง assign สำเร็จให้โหลด pending จาก server ใหม่แทนการลบ local อย่างเดียว เพราะ backend อาจ normalize pallet, เปลี่ยนสถานะ หรือมีรายการใหม่จากอุปกรณ์อื่นระหว่างนั้น

7. Error และ retry

network timeout ทำให้ไม่รู้แน่ว่า server commit หรือยัง ทางปลอดภัยคือ refresh ก่อน retry ถ้า line หายจาก pending แปลว่าสำเร็จแล้ว ถ้ายังอยู่จึงค่อยส่ง assignment ซ้ำ และ backend ควรทำ operation นี้ให้ idempotent

8. แบบฝึกหัด

เพิ่ม bulk assignment โดยเลือกหลาย line ภายใน PO เดียว ตรวจ condition ให้เข้ากัน สแกน pallet ครั้งเดียว แล้วส่ง lineIds ทั้งชุด พร้อมทดสอบ success, partial conflict และ refresh หลัง timeout
