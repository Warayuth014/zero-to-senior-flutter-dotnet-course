Package evaluation playbook: เป้าหมายไม่ใช่จำ packageนับพัน แต่เรียนวิธีทำความเข้าใจ dependencyใหม่อย่างปลอดภัยและพิสูจน์ด้วย spikeเล็ก

1. เริ่มจาก problem statement

เขียน painที่ต้องแก้ เช่น ownershipไม่ชัด, async cacheซ้ำ, search raceหรือทีม review transitionsยาก ถ้าไม่มี pain measurable การเพิ่ม packageคือภาระ

2. ตรวจแหล่งทางการ

ดู pub.dev publisher, latest stable, SDK/platform support, changelog, repository issues, licenseและmaintenance cadence อ่าน docsของ versionที่ lockfileใช้ ไม่อ้าง tutorialเก่าเป็น sourceหลัก

3. Dependency footprint

รัน flutter pub deps/pub outdated ดู transitive dependencies, constraintsและbuild/codegen impact ตรวจ native permissions/size/securityถ้ามี platform plugin

4. Spike behaviorเดียว

ย้าย Task flowหนึ่ง sliceรวม success/error/timeout/test ไม่ทำ counter demoอย่างเดียว เพราะ packageที่ดูสั้นใน happy pathอาจซับซ้อนเมื่อ production failure

5. Test upgrade

pin versionและเก็บ analyze/unit/widget tests รัน flutter pub upgrade --dry-run ก่อนอัปเดต อ่าน breaking changesและ commit lockfileสำหรับ app

6. Final lab

flutter run -t lib/state_patterns_main.dart
flutter analyze --no-pub
flutter test --no-pub

ลอง complete/refreshทุกแท็บและอธิบาย stale cacheเมื่อแต่ละ containerมี snapshotของตนเอง

7. Assignment

เลือกหนึ่งแนวสำหรับ Final Project เขียน ADRและลบอีกสอง packageจาก production branch แต่เก็บ comparison lab/บทเรียนเป็น reference พร้อมเพิ่ม unknown-outcome testให้ implementationที่เลือก

8. Graduation checkpoint

คุณควรเปิด packageที่ไม่เคยใช้ อ่าน official example/changelog สร้าง seamและ spikeพร้อม tests แล้วตัดสินใจได้ภายในข้อจำกัด ไม่จำเป็นต้องรู้ APIของทุก packageล่วงหน้า
