27-08 · State & Lifecycle

Riverpod AsyncValue refresh error และ mutation

Part 27: State Management: Provider, Riverpod & BLoC/Cubit

AsyncValue ไม่พอทุกอย่าง: AsyncValue เหมาะกับ lifecycleของ resource แต่ per-task mutation, stale snapshotและ transient message ยังต้อง modelใน domain/UI stateอย่างตั้งใจ

1. Initial async

asyncState.when(loading/error/data) ทำสาม branchชัดสำหรับ buildแรก หาก errorมี retry ให้ invalidate providerหรือเรียก recovery methodตาม semantics

2. Refresh with data

Lab เก็บ TaskPatternState.refreshing ภายใน AsyncData เพื่อรักษา listเดิมขณะ refresh ไม่เปลี่ยนทั้ง providerเป็น AsyncLoadingจนหน้ากระพริบ

3. Mutation state

busyTaskIds แยกราย taskเพราะ resourceทั้ง listยัง dataอยู่ การใช้ AsyncLoadingทั้ง listเมื่อ completeหนึ่งรายการจะล็อกงานอื่นและสื่อผิด

4. Known error

HTTP failureที่รู้ผลเก็บ errorพร้อม snapshotเดิม UIแสดง banner ส่วน initial build errorที่ไม่มี snapshotใช้ AsyncErrorเต็ม node

5. Unknown outcome

Notifier reload repositoryเพื่อ reconcileเหมือน TaskStore/Cubit Packageไม่เปลี่ยนกฎ distributed system; logicนี้ต้องเหมือนกันทุก implementation

6. Side effect message

messageใน stateอาจถูกแสดงซ้ำเมื่อ widget resubscribe Productionควรใช้ ref.listen พร้อม event identity/consume policy หรือแสดง statusใน UIที่ idempotent

7. Retry policy

Riverpod 3มี retry behaviorบางส่วน แต่ mutationธุรกิจต้องกำหนดเองและ replay keyเดิม อย่าเปิด generic automatic retryบน POSTเพียงเพราะ frameworkทำได้

8. Exercise

จำลอง refresh failขณะที่มี tasks ตรวจว่า listยังอยู่/error bannerขึ้น แล้วจำลอง initial build fail ตรวจว่าเข้า AsyncError ทั้งสองกรณีต้องมี recoveryต่างกัน
