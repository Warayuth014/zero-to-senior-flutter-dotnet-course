Provider dependency graph และ ProxyProvider

Part 27: State Management: Provider, Riverpod & BLoC/Cubit

Dependency graph: MultiProvider ทำ nested providers อ่านง่ายขึ้น ส่วน ProxyProvider สร้าง dependency ที่เปลี่ยนตาม provider อื่น อย่าใช้เพื่อซ่อน graph ที่หมุนเป็นวง

1. MultiProvider

MultiProvider(providers: [
  Provider<TaskRepository>(create: buildRepository),
  ChangeNotifierProvider<TaskStore>(create: buildStore),
], child: app)

เป็น syntax flatten เท่านั้น scope/order ยังสำคัญเหมือน nesting

2. ProxyProvider

เมื่อ repository ต้องเปลี่ยนตาม ConnectionProfile ใช้ ProxyProvider รับ profile/api แล้วสร้างหรือ update dependency ห้ามอ่าน profile ครั้งเดียวใน create แล้วหวังว่าจะเปลี่ยนตาม

3. Recreate หรือ update

เปลี่ยน server ควร recreate client/repository/store และล้าง session มากกว่าดัด baseUrl ของ object ที่มี in-flight requests ต้องกำหนด disposal ของ graph เก่า

4. Cyclic dependency

AuthStore ต้องใช้ ApiClient และ ApiClient ต้องอ่าน token ได้ แต่ไม่ควรให้ทั้งคู่ constructor อ้างกัน ใช้ token source interface/interceptor callback หรือ composition service ตัดวงจร

5. RepositoryProvider

ใน flutter_bloc มี RepositoryProvider ทำหน้าที่คล้าย Provider สำหรับ dependency ที่ไม่ใช่ state controller แนวคิด graph/ownership เดียวกันแม้ชื่อ package ต่าง

6. Test override

Provider widget test ครอบ subtree ด้วย Provider.value ของ fake repository/store แต่ controller unit test ยังควรสร้างตรงเพื่อ feedback เร็ว

7. Graph review

วาด nodes และ arrows ของ config→client→repository→store→widget ทุก nodeต้องมี ownerและ disposal policy ถ้า graph อธิบายไม่ได้ MultiProvider ยาวกว่าย่อมแก้ไม่ได้

8. Checkpoint

จำกัด package state management ไว้ composition/UI binding ส่วน repository interface ยังไม่ import package ใด ทำให้ graph เปลี่ยน framework โดย contract เดิมอยู่
