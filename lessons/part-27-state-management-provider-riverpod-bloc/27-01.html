เป้าหมาย Part 27: ไม่หาผู้ชนะตลอดกาล แต่ใช้ behavior เดียวกันวัดว่า package ใดทำให้ ownership, async workflow, rebuild และ test ของทีมชัดขึ้น

1. Flutter มี state อยู่แล้ว

setState, ValueNotifier, ChangeNotifier และ InheritedWidget เป็น primitives ที่เพียงพอ Package ไม่ได้ทำให้ business logic ถูกอัตโนมัติ แต่ช่วยกำหนดวิธีประกอบ dependency, subscribe state และจัด lifecycle ให้สม่ำเสมอ

2. เมื่อไร package เริ่มคุ้ม

เมื่อ state ข้ามหลาย route, dependency graph โต, async states ซ้อน, ต้อง override ใน test หรือทีมต้องการ convention ร่วม การส่ง constructor ยาว/หา ancestor เองเริ่มมีต้นทุน Package ช่วยลด plumbing แต่เพิ่ม API และ migration cost

3. Behavior ที่ตรึงไว้

ทั้งสามแบบโหลด task, refresh, complete ราย task, ป้องกัน command ซ้ำและ reconcile unknown outcome ผ่าน TaskRepository เดียวกัน ความต่างจึงอยู่ที่ state container/widget binding ไม่ใช่ endpoint คนละแบบ

4. ตัวเลือกใน lab

  • Provider + ChangeNotifier: mutable controller และ widget-tree scope
  • Riverpod AsyncNotifier: provider graph กับ AsyncValue
  • flutter_bloc + Cubit: immutable state stream และ explicit emit

5. อย่าติดตั้งเพราะนิยม

ถามว่าใคร own state, state อายุเท่าไร, side effect อยู่ไหน, test ต้องสร้างอะไร, failure path แสดงอย่างไร และทีม debug ได้หรือไม่ Popularity เป็น signal ด้าน ecosystem ไม่ใช่ architecture decision

6. Package ไม่แทน repository

Provider/Riverpod/Bloc ไม่ควร decode JSON หรือรู้ HTTP status โดยตรง Controller รับ typed repository เพื่อให้เปลี่ยน state library โดย data contract เดิมไม่พัง

7. วิธีเปิด lab

flutter run -t lib/state_patterns_main.dart
  --dart-define=WMS_API_BASE_URL=http://localhost:5080

สามแท็บใช้ backend เดียวกัน จึง refresh ก่อนเปรียบเทียบหลัง mutation จากอีกแท็บ

8. Rubric

ให้คะแนน readability, ownership, async/race handling, rebuild precision, test isolation, tooling, team familiarity และ migration cost อย่างละหลักฐาน ห้ามให้คะแนนจากจำนวนบรรทัดอย่างเดียว
