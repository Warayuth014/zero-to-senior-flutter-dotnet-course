1. ปัญหาที่บทนี้แก้

คนที่เพิ่งทำแอปคลังครั้งแรกมักคิดว่าต้องเขียนโค้ดคุยกับเครื่องสแกนโดยตรง เช่นเปิดกล้อง เชื่อม Bluetooth หรือเรียก SDK ของผู้ผลิต

ความจริงคือ เครื่องสแกนของ PDA ส่วนใหญ่ไม่ต้องเขียนโค้ดอะไรเลย เพราะมันปลอมตัวเป็นแป้นพิมพ์ — และเมื่อรู้ข้อนี้ การออกแบบหน้าจอทั้งหมดจะเปลี่ยนไป

ผลที่ตามมาซึ่งสำคัญที่สุด — ทุกเรื่องที่คุยกันใน 3.2 เรื่องโฟกัส กลายเป็นเรื่องคอขาดบาดตาย เพราะถ้าไม่มีช่องไหนโฟกัสอยู่ ข้อความจะไปไหนไม่รู้

4. ทำไมรูปแบบนี้ถึงดี

ข้อดีผลในทางปฏิบัติ
ไม่ต้องพึ่ง SDK ของผู้ผลิตเปลี่ยนยี่ห้อเครื่องสแกนได้โดยไม่แก้โค้ด
ทดสอบได้ด้วยแป้นพิมพ์ธรรมดาพัฒนาบนเครื่องคอมได้โดยไม่ต้องมี PDA
มีทางป้อนเองสำรองอยู่แล้วบาร์โค้ดเสียหายก็พิมพ์เองได้ทันที
เขียนเทสต์ได้จำลองการยิงในเทสต์ได้ตรง ๆ

ข้อสุดท้ายคือสิ่งที่ lab ทำ

/// จำลองการยิงบาร์โค้ด — เครื่องสแกนพิมพ์รหัสแล้วกด Enter ให้
Future<void> scan(WidgetTester tester, String code) async {
  await tester.enterText(find.byKey(const Key('barcode-field')), code);
  await tester.testTextInput.receiveAction(TextInputAction.done);
  await tester.pump();
}

สองบรรทัดนี้คือทั้งหมดที่ต้องใช้จำลองเครื่องสแกน — พิมพ์ข้อความ แล้วส่งสัญญาณยืนยัน เพราะนั่นคือสิ่งที่เครื่องสแกนทำจริง ๆ

5. การตั้งค่าเครื่องสแกนที่ต้องรู้

สิ่งที่ตั้งได้ที่ตัวเครื่อง ไม่ใช่ในโค้ด

ตั้งค่าควรตั้งเป็นถ้าตั้งผิดจะเกิดอะไร
suffixEnterถ้าเป็น Tab จะย้ายโฟกัสแทนที่จะยืนยัน
prefixไม่มีจะมีอักขระแปลกนำหน้ารหัสทุกครั้ง
หน่วงระหว่างตัวอักษรต่ำสุดที่ยังไม่ตกหล่นสูงไปจะยิงช้า ต่ำไปตัวอักษรอาจหาย
ภาษาแป้นพิมพ์ตรงกับที่ระบบตั้งไว้อักขระบางตัวเพี้ยน เช่นขีดกลางกลายเป็นตัวอื่น
อาการคลาสสิกที่โทษกันไปมา: พนักงานบอกว่า “ยิงแล้วเด้งไปช่องอื่น” ซึ่งฟังดูเหมือนบั๊กของแอป แต่จริง ๆ คือเครื่องสแกนถูกตั้ง suffix เป็น Tab ไม่ใช่ Enter — Tab แปลว่า “ไปช่องถัดไป” ในทุกระบบ ไม่ใช่ “ยืนยัน”

ทางแก้ที่ถูกคือแก้ที่การตั้งค่าเครื่อง และบันทึกไว้เป็นเอกสารการติดตั้ง ไม่ใช่เขียนโค้ดรองรับ Tab เพิ่ม เพราะจะกลายเป็นว่าแต่ละเครื่องพฤติกรรมไม่เหมือนกัน

6. อย่าเดาจากความเร็วในการพิมพ์

บางคนพยายามแยกว่า “ถ้าพิมพ์เร็วกว่า 30 มิลลิวินาทีต่อตัว แปลว่ามาจากเครื่องสแกน” ซึ่งใช้ไม่ได้จริง

ทำไมใช้ไม่ได้
เครื่องสแกนแต่ละรุ่นตั้งหน่วงต่างกัน
เมื่อ PDA ทำงานหนัก จังหวะจะเพี้ยน
ผู้ใช้วางข้อความจากที่อื่นได้ ซึ่งเร็วกว่าเครื่องสแกนอีก
ทดสอบซ้ำได้ยาก เพราะขึ้นกับสภาพเครื่อง ณ ขณะนั้น

ถ้าจำเป็นต้องแยกจริง ๆ ให้ตั้ง prefix เฉพาะที่ตัวเครื่องสแกน แล้วตรวจจากอักขระนั้น ซึ่งแน่นอนและทดสอบได้

7. ผลต่อการออกแบบหน้าจอ

เมื่อรู้ว่าเครื่องสแกนคือแป้นพิมพ์ ข้อกำหนดของหน้าจอจะชัดขึ้นทันที

  1. ต้องมีช่องที่โฟกัสอยู่เสมอ — ตาม 3.2
  2. ต้องบอกให้ชัดว่ากำลังรออะไร — เช่นป้าย “สแกนพาเลท” เทียบกับ “สแกนตำแหน่ง” ไม่งั้นพนักงานยิงผิดประเภท
  3. ต้องปิดช่องเมื่อไม่พร้อมรับ — เช่นระหว่างบันทึก ไม่งั้นรหัสจะเข้ามาปนกับข้อมูลที่กำลังส่ง
  4. ต้องมีปุ่มพิมพ์เองสำรอง — บาร์โค้ดเปียกน้ำหรือฉีกขาดเกิดขึ้นทุกวัน

ใน lab ข้อ 3 ถูกจัดการไว้แล้วสองชั้น

// ชั้นที่ 1 — ปิดช่องกรอกทางหน้าจอ
TextFormField(
  enabled: !_submitting,
  ...
)

// ชั้นที่ 2 — ปฏิเสธที่ตรรกะด้วย
ScanOutcome accept(String raw) {
  if (_busy) return ScanOutcome.busy;
  ...
}

เหตุผลที่ต้องมีสองชั้นเหมือนกับที่คุยใน 2.13 — การปิดช่องเป็นการสื่อสารกับผู้ใช้ ส่วนการปฏิเสธที่ตรรกะเป็นการป้องกันจริง ซึ่งเทสต์ตรวจไว้แล้ว

test('ระหว่างบันทึก ไม่รับตัวใหม่', () {
  final session = ScanSession(operatorName: 'สมชาย');
  session.beginSubmit();

  expect(session.accept('PAL-1001'), ScanOutcome.busy);
  expect(session.count, 0);
});

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ยิงแล้วเด้งไปช่องอื่นแทนที่จะยืนยันเครื่องสแกนตั้ง suffix เป็น Tabแก้ที่การตั้งค่าเครื่อง
ยิงแล้วไม่มีอะไรเกิดขึ้นเลยไม่มีช่องไหนโฟกัสทบทวน 3.2
มีอักขระแปลกนำหน้ารหัสทุกครั้งตั้ง prefix ไว้แก้ที่การตั้งค่าเครื่อง
ขีดกลางกลายเป็นอักขระอื่นภาษาแป้นพิมพ์ไม่ตรงกันตั้งภาษาให้ตรงทั้งเครื่องสแกนและระบบ
บางตัวอักษรหายไปหน่วงระหว่างตัวอักษรต่ำเกินเพิ่มหน่วงเล็กน้อยที่เครื่อง
ยิงระหว่างบันทึกแล้วข้อมูลปนกันไม่ได้ปิดรับระหว่างบันทึกปิดทั้งที่หน้าจอและที่ตรรกะ
พยายามเขียนโค้ดคุยกับเครื่องสแกนโดยตรงไม่รู้ว่ามันเป็นแป้นพิมพ์ใช้ TextField ธรรมดา

9. แบบฝึกหัด

ทีมติดตั้งรายงานปัญหาสามข้อจากหน้างานจริง จงระบุว่าแต่ละข้อควรแก้ที่แอปหรือที่การตั้งค่าเครื่อง พร้อมเหตุผล

  1. ยิงบาร์โค้ดแล้วโฟกัสเด้งไปที่ปุ่มบันทึก แต่ไม่มีอะไรถูกเพิ่ม
  2. ยิงแล้วได้รหัสถูกต้อง แต่ระบบบอกว่ารูปแบบไม่ถูกต้องทุกครั้ง เมื่อดูในช่องกรอกเห็นเป็น ]C1PAL-1001
  3. ยิงตอนกล่องยืนยันเปิดอยู่ แล้วรหัสไปโผล่ในหน้าจอถัดไปหลังกดยืนยัน
ดูแนวคำตอบและเหตุผล
ข้อแก้ที่เหตุผล
1การตั้งค่าเครื่องsuffix เป็น Tab ไม่ใช่ Enter
2การตั้งค่าเครื่องเปิดการส่งรหัส symbology นำหน้าไว้
3แอปไม่ได้ปิดรับระหว่างที่กล่องเปิดอยู่

ข้อ 1 — ทำไมไม่แก้ที่แอป

เราเขียนโค้ดรองรับ Tab เพิ่มได้ แต่จะเกิดปัญหาสองอย่าง — เครื่องที่ตั้ง Enter ถูกต้องอยู่แล้วจะมีพฤติกรรมต่างจากเครื่องนี้ และเมื่อมีเครื่องรุ่นที่สามที่ตั้งเป็นอย่างอื่นอีก โค้ดจะกลายเป็นชุด if ที่ไม่มีใครกล้าแตะ

ทางที่ถูกคือกำหนดเป็นข้อกำหนดการติดตั้งว่า ทุกเครื่องต้องตั้ง suffix เป็น Enter แล้วเขียนไว้ในเอกสาร ซึ่งทำให้แอปทำงานเหมือนกันทุกเครื่อง

ข้อ 2 — ทำไมไม่ตัดอักขระนำหน้าในโค้ด

]C1 คือรหัสบอกชนิดบาร์โค้ดที่เครื่องสแกนเติมมาให้ ถ้าเราเขียนโค้ดตัดสามตัวหน้าออก จะพังทันทีเมื่อเจอบาร์โค้ดชนิดอื่นที่รหัสนำหน้ายาวไม่เท่ากัน หรือเมื่อมีคนไปปิดการตั้งค่านี้ที่เครื่อง

อย่างไรก็ตาม ถ้าตัดสินใจว่าจะใช้รหัสนำหน้าเพื่อแยกชนิด ให้เขียนตัวแปลงที่คืนผลแบบมีความหมาย ไม่ใช่ตัดด้วยตำแหน่งตัวอักษร

// ถ้าจำเป็นต้องรองรับจริง — คืนผลที่มีความหมาย ไม่ใช่ substring ลอย ๆ
({String code, String? symbology}) parseScannerPayload(String raw) {
  final match = RegExp(r'^\](\w\d)(.*)$').firstMatch(raw);
  if (match == null) return (code: raw, symbology: null);
  return (code: match.group(2)!, symbology: match.group(1));
}

ข้อ 3 — ทำไมข้อนี้เป็นของแอป

เพราะไม่มีการตั้งค่าใดของเครื่องสแกนที่รู้ว่ากล่องยืนยันเปิดอยู่ — นั่นเป็นสถานะของแอปล้วน ๆ

ทางแก้คือปิดรับระหว่างที่กล่องเปิด แล้วคืนโฟกัสหลังปิด ตามที่คุยใน 3.2 หัวข้อ 7

Future<void> _submit() async {
  _session.beginSubmit();                    // ปิดรับทันที
  try {
    final confirmed = await _confirmSubmit();
    if (!mounted || confirmed != true) return;
    // ... บันทึก ...
  } finally {
    _session.endSubmit();                    // เปิดรับเสมอ แม้ยกเลิก
    if (mounted) _barcodeFocus.requestFocus();
  }
}

หลักที่ใช้ตัดสินได้ทุกครั้ง: ถ้าอาการเกี่ยวกับ รูปแบบของข้อมูลที่ส่งมา ให้แก้ที่เครื่อง ถ้าเกี่ยวกับ สถานะของแอป ณ ขณะนั้น ให้แก้ที่แอป

ลองต่อ: ในเทสต์ของ lab ลองเปลี่ยน receiveAction(TextInputAction.done) เป็นไม่เรียกเลย แล้วดูว่าเทสต์ล้มเหลวอย่างไร — นั่นคือการจำลองเครื่องที่ไม่มี suffix เลย

10. สรุปท้ายบท

  • เครื่องสแกนของ PDA ส่วนใหญ่ทำงานเหมือนแป้นพิมพ์ ไม่ต้องเขียนโค้ดพิเศษ
  • ทุกอย่างที่เรียนใน 3.1–3.4 ใช้ได้ตรง ๆ
  • จึงทดสอบด้วยแป้นพิมพ์ธรรมดาและเขียนเทสต์จำลองได้
  • suffix ต้องเป็น Enter ไม่ใช่ Tab
  • อย่าเดาแหล่งที่มาจากความเร็วในการพิมพ์
  • ต้องบอกให้ชัดว่ากำลังรอสแกนอะไร และปิดรับเมื่อไม่พร้อม
  • ปัญหาเรื่องรูปแบบข้อมูลแก้ที่เครื่อง ปัญหาเรื่องสถานะแก้ที่แอป

บทถัดไป: 3.6 จะจัดการกับความจริงที่ว่าข้อมูลที่ยิงมาไม่เคยสะอาด — ต้องจัดรูปแบบให้เป็นมาตรฐานเดียวก่อนนำไปเทียบหรือบันทึก
