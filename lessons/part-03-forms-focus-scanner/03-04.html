1. ปัญหาที่บทนี้แก้

ผู้ใช้ยืนยันข้อมูลได้หลายทาง — กดปุ่มบนหน้าจอ กด Enter บนแป้นพิมพ์ หรือให้เครื่องสแกนกด Enter ให้

ถ้าเราเขียนโค้ดแยกกันสำหรับแต่ละทาง วันหนึ่งจะมีทางที่ลืมแก้ ผลคือ “กดปุ่มแล้วได้ผลอย่างหนึ่ง กด Enter แล้วได้อีกอย่าง” ซึ่งเป็นบั๊กที่หาสาเหตุยากเพราะไม่มีใครทดสอบครบทุกทาง

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
keyboardTypeบอกระบบว่าควรแสดงแป้นพิมพ์แบบไหน
textInputActionปุ่มมุมขวาล่างของแป้นพิมพ์จะเป็นอะไร
onSubmittedยิงเมื่อกดปุ่มยืนยันบนแป้นพิมพ์หรือ Enter
inputFormattersตัวกรองที่จำกัดสิ่งที่พิมพ์ลงไปได้
keyboard wedgeเครื่องสแกนที่ทำงานเหมือนแป้นพิมพ์

3. Mental model: ทุกทางไปที่เดียว

กดปุ่มบนหน้าจอ ──┐
กด Enter        ──┼──→  _handleScan()  ──→  ตรรกะเดียว
เครื่องสแกนยิง   ──┘
ประโยคเดียวที่ต้องจำ: ทุกทางที่ผู้ใช้ยืนยันต้องเรียก method เดียวกัน — ถ้าต้องคัดลอกตรรกะไปอีกที่ แปลว่าออกแบบผิดแล้ว

ใน lab เราทำแบบนี้

TextFormField(
  ...
  // เครื่องสแกนกด Enter ให้ จึงเข้าทางนี้เป็นหลัก
  onFieldSubmitted: (_) => _handleScan(),
)

สังเกตว่า onFieldSubmitted รับค่าที่พิมพ์เข้ามาด้วย แต่เราไม่ใช้ (เขียนเป็น _) แล้วไปอ่านจาก controller แทน — เพราะ _handleScan ต้องเรียกจากปุ่มได้ด้วย ซึ่งปุ่มไม่มีค่าให้ส่ง การอ่านจากแหล่งเดียวคือ controller ทำให้ทั้งสองทางได้ค่าตรงกันแน่นอน

4. เลือกแป้นพิมพ์ให้เหมาะกับข้อมูล

keyboardTypeเหมาะกับ
TextInputType.numberจำนวน
TextInputType.numberWithOptions(decimal: true)น้ำหนัก
TextInputType.textข้อความทั่วไป (ค่าเริ่มต้น)
TextInputType.visiblePasswordรหัสที่ไม่อยากให้ระบบเดาคำให้
TextFormField(
  controller: _quantityController,
  keyboardType: TextInputType.number,      // แป้นตัวเลขสะดวกกว่า
  validator: (value) => validateQuantity(value),
)
keyboardType เป็นแค่คำแนะนำ ไม่ใช่การบังคับ — ผู้ใช้ยังวางข้อความจากที่อื่นได้ ต่อแป้นพิมพ์จริงได้ และเครื่องสแกนก็ส่งอะไรก็ได้ ดังนั้น ต้องมี validator เสมอ ไม่ว่าจะตั้ง keyboardType ไว้อย่างไร

5. textInputAction: ปุ่มมุมขวาล่าง

ค่าปุ่มแสดงเป็นเหมาะกับ
doneเสร็จสิ้นช่องสุดท้ายหรือช่องเดียว
nextถัดไปฟอร์มหลายช่องเรียงกัน
searchค้นหาช่องค้นหา

สำหรับช่องรับบาร์โค้ด ใช้ done เพราะการยิงหนึ่งครั้งคือการจบหนึ่งรายการ ไม่ใช่การไปช่องถัดไป

6. inputFormatters: กรองตั้งแต่ตอนพิมพ์

TextFormField(
  keyboardType: TextInputType.number,
  inputFormatters: [
    FilteringTextInputFormatter.digitsOnly,      // รับเฉพาะตัวเลข
    LengthLimitingTextInputFormatter(4),         // ไม่เกิน 4 หลัก
  ],
)

ต่างจาก validator ตรงที่ตัวกรองทำงาน ระหว่างพิมพ์ — ตัวอักษรที่ไม่ผ่านจะไม่ปรากฏเลย ส่วน validator ทำงานตอนตรวจ

inputFormattersvalidator
ทำงานเมื่อทุกครั้งที่พิมพ์ตอนสั่งตรวจ
ผู้ใช้เห็นอะไรพิมพ์ไม่ออกข้อความบอกเหตุผล
เหมาะกับกันสิ่งที่ไม่ควรมีเลยบอกว่าค่านั้นผิดเพราะอะไร
ห้ามใช้ digitsOnly กับช่องบาร์โค้ด เพราะบาร์โค้ดจริงมักมีขีดกลางและตัวอักษร เช่น PAL-1001 ถ้ากรองเหลือแต่ตัวเลข เครื่องสแกนจะยิงมาแล้วได้ 1001 ซึ่งผิด และผู้ใช้จะไม่รู้ว่าเกิดอะไรขึ้นเพราะไม่มีข้อความอะไรบอก

โดยทั่วไปสำหรับช่องบาร์โค้ด ให้ รับทุกอย่างเข้ามาก่อน แล้วค่อยจัดรูปแบบและตรวจในตรรกะ ซึ่งเป็นเรื่องของ 3.6

7. รวมทุกทางไว้ที่เดียว

// method เดียวที่ทุกทางเรียก
void _handleScan() {
  final outcome = _session.accept(_barcodeController.text);
  ...
}

// ทางที่ 1 — เครื่องสแกนหรือกด Enter
onFieldSubmitted: (_) => _handleScan(),

// ทางที่ 2 — ปุ่มบนหน้าจอ (ถ้ามี)
IconButton(onPressed: _handleScan, icon: const Icon(Icons.qr_code_scanner)),

สังเกตว่าปุ่มส่ง _handleScan ไปตรง ๆ โดยไม่ใส่วงเล็บ ตามที่เรียนใน D1.11 — ส่วนทางแรกต้องห่อด้วย (_) => เพราะ onFieldSubmitted ส่งค่ามาให้ด้วยแต่ _handleScan ไม่รับ

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ยิงบาร์โค้ดแล้วได้แต่ตัวเลข ขีดกลางหายใช้ digitsOnly กับช่องบาร์โค้ดเอาตัวกรองออก แล้วตรวจในตรรกะแทน
กดปุ่มกับกด Enter ได้ผลต่างกันเขียนตรรกะสองชุดรวมเป็น method เดียว
ตั้ง keyboardType: number แล้วยังมีตัวอักษรเข้ามาเข้าใจว่าเป็นการบังคับต้องมี validator เสมอ
กด Enter แล้วไม่มีอะไรเกิดขึ้นไม่ได้ต่อ onSubmittedเพิ่ม onFieldSubmitted
เครื่องสแกนยิงแล้วข้อมูลไม่ครบจำกัดความยาวไว้สั้นเกินตรวจความยาวจริงของบาร์โค้ดที่ใช้
ใช้ onChanged เรียกตรรกะแล้วทำงานทุกตัวอักษรเครื่องสแกนพิมพ์ทีละตัวใช้ onSubmitted เพราะยิงครั้งเดียวตอนจบ

แถวสุดท้ายสำคัญมากและเป็นกับดักที่เจอบ่อย — เครื่องสแกนพิมพ์รหัสทีละตัวอักษรเหมือนคนพิมพ์เร็วมาก ถ้าเราผูกตรรกะไว้กับ onChanged รหัส PAL-1001 จะทำให้ตรรกะทำงาน 8 ครั้ง โดย 7 ครั้งแรกเป็นข้อมูลที่ยังไม่ครบ

9. แบบฝึกหัด

หน้าจอนับสต็อกมีสองช่อง

  • ช่องบาร์โค้ด — รับจากเครื่องสแกน
  • ช่องจำนวน — พิมพ์เอง ไม่เกิน 4 หลัก
  1. ตั้งค่า keyboardType, textInputAction และ inputFormatters ของแต่ละช่องให้เหมาะสม
  2. ทำให้กด Enter ที่ช่องบาร์โค้ดแล้วไปช่องจำนวน และกด Enter ที่ช่องจำนวนแล้วบันทึก
  3. อธิบายว่าทำไมช่องบาร์โค้ดไม่ควรมี inputFormatters
ดูแนวคำตอบและเหตุผล
// ช่องบาร์โค้ด — รับทุกอย่าง แล้วไปตรวจในตรรกะ
TextFormField(
  controller: _barcodeController,
  focusNode: _barcodeFocus,
  autofocus: true,
  // ไม่ตั้ง keyboardType เพราะบาร์โค้ดมีทั้งตัวอักษรและตัวเลข
  textInputAction: TextInputAction.next,        // ข้อ 2
  // ไม่มี inputFormatters — ดูข้อ 3
  decoration: const InputDecoration(
    labelText: 'บาร์โค้ด',
    border: OutlineInputBorder(),
  ),
  onFieldSubmitted: (_) => _onBarcodeEntered(),
),

// ช่องจำนวน — พิมพ์เอง จึงกรองได้เต็มที่
TextFormField(
  controller: _quantityController,
  focusNode: _quantityFocus,
  keyboardType: TextInputType.number,
  textInputAction: TextInputAction.done,        // ข้อ 2
  inputFormatters: [
    FilteringTextInputFormatter.digitsOnly,
    LengthLimitingTextInputFormatter(4),
  ],
  validator: (value) => validateQuantity(value, max: 9999),
  onFieldSubmitted: (_) => _submit(),
),
void _onBarcodeEntered() {
  final outcome = _session.accept(_barcodeController.text);
  if (outcome.isFailure) {
    _barcodeFocus.requestFocus();     // ผิด -> อยู่ที่เดิมให้แก้
    return;
  }
  _barcodeController.clear();
  _quantityFocus.requestFocus();      // ถูก -> ไปช่องจำนวน (3.2)
}

ข้อ 3 — ทำไมช่องบาร์โค้ดไม่ควรมี inputFormatters

สามเหตุผลที่ทำงานร่วมกัน

  1. บาร์โค้ดมีอักขระหลากหลาย — ขีดกลาง ตัวอักษร บางระบบมีจุดหรือทับ ถ้ากรองผิดจะตัดข้อมูลสำคัญทิ้ง
  2. ตัวกรองไม่บอกอะไรผู้ใช้เลย — เมื่อเครื่องสแกนยิงมาแล้วบางส่วนถูกกรองทิ้ง หน้าจอจะแสดงรหัสที่ไม่ครบโดยไม่มีข้อความอะไร พนักงานจะคิดว่าเครื่องสแกนเสีย
  3. เราต้องการเห็นสิ่งที่ยิงมาจริง — เมื่อยิงผิด การเก็บค่าดิบไว้ให้ผู้ใช้เห็นช่วยให้เขาแก้ปัญหาได้เอง ตามที่ทำใน lab

ทางที่ถูกคือรับทุกอย่างเข้ามา แล้วให้ ScanSession.accept() เป็นคนตัดสินว่ารูปแบบถูกหรือไม่ พร้อมบอกเหตุผล — ซึ่งเป็นการแยกหน้าที่ตามหลักด่านตรวจใน D1.19

ข้อสังเกตของ _onBarcodeEntered: โฟกัสไปคนละที่ตามผลลัพธ์ — ถ้าผิดให้อยู่ที่เดิมเพื่อให้ยิงใหม่ได้ทันที ถ้าถูกจึงไปช่องจำนวน นี่คือการใช้ผลลัพธ์ที่มีความหมายจาก enum ให้เป็นประโยชน์ แทนที่จะคืนแค่ bool

ลองต่อ: ใส่ FilteringTextInputFormatter.digitsOnly ที่ช่องบาร์โค้ดแล้วยิง PAL-1001 ดู จะเห็นว่าได้ 1001 และระบบปฏิเสธด้วยข้อความ “รูปแบบบาร์โค้ดไม่ถูกต้อง” ทั้งที่พนักงานยิงถูก — เป็นตัวอย่างของบั๊กที่โทษกันไปมาระหว่างทีมแอปกับทีมอุปกรณ์

10. สรุปท้ายบท

  • ทุกทางที่ผู้ใช้ยืนยันต้องเรียก method เดียวกัน
  • อ่านค่าจาก controller ไม่ใช่จาก parameter ของ callback เพื่อให้ทุกทางได้ค่าตรงกัน
  • keyboardType เป็นคำแนะนำ ไม่ใช่การบังคับ — ต้องมี validator เสมอ
  • inputFormatters กรองตอนพิมพ์ ส่วน validator บอกเหตุผลตอนตรวจ
  • ห้ามใช้ตัวกรองกับช่องบาร์โค้ด
  • ใช้ onSubmitted ไม่ใช่ onChanged เพราะเครื่องสแกนพิมพ์ทีละตัว
