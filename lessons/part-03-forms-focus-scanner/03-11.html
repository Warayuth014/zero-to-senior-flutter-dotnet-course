1. HapticFeedback

Future<void> feedback(ScanOutcome outcome) => switch (outcome) {
  ScanAccepted() => HapticFeedback.mediumImpact(),
  ScanRejected() => HapticFeedback.heavyImpact(),
};

importจาก flutter/services.dart และไม่ assumeว่าอุปกรณ์ทุกเครื่องสั่น การเรียกไม่ควร block state transition; Absolute ใช้ medium/heavy impact คู่ flashสี

2. Visual flash และ status

สีเขียว/แดง flashสั้นช่วย peripheral vision แต่ต้องมี icon/text “รับแล้ว/ไม่พบ serial” เพราะตาบอดสีและแสงคลัง Timerต้อง cancelของเดิมก่อนตั้งใหม่เพื่อไม่ให้ flashเก่าล้าง stateใหม่ และ cancelใน dispose

3. เสียงตอบรับ

ใช้ SystemSound.play สำหรับเสียงระบบที่รองรับ หรือ audio asset/packageเมื่อ productต้องการ patternเฉพาะ โหลด/เตรียม playerล่วงหน้าเพื่อลด latency คุม volume/channelและเคารพ silent policy อย่าเล่นไฟล์ใหม่ทุก scanจน resourceสะสม

4. Scanner beep vs app sound

เสียง scannerมักแปลว่า “อ่านบาร์โค้ดทางกายภาพได้” ไม่ได้แปลว่า backendยอมรับ App feedbackต้องแยก accepted/rejectedอย่างชัด ผู้ใช้จึงไม่เข้าใจ beepแรกว่า transactionสำเร็จแล้ว

5. Feedback matrix

OutcomeภาพHaptic/เสียงFocus
Acceptedเขียว + countสั้น/สูงช่องถัดไปหรือเดิม
Duplicateส้ม + codeสองจังหวะเดิม
Rejectedแดง + วิธีแก้หนัก/ต่ำเดิมพร้อม retry
Network uncertainเหลือง + reconcileไม่ใช้เสียง successlockตาม policy

6. Accessibility และ preference

เพิ่ม Semantics live region/announcementอย่างไม่ spam, เคารพ reduce motion, ตั้งปิดเสียง/hapticได้ และไม่พึ่ง animationอย่างเดียว Feedbackต้องสั้นแต่ข้อมูล errorเต็มยังเปิดดูได้

7. แบบฝึกหัด

Scanner beepทุกครั้งแม้ serialซ้ำ ควรออกแบบ app feedbackให้ผู้ใช้แยกได้ทันทีอย่างไร?

แนวคำตอบ

เสียง hardwareเป็น “อ่าน labelได้”; app duplicateใช้ amber banner + icon duplicate + haptic/เสียง patternต่างจาก accepted, แสดง serialและไม่เพิ่ม count คืน focusช่องเดิม ผู้ใช้จึงรู้ว่าต้อง scanชิ้นอื่นแม้ไม่ได้อ่านประโยคยาว

8. จุดพลาด

อย่าแจ้ง successก่อน await server commit และอย่าใช้ SnackBarยาวกองทุก scan จนผลล่าสุดถูกบัง ใช้ status area/flashที่ replaceได้และเก็บ audit/historyแยกเมื่อจำเป็น
