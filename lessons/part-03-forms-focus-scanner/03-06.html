1. ปัญหาที่บทนี้แก้

ข้อมูลที่ยิงมาจากเครื่องสแกนไม่เคยสะอาด และความไม่สะอาดนั้นมองไม่เห็นด้วยตา

'PAL-1001'      ← ยิงจากเครื่อง A
'pal-1001'      ← ยิงจากเครื่อง B ที่ตั้งค่าต่างกัน
'PAL-1001 '     ← มีช่องว่างท้ายจากการตั้ง suffix
' PAL-1001'     ← ผู้ใช้พิมพ์เองแล้วเผลอเคาะช่องว่าง

ทั้งสี่บรรทัดคือพาเลทใบเดียวกัน แต่ถ้าเทียบด้วยเครื่องหมายเท่ากับตรง ๆ จะได้ว่าเป็นคนละใบทั้งหมด — ผลคือระบบกันซ้ำไม่ทำงาน และรายงานสต็อกมีพาเลทใบเดียวปรากฏสี่รายการ

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
normalizeแปลงหลายรูปแบบให้เป็นรูปแบบมาตรฐานเดียว
canonical valueรูปแบบมาตรฐานที่ระบบใช้เทียบและบันทึก
raw valueค่าดิบที่ได้รับมาก่อนแปลง
case-sensitiveตัวพิมพ์เล็กใหญ่มีความหมายต่างกัน
identifierรหัสที่ใช้ระบุตัวตน

3. Mental model: จุดเดียวที่แปลง

ข้อความดิบจากช่องกรอก
        ↓
   [ normalize ]      ← ที่นี่ที่เดียว
        ↓
   ค่ามาตรฐาน  ──→ เทียบ / เก็บ / ส่งขึ้น server
ประโยคเดียวที่ต้องจำ: แปลงครั้งเดียวตอนรับเข้า แล้วใช้ค่ามาตรฐานตลอดทั้งระบบ — ถ้ามีการแปลงกระจายอยู่หลายที่ วันหนึ่งจะมีที่ที่ใช้กฎไม่ตรงกัน แล้วเทียบไม่เจอโดยไม่มีใครรู้ว่าทำไม

4. ดูของจริงใน lab

/// จัดรูปแบบบาร์โค้ดที่อ่านได้ ให้เทียบกันได้เสมอ
///
/// เครื่องสแกนบางรุ่นแถมช่องว่าง บางรุ่นส่งตัวพิมพ์เล็ก
/// ถ้าไม่จัดรูปแบบก่อน 'pal-1001' กับ 'PAL-1001 ' จะถูกนับเป็นคนละใบ
String normalizeBarcode(String raw) => raw.trim().toUpperCase();

/// รหัสพาเลทที่ระบบนี้ยอมรับ
bool isValidPalletCode(String normalized) =>
    RegExp(r'^PAL-\d{4,6}$').hasMatch(normalized);

และจุดที่เรียกใช้มีที่เดียว

ScanOutcome accept(String raw) {
  if (_busy) return ScanOutcome.busy;

  final code = normalizeBarcode(raw);          // แปลงที่นี่
  if (code.isEmpty) return ScanOutcome.empty;
  if (!isValidPalletCode(code)) return ScanOutcome.badFormat;
  if (!_seen.add(code)) return ScanOutcome.duplicate;

  _accepted.add(code);                          // เก็บค่ามาตรฐาน
  return ScanOutcome.accepted;
}

สังเกตลำดับสามขั้น — แปลง แล้วตรวจรูปแบบ แล้วค่อยเทียบซ้ำ ถ้าสลับลำดับจะพัง เช่นถ้าเทียบซ้ำก่อนแปลง ก็กันซ้ำไม่ได้ตามที่ยกตัวอย่างในหัวข้อ 1

เทสต์ยืนยันไว้แล้ว

test('ยิงซ้ำถูกปฏิเสธ แม้ตัวพิมพ์และช่องว่างต่างกัน', () {
  final session = ScanSession(operatorName: 'สมชาย');
  session.accept('PAL-1001');

  expect(session.accept('  pal-1001'), ScanOutcome.duplicate);
  expect(session.count, 1);
});

5. ไม่ใช่ทุกอย่างที่แปลงได้

นี่คือจุดที่คนพลาดบ่อยที่สุด — เขียนฟังก์ชัน normalize ตัวเดียวแล้วเอาไปใช้กับข้อมูลทุกชนิด

ชนิดข้อมูลแปลงอย่างไรเหตุผล
รหัสพาเลท ตำแหน่งตัดช่องว่าง + ตัวพิมพ์ใหญ่ระบบไม่สนตัวพิมพ์
ซีเรียลของผู้ผลิตตัดช่องว่างอย่างเดียวบางระบบ aB9 กับ AB9 คนละตัว
รหัสผ่านห้ามแปลงอะไรเลยตัวพิมพ์มีความหมายเสมอ
จำนวนตัดช่องว่างแล้วแปลงเป็นตัวเลขเป็นตัวเลขจริง ไม่ใช่รหัส
กับดักเรื่องเลขศูนย์นำหน้า — รหัส 001234 ถ้าเผลอแปลงเป็นตัวเลขจะกลายเป็น 1234 แล้วเทียบกับข้อมูลใน server ไม่เจอ ให้เก็บรหัสทุกชนิดเป็น ข้อความ เสมอ และแปลงเป็นตัวเลขเฉพาะสิ่งที่เป็นจำนวนจริง ๆ (ทบทวน D1.19)

6. เก็บค่าดิบไว้ด้วยเมื่อจำเป็น

เมื่อยิงแล้วถูกปฏิเสธ ผู้ใช้ต้องเห็นว่ายิงอะไรเข้าไป ไม่ใช่เห็นค่าที่แปลงแล้ว

if (outcome.shouldClearInput) {
  _barcodeController.clear();      // ล้างเฉพาะเมื่อสำเร็จ
}

ใน lab เราจึงล้างช่องเฉพาะกรณีสำเร็จ ส่วนกรณีอื่นเก็บค่าดิบไว้ตามที่เทสต์ยืนยัน

// เก็บค่าไว้ให้ผู้ใช้เห็นว่ายิงอะไรเข้าไป
expect(field.controller?.text, '  pal-1001  ');

ประโยชน์จริงในหน้างาน — เมื่อพนักงานเห็นว่ารหัสที่ยิงมามีอักขระแปลกปน เขาจะรู้เองว่าฉลากเสียหรือเครื่องสแกนตั้งค่าผิด แทนที่จะยิงซ้ำสิบครั้งแล้วเรียกช่างไอที

7. แปลงชุดเปรียบเทียบด้วยกฎเดียวกัน

ข้อผิดพลาดที่ละเอียดอ่อนและหายาก — แปลงเฉพาะค่าที่ยิงมา แต่ลืมแปลงข้อมูลที่เอามาเทียบ

// ผิด — ข้อมูลจาก server ยังเป็นค่าดิบ
final scanned = normalizeBarcode(input);       // 'PAL-1001'
if (allowedCodes.contains(scanned)) { ... }    // ข้างในเป็น 'pal-1001'

// ถูก — แปลงทั้งสองฝั่งด้วยกฎเดียวกัน ครั้งเดียวตอนโหลด
final allowed = rawCodes.map(normalizeBarcode).toSet();
if (allowed.contains(scanned)) { ... }

สังเกตว่าเราแปลงชุดข้อมูลอ้างอิง ครั้งเดียวตอนโหลด ไม่ใช่แปลงทุกครั้งที่เทียบ ซึ่งทั้งถูกต้องและเร็วกว่า

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
กันซ้ำไม่ทำงาน ทั้งที่ยิงรหัสเดิมไม่ได้แปลงก่อนเทียบแปลงก่อนเสมอ
รายงานมีพาเลทใบเดียวหลายรายการเก็บค่าดิบลงฐานข้อมูลเก็บค่ามาตรฐาน
เลขศูนย์นำหน้าหายไปแปลงรหัสเป็นตัวเลขเก็บรหัสเป็นข้อความเสมอ
ซีเรียลที่ถูกต้องถูกปฏิเสธแปลงเป็นตัวพิมพ์ใหญ่ทั้งที่ระบบแยกตัวพิมพ์ใช้กฎแยกตามชนิดข้อมูล
เทียบกับข้อมูลจาก server ไม่เจอแปลงฝั่งเดียวแปลงทั้งสองฝั่งด้วยกฎเดียวกัน
ยิงผิดแล้วไม่รู้ว่าผิดเพราะอะไรล้างช่องทุกกรณีล้างเฉพาะเมื่อสำเร็จ
หาบั๊กไม่เจอเพราะแปลงหลายที่มีการแปลงกระจายอยู่รวมไว้ที่ฟังก์ชันเดียว

9. แบบฝึกหัด

ระบบรับข้อมูลสามชนิดจากเครื่องสแกน จงกำหนดกฎการแปลงของแต่ละชนิดพร้อมเหตุผล

ชนิดตัวอย่างค่าดิบข้อมูลเพิ่มเติม
รหัสพาเลท' pal-001234 \r\n'ระบบไม่แยกตัวพิมพ์
ซีเรียลผู้ผลิต'Sn-aB9 'ผู้ผลิตยืนยันว่าแยกตัวพิมพ์
จำนวน' 005 'เป็นจำนวนชิ้น
  1. เขียนฟังก์ชันแปลงของแต่ละชนิด
  2. อธิบายว่าทำไมใช้ฟังก์ชันเดียวกันทั้งสามไม่ได้
  3. เขียนเทสต์ที่จับความผิดพลาดถ้ามีคนเผลอใช้กฎผิด
ดูแนวคำตอบและเหตุผล
/// รหัสพาเลท — ไม่แยกตัวพิมพ์ จึงแปลงเป็นตัวพิมพ์ใหญ่ได้
String normalizePalletCode(String raw) => raw.trim().toUpperCase();

/// ซีเรียล — แยกตัวพิมพ์ จึงตัดช่องว่างอย่างเดียว
String normalizeSerial(String raw) => raw.trim();

/// จำนวน — เป็นตัวเลขจริง จึงแปลงเป็น int ได้
int? parseQuantity(String raw) => int.tryParse(raw.trim());

ผลลัพธ์กับค่าตัวอย่าง

ค่าดิบผลลัพธ์สังเกต
' pal-001234 \r\n''PAL-001234'เลขศูนย์นำหน้ายังอยู่ครบ
'Sn-aB9 ''Sn-aB9'ตัวพิมพ์เดิมถูกรักษาไว้
' 005 '5กลายเป็นตัวเลขจริง

ข้อ 2 — ทำไมใช้ฟังก์ชันเดียวกันไม่ได้

ถ้าใช้ trim().toUpperCase() กับทั้งสามชนิด จะเกิดความเสียหายคนละแบบ

  • ซีเรียลจะพัง — 'Sn-aB9' กลายเป็น 'SN-AB9' ซึ่งผู้ผลิตถือว่าเป็นคนละตัว ระบบจะเทียบกับฐานข้อมูลไม่เจอ และที่แย่กว่าคือถ้าบังเอิญเจอ อาจไปตรงกับซีเรียลของสินค้าคนละชิ้น
  • จำนวนจะยังเป็นข้อความ — '005' เอาไปบวกลบไม่ได้ และถ้าเทียบกับ '5' จะได้ว่าไม่เท่ากัน

และถ้าใช้ int.tryParse กับทั้งสาม รหัสพาเลท PAL-001234 จะแปลงไม่ได้เลย ส่วนถ้ารหัสเป็นตัวเลขล้วน 001234 จะกลายเป็น 1234 แล้วเลขศูนย์หายไปสี่ตัวโดยไม่มี error อะไร — เป็นบั๊กที่เงียบที่สุดในบทนี้

ข้อ 3 — เทสต์ที่จับการใช้กฎผิด

test('รหัสพาเลทเก็บเลขศูนย์นำหน้าไว้', () {
  expect(normalizePalletCode(' pal-001234 '), 'PAL-001234');
});

test('ซีเรียลรักษาตัวพิมพ์เดิม', () {
  expect(normalizeSerial('Sn-aB9 '), 'Sn-aB9');

  // เทสต์เชิงลบ — ถ้ามีคนเผลอเปลี่ยนไปใช้กฎของพาเลท เทสต์นี้จะล้ม
  expect(normalizeSerial('Sn-aB9'), isNot('SN-AB9'));
});

test('ซีเรียลที่ต่างกันแค่ตัวพิมพ์ ถือเป็นคนละตัว', () {
  final seen = <String>{};
  seen.add(normalizeSerial('Sn-aB9'));

  expect(seen.contains(normalizeSerial('SN-AB9')), isFalse);
});

test('จำนวนแปลงเป็นตัวเลขและตัดเลขศูนย์นำหน้าได้', () {
  expect(parseQuantity(' 005 '), 5);
  expect(parseQuantity('abc'), isNull);
});

ทำไมเทสต์ตัวที่สองมี isNot

เพราะเทสต์ปกติตรวจว่า “ได้ผลที่ถูก” แต่ไม่ได้กันคนเผลอเปลี่ยนกฎ — expect(normalizeSerial('Sn-aB9'), 'Sn-aB9') จะล้มถ้ามีคนเปลี่ยนเป็น toUpperCase() จริง แต่การเขียน isNot เพิ่มทำให้ เจตนาชัดขึ้นสำหรับคนอ่าน ว่าตัวพิมพ์ต่างกันคือคนละตัว ไม่ใช่แค่บังเอิญผลตรง

เทสต์ตัวที่สามคือตัวที่มีค่าที่สุด เพราะมันทดสอบ พฤติกรรมของระบบ ไม่ใช่แค่ผลของฟังก์ชัน — มันตอบคำถามว่า “ถ้ายิงซีเรียลที่ตัวพิมพ์ต่างกัน ระบบจะนับเป็นคนละตัวหรือไม่” ซึ่งเป็นสิ่งที่ธุรกิจสนใจจริง

ลองต่อ: เปลี่ยน normalizeSerial ให้ใช้ toUpperCase() แล้วรันเทสต์ — ควรเห็นสองตัวล้มเหลว ซึ่งยืนยันว่าเทสต์จับได้จริง จากนั้นแก้กลับ

10. สรุปท้ายบท

  • ข้อมูลที่ยิงมาไม่เคยสะอาด และความไม่สะอาดมองไม่เห็นด้วยตา
  • แปลงครั้งเดียวตอนรับเข้า แล้วใช้ค่ามาตรฐานตลอดระบบ
  • ลำดับคือ แปลง → ตรวจรูปแบบ → เทียบซ้ำ
  • กฎการแปลงต่างกันตามชนิดข้อมูล ไม่ใช่ฟังก์ชันเดียวใช้ทุกที่
  • เก็บรหัสเป็นข้อความเสมอ อย่าแปลงเป็นตัวเลข
  • แปลงข้อมูลที่เอามาเทียบด้วยกฎเดียวกัน
  • เมื่อยิงผิด ให้เก็บค่าดิบไว้ให้ผู้ใช้เห็น
