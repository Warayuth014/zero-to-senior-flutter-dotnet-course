1. ปัญหาที่บทนี้แก้

การตรวจจำนวนดูเหมือนง่ายที่สุดในบทนี้ — แค่ตรวจว่าเป็นตัวเลขและมากกว่าศูนย์ แต่ในงานจริงมีกรณีขอบมากกว่าที่คิด และเป็นจุดที่ความผิดพลาดกระทบสต็อกโดยตรง

' 12 '      ← มีช่องว่าง
'012'       ← มีศูนย์นำหน้า
'1.5'       ← ทศนิยมทั้งที่นับเป็นชิ้น
'12abc'     ← ผู้ใช้พิมพ์ต่อท้ายโดยไม่ตั้งใจ
'-5'        ← ติดลบ
''          ← ยังไม่กรอก
'999999'    ← เกินความเป็นจริง

4. ดูของจริงใน lab

String? validateQuantity(String? raw, {int max = 999}) {
  final text = raw?.trim() ?? '';
  if (text.isEmpty) return 'กรุณากรอกจำนวน';

  final value = int.tryParse(text);
  if (value == null) return 'จำนวนต้องเป็นตัวเลข';
  if (value <= 0) return 'จำนวนต้องมากกว่า 0';
  if (value > max) return 'จำนวนต้องไม่เกิน $max';
  return null;
}

สังเกตว่าแต่ละกรณีมีข้อความของตัวเอง ไม่ใช่ “จำนวนไม่ถูกต้อง” เหมือนกันหมด เพราะผู้ใช้ต้องรู้ว่าต้องแก้อะไร

ค่าที่ใส่ผลลัพธ์ผู้ใช้ควรทำอะไร
''กรุณากรอกจำนวนกรอก
'มาก'จำนวนต้องเป็นตัวเลขพิมพ์เป็นเลข
'0'จำนวนต้องมากกว่า 0ใส่เลขที่มากกว่า 0
'1000'จำนวนต้องไม่เกิน 999ลดจำนวน หรือแยกเป็นสองรายการ
' 012 'ผ่าน ได้ค่า 12—

5. ทำไมต้อง tryParse ไม่ใช่ parse

int.parse('มาก')      // โยน FormatException — โปรแกรมพัง
int.tryParse('มาก')   // คืน null — จัดการต่อได้

ทบทวนจาก D1.2 หัวข้อ 7: ใช้ tryParse เมื่อค่ามาจากผู้ใช้หรือเครือข่าย เพราะเราควบคุมไม่ได้ว่าจะได้อะไรมา

อย่าเขียน int.tryParse(text) ?? 0 ในการตรวจจำนวน เพราะจะทำให้ข้อความที่แปลงไม่ได้กลายเป็นเลข 0 เงียบ ๆ แล้วไปตกที่กฎ “ต้องมากกว่า 0” ผู้ใช้จะเห็นข้อความว่า “จำนวนต้องมากกว่า 0” ทั้งที่ปัญหาจริงคือพิมพ์ตัวอักษรปน — เป็นความผิดพลาดแบบเดียวกับที่ D1.19 เตือนเรื่องการกลบข้อมูลเสีย

6. ศูนย์นำหน้ากับรหัส

ทบทวนจาก 3.6 — รหัสห้ามแปลงเป็นตัวเลข แต่จำนวนแปลงได้ ความต่างอยู่ที่ความหมาย

รหัส เช่น 001234จำนวน เช่น 012
ศูนย์นำหน้ามีความหมายไหมมี — เป็นส่วนหนึ่งของรหัสไม่มี — 012 กับ 12 คือจำนวนเดียวกัน
เก็บเป็นชนิดอะไรข้อความตัวเลข
แปลงเป็นตัวเลขได้ไหมห้ามได้

ดังนั้น int.tryParse(' 012 ') ได้ 12 ซึ่งถูกต้องสำหรับจำนวน — และควรแสดงกลับเป็น 12 หลังบันทึก เพื่อไม่ให้ผู้ใช้สับสน

7. ทศนิยมและหน่วยนับ

ก่อนเขียนการตรวจ ต้องถามก่อนว่าหน่วยนับอนุญาตทศนิยมไหม

หน่วยทศนิยมชนิดที่ควรใช้
ชิ้น กล่อง พาเลทไม่int
กิโลกรัม เมตร ลิตรได้ต้องตกลงจำนวนทศนิยมกับ server
ถ้าหน่วยเป็นชิ้นแล้วผู้ใช้ใส่ 1.5 ต้องปฏิเสธด้วยข้อความที่ชัด เช่น “จำนวนชิ้นต้องเป็นจำนวนเต็ม” ไม่ใช่ปัดเป็น 1 หรือ 2 เงียบ ๆ — การปัดเศษที่ผู้ใช้ไม่รู้ตัวทำให้สต็อกไม่ตรงและไม่มีใครหาสาเหตุเจอ

สำหรับหน่วยที่มีทศนิยม อย่าใช้ double กับค่าที่ต้องแม่นยำโดยไม่กำหนดจำนวนทศนิยมให้ตรงกับฝั่ง .NET เพราะการคำนวณทศนิยมมีการปัดเศษที่มองไม่เห็น

8. เพดานที่มาจากข้อมูลจริง

เพดานคงที่อย่าง max: 999 ใช้ได้เป็นตาข่ายกันพิมพ์ผิด แต่งานจริงมักมีเพดานที่มาจากข้อมูล

String? validateMoveQuantity(String? raw, {required int available}) {
  final text = raw?.trim() ?? '';
  if (text.isEmpty) return 'กรุณากรอกจำนวน';

  final value = int.tryParse(text);
  if (value == null) return 'จำนวนต้องเป็นตัวเลข';
  if (value <= 0) return 'จำนวนต้องมากกว่า 0';
  if (value > available) return 'มีอยู่เพียง $available ชิ้น';
  return null;
}

สองข้อที่ต้องจำเกี่ยวกับเพดานแบบนี้

  1. ต้องแสดงค่าให้ผู้ใช้เห็นใกล้ช่องกรอก เช่น “เหลือ 7 ชิ้น” ไม่ใช่ให้เขาลองใส่แล้วถูกปฏิเสธ
  2. ค่านั้นอาจล้าสมัยแล้ว — เป็นภาพนิ่งจากตอนที่โหลดมา ระหว่างที่พนักงานกรอก คนอื่นอาจหยิบของไปแล้ว

ข้อสองคือเหตุผลที่ 3.3 หัวข้อ 7 บอกว่า server ต้องตรวจซ้ำ และเมื่อ server ปฏิเสธ ต้องแสดงข้อความที่ไม่ทำให้ผู้ใช้รู้สึกว่าตัวเองผิด เพราะเขาทำถูกตามข้อมูลที่เห็น

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แอปพังเมื่อผู้ใช้พิมพ์ตัวอักษรใช้ int.parseเปลี่ยนเป็น int.tryParse
ข้อความบอกว่า “ต้องมากกว่า 0” ทั้งที่พิมพ์ตัวอักษรใช้ ?? 0 กลบค่าที่แปลงไม่ได้แยกกรณีแปลงไม่ได้ออกมา
สต็อกไม่ตรงโดยหาสาเหตุไม่เจอปัดเศษทศนิยมเงียบ ๆปฏิเสธพร้อมข้อความชัด
ผู้ใช้ลองใส่หลายครั้งกว่าจะผ่านไม่ได้แสดงเพดานให้เห็นแสดง “เหลือ N ชิ้น” ใกล้ช่อง
ผ่านที่แอปแต่ server ปฏิเสธข้อมูลที่แอปถือล้าสมัยแสดงข้อความจาก server และเสนอให้โหลดใหม่
ทุกข้อผิดพลาดขึ้นข้อความเดียวกันรวมทุกกรณีเป็น “ไม่ถูกต้อง”แยกข้อความตามสาเหตุ
ช่องว่างถูกนับเป็น 0ไม่แยก “ยังไม่กรอก” จาก “กรอกเป็นศูนย์”ตรวจ isEmpty ก่อน

10. แบบฝึกหัด

หน้าจอย้ายสินค้ามีของเหลือ 12 ชิ้น หน่วยเป็นชิ้น ผู้ใช้ลองใส่ค่าเหล่านี้

ค่าที่ใส่ผลที่ควรได้
' 013 '?
'1.5'?
'abc'?
''?
'05'?
'-3'?
  1. เติมตารางให้ครบพร้อมข้อความที่ผู้ใช้จะเห็น
  2. เขียน validator ที่ให้ผลตามตาราง
  3. เขียนเทสต์ครบทุกแถว
ดูแนวคำตอบและเหตุผล
ค่าที่ใส่ผลลัพธ์ข้อความเหตุผล
' 013 'ไม่ผ่านมีอยู่เพียง 12 ชิ้นตัดช่องว่างและศูนย์นำหน้าได้ 13 ซึ่งเกิน
'1.5'ไม่ผ่านจำนวนชิ้นต้องเป็นจำนวนเต็มหน่วยเป็นชิ้น ทศนิยมไม่มีความหมาย
'abc'ไม่ผ่านจำนวนต้องเป็นตัวเลขแปลงไม่ได้เลย
''ไม่ผ่านกรุณากรอกจำนวนยังไม่กรอก คนละเรื่องกับกรอกผิด
'05'ผ่าน—ได้ 5 ซึ่งอยู่ในช่วง
'-3'ไม่ผ่านจำนวนต้องมากกว่า 0ติดลบไม่มีความหมายในการย้ายของ
String? validateMoveQuantity(String? raw, {required int available}) {
  final text = raw?.trim() ?? '';
  if (text.isEmpty) return 'กรุณากรอกจำนวน';

  // แยกกรณีทศนิยมออกมาก่อน เพื่อให้ข้อความตรงกับปัญหาจริง
  if (text.contains('.') || text.contains(',')) {
    return 'จำนวนชิ้นต้องเป็นจำนวนเต็ม';
  }

  final value = int.tryParse(text);
  if (value == null) return 'จำนวนต้องเป็นตัวเลข';
  if (value <= 0) return 'จำนวนต้องมากกว่า 0';
  if (value > available) return 'มีอยู่เพียง $available ชิ้น';
  return null;
}
void main() {
  const available = 12;

  test('เกินจำนวนที่มี', () {
    expect(
      validateMoveQuantity(' 013 ', available: available),
      'มีอยู่เพียง 12 ชิ้น',
    );
  });

  test('ทศนิยมถูกปฏิเสธด้วยข้อความเฉพาะ', () {
    expect(
      validateMoveQuantity('1.5', available: available),
      'จำนวนชิ้นต้องเป็นจำนวนเต็ม',
    );
  });

  test('ตัวอักษรถูกปฏิเสธคนละข้อความกับทศนิยม', () {
    expect(
      validateMoveQuantity('abc', available: available),
      'จำนวนต้องเป็นตัวเลข',
    );
  });

  test('ค่าว่างต่างจากศูนย์', () {
    expect(validateMoveQuantity('', available: available), 'กรุณากรอกจำนวน');
    expect(
      validateMoveQuantity('0', available: available),
      'จำนวนต้องมากกว่า 0',
    );
  });

  test('ศูนย์นำหน้าผ่านได้', () {
    expect(validateMoveQuantity('05', available: available), isNull);
  });

  test('ติดลบถูกปฏิเสธ', () {
    expect(
      validateMoveQuantity('-3', available: available),
      'จำนวนต้องมากกว่า 0',
    );
  });
}

ทำไมต้องดักทศนิยมก่อน tryParse

เพราะ int.tryParse('1.5') คืน null เหมือนกับ int.tryParse('abc') ทุกประการ ถ้าไม่แยกออกมาก่อน ผู้ใช้ที่พิมพ์ 1.5 จะเห็นข้อความ “จำนวนต้องเป็นตัวเลข” ทั้งที่เขาพิมพ์ตัวเลข — ข้อความนั้นทำให้เขางงและลองพิมพ์ใหม่แบบเดิม

การแยกออกมาทำให้ข้อความบอกปัญหาจริงว่าหน่วยนี้ไม่รับทศนิยม ซึ่งผู้ใช้แก้ได้ทันที

ทำไมตรวจทั้ง . และ ,

เพราะบางประเทศใช้จุลภาคเป็นตัวคั่นทศนิยม และผู้ใช้ที่คุ้นกับรูปแบบนั้นอาจพิมพ์ 1,5 — การไม่ดักไว้จะทำให้ได้ข้อความที่ไม่ตรงปัญหาเช่นกัน

จุดที่คนมักพลาดในเทสต์: เขียนแค่ expect(validateMoveQuantity('abc', ...), isNotNull) ซึ่งผ่านแม้ข้อความจะผิด — การตรวจข้อความจริงทำให้เทสต์จับได้เมื่อมีคนรวมกรณีเข้าด้วยกันในภายหลัง

ลองต่อ: ลบการดักทศนิยมออก แล้วรันเทสต์ — ตัวที่สองจะล้มเหลวโดยบอกว่าได้ “จำนวนต้องเป็นตัวเลข” แทน ซึ่งยืนยันว่าเทสต์จับความต่างของข้อความได้จริง

11. สรุปท้ายบท

  • แยกสามขั้น — ตัดช่องว่าง แปลง ตรวจช่วง
  • ใช้ int.tryParse เสมอ ไม่ใช่ int.parse
  • อย่าใช้ ?? 0 กลบค่าที่แปลงไม่ได้
  • แต่ละกรณีต้องมีข้อความของตัวเอง ผู้ใช้จะได้รู้ว่าแก้อะไร
  • ศูนย์นำหน้าไม่มีความหมายในจำนวน แต่มีในรหัส
  • อย่าปัดเศษทศนิยมเงียบ ๆ ให้ปฏิเสธพร้อมบอกเหตุผล
  • แสดงเพดานให้ผู้ใช้เห็นใกล้ช่องกรอก
  • ค่าที่แอปถืออาจล้าสมัย server ต้องตรวจซ้ำเสมอ
