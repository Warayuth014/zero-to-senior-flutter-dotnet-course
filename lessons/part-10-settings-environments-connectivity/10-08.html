1. คำถาม

แอปต้องรู้ว่าเซิร์ฟเวอร์ตอบไหม เพื่อแสดงจุดสถานะบนหัวจอ คำถามคือ ตรวจตอนไหน

คำตอบที่นึกออกก่อนคือ “ตรวจทุก 10 วินาที” ซึ่งผิดสำหรับเครื่องที่ถือทั้งวัน

2. ทำไมตัวจับเวลาถึงแพงบน PDA

ทุก 10 วินาทีตัวเลขจริงใน 8 ชั่วโมง
จำนวนคำขอ2,880 ครั้งต่อเครื่องต่อวัน
PDA 20 เครื่องในคลัง57,600 ครั้งต่อวัน
ประโยชน์ที่ได้จุดสีที่ผู้ใช้มองปีละไม่กี่ครั้ง

ต้นทุนไม่ได้มีแค่คำขอ Wi-Fi ที่ต้องปลุกวิทยุขึ้นมาทุก 10 วินาที กินแบตมากกว่าตัวคำขอเองหลายเท่า และ PDA ที่แบตหมดตอนบ่ายสามคือปัญหาที่ใหญ่กว่าจุดสีที่ไม่อัปเดต

3. จังหวะที่ควรตรวจ

หลักคือ ตรวจตอนที่คำตอบทั้งใหม่และกำลังจะถูกมอง

จังหวะเพราะ
ตอนเปิดจอหลักผู้ใช้เพิ่งเข้ามา กำลังจะเริ่มทำงาน
ตอนกลับมาจากพื้นหลังระหว่างที่แอปหลับ PDA อาจเดินออกนอกรัศมี Wi-Fi หรือเซิร์ฟเวอร์อาจถูกรีสตาร์ท และไม่มีอะไรบอกแอปเลย
หลังสลับ profileสถานะเดิมเป็นของเครื่องอื่น
ตอนผู้ใช้กดปุ่มทดสอบเขาถามเอง

ทั้งสี่จังหวะเป็น เหตุการณ์ ไม่ใช่ตัวจับเวลา จำนวนครั้งจึงเป็นสิบ ไม่ใช่พัน

/// เรียกตอนเปิดจอ ตอนกลับมาจากพื้นหลัง และหลังสลับ profile
/// **ไม่มีตัวจับเวลาที่วิ่งตลอด** เพราะเครื่องที่ถือทั้งวันไม่ควรเปลืองแบต
/// และคลื่นวิทยุไปกับจุดสีที่ไม่มีใครมอง
Future<ServerStatus> refreshStatus({http.Client? client}) async { ... }

4. จับจังหวะกลับมาจากพื้นหลัง

class _WarehouseShellState extends State<WarehouseShell>
    with WidgetsBindingObserver {

  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addObserver(this);
    unawaited(ConnectionController.instance.refreshStatus());
  }

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    if (state == AppLifecycleState.resumed) {
      unawaited(ConnectionController.instance.refreshStatus());
    }
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeObserver(this);
    super.dispose();
  }
}
ส่วนหน้าที่
with WidgetsBindingObservermixin ที่เปิดให้รับแจ้งเหตุการณ์ระดับแอป
addObserver / removeObserverสมัครและยกเลิก ต้องมาคู่กันเสมอ ไม่งั้นรั่ว (4.11)
AppLifecycleState.resumedกลับมาอยู่หน้าจอและรับ input ได้แล้ว
unawaited(...)บอกชัดว่าตั้งใจไม่รอผล ไม่ใช่ลืมใส่ await
สถานะอื่นของวงจรชีวิต: inactive (กำลังจะไป เช่นมีสายเข้า), paused (อยู่พื้นหลัง), detached (ยังรันแต่ไม่มีหน้าจอ), hidden ตรวจเฉพาะ resumed ก็พอสำหรับงานนี้

5. สองสถานะที่ต้องประกาศ

Future<ServerStatus> refreshStatus({http.Client? client}) async {
  ...
  _status = ServerStatus.checking;
  notifyListeners();                    // ← ครั้งที่หนึ่ง

  final result = await probeServer(baseUrl: url, client: client);
  _lastResult = result;
  _status = result.ok ? ServerStatus.connected : ServerStatus.disconnected;
  notifyListeners();                    // ← ครั้งที่สอง
  return _status;
}

ถ้าประกาศแค่ครั้งเดียวตอนจบ ผู้ใช้ที่กดปุ่มทดสอบจะเห็นหน้าจอนิ่งอยู่แปดวินาทีแล้วค่อยเปลี่ยน ซึ่งดูเหมือนปุ่มไม่ทำงาน เทสต์บังคับข้อนี้ไว้

test('ตรวจแล้วประกาศสองครั้ง คือกำลังตรวจ และผลลัพธ์', () async {
  final states = <ServerStatus>[];
  store.addListener(() => states.add(store.status));

  await store.refreshStatus(client: ...);

  expect(states, [ServerStatus.checking, ServerStatus.connected]);
});

เทสต์นี้ตรวจลำดับของสถานะ ไม่ใช่แค่ค่าสุดท้าย ซึ่งเป็นวิธีเดียวที่จะจับได้ว่ามีสถานะระหว่างทางจริง

6. สี่สถานะ ไม่ใช่สอง

enum ServerStatus { unknown, checking, connected, disconnected }
สถานะผู้ใช้เห็นหมายความว่า
unknownจุดสีเทายังไม่เคยตรวจ หรือเพิ่งสลับ profile
checkingจุดกะพริบกำลังถามอยู่
connectedจุดเขียวตรวจล่าสุดแล้วตอบ
disconnectedจุดแดงตรวจล่าสุดแล้วไม่ตอบ

unknown จำเป็นด้วยเหตุผลเดียวกับ AuthStatus.unknown ใน 8.6 — ถ้าไม่มี ค่าเริ่มต้นต้องเป็น disconnected ซึ่งทำให้ผู้ใช้เห็นจุดแดงตอนเปิดแอปทุกครั้ง ทั้งที่ยังไม่มีใครถามเลย

7. จุดสีบอกอดีต ไม่ใช่ปัจจุบัน

จุดเขียวแปลว่า “ตอนที่ตรวจครั้งล่าสุด เซิร์ฟเวอร์ตอบ” ไม่ได้แปลว่า “ตอนนี้ตอบ” — และไม่มีทางทำให้แปลว่าอย่างหลังได้ เพราะกว่าจะรู้ก็ต้องยิงคำขอไปแล้ว

ผลตามมาที่ต้องออกแบบเผื่อ

อย่าให้
ปิดปุ่มทำงานเมื่อจุดเป็นสีแดงให้กดได้ แล้วรายงานผลจริงตอนล้มเหลว
ข้ามการจัดการข้อผิดพลาดเพราะจุดเขียวจัดการทุกครั้งเหมือนไม่มีจุด
ใช้จุดตัดสินว่าจะยิงคำขอไหมยิงเสมอ ให้คำขอเป็นคนตอบ

จุดสถานะเป็นเครื่องมือวินิจฉัย ไม่ใช่เครื่องมือควบคุม — มีไว้ให้ผู้ใช้ที่เจอปัญหาตอบได้ว่า “เน็ตฉันหรือเซิร์ฟเวอร์เขา”

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แบตหมดเร็วผิดปกติตัวจับเวลาตรวจตลอดเวลาตรวจตามเหตุการณ์
ตัวจับเวลายังวิ่งหลังปิดจอไม่ได้ยกเลิกใน disposeยกเลิกทุกตัว (4.11)
กดปุ่มทดสอบแล้วเหมือนไม่มีอะไรเกิดขึ้นไม่ประกาศสถานะ checkingประกาศสองครั้ง
จุดแดงตอนเปิดแอปทุกครั้งไม่มีสถานะ unknownเริ่มที่ unknown
ผู้ใช้กดปุ่มไม่ได้เพราะจุดแดงเอาจุดไปควบคุมปุ่มให้กดได้เสมอ

9. แบบฝึกหัด

หัวหน้าอยากให้จุดสถานะแม่นกว่านี้ เพราะผู้ใช้บ่นว่าจุดเขียวแต่ยิงไม่เข้า

  1. เพิ่มความถี่เป็นทุก 5 วินาทีจะแก้ได้ไหม
  2. มีทางอื่นไหม
แนวคำตอบ

1. ไม่ — ต่อให้ตรวจทุก 1 วินาที ก็ยังมีช่องว่างระหว่างการตรวจกับการยิงจริงอยู่ดี ปัญหาไม่ได้อยู่ที่ความถี่ แต่อยู่ที่ธรรมชาติของการตรวจล่วงหน้า และการเพิ่มความถี่แลกแบตไปกับสิ่งที่แก้ไม่ได้

2. ใช้คำขอจริงเป็นตัวอัปเดตสถานะ ซึ่งแม่นที่สุดเพราะมันคือสิ่งที่เกิดขึ้นจริง

// ใน ApiClient — ทุกคำขอรายงานผลกลับมา
try {
  final response = await _client.get(...);
  onReachable?.call(true);
  return _decode(response);
} on SocketException {
  onReachable?.call(false);      // รู้ทันทีที่เกิดจริง
  rethrow;
}

ได้สามอย่างพร้อมกัน คือแม่นที่สุด, ไม่มีคำขอเพิ่มแม้แต่ครั้งเดียว และอัปเดตบ่อยพอดีคือทุกครั้งที่ผู้ใช้ทำงาน

ยังต้องเก็บการตรวจแบบเดิมไว้สำหรับสองกรณีที่คำขอจริงไม่ครอบคลุม คือตอนเปิดแอปก่อนยิงอะไรเลย และตอนกดปุ่มทดสอบที่อยู่ที่ยังไม่ได้ใช้งานในฟอร์ม

ข้อคิด: เมื่อการวัดกับสิ่งที่สนใจไม่ตรงกัน อย่าวัดถี่ขึ้น — ให้หาทางวัดสิ่งที่สนใจโดยตรง

10. สรุป

  • ตรวจตามเหตุการณ์ ไม่ใช่ตามตัวจับเวลา
  • เหตุการณ์ที่คุ้มค่าคือ เปิดจอ กลับจากพื้นหลัง สลับ profile และผู้ใช้กดถาม
  • ประกาศสถานะ checking ด้วย ไม่ใช่แค่ผลลัพธ์
  • ต้องมีสถานะ unknown แยกจาก “ตรวจแล้วไม่ตอบ”
  • จุดสถานะเป็นเครื่องมือวินิจฉัย ไม่ใช่เครื่องมือควบคุม
