1. ผู้ใช้ต้องการรู้อะไรจริง ๆ

เวลามีปัญหา ผู้ปฏิบัติงานในคลังถามคำถามเดียว

“เครื่องฉันมีปัญหา หรือระบบมีปัญหา”

เพราะคำตอบสองอย่างนี้พาไปคนละทาง

คำตอบเขาทำอะไรต่อ
เครื่องนี้ไม่มีสัญญาณเดินไปที่ที่มีสัญญาณ แล้วทำต่อ
เซิร์ฟเวอร์ไม่ตอบโทรแจ้งไอที แล้วรอ หรือใช้กระดาษไปก่อน

จุดสถานะที่ดีต้องช่วยแยกสองอย่างนี้ให้ได้ ถ้าแยกไม่ได้ ผู้ใช้จะเสียเวลาเดินหาสัญญาณทั้งที่เซิร์ฟเวอร์ล่ม

2. สองระดับที่ต่างกัน

มีสัญญาณเน็ตไหมเซิร์ฟเวอร์ตอบไหม
รู้ได้จากระบบปฏิบัติการ (connectivity_plus)ยิงคำขอจริง
รู้ได้เร็วแค่ไหนทันทีต้องรอคำตอบ
บอกอะไรได้“ไม่ต้องลองก็รู้ว่าไม่ได้”“ลองแล้วได้/ไม่ได้”
บอกอะไรไม่ได้ต่อ Wi-Fi อยู่ แต่ Wi-Fi นั้นไปไม่ถึงเซิร์ฟเวอร์—
แถวสุดท้ายคือกับดัก — “มีสัญญาณ” ไม่ได้แปลว่า “ใช้งานได้” ในคลังที่มี Wi-Fi หลายวง PDA อาจเกาะวงที่แรงกว่าแต่ไปไม่ถึงเซิร์ฟเวอร์ ระบบปฏิบัติการจะรายงานว่าเชื่อมต่ออยู่

ผลคือ สถานะเครือข่ายใช้ยืนยันว่าใช้ไม่ได้ ไม่ใช่ยืนยันว่าใช้ได้

3. ใช้สถานะเครือข่ายอย่างไรให้ถูก

ใช้ทำอย่าใช้ทำ
อธิบายความล้มเหลวที่เกิดแล้ว ให้ชัดขึ้นปิดปุ่มไว้ล่วงหน้า
เลือกข้อความที่ตรงกว่าข้ามการยิงคำขอ
ลองใหม่อัตโนมัติเมื่อสัญญาณกลับมาตัดสินว่าคำขอจะสำเร็จหรือไม่
// ยิงเสมอ แล้วใช้สถานะเครือข่ายอธิบายผลที่ได้
} on ApiException catch (error) {
  if (error.kind == ApiFailureKind.network) {
    _failure = hasNoNetwork
        ? const Failure('เครื่องนี้ไม่มีสัญญาณ ลองเดินไปที่ที่สัญญาณดีกว่า')
        : const Failure('มีสัญญาณ แต่ติดต่อเซิร์ฟเวอร์ไม่ได้ แจ้งไอทีถ้ายังไม่หาย');
  }
}

ข้อความสองอันนี้พาผู้ใช้ไปคนละทาง และนั่นคือทั้งหมดที่จุดสถานะควรทำ

4. ทำไมห้ามปิดปุ่ม

การปิดปุ่มเมื่อ “ออฟไลน์” ดูเหมือนช่วยผู้ใช้ แต่สร้างปัญหาสามข้อ

ปัญหารูปธรรม
รายงานผิดพลาดได้ระบบปฏิบัติการบอกว่าไม่มีเน็ตทั้งที่มี ผู้ใช้ทำงานไม่ได้ทั้งที่ทำได้
ผู้ใช้ไม่รู้ว่าทำไมกดไม่ได้ปุ่มจางคือความลึกลับ ต่างจากข้อความผิดพลาดที่อธิบาย
ต้องมีโค้ดจัดการความล้มเหลวอยู่ดีสัญญาณอาจหายระหว่างที่คำขอกำลังเดินทาง — เขียนโค้ดสองชุดเพื่อป้องกันเรื่องเดียว

แถวสุดท้ายเป็นเหตุผลทางวิศวกรรมล้วน ๆ — โค้ดที่ปิดปุ่มไม่ได้แทนที่โค้ดจัดการความล้มเหลว มันแค่เพิ่มเข้ามาอีกชุด

5. จุดสถานะที่แสดงข้อมูลครบ

ListenableBuilder(
  listenable: store,
  builder: (context, _) => Tooltip(
    message: store.lastResult?.message ?? 'ยังไม่ได้ตรวจ',
    child: Row(
      children: [
        _StatusDot(status: store.status),
        const SizedBox(width: 6),
        // ชื่อ profile ไม่ใช่ IP — IP ยาวเกินและผู้ใช้จำชื่อได้ดีกว่า (10.4)
        Text(store.active?.name ?? ''),
      ],
    ),
  ),
)
ส่วนตอบคำถามว่า
สีของจุดตรวจครั้งล่าสุดผลเป็นอย่างไร
ชื่อ profileตอนนี้ต่อกับเครื่องไหน
ข้อความเมื่อกดค้างล้มเหลวเพราะอะไร

ข้อที่สองสำคัญและมักถูกลืม — ปัญหาที่พบบ่อยที่สุดในการใช้งานจริงไม่ใช่ “ต่อไม่ได้” แต่คือ “ต่อผิดเครื่องโดยไม่รู้ตัว” ซึ่งจุดสีเขียวอย่างเดียวช่วยอะไรไม่ได้เลย

6. เมื่อสัญญาณกลับมา

// ฟังการเปลี่ยนแปลงของเครือข่าย แล้วตรวจซ้ำเมื่อกลับมา
_subscription = Connectivity().onConnectivityChanged.listen((result) {
  final online = !result.contains(ConnectivityResult.none);
  if (online && !_wasOnline) {
    unawaited(store.refreshStatus());
  }
  _wasOnline = online;
});
ทำอย่าทำ
ตรวจสถานะซ้ำยิงคำสั่งที่ค้างอยู่ซ้ำอัตโนมัติ
โหลดข้อมูลที่แสดงอยู่ใหม่ส่งคำสั่งที่ผลไม่แน่นอนซ้ำ

ฝั่งขวาคือกฎเดิมจาก 7.10 — คำสั่งที่ไม่รู้ผลห้ามส่งซ้ำเอง ต้องให้ผู้ใช้ตัดสินหลังเห็นสถานะจริง เพราะการรับของเข้าคลังซ้ำสองครั้งแก้ยากกว่าการรับช้าไปหนึ่งนาที

อย่าลืมยกเลิก subscription ใน dispose ตามกฎใน 4.11

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ผู้ใช้ทำงานไม่ได้ทั้งที่เน็ตปกติเชื่อ connectivity แล้วปิดปุ่มยิงเสมอ
จุดเขียวแต่ต่อผิดเครื่องไม่ได้แสดงชื่อ profileแสดงชื่อคู่กับจุด
ผู้ใช้ไม่รู้ว่าล้มเหลวเพราะอะไรจุดสีอย่างเดียวไม่มีรายละเอียดเก็บและแสดงข้อความล่าสุด
สัญญาณกลับมาแล้วยิงคำสั่งซ้ำเองลองใหม่อัตโนมัติกับคำสั่งที่ไม่รู้ผลลองใหม่เฉพาะการอ่าน
แอปช้าลงหลังใช้ไปนานไม่ได้ยกเลิก subscriptionยกเลิกใน dispose

8. แบบฝึกหัด

หัวหน้าคลังขอสองอย่าง

  1. “ถ้าเน็ตหลุด ให้ขึ้นแถบแดงเต็มจอว่าใช้งานไม่ได้”
  2. “ให้เก็บงานที่ทำค้างไว้แล้วส่งเองตอนเน็ตกลับมา”
แนวคำตอบ

1. อย่าทำตามตรงตัว เพราะแถบแดงเต็มจอตั้งอยู่บนข้อมูลที่เชื่อไม่ได้ (§2) ผู้ใช้ที่เห็นแถบแดงทั้งที่ทำงานได้จะเรียนรู้ที่จะไม่สนใจมัน แล้ววันที่มันถูกจริงก็จะไม่มีใครสนใจเหมือนกัน

สิ่งที่ตอบความต้องการจริงคือ “ผู้ใช้ไม่รู้ตัวว่าออฟไลน์แล้วทำงานเสียเปล่า” ซึ่งแก้ได้ด้วย

  • แถบบางที่หัวจอเมื่อคำขอจริงล้มเหลว ไม่ใช่เมื่อระบบปฏิบัติการบอกว่าไม่มีเน็ต
  • ข้อความบอกว่าล้มเหลวเมื่อไหร่ เช่น “ติดต่อเซิร์ฟเวอร์ไม่ได้ตั้งแต่ 14:32”
  • ปุ่มลองใหม่ที่กดได้ทันที

2. ทำได้ แต่ต้องแยกสองอย่าง

ทำได้ปลอดภัยอันตราย
เก็บร่างที่ผู้ใช้กรอกไว้ ไม่ให้หายส่งคำสั่งเองเมื่อเน็ตกลับมา
เตือนว่ามีงานค้างรอส่งส่งโดยผู้ใช้ไม่เห็น

เหตุผลที่ฝั่งขวาอันตราย: ระหว่างที่ออฟไลน์อยู่ครึ่งชั่วโมง สถานะของจริงในคลังอาจเปลี่ยนไปแล้ว — พาเลทที่จะรับเข้าอาจถูกคนอื่นรับไปแล้ว การส่งคำสั่งเก่าโดยไม่ตรวจสอบจะเขียนข้อมูลผิด และไม่มีใครรู้ว่าเกิดขึ้นเมื่อไหร่

ทางที่ปลอดภัยคือเก็บร่างไว้ แล้วเมื่อเน็ตกลับมา ให้แสดงว่า “มีงานค้าง 3 รายการ” พร้อมปุ่มให้ผู้ใช้ตรวจแล้วส่งเอง ซึ่งเป็นหัวข้อเต็ม ๆ ของ Part 29

9. สรุป

  • ผู้ใช้อยากรู้แค่ว่า “เครื่องฉันหรือระบบ” — ออกแบบให้ตอบคำถามนั้น
  • สถานะเครือข่ายยืนยันได้ว่าใช้ไม่ได้ แต่ยืนยันไม่ได้ว่าใช้ได้
  • ยิงคำขอเสมอ ใช้สถานะอธิบายผล ไม่ใช่ขวางไว้ก่อน
  • แสดงชื่อ profile คู่กับจุดสี เพราะ “ต่อผิดเครื่อง” เจอบ่อยกว่า “ต่อไม่ได้”
  • สัญญาณกลับมาให้โหลดข้อมูลใหม่ ไม่ใช่ส่งคำสั่งซ้ำ

บทหน้า: ประกอบทั้งหมดเป็นหน้าตั้งค่าที่ใช้งานได้จริง
