3. Typed settings หมายความว่าอะไร

Typed settings คือการเก็บค่าตั้งค่าเป็นชนิดที่มีความหมาย แทนที่จะเป็น Map<String, dynamic> หรือถุงของ String

เทียบสองแบบ

// แบบถุง
final settings = <String, dynamic>{};
settings['port'] = '6191';
final port = settings['prot'];        // พิมพ์ผิด ได้ null คอมไพล์ผ่าน
final url = 'http://${settings['host']}:${settings['port']}';
// แบบมีชนิด
class ServerProfile {
  final String host;
  final int port;
  String get baseUrl => '${protocol.name}://$host:$port${normalizeBasePath(basePath)}';
}

final url = profile.baseUrl;          // พิมพ์ผิดชื่อฟิลด์ = คอมไพล์ไม่ผ่าน
แบบถุงแบบมีชนิด
พิมพ์ชื่อคีย์ผิดแล้วเงียบคอมไพเลอร์ฟ้อง
ทุกที่ที่ใช้ต้องรู้ว่าคีย์ชื่ออะไรและเป็นชนิดไหนอ่านจากคลาสได้
การประกอบ URL กระจายทุกที่ที่ใช้อยู่ที่ getter เดียว
เพิ่มค่าใหม่ไม่มีใครรู้เพิ่มฟิลด์ คอมไพเลอร์บอกทุกที่ที่ต้องแก้

5. enum แทนข้อความ

enum ServerProtocol {
  http,
  https;

  static ServerProtocol parse(String? raw) =>
      raw?.toLowerCase() == 'https' ? ServerProtocol.https : ServerProtocol.http;
}

ถ้าเก็บเป็น String จะมีค่าที่เป็นไปได้ไม่จำกัด — 'https', 'HTTPS', 'https://', 'ftp' ล้วนใส่ได้หมด พอเป็น enum เหลือสองค่าเท่านั้น และ switch ที่ครอบคลุมไม่ครบจะคอมไพล์ไม่ผ่าน

สังเกต parse ที่มีค่าปริยาย — อ่านค่าที่เก็บไว้แล้วไม่รู้จัก ให้ตกไปที่ http ไม่ใช่โยน เพราะไฟล์ที่เราเขียนเองบนเครื่องนี้ ไม่ใช่สัญญากับเซิร์ฟเวอร์ (10.5 จะอธิบายความต่างนี้)

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เปลี่ยนพอร์ตแล้วบางส่วนของแอปยังยิงพอร์ตเก่าค่าถูกคัดลอกไว้หลายที่รวมไว้ที่เดียว อ่านผ่าน getter
ผู้ใช้ตั้งค่าผิดแล้วแอปพังโดยไม่บอกอะไรไม่มีการตรวจตรวจรายช่องพร้อมบอกว่าควรไปอยู่ที่ไหน (10.7)
ต้อง build ใหม่ทุกครั้งที่เซิร์ฟเวอร์ย้ายที่อยู่เป็นค่าคงที่ในโค้ดทำเป็น profile ที่ผู้ใช้แก้ได้
เปิดให้ผู้ใช้แก้ทุกอย่างรวมถึง /apiคิดว่ายืดหยุ่นไว้ก่อนดีเปิดเฉพาะค่าที่ผู้ใช้รู้คำตอบ

8. แบบฝึกหัด

ทีมเสนอให้เพิ่มค่าตั้งค่าที่ผู้ใช้แก้ได้สี่ตัว ตัดสินทีละตัวว่าควรให้แก้ไหม

  1. ระยะเวลา timeout ของคำขอ
  2. ชื่อเครื่อง PDA ที่แสดงบนหัวจอ
  3. จำนวนรายการต่อหน้าในลิสต์
  4. เปิด/ปิดเสียงบี๊บตอนสแกน
แนวคำตอบ

1. ไม่ — ผู้ใช้ไม่มีข้อมูลพอจะตัดสิน และค่าที่ตั้งผิดทำให้เกิดปัญหาที่วินิจฉัยยาก เช่นตั้ง 2 วินาทีแล้วคำขอที่ปกติจะเสร็จใน 3 วินาที กลายเป็น timeout ที่ผลไม่แน่นอน (7.10) ถ้าเน็ตในคลังช้าจริง ให้ทีมพัฒนาปรับค่าในโค้ด

2. ได้ — ผู้ใช้รู้ว่าเครื่องนี้คือเครื่องไหนดีกว่าใคร และตั้งผิดก็แค่ชื่อผิด

3. ไม่ — เป็นเรื่องของประสิทธิภาพที่ผู้ใช้ไม่ควรต้องคิด ถ้าลิสต์ช้าให้แก้ที่การแบ่งหน้า ไม่ใช่ผลักภาระให้ผู้ใช้

4. ได้ — เป็นความชอบส่วนตัวและสภาพแวดล้อม คลังที่เสียงดังต้องการเสียง ห้องเย็นที่เงียบอาจไม่ต้องการ

รูปแบบที่เห็น: ให้แก้ได้เมื่อ (ก) ผู้ใช้รู้คำตอบดีกว่าเรา และ (ข) ตั้งผิดแล้วเสียหายจำกัดและเห็นได้ทันที ถ้าขาดข้อใดข้อหนึ่ง อย่าเปิด

9. สรุป

  • ค่าตั้งค่ามาจากสามชั้น คือโค้ด, ตอน build และผู้ใช้
  • เปิดให้ผู้ใช้แก้เฉพาะค่าที่เขารู้คำตอบและตั้งผิดแล้วเห็นทันที
  • เก็บเป็นชนิดที่มีความหมาย ไม่ใช่ถุงของข้อความ
  • ค่าเริ่มต้นอยู่ที่เดียวเสมอ

บทหน้า: ชั้นกลาง — ค่าที่ตรึงไว้ตอน build และวิธีที่มันชนะทุกอย่าง
