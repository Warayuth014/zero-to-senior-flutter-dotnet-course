3. เส้นทางทั้งหมดในภาพเดียว

เปิดแอป
  └─ ProfileStore.load()                              ← 10.6
       ├─ ไม่มีของเก่า → สร้างตัวเริ่มต้น + บันทึก
       ├─ มีของเก่า    → อ่านกลับ ทิ้งแถวที่เสีย        ← 10.5
       └─ resolveBaseUrl(activeBaseUrl)               ← 10.2
            └─ --dart-define ชนะทุกอย่าง

ผู้ใช้เปิดหน้าตั้งค่า
  ├─ เห็นรายการ + ตัวที่ใช้อยู่ + จุดสถานะ              ← 10.12
  ├─ กด "เพิ่ม" → ProfileDraft ใหม่                    ← 10.11
  │    ├─ พิมพ์ → validateDraft ทุกครั้งที่เปลี่ยน       ← 10.7
  │    ├─ กด "ทดสอบ" → probeServer(baseUrl ของร่าง)    ← 10.9
  │    ├─ กด "บันทึก" → toProfile → saveAsNew          ← 10.6
  │    └─ กดปิดทั้งที่ยังไม่บันทึก → เตือน               ← 10.11
  ├─ กด "ใช้ตัวนี้" → activate → ล้างสถานะ             ← 10.6
  │    └─ session ที่ผูกกับเซิร์ฟเวอร์เก่าถูกล้าง        ← 8.11
  └─ กด "ลบ" → remove (ตัวสุดท้ายลบไม่ได้)             ← 10.6

กลับมาจากพื้นหลัง
  └─ refreshStatus()                                  ← 10.8

5. เกณฑ์ที่ต้องผ่าน

#เกณฑ์บท
1เปิดแอปครั้งแรกมี profile ให้ใช้ทันที และบันทึกไว้ ไม่สร้างใหม่ทุกครั้ง10.6
2ข้อมูลที่เก็บไว้เสียหนึ่งแถว ต้องยังใช้แถวที่เหลือได้10.5
3มีตัวที่ใช้งานอยู่หนึ่งตัวเสมอ ไม่ว่าจะทำอะไรกับรายการ10.6
4บันทึกไม่ทำให้สลับ และสลับเป็นปุ่มแยก10.6
5สลับแล้วสถานะการเชื่อมต่อของเครื่องเก่าต้องถูกล้าง10.6
6ลบตัวสุดท้ายไม่ได้ และลบตัวที่ใช้อยู่ต้องมีตัวแทน10.6
7ข้อความผิดพลาดแสดงใต้ช่องที่ผิด ไม่ใช่กองรวมกัน10.7
8ทุกข้อความบอกว่าค่านั้นควรไปอยู่ที่ไหน10.7
9เปิดฟอร์มเปล่ามาต้องไม่เห็นสีแดงจนกว่าจะแตะช่องหรือกดบันทึก10.7
10ปุ่มทดสอบใช้ที่อยู่ในฟอร์ม ไม่ใช่ที่อยู่ที่ใช้งานอยู่10.9
11เซิร์ฟเวอร์ที่ตอบ 200 พร้อม HTML ต้องขึ้นว่าไม่สำเร็จ พร้อมชี้ไปที่ Base Path10.10
12ใส่ /api ใน Base Path ต้องถูกดักพร้อมอธิบายว่าจะเกิดอะไร10.10
13กดปิดทั้งที่แก้ไปแล้ว ต้องเตือนด้วยปุ่มที่เขียนเป็นการกระทำ10.11
14เปิดฟอร์มแล้วปิดทันทีโดยไม่แก้อะไร ต้องไม่เตือน10.11
15จุดสถานะแสดงชื่อ profile ด้วย ไม่ใช่แค่สี10.12
16ปุ่มทำงานทุกปุ่มกดได้เสมอ ไม่ว่าสถานะจะเป็นอะไร10.12
17ระหว่างตรวจต้องเห็นว่ากำลังตรวจอยู่10.8
18ตรวจตอนเปิดจอและตอนกลับจากพื้นหลัง ไม่มีตัวจับเวลาวนตลอด10.8

final _touched = <String>{};
var _submitted = false;

String? errorFor(String field, String? message) =>
    _touched.contains(field) || _submitted ? message : null;

TextField(
  onTap: () => setState(() => _touched.add('host')),
  decoration: InputDecoration(errorText: errorFor('host', validation.host)),
)

เกณฑ์ 10 — ทดสอบที่อยู่ในฟอร์ม

ต้องประกอบ URL จากร่างเอง โดยไม่ผ่าน toProfile เพราะร่างอาจยังไม่ผ่านการตรวจ

Future<void> _test() async {
  final validation = validateDraft(_draft);
  if (!validation.isValid) {
    setState(() => _submitted = true);   // โชว์ข้อความก่อน แล้วไม่ต้องยิง
    return;
  }
  final candidate = _draft.toProfile(id: 'ชั่วคราว');
  setState(() => _testing = true);
  final result = await probeServer(baseUrl: candidate.baseUrl);
  if (!mounted) return;
  setState(() { _testing = false; _testResult = result; });
}

8. ข้อผิดพลาดที่พบบ่อยตอนทำ lab นี้

อาการสาเหตุวิธีแก้
พิมพ์ในฟอร์มแล้วค่าไม่เข้าร่างใช้ TextEditingController แต่ไม่ได้เขียนกลับonChanged อัปเดตร่างทุกครั้ง
เตือนหลังบันทึกสำเร็จไม่ได้อัปเดตตัวที่ใช้เทียบตั้ง _saved เป็นตัวที่เพิ่งบันทึก
ปุ่มทดสอบยิงที่อยู่เก่าใช้ store.activeBaseUrlประกอบจากร่าง
รายการไม่อัปเดตหลังบันทึกไม่ได้ฟัง storeListenableBuilder
เทสต์ widget ล้มเพราะ plugin ไม่มีใช้ที่เก็บจริงใส่ InMemorySettingsStorage
สลับแล้วยังเห็นข้อมูลของเซิร์ฟเวอร์เก่าstore ของฟีเจอร์อื่นไม่ได้ล้างล้างพร้อมกัน (8.8)

9. แบบทดสอบตัวเองก่อนจบ Part 10

  1. ค่าตั้งค่ามาจากสามชั้นไหนบ้าง (10.1)
  2. ใช้เกณฑ์อะไรตัดสินว่าค่าไหนควรให้ผู้ใช้แก้ (10.1)
  3. ทำไม String.fromEnvironment ต้องอยู่ใน const (10.2)
  4. ทำไมลำดับความสำคัญของค่าต้องตัดสินที่เดียว (10.2)
  5. normalizeBasePath('/') ต้องคืนอะไร และทำไม (10.3)
  6. เมื่อไหร่ควร normalize และเมื่อไหร่ควรตรวจแล้วบอก (10.3)
  7. ทำไม profile ต้องมี id แยกจากชื่อและที่อยู่ (10.4)
  8. ทำไมห้ามเอา environment ไปเปลี่ยนพฤติกรรมของแอป (10.4)
  9. ทำไมข้อมูลบนเครื่องนี้ถึงทิ้งแถวเสียได้ ต่างจากข้อมูลจากเซิร์ฟเวอร์ (10.5)
  10. ทำไม activeId ถึงเก็บเป็นธงบนแถว (10.5)
  11. ทำไมบันทึกกับสลับต้องเป็นคนละการกระทำ (10.6)
  12. สลับ profile แล้วต้องล้างอะไรบ้าง (10.6, 8.11)
  13. ข้อความผิดพลาดที่ดีต่างจากที่ไม่ดีอย่างไร (10.7)
  14. ทำไมต้องตรวจจากร่าง ไม่ใช่จากโมเดล (10.7, 10.11)
  15. ทำไมไม่ควรตรวจการเชื่อมต่อด้วยตัวจับเวลา (10.8)
  16. ทำไมต้องมีสถานะ unknown (10.8)
  17. ทำไมรหัสตอบกลับ 200 ถึงไม่พอ (10.9, 10.10)
  18. health endpoint ไม่ควรมีอะไรอยู่ในนั้น (10.9)
  19. ทำไม probe ถึงไม่ใช้ ApiClient (10.9)
  20. ทำไมร่างเปล่าถึงไม่ควรนับว่าแก้แล้ว (10.11)
  21. สถานะเครือข่ายยืนยันอะไรได้และไม่ได้ (10.12)
  22. ทำไมไม่ควรปิดปุ่มเมื่อออฟไลน์ (10.12)

10. สรุปท้าย Part 10

สิ่งที่ทำได้แล้ว

  • แยกได้ว่าค่าตั้งค่าไหนอยู่ชั้นไหน และค่าไหนควรให้ผู้ใช้แก้
  • ใช้ --dart-define และรวมลำดับความสำคัญไว้ที่เดียว
  • แปลงค่าที่ผู้ใช้พิมพ์ให้เหลือรูปแบบเดียวที่ขอบ
  • เก็บหลาย profile ลงเครื่องโดยแถวเสียไม่ทำลายที่เหลือ
  • รักษากฎ “มีตัวที่ใช้งานอยู่หนึ่งตัวเสมอ” ในทุกเส้นทาง
  • ตรวจฟอร์มรายช่อง พร้อมข้อความที่บอกว่าต้องทำอะไรต่อ
  • ตรวจการเชื่อมต่อโดยอ่านเนื้อหา ไม่ใช่แค่รหัสตอบกลับ
  • รู้จักกับดัก “200 ที่ไม่ใช่ของเรา” และดักไว้สองชั้น
  • เตือนก่อนทิ้งงานที่ผู้ใช้กรอกค้างไว้
  • แสดงสถานะเครือข่ายโดยไม่ขวางการทำงานและไม่หลอกผู้ใช้

สิ่งที่ยังไม่ได้ทำและจะทำที่ไหน
