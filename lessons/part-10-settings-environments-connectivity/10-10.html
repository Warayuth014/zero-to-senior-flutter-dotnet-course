Blazor fallback trap: SPA hostอาจตอบ index.html พร้อม 200ให้ pathที่ไม่มี route ดังนั้น typoใน API/base pathดูเหมือน server healthyถ้าตรวจแต่ status

1. Scenario

GET /wrong-prefix/api/WMS/mobile_health
HTTP/1.1 200 OK
Content-Type: text/html

<!doctype html><html>...Blazor app...</html>

2. Why it happens

Fallback routeส่ง host pageให้ client-side routing จัดการ เหมาะ browser navigationแต่ API probeที่ไม่ตรวจ contentเข้าใจผิด

3. Defensive probe

ต้องตรวจ expected content-type, JSON decode, top-level mapและ exact service marker ถ้า HTMLให้ wrongService/basePath ไม่ใช่ generic malformed JSON

4. API routing order

ฝั่ง .NET map API/healthก่อน fallbackและอาจแยก API host/domainเพื่อ ambiguityน้อย แต่ clientยังต้องตรวจ payloadเพราะ proxy/captive portalตอบ HTMLได้

5. Error message

บอกว่า “serverตอบแต่ไม่ใช่ WMS API—ตรวจ Base Path” ต่างจาก “ติดต่อไม่ได้” เพราะ networkและhostทำงานแล้ว ผู้ใช้ควรแก้ pathไม่ใช่ Wi-Fi

6. Security angle

อย่า log HTML bodyทั้งหน้า อาจมี config/script metadata ให้เก็บ status, content-type, lengthและ safe prefixที่ truncate/redact

7. แบบฝึกหัด

status 404 JSON ProblemDetailsกับ 200 HTMLควรจัดกลุ่มเหมือนกันไหม?

แนวคำตอบ

ทั้งคู่อาจบอก route/base pathผิดแต่ evidenceต่าง: 404 API response vs fallback host page จึงเก็บ typed resultแยกเพื่อ diagnostics

8. Regression test

MockClientคืน HTML 200แล้ว assert ok == false, messageชี้ base pathและ status dotไม่เปลี่ยน online
