จบบทนี้แล้วจะทำได้: เขียนการตรวจฟอร์มที่บอกผู้ใช้ว่าต้องทำอะไรต่อ ไม่ใช่แค่บอกว่าผิด

1. ผู้ใช้ไม่ได้พิมพ์ผิด เขาพิมพ์ในช่องผิด

ลองดูสิ่งที่ผู้ใช้พิมพ์ลงช่อง host จริง ๆ

พิมพ์เขาคิดว่าที่ถูกคือ
http://192.168.1.194คัดลอกจากเบราว์เซอร์มาทั้งอันเอา http:// ออก ไปเลือกที่ช่อง Protocol
192.168.1.194:6191ที่อยู่เต็มคือแบบนี้พอร์ตไปช่อง Port
192.168.1.194/wmsเส้นทางเป็นส่วนหนึ่งของที่อยู่เส้นทางไปช่อง Base Path

ทั้งสามกรณี ผู้ใช้เข้าใจถูกว่าที่อยู่เซิร์ฟเวอร์คืออะไร เขาแค่ไม่รู้ว่าฟอร์มนี้แยกเป็นสี่ช่อง ข้อความว่า “รูปแบบไม่ถูกต้อง” จึงไม่ช่วยอะไรเลย

2. ข้อความที่ดีบอกว่าค่าควรไปอยู่ที่ไหน

String? _validateHost(String raw) {
  final host = raw.trim();
  if (host.isEmpty) return 'ใส่ IP หรือชื่อเครื่อง';
  if (host.contains('://') || host.toLowerCase().startsWith('http')) {
    return 'ใส่เฉพาะที่อยู่ ไม่ต้องมี http:// (เลือกที่ช่อง Protocol)';
  }
  if (host.contains('/')) return 'เส้นทางให้ใส่ที่ช่อง Base Path';
  if (host.contains(':')) return 'พอร์ตให้ใส่ที่ช่อง Port';
  if (host.contains(' ')) return 'ห้ามมีช่องว่าง';
  return null;
}
ข้อความที่ไม่ช่วยข้อความที่ช่วย
รูปแบบไม่ถูกต้องพอร์ตให้ใส่ที่ช่อง Port
Invalid hostใส่เฉพาะที่อยู่ ไม่ต้องมี http://
กรุณากรอกให้ถูกต้องเส้นทางให้ใส่ที่ช่อง Base Path
เกณฑ์ที่ใช้ตรวจข้อความของตัวเอง: อ่านแล้วรู้ไหมว่าต้องกดตรงไหนต่อ ถ้าไม่รู้ แปลว่ายังเขียนไม่เสร็จ

3. ลำดับของการตรวจมีความหมาย

ค่า http://192.168.1.194:6191/wms ผิดทั้งสามข้อ แต่ผู้ใช้ควรเห็นข้อความเดียว และควรเป็นข้อความที่ทำให้เขาไปได้ไกลที่สุด

ลำดับในโค้ดคือ ว่าง → มี scheme → มีทับ → มีโคลอน → มีช่องว่าง เรียงจาก “ผิดชัดที่สุด” ไปหา “ผิดที่เจอน้อยที่สุด” — ผู้ใช้แก้ทีละอย่าง แล้วข้อความจะเปลี่ยนไปเรื่อย ๆ จนหมด

ทางเลือกอีกทางคือแสดงทุกข้อพร้อมกัน ซึ่งดูเหมือนช่วยมากกว่า แต่กลับทำให้ผู้ใช้ที่พิมพ์ค่าเดียวเห็นข้อความสามบรรทัดจนสับสนว่าตกลงผิดกี่เรื่อง

4. ผลลัพธ์แยกรายช่อง

class ProfileValidation {
  const ProfileValidation({this.name, this.host, this.port, this.basePath});

  final String? name;
  final String? host;
  final String? port;
  final String? basePath;

  bool get isValid =>
      name == null && host == null && port == null && basePath == null;
}

ไม่ใช่ List<String> เพราะข้อความกองเดียวบังคับให้ผู้ใช้เดาว่าบรรทัดไหนหมายถึงช่องไหน พอแยกรายช่องแล้ว UI แสดงใต้ช่องที่ผิดได้ตรงตัว

TextField(
  decoration: InputDecoration(
    labelText: 'Host',
    errorText: validation.host,     // null = ไม่มีข้อความ ไม่ต้อง if
  ),
)

สังเกตว่า errorText รับ String? อยู่แล้ว การออกแบบให้เป็น nullable ต่อกับ Flutter ได้พอดีโดยไม่ต้องเขียนเงื่อนไข

5. ตรวจตอนไหน

ตอนเหมาะกับไม่เหมาะกับ
ทุกตัวอักษรที่พิมพ์ความยาวรหัสผ่านช่องที่ยังพิมพ์ไม่เสร็จก็ผิดอยู่แล้ว เช่นพิมพ์ 1 ในช่องพอร์ต
ตอนออกจากช่องส่วนใหญ่ผู้ใช้ที่กด Save เลยโดยไม่ออกจากช่อง
ตอนกดบันทึกการตรวจข้ามช่องผู้ใช้ต้องกดก่อนถึงจะรู้ว่าผิด

ที่ใช้ได้จริงคือผสม — ตรวจตอนออกจากช่องสำหรับช่องที่เคยแตะแล้ว และตรวจทุกช่องตอนกดบันทึก

// เก็บว่าช่องไหนเคยถูกแตะแล้ว
final _touched = <String>{};

String? errorFor(String field, String? message) =>
    _touched.contains(field) || _submitted ? message : null;

ผลคือผู้ใช้ที่เพิ่งเปิดฟอร์มเปล่าไม่เห็นข้อความสีแดงเต็มจอตั้งแต่ยังไม่ได้พิมพ์อะไร

6. ตรวจข้อความดิบ ไม่ใช่โมเดล

ProfileValidation validateDraft(ProfileDraft draft) { ... }

รับ ProfileDraft ที่มี port เป็น String ไม่ใช่ ServerProfile ที่มี port เป็น int เพราะระหว่างพิมพ์ ค่ายังแปลงไม่ได้

test('พอร์ตที่ยังพิมพ์ไม่เสร็จ ต้องไม่ทำให้พังทั้งฟอร์ม', () {
  expect(validateDraft(draft(port: '')).port, isNotNull);
  expect(validateDraft(draft(port: '61')).port, isNull);
});

'61' ผ่านเพราะเป็นพอร์ตที่ใช้ได้จริง แม้ผู้ใช้ตั้งใจจะพิมพ์ 6191 ก็ตาม — การตรวจตัดสินจากค่าที่มี ไม่ใช่จากการเดาว่าเขาจะพิมพ์อะไรต่อ

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เปิดฟอร์มมาเห็นสีแดงเต็มจอตรวจตั้งแต่ยังไม่พิมพ์เก็บว่าช่องไหนเคยถูกแตะ
ข้อความผิดพลาดไม่บอกว่าต้องทำอะไรเขียนว่า “รูปแบบไม่ถูกต้อง”บอกว่าค่านั้นควรไปอยู่ที่ไหน
ผู้ใช้แก้แล้วข้อความไม่หายตรวจแค่ตอนกดบันทึกตรวจใหม่ทุกครั้งที่ค่าเปลี่ยน
ตรวจผ่านแล้วยังพังตอนบันทึกตรวจกับค่าที่แปลงแล้ว ไม่ใช่ค่าดิบตรวจจากร่าง
แก้ให้ผู้ใช้เองเงียบ ๆคิดว่าเป็นความสะดวกบอก ไม่ใช่แก้ให้ (10.3)

8. แบบฝึกหัด

มีรายงานจากหน้างานสามเรื่อง

  1. ผู้ใช้พิมพ์ localhost ในช่อง host บน PDA แล้วต่อไม่ติด
  2. ผู้ใช้ตั้งชื่อ profile ว่า 192.168.1.194 แล้วบอกว่าแยกไม่ออกว่าอันไหนคืออันไหน
  3. ผู้ใช้บันทึก profile ที่มีที่อยู่ซ้ำกับตัวที่มีอยู่แล้ว

แต่ละข้อควรเพิ่มการตรวจไหม

แนวคำตอบ

1. ควรเตือน แต่ไม่ห้าม — localhost บน PDA หมายถึงตัว PDA เอง ซึ่งไม่มีเซิร์ฟเวอร์อยู่ แต่บนเครื่อง dev มันถูกต้อง และเป็นค่าเริ่มต้นของ lab เอง ทางที่ถูกคือคำเตือนที่บันทึกต่อได้

// คำเตือน ไม่ใช่ข้อผิดพลาด — บันทึกได้ แต่บอกให้รู้ตัว
if (host == 'localhost' || host == '127.0.0.1') {
  return 'ที่อยู่นี้หมายถึงตัวเครื่องนี้เอง ถ้าเซิร์ฟเวอร์อยู่คนละเครื่อง ให้ใส่ IP ของเครื่องนั้น';
}

ต้องแยกชนิดของข้อความเป็น “ผิด” กับ “น่าสงสัย” ซึ่งแปลว่า ProfileValidation ต้องมีมากกว่า String? ต่อช่อง

2. ไม่ควรห้าม — ผู้ใช้บางคนอยากตั้งชื่อแบบนั้นจริง ๆ และการห้ามไม่ได้แก้ปัญหาที่แท้จริงคือ “แยกไม่ออก” สิ่งที่แก้ได้จริงคือแสดงทั้งชื่อและที่อยู่ในรายการ แล้วปัญหาหายไปเองโดยไม่ต้องตรวจอะไร

3. ควรเตือน เพราะ profile สองตัวที่ชี้ที่เดียวกันมักเกิดจากการกด “บันทึกเป็นตัวใหม่” แทน “บันทึก” แต่ห้ามไม่ได้ เพราะผู้ใช้อาจตั้งใจมีสองชื่อสำหรับเครื่องเดียวกัน เช่น “คลังหลัก” กับ “ทดสอบชั่วคราว” ที่บังเอิญเป็นเครื่องเดียวกันตอนนี้

รูปแบบที่เห็นทั้งสามข้อ: คำถามที่ควรถามไม่ใช่ “ค่านี้ผิดไหม” แต่คือ “ค่านี้ผิดแน่นอน หรือแค่น่าสงสัย” — ห้ามเฉพาะสิ่งที่ผิดแน่นอน ที่เหลือให้เตือนแล้วปล่อยให้ผู้ใช้ตัดสิน เพราะเขารู้หน้างานดีกว่าเรา

9. สรุป

  • ผู้ใช้ส่วนใหญ่ไม่ได้พิมพ์ผิด เขาพิมพ์ค่าที่ถูกลงช่องผิด
  • ข้อความต้องบอกว่าค่านั้นควรไปอยู่ที่ไหน
  • แยกผลลัพธ์รายช่อง เพื่อแสดงใต้ช่องที่ผิด
  • ตรวจจากข้อความดิบในร่าง ไม่ใช่จากโมเดลที่แปลงแล้ว
  • ห้ามเฉพาะสิ่งที่ผิดแน่นอน ที่น่าสงสัยให้เตือน

บทหน้า: ตรวจว่าที่อยู่ที่ผู้ใช้กรอก มีเซิร์ฟเวอร์อยู่จริงไหม
