1. --dart-define คืออะไร

คือวิธีส่งค่าเข้าไปในแอปตอน build ค่าจะถูกฝังเข้าไปในไฟล์ที่ได้ เปลี่ยนทีหลังไม่ได้จนกว่าจะ build ใหม่
flutter run --dart-define=WMS_API_BASE_URL=http://192.168.1.50:6191
flutter build apk --dart-define=WMS_API_BASE_URL=https://wms.company.com

อ่านค่าในโค้ดด้วย

const String _baseUrlOverride = String.fromEnvironment('WMS_API_BASE_URL');
สิ่งที่ต้องรู้รายละเอียด
ต้องเป็น constString.fromEnvironment อ่านค่าได้ตอนคอมไพล์เท่านั้น ใส่ใน final จะได้ค่าว่างเสมอ
ไม่ส่งมาจะได้ ''ไม่ใช่ null ต้องเช็คด้วย isNotEmpty
มีคู่แฝดสำหรับชนิดอื่นint.fromEnvironment, bool.fromEnvironment
ไม่ใช่ที่เก็บความลับค่าอยู่ในไฟล์ที่แจกออกไป แกะดูได้ ห้ามใส่รหัสผ่านหรือ API key

2. ใช้ตอนไหน

เหมาะไม่เหมาะ
build ที่ตรึงไว้กับเซิร์ฟเวอร์เดียว เช่นส่งให้ลูกค้ารายหนึ่งค่าที่ผู้ใช้ควรเปลี่ยนเองได้
เปิดปิดโหมด debug ในตัวแอปความลับทุกชนิด
ระบุว่านี่คือ build ของ dev, staging หรือ prodค่าที่เปลี่ยนบ่อยกว่าที่ build

3. ปัญหาที่แท้จริง: ค่ามาจากสามที่ ใครชนะ

ตอนนี้ที่อยู่เซิร์ฟเวอร์อาจมาจาก

  1. --dart-define ที่ตรึงไว้ตอน build
  2. profile ที่ผู้ใช้เลือก
  3. ค่าเริ่มต้นในโค้ด

ถ้าแต่ละที่ในแอปตัดสินลำดับเอง จะเกิดอาการที่วินิจฉัยยากที่สุดในบทนี้ — คำขอไปที่เซิร์ฟเวอร์หนึ่ง แต่จุดแสดงสถานะรายงานอีกเซิร์ฟเวอร์หนึ่ง

โปรเจกต์จริงเคยเป็นแบบนี้มาก่อน และแก้ด้วยการรวมไว้ที่ฟังก์ชันเดียว

/// ลำดับ อันแรกที่เจอชนะ
///   1. --dart-define=WMS_API_BASE_URL  (build ที่ตรึงไว้กับเซิร์ฟเวอร์เดียว)
///   2. activeBaseUrl — profile ที่ผู้ใช้เลือก (null ก่อนโหลดเสร็จ)
///   3. ค่าเริ่มต้นในโค้ด ใช้จนกว่าจะมี profile ตัวแรก
String resolveBaseUrl(String? activeBaseUrl) {
  if (_baseUrlOverride.isNotEmpty) return _baseUrlOverride;
  if (activeBaseUrl != null && activeBaseUrl.isNotEmpty) return activeBaseUrl;
  return 'http://$defaultServerHost:$defaultServerPort';
}

ทั้งคำขอจริงและตัวตรวจสถานะเรียกฟังก์ชันเดียวกันนี้ จึงเป็นไปไม่ได้ที่สองอย่างจะชี้คนละที่

4. บอกผู้ใช้เมื่อค่าที่เขาตั้งจะไม่มีผล

ถ้า build นี้ตรึงเซิร์ฟเวอร์ไว้แล้ว ผู้ใช้ที่ไปแก้ profile จะบันทึกได้ กดสลับได้ แล้วไม่มีอะไรเปลี่ยน — เป็นประสบการณ์ที่แย่ที่สุดแบบหนึ่ง เพราะดูเหมือนแอปพัง

/// จริงเมื่อ build นี้ถูกตรึงด้วย --dart-define ซึ่ง profile ทับไม่ได้
/// หน้าตั้งค่าจะบอกไว้ แทนที่จะปล่อยให้ผู้ใช้บันทึกค่าที่ไม่มีผลอะไร
bool get isBaseUrlPinnedByBuild => _baseUrlOverride.isNotEmpty;
หลักที่ใช้ได้ทั่วไป: ทุกครั้งที่มีลำดับความสำคัญ ต้องมีทางบอกผู้ใช้ว่าค่าที่เขาแก้ถูกอะไรทับอยู่ ไม่งั้นเขาจะแก้ซ้ำหลายรอบแล้วสรุปว่าแอปเสีย

แทนที่จะเรียงลำดับอย่างเดียว มันไล่ลองต่อจริงทีละตัวแล้วใช้ตัวแรกที่ติด

ได้เสีย
นักพัฒนาไม่ต้องตั้งค่าอะไรเลยตอนรันบนเครื่องตัวเองการเปิดแอปครั้งแรกช้าลงเท่ากับเวลาที่ใช้ลองทีละตัว
สลับระหว่าง emulator กับเครื่องจริงได้เองผลไม่แน่นอน — เครื่องที่บังเอิญมีอะไรฟังอยู่ที่พอร์ตนั้นจะถูกเลือก
ไม่ต้องมีหน้าตั้งค่าตั้งแต่วันแรกผู้ใช้ไม่มีทางรู้ว่าตอนนี้ต่อกับเครื่องไหนอยู่

แถวสุดท้ายคือสิ่งที่ทำให้แนวนี้ไปต่อยาก — เมื่อมีปัญหา ไม่มีใครตอบได้ว่าแอปกำลังคุยกับใคร การมี profile ที่ผู้ใช้เลือกเองแก้ข้อนี้ตรง ๆ

สังเกตว่าทั้งสองแนวไม่ผิด — แนวแรกเหมาะกับตอนที่ยังไม่มีหน้าตั้งค่าและอยากให้ dev เริ่มได้เร็ว แนวหลังเหมาะกับตอนที่แอปออกไปอยู่ในมือผู้ใช้จริงแล้ว

6. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
String.fromEnvironment ได้ค่าว่างเสมอไม่ได้ประกาศเป็น constconst String x = String.fromEnvironment(...)
ส่ง --dart-define แล้วไม่มีผลชื่อคีย์ไม่ตรงกันเป๊ะ ตัวพิมพ์ใหญ่เล็กมีความหมายตรวจชื่อ
คำขอกับจุดสถานะชี้คนละเซิร์ฟเวอร์สองที่คำนวณ base URL เองรวมไว้ที่ฟังก์ชันเดียว
ผู้ใช้แก้ที่อยู่แล้วไม่มีอะไรเปลี่ยนถูก --dart-define ทับบอกในหน้าตั้งค่า
API key หลุดใส่ไว้ใน --dart-defineอย่าใส่ความลับในแอป ให้เซิร์ฟเวอร์ถือ

7. แบบฝึกหัด

ทีมจะส่งแอปให้ลูกค้าสามราย แต่ละรายมีเซิร์ฟเวอร์ของตัวเองที่ไม่เปลี่ยนอีก และไม่อยากให้พนักงานของลูกค้าไปแก้ที่อยู่ได้

  1. ควรใช้วิธีไหน
  2. ถ้าวันหนึ่งลูกค้ารายที่สองย้ายเซิร์ฟเวอร์ จะเกิดอะไรขึ้น
แนวคำตอบ

1. --dart-define ตอน build ทำสาม build คนละที่อยู่ พร้อมกับให้หน้าตั้งค่าแสดงว่าถูกตรึงไว้และแก้ไม่ได้ ตามที่ isBaseUrlPinnedByBuild ทำ

2. ต้อง build ใหม่แล้วส่งให้ติดตั้งใหม่ทุกเครื่อง ซึ่งอาจใช้เวลาเป็นวัน

ตรงนี้เป็นการแลก ไม่ใช่ทางที่ถูกทางเดียว ทางสายกลางที่ใช้ได้จริงคือ ตรึงค่าเริ่มต้นไว้ตอน build แต่ยังเปิดให้แก้ได้จากหน้าที่เข้าถึงยากหน่อย เช่นต้องกดชื่อแอปค้างไว้ห้าวินาที ผลคือพนักงานทั่วไปไม่ไปแตะ แต่ช่างที่ไปหน้างานแก้ได้ทันทีโดยไม่ต้องรอ build

ข้อคิดที่สำคัญกว่า: การล็อกไม่ให้แก้ ดูปลอดภัยตอนออกแบบ แต่กลายเป็นค่าใช้จ่ายในวันที่ต้องแก้จริง — และวันนั้นมักมาถึงเสมอ ตรงกับที่ 8.11 สรุปไว้ว่า “ต้องติดตั้งแอปใหม่” เกือบทุกครั้งแปลว่ามีสถานะที่ผู้ใช้เข้าไม่ถึง

8. สรุป

  • --dart-define ฝังค่าตอน build ต้องอ่านด้วย const และไม่ใช่ที่เก็บความลับ
  • ลำดับความสำคัญของค่าต้องตัดสินที่ฟังก์ชันเดียว ทุกคนเรียกที่เดียวกัน
  • เมื่อค่าที่ผู้ใช้แก้ถูกทับ ต้องบอกให้รู้
  • การไล่ลองต่อทีละที่อยู่ทำให้เริ่มง่าย แต่ทำให้ไม่มีใครตอบได้ว่าตอนนี้ต่อกับใคร
