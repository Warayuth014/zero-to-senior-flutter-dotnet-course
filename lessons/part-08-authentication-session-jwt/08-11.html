Session ผูกกับ security realm: token จาก Server A ห้ามถูกส่งไป Server B แม้ host ทั้งคู่เป็น WMS เพราะ issuer, audience, tenant และข้อมูลผู้ใช้คนละชุด

1. Threat

ผู้ใช้ login production แล้วเปลี่ยน base URL เป็น dev ถ้า ApiClient ยังถือ token จะส่ง credential production ไป host ใหม่และอาจเปิดเผย tokenใน log/server ที่ไม่ควรเห็น

2. Server identity

connection profile ควรมี stable server ID/realm จาก trusted health/auth metadata ไม่ใช้แค่ label ที่ผู้ใช้พิมพ์ และ session envelope เก็บ server ID ที่ออก token

3. Switch algorithm

  1. หยุด authenticated requests
  2. เพิ่ม session generation
  3. clear token/session/user caches
  4. เปลี่ยน profile/base URL
  5. probe service identity
  6. กลับ login สำหรับ server ใหม่

4. Same host config edit

แม้เปลี่ยน protocol/port/pathเล็กน้อยให้ถือเป็น realm change เว้นแต่ serverพิสูจน์ identityตรงและ policy อนุญาต อย่าเดาจาก hostname string

5. UI confirmation

ถ้ามี session active ให้แจ้งว่าเปลี่ยน serverแล้วต้องออกจากระบบและล้างงานที่ยังไม่ส่ง ป้องกันผู้ใช้คิดว่าข้อมูลหายหรือส่งผิดคลัง

6. ของจริง

connection controller ใช้ ApiClient ตัวเดิมเพื่อรักษา tokenเมื่อปรับ setting แต่ productionต้องกำหนดชัดว่า setting ใดไม่เปลี่ยน realm และ setting ใดบังคับ logout

7. แบบฝึกหัด

เปลี่ยนจาก http://192.168.1.5:5000 เป็น HTTPS domain ที่ reverse proxy ไป serverเดิม ควรเก็บ sessionไหม?

แนวคำตอบ

ตัดสินจาก verified server/issuer identity และ migration policy ไม่ใช่ URL similarity; ค่าเริ่มต้นที่ปลอดภัยคือ clear แล้ว login ใหม่

8. Tests

switch A→B, switch ขณะ request, probe wrong service, switch offline, cancel switch และตรวจว่า Authorization ของ A ไม่เคยถึง B
