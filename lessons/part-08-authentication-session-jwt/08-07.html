Expiration กับ 401 เป็นคนละสัญญาณ: client รู้เวลา expiry ล่วงหน้าได้ แต่ server ยังอาจ 401 เพราะ revoke, signing key, issuer/audience หรือ clock policy

1. Proactive check

bool shouldRefresh(DateTime now) =>
    !now.isBefore(session.expiresAt.subtract(const Duration(minutes: 1)));

ถ้าไม่มี refresh-token contract ให้ proactive check พา login ใหม่ ไม่สร้าง refresh เอง

2. Reactive 401

ApiClient แจ้ง AuthCoordinator เมื่อ authenticated request ได้ 401 แต่ไม่ควร logout จาก 401 ของ login endpoint หรือ anonymous probe และต้องป้องกันหลาย request trigger logout/dialog ซ้ำ

3. Single-flight refresh

ถ้ามี refresh token ให้ request พร้อมกันรอ refresh Future เดียว เมื่อสำเร็จ retry request ที่ปลอดภัยตาม policy; เมื่อ refresh ล้มให้ clear session ครั้งเดียว

4. 401 vs 403

401 ทำให้ credential invalid จึงอาจยุติ session ส่วน 403 session ยัง validแต่ไม่มี permission ห้าม logout อัตโนมัติและห้าม refresh วน

5. Command uncertainty

401 มักเกิดก่อน endpoint ทำ business logic แต่ proxy/middleware custom อาจต่างกัน Command retry หลัง refresh ต้องพิจารณา idempotency เช่นเดียวกับ timeout

6. User experience

เก็บ intended destination ได้เฉพาะข้อมูลไม่ลับแล้วพา login จากนั้นให้ผู้ใช้เริ่ม command ใหม่ อย่าเก็บ password หรือ replay mutation ที่ยังไม่แน่ชัดโดยอัตโนมัติ

7. แบบฝึกหัด

สาม API ได้ 401 พร้อมกันควรเกิดอะไร?

เฉลย

refresh/logout transition เดียว, clear session ครั้งเดียว, cancel/ignore responses ด้วย generation และแสดง login หนึ่งครั้ง ไม่เปิดสาม dialog

8. Test matrix

expired ก่อนยิง, 401 หนึ่ง/หลาย request, 403, refresh success/fail, logout ระหว่าง refresh และ command ที่ห้าม retry
