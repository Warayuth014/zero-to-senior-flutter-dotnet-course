1. ปัญหาที่บทนี้แก้

8.5 ตัดสินแล้วว่า เก็บอะไร — บทนี้ตอบว่า เก็บที่ไหน

เพราะที่เก็บบนเครื่องมีหลายแบบ และไม่ได้ปลอดภัยเท่ากัน

ที่เก็บใครอ่านได้บ้าง
ที่เก็บค่าตั้งค่าแบบธรรมดาแอปนั้น และใครก็ตามที่เข้าถึงไฟล์ในเครื่องได้
ที่เก็บที่ระบบปฏิบัติการปกป้องแอปนั้น และถูกเข้ารหัสด้วยกุญแจของเครื่อง

ความต่างสำคัญบน PDA เป็นพิเศษ — เครื่องอาจถูกตั้งค่าให้เข้าถึงไฟล์ได้ง่ายกว่าโทรศัพท์ทั่วไป เพราะทีมไอทีต้องดูแลหลายสิบเครื่อง

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย

3. Mental model: จัดชั้นก่อนเลือกที่เก็บ

ความลับ        →  token, refresh token       →  ที่เก็บที่ปกป้อง
ข้อมูลส่วนตัว  →  ชื่อผู้ใช้                  →  ที่เก็บธรรมดาได้
ไม่ลับเลย      →  ที่อยู่เซิร์ฟเวอร์, ขนาดตัวอักษร →  ที่เก็บธรรมดา
ประโยคเดียวที่ต้องจำ: เกณฑ์คือถามว่า “ถ้าคนอื่นอ่านค่านี้ได้ เขาทำอะไรได้บ้าง” — ถ้าคำตอบคือ “สวมรอยเป็นผู้ใช้คนนี้” นั่นคือความลับ

4. แยกที่เก็บตามชั้น

ข้อมูลถ้ารั่วแล้วเกิดอะไรเก็บที่
accessTokenสวมรอยได้จนหมดอายุที่เก็บที่ปกป้อง
refreshTokenสวมรอยได้ยาวกว่ามาก (8.5)ที่เก็บที่ปกป้อง
usernameรู้ว่าใครใช้เครื่องนี้ธรรมดาได้
expiresAtไม่มีอะไรธรรมดาได้
serverIdไม่มีอะไรธรรมดาได้
rolesรู้ว่าคนนี้มีสิทธิ์อะไรธรรมดาได้ — เพราะเซิร์ฟเวอร์ตรวจอยู่แล้ว (8.9)

ใน lab เก็บทุกอย่างไว้ก้อนเดียวเพื่อความง่าย — และเพราะทั้งก้อนอยู่ในที่เก็บที่ปกป้อง จึงปลอดภัยกว่าที่จำเป็น

String encode(AuthSession session) => jsonEncode({
  'schemaVersion': sessionSchemaVersion,
  'serverId': session.serverId,
  'username': session.username,
  'accessToken': session.accessToken,
  'expiresAt': session.expiresAt.toIso8601String(),
  'roles': session.roles.toList(),
});

ข้อแลกคือช้ากว่าเล็กน้อย เพราะที่เก็บที่ปกป้องต้องเข้ารหัสทุกครั้ง — ซึ่งไม่สำคัญเมื่ออ่านเขียนแค่ตอนเข้าและออกจากระบบ

5. ที่เก็บเป็นสัญญา ไม่ใช่คลาสจริง

เปิด lib/auth/session_storage.dart

/// ที่เก็บ session ข้ามการปิดแอป
///
/// เป็นสัญญา ไม่ใช่คลาสจริง เพราะที่เก็บจริงต่างกันตามแพลตฟอร์ม
/// และเทสต์ต้องใช้ของปลอมที่ควบคุมได้ (8.10)
abstract interface class SessionStorage {
  Future<AuthSession?> read();
  Future<void> write(AuthSession session);
  Future<void> clear();
}

ทำให้เปลี่ยนที่เก็บได้โดยไม่แตะ SessionStore เลย

// ตอนใช้งานจริง
final storage = SecureSessionStorage();

// ตอนเทสต์
final storage = InMemorySessionStorage();

// ตอนพัฒนาบนเครื่องที่ยังไม่มีที่เก็บที่ปกป้อง
final storage = InMemorySessionStorage();   // ไม่จำข้ามการเปิดแอป

และการแยกสัญญาออกมาทำให้ ทดสอบกรณีที่เก็บล้มเหลวได้ ซึ่งเป็นกรณีที่เกิดจริงและทำให้เกิดจริงยาก

/// จำลองความล้มเหลวได้ เพราะที่เก็บจริงเขียนไม่สำเร็จได้ และนั่นคือกรณี
/// ที่ต้องออกแบบไว้ ไม่ใช่กรณีที่หวังว่าจะไม่เกิด
class InMemorySessionStorage implements SessionStorage {
  String? raw;
  bool failOnWrite = false;
  bool failOnRead = false;
  ...
}

6. ที่เก็บที่ปกป้องก็ล้มเหลวได้

สาเหตุที่ล้มเหลวเกิดเมื่อ
ระบบกุญแจของเครื่องมีปัญหาบางรุ่นของ Android
ผู้ใช้ยังไม่ได้ตั้งรหัสปลดล็อกเครื่องบางการตั้งค่าต้องมีก่อน
กุญแจถูกล้างหลังเปลี่ยนรหัสปลดล็อกอ่านของเดิมไม่ได้
พื้นที่เต็มPDA ที่มีที่เก็บน้อย

แถวที่สามน่าสนใจ — เขียนได้ตอนแรก แต่อ่านไม่ได้ทีหลัง ซึ่งเป็นเหตุผลที่การอ่านต้องดักไว้ด้วย

try {
  stored = await storage.read();
} on SessionStorageException {
  // อ่านไม่ได้ก็แค่ให้ล็อกอินใหม่ ไม่ควรทำให้เปิดแอปไม่ได้
  stored = null;
}

และการเขียนที่ล้มเหลวไม่ควรทำให้เข้าสู่ระบบไม่ได้ ตามที่ตัดสินไว้ใน 8.5

try {
  await storage.write(session);
} on SessionStorageException {
  _errorMessage = 'เข้าสู่ระบบได้ แต่จำไว้ให้ไม่ได้ '
      'ครั้งหน้าต้องเข้าสู่ระบบใหม่';
}

7. ที่เก็บที่ปกป้องไม่ได้แปลว่าปลอดภัยเสมอ

สิ่งที่ต้องเข้าใจให้ตรง

ป้องกันได้ป้องกันไม่ได้
แอปอื่นอ่านค่าเครื่องที่ถูกปลดล็อกระบบป้องกัน
อ่านไฟล์ตรง ๆ จากที่เก็บคนที่ถือเครื่องที่ปลดล็อกอยู่
สำรองข้อมูลแล้วเอาไปเปิดที่เครื่องอื่นโปรแกรมที่ฝังในเครื่องที่ถูกแก้ไข

ผลตามมาที่สำคัญกับงานคลัง — PDA ที่วางทิ้งไว้โดยไม่ล็อกหน้าจอ คือ token ที่ใครก็หยิบไปใช้ได้

ซึ่งแก้ด้วยที่เก็บไม่ได้ ต้องแก้ด้วยเรื่องอื่น

ทางลดช่วยอย่างไร
token อายุสั้นจำกัดความเสียหายตามเวลา
ล็อกหน้าจอเมื่อไม่ได้ใช้เป็นการตั้งค่าของเครื่อง ไม่ใช่ของแอป
ยกเลิก token ได้จากส่วนกลางเมื่อเครื่องหาย

8. ไม่ควรเก็บอะไรเลยก็เป็นทางเลือก

สถานการณ์ควรจำไหม
PDA ประจำตัวคนเดียวจำได้ — สะดวกและความเสี่ยงต่ำ
PDA ส่วนกลางที่เปลี่ยนมือทุกกะควรคิดให้ดี
เครื่องที่ใช้กับข้อมูลอ่อนไหวมากอาจไม่จำเลย

แถวกลางเป็นกรณีของงานคลังส่วนใหญ่ และคำตอบขึ้นกับว่า คนกะถัดไปควรต้องเข้าสู่ระบบใหม่หรือไม่

ถ้าจำไว้     →  คนกะถัดไปเปิดแอปมาแล้วเป็นคนกะก่อน  ← อันตราย
ถ้าไม่จำ     →  ทุกคนต้องเข้าสู่ระบบทุกครั้ง        ← ปลอดภัยแต่ช้า

ทางสายกลางที่ใช้ได้จริง — จำไว้ในช่วงเวลาที่สั้นกว่าหนึ่งกะ เช่นสี่ชั่วโมง ทำให้คนที่วางเครื่องไปกินข้าวไม่ต้องล็อกอินใหม่ แต่คนกะถัดไปต้อง

ซึ่งทำได้โดยไม่ต้องเปลี่ยนที่เก็บเลย — แค่ตั้งอายุ token ให้เหมาะ

9. อย่าเก็บสิ่งที่ไม่ควรเก็บลงในที่เก็บที่ปกป้อง

ความเข้าใจผิดที่ตรงข้ามกัน

// ผิด — ที่เก็บที่ปกป้องไม่ได้ทำให้การเก็บรหัสผ่านกลายเป็นเรื่องที่ยอมรับได้
await secureStorage.write('password', password);
เหตุผลรายละเอียด
รหัสผ่านใช้ได้ตลอดไปต่างจาก token ที่หมดอายุเอง (8.5)
ใช้เข้าระบบอื่นได้คนมักใช้รหัสผ่านซ้ำ
ยกเลิกจากส่วนกลางไม่ได้ต้องให้ผู้ใช้เปลี่ยนเอง

ที่เก็บที่ปกป้องลดความเสี่ยง แต่ไม่ได้เปลี่ยนว่าอะไรควรเก็บ — คำถามว่า “ควรเก็บไหม” ต้องตอบก่อนคำถามว่า “เก็บที่ไหน”

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
token อยู่ในไฟล์ที่อ่านได้ง่ายเก็บในที่เก็บธรรมดาย้ายไปที่เก็บที่ปกป้อง
เปิดแอปไม่ได้บนบางเครื่องที่เก็บที่ปกป้องล้มเหลวแล้วไม่ดักดักแล้วให้ล็อกอินใหม่
เข้าสู่ระบบไม่ได้เพราะเขียนไม่ได้ถือว่าเขียนไม่ได้คือล้มเหลวให้ใช้งานรอบนี้ได้ (8.5)
เปลี่ยนรหัสปลดล็อกเครื่องแล้วอ่านของเดิมไม่ได้กุญแจถูกล้างดักที่การอ่านด้วย
คิดว่าที่เก็บที่ปกป้องแก้ได้ทุกอย่างไม่ได้แยกว่าป้องกันอะไรได้บ้างลด token ให้อายุสั้นด้วย
เก็บรหัสผ่านเพราะคิดว่าที่เก็บปลอดภัยแล้วตอบคำถามผิดลำดับถามก่อนว่าควรเก็บไหม

11. แบบฝึกหัด

ทีมกำลังจะเลือกที่เก็บสำหรับข้อมูลหกอย่าง

#ข้อมูล
1accessToken
2ที่อยู่เซิร์ฟเวอร์ที่ผู้ใช้ตั้งไว้
3ชื่อผู้ใช้ล่าสุดที่เข้าสู่ระบบ
4ร่างใบรับเข้าที่ยังไม่ได้ส่ง
5รหัสคำสั่งที่ยังค้างอยู่ (4.14)
6รูปถ่ายสินค้าเสียหายที่รอส่ง
  1. จัดแต่ละอย่างลงที่เก็บที่เหมาะสม
  2. ระบุว่าอันไหนต้องล้างเมื่อออกจากระบบ
  3. ข้อ 6 มีเรื่องที่ต้องคิดเป็นพิเศษ — อธิบาย
ดูแนวคำตอบและเหตุผล

ข้อ 1 และ 2

#เก็บที่ล้างเมื่อออกจากระบบเหตุผล
1ที่เก็บที่ปกป้องล้างสวมรอยได้
2ธรรมดาไม่ล้างเป็นการตั้งค่าของเครื่อง ไม่ใช่ของผู้ใช้ (8.5)
3ธรรมดาไม่ล้างใช้เติมให้ตอนเข้าสู่ระบบใหม่ (8.7)
4ธรรมดา แต่ผูกกับผู้ใช้ไม่ล้างเป็นงานของผู้ใช้ (8.8)
5ธรรมดา แต่ผูกกับผู้ใช้ไม่ล้างต้องใช้ตอนส่งซ้ำ
6ดูข้อ 3ดูข้อ 3

ข้อ 2 น่าสนใจ — ที่อยู่เซิร์ฟเวอร์ไม่ควรล้างตอนออกจากระบบ เพราะเป็นการตั้งค่าที่ทีมติดตั้งเป็นคนตั้ง ไม่ใช่ผู้ใช้

ถ้าล้างด้วย คนกะถัดไปจะเปิดแอปมาแล้วต้องตั้งค่าเซิร์ฟเวอร์ใหม่ ซึ่งเขาไม่รู้ว่าต้องใส่อะไร

ข้อ 3 กับ 4 อยู่ในที่เก็บธรรมดาได้ แต่ ต้องผูกกับผู้ใช้ ตามที่ 5.4 และ 8.8 ย้ำไว้

await draftStorage.save(userId: session.username, draft: draft);

ข้อ 3 — รูปถ่ายที่รอส่ง

เป็นข้อที่ยากที่สุดเพราะมีหลายมิติ

มิติที่หนึ่ง — เก็บที่ไหน

ทางเลือกปัญหา
ที่เก็บที่ปกป้องไม่ได้ออกแบบมาเก็บไฟล์ใหญ่ — ช้าและมีข้อจำกัดขนาด
ไฟล์ในพื้นที่ของแอปเหมาะกับขนาด แต่ไม่ได้เข้ารหัส
คลังรูปของเครื่องอันตราย — แอปอื่นเห็นได้ และไปโผล่ในแกลเลอรี

คำตอบคือ ไฟล์ในพื้นที่ของแอป — เพราะรูปสินค้าเสียหายไม่ใช่ความลับระดับ token แต่ก็ไม่ควรไปโผล่ในแกลเลอรีให้ทุกคนเห็น

มิติที่สอง — ล้างเมื่อออกจากระบบไหม

นี่คือจุดที่ต้องคิดต่างจากข้ออื่น

ร่างใบรับเข้า (ข้อ 4)รูปถ่าย (ข้อ 6)
เป็นงานของผู้ใช้ไหมใช่ใช่
คนอื่นเห็นแล้วเสียหายไหมเห็นตัวเลขและรหัสสินค้าเห็นภาพจริงในคลัง
กินพื้นที่แค่ไหนน้อยมากมาก

สองแถวล่างทำให้คำตอบต่างจากข้อ 4

เก็บไว้ แต่ต้อง
  1. ผูกกับผู้ใช้ที่ถ่าย — คนถัดไปต้องไม่เห็น
  2. มีวันหมดอายุ — ลบอัตโนมัติหลัง 7 วัน
  3. ลบทันทีที่ส่งสำเร็จ — ไม่เก็บไว้ซ้ำ

ข้อ 2 จำเป็นเพราะ รูปที่ส่งไม่สำเร็จแล้วไม่มีใครกลับมาส่ง จะกินพื้นที่ไปเรื่อย ๆ จนเครื่องเต็ม แล้วทำให้ที่เก็บอื่นล้มเหลวตามไปด้วย ซึ่งเป็นสาเหตุหนึ่งในหัวข้อ 6

มิติที่สาม — สิ่งที่มักถูกลืม

ต้องทำเพราะ
ปิดการสำรองข้อมูลขึ้นคลาวด์ของโฟลเดอร์นี้ไม่งั้นรูปในคลังจะไปอยู่ในบัญชีส่วนตัวของพนักงาน
ไม่ใส่ตำแหน่งที่ถ่ายลงในไฟล์เป็นข้อมูลที่ไม่จำเป็นและอ่อนไหว

แถวแรกเป็นเรื่องที่คนไม่ค่อยคิดถึง — ระบบปฏิบัติการสำรองไฟล์ของแอปขึ้นคลาวด์ให้โดยอัตโนมัติในหลายกรณี และถ้าไม่ตั้งค่ายกเว้น รูปภายในคลังจะถูกคัดลอกออกไปโดยไม่มีใครตั้งใจ

บทเรียนที่ควรจำ: การเลือกที่เก็บไม่ได้ดูแค่ว่าอ่อนไหวแค่ไหน — ต้องดูขนาด อายุ และเส้นทางที่ข้อมูลอาจไหลออกไปโดยไม่ตั้งใจด้วย และไฟล์ขนาดใหญ่ที่ไม่มีวันหมดอายุ จะกลายเป็นสาเหตุที่ทำให้ที่เก็บอื่นล้มเหลว

12. สรุปท้ายบท

  • จัดชั้นความอ่อนไหวก่อน แล้วค่อยเลือกที่เก็บ
  • เกณฑ์คือถามว่าถ้าคนอื่นอ่านได้ เขาทำอะไรได้บ้าง
  • token ต้องอยู่ในที่เก็บที่ปกป้อง
  • ที่เก็บเป็นสัญญา เพื่อให้เปลี่ยนได้และทดสอบกรณีล้มเหลวได้
  • ที่เก็บที่ปกป้องก็ล้มเหลวได้ ทั้งตอนเขียนและตอนอ่าน
  • มันป้องกันแอปอื่น แต่ไม่ป้องกันคนที่ถือเครื่องที่ปลดล็อกอยู่
  • token อายุสั้นช่วยจำกัดความเสียหายที่ที่เก็บช่วยไม่ได้
  • คำถามว่า “ควรเก็บไหม” ต้องตอบก่อน “เก็บที่ไหน”
