1. ปัญหาที่บทนี้แก้

8.1 แยกคำสองคำไว้แล้ว และบทนี้คือที่ที่ความต่างนั้นสำคัญที่สุด

ยืนยันตัวตนสิทธิ์
ตอบคำถามคุณเป็นใครคุณทำอะไรได้
ตอบเมื่อไหร่ตอนเข้าสู่ระบบ ครั้งเดียวทุกครั้งที่ทำอะไร
ใครตอบเซิร์ฟเวอร์เซิร์ฟเวอร์

แถวล่างสำคัญ — ทั้งสองอย่างเซิร์ฟเวอร์เป็นคนตอบ ส่วนแอปแค่ใช้ข้อมูลนั้นทำให้หน้าจอสะดวกขึ้น

ความเข้าใจผิดที่พบบ่อยคือคิดว่าการซ่อนปุ่มคือการป้องกัน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
roleกลุ่มสิทธิ์ที่ตั้งชื่อไว้ เช่น PICKER
permissionสิทธิ์ทำสิ่งหนึ่ง เช่นปรับยอดสต๊อก
least privilegeให้สิทธิ์เท่าที่จำเป็นเท่านั้น

3. Mental model: ซ่อนปุ่มคือความสุภาพ ไม่ใช่รั้ว

ซ่อนปุ่ม   →  ผู้ใช้ไม่เห็นสิ่งที่กดไม่ได้  →  ประสบการณ์ดีขึ้น
เซิร์ฟเวอร์ตรวจ  →  ทำไม่ได้จริง            →  ป้องกันได้จริง
ประโยคเดียวที่ต้องจำ: การซ่อนปุ่มช่วยคนที่ตั้งใจทำงาน — ไม่ได้ช่วยกับคนที่ตั้งใจข้าม เพราะคำขอส่งตรงถึงเซิร์ฟเวอร์ได้โดยไม่ผ่านหน้าจอ

4. ใช้ role ปรับหน้าจอ

เปิด lib/auth/auth_session.dart

bool hasRole(String role) => roles.contains(role);
// ในหน้าจอ
if (session.hasRole('SUPERVISOR'))
  FilledButton(

  ),
ได้อะไร
คนที่ไม่มีสิทธิ์ไม่เห็นปุ่มที่กดไปก็ถูกปฏิเสธ
หน้าจอไม่รกด้วยสิ่งที่ใช้ไม่ได้

5. ทำไมถึงป้องกันไม่ได้

เหตุผลที่ตรงไปตรงมาที่สุด

คำขอที่แอปส่ง:
POST /api/WMS/stock/adjust
Authorization: Bearer eyJ...

ใครก็ตามที่มี token นี้ ส่งคำขอเดียวกันได้โดยไม่ต้องผ่านแอปเลย

วิธีที่ข้ามหน้าจอได้
ใช้เครื่องมือทดสอบ API ยิงตรง
แก้แอปแล้วติดตั้งเอง
ดักคำขอแล้วส่งซ้ำโดยแก้ค่า

ทั้งสามไม่ต้องใช้ความสามารถพิเศษอะไร — และ token ที่ได้มาก็เป็นของผู้ใช้เองอย่างถูกต้อง

เป็นหลักเดียวกับ 6.12 หัวข้อ 6 — การตรวจฝั่งแอปคือประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย

6. role ในแอปอาจไม่ใช่ความจริงล่าสุด

08:00  เข้าสู่ระบบ → token มี role SUPERVISOR
10:30  หัวหน้าถอดสิทธิ์ SUPERVISOR ออก
10:31  แอปยังแสดงปุ่มปรับยอด เพราะ token เดิมยังบอกว่ามีสิทธิ์
10:32  กดปุ่ม → server ปฏิเสธ 403
สิ่งที่ต้องรับมือทำอย่างไร
ปุ่มยังแสดงอยู่ทั้งที่ไม่มีสิทธิ์แล้วยอมรับ — เป็นข้อจำกัดตามธรรมชาติ
กดแล้วได้ 403ต้องรับมือให้ดี เพราะเกิดได้จริง
ผู้ใช้สับสนว่าทำไมปุ่มมีแต่กดไม่ได้บอกให้ชัด และเสนอให้เข้าสู่ระบบใหม่
case ApiFailureKind.forbidden:
  // ไม่ออกจากระบบ — สิทธิ์เปลี่ยน ไม่ใช่ตัวตนเปลี่ยน (7.5)
  showResultBanner(
    messenger,
    '${error.userMessage}\nหากเพิ่งได้รับสิทธิ์ กรุณาเข้าสู่ระบบใหม่',
    isError: true,
  );

ข้อความท่อนหลังสำคัญ — เพราะกรณีตรงข้ามก็เกิดเหมือนกัน คือ เพิ่งได้รับสิทธิ์แต่ token เก่ายังไม่มี ซึ่งแก้ได้ด้วยการเข้าสู่ระบบใหม่

7. อย่ากระจายชื่อ role ไปทั่วแอป

// เลี่ยง — ชื่อ role กระจายทุกหน้าจอ
if (session.hasRole('SUPERVISOR')) ...
if (session.hasRole('supervisor')) ...        // ตัวพิมพ์ไม่ตรง
if (session.hasRole('SUPERVISOR') || session.hasRole('ADMIN')) ...

ปัญหาเดียวกับ magic string ใน 6.9 — พิมพ์ผิดแล้วไม่มีอะไรเตือน และเปลี่ยนกติกาต้องไล่แก้ทุกที่

// รวมกฎไว้ที่เดียว
extension SessionPermissions on AuthSession {
  bool get canAdjustStock => hasRole('SUPERVISOR') || hasRole('ADMIN');
  bool get canCancelOrder => hasRole('SUPERVISOR');
  bool get canPick => hasRole('PICKER') || hasRole('SUPERVISOR');
}
// ในหน้าจอ — อ่านแล้วรู้ว่ากฎคืออะไร
if (session.canAdjustStock) ...
ได้อะไร
เปลี่ยนกฎที่เดียว ทุกหน้าจอเปลี่ยนตาม
ชื่อเมธอดบอกความหมาย ไม่ใช่บอกชื่อ role
เขียนเทสต์ของกฎได้โดยไม่ต้องสร้างหน้าจอ

เป็นหลักเดียวกับ 6.12 หัวข้อ 9 — รวมกฎไว้ที่ model ไม่ให้แต่ละหน้าจอตีความเอง

8. ปิดปุ่มดีกว่าซ่อน ในบางกรณี

สถานการณ์ควรทำเพราะ
สิทธิ์ที่คนส่วนใหญ่ไม่มีซ่อนไม่รกจอ และไม่ทำให้สงสัย
สิทธิ์ที่คนควรมีแต่ยังไม่มีปิดแต่แสดงให้รู้ว่ามีความสามารถนี้อยู่ และขอสิทธิ์ได้
สิทธิ์ที่ขึ้นกับสถานะของงานปิดพร้อมบอกเหตุผลผู้ใช้แก้เองได้
// แถวกลาง — เห็นแต่กดไม่ได้ พร้อมเหตุผล
Tooltip(
  message: 'ต้องมีสิทธิ์หัวหน้างาน',
  child: FilledButton(
    onPressed: session.canAdjustStock ? _adjust : null,
    child: const Text('ปรับยอด'),
  ),
)

การซ่อนทั้งหมดทำให้เกิดคำถามที่ตอบยาก — “ทำไมเครื่องของฉันไม่มีปุ่มนี้ แต่ของเพื่อนมี” ซึ่งคนหน้างานจะคิดว่าแอปพัง

9. ฝั่ง .NET ต้องตรวจทุกครั้ง

// ฝั่ง server (แนวคิด — รายละเอียดอยู่ในคอร์ส .NET)
app.MapPost("/api/WMS/stock/adjust", async (...) => { ... })
   .RequireAuthorization("CanAdjustStock");
ต้องตกลงเพราะ
ทุก endpoint ที่เปลี่ยนข้อมูลต้องมีการตรวจไม่มีข้อยกเว้น
ตอบ 403 พร้อมบอกว่าขาดสิทธิ์อะไรผู้ใช้จะได้รู้ว่าต้องขออะไร
ชื่อ role ที่ตรงกันทั้งสองฝั่งไม่งั้นซ่อนปุ่มผิดคน

แถวที่สองมีประโยชน์มากกว่าที่คิด

403 {
  "detail": "ต้องมีสิทธิ์ SUPERVISOR จึงจะปรับยอดได้",
  "errorCode": "MISSING_PERMISSION"
}

ทำให้แอปแสดงข้อความที่บอกได้ว่าต้องไปขออะไร แทนที่จะบอกแค่ “ไม่มีสิทธิ์”

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
คิดว่าซ่อนปุ่มแล้วปลอดภัยเข้าใจผิดว่าเป็นการป้องกันเซิร์ฟเวอร์ต้องตรวจทุกครั้ง
ถูกเด้งออกเมื่อได้ 403เหมารวมกับ 401แยกสองรหัส (7.5)
ชื่อ role พิมพ์ผิดแล้วไม่มีอะไรเตือนกระจายชื่อไปทั่วแอปรวมกฎไว้ที่เดียว
เพิ่งได้สิทธิ์แต่ยังกดไม่ได้token เก่ายังไม่มี role ใหม่บอกให้เข้าสู่ระบบใหม่
“ทำไมเครื่องฉันไม่มีปุ่มนี้”ซ่อนโดยไม่บอกเหตุผลปิดพร้อมบอกว่าต้องมีสิทธิ์อะไร
ปุ่มหายไปกลางกะสิทธิ์ถูกถอดแล้วโหลด session ใหม่บอกผู้ใช้ ไม่ให้คิดว่าแอปพัง

11. แบบฝึกหัด

ระบบมีสาม role และสี่การกระทำ

roleทำอะไรได้
PICKERดูงาน หยิบสินค้า
SUPERVISORทุกอย่างของ PICKER + ปรับยอด + ยกเลิกงาน
VIEWERดูอย่างเดียว
  1. เขียนกฎสิทธิ์ที่รวมไว้ที่เดียว
  2. ตัดสินว่าปุ่มไหนควรซ่อน ปุ่มไหนควรปิดแต่แสดง
  3. ตอบว่าถ้าฝั่งหลังบ้านเพิ่ม role AUDITOR ที่ดูได้ทุกคลังแต่แก้ไม่ได้ ฝั่งแอปต้องแก้อะไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — กฎสิทธิ์

extension SessionPermissions on AuthSession {
  /// ดูรายการงาน — ทุก role ทำได้
  bool get canViewTasks =>
      hasRole('PICKER') || hasRole('SUPERVISOR') || hasRole('VIEWER');

  bool get canPick => hasRole('PICKER') || hasRole('SUPERVISOR');

  bool get canAdjustStock => hasRole('SUPERVISOR');

  bool get canCancelTask => hasRole('SUPERVISOR');
}

สังเกตว่า เขียนเป็นรายชื่อที่อนุญาต ไม่ใช่รายชื่อที่ห้าม

// อันตราย — role ใหม่ที่เพิ่มมาจะได้สิทธิ์โดยอัตโนมัติ
bool get canPick => !hasRole('VIEWER');

เป็นหลักเดียวกับ isRetryable ใน 7.14 และ canWorkOn ใน 6.9 — และข้อ 3 จะแสดงว่าทำไมสำคัญ

ข้อ 2 — ซ่อนหรือปิด

ปุ่มทำอย่างไรเหตุผล
ดูงานแสดงเสมอทุก role ทำได้
หยิบสินค้าปิดแต่แสดง สำหรับ VIEWERเป็นงานหลักของแอป — ซ่อนแล้วจะงงว่าใช้แอปทำอะไร
ปรับยอดซ่อน สำหรับ PICKERคนหยิบของส่วนใหญ่ไม่เคยต้องใช้
ยกเลิกงานปิดแต่แสดงมีกรณีที่คนหยิบอยากยกเลิกแล้วต้องขอหัวหน้า

เกณฑ์ที่ใช้ตัดสิน — ถ้าผู้ใช้มีเหตุผลที่จะอยากทำสิ่งนั้น ให้แสดงแล้วบอกว่าต้องมีสิทธิ์อะไร

// VIEWER เห็นปุ่มหยิบ แต่กดไม่ได้ พร้อมเหตุผล
Tooltip(
  message: 'บัญชีของคุณดูข้อมูลได้อย่างเดียว',
  child: FilledButton(
    onPressed: session.canPick ? _pick : null,
    child: const Text('หยิบสินค้า'),
  ),
)

ถ้าซ่อนไปเลย VIEWER จะเปิดแอปมาแล้วเห็นแค่รายการที่กดอะไรไม่ได้เลย และจะคิดว่าแอปโหลดไม่ครบ

ข้อ 3 — เพิ่ม role AUDITOR

ถ้าเขียนเป็นรายชื่อที่อนุญาตตามข้อ 1 คำตอบคือ เพิ่มชื่อเข้าไปในกฎที่เกี่ยวข้องเท่านั้น

bool get canViewTasks =>
    hasRole('PICKER') ||
    hasRole('SUPERVISOR') ||
    hasRole('VIEWER') ||
    hasRole('AUDITOR');       // เพิ่มบรรทัดเดียว

// กฎอื่นไม่ต้องแตะเลย — AUDITOR แก้ไม่ได้อยู่แล้ว

แต่ถ้าเขียนเป็นรายชื่อที่ห้าม จะเกิดช่องโหว่ทันที

bool get canPick => !hasRole('VIEWER');

// AUDITOR ไม่ใช่ VIEWER → เงื่อนไขเป็นจริง → เห็นปุ่มหยิบสินค้า
// ทั้งที่ไม่ควรมีสิทธิ์

และเพราะเป็นแค่การซ่อนปุ่ม ช่องโหว่นี้ไม่ได้ทำให้ AUDITOR หยิบของได้จริง — เซิร์ฟเวอร์จะปฏิเสธอยู่ดี

แต่มันสร้างปัญหาอื่น

ผลที่ตามมา
AUDITOR เห็นปุ่มที่กดแล้วได้ 403 ทุกครั้ง
คิดว่าแอปพัง แล้วแจ้งทีม
ทีมเสียเวลาไล่หาสาเหตุที่ไม่ใช่บั๊กจริง

สิ่งที่ต้องทำเพิ่มนอกจากแก้กฎ

ทำอะไรเพราะ
ตกลงชื่อ role กับฝั่งหลังบ้านก่อนถ้าสะกดต่างกัน จะซ่อนปุ่มผิดคน
ตรวจว่ามีกฎไหนที่ควรรวม AUDITOR อีกเช่นดูรายงาน
เขียนเทสต์ของกฎแต่ละข้อกับ role ใหม่ยืนยันว่าไม่ได้สิทธิ์เกิน
test('AUDITOR ดูได้อย่างเดียว', () {
  final session = sessionWithRoles({'AUDITOR'});

  expect(session.canViewTasks, isTrue);
  expect(session.canPick, isFalse);
  expect(session.canAdjustStock, isFalse);
  expect(session.canCancelTask, isFalse);
});

เทสต์แบบนี้เขียนง่ายและเร็วมาก เพราะกฎถูกรวมไว้ที่เดียวและไม่ต้องสร้างหน้าจอ

บทเรียนที่ควรจำ: การเขียนกฎสิทธิ์เป็นรายชื่อที่อนุญาต ทำให้ role ใหม่ ไม่ได้อะไรเลยโดยอัตโนมัติ ซึ่งเป็นค่าตั้งต้นที่ปลอดภัย — ส่วนรายชื่อที่ห้ามให้ค่าตั้งต้นตรงข้าม และผิดพลาดในทางที่อันตรายกว่า

12. สรุปท้ายบท

  • ยืนยันตัวตนกับสิทธิ์เป็นคนละคำถาม และเซิร์ฟเวอร์ตอบทั้งคู่
  • ซ่อนปุ่มคือประสบการณ์ ไม่ใช่การป้องกัน
  • คำขอส่งตรงถึงเซิร์ฟเวอร์ได้โดยไม่ผ่านหน้าจอ
  • role ใน token อาจไม่ใช่ความจริงล่าสุด ต้องรับมือกับ 403 เสมอ
  • 403 ไม่ควรทำให้ออกจากระบบ
  • รวมกฎสิทธิ์ไว้ที่เดียว อย่ากระจายชื่อ role
  • เขียนกฎเป็นรายชื่อที่อนุญาต ไม่ใช่รายชื่อที่ห้าม
  • สิทธิ์ที่ผู้ใช้มีเหตุผลจะอยากใช้ ควรปิดแต่แสดงพร้อมเหตุผล
