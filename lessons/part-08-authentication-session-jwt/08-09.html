UI permission เป็น UX ไม่ใช่ security: ใช้ซ่อน/disable action ที่ผู้ใช้ทำไม่ได้ แต่ .NET endpoint ต้อง enforce policy ทุกครั้ง

1. Role vs permission

Role เช่น OPERATOR/SUPERVISOR เป็นกลุ่มกว้าง ส่วน permission เช่น inventory.adjust สื่อ action ชัดและลด if-role กระจายเมื่อ role เปลี่ยน

2. Typed access

enum Permission { receive, pick, adjustInventory }

bool can(Permission p) => session.permissions.contains(p);

if (auth.can(Permission.adjustInventory))
  FilledButton(onPressed: adjust, child: const Text('ปรับสต็อก'));

3. Claim normalization

.NET role claim อาจเป็น string เดียว/list/URI key ให้ Auth mapper normalize เป็น lower/upper convention และ immutable set จุดเดียว ไม่เทียบ raw dynamic ใน widgets

4. Hide หรือ disable

ซ่อน action ที่ไม่เกี่ยวกับผู้ใช้เพื่อลด clutter; disable พร้อมเหตุผลเมื่อผู้ใช้ควรรู้ว่าฟีเจอร์มีแต่ต้องขอสิทธิ์ โดยคำนึง accessibility

5. Server remains authority

permission อาจเปลี่ยนหลัง token ออก, device offline หรือ client ถูกดัดแปลง จึง handle 403 เสมอและ refresh profile/session ตาม policy

6. Avoid route-only protection

เมนูไม่แสดงไม่ได้แปลว่า route เข้าไม่ได้ Route guard ตรวจ session/permission อีกชั้น แต่ endpoint ยังต้อง authorize เป็นชั้นสุดท้าย

7. แบบฝึกหัด

SUPERVISOR เห็นปุ่ม adjust แต่ serverตอบ 403 ควรทำอย่างไร?

เฉลย

แสดงไม่มีสิทธิ์ ไม่ logout; invalidate/refresh permission stateถ้ารองรับ และ log trace ID—not retry วนหรือฝืน UI

8. Tests

ไม่มี claim, role เดี่ยว/หลาย role, case ต่าง, unknown permission, route deep link และ 403 หลัง UI เปิด action
