AuthRepository เป็น boundary: LoginScreen จัด form/feedback; repository รู้ endpoint, DTO, session persistence และการผูก token กับ ApiClient

1. ปัญหาของ fat LoginScreen

ถ้า widget ต่อ URL, encode password, parse token, เขียน storage และ navigate เอง จะทดสอบยากและ logic auth ซ้ำทุกหน้าที่ต้อง re-login

2. Interface

abstract interface class AuthRepository {
  AuthSession? get session;
  Future<AuthSession> login(LoginRequest request);
  Future<void> restore();
  Future<void> logout();
}

3. Screen เหลือ orchestration

try {
  await auth.login(LoginRequest(
    username: user.text.trim(), password: pass.text));
  if (!context.mounted) return;
  Navigator.pushReplacement(context, shellRoute());
} on InvalidCredentialsException {
  setState(() => error = 'ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง');
}

4. Dependency graph

composition root สร้าง TokenStore → ApiClient → AuthRepository แล้วส่ง instance เดียวให้ LoginScreen และ shell เพื่อให้ bearer token/session เป็น single source of truth

5. Repository ไม่ควรรู้ BuildContext

คืน typed result/exception ให้ controller หรือ screen ตัดสิน navigation/dialog เพราะ repository ต้องใช้ได้ใน bootstrap, background flow และ unit test

6. ของจริงและจุดต่อยอด

wms_absolute_mobile แยก repository แล้ว แต่ session ยังอยู่ memory และ repository ตั้ง _api.authToken โดยตรง ขั้นต่อไปคือ inject session/token store และ notifier เพื่อ restore/logout แบบทดสอบได้

7. แบบฝึกหัด

เขียน fake repository ที่ login EMP001 สำเร็จและ user อื่น throw InvalidCredentials เพื่อทดสอบ LoginScreen โดยไม่เปิด server

เฉลย

fake ต้องบันทึก request เพื่อ assert trim/ไม่ submit ซ้ำ และ expose session หลังสำเร็จ

8. Review rule

หากพบ SharedPreferences.getInstance(), jsonDecode หรือ Authorization header ใน LoginScreen ให้ย้ายออกไป boundary ที่รับผิดชอบ
