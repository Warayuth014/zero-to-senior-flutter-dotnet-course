2. part ทำอะไร

ปกติแต่ละไฟล์ Dart เป็นหน่วยของตัวเอง สิ่งที่ขึ้นต้นด้วยขีดล่างจะเห็นได้เฉพาะในไฟล์นั้น

// ถ้าเป็นไฟล์ธรรมดา บรรทัดนี้จะคอมไพล์ไม่ผ่าน
final response = await _get('/receiving/po/$poId');
//                          ^^^^ _get เป็น private ของ api_service.dart

part ทำให้เก้าไฟล์นี้กลายเป็นเนื้อเดียวกันกับ api_service.dart ในสายตาคอมไพเลอร์

partimport
เห็นสิ่งที่ขึ้นต้นด้วย _เห็นไม่เห็น
ต้องประกาศสองฝั่งต้อง (part + part of)ฝั่งเดียว
มี import ของตัวเองไม่มี ใช้ของไฟล์หลักมี
นับเป็นไฟล์แยกตอนอ่านใช่ใช่

สังเกตแถวที่สาม — ไฟล์ใน api/ ไม่มี import เลยแม้แต่บรรทัดเดียว ทั้งที่ใช้ File, Uri, และคลาสโมเดลทั้งหมด เพราะได้มาจาก api_service.dart ทั้งหมด

ผลที่ต้องรู้ตอนแก้: ถ้าจะใช้คลาสใหม่ใน picking_api.dart ต้องไปเพิ่ม import ที่ api_service.dart ไม่ใช่ที่ไฟล์ที่กำลังแก้ — เป็นจุดที่คนใหม่งงบ่อยที่สุด

3. extension ทำอะไร

extension เพิ่มเมธอดให้คลาสที่มีอยู่แล้ว โดยไม่ต้องแก้ตัวคลาส

extension ReceivingApi on ApiService {
  Future<ApiResult<POResponse>> getPO(String poId) async { ... }
}

ทำให้เรียกได้เหมือนเป็นเมธอดของ ApiService เอง

final result = await ApiService().getPO('PO-2024-001');

ประโยชน์ที่ได้จริง

ประโยชน์รายละเอียด
api_service.dart ไม่บวมถ้าเอา 42 เมธอดมาไว้ในคลาสจะยาว 700+ บรรทัด
หาของง่ายอยากรู้เรื่อง picking เปิดไฟล์เดียว
แก้คนละโดเมนไม่ชนกันสองคนแก้คนละไฟล์ merge ได้

ข้อจำกัดที่ต้องรู้

ข้อจำกัดผล
extension เพิ่ม state ไม่ได้ประกาศ field ในนี้ไม่ได้ ต้องไปไว้ที่คลาส
ไม่ใช่ชั้นที่แยกจริงยังเป็น ApiService ตัวเดิม สลับตัวปลอมไม่ได้
ชื่อชนกันได้ถ้ามีสอง extensionต้องระวังตั้งชื่อเมธอดซ้ำ

แถวกลางสำคัญ — การแยกเป็นเก้าไฟล์ช่วยเรื่องการอ่าน ไม่ได้ช่วยเรื่องการทดสอบ ต่างจากชั้น repository ที่ 9.4 สอน ซึ่งแยกด้วย interface และสลับได้จริง

4. รูปแบบที่ซ้ำกัน 42 ครั้ง

Future<ApiResult<POResponse>> getPO(String poId) async {
  final response = await _get('/receiving/po/$poId');
  if (!response.success) return ApiResult.error(response.error);

  return ApiResult.success(POResponse.fromJson(response.data!));
}

สี่บรรทัดนี้ทำสามอย่าง

บรรทัดทำอะไร
1ประกอบ path แล้วยิง
2ล้มเหลว → ส่งต่อ
3สำเร็จ → แปลง Map เป็นโมเดล

นี่คือหน้าที่ที่ 9.5 เรียกว่า “ชั้นที่แปลงข้อมูลดิบเป็นชนิดที่โดเมนใช้” — จอไม่ต้องรู้จัก Map<String, dynamic> เลย ได้ POResponse ที่มีชนิดกำกับครบ

รูปแบบการประกอบ path มีสามแบบในโปรเจกต์

// แบบที่ 1 — ต่อสตริงตรง ๆ
await _get('/receiving/po/$poId');

// แบบที่ 2 — ใช้ Uri สำหรับ query parameters
final path = Uri(
  path: '/receiving/validate-serial',
  queryParameters: {'partId': partId, 'serialNo': serialNo},
).toString();

// แบบที่ 3 — เข้ารหัสเอง
final qs = pickOrderId != null
    ? '?pickOrderId=${Uri.encodeQueryComponent(pickOrderId)}'
    : '';
แบบปลอดภัยไหม
1ไม่ ถ้าค่ามีอักขระพิเศษ เช่น # หรือช่องว่าง
2ปลอดภัย — Uri เข้ารหัสให้
3ปลอดภัย แต่ต้องจำเองทุกครั้ง

ในทางปฏิบัติแบบที่ 1 ทำงานได้เพราะรหัส PO และรหัสพาเลทเป็นตัวอักษรกับตัวเลขล้วน แต่ถ้าวันหนึ่งมีรหัสที่มีขีดทับหรือช่องว่าง จะพังโดยไม่มีคำเตือน

ผลที่ตามมา — ApiResult.isNotFound ใช้ได้กับ 23 เมธอดและใช้ไม่ได้กับอีก 20 โดยที่ไม่มีอะไรบอก

final result = await api.getPO(poId);
if (result.isNotFound) {          // ← ไม่มีวันเป็น true เพราะ getPO ทิ้ง statusCode
  showNotFoundMessage();
}
สิ่งที่ทำให้เรื่องนี้อันตราย: โค้ดคอมไพล์ผ่าน ไม่มีคำเตือน และเงื่อนไขเป็น false เงียบ ๆ ผลคือแอปแสดงข้อความผิดพลาดทั่วไปแทนข้อความที่ควรบอกว่า “ไม่พบ PO นี้”

ตอนนี้ยังไม่มีจอไหนใช้ isNotFound เลย — ค้นทั้งโปรเจกต์เจอที่เดียวคือบรรทัดที่ประกาศมันเอง จึงยังไม่เกิดปัญหา แต่คนแรกที่หยิบไปใช้จะเจอทันที และจะหาสาเหตุยากมาก

แก้ได้ด้วยการเปลี่ยน 20 บรรทัด

- if (!response.success) return ApiResult.error(response.error);
+ if (!response.success) {
+   return ApiResult.error(response.error, statusCode: response.statusCode);
+ }

วิธีที่ดีกว่าคือทำให้ลืมไม่ได้ตั้งแต่แรก — เพิ่มตัวช่วยใน ApiResult

/// แปลงความล้มเหลวเป็นชนิดอื่นโดยพก statusCode ไปด้วยเสมอ
ApiResult<R> asFailure<R>() => ApiResult<R>.error(error, statusCode: statusCode);
if (!response.success) return response.asFailure();

สั้นกว่าเดิม อ่านง่ายกว่า และไม่มีทางลืมเพราะไม่มีอะไรให้ลืม

6. ความไม่สม่ำเสมออื่นที่เจอในไฟล์เดียวกัน

picking_api.dart มีทั้งสามแบบของการคืนรายการ

// แบบ A — กัน null ไว้
final items = (response.data!['items'] as List? ?? [])

// แบบ B — ไม่กัน
final list = (response.data!['items'] as List).cast<Map<String, dynamic>>();

แบบ B จะโยน TypeError ถ้าเซิร์ฟเวอร์ไม่ส่ง items มา ซึ่งเกิดได้ถ้ามีการเปลี่ยนฝั่ง .NET

และมีเมธอดหนึ่งที่คืนชนิดที่น่าสนใจ

Future<ApiResult<({String palletId, bool continued})?>>
    getSuggestedDestPallet({String? pickOrderId}) async {
  ...
  if (list.isEmpty) return ApiResult.success(null);   // ← สำเร็จ แต่ไม่มีข้อมูล

แยก “สำเร็จแต่ไม่มีพาเลทว่าง” ออกจาก “ล้มเหลว” ได้ถูกต้อง — ตรงกับที่ 6.11 สอนว่าอย่าเอา null ไปปนกับความผิดพลาด

ผลลัพธ์แปลว่าจอควรทำ
success + ข้อมูลมีพาเลทแนะนำเติมให้เลย
success + nullไม่มีพาเลทว่างให้ผู้ใช้สแกนเอง
errorถามไม่ได้แสดงข้อความ

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
ไฟล์ใน api/ เป็นไฟล์แยก เพิ่ม import ที่นั่นได้ต้องเพิ่มที่ api_service.dart
การแยกเป็นเก้าไฟล์ทำให้เทสต์ง่ายขึ้นช่วยการอ่าน ไม่ช่วยการทดสอบ
isNotFound ใช้ได้ทุกเมธอดใช้ได้ 23 จาก 43 จุด
ต่อ path ด้วยสตริงปลอดภัยพังถ้าค่ามีอักขระพิเศษ
ApiResult.success(null) แปลว่ามีอะไรผิดแปลว่าสำเร็จและคำตอบคือ “ไม่มี”

8. แบบฝึกหัด

ต้องเพิ่ม endpoint ใหม่: ค้นหา PO จากรหัสผู้ขาย คืนรายการ PO ที่ยังไม่ปิด

  1. ต้องแตะไฟล์ไหนบ้าง เรียงตามลำดับที่ทำจริง
  2. เขียนเมธอดให้ครบ โดยไม่ทำผิดแบบที่บทนี้ชี้ไว้
  3. ถ้าผู้ขายไม่มี PO ค้างเลย ควรคืนอะไร
แนวคำตอบ

ข้อ 1

ลำดับไฟล์ทำอะไร
1ฝั่ง .NETทำ endpoint ให้มีก่อน ไม่งั้นทดสอบไม่ได้
2models/receiving/receiving_models.dartเพิ่มคลาสถ้ารูปร่างข้อมูลใหม่
3services/api/receiving_api.dartเพิ่มเมธอด
4จอที่ใช้เรียกและแสดง

ไม่ต้องแตะ api_service.dart ยกเว้นต้องใช้คลาสจากไลบรารีใหม่

ข้อ 2

/// ค้นหา PO ที่ยังไม่ปิดของผู้ขายรายหนึ่ง
/// คืนรายการว่างถ้าไม่มี PO ค้าง — ไม่ใช่ความล้มเหลว
Future<ApiResult<List<POSummary>>> getOpenPOsBySupplier(String supplierId) async {
  // ใช้ Uri เพื่อให้รหัสผู้ขายที่มีอักขระพิเศษไม่ทำ path พัง
  final path = Uri(
    path: '/receiving/pos',
    queryParameters: {'supplierId': supplierId, 'status': 'OPEN'},
  ).toString();

  final response = await _get(path);
  if (!response.success) {
    // ส่ง statusCode ต่อ ไม่งั้น isNotFound ใช้ไม่ได้
    return ApiResult.error(response.error, statusCode: response.statusCode);
  }

  // กัน null ไว้ — เซิร์ฟเวอร์อาจไม่ส่ง items มาถ้าไม่มีข้อมูล
  final items = (response.data!['items'] as List? ?? [])
      .map((e) => POSummary.fromJson(e as Map<String, dynamic>))
      .toList();

  return ApiResult.success(items);
}

สี่จุดที่เลี่ยงกับดักของบทนี้: ใช้ Uri, ส่ง statusCode ต่อ, กัน null ที่ items, และ cast ชนิดของสมาชิกให้ชัด

ข้อ 3 — ไม่มี PO ค้าง

ทางเลือกเหมาะไหม
ApiResult.success([])ใช่ — ถามสำเร็จ คำตอบคือไม่มี
ApiResult.success(null)ไม่ — ทำให้จอต้องตรวจสองอย่าง (null และ ว่าง)
ApiResult.error('ไม่พบ PO')ไม่ — จอจะแสดงเป็นข้อความผิดพลาดสีแดง ทั้งที่ไม่มีอะไรผิด

ต่างจาก getSuggestedDestPallet ที่คืน null ได้อย่างถูกต้อง เพราะที่นั่นคำตอบคือของชิ้นเดียว ไม่ใช่รายการ — ของชิ้นเดียวที่ไม่มีคือ null แต่รายการที่ไม่มีสมาชิกคือรายการว่าง

สิ่งที่จอต้องทำต่างกัน

if (!result.success) {
  showError(result.error!);              // ถามไม่ได้
} else if (result.data!.isEmpty) {
  showEmptyState('ผู้ขายรายนี้ไม่มี PO ค้าง');   // ถามได้ คำตอบคือไม่มี
} else {
  showList(result.data!);
}

สามทางนี้ต้องแยกกันเสมอ เพราะผู้ใช้ต้องทำคนละอย่าง — ทางแรกลองใหม่ ทางที่สองไปสแกนที่อื่น ทางที่สามทำงานต่อ

9. สรุป

  • เก้าไฟล์ใน services/api/ รวม 568 บรรทัด 42 endpoint และเป็น part ของ api_service.dart
  • part ทำให้เห็นเมธอดที่ขึ้นต้นด้วยขีดล่าง แต่ต้องเพิ่ม import ที่ไฟล์หลัก
  • extension ช่วยจัดระเบียบให้อ่านง่าย แต่ไม่ได้แยกชั้นจริงและไม่ช่วยเรื่องเทสต์
  • รูปแบบซ้ำ 42 ครั้ง: ยิง → ล้มเหลวส่งต่อ → สำเร็จแปลงเป็นโมเดล
  • 23 จุดส่ง statusCode ต่อ อีก 20 จุดทิ้ง ทำให้ isNotFound ใช้ได้ไม่ทั่ว
  • ยังไม่มีจอไหนใช้ isNotFound จึงยังไม่เกิดปัญหา แต่คนแรกที่ใช้จะเจอ
  • เพิ่ม asFailure() แล้วจะลืมไม่ได้อีก
  • รายการที่ไม่มีสมาชิกคือรายการว่าง ไม่ใช่ null และไม่ใช่ความล้มเหลว
