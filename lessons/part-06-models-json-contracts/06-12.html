              [2] ก่อนส่ง         ตรวจว่าคำสั่งสมเหตุสมผล

4. ด่านที่ 4: ตรงตามสัญญาไหม

นี่คือด่านที่ Part 6 ทั้ง Part พูดถึง แบ่งเป็นสองชั้นย่อย

ชั้นตรวจอะไรอยู่ที่
รูปแบบคีย์มีไหม ชนิดถูกไหม เวลามีเขตเวลาไหมjson_read.dart + DTO
ความหมายจำนวนมากกว่าศูนย์ไหม สถานะรู้จักไหมตัวแปลงเป็น domain

เส้นแบ่งคือ ต้องรู้เรื่องธุรกิจถึงจะตรวจได้หรือไม่

// รูปแบบ — ไม่ต้องรู้ว่าเป็นข้อมูลอะไร
quantity: requireInt(json, 'quantity', path: path),

// ความหมาย — ต้องรู้ว่าจำนวนของงานหยิบสินค้าติดลบไม่ได้
if (dto.quantity <= 0) {
  throw ContractException(..., 'จำนวนต้องมากกว่าศูนย์ แต่ได้ ${dto.quantity}');
}

สังเกตว่า requireInt ไม่รู้ว่า quantity คืออะไร มันแค่รู้ว่าเป็นจำนวนเต็ม — จึงเอาไปใช้กับ field ไหนก็ได้ ส่วนกฎว่าต้องมากกว่าศูนย์ ใช้ได้เฉพาะกับจำนวนของงาน ไม่ใช่กับส่วนลดที่ติดลบได้

5. ผิดที่เดียวคือผิดทั้งก้อน

คำถามที่ต้องตอบ — เมื่อบรรทัดที่ 7 จาก 20 มีข้อมูลผิด ควรทำอย่างไร

ทางเลือกเหมาะกับ
ปฏิเสธทั้งก้อนงานที่ทำครึ่ง ๆ ไม่ได้ เช่นใบรับเข้า
เอาเฉพาะที่ใช้ได้ แล้วบอกจำนวนที่ตกไปรายการที่แต่ละแถวเป็นอิสระ เช่นรายการงานประจำวัน

lab เลือกแบบแรกทั้งสองที่ เพราะทั้งรายการงานและใบรับเข้าเป็นข้อมูลที่ใช้ตัดสินใจทำงานจริง

// ใน TaskPageDto — แถวไหนพัง ทั้งหน้าไม่ผ่าน
for (var index = 0; index < rawItems.length; index++) {
  final path = 'items[$index]';
  items.add(TaskDto.fromJson(requireMap(rawItems[index], path), path: path));
}

เหตุผลที่ไม่ข้ามแถวที่เสีย — ผู้ใช้ไม่มีทางรู้ว่าเห็นไม่ครบ

เซิร์ฟเวอร์ส่งมา 20 งาน แต่แถวที่ 7 ข้อมูลเสีย
  → ข้ามไป แสดง 19 งาน
  → คนหน้างานทำครบ 19 แล้วปิดวัน
  → งานที่ 7 ไม่มีใครทำ และไม่มีใครรู้

ถ้าจำเป็นต้องข้ามจริง ๆ ต้องแสดงให้เห็นเสมอว่าข้ามไปกี่รายการ ไม่ใช่ข้ามเงียบ ๆ

7. แยกชนิดความล้มเหลวให้รับมือถูก

ความล้มเหลวคนละชนิดต้องให้ผู้ใช้ทำคนละอย่าง

ชนิดสาเหตุผู้ใช้ควรทำลองใหม่ช่วยไหม
เครือข่ายเน็ตหลุด หมดเวลารอลองใหม่ช่วย
สัญญาข้อมูลไม่ตรงที่ตกลงแจ้งทีมไม่ช่วย
สิทธิ์ไม่มีสิทธิ์ทำติดต่อหัวหน้าไม่ช่วย
ขัดแย้งคนอื่นทำไปก่อนโหลดใหม่แล้วดูอีกทีไม่ช่วย
กฎธุรกิจของไม่พอแก้จำนวนแล้วส่งใหม่ไม่ช่วยถ้าไม่แก้

ถ้ายุบทุกชนิดเป็น “เกิดข้อผิดพลาด” พร้อมปุ่มลองใหม่ ผู้ใช้จะกดลองใหม่กับทุกอย่าง และสี่ในห้าแถวจะได้ผลเดิม

8. บันทึกให้พอตามไปแก้

ความล้มเหลวเรื่องสัญญาต่างจากชนิดอื่น — มันแปลว่า มีคนต้องแก้อะไรบางอย่าง ไม่ใช่แค่ผู้ใช้ลองใหม่

ต้องรู้เพื่อ
endpoint ไหนรู้ว่าทีมไหนต้องแก้
path ที่พังรู้ว่า field ไหน
รุ่นของแอปรู้ว่าเป็นแอปเก่าหรือเซิร์ฟเวอร์ใหม่
เกิดกี่ครั้งรู้ว่าเป็นข้อมูลเสียใบเดียว หรือสัญญาเปลี่ยนทั้งระบบ

แถวสุดท้ายสำคัญ — ถ้าเกิดครั้งเดียวคือข้อมูลใบนั้นเสีย แต่ถ้าเกิดทุกคำขอคือสัญญาเปลี่ยน ซึ่งเร่งด่วนกว่ามาก

และตามที่บอกใน 6.8 — บันทึก path กับชนิด แต่ไม่บันทึก payload ทั้งก้อน

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
กฎธุรกิจอยู่ในตัวอ่าน JSONไม่ได้แยกรูปแบบออกจากความหมายย้ายไปตัวแปลงเป็น domain
ทุกหน้าจอมีเงื่อนไขของตัวเองไม่ได้รวมกฎไว้ที่ modelทำเป็น getter
งานหายไปโดยไม่มีใครรู้ข้ามแถวที่เสียเงียบ ๆปฏิเสธทั้งก้อน หรือแสดงจำนวนที่ตกไป
ผู้ใช้กดลองใหม่กับทุกอย่างยุบทุกความล้มเหลวเป็นชนิดเดียวแยกชนิดตั้งแต่ exception
เชื่อว่าตรวจฝั่งแอปแล้วปลอดภัยเข้าใจผิดว่าด่าน 1–2 คือความปลอดภัยเซิร์ฟเวอร์ต้องตรวจซ้ำเสมอ
รู้ว่าพังแต่ไม่รู้ว่าเร่งด่วนแค่ไหนไม่ได้นับจำนวนครั้งบันทึกเป็นตัวนับ
ตรวจซ้ำหลายรอบในแอปไม่เชื่อว่าด่านก่อนหน้าตรวจแล้วให้ผ่านด่านแปลงแล้วเชื่อได้

11. แบบฝึกหัด

ฟีเจอร์ปรับยอดสต๊อกมีกฎห้าข้อ

#กฎ
1ต้องกรอกจำนวน และต้องเป็นตัวเลข
2จำนวนที่ปรับต้องไม่เกิน 999
3ต้องเลือกเหตุผลในการปรับ
4ยอดหลังปรับต้องไม่ติดลบ
5ผู้ใช้ต้องมีสิทธิ์ปรับยอดของคลังนั้น
  1. จัดแต่ละกฎลงด่านตามหัวข้อ 3
  2. ระบุกฎที่ต้องตรวจมากกว่าหนึ่งด่าน และอธิบายว่าทำไม
  3. ตอบว่าถ้าเซิร์ฟเวอร์ปฏิเสธเพราะกฎข้อ 4 แอปควรทำอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — จัดลงด่าน

กฎด่าน 1 (หน้าจอ)ด่าน 2 (ก่อนส่ง)ด่าน 3 (เซิร์ฟเวอร์)
1. กรอกจำนวน เป็นตัวเลขใช่ใช่ใช่
2. ไม่เกิน 999ใช่ใช่ใช่
3. ต้องเลือกเหตุผลใช่ใช่ใช่
4. ยอดหลังปรับไม่ติดลบบอกได้ แต่ไม่แน่บอกได้ แต่ไม่แน่ใช่ — ที่นี่เท่านั้นที่แน่
5. มีสิทธิ์ปรับยอดซ่อนปุ่มได้—ใช่ — ที่นี่เท่านั้น

สังเกตว่าคอลัมน์ขวาสุดมีเครื่องหมายทุกแถว — เซิร์ฟเวอร์ต้องตรวจทุกกฎ ไม่มีข้อยกเว้น

ข้อ 2 — กฎที่ต้องตรวจหลายด่าน และเพราะอะไร

ต้องแยกเหตุผลสองแบบออกจากกัน

แบบที่หนึ่ง — ตรวจซ้ำเพื่อประสบการณ์ (กฎ 1, 2, 3)

ตรวจที่ไหนได้อะไร
หน้าจอผู้ใช้รู้ทันทีขณะพิมพ์ ไม่ต้องรอเซิร์ฟเวอร์
เซิร์ฟเวอร์เป็นด่านจริง กันกรณีที่แอปมีบั๊กหรือถูกข้าม

กฎสามข้อนี้ ผลไม่เปลี่ยนตามเวลา — 1000 เกิน 999 ไม่ว่าจะตรวจเมื่อไหร่ การตรวจฝั่งแอปจึงให้คำตอบที่ตรงกับเซิร์ฟเวอร์เสมอ

แบบที่สอง — ตรวจฝั่งแอปได้แค่ประมาณ (กฎ 4)

10:00:00  โหลดข้อมูล — ยอดคงเหลือ 50
10:00:20  คนอื่นเบิกไป 45 ชิ้น
10:00:30  ผู้ใช้กรอกปรับลด 20
          → แอปคำนวณ 50 - 20 = 30 → ผ่าน
          → เซิร์ฟเวอร์คำนวณ 5 - 20 = -15 → ปฏิเสธ

แอปไม่ได้ตรวจผิด — มันตรวจถูกตามข้อมูลที่มี แต่ข้อมูลที่มีเก่าไปแล้ว

กฎ 1–3กฎ 4
แอปตรวจแล้วมั่นใจได้ไหมได้ไม่ได้
ควรบอกผู้ใช้อย่างไร“เกิน 999 ไม่ได้”“จากข้อมูลล่าสุดจะเหลือ 30” — เป็นการประมาณ
ถ้าเซิร์ฟเวอร์ปฏิเสธแปลว่าแอปมีบั๊กเป็นเรื่องปกติ ไม่ใช่บั๊ก

แถวสุดท้ายสำคัญ — การที่เซิร์ฟเวอร์ปฏิเสธกฎ 4 ไม่ใช่ความผิดพลาดของใคร จึงต้องออกแบบให้เป็นเส้นทางปกติ ไม่ใช่หน้าจอผิดพลาด

ฝั่งแอปซ่อนปุ่มได้ตามสิทธิ์ที่รู้ แต่นั่นเป็นแค่การจัดหน้าจอ ไม่ใช่การตรวจ — เพราะสิทธิ์อาจถูกเพิกถอนหลังจากที่แอปโหลดข้อมูลไปแล้ว และเพราะคำขอส่งตรงถึงเซิร์ฟเวอร์ได้โดยไม่ผ่านหน้าจอ

ข้อ 3 — เมื่อเซิร์ฟเวอร์ปฏิเสธเพราะกฎ 4

สิ่งที่ต้องทำตามลำดับ

1. อย่าแสดงเป็น "เกิดข้อผิดพลาด"
     เป็นเส้นทางปกติ ไม่ใช่ความล้มเหลวของระบบ

2. บอกความจริงล่าสุดที่เซิร์ฟเวอร์ส่งกลับมา
     "ยอดคงเหลือปัจจุบันคือ 5 ไม่ใช่ 50 ที่แสดงอยู่"

3. อัปเดตข้อมูลบนจอให้ตรงกับความจริง
     ไม่ให้ผู้ใช้ตัดสินใจจากตัวเลขเก่าอีก

4. เก็บสิ่งที่ผู้ใช้กรอกไว้
     อย่าล้างฟอร์มให้กรอกใหม่ทั้งหมด

5. ให้แก้แล้วส่งใหม่ได้ทันที
     พร้อมรหัสคำสั่งใหม่ เพราะเป็นเจตนาใหม่ (4.14)
} on StockConflictException catch (error) {
  // ไม่ใช่ข้อผิดพลาด — เป็นข้อมูลใหม่
  _availableQuantity = error.currentQuantity;   // แก้ข้อ 3
  _message = 'ยอดคงเหลือเปลี่ยนเป็น ${error.currentQuantity} '
      'กรุณาตรวจสอบแล้วปรับใหม่';
  // ไม่แตะค่าที่ผู้ใช้กรอก — แก้ข้อ 4
  notifyListeners();
}

ห้ามทำเพราะ
ส่งซ้ำอัตโนมัติยอดยังไม่พออยู่ดี และอาจส่งซ้ำเป็นสิบครั้ง
ปรับจำนวนให้เองเป็นค่าที่พอดีตัดสินใจแทนผู้ใช้ในเรื่องที่กระทบสต๊อก
ใช้รหัสคำสั่งเดิมตอนส่งใหม่รู้แน่ว่าครั้งก่อนถูกปฏิเสธ จึงเป็นเจตนาใหม่ (4.14)
ล้างฟอร์มทั้งหมดผู้ใช้ต้องกรอกใหม่โดยไม่จำเป็น

บทเรียนที่ควรจำ: กฎที่ผลขึ้นกับเวลา ฝั่งแอปตรวจได้แค่ประมาณ — และการปฏิเสธจากเซิร์ฟเวอร์สำหรับกฎแบบนี้ไม่ใช่ความผิดพลาด แต่คือ ข้อมูลใหม่ที่ควรเอามาอัปเดตหน้าจอ

12. สรุปท้ายบท

  • มีสี่ด่าน และแต่ละด่านมีจุดประสงค์ต่างกัน
  • ด่านแปลง JSON แบ่งเป็นตรวจรูปแบบกับตรวจความหมาย
  • เส้นแบ่งคือต้องรู้เรื่องธุรกิจถึงจะตรวจได้หรือไม่
  • ข้ามแถวที่เสียเงียบ ๆ ทำให้งานหายโดยไม่มีใครรู้
  • การตรวจฝั่งแอปคือประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย
  • เซิร์ฟเวอร์ต้องตรวจทุกกฎ เพราะแอปไม่มีทางรู้สถานะล่าสุด
  • แยกชนิดความล้มเหลว เพื่อให้ผู้ใช้ทำสิ่งที่ถูก
  • รวมกฎธุรกิจไว้ที่ model ไม่ให้แต่ละหน้าจอตีความเอง
  • กฎที่ผลขึ้นกับเวลา การถูกปฏิเสธไม่ใช่ความผิดพลาด
