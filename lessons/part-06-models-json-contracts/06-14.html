ข้อความ JSON จากเซิร์ฟเวอร์

5. เกณฑ์ที่ต้องผ่าน

#เกณฑ์บท
1แยก DTO กับ domain model ชัดเจน6.1
2อ่านทุกค่าผ่านตัวช่วยกลาง ไม่มี as ตรง ๆ6.2, 6.8
3requestedQuantity ที่มีเศษ ผ่านได้เฉพาะหน่วยที่ยอมให้มีเศษ6.3
4remark ที่เป็นข้อความว่าง ให้ผลเหมือนไม่มีคีย์6.4
5บรรทัดที่พังต้องบอก path ถึงระดับ lines[1].requestedQuantity6.5
6เวลาที่ไม่มีเขตเวลาต้องถูกปฏิเสธ และ offset ต้องแปลงเป็น UTC6.6
7รับ PascalCase จาก endpoint เก่าได้6.7
8statusCode ที่ไม่รู้จักเป็น unknown และทำงานต่อไม่ได้6.9
9totalCount ที่ขัดแย้งกับจำนวนบรรทัด ต้องถูกปฏิเสธ6.10
10model แก้ไม่ได้ มี == คู่ hashCode และล้างค่า nullable ได้6.11
11กฎธุรกิจอยู่ที่ตัวแปลง ไม่อยู่ในตัวอ่าน JSON6.12
12มีไฟล์ตัวอย่างอย่างน้อยสองไฟล์ และเทสต์อย่างน้อย 15 ข้อ6.13
13มี DTO ขาขึ้นสำหรับคำสั่งยืนยันการหยิบ พร้อมรหัสคำสั่ง6.2, 4.14

เกณฑ์ข้อ 3 ยากที่สุด เพราะกฎขึ้นกับ field อื่นในก้อนเดียวกัน ซึ่งเป็นข้อสรุปของ 6.3 แบบฝึกหัดข้อ 3

6. คำใบ้สำหรับข้อที่ยาก

เกณฑ์ 3 — จำนวนที่มีเศษ

ตัวอ่าน JSON ไม่รู้เรื่องหน่วย จึงตรวจข้อนี้ไม่ได้ ต้องอ่านมาเป็น double ก่อน แล้วตรวจตอนแปลงเป็น domain

// DTO — อ่านมาเฉย ๆ
final double requestedQuantity;
final String unitOfMeasure;

// domain — ตรงนี้รู้จักหน่วยแล้ว จึงตรวจได้
if (unit.mustBeWhole && dto.requestedQuantity != dto.requestedQuantity.roundToDouble()) {
  throw ContractException('$path.requestedQuantity', '...');
}

เกณฑ์ 8 — สถานะที่ไม่รู้จัก

อย่าลืมว่าต้องมีทั้งสองอย่าง — ไม่พัง และทำงานต่อไม่ได้ (6.9 หัวข้อ 6)

เกณฑ์ 10 — ล้างค่า nullable

ใบเบิกมี remark ที่ล้างได้ และบรรทัดมี lotNumber ที่ล้างได้ — ต้องมีเมธอดแยกทั้งคู่ (6.11 หัวข้อ 5)

เกณฑ์ 13 — คำสั่งขาขึ้น

class ConfirmPickRequest {
  const ConfirmPickRequest({
    required this.requestNo,
    required this.lines,
    required this.commandId,
  });

  Map<String, Object?> toJson() => {
    'requestNo': requestNo,
    'commandId': commandId,
    'lines': [for (final line in lines) line.toJson()],
  };
}

สังเกตว่าไม่ส่ง statusCode ขึ้นไป — การยืนยันการหยิบคือการขอเปลี่ยนสถานะอยู่แล้ว การส่งสถานะไปด้วยจะเกิดคำถามว่าถ้าไม่ตรงกับที่เซิร์ฟเวอร์มีจะเชื่อฝั่งไหน (6.2 หัวข้อ 7)

7. ไฟล์ตัวอย่างที่ควรมี

ไฟล์ครอบอะไร

8. เทสต์ที่ต้องเขียน

อย่างน้อย 15 ข้อ ตัวอย่างสามข้อที่คิดยากที่สุด

test('หน่วยชิ้นมีเศษไม่ได้ แต่หน่วยกิโลกรัมมีได้', () {
  final pcs = PickLineDto.fromJson(
    lineJson({'requestedQuantity': 24.5, 'unitOfMeasure': 'PCS'}),
  );
  expect(
    () => toPickLine(pcs, path: 'lines[0]'),
    throwsA(isA<ContractException>()
        .having((e) => e.path, 'path', 'lines[0].requestedQuantity')),
  );

  final kg = PickLineDto.fromJson(
    lineJson({'requestedQuantity': 24.5, 'unitOfMeasure': 'KG'}),
  );
  expect(toPickLine(kg, path: 'lines[0]').requestedQuantity, 24.5);
});
test('หน่วยที่ไม่รู้จัก ต้องไม่เดาว่ามีเศษได้หรือไม่', () {
  final line = PickLineDto.fromJson(
    lineJson({'requestedQuantity': 24.5, 'unitOfMeasure': 'ตัน'}),
  );

  // เลือกทางที่ปลอดภัย — ไม่รู้จักหน่วย แปลว่าตัดสินไม่ได้
  expect(() => toPickLine(line, path: 'lines[0]'),
      throwsA(isA<ContractException>()));
});
test('ใบที่อนุมัติแล้วต้องมีเวลาอนุมัติ', () {
  final json = fixture('pick_request.json')..['approvedAt'] = null;

  // statusCode 30 แปลว่าอนุมัติแล้ว แต่ไม่มีเวลาอนุมัติ — ขัดแย้งกันเอง
  expect(() => PickRequestDto.fromJson(json).toDomain(),
      throwsA(isA<ContractException>()));
});

ข้อสุดท้ายเป็นกฎที่ไม่มีในโจทย์ตรง ๆ แต่ได้มาจากการอ่านความหมายของ statusCode — ซึ่งเป็นสิ่งที่ต้องยืนยันกับทีมหลังบ้านก่อนใส่ลงไป

9. เทียบกับของจริงในโปรเจกต์

เปิด lib/features/tasks/wms_task.dart ซึ่งเป็น model ที่ใช้จริงและจะเรียนเต็ม ๆ ใน Part 30

@freezed
abstract class WmsTask with _$WmsTask {
  const factory WmsTask({
    required String id,
    required String from,
    required String to,
    required TaskStatus status,
  }) = _WmsTask;

  factory WmsTask.fromJson(Map<String, dynamic> json) =>
      _$WmsTaskFromJson(_normalizeTaskJson(json));
}
เรื่องTask (บทเรียน)WmsTask (ของจริง)
fromJsonเขียนเองให้เครื่องมือสร้าง
copyWith, ==, hashCodeเขียนเองให้เครื่องมือสร้าง
การตรวจสอบอยู่ในตัวอ่านกลางอยู่ใน _normalizeTaskJson
สถานะที่ไม่รู้จักunknownโยนข้อผิดพลาด

แถวสุดท้ายต่างกันจริง และเป็นความต่างที่ควรตั้งคำถาม

final rawStatus = requiredText('status').toLowerCase();
if (!TaskStatus.values.any((value) => value.name == rawStatus)) {
  throw FormatException('ไม่รู้จัก task.status: $rawStatus');
}
ทางเลือกเหมาะเมื่อ
โยนข้อผิดพลาดชุดสถานะปิด ไม่มีการเพิ่มบ่อย และอยากรู้ทันทีถ้าสัญญาเปลี่ยน
ใช้ unknownชุดสถานะเปิด และแอปบน PDA อัปเดตช้ากว่าเซิร์ฟเวอร์

สำหรับงานบน PDA ที่อัปเดตแอปยาก ทางที่สองปลอดภัยกว่า — แต่ทางแรกก็มีเหตุผลถ้าชุดสถานะนิ่งแล้วจริง ๆ

อย่าสรุปว่าของจริงต้องดีกว่าเสมอ ให้ดูว่ามันแลกอะไร แล้วถามว่าเหตุผลนั้นยังใช้ได้กับงานตรงหน้าไหม — เป็นวิธีอ่านโค้ดแบบเดียวกับที่ใช้ใน 4.16

10. ข้อผิดพลาดที่พบบ่อยตอนทำ lab นี้

อาการสาเหตุวิธีแก้
อ่านไฟล์ตัวอย่างไม่เจอเส้นทางผิดใช้ File('test/fixtures/...') — เทสต์รันจากรากของโปรเจกต์
แก้ไฟล์ตัวอย่างในเทสต์แล้วเทสต์อื่นพังjsonDecode คืน map ที่แก้ได้ และแชร์กันอ่านไฟล์ใหม่ทุกครั้งในแต่ละเทสต์
path ไม่ตรงกับที่คาดลืมส่ง path ต่อลงไปส่งทุกชั้น (6.5)
ตรวจหน่วยในตัวอ่าน JSON แล้วโค้ดพันกันวางกฎผิดชั้นย้ายไปตัวแปลง (6.12)
const constructor ใช้ไม่ได้มี List.unmodifiable ใน initializerยอมไม่ใช้ const (6.11)
เทสต์เทียบ DateTime แล้วไม่เท่ากันตัวหนึ่งเป็น UTC อีกตัวเป็นเวลาท้องถิ่นเทียบกับ DateTime.utc(...)

11. แบบทดสอบตัวเองก่อนจบ Part 6

  1. DTO กับ domain model ต่างกันอย่างไร และทำไมห้ามส่ง DTO เข้าหน้าจอ (6.1)
  2. ทำไมไม่ควรใช้ as อ่านค่าจาก JSON (6.2, 6.8)
  3. “ไม่มีคีย์” กับ “มีคีย์แต่เป็น null” ต่างกันอย่างไร และทำไมต้องแยก (6.2)
  4. JSON ส่ง 12, 12.0, "12" มา ควรรับอันไหนบ้าง เพราะอะไร (6.3)
  5. ทำไมปฏิเสธ 1.9 แต่รับ 12.0 (6.3)
  6. เมื่อไหร่ค่าตั้งต้นใช้ได้ และเมื่อไหร่มันคือการเดา (6.4)
  7. ทำไมข้อความผิดพลาดต้องมี path (6.5)
  8. เวลาที่ไม่มีเขตเวลาแปลว่าอะไร และควรทำอย่างไร (6.6)
  9. ทำไมใช้ containsKey ไม่ใช่ ?? ตอนรองรับสองชื่อคีย์ (6.7)
  10. as กับ is ต่างกันอย่างไร (6.8)
  11. ทำไม enum สถานะต้องมี unknown (6.9)
  12. ทำไม canWorkOn ต้องเขียนเป็นรายชื่อที่อนุญาต (6.9)
  13. items.length กับ totalCount ตอบคำถามคนละข้ออย่างไร (6.10)
  14. ทำไม copyWith(note: null) ไม่มีผล (6.11)
  15. การตรวจฝั่งแอปเป็นความปลอดภัยหรือไม่ (6.12)
  16. จะรู้ได้อย่างไรว่าเทสต์ครอบพอแล้ว (6.13)

12. สรุปท้าย Part 6

สิ่งที่ทำได้แล้ว

  • แยกภาษาของสายออกจากภาษาของธุรกิจ
  • อ่านค่าจาก JSON ผ่านตัวช่วยกลางที่บอกได้ว่าพังตรงไหน
  • รับตัวเลขที่เขียนคนละแบบ แต่ไม่ยอมให้ความหมายเปลี่ยน
  • แยก “ไม่มีค่า” “ไม่รู้ค่า” และ “ค่าเป็นศูนย์” ออกจากกัน
  • อ่าน JSON ที่ซ้อนกันพร้อมบอกตำแหน่งถึงระดับบรรทัด
  • จัดการเวลาให้ทุกเครื่องเห็นตรงกัน
  • รองรับชื่อคีย์สองแบบโดยเก็บความยุ่งไว้ที่เดียว
  • กัก dynamic ไว้ที่ขอบ
  • แปลงสถานะเป็น enum ที่รับมือกับค่าที่ไม่รู้จักได้
  • อ่านซองที่ห่อรายการและแบ่งหน้าโดยไม่ซ้ำไม่ขาด
  • เขียน model ที่แก้ไม่ได้และเทียบค่าได้
  • วางการตรวจสอบให้ถูกชั้น
  • ตรึงสัญญาด้วยเทสต์ที่รันได้ในไม่ถึงวินาที
