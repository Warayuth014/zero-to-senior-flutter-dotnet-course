1. ปัญหาที่บทนี้แก้

ตลอดห้า Part ที่ผ่านมา ข้อมูลทั้งหมดเป็นของปลอมที่เขียนไว้ในโค้ด

const NavTask(id: 'T-001', palletCode: 'PAL-0101', quantity: 12),

ของจริงที่มาจากเซิร์ฟเวอร์หน้าตาแบบนี้

{
  "id": "T-001",
  "palletCode": "PAL-0101",
  "quantity": 12,
  "status": "PENDING",
  "createdAt": "2026-08-15T03:00:00Z",
  "note": null
}

ทางที่ง่ายที่สุดคือทำคลาสเดียวให้ตรงกับ JSON แล้วใช้ทั้งแอป ซึ่งได้ผลจนกระทั่งเจอสิ่งเหล่านี้

สิ่งที่เกิดขึ้นจริงผลถ้ามี model ชั้นเดียว
status เป็นข้อความเขียน if (task.status == 'PENDING') กระจายทั่วหน้าจอ
เซิร์ฟเวอร์เก่าส่ง "Id" ตัวใหญ่ต้องเขียน json['id'] ?? json['Id'] ในทุก model
เซิร์ฟเวอร์เปลี่ยนชื่อ fieldต้องแก้ทุกที่ที่ใช้ ตั้งแต่ปุ่มยันข้อความบนจอ
บางครั้ง quantity เป็น nullต้องเขียน ?? 0 เต็มไปหมด แล้วยอดคลาดเคลื่อน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
JSONรูปแบบข้อความที่ใช้ส่งข้อมูลระหว่างแอปกับเซิร์ฟเวอร์
wire / บนสายรูปแบบของข้อมูลตอนเดินทาง
DTOคลาสที่สะท้อนหน้าตาของข้อมูลบนสายตรง ๆ
domain modelคลาสที่สะท้อนสิ่งที่ธุรกิจสนใจ
mapperตัวแปลงจากชั้นหนึ่งไปอีกชั้น
contract / สัญญาข้อตกลงว่าข้อมูลจะมีหน้าตาแบบไหน

3. Mental model: สองภาษาที่ต้องแปล

ภาษาของสาย                       ภาษาของธุรกิจ
─────────────                    ──────────────
status: "PENDING"      ──แปล──→  status: TaskStatus.pending
quantity: "12"                   quantity: 12
createdAt: "...+07:00"           createdAt: DateTime (UTC)
note: ""                         note: null
ประโยคเดียวที่ต้องจำ: เซิร์ฟเวอร์พูดภาษาของมัน แอปพูดภาษาของเรา — งานของชั้นแปลคือทำให้ทั้งสองฝั่งไม่ต้องรู้จักกัน

ประโยชน์ที่ได้ทันทีคือ เมื่อเซิร์ฟเวอร์เปลี่ยน มีแค่ที่เดียวที่ต้องแก้

4. สองชั้นที่ต้องมี

เปิด lib/json_basics/task_dto.dart

class TaskDto {

เปิด lib/json_basics/task_domain.dart

/// งานหนึ่งชิ้นในภาษาของธุรกิจ ไม่ใช่ภาษาของสาย
class Task {
  final String id;
  final String palletCode;
  final int quantity;
  final TaskStatus status;     // เป็น enum แล้ว
  final DateTime createdAt;
  final String? note;
}

ดูเผิน ๆ เหมือนซ้ำซ้อน แต่ต่างกันสามอย่างที่สำคัญ

TaskDtoTask
statusString — เพราะเซิร์ฟเวอร์อาจส่งค่าที่เราไม่รู้จักTaskStatus — เพราะแอปต้องตัดสินใจจากมัน
ค่าถูกตรวจแล้วหรือยังตรวจแค่รูปแบบตรวจกฎธุรกิจแล้ว เช่นจำนวนต้องมากกว่าศูนย์
ใครใช้ชั้นที่คุยกับเซิร์ฟเวอร์เท่านั้นทุกที่ในแอป
ห้ามส่ง TaskDto เข้าไปในหน้าจอเด็ดขาด — ทันทีที่ทำ หน้าจอจะต้องรู้เรื่องชื่อ field ของเซิร์ฟเวอร์ และการเปลี่ยนฝั่งเซิร์ฟเวอร์จะลามไปทั้งแอป

5. ตัวแปลงคือด่านสุดท้าย

Task toTask(TaskDto dto, {String path = ''}) {
  if (dto.quantity <= 0) {
    throw ContractException(
      path.isEmpty ? 'quantity' : '$path.quantity',
      'จำนวนต้องมากกว่าศูนย์ แต่ได้ ${dto.quantity}',
    );
  }

  return Task(
    id: dto.id,
    palletCode: dto.palletCode,
    quantity: dto.quantity,
    status: parseTaskStatus(dto.status),    // ข้อความ → enum
    createdAt: dto.createdAt,
    note: dto.note,
  );
}

สองอย่างที่เกิดตรงนี้

สิ่งที่ทำทำไมต้องทำที่นี่
ตรวจกฎธุรกิจผ่านด่านนี้แล้ว ที่อื่นไม่ต้องตรวจซ้ำอีก
แปลงข้อความเป็น enumทำที่เดียว ไม่ใช่ที่ทุกหน้าจอ

ผลที่ได้คือ ถ้ามี Task อยู่ในมือ แปลว่ามันถูกต้องแน่นอน ซึ่งเป็นหลักเดียวกับ 4.7 — ทำให้ค่าที่เป็นไปไม่ได้สร้างไม่ได้ตั้งแต่แรก

6. ทำไมจำนวนติดลบต้องปฏิเสธ ไม่ใช่ปรับเป็นศูนย์

// ทางที่ดูใจดี แต่อันตราย
quantity: dto.quantity < 0 ? 0 : dto.quantity,

ถ้าเซิร์ฟเวอร์ส่งจำนวน -5 มา แปลว่ามีบางอย่างผิดอยู่แล้ว — อาจเป็นบั๊กฝั่งหลังบ้าน หรือข้อมูลในฐานข้อมูลเสีย

ถ้าปรับเป็นศูนย์เงียบ ๆถ้าปฏิเสธ
คนหน้างานหยิบของ 0 ชิ้นแล้วปิดงานเห็นข้อผิดพลาดทันที และแจ้งได้
ยอดในระบบเพี้ยนโดยไม่มีใครรู้ปัญหาถูกพบตั้งแต่วันแรก
ไล่หาสาเหตุไม่ได้ เพราะไม่มีร่องรอยรู้ว่าพังที่ไหนและเพราะอะไร

เป็นหลักเดียวกับ 4.8 หัวข้อ 6 — อย่ากลืนสิ่งที่แปลว่ามีบั๊ก ให้มันดังตั้งแต่ตอนที่ยังหาสาเหตุได้

7. ชั้นที่สาม: model ของหน้าจอ

บางครั้งหน้าจอต้องการสิ่งที่ธุรกิจไม่มีคำเรียก

class TaskTileViewModel {
  const TaskTileViewModel({
    required this.title,
    required this.subtitle,
    required this.badgeColor,
    required this.canTap,
  });
  ...
}
สิ่งที่หน้าจอต้องการธุรกิจมีคำนี้ไหม
สีของป้ายสถานะไม่มี
ข้อความ “12 ชิ้น · เมื่อ 3 นาทีที่แล้ว”ไม่มี
แตะได้หรือไม่ใกล้เคียง แต่ไม่ตรง

แต่ ส่วนใหญ่ยังไม่ต้องมีชั้นนี้ — สร้างเมื่อพบว่าหน้าจอต้องคำนวณเรื่องเดิมซ้ำหลายที่จริง ๆ ไม่ใช่สร้างไว้ก่อน

ใน lab จึงมีแค่สองชั้น เพราะหน้าจอคำนวณสิ่งที่ต้องใช้จาก Task ได้โดยตรง

8. เมื่อไหร่ที่สองชั้นก็ยังเยอะเกิน

สถานการณ์ควรมีกี่ชั้น
ข้อมูลตั้งค่าง่าย ๆ ที่แอปแค่แสดงชั้นเดียวก็พอ
ข้อมูลที่มีสถานะ กฎ หรือการคำนวณสองชั้น
ข้อมูลที่หน้าจอต้องจัดรูปแบบเยอะสามชั้น

เกณฑ์ที่ใช้ตัดสิน — ถามว่า หน้าตาของ JSON กับสิ่งที่ธุรกิจสนใจ ต่างกันไหม

ถ้าตอบว่าแปลว่า
เหมือนกันเป๊ะ และไม่มีกฎอะไรชั้นเดียวพอ แต่บันทึกไว้ว่าทำไม
ต่างกันแม้แต่เรื่องเดียวแยกสองชั้น

และเมื่อเลือกชั้นเดียว ให้รู้ตัวว่ากำลังแลกอะไร — วันที่เซิร์ฟเวอร์เปลี่ยน จะไม่มีที่กันการเปลี่ยนแปลงนั้นไม่ให้ลามเข้ามา

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เซิร์ฟเวอร์เปลี่ยนชื่อ field แล้วต้องแก้สิบไฟล์ใช้ DTO ทั้งแอปแยก domain model
if (status == 'PENDING') กระจายทั่วหน้าจอไม่ได้แปลงเป็น enumแปลงที่ mapper
ยอดเพี้ยนโดยไม่มีใครรู้ใส่ ?? 0 ให้ค่าที่ผิดปฏิเสธค่าที่ผิด
คลาสเดียวมีทั้ง fromJson สีของป้าย และกฎธุรกิจยัดทุกอย่างไว้ที่เดียวแยกตามหน้าที่
สร้างสามชั้นตั้งแต่วันแรกแล้วเขียนโค้ดซ้ำแยกชั้นเกินจำเป็นเริ่มสองชั้น เพิ่มเมื่อเจอปัญหาจริง

10. แบบฝึกหัด

เซิร์ฟเวอร์ส่งข้อมูลใบรับเข้ามาแบบนี้

{
  "orderNo": "IN-2026-0812",
  "supplierName": "บริษัท ซัพพลาย จำกัด",
  "statusCode": 20,
  "expectedAt": "2026-08-16T01:00:00Z",
  "receivedQty": null,
  "expectedQty": 130
}

โดยที่ statusCode มีความหมายตามนี้ — 10 คือรอรับ, 20 คือกำลังรับ, 30 คือรับครบแล้ว

  1. ออกแบบ DTO และ domain model
  2. เขียนตัวแปลง พร้อมตัดสินว่า receivedQty ที่เป็น null ควรกลายเป็นอะไร
  3. ตอบว่าถ้าเซิร์ฟเวอร์ส่ง statusCode: 40 ที่ไม่มีในเอกสาร ควรทำอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — สองชั้น

// ชั้นสาย — รับมาตามที่ส่งมา ไม่ตัดสินอะไร
class InboundOrderDto {
  const InboundOrderDto({
    required this.orderNo,
    required this.supplierName,
    required this.statusCode,      // ยังเป็นตัวเลข
    required this.expectedQty,
    this.expectedAt,
    this.receivedQty,              // ยังเป็น null ได้
  });

  final String orderNo;
  final String supplierName;
  final int statusCode;
  final int expectedQty;
  final DateTime? expectedAt;
  final int? receivedQty;
}
// ชั้นธุรกิจ — ตรวจแล้ว แปลงแล้ว ใช้ได้เลย
enum InboundStatus { waiting, receiving, completed, unknown }

class InboundOrder {
  const InboundOrder({
    required this.orderNo,
    required this.supplierName,
    required this.status,
    required this.expectedQuantity,
    required this.receivedQuantity,   // ไม่เป็น null แล้ว
    this.expectedAt,
  });

  final String orderNo;
  final String supplierName;
  final InboundStatus status;
  final int expectedQuantity;
  final int receivedQuantity;
  final DateTime? expectedAt;

  // คำนวณเอา ไม่เก็บ (4.2)
  int get remainingQuantity => expectedQuantity - receivedQuantity;
  bool get isFullyReceived => receivedQuantity >= expectedQuantity;
}

ข้อ 2 — ตัวแปลง และ receivedQty ที่เป็น null

InboundStatus parseInboundStatus(int code) => switch (code) {
  10 => InboundStatus.waiting,
  20 => InboundStatus.receiving,
  30 => InboundStatus.completed,
  _ => InboundStatus.unknown,
};

InboundOrder toInboundOrder(InboundOrderDto dto) {
  if (dto.expectedQty <= 0) {
    throw const ContractException('expectedQty', 'จำนวนที่คาดต้องมากกว่าศูนย์');
  }

  final received = dto.receivedQty ?? 0;
  if (received < 0) {
    throw const ContractException('receivedQty', 'จำนวนที่รับต้องไม่ติดลบ');
  }

  return InboundOrder(
    orderNo: dto.orderNo,
    supplierName: dto.supplierName,
    status: parseInboundStatus(dto.statusCode),
    expectedQuantity: dto.expectedQty,
    receivedQuantity: received,
    expectedAt: dto.expectedAt,
  );
}

ทำไม receivedQty ที่เป็น null กลายเป็น 0 ได้ ทั้งที่หัวข้อ 6 บอกว่าห้าม

นี่คือจุดที่ต้องแยกให้ออก และเป็นสาระของข้อนี้

receivedQty: nullquantity: -5
แปลว่าอะไรยังไม่เริ่มรับ — เป็นสถานะปกติค่าที่เป็นไปไม่ได้ — ต้องมีอะไรผิด
เดาได้ไหมว่าควรเป็นเท่าไหร่ได้ — ยังไม่รับ ก็คือรับไป 0ไม่ได้ — ไม่รู้ว่าที่ถูกคือเท่าไหร่
ควรทำอย่างไรใส่ค่าตั้งต้นได้ปฏิเสธ

เกณฑ์คือ ถ้า null มีความหมายที่ตกลงกันไว้แล้ว ให้แปลงตามความหมายนั้น แต่ถ้ามันแปลว่า "ไม่รู้" ห้ามเดา

และต้องยืนยันกับฝั่งหลังบ้านก่อนว่า null ตรงนี้แปลว่า “ยังไม่รับ” จริง ไม่ใช่ “ลืมใส่มา” — ถ้าตอบไม่ได้ ก็ยังเดาไม่ได้

ข้อ 3 — statusCode: 40 ที่ไม่มีในเอกสาร

ต้องไม่พัง แต่ต้องไม่แกล้งทำเป็นรู้จัก

_ => InboundStatus.unknown,

เหตุผลที่ไม่ควรโยนข้อผิดพลาด

ถ้าโยนผลที่เกิด
ทั้งรายการโหลดไม่ได้ใบอื่นอีก 40 ใบที่ปกติดี ก็ใช้ไม่ได้ไปด้วย
คนหน้างานทำงานไม่ได้เลยทั้งที่ปัญหาคือใบเดียว

เหตุผลที่ไม่ควรเดาว่าเป็นอย่างอื่น

_ => InboundStatus.waiting,     // อันตราย

ถ้า 40 หมายถึง “ยกเลิกแล้ว” แต่แอปแสดงว่า “รอรับ” คนหน้างานจะไปรับของที่ถูกยกเลิกไปแล้ว

สิ่งที่ต้องทำคู่กับ unknown

ต้องทำเพราะ
แสดงว่า “สถานะไม่รู้จัก” ตรง ๆผู้ใช้จะได้ไม่เข้าใจผิด
ห้ามให้กดทำงานต่อไม่รู้ว่าทำได้หรือไม่
บันทึก log ว่าเจอค่าอะไรทีมจะได้รู้ว่าต้องอัปเดตแอป
บอกให้ผู้ใช้อัปเดตแอปเป็นทางแก้จริงของปัญหานี้

ใน lab เห็นแนวคิดนี้ได้ที่ TaskStatus.unknown ซึ่งมี canWorkOn เป็น false — รู้จักว่ามีอยู่ แต่ไม่ให้ทำอะไรกับมัน

11. สรุปท้ายบท

  • เซิร์ฟเวอร์พูดภาษาของมัน แอปพูดภาษาของเรา ต้องมีชั้นแปล
  • DTO สะท้อนหน้าตาบนสาย ไม่ตัดสินอะไร
  • domain model สะท้อนสิ่งที่ธุรกิจสนใจ และถูกตรวจแล้ว
  • ห้ามส่ง DTO เข้าหน้าจอ ไม่งั้นการเปลี่ยนฝั่งเซิร์ฟเวอร์จะลามทั้งแอป
  • ตัวแปลงคือด่านสุดท้าย — ผ่านแล้วที่อื่นไม่ต้องตรวจซ้ำ
  • ค่าที่แปลว่ามีบั๊ก ต้องปฏิเสธ ไม่ใช่ปรับให้ดูดี
  • null ที่มีความหมายตกลงไว้แล้ว แปลงได้ แต่ null ที่แปลว่าไม่รู้ ห้ามเดา
  • ชั้นที่สามสำหรับหน้าจอ สร้างเมื่อเจอปัญหาจริง ไม่ใช่สร้างไว้ก่อน
