1. ปัญหาที่บทนี้แก้

โค้ดที่เขียนเพื่อให้ compiler เลิกบ่น

id: json['id'] as String? ?? '',
quantity: json['quantity'] as int? ?? 0,
palletCode: json['palletCode'] as String? ?? '',

คอมไพล์ผ่าน ไม่พังตอนรัน และ เป็นโค้ดที่อันตรายที่สุดในบทนี้

เซิร์ฟเวอร์ส่งข้อมูลไม่ครบ
  → แอปสร้างงานที่ id เป็นข้อความว่าง จำนวน 0 พาเลทว่าง
  → หน้าจอแสดงงานนั้นตามปกติ
  → คนหน้างานกดปิดงานที่ไม่มีตัวตน
  → เซิร์ฟเวอร์ปฏิเสธ แต่ไม่มีใครเข้าใจว่าทำไม

ปัญหาไม่ใช่ว่ามันพัง — ปัญหาคือ มันไม่พัง แล้วเดินหน้าต่อด้วยข้อมูลที่ไม่มีอยู่จริง

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
nullableชนิดที่เป็น null ได้ เขียนด้วย ?
requiredต้องมีค่าเสมอ
defaultค่าที่ใช้แทนเมื่อไม่มีค่าส่งมา
sentinelค่าพิเศษที่ใช้แทนความหมายอื่น
invariantกฎที่ต้องเป็นจริงเสมอ

3. Mental model: สามอย่างที่หน้าตาเหมือนกัน

{"receivedQty": 0}        → รับไปแล้ว 0 ชิ้น  (รู้ค่า และค่าคือศูนย์)
{"receivedQty": null}     → ยังไม่ได้เริ่มรับ  (ไม่มีค่า แต่รู้ว่าทำไม)
{}                        → เซิร์ฟเวอร์ไม่ได้บอก (ไม่รู้เลย)
ประโยคเดียวที่ต้องจำ: ก่อนใส่ ? หรือ ?? 0 ให้ตอบก่อนว่าค่านั้น ไม่มี เพราะอะไร — ถ้าตอบไม่ได้ แปลว่ายังไม่ควรใส่

4. เกณฑ์ตัดสินว่า field ไหนควรเป็น nullable

คำถามถ้าตอบว่าใช่
มีสถานะปกติของธุรกิจที่ค่านี้ไม่มีจริง ๆ ไหมเป็น nullable ได้
ใส่ ? เพราะ compiler บ่นหรือเปล่าไม่ควรเป็น nullable

ดูของจริงใน lib/json_basics/task_dto.dart

final String id;              // ไม่มีทางไม่มี — งานที่ไม่มีรหัสไม่ใช่งาน
final String palletCode;      // ไม่มีทางไม่มี
final int quantity;           // ไม่มีทางไม่มี
final DateTime createdAt;     // ไม่มีทางไม่มี
final String? note;           // มีสถานะปกติที่ไม่มีหมายเหตุ

มีแค่ note ตัวเดียวที่เป็น nullable และมีเหตุผลชัดเจน — งานส่วนใหญ่ไม่มีหมายเหตุ ซึ่งเป็นเรื่องปกติ ไม่ใช่ข้อมูลขาด

เทียบกับ lib/json_basics/inbound_dto.dart

final DateTime? expectedAt;   // เวลาที่คาดว่าของจะมาถึง อาจยังไม่รู้

อันนี้ก็มีเหตุผล — ใบรับเข้าที่ยังไม่ได้นัดวันส่งของ ก็ยังไม่มีเวลาที่คาดไว้

5. สิ่งที่จำเป็นแต่ไม่มี คือความล้มเหลว

Object? _require(Map<String, dynamic> json, String key, String path) {
  final value = _raw(json, key);
  if (identical(value, _absent)) {
    throw ContractException(_at(path, key), 'ไม่มีคีย์นี้ในข้อมูลที่ได้รับ');
  }
  if (value == null) {
    throw ContractException(_at(path, key), 'ค่าต้องไม่เป็น null');
  }
  return value;
}

เหตุผลที่ต้องโยนแทนที่จะใส่ค่าตั้งต้น

สิ่งที่เกิดถ้าใส่ค่าตั้งต้นถ้าโยน
เซิร์ฟเวอร์เปลี่ยนชื่อ fieldทุกงานมี id ว่าง แต่หน้าจอยังแสดงปกติเห็นทันทีว่าคีย์ไหนหาย
ข้อมูลในฐานข้อมูลไม่ครบคนหน้างานทำงานกับข้อมูลที่ไม่มีจริงรู้ว่าใบไหนมีปัญหา
เราสะกดชื่อคีย์ผิดทุกอย่างว่างเปล่าโดยไม่รู้สาเหตุข้อความบอกชื่อคีย์ที่หาไม่เจอ

สังเกตว่าทั้งสามกรณีในคอลัมน์กลาง ไม่มีอะไรพัง — ซึ่งทำให้ปัญหาอยู่ในระบบได้นานเป็นเดือน

6. ค่าตั้งต้นที่ใช้ได้ กับที่ใช้ไม่ได้

ไม่ใช่ว่าค่าตั้งต้นผิดเสมอ — มันผิดเมื่อเป็นการเดา

สถานการณ์ค่าตั้งต้นใช้ได้ไหม
details ไม่มี และตกลงกันว่าแปลว่าไม่มีบรรทัด[]ได้
receivedQty เป็น null และตกลงกันว่าแปลว่ายังไม่เริ่มรับ0ได้
quantity ไม่มี และไม่รู้ว่าทำไม0ไม่ได้
id ไม่มี''ไม่ได้

ความต่างอยู่ที่ประโยคเดียว — ตกลงกันไว้แล้วหรือกำลังเดา

// ตกลงกันแล้ว — บันทึกเหตุผลไว้ในโค้ด
/// เซิร์ฟเวอร์ไม่ส่ง receivedQty มาเมื่อยังไม่เริ่มรับของ
/// ซึ่งตกลงกันแล้วว่าหมายถึง 0 (ยืนยันกับทีมหลังบ้าน 2026-08-10)
final received = dto.receivedQty ?? 0;

ถ้าเขียนเหตุผลไม่ได้ แปลว่ายังไม่ได้ตกลง และยังใส่ค่าตั้งต้นไม่ได้

7. ข้อความว่างกับ null

ฝั่ง .NET มักส่งข้อความว่างแทน null เพราะเป็นค่าตั้งต้นของบางการตั้งค่า

{"note": ""}      ← ไม่มีหมายเหตุ
{"note": null}    ← ไม่มีหมายเหตุเหมือนกัน
{}                ← ไม่มีหมายเหตุเหมือนกันอีก

ใน lab จึงยุบทั้งสามเป็นอันเดียว

/// อ่านข้อความที่เซิร์ฟเวอร์อนุญาตให้ไม่มีได้
///
/// ทั้งไม่มีคีย์ ค่าเป็น null และข้อความว่าง ถือเป็น null เหมือนกัน
/// เพราะทั้งสามหมายถึง "ไม่มีข้อมูล" ในความหมายของหน้าจอ
String? readString(Map<String, dynamic> json, String key, {String path = ''}) {
  final value = _raw(json, key);
  if (identical(value, _absent) || value == null) return null;
  ...
  final trimmed = value.trim();
  return trimmed.isEmpty ? null : trimmed;
}

เทสต์ตรึงไว้ว่าทั้งสามให้ผลเหมือนกัน

test('หมายเหตุที่ไม่มี ค่า null และข้อความว่าง ให้ผลเหมือนกัน', () {
  expect(TaskDto.fromJson(taskJson()).note, isNull);
  expect(TaskDto.fromJson(taskJson({'note': null})).note, isNull);
  expect(TaskDto.fromJson(taskJson({'note': '  '})).note, isNull);
});
แต่การยุบนี้ต้องเป็นการตัดสินใจ ไม่ใช่ค่าตั้งต้นของทุก field — ถ้ามีระบบไหนที่ข้อความว่างแปลว่า “ตั้งใจล้างค่า” ต่างจาก null ที่แปลว่า “ไม่แตะ” การยุบจะทำให้ความหมายหายไป

8. ข้อความว่างไม่ผ่านสำหรับ field ที่จำเป็น

final trimmed = value.trim();
if (trimmed.isEmpty) {
  throw ContractException(_at(path, key), 'ต้องไม่เป็นข้อความว่าง');
}
return trimmed;

เพราะรหัสพาเลทที่เป็นข้อความว่าง ก็เท่ากับไม่มีรหัสพาเลท — การปล่อยผ่านแค่เพราะ “คีย์มีอยู่จริง” คือการยอมรับข้อมูลที่ใช้ไม่ได้

และการ trim() ก่อนก็สำคัญ เพราะ " " ที่มีแต่ช่องว่างไม่ต่างจากว่างเปล่า

9. อย่าให้หน้าจอเขียนค่าตกแต่งกลับเข้าข้อมูล

// หน้าจอแสดงแบบนี้ได้
Text(task.note ?? '—')
// แต่ห้ามเขียนกลับ
task.copyWith(note: task.note ?? '—')     // ตอนนี้หมายเหตุคือ "—" จริง ๆ แล้ว

ขีดกลางเป็นสิ่งที่ผู้ใช้ควรเห็นเมื่อไม่มีข้อมูล ไม่ใช่ค่าของข้อมูล ถ้ามันเข้าไปอยู่ในข้อมูลจริง วันหนึ่งจะถูกส่งกลับขึ้นเซิร์ฟเวอร์

ชั้นรู้จัก null ไหม
ข้อมูลรู้ — null แปลว่าไม่มี
หน้าจอแปลง null เป็นสิ่งที่อ่านได้ ตอนแสดงเท่านั้น

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แอปแสดงงานที่ไม่มีอยู่จริงใส่ ?? '' ให้ field ที่จำเป็นปฏิเสธเมื่อไม่มี
ยอดรวมเพี้ยนโดยไม่มีใครรู้ใส่ ?? 0 ให้จำนวนที่หายไปแยก “ไม่มี” จาก “เป็นศูนย์”
เซิร์ฟเวอร์เปลี่ยนชื่อ field แล้วไม่มีใครรู้เป็นเดือนค่าตั้งต้นกลบทุกอย่างให้ field ที่จำเป็นดังเมื่อหาย
? เต็มไปหมดจนต้องเช็ก null ทุกบรรทัดใส่ ? เพราะ compiler บ่นถามก่อนว่ามีสถานะปกติที่ไม่มีค่าไหม
หมายเหตุกลายเป็น "—" ในฐานข้อมูลเขียนค่าตกแต่งกลับเข้าข้อมูลแปลงตอนแสดงเท่านั้น
รหัสพาเลทเป็นข้อความว่างแล้วผ่านตรวจแค่ว่ามีคีย์ตรวจว่าไม่ว่างด้วย

11. แบบฝึกหัด

ทีมหลังบ้านส่งสัญญาของใบเบิกมาให้

{
  "requestNo": "RQ-2026-0451",
  "requesterName": "สมชาย ใจดี",
  "approverName": null,
  "approvedAt": null,
  "remark": "",
  "totalItems": 5,
  "pickedItems": null,
  "cancelReason": null
}

โดยที่ใบนี้อยู่ในสถานะ “รออนุมัติ”

  1. ตัดสินว่า field ไหนควรเป็น nullable ใน DTO และเพราะอะไร
  2. ออกแบบ domain model ที่ทำให้สถานะที่เป็นไปไม่ได้ สร้างไม่ได้
  3. ตอบว่า pickedItems: null ควรกลายเป็น 0 หรือไม่
ดูแนวคำตอบและเหตุผล

ข้อ 1 — nullable ใน DTO

fieldnullableเหตุผล
requestNoไม่ใบที่ไม่มีเลขที่ไม่ใช่ใบ
requesterNameไม่ต้องมีคนขอเสมอ
approverNameใช่ยังไม่อนุมัติ ก็ยังไม่มีคนอนุมัติ
approvedAtใช่เหตุผลเดียวกัน
remarkใช่ (ผ่าน readString)ไม่มีหมายเหตุเป็นเรื่องปกติ
totalItemsไม่ใบเบิกต้องมีจำนวนรายการเสมอ
pickedItemsใช่ยังไม่เริ่มหยิบ
cancelReasonใช่ยังไม่ยกเลิก

สังเกตว่า nullable ทุกตัวมีเหตุผลร่วมกันข้อเดียว — มันขึ้นกับว่าใบอยู่สถานะไหน

ข้อ 2 — domain model ที่กันสถานะที่เป็นไปไม่ได้

ถ้าลอกโครง DTO มาตรง ๆ จะได้แบบนี้

// ยังไม่ดี — สร้างสิ่งที่เป็นไปไม่ได้ได้
class PickRequest {
  final String? approverName;
  final DateTime? approvedAt;
  final int? pickedItems;
  final String? cancelReason;
}

ปัญหาคือมันอนุญาตให้สร้างสถานะแบบนี้

สถานะที่สร้างได้แปลว่าอะไร
มี approverName แต่ไม่มี approvedAtมีคนอนุมัติแต่ไม่รู้เมื่อไหร่?
มีทั้ง approvedAt และ cancelReasonอนุมัติแล้วและยกเลิกแล้วพร้อมกัน?
มี pickedItems แต่ยังไม่อนุมัติหยิบของก่อนได้รับอนุมัติ?

ทางแก้คือใช้ sealed class ตาม 4.15 — ให้แต่ละสถานะพกเฉพาะสิ่งที่มันมีจริง

sealed class PickRequest {
  const PickRequest({required this.requestNo, required this.requesterName,
      required this.totalItems, this.remark});

  final String requestNo;
  final String requesterName;
  final int totalItems;
  final String? remark;
}

class PendingApproval extends PickRequest {
  const PendingApproval({required super.requestNo, required super.requesterName,
      required super.totalItems, super.remark});
  // ไม่มี approver ไม่มี pickedItems — เพราะยังไม่มีจริง
}

class Approved extends PickRequest {
  const Approved({required super.requestNo, required super.requesterName,
      required super.totalItems, super.remark,
      required this.approverName, required this.approvedAt,
      required this.pickedItems});

  final String approverName;      // มีแน่นอน
  final DateTime approvedAt;      // มีแน่นอน
  final int pickedItems;          // มีแน่นอน — เริ่มที่ 0

  bool get isComplete => pickedItems >= totalItems;
}

class Cancelled extends PickRequest {
  const Cancelled({required super.requestNo, required super.requesterName,
      required super.totalItems, super.remark, required this.reason});

  final String reason;            // มีแน่นอน
}

ผลที่ได้คือ ? หายไปเกือบหมด และสามสถานะที่เป็นไปไม่ได้ข้างบนสร้างไม่ได้อีกเลย

ส่วนตัวแปลงเป็นคนตัดสินว่าใบนี้อยู่สถานะไหน

PickRequest toPickRequest(PickRequestDto dto, {String path = ''}) {
  if (dto.cancelReason != null) {
    return Cancelled(..., reason: dto.cancelReason!);
  }
  if (dto.approvedAt != null) {
    // อนุมัติแล้วต้องมีชื่อผู้อนุมัติด้วย ไม่งั้นข้อมูลขัดกันเอง
    final approver = dto.approverName;
    if (approver == null) {
      throw ContractException(
        path.isEmpty ? 'approverName' : '$path.approverName',
        'ใบที่อนุมัติแล้วต้องมีชื่อผู้อนุมัติ',
      );
    }
    return Approved(..., approverName: approver,
        approvedAt: dto.approvedAt!, pickedItems: dto.pickedItems ?? 0);
  }
  return PendingApproval(...);
}

สังเกตว่า ! ที่เหลืออยู่สองตัว อยู่หลังการตรวจแล้วทั้งคู่ — ต่างจากการเขียน ! เพราะเชื่อว่ามันน่าจะมี

ข้อ 3 — pickedItems: null ควรเป็น 0 ไหม

ขึ้นกับว่าใบอยู่สถานะไหน ซึ่งเป็นคำตอบที่โครงในข้อ 2 ทำให้เห็นชัด

สถานะpickedItems: null แปลว่าควรทำ
รออนุมัติยังไม่มีสิทธิ์หยิบไม่ควรมี field นี้เลย
อนุมัติแล้วอนุมัติแล้วแต่ยังไม่เริ่มหยิบแปลงเป็น 0 ได้
ยกเลิกแล้วไม่เกี่ยวข้องแล้วไม่ควรมี field นี้

ในโจทย์ใบนี้อยู่สถานะ “รออนุมัติ” ดังนั้น คำตอบคือไม่ควรแปลงเป็น 0 แต่ควรไม่มี field นี้ตั้งแต่แรก

เหตุผลที่การแปลงเป็น 0 ในสถานะนี้เป็นการโกหก

หน้าจอแสดง "หยิบไปแล้ว 0 จาก 5 รายการ"
  → ผู้ใช้เข้าใจว่างานเริ่มแล้ว แค่ยังไม่ได้หยิบอะไร
  → ความจริงคือยังไม่ได้รับอนุมัติ ยังหยิบไม่ได้เลย

สองอย่างนี้ต่างกันสิ้นเชิงในสายตาผู้ใช้ แต่แสดงผลเหมือนกันถ้ายุบเป็น 0

บทเรียนที่ควรจำ: คำถาม “null ควรกลายเป็นอะไร” มักตอบไม่ได้ตราบใดที่ยังมองทีละ field — พอจัดสถานะให้ถูกต้องแล้ว จะพบว่า field ส่วนใหญ่ไม่ควรมีอยู่ในสถานะนั้นตั้งแต่แรก และคำถามก็หายไปเอง

12. สรุปท้ายบท

  • “ไม่มีค่า” “ไม่รู้ค่า” และ “ค่าเป็นศูนย์” เป็นคนละเรื่อง
  • ใส่ ? เมื่อมีสถานะปกติของธุรกิจที่ค่านั้นไม่มี ไม่ใช่เพราะ compiler บ่น
  • field ที่จำเป็นแต่ไม่มี ต้องดัง ไม่ใช่ถูกแทนด้วยค่าตั้งต้น
  • ค่าตั้งต้นใช้ได้เมื่อตกลงความหมายกันไว้แล้ว และควรบันทึกเหตุผลไว้ในโค้ด
  • ข้อความว่าง null และไม่มีคีย์ ยุบเป็นอันเดียวได้ ถ้าตั้งใจ
  • ข้อความว่างไม่ผ่านสำหรับ field ที่จำเป็น
  • ค่าตกแต่งอย่าง — อยู่ที่ชั้นแสดงผล ห้ามเขียนกลับเข้าข้อมูล
  • เมื่อ nullable เยอะเกินไป ให้ดูว่าจริง ๆ แล้วมันคือหลายสถานะที่ควรแยกกัน
