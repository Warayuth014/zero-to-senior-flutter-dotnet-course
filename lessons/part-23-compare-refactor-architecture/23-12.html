เป้าหมาย: ย้าย architectureทีละ seamโดยระบบ deployได้ทุกขั้น ไม่สร้าง branchใหญ่ที่เปลี่ยน UI, state, HTTPและmodelsพร้อมกัน

1. หา seamจาก call boundary

จุดที่ดีคือ API call, constructor, pure widget, mapperหรือ command method เพราะสร้าง adapter/fakeได้โดยไม่แตะ backend seamที่ไม่มี testsหรือมี globalอ่านเขียนหลายจุดต้องสร้าง façadeก่อน

2. Strangler pattern

ให้ codeใหม่ครอบ codeเดิม เช่น PackingRepositoryเรียก ApiService extensionเดิม Screenเรียก controllerใหม่ทีละ command เมื่อ consumersย้ายครบค่อยลบ direct calls จึงไม่มี rewrite day

3. Compatibility façade

class LegacyPackingFacade {
  LegacyPackingFacade(this.repository);
  Future<ApiResult<Packing>> scan(...) =>
      adapt(repository.scan(...));
}

adapterชั่วคราวต้องมี removal issue/date ไม่เช่นนั้นกลายเป็น layerถาวรสองแบบ

4. One axis per change

PRหนึ่ง extract widgets, PRถัดไป introduce repository, ต่อด้วย controller แล้วค่อยเปลี่ยน Result type การแยก axisช่วย reviewว่า behaviorเปลี่ยนหรือเพียง structureและ revertเฉพาะขั้นได้

5. Preserve server contract

Flutter refactorไม่ควรเปลี่ยน endpoint/body/statusพร้อมกัน หากจำเป็นต้องเปลี่ยน .NET ใช้ version/backward-compatible fieldsและ deploy serverก่อน clientเพราะ PDAอัปเดตไม่พร้อมกันทุกเครื่อง

6. Feature flagsเมื่อ riskสูง

ใช้ flagเลือก old/new implementationที่ repository/controller seam พร้อม metricsเทียบ success/error/latency แต่หลีกเลี่ยงสอง mutation pathsพร้อมกันถ้า backend idempotencyยังไม่พร้อม

7. Migration scoreboard

ติดตาม call sitesที่ยัง new singleton, screensที่ยังมี domain transition, raw mapsและ testsต่อ feature ไม่วัดแค่จำนวนไฟล์ migrated และห้ามประกาศเสร็จขณะ façadeเก่ายังเป็น default

8. Rollback plan

ทุก seamต้องตอบว่า rollback code/config/dataอย่างไร ไม่มี schema irreversible, command duplicateหรือ cached state incompatible Refactorที่ revertไม่ได้คือ production migration ไม่ใช่ cleanupธรรมดา
