กรณีศึกษา: WarehouseStoreรวม receiving, inventory, cycle count, task, dispatch, picking, navigation, pollingและ feedback callbacks จึงเป็น source of truthที่มีประโยชน์แต่เริ่มข้าม bounded contexts

1. สัญญาณ God Store

ไฟล์ใหญ่ไม่ใช่หลักฐานเดียว ให้ดูหลายเหตุผลในการเปลี่ยน, dependenciesสี่ repositories, busy flagsคนละ feature, navigation strings, timer matrixและ testsที่ต้องสร้าง stateมหาศาลเพื่อแตะ commandเดียว

2. สิ่งที่ต้องรักษา

single snapshotของ shared tasks/pallets, runtime step preservation, polling reconciliationและ shell-wide feedbackเป็น behaviorสำคัญ การแยก classแล้ว duplicate listsตาม storeจะสร้าง multiple sources of truthที่แย่กว่า

3. Feature store boundaries

StoreOwns
ReceivingStoreorders, pallet validation, receive session
TaskStoretasks, dispatch, manual run, polling
PickingStorepicks, queues, Store In
CycleCountStoresession, counts, phase refresh

4. Shared projections

Inventory/pallet snapshotที่หลาย featureใช้ควรมี ownerหนึ่งตัวหรือ repository cacheพร้อม immutable snapshots Storeอื่นsubscribe/refreshผ่าน explicit API ไม่จับ public listเดียวกันแล้ว mutateข้าม boundary

5. Shell coordinator

coordinatorบางๆจัด route/tab, app lifecycleและ cross-feature invalidation เช่น withdraw successให้ TaskStore.reload ไม่ถือ fieldทุก featureหรือ implement business rulesแทน stores

6. Operation state

แทน global recvSubmitting/pickingSubmitting ใช้ stateต่อ command/key เช่น dispatch task A, confirm pick B ทำให้ UI disableเฉพาะ action, errorผูก cardและทดสอบ concurrencyได้

7. Extraction order

เริ่ม CycleCountเพราะ state/repository/refreshค่อนข้างแยก ตามด้วย Picking แล้ว Task/Receivingที่แชร์มากกว่า ทุกขั้นมี façade methodsเดิมให้ viewsยัง compile จากนั้นย้าย consumersทีละหน้า

8. Success criteria

แต่ละ storeมีหนึ่งเหตุผลหลักในการเปลี่ยน, dependencyแคบ, timer/dispose ownerชัด, ไม่มี duplicated mutable truth และ flow testsเดิมผ่าน Refactorที่เพียงย้าย 1,600บรรทัดเป็นสี่ partial filesยังไม่แก้ architecture
