หลักสำคัญ: setState และ ChangeNotifierแก้คนละ scope — เปรียบเทียบ ownership/rebuild boundary ไม่ใช่จัดอันดับว่าอันไหน seniorกว่า

1. setState เหมาะกับ local UI

wmsappใช้ setStateกับ loading, scan resultและflow stateในหน้าจอ ส่วน absoluteยังใช้กับ search query, expanded historyและ dialog validation นี่ถูกต้องเมื่อ stateมี owner/consumerเป็น State objectเดียวและไม่ต้องอยู่หลัง widget dispose

2. ChangeNotifier เหมาะกับ shared feature state

WarehouseStoreถือ tasks, pallets, selected flowและcommands แล้ว shell rebuildจาก notification ทำให้หลาย viewsเห็น snapshotเดียวและ navigationกลับมาทำ taskต่อได้ Constructor-injected repositoriesช่วยทดสอบ mutationโดยไม่เปิด UI

3. Granularity cost

notifyListeners()ไม่มี payload ทุก listenerอาจ rebuildกว้าง หาก storeใหญ่และ mutateบ่อย ควรแบ่ง feature storeหรือใช้ ListenableBuilderแคบๆ ไม่แก้ด้วยการลืม notifyซึ่งสร้าง stale UIที่หา bugยากกว่า

4. Public mutable collections

แม้ storeเป็น owner แต่ public Listยังเปิดให้ callerแก้โดยไม่รักษา invariant ทางที่ปลอดภัยคือ private mutable list + unmodifiable view และ command methodsที่ mutate/notifyใน transactionเดียว

5. Async ruleเหมือนกัน

setStateต้องตรวจ mountedหลัง await ส่วน ChangeNotifierต้องตรวจ session/generationและไม่ notifyหลัง dispose ChangeNotifierไม่ได้ทำ cancellationให้อัตโนมัติ; เพียงย้ายจุดที่ต้องจัด lifecycle

6. Derived state

ค่าที่คำนวณจาก source เช่น selectedIncomingPickหรือ filtered tasksควรเป็น getter ไม่เก็บสำเนาเพิ่ม ลด notify/order bugs ส่วนค่าที่ต้อง snapshotเพื่อ workflow เช่น scannedDestinationCodeยังควร persistใน feature state

7. Refactor pattern

ก่อน: setState(() { loading=true; }); await api(); ...
หลัง: controller.submit(input)
Widget: listenable → render state
ยังคงใน Widget: controller/focus/expanded/search

ย้าย transitionพร้อม tests ไม่ย้ายสี/padding/dialogทั้งหมดเข้า store

8. Review checklist

ถาม owner, lifetime, consumer count, persistence, async invalidation, rebuild scopeและ mutation API ถ้าคำตอบคือ widgetเดียว/sessionสั้น setStateมักพอ; ถ้าข้าม routeหรือหลาย viewsค่อยยกระดับ
