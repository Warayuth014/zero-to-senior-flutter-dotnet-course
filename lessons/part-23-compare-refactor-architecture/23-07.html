หลักฐาน: wmsappมี Packing 2,290, Receiving scan 1,832 และ Picking 1,686 บรรทัด; absoluteก็มี OpsViewกว่า 2,300 บรรทัด การแยกต้องตาม cohesion ไม่ใช่เลขบรรทัดล้วน

1. Giant screenพังอย่างไร

build method, controllers, async commands, dialogsและsub-flowsอยู่ไฟล์เดียว ทำให้ review diffชนกัน, lifecycleยาก, testต้อง setupทั้งหน้าและแก้ส่วนหนึ่งกระทบอีกส่วน แต่การยาวไม่ได้พิสูจน์ bugด้วยตัวเอง

2. เริ่มจาก pure widget

ดึงส่วน renderที่รับ immutable data+callbacksออกก่อน เช่น summary, product row, scan cardและhistory panel ไม่ย้าย state ไม่เปลี่ยน behavior จึงเป็น seamความเสี่ยงต่ำและช่วยให้ parent buildอ่านเป็นโครง flow

3. Extract dialog/sheetพร้อม lifecycle

componentที่มี controller/focusควรเป็น StatefulWidgetของตัวเองและ dispose resourceที่ตนสร้าง หากรับ controllerจาก parentต้องประกาศ ownershipชัดเหมือน Pda widgetsของ absoluteที่ disposeเฉพาะ internal controller

4. อย่าแตกเป็น private methodsอย่างเดียว

Widget _buildX()ลดความยาวแต่ยัง rebuildพร้อม parentและเข้าถึง stateทุกตัว Component classสร้าง explicit inputs, key/test boundaryและลด accidental couplingได้จริง

5. ต่อด้วย feature controller

หลัง presentation seamsชัด ค่อยย้าย scan validation/API transitionออกจาก Stateเป็น controllerที่ทดสอบได้ ลำดับนี้ทำให้รู้ว่า stateใด localและ stateใด domain ไม่สร้าง mega view-modelจากการย้ายทุก fieldพร้อมกัน

6. Preserve behavior

ก่อน extractionล็อก scanner focus, keyboard Enter, scroll owner, loading disable, dialog dismissalและ navigation resultด้วย widget tests Golden screenshotอย่างเดียวจับ side effectsไม่ได้

7. Folder by feature

packing/
  packing_screen.dart       // composition
  packing_controller.dart   // transitions
  widgets/...
  dialogs/...
  packing_repository.dart

co-locateสิ่งที่เปลี่ยนด้วยกัน ไม่สร้าง global widgets dumpใหม่

8. Exit criteria

หยุดเมื่อ parentอ่าน flowได้, extracted componentมี inputsแคบ, ownershipชัดและ testsผ่าน ไม่ตั้งเป้าไฟล์ต่ำกว่า Nบรรทัดเพราะอาจสร้าง 30ไฟล์ที่ตามยากกว่าเดิม
