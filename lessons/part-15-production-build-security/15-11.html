1. เครือข่ายในคลังไม่เหมือนที่ออฟฟิศ

สภาพสาเหตุ
สัญญาณหายเป็นช่วงชั้นวางเหล็กสูงบังคลื่น
สลับจุดกระจายสัญญาณระหว่างเดินคลังกว้าง ต้องมีหลายจุด
ไม่มีสัญญาณเลยในห้องเย็นผนังหนาและเป็นโลหะ
ช้าลงตอนกะเปลี่ยนทุกเครื่องเข้าใช้พร้อมกัน
เซิร์ฟเวอร์ถูกรีสตาร์ทตอนอัปเดตงานบำรุงรักษาปกติ

คอร์สนี้ตัดสินใจเรื่องเหล่านี้ไว้กระจายอยู่หลาย Part แล้ว บทนี้รวบมาตรวจว่าครบไหม

2. รายการตรวจ — คำขอเดี่ยว

ข้อต้องมีบท
1ทุกคำขอมี timeout7.6
2timeout ของการอัปโหลดยาวกว่าคำขอปกติ13.8
3แยกชนิดความล้มเหลว ไม่ยุบเป็น “เกิดข้อผิดพลาด”7.9
4รู้ว่าคำสั่งไหนไม่รู้ผล และบอกผู้ใช้7.10
5คำสั่งที่เปลี่ยนข้อมูลมี Idempotency-Key7.13
6ลองใหม่เฉพาะ GET และเฉพาะชนิดที่ลองแล้วมีโอกาสต่าง7.12
7การลองใหม่ถอยห่างขึ้นและมีเพดาน7.12

ข้อ 4 กับ 5 ทำงานคู่กัน — รหัสคำสั่งคือสิ่งที่ทำให้การส่งซ้ำปลอดภัย และนั่นทำให้ข้อความที่บอกผู้ใช้เปลี่ยนจาก “ตรวจก่อนส่งซ้ำ” เป็น “ลองใหม่ได้เลย”

case UploadFailed(:final message, :final outcomeUnknown):
  _stage = UploadStage.failed;
  _message = outcomeUnknown
      ? '$message — ตรวจว่ารูปขึ้นแล้วหรือยังก่อนส่งซ้ำ'
      : message;

3. รายการตรวจ — สถานะและการแสดงผล

ข้อต้องมีบท
8ผู้ใช้รู้ว่าข้อมูลที่เห็นทันสมัยแค่ไหน10.12
9แสดงชื่อเซิร์ฟเวอร์ที่ใช้อยู่ ไม่ใช่แค่จุดสี10.12
10ไม่ปิดปุ่มเพราะสถานะเครือข่าย10.12
11ข้อความบอกว่า “เครื่องนี้” หรือ “ระบบ” มีปัญหา10.12
12สถานะ unknown แยกจาก “ตรวจแล้วไม่ตอบ”10.8

ข้อ 10 เป็นข้อที่ขัดกับสัญชาตญาณที่สุด และเหตุผลอยู่ที่ข้อมูลที่ใช้ตัดสินเชื่อไม่ได้ — “มีสัญญาณ” ไม่ได้แปลว่า “ใช้งานได้” และการปิดปุ่มทำให้ผู้ใช้ทำงานไม่ได้ทั้งที่ทำได้

4. รายการตรวจ — การเชื่อมต่อค้าง

ข้อต้องมีบท
13ต่อกลับได้เองเมื่อสายหลุด12.4
14โหลดใหม่ทั้งชุดหลังต่อกลับ12.4
15เข้ากลุ่มซ้ำหลังต่อกลับ ถ้า hub ใช้กลุ่ม12.2
16ต่อใหม่เมื่อแอปกลับมาจากพื้นหลัง12.4
17มีทางสำรองเมื่อเรียลไทม์ใช้ไม่ได้12.11
18ตัวจับเวลาหยุดเมื่อออกจากจอ12.8
19โหลดใหม่เป็นระยะแม้ทุกอย่างดูปกติ12.10

ข้อ 14 คือข้อที่โปรเจกต์จริงยังไม่ได้ทำ (12.4) และข้อ 19 คือการยอมรับว่าไม่มีระบบเรียลไทม์ไหนที่ไม่เคยพลาด

// ตาข่ายกันพลาด ห่างพอที่จะไม่กระทบต้นทุน แต่ถี่พอที่จะจำกัดความเสียหาย
_safetyNet = Timer.periodic(const Duration(minutes: 5), (_) {
  if (status == RealtimeStatus.connected) unawaited(load());
});

5. รายการตรวจ — งานที่ผู้ใช้ทำค้าง

ข้อต้องมีบท
20ยืนยันไม่สำเร็จ ต้องเก็บที่สแกนไว้14.6
21เตือนก่อนทิ้งงานที่กรอกค้าง10.11
22สลับเซิร์ฟเวอร์ตอนมีงานค้าง ต้องเตือนพร้อมบอกจำนวน10.6
23ไม่ส่งคำสั่งซ้ำเองเมื่อเน็ตกลับมา10.12

ข้อ 20 เป็นข้อที่กระทบผู้ใช้มากที่สุดในทางปฏิบัติ — คนที่เดินนับสต๊อกมาสี่สิบนาทีแล้วต้องเริ่มใหม่เพราะเน็ตหลุดตอนกดยืนยัน จะเลิกเชื่อถือแอปทันที

test('ยืนยันไม่สำเร็จ ต้องเก็บที่สแกนไว้', () async {
  ...
  // ผู้ใช้เดินนับมาสี่สิบนาที ห้ามให้เริ่มใหม่เพราะเน็ตหลุด
  expect(store.counted, hasLength(2));
  expect(store.canConfirm, isTrue, reason: 'ต้องกดยืนยันซ้ำได้');
});

ข้อ 23 คือด้านกลับ — การส่งซ้ำเองเมื่อเน็ตกลับมาดูเหมือนช่วย แต่สถานะจริงในคลังอาจเปลี่ยนไปแล้วระหว่างที่ออฟไลน์อยู่ครึ่งชั่วโมง

6. สิ่งที่ยังทำไม่ได้ในรุ่นนี้

เรื่องทางแก้ที่แท้จริงอยู่ที่
ทำงานตอนไม่มีเน็ตเลยเก็บลงเครื่องแล้วส่งทีหลังPart 29
รูปที่ถ่ายตอนออฟไลน์เหมือนกันPart 29
เหตุการณ์ที่พลาดระหว่างหลุดนานให้เซิร์ฟเวอร์เก็บคิวไว้ฝั่ง .NET
สิ่งที่ทำได้ตอนนี้คือบอกผู้ใช้ให้ชัดว่าอะไรทำได้และทำไม่ได้ — แอปที่บอกว่า “ตอนนี้ส่งไม่ได้ ให้เดินไปที่ที่มีสัญญาณก่อนกดยืนยัน” ดีกว่าแอปที่ปล่อยให้กดแล้วเสียงานไป

7. ทดสอบก่อนปล่อย

สิ่งที่ทดสอบด้วยเทสต์ไปแล้วครอบคลุมมาก แต่มีสิ่งที่ต้องลองบนเครื่องจริง

สถานการณ์วิธีจำลอง
สัญญาณหายกลางคันเปิดโหมดเครื่องบินระหว่างกดยืนยัน
เน็ตช้ามากใช้เครื่องมือจำกัดความเร็วของเราเตอร์
เซิร์ฟเวอร์ล่มระหว่างใช้งานหยุดเซิร์ฟเวอร์ทดสอบ
เดินออกนอกรัศมีแล้วกลับเข้ามาเดินจริงในคลัง
ทิ้งแอปไว้ในกระเป๋าครึ่งชั่วโมงทำจริง

แถวสุดท้ายเป็นสถานการณ์จาก 12.4 แบบฝึกหัด และเป็นแถวที่มักไม่มีใครทดสอบ ทั้งที่เกิดทุกวัน

# จำลองเน็ตช้าบนเครื่องที่ต่อ adb
adb shell settings put global captive_portal_detection_enabled 0
# แล้วใช้เครื่องมือของเราเตอร์จำกัดความเร็ว หรือใช้ proxy ที่หน่วงได้

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ผู้ใช้เสียงานที่ทำมานานล้างสถานะเมื่อยืนยันล้มเหลวเก็บไว้ให้กดซ้ำได้
ได้ข้อมูลซ้ำในระบบไม่มีรหัสคำสั่ง หรือสร้างใหม่ตอนลองใหม่7.13, 13.4
หน้าจอค้างข้อมูลเก่าทั้งวันไม่โหลดใหม่หลังต่อกลับ12.4
แบตหมดเร็วถามซ้ำถี่เกิน หรือตัวจับเวลาไม่หยุด12.1, 12.8
ผู้ใช้ทำงานไม่ได้ทั้งที่เน็ตปกติปิดปุ่มตามสถานะเครือข่าย10.12
เดินออกจากรัศมีแล้วแอปไม่กลับมาเองไลบรารีเลิกพยายามต่อแล้วต่อใหม่ตอนกลับมาที่หน้าจอ (12.4)

9. แบบฝึกหัด

ทีมทดสอบในออฟฟิศแล้วทุกอย่างปกติ แต่วันแรกที่ใช้ในคลังจริง ผู้ใช้บ่นสามเรื่อง

  1. “กดยืนยันแล้วค้าง ต้องปิดแอปเปิดใหม่”
  2. “ของที่รับเข้าไปแล้ว ขึ้นซ้ำสองครั้ง”
  3. “ตัวเลขบนหน้าแรกไม่ตรงกับความจริง”

วินิจฉัยแต่ละข้อ

แนวคำตอบ

ข้อ 1 — กดแล้วค้าง

สาเหตุที่เป็นไปได้ตรวจอย่างไร
ไม่มี timeout คำขอรอไปเรื่อย ๆดูว่าตั้ง .timeout() ไว้ไหม (7.6)
มี timeout แต่ยาวเกิน60 วินาทีบนเน็ตคลังคือค้างในสายตาผู้ใช้
ปุ่มถูกปิดแล้วไม่เปิดกลับfinally ไม่ได้ล้างสถานะ (4.9)

ข้อที่สามน่าสงสัยที่สุดถ้า “ต้องปิดแอปเปิดใหม่” — เพราะถ้าเป็น timeout ธรรมดา รอสักพักก็จะขึ้นข้อความเอง

ข้อ 2 — ของขึ้นซ้ำ

นี่คืออาการของ 7.10 ตรง ๆ — คำสั่งที่ไม่รู้ผลถูกส่งซ้ำ

ตรวจบท
คำสั่งมี Idempotency-Key ไหม7.13
รหัสเป็นตัวเดิมตอนลองใหม่ไหม13.4
ฝั่งเซิร์ฟเวอร์ตรวจรหัสซ้ำจริงไหม7.13
กดซ้ำระหว่างส่งได้ไหม4.9

สี่ข้อนี้ต้องผ่านทั้งหมด — ข้อใดข้อหนึ่งพลาดก็เกิดของซ้ำได้ และข้อที่สามอยู่ฝั่งเซิร์ฟเวอร์ซึ่งต้องยืนยันกับทีมหลังบ้าน ไม่ใช่สมมติว่าทำแล้ว

ข้อ 3 — ตัวเลขไม่ตรง

อาการนี้กว้างที่สุดและต้องแยกก่อน

ถ้าแปลว่า
ปิดแอปเปิดใหม่แล้วตรงข้อมูลค้างเก่า — ไม่โหลดใหม่หลังต่อกลับ (12.4)
ยังไม่ตรงหลังเปิดใหม่ข้อมูลผิดจริง — เป็นปัญหาฝั่งเซิร์ฟเวอร์หรือการบันทึกซ้ำจากข้อ 2
ตรงบางเครื่อง ไม่ตรงบางเครื่องบางเครื่องสลับ profile ไปเซิร์ฟเวอร์อื่น (10.12)

แถวแรกน่าสงสัยที่สุดและเชื่อมกับข้อ 14 ในรายการตรวจ

สิ่งที่ควรทำก่อนแก้ทั้งสามข้อ — ทั้งสามอาการอาจมาจากสาเหตุเดียวกัน

สายหลุดตอนกดยืนยัน
  → คำขอค้าง (ข้อ 1)
    → ผู้ใช้ปิดแอปเปิดใหม่ แล้วกดยืนยันอีกครั้ง
      → เซิร์ฟเวอร์ได้รับสองครั้ง (ข้อ 2)
        → ตัวเลขบนหน้าแรกนับซ้ำ (ข้อ 3)

ถ้าเป็นแบบนี้ การแก้ข้อ 1 กับการเพิ่มรหัสคำสั่ง จะทำให้ทั้งสามอาการหายพร้อมกัน

บทเรียนที่ใหญ่กว่า: รายงานจากหน้างานมักมาเป็นอาการที่ผู้ใช้เห็น ไม่ใช่สาเหตุ — งานแรกคือหาว่าอาการหลายอย่างมาจากรากเดียวกันไหม ก่อนที่จะเปิดสามงานแยกกัน

10. สรุป

  • เครือข่ายในคลังหลุดเป็นปกติ ไม่ใช่กรณีพิเศษ
  • ทุกคำขอต้องมี timeout และคำสั่งที่เปลี่ยนข้อมูลต้องมีรหัส
  • ต่อกลับแล้วต้องโหลดใหม่ทั้งชุด
  • ห้ามล้างงานที่ผู้ใช้ทำค้างเมื่อส่งไม่สำเร็จ
  • ไม่ส่งคำสั่งซ้ำเองเมื่อเน็ตกลับมา
  • ทดสอบด้วยการเดินจริงในคลังและทิ้งเครื่องไว้ในกระเป๋า
  • อาการหลายอย่างจากหน้างาน มักมาจากรากเดียวกัน

บทหน้า: รวมทุกอย่างเป็นรายการที่ตรวจได้จริงก่อนปล่อย
