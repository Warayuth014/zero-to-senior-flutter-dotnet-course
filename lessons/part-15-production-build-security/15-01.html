1. Part นี้แก้ปัญหาอะไร

สิบสี่ Part ที่ผ่านมาสร้างแอปที่ทำงานได้บนเครื่องนักพัฒนา Part นี้พาแอปออกไปอยู่ในมือผู้ใช้จริง ซึ่งมีสิ่งที่ต่างออกไปมาก

ตอนพัฒนาตอนใช้งานจริง

คุณสมบัติdebugprofilerelease

สองแถวที่มีผลกับการทำงานประจำวันมากที่สุดคือแถว assert และแถวแถบล้น

3. assert หายไปในโหมด release

String pickSummary({required int scanned, required int required}) {
  // ทั้งสองค่ามาจากการนับ จึงติดลบไม่ได้ — ถ้าติดลบแปลว่ามีบั๊กที่อื่น
  assert(scanned >= 0 && required >= 0, 'จำนวนติดลบ: $scanned/$required');
  ...
}
ผลที่ตามมารายละเอียด
ใช้ assert ตรวจสมมติฐานของทีมได้อย่างสบายใจไม่กระทบผู้ใช้และไม่กินเวลา
ห้ามใช้ assert ตรวจข้อมูลจากภายนอกในโหมด release มันหายไป แล้วข้อมูลผิดจะไหลเข้าระบบ
// ผิด — ข้อมูลจากเซิร์ฟเวอร์ต้องตรวจด้วยโค้ดที่ทำงานจริง
assert(json['quantity'] != null);

// ถูก — ตรวจแล้วโยนแบบที่ทำงานทุกโหมด (6.5)
final quantity = requireInt(json, 'quantity');
กฎที่จำง่าย — assert ตรวจบั๊กของเรา ส่วนการตรวจข้อมูลจากคนอื่นต้องใช้โค้ดปกติ

4. แถบล้นที่หายไป

ในโหมด debug เนื้อหาที่ล้นจะเห็นเป็นแถบเหลืองดำ ในโหมด release มันแค่ถูกตัดหายไปเงียบ ๆ

โหมดผู้ใช้เห็นอะไร
debugแถบเหลืองดำที่บอกว่าล้นกี่พิกเซล
releaseข้อความหรือปุ่มหายไปเฉย ๆ

นี่คือเหตุผลที่ 14.13 ยืนยันให้เขียนเทสต์ tester.takeException() — เพราะเป็นทางเดียวที่จะจับการล้นได้ก่อนที่จะกลายเป็นปุ่มที่ผู้ใช้กดไม่ได้

5. อะไรที่ควรต่างกันตามโหมด

import 'package:flutter/foundation.dart';

// ตัวแปรที่คอมไพเลอร์รู้ค่าตั้งแต่ตอน build จึงตัดโค้ดที่ไม่ใช้ทิ้งได้
if (kDebugMode) {
  debugPrint('...');
}

if (kReleaseMode) {
  await crashReporter.initialize();
}

if (kProfileMode) { ... }
ควรทำเฉพาะ debugควรทำเฉพาะ release
debugPrint ที่ละเอียดส่งรายงานข้อผิดพลาดออกไป (15.10)
เปิด debugRepaintRainbowEnabledปิดปุ่มที่ใช้ทดสอบ
ปุ่มลัดสำหรับทดสอบเก็บสถิติการใช้งาน
ข้อมูลตัวอย่างที่ใส่ไว้ให้—
kDebugMode ไม่ใช่ตัวแปรธรรมดา — มันเป็น const ที่คอมไพเลอร์รู้ค่า ทำให้โค้ดในบล็อกนั้นถูกตัดทิ้งทั้งก้อนตอน build release ไม่ใช่แค่ข้ามตอนรัน

ต่างจากการเช็คด้วยตัวแปรที่อ่านจากที่อื่น ซึ่งโค้ดจะยังติดไปในแอป

// โค้ดข้างในถูกตัดทิ้ง ไม่ติดไปกับแอป
if (kDebugMode) { showDebugPanel(); }

// โค้ดข้างในยังติดไป แม้จะไม่มีวันทำงาน
if (settings.debugEnabled) { showDebugPanel(); }

6. อย่าเชื่อตัวเลขจากโหมด debug

วัดอะไรdebug ต่างจากจริงแค่ไหน
ความเร็วในการวาดช้ากว่าหลายเท่า
เวลาเปิดแอปช้ากว่ามาก
ขนาดแอปใหญ่กว่าสองถึงสามเท่า
หน่วยความจำใกล้เคียง
จำนวนคำขอเครือข่ายเท่ากัน

สามแถวบนคือเหตุผลที่ 14.14 ยืนยันให้วัดในโหมด profile เท่านั้น — ตัวเลขจาก debug ทำให้คนไปแก้สิ่งที่ไม่ได้เป็นปัญหาจริง

ส่วนสองแถวล่างวัดในโหมด debug ได้ ซึ่งสะดวกกว่าเพราะมี DevTools ครบ

7. build บ่อยแค่ไหน

จังหวะควรทำ
ทุกวันระหว่างพัฒนาdebug
ก่อนบอกว่า “เสร็จแล้ว”release อย่างน้อยหนึ่งครั้ง แล้วลองบนเครื่องจริง
ก่อนปล่อยรุ่นrelease + ทดสอบตาม checklist (15.12)
เมื่อมีคนรายงานว่าช้าprofile บนเครื่องที่มีปัญหา

แถวที่สองเป็นแถวที่ทีมส่วนใหญ่ข้าม และเป็นที่มาของบั๊กประเภทที่ 15.3 จะแสดง — ฟีเจอร์ที่ทำงานสมบูรณ์ในโหมด debug แล้วใช้งานไม่ได้เลยในโหมด release

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ทำงานใน debug แต่ไม่ทำงานใน releaseสิทธิ์ที่ Flutter ใส่ให้เฉพาะ debug (15.3)ประกาศเองใน main manifest
ข้อมูลผิดหลุดเข้าระบบเฉพาะตอนใช้จริงใช้ assert ตรวจข้อมูลจากภายนอกใช้โค้ดที่ทำงานทุกโหมด
ปุ่มหายไปเฉพาะบนเครื่องจริงเนื้อหาล้นแต่ไม่มีแถบเตือนเขียนเทสต์ (14.13)
ไปแก้ประสิทธิภาพที่ไม่ได้เป็นปัญหาวัดในโหมด debugวัดในโหมด profile
debugPrint หลุดไปในแอปจริงไม่ได้ครอบด้วย kDebugModeครอบ
เจอปัญหาตอนใกล้ปล่อยไม่เคย build release ระหว่างทางbuild release อย่างน้อยสัปดาห์ละครั้ง

9. แบบฝึกหัด

ทีมพบว่าแอปที่ build เป็น release แล้ว “เปิดมาแล้วขาวเปล่า” แต่ในโหมด debug ทำงานปกติ

  1. สาเหตุที่เป็นไปได้
  2. จะหาอย่างไรเมื่อไม่มี log
แนวคำตอบ

1. สาเหตุที่พบบ่อย เรียงตามความน่าจะเป็น

สาเหตุทำไมเห็นเฉพาะ release
โยนใน main ก่อน runAppใน debug เห็นข้อความสีแดง ใน release เห็นจอเปล่า
ขาดสิทธิ์ INTERNET แล้วโค้ดตอนเริ่มรอคำขอสิทธิ์มีเฉพาะ debug (15.3)
asset ที่ไม่ได้ประกาศใน pubspec.yamldebug อ่านจากไฟล์ระบบได้ release อ่านจากที่รวม asset เท่านั้น
โค้ดที่พึ่ง assert ให้ทำงานassert ถูกตัดทิ้ง
ปลั๊กอินที่ต้องตั้งค่า ProGuardโค้ดถูกย่อจนหาคลาสไม่เจอ

2. วิธีหาเมื่อไม่มี log — ไล่จากง่ายไปยาก

วิธีได้อะไร
flutter run --release ต่อสาย USBได้ log ของ release build ซึ่งยังพิมพ์ข้อผิดพลาดร้ายแรงออกมา
adb logcatเห็นข้อผิดพลาดระดับ Android รวมถึงเรื่องสิทธิ์
flutter build apk --profileถ้าโหมดนี้ทำงาน แปลว่าเป็นเรื่องของการย่อโค้ด ไม่ใช่ AOT
ครอบ main ด้วยตัวจับข้อผิดพลาดเห็นสิ่งที่โยนก่อน runApp
Future<void> main() async {
  // จับทุกอย่างที่โยนตอนเริ่ม แล้วแสดงบนหน้าจอ ไม่งั้นจะเห็นจอเปล่า
  runZonedGuarded(() async {
    WidgetsFlutterBinding.ensureInitialized();
    await bootstrap();
    runApp(const WmsApp());
  }, (error, stack) {
    // อย่างน้อยต้องมีอะไรให้เห็น
    runApp(StartupFailureScreen(error: error.toString()));
  });
}

สิ่งที่ควรทำก่อนทั้งหมดนี้ — บรรทัดแรกของ flutter run --release มักบอกคำตอบอยู่แล้ว แต่คนมักข้ามเพราะคิดว่าโหมด release ไม่มี log

และบทเรียนที่ใหญ่กว่าคือจอเปล่าเป็นสิ่งที่ป้องกันได้ — แอปที่มีหน้าจอบอกความล้มเหลวตอนเริ่ม ทำให้ผู้ใช้ส่งภาพหน้าจอมาให้ได้ แทนที่จะบอกได้แค่ว่า “มันไม่ขึ้น”

10. สรุป

  • debug เขียนโค้ด profile วัดความเร็ว release ส่งให้ผู้ใช้
  • assert หายไปใน release — ใช้ตรวจบั๊กของเรา ไม่ใช่ข้อมูลจากคนอื่น
  • แถบล้นหายไปด้วย เนื้อหาที่ล้นจะถูกตัดเงียบ ๆ
  • kDebugMode ทำให้โค้ดถูกตัดทิ้ง ไม่ใช่แค่ข้ามตอนรัน
  • อย่าเชื่อตัวเลขความเร็วและขนาดจากโหมด debug
  • build release อย่างน้อยสัปดาห์ละครั้ง อย่ารอถึงวันปล่อย

บทหน้า: เลขรุ่นสองตัวที่ทำหน้าที่ต่างกันโดยสิ้นเชิง
