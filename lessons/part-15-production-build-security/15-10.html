Production diagnostics ต้องตอบว่า “อะไรเกิด ที่ไหน เมื่อไร” โดยไม่รั่วข้อมูล: ใช้ structured logs, correlation ID, crash/error reporting และ breadcrumb ที่กำหนด retention/access ชัดเจน

1. Log levels

debug/trace ปิดหรือ samplingใน release, info สำหรับ lifecycle/business milestone, warning สำหรับ recoverable anomaly, error สำหรับ operationล้มพร้อม stack/cause ไม่ใช้ errorกับ validationปกติจน alert noise

2. Structured event

logger.info('receiving.submit', fields: {
  'operationId': operationId,
  'build': buildNumber,
  'durationMs': elapsed,
  'result': 'success',
});

ใช้ stable event name/fields ไม่ parseข้อความภาษาไทยย้อนหลัง

3. Redaction

ห้าม log password, JWT/Authorization, cookie, raw request body, signed URL, รูป, full serialหรือข้อมูลบุคคล Mask/hash เฉพาะเมื่อ threat model/กฎหมายอนุญาตและ hashก็อาจเป็น identifierได้

4. Correlation

client สร้าง operation/request ID แล้วส่ง headerให้ .NET logร่วมกัน แยก session IDแบบสุ่มจาก user IDและ rotateตาม policy ช่วยไล่ timeout/duplicateโดยไม่ต้องเห็น payloadลับ

5. Crash vs handled error

Flutter framework error, platform dispatcher error และ isolate errorต้องถูก captureตามจุดที่เหมาะ แต่ network offline/validationที่ handleแล้วควรเป็น metric/breadcrumb ไม่ส่งทุกครั้งเป็น crash

6. Symbols

ถ้า obfuscate/minify ต้องเก็บ split debug info/mappingตรง build number ในที่จำกัดสิทธิ์ เพื่อ symbolicate stack trace ห้ามเผย symbolsสาธารณะหรือทำหายหลัง release

7. Operational metrics

ติดตาม crash-free sessions, login/API failure rate, p95 duration, timeout, offline queue depth, duplicate conflictและ app version adoption ตั้ง alertตาม baseline/SLO ไม่ alertทุก exceptionเดี่ยว

8. Diagnostics test

บังคับ handled/unhandled failureใน staging ตรวจ eventถึงระบบ, symbolicateได้, correlationต่อ .NETได้, redactionผ่าน และผู้ใช้มี support IDโดยไม่ต้องส่ง token/screenshotข้อมูลลับ
