1. หนึ่งบรรทัด สองเลข

# pubspec.yaml
version: 3.1.0+42
3.1.042
เรียกว่าversion nameversion code / build number
ใครดูผู้ใช้และทีมระบบปฏิบัติการ
บอกอะไรเปลี่ยนมากแค่ไหนรุ่นไหนใหม่กว่า
ซ้ำได้ไหมได้ไม่ได้
ต้องเพิ่มขึ้นไหมไม่บังคับบังคับ
Android ตัดสินว่ารุ่นไหนใหม่กว่าจากเลขหลัง + เท่านั้น — ชื่อรุ่นไม่มีผลเลย รุ่นชื่อ 4.0.0+42 ติดตั้งทับ 3.1.0+42 ไม่ได้
test('เลข build ที่มากกว่าเท่านั้นที่ติดตั้งทับได้', () {
  final installed = AppVersion.parse('3.1.0+42')!;

  expect(AppVersion.parse('3.1.0+43')!.canUpgradeFrom(installed), isTrue);
  expect(AppVersion.parse('3.1.0+42')!.canUpgradeFrom(installed), isFalse);
  // ชื่อรุ่นใหม่กว่าแต่เลข build เท่าเดิม — Android ปฏิเสธ
  expect(AppVersion.parse('4.0.0+42')!.canUpgradeFrom(installed), isFalse);
});

2. อาการเมื่อลืมเพิ่มเลข build

ทางสิ่งที่เกิด
ติดตั้งด้วย adb installล้มเหลวด้วย INSTALL_FAILED_VERSION_DOWNGRADE
ติดตั้งด้วยการกดไฟล์ APKขึ้นว่า “ไม่ได้ติดตั้งแอป” โดยไม่บอกสาเหตุ
อัปโหลด Play Storeปฏิเสธทันทีพร้อมบอกเลขที่ใช้ไปแล้ว

ทางกลางเป็นทางที่ใช้ในคลังมากที่สุด และเป็นทางที่บอกสาเหตุน้อยที่สุด — ช่างที่ไปติดตั้งจะเห็นแค่ “ไม่ได้ติดตั้งแอป” แล้วเดาว่าไฟล์เสีย

test('version ที่ไม่มีเลข build ต้องขวางการปล่อย', () {
  final pubspec = goodPubspec.replaceAll('3.1.0+42', '3.1.0');

  final findings = checkPubspec(pubspec);
  expect(findings.single.code, 'missing-build-number');
  expect(findings.single.fix, contains('+'));
});

3. ตั้งชื่อรุ่นอย่างไร

รูปแบบที่ใช้กันคือสามส่วน

3 . 1 . 0
│   │   └── แก้บั๊ก ผู้ใช้ไม่ต้องเรียนรู้อะไรใหม่
│   └────── ฟีเจอร์ใหม่ที่เข้ากันได้กับของเดิม
└────────── เปลี่ยนใหญ่ ผู้ใช้ต้องรู้ตัว
เปลี่ยนอะไรขึ้นเลขไหนตัวอย่างจากคอร์สนี้
แก้ปีไทยที่ผิดไป 543 ปีตัวท้าย11.9
เพิ่มฟีเจอร์ถ่ายรูปหลักฐานตัวกลางPart 13
เปลี่ยนวิธีเข้าสู่ระบบทั้งหมดตัวหน้าPart 8
เปลี่ยนสัญญากับเซิร์ฟเวอร์จนแอปเก่าใช้ไม่ได้ตัวหน้า14.5

สำหรับแอปภายในองค์กร ประโยชน์ของชื่อรุ่นไม่ใช่การสื่อสารกับตลาด แต่คือการให้ผู้ใช้บอกได้ว่าเขาใช้รุ่นไหนเมื่อโทรมาแจ้งปัญหา

// แสดงในหน้าตั้งค่าเสมอ
Text('${AppConfig.appTitle} ${version.pubspecLine}')   // ACETEC WMS v3 3.1.0+42
แสดงทั้งสองเลข ไม่ใช่แค่ชื่อรุ่น — เพราะสองเครื่องที่บอกว่า “3.1.0” เหมือนกัน อาจเป็นคนละ build ที่ต่างกันสิบครั้ง

4. ใครเพิ่มเลข build

วิธีข้อดีข้อเสีย
แก้มือใน pubspec.yamlเห็นชัดใน gitลืมได้ และชนกันเมื่อสองคนแก้พร้อมกัน
ส่งตอน buildลืมไม่ได้ต้องมีที่เก็บเลขล่าสุด
ใช้เลขจากระบบ CIอัตโนมัติและไม่ซ้ำแน่นอนต้องมี CI
# ส่งตอน build โดยไม่แตะ pubspec
flutter build apk --release --build-name=3.1.0 --build-number=42

# ใช้เลขลำดับของ CI
flutter build apk --release --build-number=$CI_PIPELINE_IID

สำหรับทีมเล็กที่ยังไม่มี CI ทางที่ได้ผลคือทำให้ลืมไม่ได้ ด้วยการตรวจในสคริปต์ที่ใช้ build

# tool/release.sh
current=$(grep '^version:' pubspec.yaml | cut -d'+' -f2)
last=$(git tag --list 'v*' | tail -1 | cut -d'+' -f2)

if [ "$current" -le "$last" ]; then
  echo "เลข build $current ไม่มากกว่ารุ่นก่อน ($last)"
  exit 1
fi

5. เลขรุ่นกับสัญญาฝั่งเซิร์ฟเวอร์

14.5 ทิ้งคำถามไว้ว่าจะรู้ได้อย่างไรว่าแอปกับเซิร์ฟเวอร์เข้ากันได้ — เลขรุ่นคือส่วนหนึ่งของคำตอบ

// ส่งรุ่นของแอปไปกับทุกคำขอ ทำให้ฝั่งเซิร์ฟเวอร์รู้ว่ากำลังคุยกับใคร
headers: {
  'X-App-Version': version.pubspecLine,
  ...
}
ฝั่งเซิร์ฟเวอร์ทำอะไรได้
บันทึกว่ารุ่นไหนยังใช้อยู่บ้าง — ใช้ตัดสินว่าลบสัญญาเก่าได้เมื่อไหร่ (14.5)
ตอบข้อความที่ต่างกันให้แอปรุ่นเก่า
ปฏิเสธรุ่นที่เก่าเกินไปพร้อมบอกให้อัปเดต

แถวแรกมีค่าที่สุดในทางปฏิบัติ — คำถามที่ว่า “ยังมีเครื่องที่ใช้รุ่นเก่าอยู่ไหม” ตอบได้จากข้อมูลจริง แทนที่จะเดา

6. อ่านรุ่นในโค้ด

dependencies:
  package_info_plus: ^8.0.0
final info = await PackageInfo.fromPlatform();
final version = AppVersion(
  name: info.version,        // 3.1.0

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ติดตั้งทับไม่ได้เลข build เท่าเดิมหรือน้อยลงเพิ่มทุกครั้งที่ build
ผู้ใช้บอกรุ่นไม่ได้ไม่ได้แสดงในแอปแสดงในหน้าตั้งค่า
สองเครื่องบอกรุ่นเดียวกันแต่พฤติกรรมต่างกันแสดงแค่ชื่อรุ่นแสดงเลข build ด้วย
เลข build ชนกันเมื่อสองคนปล่อยพร้อมกันแก้มือใน pubspecใช้เลขจาก CI
ไม่รู้ว่ามีเครื่องใช้รุ่นเก่าอยู่ไหมไม่ได้ส่งรุ่นไปกับคำขอส่งใน header
PackageInfo ช้าเพราะเรียกซ้ำเรียกทุกครั้งที่ต้องใช้อ่านครั้งเดียวตอนเริ่ม

8. แบบฝึกหัด

ทีมปล่อยรุ่น 3.1.0+42 ไปแล้ว แล้วพบบั๊กร้ายแรงที่ต้องแก้ด่วน

  1. รุ่นถัดไปควรเป็นเลขอะไร
  2. ถ้าต้องย้อนกลับไปรุ่นเก่าล่ะ
แนวคำตอบ

1. 3.1.1+43

test('ขึ้นรุ่นย่อยต้องเพิ่มเลข build ด้วย', () {
  final next = AppVersion.parse('3.1.0+42')!.nextPatch();
  expect(next.name, '3.1.1');
  expect(next.build, 43);
});

สังเกตว่า nextPatch() เพิ่มทั้งสองเลข — เพราะการเพิ่มแค่ชื่อรุ่นไม่ทำให้ติดตั้งทับได้ ซึ่งเป็นข้อผิดพลาดที่เจอบ่อยมาก

2. ย้อนกลับไม่ได้ตรง ๆ และนี่คือส่วนที่สำคัญที่สุดของคำถามนี้

สิ่งที่ทำไม่ได้เพราะ
ติดตั้ง 3.1.0+42 ทับ 3.1.1+43เลข build น้อยกว่า Android ปฏิเสธ
สิ่งที่ทำได้วิธี
ปล่อยโค้ดเดิมด้วยเลขใหม่build จาก tag v3.1.0 แต่ตั้งเลขเป็น 3.1.2+44
ถอนแล้วติดตั้งใหม่ทำได้แต่ข้อมูลในเครื่องหายหมด รวมถึง profile เซิร์ฟเวอร์ (Part 10)
# ย้อนโค้ดแต่เดินเลขไปข้างหน้า
git checkout v3.1.0
flutter build apk --release --build-name=3.1.2 --build-number=44

สิ่งที่ต้องระวังคือชื่อรุ่น 3.1.2 ที่มีโค้ดของ 3.1.0 จะทำให้คนสับสนในภายหลัง จึงต้อง

  • ตั้ง tag ใน git ให้ตรงกับเลขที่ปล่อยจริงเสมอ
  • บันทึกไว้ในบันทึกการเปลี่ยนแปลงว่า 3.1.2 คือการย้อนกลับไป 3.1.0

บทเรียนที่ใหญ่กว่า: การย้อนกลับที่แพงขนาดนี้เป็นเหตุผลที่ต้องมี checklist ก่อนปล่อย (15.12) — เพราะการป้องกันถูกกว่าการย้อนมาก และในคลังที่มี PDA ยี่สิบเครื่อง การย้อนแปลว่าต้องเดินไปทุกเครื่อง

9. สรุป

  • ชื่อรุ่นบอกผู้ใช้ เลข build บอกระบบปฏิบัติการ
  • Android ตัดสินจากเลข build เท่านั้น และต้องเพิ่มขึ้นเสมอ
  • แสดงทั้งสองเลขในแอป เพื่อให้ผู้ใช้บอกได้ว่าใช้รุ่นไหน
  • ทำให้ลืมเพิ่มเลขไม่ได้ ด้วย CI หรือสคริปต์ที่ตรวจ
  • ส่งรุ่นไปกับคำขอ เพื่อให้รู้ว่ายังมีเครื่องใช้รุ่นเก่าอยู่ไหม
  • ย้อนรุ่นทำได้แค่การปล่อยโค้ดเดิมด้วยเลขใหม่
