1. Android บล็อก http โดยปริยาย

ตั้งแต่ Android 9 (API 28) การเรียก http:// ถูกบล็อก

SocketException: Cleartext HTTP traffic to 192.168.1.194 not permitted
ทำไมถึงบล็อก
ใครก็ตามที่อยู่ในเครือข่ายเดียวกัน อ่านทุกอย่างที่ส่งไปมาได้ รวมถึง token
แก้ไขข้อมูลระหว่างทางได้โดยที่ทั้งสองฝั่งไม่รู้
ปลอมเป็นเซิร์ฟเวอร์ได้

แต่เซิร์ฟเวอร์ WMS ในคลังส่วนใหญ่เป็น http เพราะอยู่ในเครือข่ายภายในและไม่มีใบรับรอง จึงต้องอนุญาต — คำถามคืออนุญาตแค่ไหน

2. สองวิธี

<!-- วิธีที่หนึ่ง — อนุญาตทั้งหมด -->
<application android:usesCleartextTraffic="true">
<!-- วิธีที่สอง — อนุญาตเฉพาะที่ระบุ -->
<application android:networkSecurityConfig="@xml/network_security_config">
<!-- android/app/src/main/res/xml/network_security_config.xml -->
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <!-- ค่าปริยาย: บล็อก http ทุกที่ -->
    <base-config cleartextTrafficPermitted="false" />

    <!-- ยกเว้นเซิร์ฟเวอร์ของคลังเท่านั้น -->
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="false">192.168.1.194</domain>
        <domain includeSubdomains="false">wms.acetec.local</domain>
    </domain-config>
</network-security-config>
usesCleartextTraffic="true"network security config
เขียนบรรทัดเดียวไฟล์เพิ่มหนึ่งไฟล์
ขอบเขตทุกที่อยู่เฉพาะที่ระบุ
ถ้ามีปลั๊กอินยิงไปที่อื่นยิงได้ถูกบล็อก
เมื่อผู้ใช้พิมพ์ที่อยู่ผิดยิงไปที่นั่นได้ถูกบล็อก

แถวสุดท้ายคือประโยชน์ที่ชัดที่สุดสำหรับแอปนี้ — Part 10 เปิดให้ผู้ใช้พิมพ์ที่อยู่เซิร์ฟเวอร์เอง ซึ่งแปลว่าแอปอาจถูกชี้ไปที่ไหนก็ได้

3. ปัญหาที่ตามมาจากการให้ผู้ใช้ตั้งค่าเอง

network security config ต้องระบุที่อยู่ตอน build แต่ Part 10 ออกแบบให้ผู้ใช้เพิ่ม profile ได้เอง สองอย่างนี้ขัดกัน

ทางเลือกผล
ระบุทุกที่อยู่ที่รู้ตอน buildปลอดภัยที่สุด แต่เพิ่มสาขาใหม่ต้อง build ใหม่
อนุญาตทั้งช่วง IP ภายในยืดหยุ่นพอควร และยังบล็อกที่อยู่ภายนอก
usesCleartextTraffic="true"ยืดหยุ่นที่สุด ไม่มีการจำกัด
Android ไม่รองรับการระบุช่วง IP ใน <domain> — ระบุได้ทีละที่อยู่หรือทีละโดเมนเท่านั้น ทางที่สองจึงทำได้เฉพาะเมื่อใช้ชื่อโดเมนภายในที่มี suffix ร่วมกัน
<!-- ใช้ได้ถ้าเซิร์ฟเวอร์ทุกสาขาอยู่ใต้โดเมนเดียวกัน -->
<domain includeSubdomains="true">acetec.local</domain>

ถ้าใช้ IP ล้วน ทางที่ทำได้จริงคืออนุญาตทั้งหมดแล้วชดเชยด้วยการตรวจฝั่งแอป

// จำกัดที่อยู่ที่ยอมรับ ตอนที่ผู้ใช้บันทึก profile (10.7)
String? _validateHost(String raw) {
  final host = raw.trim();
  ...
  // เครือข่ายภายในเท่านั้น — กันการชี้ไปเซิร์ฟเวอร์ภายนอกโดยไม่ตั้งใจ
  if (!_isPrivateAddress(host) && !host.endsWith('.local')) {
    return 'อนุญาตเฉพาะเซิร์ฟเวอร์ในเครือข่ายภายใน';
  }
  return null;
}

ต้องบอกตรง ๆ ว่านี่ไม่ใช่การป้องกัน — เป็นการช่วยไม่ให้ตั้งค่าผิด ตามหลักเดียวกับ 13.9 เพราะการตรวจฝั่งแอปเลี่ยงได้เสมอ

4. เทสต์ที่แยกสองระดับ

test('ไม่มีทั้ง cleartext และ network config ต้องขวางการปล่อย', () {
  final manifest = goodManifest.replaceAll(
    'android:networkSecurityConfig="@xml/network_security_config"', '',
  );

  final findings = checkAndroidManifest(manifest);
  expect(findings.any((f) => f.code == 'cleartext-blocked'), isTrue);
});

test('อนุญาต http ทั้งหมด ผ่านได้แต่ต้องเตือน', () {
  final manifest = goodManifest.replaceAll(
    'android:networkSecurityConfig="@xml/network_security_config"',
    'android:usesCleartextTraffic="true"',
  );

  final findings = checkAndroidManifest(manifest);
  expect(findings.any((f) => f.isBlocker), isFalse);
  expect(findings.single.code, 'cleartext-too-broad');
});

สองระดับนี้สะท้อนความจริง — การอนุญาตทั้งหมดทำงานได้ จึงไม่ควรขวางการปล่อย แต่ควรมีคนรู้ว่ามันกว้างกว่าที่จำเป็น

หลักเดียวกับ 13.9 — ห้ามเฉพาะสิ่งที่ผิดแน่นอน ที่น่าสงสัยให้เตือน

5. ถ้าย้ายไป https

ได้อะไรต้องทำอะไร
ไม่ต้องมี network security config เลยติดตั้งใบรับรองบนเซิร์ฟเวอร์
token ไม่ถูกอ่านระหว่างทางต่ออายุใบรับรองเมื่อหมดอายุ
ผ่านนโยบายขององค์กรที่เข้มงวด—

ปัญหาที่เจอบ่อยคือใบรับรองที่องค์กรออกเอง ซึ่งเครื่องไม่รู้จัก

HandshakeException: Handshake error in client

10.9 แยกข้อผิดพลาดนี้ออกมาแล้ว เพราะเป็นกรณีที่พบบ่อยและมีทางแก้ชัดเจน

<!-- ให้แอปเชื่อใบรับรองขององค์กรที่ฝังมากับแอป -->
<domain-config>
    <domain includeSubdomains="true">wms.acetec.local</domain>
    <trust-anchors>
        <certificates src="@raw/acetec_ca" />
        <certificates src="system" />
    </trust-anchors>
</domain-config>
อย่าปิดการตรวจใบรับรอง ด้วยการ override badCertificateCallback ให้คืน true เสมอ — วิธีนั้นทำให้ https ไม่ต่างจาก http เลย และแย่กว่าเพราะทุกคนคิดว่าปลอดภัย
// อย่าเขียนแบบนี้ในแอปที่ปล่อยจริง
HttpOverrides.global = _AcceptAnyCertificate();   // ← ปิดการป้องกันทั้งหมด

6. iOS

iOS มีกลไกคล้ายกันชื่อ App Transport Security

<!-- ios/Runner/Info.plist -->
<key>NSAppTransportSecurity</key>
<dict>
    <key>NSExceptionDomains</key>
    <dict>
        <key>wms.acetec.local</key>
        <dict>
            <key>NSExceptionAllowsInsecureHTTPLoads</key>
            <true/>
        </dict>
    </dict>
</dict>

โปรเจกต์นี้ลงเฉพาะ Android (11.12) จึงยังไม่ต้องทำ แต่ต้องรู้ว่ามีอยู่ เพราะถ้าวันหนึ่งต้องรองรับ iPad ในคลัง จะติดตรงนี้ทันที

Apple เข้มงวดกว่า — การใช้ NSAllowsArbitraryLoads ที่เปิดทั้งหมด ต้องอธิบายเหตุผลตอนส่งขึ้น App Store และมักถูกปฏิเสธ

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Cleartext HTTP traffic not permittedไม่ได้อนุญาต httpเพิ่ม network security config
ทำงานบน Android 8 แต่ไม่ทำงานบน 9 ขึ้นไปการบล็อกเริ่มที่ API 28เหมือนกัน
ระบุโดเมนแล้วยังถูกบล็อกระบุเป็น IP แต่แอปเรียกด้วยชื่อ หรือกลับกันระบุให้ตรงกับที่เรียกจริง
เพิ่มสาขาใหม่แล้วต้อง build ใหม่ระบุที่อยู่ตายตัวใน configใช้โดเมนที่มี suffix ร่วมกัน
HandshakeException กับ httpsใบรับรองที่องค์กรออกเองฝัง CA ไว้ใน trust-anchors
ปิดการตรวจใบรับรองเพื่อให้ผ่านรีบอย่าทำ — ฝัง CA แทน

8. แบบฝึกหัด

คลังมีเซิร์ฟเวอร์สามสาขา ทุกตัวเป็น http และใช้ IP ล้วน โดยที่ฝ่ายไอทีเปลี่ยน IP ได้ตลอด

  1. ควรตั้งค่าอย่างไร
  2. มีอะไรที่ควรเสนอฝ่ายไอทีไหม
แนวคำตอบ

1. ในสถานการณ์นี้ usesCleartextTraffic="true" เป็นทางที่ทำได้จริง เพราะ

ทางเลือกทำไมใช้ไม่ได้
ระบุ IP ทั้งสามใน configIP เปลี่ยนแล้วต้อง build ใหม่ทั้งสามสาขา
ระบุช่วง IPAndroid ไม่รองรับ
ใช้โดเมนยังไม่มี

แต่ต้องชดเชยด้วยสิ่งที่ทำได้ฝั่งแอป

  • ตรวจตอนบันทึก profile ว่าเป็นที่อยู่ในเครือข่ายภายใน (10.7)
  • ตรวจว่าปลายทางเป็น WMS จริงด้วย health payload ก่อนใช้ (10.9)
  • บันทึกว่าแอปกำลังคุยกับที่อยู่ไหน เพื่อให้ตามหาได้เมื่อมีปัญหา (7.17)

2. ควรเสนอสองอย่าง และข้อแรกแก้ปัญหาทั้งหมดในคำถามนี้

เสนอได้อะไร
ตั้งชื่อโดเมนภายในให้เซิร์ฟเวอร์ เช่น wms-bkk.acetec.localIP เปลี่ยนได้โดยแอปไม่ต้องรู้ และระบุใน config ด้วย suffix เดียวได้
ใบรับรองภายในสำหรับ httpsปิดช่องที่ token ถูกอ่านระหว่างทาง

ข้อแรกมีประโยชน์เกินเรื่องความปลอดภัย — มันแก้ปัญหาที่ Part 10 ทั้ง Part พยายามแก้ด้วย

ปัญหาจาก Part 10หายไปเมื่อมีโดเมน
เซิร์ฟเวอร์ย้ายเครื่อง IP เปลี่ยน (10.1)ผู้ใช้ไม่ต้องแก้อะไรเลย
ผู้ใช้พิมพ์ IP ผิดหนึ่งตัว (10.7)ชื่อผิดแล้วหาไม่เจอทันที ไม่ใช่ไปเจอเครื่องอื่น
เช้าวันจันทร์ต้องล็อกอินใหม่เพราะ DHCP เปลี่ยน IP (8.11)หายไป

วิธีเสนอที่ได้ผล — อย่าเสนอเป็นเรื่องความปลอดภัย เพราะฝ่ายไอทีจะมองว่าเป็นงานเพิ่ม ให้เสนอเป็นการแก้ปัญหาที่เขาเจออยู่แล้ว

"ตอนนี้ทุกครั้งที่เซิร์ฟเวอร์เปลี่ยน IP ต้องเดินไปตั้งค่า PDA ทีละเครื่อง
ถ้ามีชื่อโดเมนภายใน จะแก้ที่ DNS ที่เดียวแล้วทุกเครื่องตามทันที"

นี่เป็นตัวอย่างของหลักที่ใช้ได้ทั่วไป — ข้อเสนอทางเทคนิคที่ผูกกับปัญหาที่อีกฝ่ายเจออยู่ มีโอกาสได้รับการอนุมัติมากกว่าข้อเสนอที่ผูกกับความถูกต้องทางทฤษฎี

9. สรุป

  • Android บล็อก http ตั้งแต่ API 28
  • network security config จำกัดได้เฉพาะที่ระบุ ดีกว่าอนุญาตทั้งหมด
  • Android ไม่รองรับช่วง IP ระบุได้ทีละที่อยู่หรือทีละโดเมน
  • การตรวจฝั่งแอปเป็นการช่วย ไม่ใช่การป้องกัน
  • อย่าปิดการตรวจใบรับรอง ให้ฝัง CA แทน
  • โดเมนภายในแก้ปัญหาหลายอย่างพร้อมกัน รวมถึงที่ Part 10 เจอ

บทหน้า: ใบรับรองและกุญแจที่ใช้เซ็นแอป
