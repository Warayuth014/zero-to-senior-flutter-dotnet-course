29-09 · State & Lifecycle

Transactional outbox และ atomic optimistic update

Part 29: SQLite, Drift & Offline-first Sync

Transactional outbox: local entity change และ command ที่ต้องส่ง server ต้อง commit ใน transaction เดียว ไม่เช่นนั้น crash ตรงกลางจะสร้าง state ที่กู้ไม่ได้

1. Dual-write failure

ถ้าซ่อน task แล้ว app ตายก่อนเขียน queue งานจะหายจากจอแต่ไม่มี command; ถ้าเขียน queue ก่อนแล้วซ่อนไม่สำเร็จผู้ใช้อาจกดซ้ำ

2. Atomic enqueue

enqueueComplete insert PendingCommands และ update CachedTasks.hiddenByCommand ภายใน Drift transaction เดียว

3. Command envelope

เก็บ stable ID, kind, entity ID, versioned payload, actor/tenant และเวลาสร้าง สิ่งที่ sync ต้องการต้องอยู่ durable ไม่พึ่ง session memory

4. Ordering

lab replay ตาม createdAt แต่ระบบจริงอาจต้อง order ต่อ entity/aggregate และอนุญาต parallel ข้าม entity เพื่อไม่ให้ command ช้าบล็อกทั้ง queue

5. Acknowledge

หลัง server ยืนยันจึง transaction ลบ command และปรับ/delete local projection ถ้า app ตายก่อน acknowledge การ replay ต้องปลอดภัยด้วย idempotency

6. Inbox alternative

ถ้ารับ server events ซ้ำ ให้มี inbox/event ID deduplication ฝั่ง clientเช่นกัน Outbox แก้ outgoing intent ไม่ได้แก้ inbound duplicate ทั้งหมด

7. Audit

command history สำคัญอาจย้ายไป audit table แทนลบทันที พร้อม retention/PII policy ไม่ใช้ debug log เป็นหลักฐานเดียว

8. Test

test ต้องอ่านทั้ง visible tasks และ pending commands หลัง enqueue เพื่อพิสูจน์สองผลลัพธ์ของ transaction ไม่ใช่ตรวจ UI อย่างเดียว
