Migration เป็น production code: ผู้ใช้เปิด appใหม่บนฐานข้อมูลเก่าหลายเวอร์ชัน การสร้างฐานใหม่ผ่านไม่ได้พิสูจน์ upgrade path

1. schemaVersion

เพิ่ม version เมื่อ schemaเปลี่ยนและเขียน stepจาก oldVersion ไป newVersion ห้ามลดเลขหรือแก้ migrationที่ releaseไปแล้ว

2. Additive change

เพิ่ม nullable/default columnง่ายกว่า rename/drop การเพิ่ม NOT NULLให้ tableมีข้อมูลต้องกำหนด backfillที่ deterministic

3. Rename/drop

SQLite version/platformต่างกันอาจต้องสร้าง tableใหม่, copy/transformข้อมูล, dropเก่าและ rename ภายใน transaction

4. Data migration

แยก schema changeจาก network sync อย่าให้ migrationต้อง online เพราะ appจะเปิดไม่ได้เมื่อ APIล่ม

5. Tests

เก็บ schema snapshotของ releaseก่อน สร้าง DBเก่าใส่ fixture เปิดด้วย codeใหม่แล้วตรวจ row, constraint, indexและ queryสำคัญ

6. Downgrade

mobile rollbackอาจเปิด DBใหม่ด้วย binaryเก่าไม่ได้ วาง compatibility window, feature flag หรือ forward-fix strategyก่อน rollout

7. Backup/recovery

cacheที่ rebuildได้อาจ safe reset แต่ outboxที่ยังไม่ส่งห้ามลบทิ้งเงียบ ๆ แยก recovery policyตามคุณค่าข้อมูล

8. Checkpoint

ก่อน release ต้อง test fresh install, upgradeจากทุก supported version, interrupted migration และฐานข้อมูลมี pending outbox
