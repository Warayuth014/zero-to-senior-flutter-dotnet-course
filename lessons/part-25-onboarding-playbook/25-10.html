Performance rule: วัด profile buildบน device/viewportจริงก่อน optimize แยก CPU/layout/build/network/memory/battery ไม่ตีความ “ไฟล์ใหญ่”ว่า runtimeช้าโดยตรง

1. Establish scenario

กำหนด cold start, list 1,000 rows, typing search, scan→result, open dialog, SignalR burstหรือ 8-hour shift เก็บ device/build mode/data sizeและ frame/network timingเพื่อเทียบหลังแก้

2. Rebuild diagnosis

ใช้ DevTools/rebuild trackingตรวจ widgetที่ rebuildและ cost WarehouseStore notifyกว้างอาจ rebuild shellหลายส่วน; split listeners/selectorsหรือ feature storesเมื่อ measurementชี้ ไม่ละ notification

3. List/layout

ใช้ builder/sliver, stable keys, bounded scroll owner, avoid intrinsic layoutใน rowsจำนวนมากและลด nested unbounded lists Text overflow/text scale/PDA keyboardต้องยังถูกหลัง optimization

4. Parsing/images

JSON/image decode/resizeหนักย้ายออก UI isolateตาม measurement, paginate data, cache thumbnailมี boundsและ dispose image resources ไม่สร้าง isolateสำหรับ payloadเล็กจน overheadมากกว่า

5. Network efficiency

แก้ N+1 sequential detailsด้วย batch/bounded concurrency, debounce search, coalesce refresh, pollตาม screen/lifecycleและ SignalR reconcileแทน reloadทุก event ระวัง cache staleใน mutation flows

6. Memory/lifecycle

ตรวจ controllers/listeners/timers/subscriptions, storesค้างหลัง logout, unbounded histories/imagesและ singleton callbacks DevTools heap snapshotก่อน/หลัง repeated navigationช่วยแยก leakจาก cacheที่ตั้งใจ

7. Battery/radio

all-day handheldไม่ควร health pollตลอด, task polling pause backgroundและ reconnect backoff มี metrics network wakeups/requestsต่อชั่วโมง ไม่ optimize frameอย่างเดียวแล้วกินแบต

8. Performance budget

กำหนด p95 action latency, frame jank, startup, memory, requests/minและbattery proxyต่อ device class พร้อม benchmark regressionใน PRที่แตะ hotspotsและยืนยัน correctness testsยังผ่าน
