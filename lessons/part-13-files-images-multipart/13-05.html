1. เซิร์ฟเวอร์คืนอะไรมา

200 OK
{"url": "/uploads/parts/P-100-20260821.jpg"}

สิ่งที่ได้คือเส้นทางสัมพัทธ์ ไม่ใช่ URL เต็ม ซึ่งเป็นการออกแบบที่ถูกต้อง

เก็บเส้นทางสัมพัทธ์เก็บ URL เต็ม
ย้ายเซิร์ฟเวอร์รูปยังใช้ได้รูปทั้งหมดเสีย
ผู้ใช้สลับ profile (10.6)ชี้ตามเซิร์ฟเวอร์ที่ใช้อยู่ชี้ไปเครื่องเก่า
เปลี่ยนจาก HTTP เป็น HTTPSไม่ต้องแก้ข้อมูลต้องแก้ทุกแถวในฐานข้อมูล
อยู่หลัง reverse proxyถูกต้องอัตโนมัติต้องรู้ที่อยู่ภายนอกตั้งแต่ตอนบันทึก
/// เส้นทางที่เซิร์ฟเวอร์คืนมา อาจเป็นเส้นทางสัมพัทธ์ เช่น `/uploads/a.jpg`
///
/// เก็บตามที่ได้รับ ไม่ต่อ base URL ให้ตรงนี้ — เพราะ base URL เปลี่ยนได้
/// เมื่อผู้ใช้สลับเซิร์ฟเวอร์ (10.6) ถ้าเก็บ URL เต็มไว้ วันที่สลับแล้ว
/// รูปจะชี้ไปเครื่องเก่า
final String url;

2. รับได้หลายชื่อคีย์

ทีมหลังบ้านแต่ละคนตั้งชื่อคีย์ไม่เหมือนกัน และมักไม่ตรงกันระหว่าง endpoint

String? _readUrl(String body) {
  final json = _tryDecode(body);
  if (json == null) return null;
  for (final key in ['url', 'imageUrl', 'path', 'location']) {
    final value = json[key];
    if (value is String && value.trim().isNotEmpty) return value.trim();
  }
  return null;
}

เป็นการผ่อนปรนแบบเดียวกับ 6.6 ที่รองรับทั้ง camelCase และ PascalCase — และมีข้อควรระวังเดียวกัน คือเป็นทางผ่าน ไม่ใช่ปลายทาง ควรตกลงชื่อเดียวกับทีมหลังบ้านให้ได้

test('อ่านที่อยู่ไฟล์จากชื่อคีย์ที่เซิร์ฟเวอร์อาจใช้', () async {
  for (final key in ['url', 'imageUrl', 'path', 'location']) {
    ...
    expect(outcome, isA<UploadSucceeded>(), reason: 'คีย์ $key');
  }
});

3. 200 ที่ไม่บอกที่อยู่

if (code >= 200 && code < 300) {
  final url = _readUrl(response.body);
  if (url == null) {
    // ตอบ 200 แต่ไม่บอกที่อยู่ไฟล์ — เราเก็บอะไรไว้แสดงไม่ได้เลย
    return const UploadFailed(
      ApiFailureKind.contract,
      'เซิร์ฟเวอร์รับไฟล์แล้วแต่ไม่ได้บอกที่อยู่',
    );
  }
  return UploadSucceeded(url);
}

เป็นกรณีที่น่าอึดอัด — เซิร์ฟเวอร์รับไฟล์ไปแล้วจริง แต่แอปใช้ประโยชน์ไม่ได้ ถือว่าสำเร็จก็ไม่ได้เพราะไม่มีอะไรจะเก็บ ถือว่าล้มเหลวก็ไม่ตรงเพราะไฟล์ขึ้นไปแล้ว

ทางเลือกผล
ถือว่าสำเร็จ แล้วเก็บ nullหน้าจอจะแสดงว่ามีรูปแต่โหลดไม่ขึ้น ผู้ใช้จะกดส่งใหม่เรื่อย ๆ
ถือว่าผิดสัญญาทีมเห็นปัญหาและแก้ได้ ส่วนผู้ใช้เห็นข้อความที่ตรงกับความจริง
โหลดข้อมูลใหม่แล้วดูว่ามีรูปไหมถูกที่สุด แต่ต้องมี endpoint ที่ตอบได้

lab เลือกทางที่สอง เพราะเป็นสัญญาที่ถูกละเมิดและมีคนแก้ได้ ตามหลักใน 9.13 — แต่ถ้าเกิดบ่อย ทางที่สามคือคำตอบที่ดีกว่า

4. ประกอบ URL เต็มตอนจะแสดง

// wmsapp
Future<String> getImageFullUrl(String relativePath) async {
  final base = await ApiService._resolveBase();
  final serverBase = base.replaceAll('/api', '');
  return '$serverBase$relativePath';
}

ทำงานได้ แต่มีสองจุดที่เปราะ

จุดปัญหา
replaceAll('/api', '')แทนที่ทุกที่ที่เจอ ไม่ใช่แค่ท้าย — ถ้าเซิร์ฟเวอร์อยู่ที่ http://api-server/api จะได้ http://-server
เป็น asyncทำให้ต้องใช้ FutureBuilder ตอนแสดง ซึ่งเปิดกับดักที่ 13.6 จะพูดถึง

ทางที่ปลอดภัยกว่าคือใช้ Uri แทนการจัดการสตริง

String imageUrl(String relativePath) {
  // resolve จัดการทับซ้อนและเส้นทางสัมพัทธ์ให้ถูกตามมาตรฐาน
  return Uri.parse(AppConfig.apiBaseUrl).resolve(relativePath).toString();
}
ค่าที่ได้รับresolve ให้ผลเป็น
/uploads/a.jpghttp://host:6191/uploads/a.jpg
uploads/a.jpgต่อจากเส้นทางปัจจุบัน
http://cdn.example/a.jpgใช้ตามที่ให้มาเลย เพราะเป็น URL เต็มอยู่แล้ว

แถวสุดท้ายมีค่ามาก — วันที่ทีมย้ายรูปไปเก็บที่อื่น เซิร์ฟเวอร์จะเริ่มคืน URL เต็มมา และโค้ดนี้จะยังทำงานถูกโดยไม่ต้องแก้

5. ทำให้เป็น sync ได้ด้วยงานจาก Part 10

เหตุผลที่ getImageFullUrl เป็น async คือ _resolveBase() ต้องลองต่อ socket (10.2) แต่ wms_absolute_mobile แก้ปัญหานี้ไปแล้ว

/// `ApiClient` calls this getter on every request rather than caching it, so
/// switching profiles redirects the whole app immediately
static String get apiBaseUrl =>
    resolveBaseUrl(ConnectionController.instance.activeBaseUrl);

เป็น getter ธรรมดา ไม่ใช่ Future เพราะค่าถูกโหลดเสร็จตั้งแต่ก่อน runApp แล้ว (11.13)

ได้อะไรจากการเป็น sync
ไม่ต้องใช้ FutureBuilder ตอนแสดงรูป
ไม่มีกระพริบตอนวาดใหม่ (13.6)
ยังสลับเซิร์ฟเวอร์ได้ทันที เพราะอ่านค่าใหม่ทุกครั้งที่เรียก
นี่คือตัวอย่างที่ชัดว่าการตัดสินใจใน Part หนึ่งไปแก้ปัญหาในอีก Part หนึ่ง — การทำให้ base URL อ่านได้แบบ sync ตอนออกแบบระบบ profile ทำให้การแสดงรูปง่ายขึ้นโดยไม่ได้ตั้งใจ

6. เก็บที่ไหน

เก็บที่เหมาะกับ
ฐานข้อมูลฝั่งเซิร์ฟเวอร์ที่ที่ถูกต้อง — รูปเป็นของข้อมูล ไม่ใช่ของเครื่อง
store ในหน่วยความจำระหว่างที่ยังอยู่ในจอนั้น
ที่เก็บในเครื่องเฉพาะตอนที่ยังส่งไม่ได้ (Part 29)

สิ่งที่ต้องระวังคือ อย่าเก็บที่อยู่รูปไว้ในเครื่องเป็นแหล่งความจริง — เมื่อผู้ใช้คนถัดไปมาใช้เครื่องเดียวกัน เขาควรเห็นสิ่งที่เซิร์ฟเวอร์บอก ไม่ใช่สิ่งที่ค้างอยู่จากคนก่อน (8.8)

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
สลับเซิร์ฟเวอร์แล้วรูปหายเก็บ URL เต็มเก็บเส้นทางสัมพัทธ์
URL มีทับซ้อนต่อสตริงเองใช้ Uri.resolve
host หายไปบางส่วนreplaceAll แทนที่ทุกที่ที่เจอตัดเฉพาะท้าย หรือใช้ Uri
อัปโหลดสำเร็จแต่รูปไม่ขึ้นเซิร์ฟเวอร์ไม่ได้คืนที่อยู่ถือว่าผิดสัญญา อย่าเก็บ null
ผู้ใช้คนใหม่เห็นรูปของคนก่อนเก็บที่อยู่ไว้ในเครื่องล้างพร้อมออกจากระบบ

8. แบบฝึกหัด

รูปในระบบเป็นข้อมูลที่ไม่ควรให้คนนอกเห็น แต่ตอนนี้ใครก็เปิด http://server/uploads/P-100.jpg ได้ถ้ารู้ที่อยู่

  1. เป็นปัญหาไหม
  2. จะแก้อย่างไร และกระทบฝั่งแอปอย่างไร
แนวคำตอบ

1. ขึ้นกับว่าที่อยู่เดาได้ง่ายแค่ไหน และเนื้อหาอ่อนไหวแค่ไหน

สถานการณ์ความเสี่ยง
ชื่อไฟล์เดาได้ เช่น P-100.jpgสูง — ไล่รหัสสินค้าก็ได้รูปทั้งคลัง
ชื่อไฟล์สุ่มยาวต่ำลง แต่ยังไม่ใช่การป้องกัน
รูปสินค้าทั่วไปไม่ค่อยอ่อนไหว
รูปหลักฐานความเสียหายที่มีเอกสารติดมาอ่อนไหวมาก

สังเกตว่าชื่อไฟล์สุ่มไม่ใช่การป้องกัน แต่เป็นการทำให้เดายาก — ซึ่งพอสำหรับบางกรณีแต่ไม่ใช่ทุกกรณี หลักเดียวกับ 8.9 ที่ว่าการซ่อนไม่เท่ากับการป้องกัน

2. สองทางหลัก

ทางฝั่งแอปต้องทำอะไร
เสิร์ฟรูปผ่าน endpoint ที่ตรวจ tokenต้องส่ง token ไปกับคำขอรูปด้วย ซึ่ง Image.network ธรรมดาทำไม่ได้
ให้ URL ที่มีอายุจำกัดต้องขอ URL ใหม่เมื่อหมดอายุ

ทางแรกทำได้ด้วยการส่ง header

Image.network(
  url,
  headers: {'Authorization': 'Bearer ${session.token}'},
)

แต่มีข้อจำกัดที่ต้องรู้ — บนเว็บ headers ของ Image.network ไม่ทำงาน เพราะเบราว์เซอร์โหลดรูปผ่านแท็ก img ที่แนบ header เองไม่ได้ ถ้าต้องรองรับเว็บด้วย ต้องโหลดเป็นไบต์เองแล้วใช้ Image.memory

ทางที่สองหลีกเลี่ยงปัญหานี้ทั้งหมด และเป็นทางที่ระบบเก็บไฟล์บนคลาวด์ใช้กัน — เซิร์ฟเวอร์คืน URL ที่มีลายเซ็นและหมดอายุใน 15 นาที ฝั่งแอปใช้ Image.network ธรรมดาได้เลย

สิ่งที่ควรทำก่อนทั้งสองทาง: ถามว่ารูปเหล่านี้อ่อนไหวจริงไหม เพราะถ้าเป็นรูปสินค้าทั่วไปที่ลูกค้าเห็นได้อยู่แล้วในเว็บขายของ การลงแรงป้องกันคือการจ่ายโดยไม่ได้อะไร — และแรงนั้นเอาไปทำเรื่องที่สำคัญกว่าได้

9. สรุป

  • เก็บเส้นทางสัมพัทธ์ที่เซิร์ฟเวอร์คืนมา ไม่ใช่ URL เต็ม
  • ประกอบ URL ตอนจะแสดง ด้วย Uri.resolve ไม่ใช่ต่อสตริง
  • 200 ที่ไม่บอกที่อยู่ ถือว่าผิดสัญญา อย่าเก็บ null
  • base URL ที่อ่านได้แบบ sync ทำให้การแสดงรูปง่ายขึ้นมาก
  • ชื่อไฟล์ที่เดายากไม่ใช่การป้องกัน

บทหน้า: แสดงรูปย่อในลิสต์ และกับดักที่อยู่ในโค้ดจริง
