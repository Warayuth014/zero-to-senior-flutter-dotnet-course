1. คำนวณ decoded memory

width × height × 4 bytes
4000 × 3000 × 4 ≈ 48,000,000 bytes

หลาย thumbnail ที่ decode เต็มขนาดสามารถทำให้ PDA memory ต่ำกระตุกหรือถูก kill แม้ไฟล์บน disk เล็ก

2. ลดตั้งแต่ picker

wmsapp ใช้ maxWidth: 1024, maxHeight: 1024, imageQuality: 85 เป็น baseline ที่ดี แต่ต้องกำหนดตามงาน: รูป part สำหรับดูบนจอไม่ต้องเท่ากล้อง 12 MP ส่วน barcode/ตัวอักษรเล็กต้องรักษาความคมมากกว่า

3. Decode ตามขนาดแสดงผล

Image.network(
  url,
  width: 96,
  height: 96,
  cacheWidth: 192,
  cacheHeight: 192,
  fit: BoxFit.cover,
)

width/height เป็น layout ส่วน cacheWidth/cacheHeight บอก decoder ลด bitmap ควรคูณ devicePixelRatio ให้พอคม ไม่ส่งค่าขนาดเต็มต้นฉบับ

4. ImageCache

Flutter มี in-memory image cache; key มักมาจาก URL + scale การเปลี่ยน query version ทำให้เป็นคนละ entry ตั้ง cache budget ให้เหมาะกับอุปกรณ์และอย่าเรียก clear() ทั้งระบบเพื่อแก้รูปเดียว เพราะทำให้ทุกหน้าต้อง decode ใหม่

5. Resize กับ compression

resize ลดจำนวนพิกเซล ส่วน quality ลดรายละเอียดการบีบอัด เป็นคนละแกน ทำทั้งสองก่อน upload และตรวจผลลัพธ์อีกครั้ง ถ้าต้องรักษา PNG transparency อย่าแปลง JPEG โดยไม่ตั้งใจ; ภาพถ่ายมักเหมาะ JPEG/WebP ตามที่ backend รองรับ

6. Orientation และ metadata

กล้องบางเครื่องเก็บการหมุนใน EXIF เมื่อ resize ต้อง library ที่ normalize orientation มิฉะนั้น server/thumbnail อาจแสดงรูปตะแคง พิจารณาลบ GPS/EXIF ที่ไม่จำเป็นเพื่อความเป็นส่วนตัว และเก็บเฉพาะ metadata ทางธุรกิจใน DB

7. อย่าถือ bytes หลายสำเนา

หลัง preview/upload เสร็จให้ปล่อย reference ขนาดใหญ่, dispose controller/subscription และใช้ stream สำหรับไฟล์ใหญ่ หลีกเลี่ยงลำดับ read bytes → copy resize → copy multipart พร้อมกัน ถ้าจำเป็นให้ทำงานหนักนอก UI isolate และวัดจริง

8. Performance check

วัด peak memory, jank และเวลา decode บน PDA จริงด้วยรายการ 100 รูป ทดสอบ scroll ไปกลับ, รูป 12 MP, orientation หลายแบบ, low-memory/background และตรวจว่า thumbnail ไม่ decode ขนาดต้นฉบับ
