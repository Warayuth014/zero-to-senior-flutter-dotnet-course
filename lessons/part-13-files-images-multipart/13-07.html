1. เลขที่ต้องรู้

รูปที่ถูกวาดบนหน้าจอ ต้องถูกคลายการบีบอัดเป็นพิกเซลก่อน และพิกเซลหนึ่งกิน 4 ไบต์

หน่วยความจำ = กว้าง × สูง × 4 ไบต์
รูปขนาดไฟล์หน่วยความจำตอนแสดง
1024×1024 JPEGราว 300 KB4 MB
4000×3000 JPEGราว 5 MB48 MB
56×56 ที่แสดงจริง—12 KB
ขนาดไฟล์กับหน่วยความจำไม่เกี่ยวกันเลย — JPEG ที่บีบอัดได้ดีมีไฟล์เล็กแต่คลายออกมาเท่าเดิม สิ่งที่กำหนดหน่วยความจำคือจำนวนพิกเซล ไม่ใช่ความสามารถในการบีบอัด

2. ลิสต์ที่มีรูปย่อ

ในจอจริงของ wmsapp รูปย่อแสดงที่ 56×56 แต่ไฟล์ที่อัปโหลดไปคือ 1024×1024

Container(
  width: 56,
  height: 56,
  child: Image.network(snap.data!, fit: BoxFit.cover, ...),
)
จำนวนรูปในจอหน่วยความจำที่กินที่จำเป็นจริง
14 MB12 KB
10 ใบที่เลื่อนผ่าน40 MB120 KB
50 ใบ (แคชเต็ม)200 MB600 KB

บน PDA ที่มีแรม 2 GB และระบบปฏิบัติการกินไปแล้วครึ่งหนึ่ง 200 MB คือจุดที่แอปเริ่มถูกระบบปิดตอนสลับไปแอปอื่นแล้วกลับมา

3. บรรทัดเดียวที่แก้ได้

Image.network(
  url,
  width: 56,
  height: 56,
  fit: BoxFit.cover,
  // บอกให้คลายการบีบอัดที่ขนาดนี้ ไม่ใช่ขนาดเต็ม
  cacheWidth: 112,      // 56 × devicePixelRatio ของเครื่องเป้าหมาย
  cacheHeight: 112,
)
ไม่มี cacheWidthมี
พิกเซลที่เก็บ1024×1024112×112
หน่วยความจำต่อใบ4 MB50 KB
50 ใบ200 MB2.5 MB

ลดลง 80 เท่า จากการเขียนเพิ่มสองบรรทัด

ทำไมคูณ devicePixelRatio — width: 56 เป็นหน่วยอิสระจากพิกเซล (11.11) บนจอ 2x จะกินพื้นที่จริง 112 พิกเซล ถ้าตั้ง cacheWidth: 56 รูปจะเบลอเพราะถูกขยายขึ้น
// คำนวณจากเครื่องจริง แทนที่จะเดา
final ratio = MediaQuery.devicePixelRatioOf(context);
Image.network(url, cacheWidth: (56 * ratio).round(), ...)

4. แคชรูปของ Flutter

Flutter มีแคชในหน่วยความจำให้อยู่แล้ว ชื่อ ImageCache

คุณสมบัติค่าปริยาย
จำนวนรูปสูงสุด1000 ใบ
ขนาดรวมสูงสุด100 MB
วิธีทิ้งทิ้งตัวที่ไม่ได้ใช้นานที่สุดก่อน
อยู่ได้นานแค่ไหนจนกว่าจะปิดแอป — ไม่เก็บลงดิสก์

แถวสุดท้ายสำคัญ — ปิดแอปแล้วเปิดใหม่ รูปทุกใบต้องโหลดจากเน็ตอีกครั้ง ซึ่งบนคลังที่เน็ตช้าแปลว่ารอทุกเช้า

// ปรับขนาดแคชได้ตามเครื่อง — PDA ที่แรมน้อยควรลดลง
PaintingBinding.instance.imageCache.maximumSizeBytes = 30 << 20;   // 30 MB

และล้างได้เมื่อจำเป็น

// เช่นตอนออกจากระบบ — รูปของผู้ใช้คนเก่าไม่ควรค้างอยู่ (8.8)
PaintingBinding.instance.imageCache.clear();
PaintingBinding.instance.imageCache.clearLiveImages();

5. แคชลงดิสก์

ถ้าอยากให้รูปอยู่ข้ามการปิดแอป ต้องใช้แพ็กเกจเพิ่ม

dependencies:
  cached_network_image: ^3.4.1
CachedNetworkImage(
  imageUrl: url,
  width: 56,
  height: 56,
  memCacheWidth: 112,
  fit: BoxFit.cover,
  placeholder: (_, _) => const ColoredBox(color: PdaColors.surfaceMuted),
  errorWidget: (_, _, _) => const Icon(Icons.broken_image),
)
ได้เสีย
เปิดแอปใหม่แล้วรูปขึ้นทันทีกินพื้นที่ในเครื่อง ต้องตั้งขีดจำกัด
ทำงานได้ตอนเน็ตหลุดรูปที่เปลี่ยนบนเซิร์ฟเวอร์อาจยังแสดงของเก่า
ประหยัดเน็ตมากแพ็กเกจเพิ่มอีกตัวที่ต้องดูแล

แถวที่สองแก้ด้วยการให้ URL เปลี่ยนเมื่อรูปเปลี่ยน

// ชื่อไฟล์มีรหัสคำสั่งอยู่แล้ว (13.4) รูปใหม่จึงได้ URL ใหม่เสมอ
'/uploads/P-100-upload-1755771234567.jpg'

วิธีนี้ดีกว่าการใส่ตัวเลขต่อท้ายแบบ ?v=2 เพราะไฟล์เก่ายังอยู่ ทำให้ย้อนดูได้ และแคชไม่ต้องเดาว่าอะไรเปลี่ยน

6. ตัวอย่างรูปก่อนอัปโหลด

// รูปที่เพิ่งเลือก อยู่ในหน่วยความจำแล้ว (13.2)
Image.memory(
  store.image!.bytes,
  width: 200,
  height: 200,
  fit: BoxFit.cover,
  cacheWidth: 400,     // ยังต้องใส่ แม้จะเป็นไบต์ในหน่วยความจำ
)

cacheWidth ยังจำเป็นเพราะไบต์ที่เก็บไว้เป็นข้อมูลที่บีบอัดแล้ว การวาดยังต้องคลายออกเป็นพิกเซลอยู่ดี — รูป 1024×1024 ที่แสดงที่ 200×200 ก็ยังกิน 4 MB ถ้าไม่บอก

ตอนแสดงตัวอย่างจะกินหน่วยความจำสองก้อน คือไบต์ที่บีบอัด (300 KB) กับพิกเซลที่คลายแล้ว — ซึ่งยอมรับได้เพราะมีรูปเดียว แต่ถ้าให้เลือกได้สิบใบพร้อมกัน ต้องคิดใหม่

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
แอปถูกปิดตอนสลับกลับมาแคชรูปเต็มจนระบบเลือกแอปนี้ไปปิดcacheWidth และลดขนาดแคช
เลื่อนลิสต์แล้วกระตุกคลายรูปใหญ่ตอนเลื่อนcacheWidth
รูปเบลอหลังใส่ cacheWidthไม่ได้คูณ devicePixelRatioคูณ
เปิดแอปใหม่แล้วรอรูปทุกครั้งแคชอยู่ในหน่วยความจำเท่านั้นcached_network_image
แก้รูปบนเซิร์ฟเวอร์แล้วยังเห็นของเก่าแคชลงดิสก์ให้ URL เปลี่ยนเมื่อรูปเปลี่ยน
ผู้ใช้คนใหม่เห็นรูปของคนก่อนไม่ได้ล้างแคชตอนออกจากระบบimageCache.clear()

8. แบบฝึกหัด

หน้าจอ “ประวัติการรับของ” แสดงรายการ 200 แถว แต่ละแถวมีรูปย่อ ผู้ใช้บ่นว่าเลื่อนแล้วกระตุกและบางครั้งแอปปิดเอง

  1. ตรวจอะไรก่อน
  2. แก้อย่างไร
แนวคำตอบ

1. วัดก่อนเดา ตามหลักเดียวกับ 12.11

ตรวจด้วย
หน่วยความจำที่แคชรูปใช้PaintingBinding.instance.imageCache.currentSizeBytes
ขนาดจริงของรูปที่โหลดมาDevTools แท็บ Memory ดู _Int32List ของภาพ
เฟรมที่ใช้เวลานานDevTools แท็บ Performance
ลิสต์สร้าง widget กี่ตัวใส่ debugPrint ใน itemBuilder

2. แก้เรียงตามผลที่ได้ต่อแรงที่ลง

ทำได้อะไร
ขอรูปย่อจากเซิร์ฟเวอร์มากที่สุด — ไม่ต้องดาวน์โหลด 300 KB มาแสดงที่ 56×56
cacheWidthลดหน่วยความจำ 80 เท่า
จองพื้นที่ให้รูปด้วยขนาดตายตัวลิสต์ไม่กระตุกตอนรูปโหลดเสร็จ (11.11)
แบ่งหน้าแทนที่จะโหลด 200 แถวรวดลดทั้งเน็ตและหน่วยความจำ

แถวแรกสำคัญที่สุดและต้องคุยกับทีมหลังบ้าน — endpoint ที่คืนรูปย่อ 128×128 ทำให้ทุกอย่างที่เหลือแทบไม่จำเป็น

GET /uploads/parts/P-100.jpg?w=128     ← เซิร์ฟเวอร์ย่อให้

แต่คำถามที่ควรถามก่อนทั้งหมดนี้: ผู้ใช้ต้องเห็นรูปในลิสต์ประวัติจริงหรือ

ประวัติการรับของคือรายการที่คนเปิดดูเพื่อหาว่า “ของล็อตนั้นรับเข้าเมื่อไหร่” ซึ่งตอบได้ด้วยข้อความล้วน ส่วนรูปมีประโยชน์ตอนเปิดดูรายละเอียดของแถวใดแถวหนึ่ง

ถ้าเอารูปออกจากลิสต์ ปัญหาหายทั้งหมดโดยไม่ต้องเขียนโค้ดเพิ่มแม้แต่บรรทัดเดียว และหน้าจอยังอ่านง่ายขึ้นด้วย — ทางแก้ที่ดีที่สุดของปัญหาประสิทธิภาพ บ่อยครั้งคือการไม่ทำสิ่งนั้น

ถ้าทีมยืนยันว่าต้องมี ให้ถามว่าผู้ใช้ใช้รูปนั้นตัดสินใจอะไร แล้วออกแบบจากคำตอบนั้น — เหมือนที่ 11.11 สรุปไว้

9. สรุป

  • หน่วยความจำ = กว้าง × สูง × 4 ไม่เกี่ยวกับขนาดไฟล์
  • cacheWidth ลดได้หลายสิบเท่าจากการเขียนสองบรรทัด
  • คูณ devicePixelRatio ไม่งั้นรูปเบลอ
  • แคชของ Flutter อยู่ในหน่วยความจำเท่านั้น ปิดแอปแล้วหาย
  • ให้ URL เปลี่ยนเมื่อรูปเปลี่ยน จะได้ไม่ต้องสู้กับแคช
  • ทางแก้ที่ดีที่สุด บ่อยครั้งคือขอรูปย่อจากเซิร์ฟเวอร์ หรือไม่แสดงรูปตรงนั้นเลย
