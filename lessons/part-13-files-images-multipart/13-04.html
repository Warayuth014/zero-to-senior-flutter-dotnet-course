หนึ่ง request หนึ่ง intent: fields อธิบายว่าไฟล์เป็นของ entity ใด ส่วน file คือ payload ทั้งสองส่วนต้องผ่าน authorization และ validation ร่วมกัน

1. Contract ของ Part image

POST /api/upload/part-image
Content-Type: multipart/form-data

partId = P-1001
file   = warehouse-part.jpg

wmsapp ส่ง fields: {'partId': partId} และ file part ชื่อ file ถ้าฝั่ง .NET เปลี่ยนชื่อ parameter ต้อง version contract หรือแก้ client พร้อมกัน

2. ฝั่ง Flutter

request.fields.addAll({
  'partId': partId.trim(),
  'uploadId': uploadId,
});
request.files.add(await http.MultipartFile.fromPath(
  'file', image.path, filename: image.name,
));

แปลงค่าที่ไม่ใช่ string อย่าง timestamp/number ให้เป็นรูปแบบ invariant ที่ตกลงกัน ไม่ส่ง JSON string ซ้อนใน field ถ้า model ซับซ้อนโดยไม่มี schema ชัดเจน

3. Binding ใน Minimal API

app.MapPost("/api/upload/part-image", async (
    HttpRequest request,
    CancellationToken ct) => {
  var form = await request.ReadFormAsync(ct);
  string partId = form["partId"].ToString();
  IFormFile? file = form.Files.GetFile("file");
  // validate + authorize + save
});

4. Binding model

public sealed class PartImageForm {
  public required string PartId { get; init; }
  public required IFormFile File { get; init; }
}

// Controller: ([FromForm] PartImageForm form, CancellationToken ct)

เลือก style ให้เข้ากับ backend แต่ต้องทดสอบชื่อ fields แบบ case/format ที่ client ส่งจริง

5. Validation แบบ atomic

ตรวจ partId ว่ามีจริงและผู้ใช้มีสิทธิ์, ตรวจ file, บันทึกไฟล์ แล้วอัปเดต metadata ในลำดับที่ recover ได้ หากบันทึก DB ล้มหลังเขียน disk ต้องลบ orphan หรือมี cleanup job; ถ้าเก็บ object storage ควรใช้ staging key แล้ว promote

6. หลายไฟล์

ถ้ารองรับหลายภาพ ให้ตกลงชื่อ files ซ้ำหลาย part และจำกัดทั้งจำนวนไฟล์, ขนาดต่อไฟล์ และขนาดรวม อย่าส่ง request ใหญ่มหาศาลเพราะผู้ใช้อาจเสีย network ทั้งก้อนเมื่อไฟล์เดียวผิด

7. Error ที่ actionable

{
  "type": ".../invalid-upload",
  "title": "Image rejected",
  "status": 400,
  "errors": { "file": ["Maximum size is 5 MB"] }
}

UI map field error มาที่ preview/ปุ่มเลือกใหม่ ส่วน 401/403 ต้องแยกจาก validation และ 409 ใช้เมื่อ state ของ part ขัดแย้ง

8. แบบฝึกหัด

หาก part ถูกลบหลังผู้ใช้เลือกรูปแต่ก่อนอัปโหลด server ควรตอบอะไร?

แนวคำตอบ

ตอบ 404 หากไม่เปิดเผย entity หรือ 409 หาก client รู้จัก part อยู่แล้ว พร้อมไม่เก็บไฟล์ orphan และให้ UI refresh รายการ
