Flutter ออกแบบให้สร้าง UIด้วย composition: widgetเล็กรับ input/callbackแล้วประกอบกัน แทน inheritance hierarchyหรือ build methodยักษ์ การแตกที่ดีต้องตาม responsibility/rebuild/lifecycle boundary ไม่ใช่ตามจำนวนบรรทัดอย่างเดียว

1. สัญญาของ component

class WarehouseTile extends StatelessWidget {
  const WarehouseTile({
    super.key,
    required this.title,
    required this.badge,
    required this.onTap,
  });
  final String title;
  final int badge;
  final VoidCallback onTap;
  // build presentation only
}

ชื่อ/fieldsบอก input-outputโดยไม่เปิด parent internals Childไม่ต้องรู้ store/repository/navigationถ้า callbackพอ

2. เกณฑ์ว่าควรแตกตรงไหน

  • มีชื่อโดเมน/visual responsibilityชัด เช่น DispatchTile, StatusBar
  • มี rebuild dependencyแคบกว่าส่วนอื่น
  • มี lifecycle/resourceของตน
  • reuse/testแยกมีประโยชน์
  • ส่วนใหญ่บดบัง intentของ parent

3. Dashboardจริง

Absolute HomeView แตกเป็น _DispatchTile, _Tile, _HomeIcon, _SummaryCard Parentอธิบาย layout/menu ส่วน childrenอธิบาย card/icon/dashboard mode ทำให้ local modeอยู่ SummaryCard State ไม่ทำให้ HomeViewทั้งตัว stateful

4. Private widget ดีกว่า helper Widgetเมื่อไร

Method Widget _tile(...) ใช้ได้สำหรับ fragmentเล็ก แต่ class widgetมี config/type/const/key/context/rebuild boundaryที่ชัดกว่าและ testได้ตรง ถ้า helperรับ parameterมากหรือมี nested logicให้ยกเป็น widget

5. อย่าส่ง BuildContext/storeทั้งโลก

ส่งข้อมูลขั้นต่ำและ callbackตาม use case ถ้า every childรับ WarehouseStoreแล้วเรียกได้ทุก command couplingจะกว้างและไม่รู้ dependencyที่ทำให้ rebuild อย่างไรก็ตาม container screenอาจรับ storeแล้วแจก typed propertiesเป็น patternที่เหมาะ

6. Composition กับ styling

สร้าง design widgets/tokensเช่น PdaColors/PdaMetrics/ScanBox เพื่อ reuse accessibility/touch target แต่อย่าสร้าง wrapperทุก Containerจน call siteต้องเปิด 6ไฟล์เพื่อรู้ padding ใช้ abstractionเมื่อมี policyจริง

7. แบบฝึกหัด

หน้าสแกน 1,800บรรทัดมี input, result list, confirm dialog, APIและ status animation จะแตกตามลำดับใด?

แนวคำตอบ

เพิ่ม testsก่อน → แยก pure model/state transition/repository → แยก presentational ScanInput/ResultList/StatusBanner/ConfirmSheet รับ typed inputs/callbacks → วาง lifecycle controller/focusที่ ownerเหมาะ → profile/retest ไม่เริ่มจากตัดไฟล์ทุก 100บรรทัดโดย business stateยังรวม

8. จุดพลาด

ไฟล์เล็กจำนวนมากไม่เท่ากับ compositionที่ดี ถ้า childรู้ singleton/globalทุกตัวและเปลี่ยน stateข้ามกัน boundaryเป็นเพียงชื่อไฟล์
