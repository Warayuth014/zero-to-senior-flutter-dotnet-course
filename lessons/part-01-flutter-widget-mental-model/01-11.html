1. ปัญหาที่บทนี้แก้

หน้าจอในแอปจริงมักโตขึ้นเรื่อย ๆ จนฟังก์ชัน build ยาวหลายร้อยบรรทัด อ่านแล้วไม่รู้ว่าตรงไหนคืออะไร แก้ตรงหนึ่งพังอีกตรงหนึ่ง

ใน 1.4 เราให้เกณฑ์กว้าง ๆ ไว้สามข้อ บทนี้จะทำให้ใช้งานได้จริง พร้อมเตือนกับดักฝั่งตรงข้าม — การแตกจนเป็นสิบไฟล์ที่ต้องเปิดทุกไฟล์ถึงจะเข้าใจว่าหน้าจอทำอะไร

2. คำศัพท์ที่ต้องรู้ก่อน

3. Mental model: แม่บอกโครง ลูกบอกหน้าตา

Flutter สร้าง UI ด้วยการ ประกอบ ไม่ใช่การสืบทอด — เราไม่เคยเขียน class MyButton extends ElevatedButton เลยตลอดคอร์ส แต่เราเอา widget เล็กมาซ้อนกัน

เมื่อแตกได้ดี การอ่าน build ของแม่ควรเหมือนอ่านสารบัญ

Column(
  children: [
    StatsRow(...),          // แถวสถิติ
    TapCounterLabel(...),   // ข้อความนับจำนวนครั้ง
    TaskListView(...),      // รายการงาน
  ],
)
ประโยคเดียวที่ต้องจำ: แม่ตอบว่า “หน้าจอนี้ประกอบด้วยอะไรบ้าง” ส่วนลูกตอบว่า “แต่ละชิ้นหน้าตาอย่างไร” — ถ้าอ่าน build ของแม่แล้วยังไม่รู้ว่าหน้าจอมีอะไร แปลว่าแตกยังไม่พอ

4. เกณฑ์ตัดสินว่าควรแตก

เกณฑ์คำถามที่ถามตัวเอง
ตั้งชื่อได้เรียกส่วนนี้ด้วยคำเดียวได้ไหม เช่น “การ์ดสถิติ”
ใช้ซ้ำปรากฏมากกว่าหนึ่งที่ไหม
ขอบเขต rebuild ต่างกันส่วนนี้เปลี่ยนบ่อยกว่าหรือน้อยกว่าส่วนอื่นไหม
มีของที่ต้องดูแลเองมีตัวควบคุมหรือการฟังที่ต้องคืนไหม (1.6)
ทดสอบแยกมีประโยชน์อยากเขียนเทสต์เฉพาะส่วนนี้ไหม

เข้าข้อใดข้อหนึ่งก็แตกได้ ไม่ต้องครบทุกข้อ

5. แตกเป็น class ไม่ใช่เป็น method

วิธีแตกที่คนใหม่ชอบใช้คือแยกเป็น method ที่คืน widget

// แบบ method
Widget _buildStatCard(String label, String value) {
  return Card(child: ...);
}

// แบบ class
class StatCard extends StatelessWidget {
  const StatCard({super.key, required this.label, required this.value});
  ...
}
methodclass
เขียนเร็วเร็วกว่ายาวกว่าเล็กน้อย
ใส่ const ได้ไม่ได้ได้
มี key ของตัวเองได้ไม่ได้ได้ (1.8)
เป็นขอบเขต rebuild แยกไม่เป็นเป็น
ทดสอบแยกได้ไม่ได้ได้
ปรากฏใน DevToolsไม่ปรากฏปรากฏพร้อมชื่อ

ใช้ method ได้กับชิ้นเล็กมากที่ใช้ครั้งเดียวในไฟล์นั้น แต่พอเริ่มมี parameter หลายตัวหรือมีเงื่อนไขข้างใน ให้ยกเป็น class

6. ส่งข้อมูลให้น้อยที่สุดเท่าที่จำเป็น

// แย่ — ลูกได้ทั้งโลกและทำอะไรก็ได้
TaskTile(store: warehouseStore, index: index)

// ดี — ลูกได้เฉพาะที่ต้องใช้ และบอกกลับผ่าน callback
TaskTile(
  task: task,
  done: _doneIds.contains(task.id),
  onToggle: () => _toggleDone(task.id),
)

ประโยชน์ของแบบหลังที่เห็นได้ทันที

  • อ่านบรรทัดเดียวก็รู้ว่า TaskTile ต้องใช้อะไรและทำอะไรได้
  • ทดสอบได้โดยไม่ต้องเตรียมข้อมูลทั้งระบบ — ดูเทสต์ตัวสุดท้ายใน widget_basics_test.dart ที่ประกอบ TaskTile เดี่ยว ๆ ได้เลย
  • ลูกเปลี่ยนสถานะข้ามหลังแม่ไม่ได้ เพราะไม่มีอะไรให้เปลี่ยน

ข้อยกเว้นที่ยอมรับได้: widget ระดับหน้าจอที่รับข้อมูลก้อนใหญ่มาแล้วแจกเป็นค่าย่อย ๆ ให้ลูก — นั่นคือหน้าที่ของมันโดยตรง

7. กับดัก: แตกมากเกินไป

ไฟล์เยอะไม่เท่ากับออกแบบดี ถ้าต้องเปิดหกไฟล์เพื่อตอบว่า “ปุ่มนี้มีระยะขอบเท่าไร” แสดงว่าแตกเกินความจำเป็น
สัญญาณว่าแตกเกินทางแก้
widget ที่ตั้งชื่อไม่ได้ ต้องใช้ชื่ออย่าง _Part2รวมกลับเข้าไป
widget ที่มีบรรทัดเดียวและใช้ครั้งเดียวเขียนตรงที่ใช้เลย
ห่อ Container ทุกตัวด้วย widget ของตัวเองสร้าง widget เมื่อมีกฎร่วมจริง ไม่ใช่ทุกกล่อง
ต้องส่ง parameter สิบตัวลงไปสามชั้นชั้นกลางน่าจะไม่จำเป็น

ทางสายกลางคือสร้าง widget ที่เป็น มาตรฐานร่วม ซึ่งมีกฎที่ต้องบังคับใช้จริง เช่นปุ่มสำหรับ PDA ที่ต้องใหญ่พอให้กดได้ด้วยมือที่ใส่ถุงมือ — นั่นคือกฎที่มีเหตุผล ไม่ใช่การห่อเพื่อความสวยงาม

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
build ยาวจนหาที่จะแก้ไม่เจอไม่ได้แตกเลยเริ่มจากแตกส่วนที่ตั้งชื่อได้ก่อน
แตกแล้วแต่ยังใส่ const ไม่ได้แตกเป็น method ไม่ใช่ classยกเป็น class
เปลี่ยนข้อมูลชิ้นเดียวแล้วทั้งหน้าจอวาดใหม่ทุกอย่างอยู่ในขอบเขตเดียวกันแตกส่วนที่เปลี่ยนบ่อยออกมา (1.13)
ลูกไปเปลี่ยนข้อมูลของแม่โดยตรงส่งข้อมูลทั้งก้อนลงไปส่งค่าที่ต้องใช้ + callback
เทสต์ widget หนึ่งตัวต้องเตรียมข้อมูลทั้งระบบลูกผูกกับข้อมูลก้อนใหญ่ให้ลูกรับเฉพาะที่ใช้จริง
ต้องเปิดหลายไฟล์เพื่อเข้าใจหน้าจอเดียวแตกเกินไปรวมชิ้นที่ตั้งชื่อไม่ได้กลับเข้าไป

9. แบบฝึกหัด

หน้าจอสแกนหนึ่งหน้ามีทั้งหมดในไฟล์เดียว 800 บรรทัด ประกอบด้วย

  • ช่องรับบาร์โค้ดพร้อมปุ่มยืนยัน
  • รายการรายการที่สแกนไปแล้ว
  • แถบแสดงสถานะการเชื่อมต่อ
  • กล่องยืนยันก่อนปิดงาน
  • โค้ดเรียก API และแปลงข้อมูล
  1. ลำดับการแตกควรเป็นอย่างไร และทำไม
  2. ส่วนไหนที่ ไม่ควร เป็น widget
  3. ส่วนไหนควรเป็น StatefulWidget
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ลำดับที่ปลอดภัย

  1. เขียนเทสต์คลุมพฤติกรรมหลักก่อน อย่างน้อยหนึ่งเส้นทาง เช่น “สแกนแล้วรายการเพิ่มขึ้น” — เพื่อให้รู้ทันทีถ้าการแตกทำอะไรพัง
  2. แยกโค้ดที่ไม่ใช่ UI ออกก่อน คือส่วนเรียก API และแปลงข้อมูล ย้ายไปเป็น class ธรรมดาที่ไม่ต้องใช้ Flutter — ตรงกับหลักใน D1.20 ว่าตรรกะที่ไม่ผูกกับหน้าจอคือตรรกะที่ทดสอบได้
  3. แยกส่วนที่แสดงผลล้วน ๆ ได้แก่รายการที่สแกนแล้ว และแถบสถานะ ทั้งคู่รับข้อมูลเข้ามาแล้ววาด ไม่ต้องรู้อะไรอีก
  4. แยกช่องรับบาร์โค้ด ซึ่งมีตัวควบคุมของตัวเอง จึงต้องเป็น StatefulWidget ที่ดูแลการคืนทรัพยากรเอง (1.6)
  5. แยกกล่องยืนยัน ออกเป็นฟังก์ชันที่คืนผลลัพธ์กลับมา
  6. รันเทสต์ซ้ำ ทุกขั้น

ทำไมต้องเริ่มจากส่วนที่ไม่ใช่ UI: เพราะมันเป็นส่วนที่แยกแล้วได้ประโยชน์มากที่สุดและเสี่ยงน้อยที่สุด ถ้าเริ่มจากตัดไฟล์ตามจำนวนบรรทัด เราจะได้ไฟล์เล็กหลายไฟล์ที่ยังผูกกันแน่นเหมือนเดิม ซึ่งไม่ได้แก้อะไรเลย

ข้อ 2 — สิ่งที่ไม่ควรเป็น widget

  • โค้ดเรียก API และแปลงข้อมูล — ควรเป็น class ธรรมดาที่ไม่ import Flutter เลย ทำให้เขียนเทสต์ได้โดยไม่ต้องประกอบหน้าจอ
  • กฎทางธุรกิจ เช่น “บาร์โค้ดซ้ำไม่นับซ้ำ” — ควรอยู่ในตรรกะ ไม่ใช่ใน build

ข้อ 3 — ส่วนที่ควรเป็น StatefulWidget

ส่วนชนิดเหตุผล
ช่องรับบาร์โค้ดStatefulมีตัวควบคุมข้อความและโฟกัสที่ต้องคืน
หน้าจอสแกน (ตัวนอกสุด)Statefulถือรายการที่สแกนแล้ว ซึ่งหลายส่วนต้องใช้
รายการที่สแกนแล้วStatelessรับ list เข้ามาแล้ววาด
แถบสถานะStatelessรับสถานะเข้ามาแล้ววาด

จุดที่คนมักพลาด: ทำให้ทุกส่วนเป็น StatefulWidget เพราะ “มันมีข้อมูล” — แต่รายการที่สแกนแล้ว ไม่ได้เป็นเจ้าของ ข้อมูลนั้น มันแค่แสดง เจ้าของคือหน้าจอ ตามกฎใน 1.5 ที่ว่าข้อมูลอยู่ที่ widget ต่ำที่สุดซึ่งยังครอบคลุมทุกคนที่ต้องใช้

ลองต่อ: หลังแตกเสร็จ ลองเขียนเทสต์ให้รายการที่สแกนแล้วโดยส่ง list สามรายการเข้าไปตรง ๆ — ถ้าเขียนได้โดยไม่ต้องแตะ API แปลว่าแตกถูกเส้นแล้ว

10. สรุปท้ายบท

  • Flutter สร้าง UI ด้วยการประกอบ ไม่ใช่การสืบทอด
  • build ของแม่ควรอ่านเหมือนสารบัญ
  • แตกเมื่อ ตั้งชื่อได้ / ใช้ซ้ำ / ขอบเขต rebuild ต่าง / มีของต้องดูแล / ทดสอบแยกได้
  • แตกเป็น class ดีกว่า method เพราะได้ const, key, ขอบเขต rebuild และเทสต์
  • ส่งให้ลูกเฉพาะที่ต้องใช้ พร้อม callback สำหรับแจ้งกลับ
  • แตกเกินไปก็เป็นปัญหา — ถ้าตั้งชื่อไม่ได้ ยังไม่ควรแตก
  • เริ่มแตกจากส่วนที่ไม่ใช่ UI ก่อนเสมอ
