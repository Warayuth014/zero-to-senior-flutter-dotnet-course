const widget สร้าง configuration คงที่และอาจ reuse instance ทำให้ framework short-circuit subtreeบางส่วนได้ แต่ไม่ใช่กำแพงห้าม parent build และไม่แก้ layout/paint/data workที่แพงโดยอัตโนมัติ

1. ใช้เมื่อ argumentคงที่

const SizedBox(height: 12)
const Icon(Icons.refresh)
const EdgeInsets.symmetric(horizontal: 16)

Text(task.id) // runtime data จึงไม่ const

constructorต้องประกาศ constและค่าทุก argumentอยู่ใน constant context

2. ประโยชน์จริง

  • สื่อว่าค่า/โครงนี้ไม่ขึ้นกับ stateปัจจุบัน
  • ลดการสร้าง config instanceซ้ำในบางกรณี
  • เมื่อ child widget instance identical frameworkอาจข้าม update subtree
  • analyzerช่วยแนะนำและจับสิ่งที่ควรคงที่

3. สิ่งที่ const ไม่ทำ

ถ้า const child depend on inherited Themeผ่าน buildของตน มันยัง rebuildเมื่อ dependencyเปลี่ยน; render objectยัง layout/paintเมื่อ constraints/propertyต้องเปลี่ยน; listใหญ่/image decode/API callไม่หายเพราะใส่ constรอบ icon

4. ตัวอย่างจริง

สองแอปใช้ constกับ Colors, EdgeInsets, SizedBox, icons, delegatesและ WmsApp/Login widgetsที่ configคงที่ ส่วน HomeView Tilesบางส่วนไม่ constเพราะ badge, language text, store callbackและ responsive valuesเป็น runtime

5. Rebuild scope สำคัญกว่า constจำนวน

Absolute shellมี ListenableBuilder bodyและ bottom navigationแยกกัน นี่ควบคุม dependency/rebuild scopeเชิงสถาปัตยกรรม ส่วน constเป็น micro optimization/clarityใน subtree อย่าสลับลำดับความสำคัญ

6. Measure ก่อน optimize

ใช้ DevToolsดู frame/build profile ระบุ widgetที่ rebuildและงานแพง จากนั้นแยก builder/child, ย้าย state owner, lazy list, ลด parsing/image work แล้วค่อยตรวจ const/repaint boundary

7. แบบฝึกหัด

ทำไม const Text('WMS') ยังอาจถูก layoutใหม่เมื่อหมุนจอ?

เฉลย

Widget configเดิมคงที่ แต่ parent constraints/layout treeเปลี่ยน RenderObjectจึงต้อง layoutตามขนาดใหม่ Constเกี่ยวกับ configuration identity ไม่ได้ freeze render geometry

8. จุดพลาด

อย่าแตก widget/ใส่ constทุกจุดเพื่อคะแนน lintโดยไม่อ่าน dependency tree เป้าหมายคือ correctnessและขอบเขต rebuildชัด ไม่ใช่จำนวนคำ constสูงสุด
