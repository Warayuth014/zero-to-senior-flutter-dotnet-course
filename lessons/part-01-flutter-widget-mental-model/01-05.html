1. ปัญหาที่บทนี้แก้

ใน 1.4 เราเจอกำแพงว่า StatelessWidget เก็บข้อมูลที่เปลี่ยนได้ไม่ได้เลย แต่แอปทุกตัวต้องมีข้อมูลที่เปลี่ยน — จำนวนที่นับได้ ข้อความที่ผู้ใช้พิมพ์ รายการที่ถูกเลือก

StatefulWidget คือคำตอบ และกลไกของมันตรงกับสิ่งที่เรียนไปแล้วใน 1.3 พอดี

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย

State<T>class คู่กันที่เก็บข้อมูลจริงและมี build
createState()method ที่สร้าง State ให้ครั้งเดียวตอนเริ่ม
setStateบอก Flutter ว่า “ข้อมูลเปลี่ยนแล้ว ช่วยวาดใหม่”
widget.xxxวิธีที่ State อ่านค่าที่แม่ส่งมา

3. Mental model: ทำไมต้องแยกเป็นสอง class

คนใหม่มักงงว่าทำไม StatefulWidget ต้องเขียนสอง class คำตอบอยู่ใน 1.3 ทั้งหมด

StatefulWidgetState
เทียบกับ 1.3ใบสั่งงานความจำของช่าง
ถูกสร้างใหม่ทุกครั้งที่ rebuildครั้งเดียวตอนเริ่ม
เก็บอะไรค่าที่แม่ส่งมา (final ทั้งหมด)ข้อมูลที่เปลี่ยนได้
อยู่นานแค่ไหนชั่วครู่ตราบที่ Element ยังอยู่
ประโยคเดียวที่ต้องจำ: ที่ต้องแยกสอง class เพราะของสองอย่างนี้มี อายุ ต่างกัน — widget ตายทุกรอบ ส่วนข้อมูลต้องอยู่รอด

4. โครงสร้างที่ต้องเขียนทุกครั้ง

เปิด lib/beginner_main.dart ใน lab

class WarehouseCounterScreen extends StatefulWidget {
  const WarehouseCounterScreen({super.key});

  @override
  State<WarehouseCounterScreen> createState() => _WarehouseCounterScreenState();
}

class _WarehouseCounterScreenState extends State<WarehouseCounterScreen> {
  int _itemCount = 0;          // ข้อมูลที่เปลี่ยนได้ อยู่ตรงนี้

  void _addItem() {
    setState(() {
      _itemCount++;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(/* ใช้ _itemCount ตรงนี้ */);
  }
}
สังเกตเหตุผล
build อยู่ใน State ไม่ใช่ใน widgetเพราะต้องเข้าถึงข้อมูลที่เปลี่ยนได้
ชื่อ State ขึ้นต้นด้วย _เป็นรายละเอียดภายในไฟล์ ไม่ให้ใครนอกไฟล์แตะ (D1.7, D1.18)
_itemCount ไม่ใช่ finalเพราะมันคือสิ่งที่ต้องเปลี่ยนได้
State<WarehouseCounterScreen>generic บอกว่าผูกกับ widget ตัวไหน (D1.9)

5. setState ทำอะไรกันแน่

setState(() {
  _itemCount++;
});

มันทำสองอย่างตามลำดับ

  1. เรียกฟังก์ชันที่เราส่งเข้าไปทันที — ตรงนี้คือที่ที่เราเปลี่ยนค่า
  2. ทำเครื่องหมายว่า “ตรงนี้ต้องวาดใหม่” แล้ว Flutter จะมา build ให้ในรอบถัดไป
สิ่งที่ setState ไม่ได้ทำ: มันไม่ได้เปลี่ยนค่าให้เราเอง เราต้องเปลี่ยนเองในฟังก์ชันที่ส่งไป และมันไม่ได้วาดหน้าจอทันทีในบรรทัดถัดไป — การวาดเกิดขึ้นทีหลัง
เขียนแบบผลลัพธ์
setState(() => _itemCount++);ถูก — เปลี่ยนค่าและแจ้งครบ
_itemCount++; เฉย ๆค่าเปลี่ยนจริง แต่หน้าจอไม่อัปเดต
_itemCount++; setState(() {});ได้ผลเหมือนกัน แต่อ่านยากกว่าและเสี่ยงลืมภายหลัง

อาการ “กดปุ่มแล้วไม่มีอะไรเกิดขึ้น” ที่คนใหม่เจอกันเกือบทุกคน มาจากแถวที่สองในตารางนี้

6. งานที่ต้องรอ ให้รอให้เสร็จก่อน แล้วค่อย setState

// ผิด — ใส่งานที่ต้องรอไว้ข้างใน
setState(() async {
  final result = await api.load();
  _items = result;
});

// ถูก — รอให้เสร็จก่อน แล้วค่อยแจ้ง
Future<void> _load() async {
  final result = await api.load();
  setState(() {
    _items = result;
  });
}

เหตุผลตรงกับ D1.15: ฟังก์ชันใน setState ควรทำงานเสร็จทันที ถ้าใส่งานที่ต้องรอเข้าไป Flutter จะทำเครื่องหมายและวาดใหม่ตั้งแต่ก่อนข้อมูลจะมาถึง

ยังมีเรื่องสำคัญอีกข้อที่ค้างไว้ — ระหว่างที่เรารอ ผู้ใช้อาจกดย้อนกลับออกจากหน้าจอไปแล้ว การเรียก setState ตอนนั้นจะเกิด error เรื่องนี้จะแก้อย่างเป็นระบบใน 1.6 และ 3.13

7. ข้อมูลควรอยู่ที่ widget ไหน

คำถามนี้สำคัญกว่าไวยากรณ์ทั้งหมดในบทนี้ ใช้กฎข้อเดียว

เก็บข้อมูลไว้ที่ widget ที่ต่ำที่สุด ซึ่งยังครอบคลุมทุกคนที่ต้องใช้ข้อมูลนั้น

ดูตัวอย่างจริงจาก lab widget_basics_app.dart

ข้อมูลใครต้องใช้เก็บที่ไหน
งานใบไหนเสร็จแล้วบ้างแถวงานทุกแถว และการ์ดสรุปยอด_DashboardScreenState ซึ่งเป็นแม่ของทั้งสอง
ชื่อและจำนวนของงานหนึ่งใบเฉพาะแถวนั้นส่งผ่าน constructor ไม่ต้องเก็บ
สีของแถวเมื่อทำเสร็จเฉพาะแถวนั้น และคำนวณได้คำนวณใน build ไม่เก็บ

สังเกตว่า TaskTile เป็น StatelessWidget ทั้งที่มันมีสถานะ “เสร็จ/ไม่เสร็จ” — เพราะสถานะนั้น ไม่ใช่ของมัน การ์ดสรุปยอดก็ต้องรู้ด้วย ข้อมูลจึงต้องอยู่ที่แม่ แล้วส่งลงมาเป็นค่า พร้อม callback สำหรับแจ้งกลับขึ้นไป (เรื่อง callback อยู่ใน 1.12)

ถ้าเก็บไว้ที่ TaskTile เอง จะเกิดอาการคลาสสิก: กดแล้วแถวเปลี่ยนเป็นขีดฆ่า แต่ตัวเลข “ยังไม่เสร็จ” ด้านบนไม่ลด เพราะไม่มีใครบอกมัน

8. Stateless หรือ Stateful — ตัดสินอย่างไร

คำถามถ้าตอบว่าใช่
widget นี้ต้องจำอะไรระหว่าง rebuild ไหมStateful
มันเป็นเจ้าของตัวควบคุมที่ต้องคืนทรัพยากรไหม (ช่องกรอก, อนิเมชัน)Stateful
ข้อมูลที่ใช้มาจากแม่ทั้งหมดไหมStateless
ค่าที่ต้องการคำนวณจากค่าที่ได้รับได้ไหมStateless

ค่าเริ่มต้นควรเป็น StatelessWidget เสมอ แล้วค่อยเปลี่ยนเมื่อมีเหตุผลชัดเจน — เพราะมันทดสอบง่ายกว่า อ่านง่ายกว่า และไม่มีเรื่องวงจรชีวิตให้พลาด

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
กดปุ่มแล้วไม่มีอะไรเกิดขึ้นเปลี่ยนค่าโดยไม่เรียก setStateห่อการเปลี่ยนค่าไว้ใน setState
setState() called after dispose()เรียกหลังผู้ใช้ออกจากหน้าจอไปแล้วตรวจสถานะก่อนเรียก (1.6, 3.13)
setState() called during buildเรียก setState ใน buildย้ายไปเรียกจาก callback ของผู้ใช้แทน
แถวเปลี่ยนแต่ยอดสรุปไม่เปลี่ยนข้อมูลเก็บต่ำเกินไปย้ายขึ้นไปที่แม่ร่วมของทั้งสอง
คัดลอกค่าจากแม่มาเก็บใน State แล้วค่าไม่อัปเดตคัดลอกครั้งเดียวตอนเริ่มอ่านจาก widget.xxx ตรง ๆ หรือดูวิธีซิงก์ใน 1.6
ทุก widget ในโปรเจกต์เป็น StatefulWidgetเปลี่ยนเป็น Stateful เพื่อความสบายใจเริ่มจาก Stateless เสมอ

10. แบบฝึกหัด

ในแอป lab beginner_main.dart ให้เพิ่มความสามารถ

  1. ปุ่ม “ลดหนึ่งรายการ” ที่ลดจำนวนลงทีละหนึ่ง
  2. จำนวนต้องไม่ติดลบ
  3. ปุ่มต้องกดไม่ได้เมื่อจำนวนเป็นศูนย์
  4. แสดงข้อความ ครบเป้าแล้ว เมื่อจำนวนถึง 10 หรือมากกว่า โดยห้ามเก็บข้อความนี้เป็น field
ดูแนวคำตอบและเหตุผล
class _WarehouseCounterScreenState extends State<WarehouseCounterScreen> {
  int _itemCount = 0;

  // ค่าที่คำนวณได้ ไม่เก็บซ้ำ — หลักเดียวกับ D1.7 และ 1.4
  bool get _isEmpty => _itemCount == 0;
  bool get _reachedGoal => _itemCount >= 10;

  void _addItem() => setState(() => _itemCount++);

  void _removeItem() {
    if (_isEmpty) return;              // กันไว้ที่ตรรกะด้วย ไม่ใช่แค่ที่ปุ่ม
    setState(() => _itemCount--);
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Column(
        children: [
          Text('$_itemCount รายการ'),
          if (_reachedGoal) const Text('ครบเป้าแล้ว'),
          FilledButton(onPressed: _addItem, child: const Text('เพิ่มสินค้า')),
          OutlinedButton(
            // ส่ง null เพื่อปิดปุ่ม — Flutter จะทำให้เป็นสีจางและกดไม่ได้เอง
            onPressed: _isEmpty ? null : _removeItem,
            child: const Text('ลดหนึ่งรายการ'),
          ),
        ],
      ),
    );
  }
}

ทำไมต้องกันค่าติดลบสองที่: ปุ่มที่ปิดอยู่ป้องกันได้แค่การกดด้วยนิ้ว แต่ _removeItem อาจถูกเรียกจากที่อื่นในอนาคต เช่นจากปุ่มลัดบนแป้นพิมพ์หรือจากเทสต์ — กฎทางธุรกิจต้องอยู่ในตรรกะ ส่วนการปิดปุ่มเป็นเพียงการสื่อสารกับผู้ใช้

ทำไม onPressed: null ถึงปิดปุ่ม: Flutter ใช้ข้อตกลงว่า callback ที่เป็น null แปลว่า “ไม่มีอะไรให้ทำ” จึงทำให้ปุ่มเป็นสีจางและไม่ตอบสนองโดยอัตโนมัติ — เป็นการใช้ nullable callback จาก D1.11 ที่ตรงไปตรงมาและอ่านง่ายกว่าการมี field isEnabled แยกต่างหาก

ทำไม _reachedGoal เป็น getter ไม่ใช่ field: เพราะถ้าเก็บเป็น field เราต้องอัปเดตมันทั้งใน _addItem และ _removeItem วันที่มีคนเพิ่ม method ที่สามเข้ามาแล้วลืมอัปเดต หน้าจอจะแสดง “ครบเป้าแล้ว” ทั้งที่จำนวนเหลือ 3 — บั๊กแบบนี้หาสาเหตุยากเพราะตัวเลขที่แสดงยังถูกต้อง

จุดที่คนมักพลาด: เขียน if (_itemCount > 0) setState(() => _itemCount--); ซึ่งถูกต้องเช่นกัน แต่การแยกเงื่อนไขออกมาเป็น _isEmpty ทำให้ปุ่มกับตรรกะใช้เกณฑ์เดียวกันแน่นอน ไม่มีทางเขียนไม่ตรงกันได้

ลองต่อ: ย้าย _itemCount ออกไปเป็นตัวแปรระดับไฟล์นอก class แล้วรันดู — จะเห็นว่าค่ายังคงอยู่ข้าม rebuild เหมือนกัน แต่ถ้าเปิดหน้าจอนี้สองครั้งพร้อมกันจะใช้ค่าร่วมกันโดยไม่ตั้งใจ นั่นคือเหตุผลที่ข้อมูลควรอยู่ใน State

11. สรุปท้ายบท

  • StatefulWidget แยกเป็นสอง class เพราะ widget กับข้อมูลมีอายุต่างกัน
  • ข้อมูลที่เปลี่ยนได้อยู่ใน State และรอดจากการ rebuild
  • setState ไม่ได้เปลี่ยนค่าให้ เราต้องเปลี่ยนเอง แล้วมันแจ้งให้วาดใหม่
  • งานที่ต้องรอ ให้รอเสร็จก่อน แล้วค่อย setState
  • เก็บข้อมูลไว้ที่ widget ต่ำที่สุดที่ยังครอบคลุมทุกคนที่ต้องใช้
  • เริ่มจาก StatelessWidget เสมอ แล้วค่อยเปลี่ยนเมื่อมีเหตุผล
