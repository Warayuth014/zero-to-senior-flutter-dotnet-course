1. ปัญหาที่บทนี้แก้

คนหน้างานสองคนทำงานใน order เดียวกัน คนแรกปิดงานบรรทัดที่ 3 ไปแล้ว แต่จอของคนที่สองยังแสดงว่ายังไม่เสร็จ — เพราะข้อมูลบนจอถูกโหลดมาตั้งแต่ตอนเปิดหน้าจอ

ทางแก้ที่ตรงที่สุดคือให้แอปถามเซิร์ฟเวอร์เองเป็นระยะ ซึ่งเรียกว่า polling

แต่พอทำจริงจะเจอปัญหาชุดใหม่ทันที

ปัญหาอาการที่หน้างาน
คำขอซ้อนกันเน็ตช้าอยู่แล้วยิ่งช้าลงเรื่อย ๆ
รีเฟรชระหว่างที่ผู้ใช้กำลังกดปุ่มสิ่งที่เพิ่งกดถูกเขียนทับกลับเป็นค่าเก่า
ตัวจับเวลาไม่เคยหยุดแบตหมดก่อนหมดกะ
เน็ตหลุด แต่ยังยิงทุก 5 วินาทียิงเปล่าเป็นร้อยครั้ง

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
pollingถามซ้ำเป็นระยะว่ามีอะไรใหม่ไหม
Timer.periodicตัวจับเวลาที่ยิงซ้ำทุกช่วงเวลา
tickหนึ่งครั้งที่ตัวจับเวลายิง
overlapคำขอใหม่เริ่มทั้งที่คำขอเก่ายังไม่จบ
backoffยืดระยะเวลาออกเมื่อล้มเหลวติดกัน
jitterสุ่มเวลาเล็กน้อย ไม่ให้ทุกเครื่องยิงพร้อมกัน
fakeAsyncเครื่องมือทดสอบที่ทำให้เราเดินเวลาเองได้

3. Mental model: ตัวจับเวลาไม่สนใจว่าคุณเสร็จหรือยัง

Timer.periodic 5 วินาที + คำขอที่ใช้เวลา 8 วินาที

0s   tick → คำขอ A เริ่ม ─────────────────→ จบ 8s
5s   tick → คำขอ B เริ่ม ─────────────────→ จบ 13s
10s  tick → คำขอ C เริ่ม ─────────────────→ จบ 18s
15s  tick → คำขอ D เริ่ม ...

จำนวนคำขอที่วิ่งพร้อมกัน เพิ่มขึ้นเรื่อย ๆ ไม่มีวันหยุด
ประโยคเดียวที่ต้องจำ: Timer.periodic ยิงตามนาฬิกา ไม่ได้ยิงตามงาน — เราต้องเป็นคนตัดสินใจเองว่า tick ไหนควรข้าม

4. โครงพื้นฐานใน lab

เปิด lib/state_basics/pick_store.dart

Timer? _pollTimer;

void startPolling(Duration interval) {
  stopPolling();                                  // 1. กันเปิดซ้อน
  _pollTimer = Timer.periodic(interval, (_) {
    if (_busyLineIds.isEmpty) load();             // 2. ข้าม tick เมื่อไม่ว่าง
  });
}

void stopPolling() {
  _pollTimer?.cancel();
  _pollTimer = null;
}

@override
void dispose() {
  stopPolling();                                  // 3. คู่ตรงข้าม
  _generation++;
  super.dispose();
}

สามบรรทัดสำคัญ ทำหน้าที่ต่างกัน

#กันอะไรถ้าไม่มีจะเป็นอย่างไร
1เรียก startPolling สองครั้งมีตัวจับเวลาสองตัววิ่งพร้อมกัน ตัวเก่าไม่มีใครถือแล้วจึงหยุดไม่ได้อีกเลย
2รีเฟรชขณะผู้ใช้กำลังส่งคำสั่งข้อมูลจากเซิร์ฟเวอร์ทับสิ่งที่ผู้ใช้เพิ่งกด
3ตัวจับเวลาเดินต่อหลัง store ตายแล้วยิงคำขอไปเรื่อย ๆ ตลอดอายุแอป

5. ทำไมต้องข้าม tick ตอนผู้ใช้กำลังกด

บรรทัด if (_busyLineIds.isEmpty) ดูเล็กมาก แต่กันเหตุการณ์ที่อธิบายให้ผู้ใช้เข้าใจยากที่สุด

0.0s  ผู้ใช้กดปิดงาน L-3 → จอแสดงว่าเสร็จแล้วทันที (4.13)
0.1s  คำขอ markDone กำลังวิ่งไป server
0.2s  tick ของ polling → load() ยิงไปถาม server
0.6s  load() ได้ผลกลับมา: L-3 "ยังไม่เสร็จ" (เพราะ markDone ยังไปไม่ถึง)
0.6s  จอเปลี่ยนกลับเป็นยังไม่เสร็จ            ← ผู้ใช้เห็นสิ่งที่กดหายไป
0.9s  markDone สำเร็จ
0.9s  จอเปลี่ยนเป็นเสร็จอีกครั้ง

ผู้ใช้เห็นเครื่องหมายถูกกระพริบหายแล้วกลับมา ซึ่งทำให้ไม่มั่นใจว่ากดติดหรือไม่ และมักจะกดซ้ำ

การข้าม tick แก้เรื่องนี้ตรง ๆ — ระหว่างที่มีคำสั่งของผู้ใช้ค้างอยู่ ห้ามให้ข้อมูลจากที่อื่นมาทับ

สังเกตว่า _busyLineIds เป็นตัวเดียวกับที่ใช้ล็อกปุ่มใน 4.8 — ตัวเดียวทำสองหน้าที่ที่สอดคล้องกัน

6. กันคำขอซ้อนกัน

การข้าม tick ตอนผู้ใช้กดยังไม่พอ เพราะ tick ถัดไปอาจมาก่อนที่ load() ของ tick ก่อนหน้าจะจบ

bool _refreshing = false;

Future<void> _refreshIfIdle() async {
  if (_refreshing) return;        // ยังไม่จบ ข้าม tick นี้ไป
  _refreshing = true;
  try {
    await load();
  } finally {
    _refreshing = false;          // ปลดเสมอ (4.8)
  }
}
_pollTimer = Timer.periodic(interval, (_) {
  if (_busyLineIds.isEmpty) unawaited(_refreshIfIdle());
});

ผลที่ได้เมื่อคำขอใช้เวลานานกว่ารอบ

0s   tick → เริ่ม ─────────────────→ จบ 8s
5s   tick → ข้าม (ยังไม่จบ)
10s  tick → เริ่ม ─────────────────→ จบ 18s
15s  tick → ข้าม

เป็นการ ข้าม ไม่ใช่การเข้าคิว ซึ่งถูกต้องสำหรับ polling เพราะเราต้องการข้อมูลล่าสุด ไม่ได้ต้องการทุกครั้งที่นาฬิกาเดิน

สังเกตว่าใช้ unawaited ตามที่เรียนใน 4.8 — เพราะ callback ของ Timer.periodic ไม่รอ Future อยู่แล้ว การเขียน unawaited จึงเป็นการบอกคนอ่านว่าตั้งใจ ไม่ใช่ลืม

7. หยุดเมื่อไม่มีใครดู

PDA เปิดทั้งกะ ถ้า polling ทำงานตลอดโดยไม่สนใจว่าแอปอยู่หน้าไหน จะเสียทั้งแบตและปริมาณข้อมูล

สถานการณ์ควรทำ
เปิดหน้าที่ต้องใช้ข้อมูลสดเริ่ม polling
ออกจากหน้านั้นหยุด
แอปถูกย่อลง / ปิดจอหยุด
กลับมาที่แอปรีเฟรชทันทีหนึ่งครั้ง แล้วเริ่มใหม่

ข้อสุดท้ายสำคัญ — คนเปิดจอกลับมาแล้วต้องเห็นข้อมูลล่าสุดทันที ไม่ใช่รออีก 5 วินาที

class _PickScreenState extends State<PickScreen> with WidgetsBindingObserver {
  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addObserver(this);
    widget.store.load();
    widget.store.startPolling(const Duration(seconds: 10));
  }

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    switch (state) {
      case AppLifecycleState.resumed:
        widget.store.load();                                   // สดทันที
        widget.store.startPolling(const Duration(seconds: 10));
      case AppLifecycleState.paused ||
           AppLifecycleState.inactive ||
           AppLifecycleState.hidden ||
           AppLifecycleState.detached:
        widget.store.stopPolling();
    }
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeObserver(this);   // คู่ตรงข้าม
    widget.store.stopPolling();
    super.dispose();
  }
}

สังเกตว่า startPolling เรียกซ้ำได้ปลอดภัย เพราะบรรทัดแรกของมันคือ stopPolling() — นี่คือประโยชน์ของการออกแบบให้เรียกซ้ำแล้วไม่พัง

รายละเอียดของ WidgetsBindingObserver จะลงลึกใน Part 5

8. เลือกจังหวะให้เหมาะกับข้อมูล

คำถามที่ต้องตอบก่อนตั้งตัวเลขคือ ข้อมูลนี้เก่าได้กี่วินาทีโดยไม่ทำให้ใครทำงานผิด

ข้อมูลเก่าได้แค่ไหนแนวทาง
รายการงานที่หลายคนแย่งกันทำไม่กี่วินาทีpolling 5–10 วินาที
รายการงานของตัวเองคนเดียวเป็นนาทีรีเฟรชตอนเข้าหน้าจอก็พอ
ยอดคงคลังในรายงานเป็นนาทีปุ่มรีเฟรช
สถานะการเชื่อมต่อ—ดูจากผลของคำขอจริงที่ยิงอยู่แล้ว ไม่ต้อง ping แยก

ข้อสุดท้ายเป็นกับดักที่พบบ่อย — การยิง ping ทุกวินาทีเพื่อโชว์จุดสีเขียว คือการยิงคำขอ 28,800 ครั้งต่อกะ เพื่อข้อมูลที่ได้มาฟรีอยู่แล้วจากคำขออื่นที่แอปยิงอยู่

ก่อนจะเพิ่ม polling ให้ถามก่อนว่ามีเหตุการณ์ที่รู้อยู่แล้วให้ใช้แทนได้ไหม — เข้าหน้าจอ กลับมาที่แอป ปิดงานสำเร็จ ล้วนเป็นจังหวะที่ควรรีเฟรชอยู่แล้ว และแม่นกว่าการเดาเวลา

9. เมื่อล้มเหลวติดกัน ต้องยืดระยะ

เน็ตในคลังหลุดเป็นช่วง ๆ ถ้ายังยิงทุก 5 วินาทีตลอดที่หลุด จะได้คำขอที่ล้มเหลวเป็นร้อยครั้ง กินแบตและทำให้ log เต็มไปด้วยเรื่องเดียว

int _failureCount = 0;

Duration get _nextInterval {
  if (_failureCount == 0) return const Duration(seconds: 10);
  final seconds = 10 * (1 << _failureCount);     // 20, 40, 80, 160...
  final capped = seconds.clamp(10, 300);          // ไม่เกิน 5 นาที
  final jitter = Random().nextInt(3000);          // สุ่ม 0–3 วินาที
  return Duration(milliseconds: capped * 1000 + jitter);
}
ส่วนประกอบทำไมต้องมี
ยืดเป็นทวีคูณลดการยิงเปล่าอย่างรวดเร็ว
มีเพดานไม่งั้นพอเน็ตกลับมา จะรอเป็นชั่วโมงกว่าจะรู้
jitterPDA ทั้งคลังหลุดพร้อมกัน ถ้าไม่สุ่มก็จะกลับมายิงพร้อมกันจนล้ม server
รีเซ็ตเมื่อสำเร็จกลับสู่จังหวะปกติทันที

และต้องรีเซ็ตทันทีเมื่อผู้ใช้กดรีเฟรชเองหรือเปิดแอปกลับมา — เพราะนั่นแปลว่ามีคนกำลังรอดูอยู่

10. ทดสอบโดยไม่ต้องรอเวลาจริง

เทสต์ที่รอ 10 วินาทีจริงคือเทสต์ที่ไม่มีใครยอมรัน fakeAsync ให้เราเดินเวลาเองได้

import 'package:fake_async/fake_async.dart';

test('polling ยิงซ้ำตามรอบ และหยุดเมื่อสั่งหยุด', () {
  fakeAsync((async) {
    store.startPolling(const Duration(seconds: 5));

    async.elapse(const Duration(seconds: 12));   // เดินเวลา 12 วินาทีทันที
    expect(repository.fetchCount, 2);            // ยิงไป 2 รอบ

    store.stopPolling();
    async.elapse(const Duration(seconds: 30));
    expect(repository.fetchCount, 2);            // ไม่เพิ่มอีก
  });
});

สิ่งที่ควรมีเทสต์ครอบ

เรื่องทำไมต้องมี
ยิงตามรอบจริงยืนยันว่าตัวจับเวลาทำงาน
ข้าม tick เมื่อมีคำสั่งค้างอยู่กันอาการกระพริบในหัวข้อ 5
ไม่ยิงซ้อนกันกันปัญหาในหัวข้อ 6
stopPolling แล้วหยุดจริงป้องกันตัวจับเวลารั่ว
startPolling สองครั้งแล้วไม่ยิงสองเท่ายืนยันว่าเรียกซ้ำได้
dispose แล้วหยุดจริงเรื่องเดียวกับ 3.12
fakeAsync ใช้กับ callback ที่เป็นแบบธรรมดา ไม่ต้องใส่ async ให้ตัวฟังก์ชันของ fakeAsync เอง และอย่า await ข้างในโดยตรง — ให้ใช้ async.elapse() เดินเวลาแทน

11. ยกเลิกตัวจับเวลาไม่ได้ยกเลิกคำขอ

ประเด็นสุดท้ายที่ต้องเชื่อมกลับไป 4.10

store.stopPolling();     // หยุด tick ในอนาคต
// แต่ load() ที่เริ่มไปแล้วเมื่อ 2 วินาทีก่อน ยังวิ่งอยู่
// และจะกลับมาเขียนลง state ตามปกติ

นี่คือเหตุผลที่ dispose() ต้องมีทั้งสองบรรทัด

@override
void dispose() {
  stopPolling();      // หยุดที่จะเกิดในอนาคต
  _generation++;      // ทิ้งผลของที่เกิดไปแล้ว
  super.dispose();
}

ขาดบรรทัดใดบรรทัดหนึ่งก็ยังรั่ว

12. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ยิ่งใช้ยิ่งช้า คำขอเยอะขึ้นเรื่อย ๆคำขอซ้อนกันธง _refreshing + finally
สิ่งที่เพิ่งกดกลับเป็นค่าเก่าแวบหนึ่งpolling ทับคำสั่งของผู้ใช้ข้าม tick เมื่อมีคำสั่งค้าง
แบตหมดเร็วผิดปกติไม่หยุดเมื่อออกจากหน้าจอหรือย่อแอปผูกกับ lifecycle
ปิดหน้าจอแล้วยังเห็นคำขอในบันทึกเครือข่ายไม่ยกเลิกใน disposestopPolling() ใน dispose
ยิงถี่เป็นสองเท่าเรียก startPolling ซ้ำโดยไม่ยกเลิกตัวเก่าเริ่มด้วย stopPolling()
เน็ตหลุดแล้วยิงเปล่าเป็นร้อยครั้งไม่มี backoffยืดระยะ + เพดาน + jitter
เน็ตกลับมาแล้วรอนานกว่าจะรู้backoff ไม่มีเพดาน หรือไม่รีเซ็ตใส่เพดาน และรีเซ็ตเมื่อกลับมาที่แอป
เทสต์ช้ามากหรือแดงเป็นครั้งคราวรอเวลาจริงในเทสต์fakeAsync

ข้อ 1 — ข้อบกพร่อง

#ข้อบกพร่องผลที่เกิด
1ไม่เก็บ Timer ไว้ในตัวแปรยกเลิกไม่ได้เลยตลอดอายุแอป
2เริ่มใน constructorยิงตั้งแต่สร้าง store แม้ยังไม่มีใครเปิดหน้าจอ
3ไม่มี dispose ที่ยกเลิกตัวจับเวลารั่ว
4ไม่กันคำขอซ้อนรอบ 3 วินาทีกับเน็ตช้า = คำขอสะสม
5ไม่กันการทับคำสั่งของผู้ใช้สิ่งที่กดกระพริบกลับ
6ไม่มี try/catchเน็ตหลุดครั้งเดียว = unhandled exception
7ไม่มีตัวนับรุ่นผลเก่าทับผลใหม่ (4.10)
8ไม่มี backoffเน็ตหลุด = ยิงเปล่าทุก 3 วินาที
93 วินาทีอาจถี่เกินไปไม่ได้ตอบว่าข้อมูลนี้เก่าได้แค่ไหน

ข้อ 2 — เขียนใหม่

class TaskStore extends ChangeNotifier {
  TaskStore({required this.repository});          // แก้ข้อ 2

  final TaskRepository repository;

  Timer? _pollTimer;                              // แก้ข้อ 1
  bool _refreshing = false;
  int _generation = 0;
  int _failureCount = 0;
  final Set<String> _busyTaskIds = <String>{};

  void startPolling() {
    stopPolling();                                // เรียกซ้ำได้ปลอดภัย
    _pollTimer = Timer.periodic(_interval, (_) {
      if (_busyTaskIds.isEmpty) {                 // แก้ข้อ 5
        unawaited(_refreshIfIdle());
      }
    });
  }

  void stopPolling() {
    _pollTimer?.cancel();
    _pollTimer = null;
  }

  Duration get _interval {                        // แก้ข้อ 8, 9
    if (_failureCount == 0) return const Duration(seconds: 10);
    final seconds = (10 * (1 << _failureCount)).clamp(10, 300);
    return Duration(milliseconds: seconds * 1000 + Random().nextInt(3000));
  }

  Future<void> _refreshIfIdle() async {
    if (_refreshing) return;                      // แก้ข้อ 4
    _refreshing = true;
    try {
      await load();
    } finally {
      _refreshing = false;
    }
  }

  Future<void> load() async {
    final generation = ++_generation;             // แก้ข้อ 7
    try {
      final result = await repository.fetchTasks();
      if (generation != _generation) return;
      _tasks = result;
      if (_failureCount != 0) {                   // รีเซ็ตแล้วกลับจังหวะปกติ
        _failureCount = 0;
        if (_pollTimer != null) startPolling();
      }
    } on TaskException catch (error) {            // แก้ข้อ 6
      if (generation != _generation) return;
      _errorMessage = error.message;
      _failureCount++;
      if (_pollTimer != null) startPolling();     // ยืดระยะ
    } finally {
      if (generation == _generation) notifyListeners();
    }
  }

  @override
  void dispose() {                                // แก้ข้อ 3
    stopPolling();
    _generation++;
    super.dispose();
  }
}

สังเกตว่าการเปลี่ยนจังหวะทำโดยเรียก startPolling() ใหม่ ซึ่งทำได้เพราะออกแบบให้เรียกซ้ำแล้วไม่พังตั้งแต่แรก และเช็ก _pollTimer != null ก่อน เพื่อไม่ให้ load() ที่ผู้ใช้กดเองไปเปิด polling ที่ยังไม่ได้เริ่ม

ข้อ 3 — ถ้าเปลี่ยนเป็นรีเฟรชตอนเข้าหน้าจออย่างเดียว

ได้เสีย
โค้ดสั้นลงมาก — ไม่ต้องมีตัวจับเวลา backoff หรือการข้าม tickข้อมูลไม่สดระหว่างที่ค้างหน้าเดิม
ประหยัดแบตและปริมาณข้อมูลชัดเจนคนสองคนทำงานเดียวกันจะเห็นไม่ตรงกันจนกว่าจะออกแล้วเข้าใหม่
บั๊กที่เป็นไปได้น้อยลงมากต้องสอนผู้ใช้ให้รู้วิธีรีเฟรช

คำตอบที่ควรให้คือ “ขึ้นกับว่าข้อมูลนี้แข่งกันหรือเปล่า”

กรณีเลือก
งานถูกจ่ายให้คนเดียว ไม่มีใครมาแย่งรีเฟรชตอนเข้าหน้าจอ + ปุ่มรีเฟรช พอแล้ว
หลายคนหยิบจาก order เดียวกันต้องมี polling ไม่งั้นสองคนไปหยิบของชิ้นเดียวกัน

และมีทางสายกลางที่มักดีที่สุดในทางปฏิบัติ — รีเฟรชตามเหตุการณ์ที่รู้อยู่แล้ว คือตอนเข้าหน้าจอ ตอนกลับมาที่แอป และตอนที่คำสั่งของผู้ใช้สำเร็จ ซึ่งครอบคลุมกรณีจริงได้เกือบหมดโดยไม่ต้องมีตัวจับเวลาเลย แล้วค่อยเพิ่ม polling เฉพาะหน้าที่พิสูจน์ได้ว่ามีการแย่งงานกันจริง

ลองต่อ: ใน test/pick_store_test.dart มีเทสต์ polling ที่ใช้ fakeAsync อยู่แล้ว ลองเพิ่มเทสต์ว่าเรียก startPolling สองครั้งติดกันแล้วจำนวนคำขอต้องไม่เพิ่มเป็นสองเท่า — แล้วลองลบ stopPolling() บรรทัดแรกออกเพื่อดูว่าเทสต์จับได้จริง

14. สรุปท้ายบท

  • Timer.periodic ยิงตามนาฬิกา ไม่รอให้งานเดิมจบ
  • ต้องมีธงกันคำขอซ้อน และปลดใน finally
  • ข้าม tick เมื่อมีคำสั่งของผู้ใช้ค้างอยู่ ไม่งั้นสิ่งที่กดจะกระพริบกลับ
  • เก็บ Timer ไว้เสมอ และให้ startPolling เริ่มด้วย stopPolling
  • ผูกกับ lifecycle — หยุดเมื่อไม่มีใครดู และรีเฟรชทันทีเมื่อกลับมา
  • เมื่อล้มเหลวติดกัน ให้ยืดระยะ มีเพดาน และใส่ jitter
  • ตั้งจังหวะจากคำถามว่าข้อมูลนี้เก่าได้กี่วินาที ไม่ใช่จากความรู้สึก
  • เหตุการณ์ที่รู้อยู่แล้วมักแทน polling ได้ และแม่นกว่า
  • ยกเลิกตัวจับเวลาไม่ได้ยกเลิกคำขอที่เริ่มไปแล้ว — ต้องมีตัวนับรุ่นด้วย
  • ทดสอบด้วย fakeAsync ไม่ใช่ด้วยการรอจริง
