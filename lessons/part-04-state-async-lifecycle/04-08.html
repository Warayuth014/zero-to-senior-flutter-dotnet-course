1. ปัญหาที่บทนี้แก้

อาการนี้เจอกันทุกทีม — กดปุ่มแล้วปุ่มค้างเป็น “กำลังส่ง...” ตลอดกาล ต้องปิดแอปแล้วเปิดใหม่

Future<void> markDone(String lineId) async {
  _busy = true;
  notifyListeners();

  await repository.markDone(lineId);   // ← ถ้าตรงนี้โยน exception

  _busy = false;                        // ← บรรทัดนี้ไม่ถูกรัน ตลอดกาล
  notifyListeners();
}

ผู้ใช้ไม่ได้ทำอะไรผิด และแอปก็ไม่ได้ crash ให้เห็น — มันแค่ ไม่กลับมา ซึ่งบนหน้างานคือแย่กว่า crash เพราะไม่มีใครรู้ว่าต้องทำอะไร

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
tryก้อนที่อาจโยน exception
on X catchดักเฉพาะ exception ชนิด X
finallyก้อนที่ทำงานเสมอ ไม่ว่าจะสำเร็จ ล้มเหลว หรือ return ออกไป
busy lockธงกันไม่ให้คำสั่งเดิมถูกสั่งซ้ำระหว่างที่ยังไม่จบ
cleanupงานเก็บกวาดที่ต้องเกิดแน่นอน เช่นปลดล็อก
rethrowโยน exception เดิมต่อขึ้นไป

3. Mental model: ทางออกมีมากกว่าที่คิด

เรามักคิดว่าฟังก์ชันจบได้สองแบบ — สำเร็จ หรือ พัง แต่จริง ๆ แล้ว

เข้าฟังก์ชัน
    │
    ├─→ ทำครบแล้ว return             ✓ นึกถึง
    ├─→ return กลางทาง (guard)        ✗ มักลืม
    ├─→ exception ที่เราดัก           ✓ นึกถึง
    ├─→ exception ที่เราไม่ได้ดัก      ✗ มักลืม
    └─→ exception จากใน catch เอง     ✗ ลืมสนิท
ประโยคเดียวที่ต้องจำ: ถ้าโค้ดปลดล็อกอยู่ในเส้นทางใดเส้นทางหนึ่ง มันจะถูกข้ามในเส้นทางที่เหลือ — ให้มันอยู่ใน finally ซึ่งเป็นที่เดียวที่ทุกเส้นทางต้องผ่าน

4. โครงที่ถูกต้อง

เปิด lib/state_basics/pick_store.dart ดูโครงของ markDone

Future<void> markDone(String lineId) async {
  if (_busyLineIds.contains(lineId)) return;   // ยังไม่ล็อก จึงยัง return ได้
  final index = _lines.indexWhere((line) => line.id == lineId);
  if (index == -1) return;
  final before = _lines[index];
  if (before.done) return;

  _busyLineIds.add(lineId);                    // ← ล็อกตรงนี้
  _errorMessage = null;
  notifyListeners();

  try {
    await repository.markDone(lineId, commandId: commandId);
  } on PickException catch (error) {
    ...
    _errorMessage = error.message;
  } finally {
    _busyLineIds.remove(lineId);               // ← ปลดล็อกเสมอ
    notifyListeners();
  }
}

สังเกตลำดับ — การตรวจทั้งหมดจบก่อนที่จะล็อก

ถ้าล็อกก่อนตรวจผลที่ตามมา
_busyLineIds.add(); if (index == -1) return;เจอบรรทัดที่ไม่มีจริง แล้ว return ทั้งที่ล็อกไว้แล้ว — ล็อกค้างถาวร

นี่เป็นเหตุผลว่าทำไมกฎ “ตรวจให้จบก่อนแล้วค่อยล็อก” จึงสำคัญพอ ๆ กับ finally เอง

5. ทำไม finally ถึงจำเป็นจริง ๆ

หลายคนคิดว่าเขียนแบบนี้ก็พอ

try {
  await repository.markDone(lineId);
  _busyLineIds.remove(lineId);    // ปลดในทางสำเร็จ
  notifyListeners();
} on PickException catch (error) {
  _errorMessage = error.message;
  _busyLineIds.remove(lineId);    // ปลดในทางล้มเหลว
  notifyListeners();
}

ครอบสองทางแล้ว ดูเหมือนครบ แต่ยังพังในสามกรณี

กรณีผลที่เกิด
โยน exception ชนิดอื่นที่ไม่ใช่ PickException เช่น FormatExceptioncatch ไม่ครอบ ล็อกค้าง
เพิ่ม return ใน catch ทีหลัง (เกิดขึ้นจริงใน lab)บรรทัดปลดล็อกที่อยู่หลัง return ถูกข้าม
โค้ดใน catch เองโยน exceptionปลดล็อกไม่ทัน

และมีข้อเสียที่มองเห็นได้ทันทีคือ โค้ดปลดล็อกถูกเขียนซ้ำสองที่ ซึ่งวันหนึ่งจะแก้ที่เดียวแล้วลืมอีกที่

ข้อสองไม่ใช่เรื่องสมมติ — markDone ใน lab มี return อยู่กลาง catch จริง ๆ

} on PickException catch (error) {
  if (error.outcomeUnknown) {
    _errorMessage = '${error.message} กำลังตรวจสอบสถานะล่าสุด';
    notifyListeners();
    await load();
    return;              // ← ออกจากตรงนี้เลย
  }
  ...
} finally {
  _busyLineIds.remove(lineId);   // ← ยังทำงาน แม้ return ไปแล้ว
  notifyListeners();
}

return ใน try หรือ catch ไม่ข้าม finally — Dart รัน finally ให้ก่อนแล้วจึงออกจากฟังก์ชันจริง

6. จับเฉพาะที่จัดการได้

โค้ดที่เจอบ่อยและอันตรายเงียบ ๆ

} catch (e) {
  _errorMessage = 'เกิดข้อผิดพลาด';   // กลืนทุกอย่าง
}

catch (e) เปล่า ๆ จับ ทุกอย่าง รวมถึงบั๊กของเราเอง

สิ่งที่ถูกกลืนไปด้วยสาเหตุจริงสิ่งที่ผู้ใช้เห็น
NoSuchMethodErrorเผลอเรียกเมธอดบนค่า null“เกิดข้อผิดพลาด”
RangeErrorเข้าถึง index เกินขอบ“เกิดข้อผิดพลาด”
TypeErrorแปลง JSON ผิดชนิด“เกิดข้อผิดพลาด”

ทั้งสามคือบั๊กที่ต้องแก้ที่โค้ด ไม่ใช่เรื่องที่ผู้ใช้ลองใหม่แล้วหาย แต่พอถูกกลืนเป็นข้อความเดียวกับ “เน็ตหลุด” ก็ไม่มีใครรู้ว่ามันมีอยู่ — จนกระทั่งข้อมูลเสียหายไปแล้ว

วิธีที่ถูกคือ ประกาศชนิดที่จัดการได้ให้ชัด

} on PickException catch (error) {
  _errorMessage = error.message;   // นี่คือสิ่งที่คาดไว้แล้ว
}
// ชนิดอื่นปล่อยผ่านขึ้นไป — จะเห็นตอนพัฒนา และเข้า crash report ตอนใช้จริง

สังเกตว่า PickException ถูกสร้างขึ้นมาใน pick_repository.dart เพื่อการนี้โดยเฉพาะ — เป็นหน้าที่ของ repository ที่จะแปลงเรื่องระดับ HTTP ให้เป็นความล้มเหลวที่ store เข้าใจ (เรื่องนี้จะทำเต็มรูปแบบใน Part 8)

ถ้าจำเป็นต้องจับกว้างจริง ๆ (เช่นชั้นบนสุดของแอป) ให้ log แล้ว rethrow — อย่าจับแล้วเงียบ

7. อ่านค่าที่ต้องใช้ก่อน await

ระหว่าง await โลกไม่ได้หยุด — ผู้ใช้กดปุ่มอื่นได้ การโหลดซ้ำเสร็จได้ รายการเปลี่ยนได้

// เสี่ยง — อ่านหลัง await
await repository.markDone(lineId);
final index = _lines.indexWhere((line) => line.id == lineId);
_lines[index] = ...;      // รายการอาจเปลี่ยนไปแล้ว index อาจไม่ใช่ตัวเดิม
// ปลอดภัย — อ่านก่อน await เก็บไว้ในตัวแปรของตัวเอง
final before = _lines[index];        // สำเนาที่ไม่มีใครแก้ได้
await repository.markDone(lineId);
// ใช้ before ต่อได้ตามที่ตั้งใจ

ใน lab ตัวแปร before ถูกอ่านไว้ก่อนเสมอ ซึ่งเป็นสิ่งที่ทำให้ _rollback ใน 4.13 ทำงานถูกต้อง

ประเด็นนี้เป็นครึ่งหนึ่งของปัญหาใหญ่กว่า — อีกครึ่งคือ “ผลของคำขอเก่ามาถึงช้ากว่าคำขอใหม่” ซึ่งจะแก้ด้วยตัวนับรุ่นใน 4.10

8. ปลดล็อกใน store กับตรวจ mounted ใน widget เป็นคนละเรื่อง

จุดที่สับสนกันบ่อย

storewidget
หลัง await ต้องตรวจอะไรไม่มี mounted ให้ตรวจต้องตรวจ mounted

สิ่งที่ห้ามทำคือข้ามงานเก็บกวาดเพราะคิดว่า “หน้าจอปิดไปแล้ว ไม่มีใครดู”

} finally {
  if (hasListeners) {              // ผิด
    _busyLineIds.remove(lineId);
    notifyListeners();

ถ้าผู้ใช้ปิดหน้าจอแล้วเปิดใหม่ด้วย store ตัวเดิม ล็อกจะยังค้างอยู่จากรอบก่อน — ปุ่มนั้นจะกดไม่ได้ตลอดกาลโดยไม่มีใครหาสาเหตุเจอ

รายละเอียดของ mounted ฝั่ง widget อยู่ใน 4.9

9. เมื่อต้องรอหลายอย่างพร้อมกัน

// เรียงกัน — ช้ากว่า เพราะรอทีละอัน
final tasks = await repository.fetchTasks();      // 300ms
final summary = await repository.fetchSummary();  // 300ms
// รวม 600ms
// พร้อมกัน
await Future.wait([
  repository.fetchTasks(),
  repository.fetchSummary(),
]);
// รวม ~300ms

แต่ Future.wait มีพฤติกรรมที่ต้องรู้ — ถ้ามีตัวใดตัวหนึ่งล้มเหลว ตัวรวมจะล้มเหลวทันที ทั้งที่ตัวอื่นยังวิ่งอยู่ และผลของตัวที่สำเร็จจะหายไป

ทางแก้ที่ตรงกับสิ่งที่ต้องการใน 4.7 หัวข้อ 10 คือให้แต่ละงาน จัดการความล้มเหลวของตัวเองข้างใน

Future<void> loadAll() async {
  await Future.wait([
    _loadTasks(),      // ข้างในมี try/catch ของตัวเอง ตั้ง _tasksState
    _loadSummary(),    // ข้างในมี try/catch ของตัวเอง ตั้ง _summaryState
  ]);
  // มาถึงตรงนี้แปลว่าทั้งคู่ "จบแล้ว" ไม่ใช่ "สำเร็จทั้งคู่"
}
รูปแบบเหมาะกับ
แต่ละงานจัดการ error เองบางส่วนล้มได้ หน้ายังใช้ได้ (พบบ่อยที่สุด)
ปล่อยให้ Future.wait ล้มทั้งชุดต้องได้ครบทุกอย่างถึงจะทำต่อได้

10. งานที่ไม่ต้องรอผล

บางงานสั่งแล้วไม่ต้องรอ เช่นรีเฟรชตัวเลขบนแท็บหลังจากปิดงานสำเร็จ

// เจตนาไม่ชัด — คนอ่านไม่รู้ว่าลืม await หรือตั้งใจ
badgeStore.refresh();
import 'dart:async';

// เจตนาชัด
unawaited(badgeStore.refresh());

แต่มีเงื่อนไขที่ห้ามลืม — งานนั้นต้องจัดการ error ของตัวเองให้ครบข้างใน เพราะไม่มีใครรออยู่รับ ถ้ามันโยน exception ออกมาจะกลายเป็น unhandled error ที่ทำให้แอปพังในที่ที่ดูไม่เกี่ยวกันเลย

อย่าใช้ unawaited กับงานที่ขั้นถัดไปต้องใช้ผลลัพธ์ — ถ้าไม่แน่ใจ ให้ await ไว้ก่อน

11. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ปุ่มค้าง “กำลังส่ง” ตลอดกาลปลดล็อกไม่ได้อยู่ใน finallyย้ายเข้า finally
ค้างเฉพาะบางกรณีที่หาไม่เจอมี return ก่อนถึงบรรทัดปลดล็อกfinally ครอบให้แล้ว
ล็อกค้างแม้ยังไม่ได้ยิงคำขอล็อกก่อนตรวจเงื่อนไขจบตรวจให้จบก่อนแล้วค่อยล็อก
ทุกปัญหาขึ้น “เกิดข้อผิดพลาด” เหมือนกันหมดcatch (e) จับทุกอย่างใช้ on X catch
บั๊กจริงไม่เคยถูกรายงานถูกกลืนใน catch กว้างlog แล้ว rethrow
โหลดหลายอย่างแล้วได้ข้อมูลไม่ครบFuture.wait ล้มทั้งชุดเพราะตัวเดียวให้แต่ละงานจัดการ error เอง
แอปพังในที่ที่ไม่เกี่ยวกันเลยงาน fire-and-forget ไม่จัดการ errorใส่ try/catch ในงานนั้น
เปิดหน้าจอใหม่แล้วปุ่มกดไม่ได้ข้ามการปลดล็อกเพราะหน้าจอปิดไปแล้วปลดล็อกเสมอ ไม่ต้องสนใจว่ามีใครดูอยู่

Future<void> confirmReceipt(String draftId) async {
  if (_submitting) return;                      // แก้ข้อ 5

  // ตรวจให้จบก่อนล็อก — แก้ข้อ 1 และข้อ 3 ของแบบฝึกหัดข้อ 3
  final index = _drafts.indexWhere((d) => d.id == draftId);
  if (index == -1) {
    _error = 'ไม่พบรายการที่ต้องการยืนยัน';
    notifyListeners();
    return;
  }
  final draft = _drafts[index];                 // อ่านก่อน await (หัวข้อ 7)

  _submitting = true;
  _error = null;
  notifyListeners();

  var succeeded = false;
  try {
    final receipt = await repository.confirm(draft);
    _receipts.add(receipt);
    succeeded = true;
  } on ReceiptException catch (error) {         // แก้ข้อ 3
    _error = error.message;
  } finally {                                   // แก้ข้อ 2 และข้อ 4
    _submitting = false;
    notifyListeners();
  }

  if (succeeded) {                              // แก้ข้อ 6
    unawaited(badgeStore.refresh());
  }
}

เรื่องข้อ 7 — ต้องเข้าไปดู badgeStore.refresh() ว่ามี try/catch ของตัวเองหรือยัง ถ้ายังไม่มี ต้องเติม ไม่ใช่ห่อ try/catch ตรงจุดเรียก เพราะ unawaited แปลว่าเราไม่ได้รออยู่แล้ว exception จะไม่วิ่งมาถึงจุดนี้

ข้อ 3 — ทำไม firstWhere ตรงนั้นอันตราย

สามชั้นซ้อนกัน

ชั้นที่หนึ่ง — firstWhere ที่ไม่มี orElse จะโยน StateError เมื่อหาไม่เจอ ไม่ได้คืน null

ชั้นที่สอง — มันอยู่ หลัง _submitting = true แต่ นอก try ดังนั้นเมื่อโยน จะไม่มีอะไรปลดล็อกให้เลย แม้จะมี finally ก็ตาม เพราะยังไม่ได้เข้า try

_submitting = true;          // ล็อกแล้ว
final draft = _drafts.firstWhere(...);   // โยนตรงนี้ → ออกจากฟังก์ชันเลย
try { ... } finally { ... }              // ไม่เคยถึงบรรทัดนี้

ผลคือปุ่มยืนยันค้างถาวร ต้องปิดแอป

ชั้นที่สาม — StateError คือชนิดที่ปกติหมายถึงบั๊ก ทำให้ตอนไล่หาสาเหตุจะสับสนว่าเป็นปัญหาที่ไหน

ทางแก้คือใช้ indexWhere ที่คืน -1 แทนการโยน แล้วตัดสินใจอย่างชัดเจนว่าจะทำอะไรเมื่อหาไม่เจอ — เป็นรูปแบบเดียวกับที่ markDone ใน lab ใช้

ลองต่อ: ใน test/pick_store_test.dart ให้ลองย้าย _busyLineIds.remove(lineId) ออกจาก finally ไปไว้ท้าย try แล้วรัน flutter test — จะเห็นว่าเทสต์ที่ทำให้ repository ล้มเหลวจับได้ทันทีว่า isBusy ยังเป็น true อยู่

13. สรุปท้ายบท

  • ฟังก์ชันออกได้หลายทางมากกว่าที่นึก — finally คือที่เดียวที่ทุกทางต้องผ่าน
  • return ใน try หรือ catch ไม่ข้าม finally
  • ตรวจเงื่อนไขให้จบก่อน แล้วค่อยล็อก
  • จับเฉพาะ exception ชนิดที่จัดการได้จริง ชนิดอื่นปล่อยผ่านให้เห็น
  • อ่านค่าที่ต้องใช้เก็บไว้ก่อน await
  • store ไม่มี mounted และห้ามข้ามงานเก็บกวาดเพราะหน้าจอปิด
  • Future.wait ล้มทั้งชุดเมื่อมีตัวเดียวล้ม — ให้แต่ละงานจัดการ error เอง
  • unawaited ใช้ได้เมื่องานนั้นจัดการ error ครบข้างในแล้ว

บทถัดไป: 4.9 จะข้ามไปฝั่ง widget — หลัง await หน้าจออาจถูกปิดไปแล้ว และการใช้ context ต่อจะทำให้เกิด exception ที่อ่านยากที่สุดชนิดหนึ่งใน Flutter
