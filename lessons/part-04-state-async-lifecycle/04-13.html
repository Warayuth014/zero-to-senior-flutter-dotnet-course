Optimistic UI แสดงผลเหมือนสำเร็จก่อน serverตอบเพื่อความเร็ว เหมาะ actionย้อนกลับง่าย/โอกาส failต่ำ แต่ warehouse stock/task commitเสี่ยงสูงจึงมักใช้ pendingหรือ pessimistic state พร้อม rollback/reconcileที่ชัด

1. Optimistic transaction

Future<void> togglePinned(Task task) async {
  final before = task.isPinned;
  _replace(task.copyWith(isPinned: !before));
  notifyListeners();
  try {
    await repository.setPinned(task.id, !before);
  } catch (e) {
    _replace(task.copyWith(isPinned: before));
    _error = 'บันทึกไม่สำเร็จ';
    notifyListeners();
  }
}

2. Rollback snapshot

เก็บค่าก่อน mutationและ operation ID หากมี optimisticหลายครั้งซ้อน rollbackเก่าไม่ควรทับ actionใหม่ ใช้ per-entity version/queueหรือ serialize command ไม่เก็บ reference mutableที่ถูกแก้ต่อจน snapshotไม่จริง

3. Pending state

ทางกลางคือแสดง row/card pendingทันทีแต่ไม่รวมใน committed stockจน serverตอบ ผู้ใช้เห็น responsivenessและเข้าใจยังไม่เสร็จ เมื่อ failให้ retry/remove pending เมื่อ timeout/unknownให้ reconcileก่อนส่งซ้ำ

4. Warehouse risk

การรับเข้า, หยิบ, putawayเปลี่ยน inventoryและอาจมีหลายเครื่องทำพร้อมกัน ควรรอ authoritative response/Conflictก่อนแสดง done WarehouseStoreหลาย commandตั้ง submittingแล้ว apply task/statusหลัง awaitซึ่งเป็น pessimisticที่เหมาะกว่า

5. Server reconciliation

Rollback localไม่พอหาก server commitแต่ responseหาย Queryด้วย operation ID/entity versionหรือ refresh authoritative list WarehouseStoreกรณีออกจาก receive flowระหว่าง awaitไม่ restore UIเก่าแต่ unawaited reload receivingเพื่อ reconcile

6. Error UX

บอกว่า actionถูก rollback, pendingหรือสถานะไม่แน่ชัด ไม่แสดง successแล้วเปลี่ยนเป็น errorเงียบ ๆ ให้ undoเฉพาะก่อน server commitหรือ endpointรองรับ compensating actionจริง

8. จุดพลาด

อย่า rollbackด้วยการ reloadแล้วคิดว่าปลอดภัยเสมอ Reloadอาจ fail/ช้าและมี actionใหม่แล้ว ต้องมี operation identity, conflict policyและ authoritative reconciliation
