1. ปัญหาที่บทนี้แก้

เมื่อหน้าจอต้องแสดงหลายอย่าง เรามักเก็บทุกอย่างไว้เป็นตัวแปรแยกกัน

List<PickLine> _lines = [];
int _remainingCount = 0;      // จำนวนที่ยังไม่เสร็จ
bool _allDone = false;        // เสร็จหมดหรือยัง
bool _hasLines = false;       // มีรายการไหม

ปัญหาคือทั้งสามตัวล่างคำนวณจากตัวบนได้ทั้งหมด — และทุกครั้งที่ _lines เปลี่ยน เราต้องจำอัปเดตทั้งสามตัวให้ตรง

วันหนึ่งจะมี method ที่ลืม แล้วหน้าจอจะแสดงว่า “เหลือ 3 รายการ” พร้อมข้อความ “เสร็จหมดแล้ว” พร้อมกัน

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
derived valueค่าที่คำนวณจากค่าอื่นได้
source of truthข้อมูลต้นทางที่ถือความจริง
impossible stateชุดค่าที่เป็นไปไม่ได้ในโลกจริง แต่โค้ดยอมให้เกิด
normalizeจัดรูปข้อมูลให้ไม่ซ้ำซ้อน
memoizeจำผลการคำนวณไว้ใช้ซ้ำ

3. Mental model: ข้อมูลชั้นเดียว

_lines            ← เก็บจริง (source of truth)
   │
   ├─ remainingCount   ← คำนวณ
   ├─ allDone          ← คำนวณ
   └─ hasLines         ← คำนวณ
ประโยคเดียวที่ต้องจำ: ถ้าคำนวณจากค่าอื่นได้ อย่าเก็บซ้ำ — เพราะข้อมูลสองชุดที่ต้อง “ตรงกัน” จะมีวันที่ไม่ตรงกันเสมอ นี่คือหลักเดียวกับ remaining ในแบบฝึกหัด D1.7

4. ดูของจริงใน lab

class PickStore extends ChangeNotifier {
  List<PickLine> _lines = const [];        // เก็บอย่างเดียว

  List<PickLine> get lines => List.unmodifiable(_lines);

  /// ค่าที่คำนวณจากค่าอื่นได้ ไม่เก็บซ้ำ (D1.7)
  int get remainingCount => _lines.where((line) => !line.done).length;

  bool get allDone => _lines.isNotEmpty && remainingCount == 0;
}

ผลที่ได้ทันที — เมื่อ _lines เปลี่ยนด้วยวิธีใดก็ตาม ตัวเลขทั้งหมดถูกต้องเสมอโดยอัตโนมัติ ไม่มีทางไม่ตรงกันได้เลย

เทสต์ยืนยันว่าค่าปรับตามโดยที่เราไม่ต้องเขียนโค้ดอัปเดตเลย

test('allDone เป็นจริงเมื่อไม่มีอะไรเหลือ', () async {
  await store.load();
  expect(store.allDone, isFalse);

  await store.markDone('L-1');
  await store.markDone('L-2');

  expect(store.remainingCount, 0);
  expect(store.allDone, isTrue);
});

สังเกตว่า markDone ไม่ได้แตะ remainingCount หรือ allDone เลย — มันแค่แก้ _lines แล้วที่เหลือถูกต้องตามไปเอง

5. สังเกตเรื่อง allDone

bool get allDone => _lines.isNotEmpty && remainingCount == 0;

ทำไมต้องมี _lines.isNotEmpty ด้วย — เพราะถ้าเขียนแค่ remainingCount == 0 รายการว่างเปล่าจะถือว่า “เสร็จหมดแล้ว” ซึ่งผิด

สถานการณ์remainingCount == 0ความหมายจริง
ยังไม่มีงานเลยจริงยังไม่มีงาน ไม่ใช่ทำเสร็จ
มี 3 งาน ทำครบแล้วจริงเสร็จหมดแล้ว

นี่คือเหตุผลที่การแยกสถานะ empty ออกจาก ready สำคัญ ซึ่งเป็นเรื่องเดียวกับที่คุยไว้ใน 2.7 หัวข้อ 3 และจะกลับมาอีกครั้งใน 4.7

6. เก็บรหัส ไม่เก็บ object

เมื่อต้องจำว่า “ผู้ใช้เลือกรายการไหนอยู่” มีสองทางเลือก

// เสี่ยง — เก็บ object ทั้งก้อน
PickLine? _selected;

// ปลอดภัย — เก็บรหัสแล้วหาเอา
String? _selectedId;
PickLine? get selected =>
    _lines.where((line) => line.id == _selectedId).firstOrNull;

ปัญหาของแบบแรกเกิดเมื่อโหลดข้อมูลใหม่ — _lines ได้ object ชุดใหม่จาก server แต่ _selected ยังชี้ object เก่าที่ข้อมูลอาจเปลี่ยนไปแล้ว

โหลดครั้งแรก:  _selected = PickLine(L-1, done: false)
ผู้ใช้กดเสร็จบนเครื่องอื่น
โหลดใหม่:      _lines มี PickLine(L-1, done: true)
              _selected ยังเป็น done: false   ← ข้อมูลค้าง

แบบที่สองหาใหม่ทุกครั้งจากข้อมูลล่าสุด จึงไม่มีทางค้าง — และถ้ารายการนั้นหายไปเลย selected จะเป็น null เองซึ่งถูกต้อง

ใน lab เราใช้หลักเดียวกันกับสิ่งที่ต้องจำข้ามการโหลด

/// บรรทัดที่กำลังส่งคำสั่งอยู่ — เก็บเป็น id ไม่ใช่ตำแหน่ง (1.8)
final Set<String> _busyLineIds = <String>{};

7. เมื่อไหร่ที่เก็บซ้ำได้

สถานการณ์เก็บซ้ำได้ไหมเหตุผล
นับจำนวนใน list ไม่กี่สิบรายการไม่ควรคำนวณเร็วมาก ไม่คุ้มความเสี่ยง
คำนวณหนักบนข้อมูลหมื่นรายการ ที่เรียกทุกครั้งที่วาดได้ ถ้าวัดแล้วต้องมีวิธีล้างค่าที่จำไว้เมื่อข้อมูลเปลี่ยน
ตัวเลขที่ server เป็นคนคำนวณต้องเก็บไม่ใช่ค่าที่คำนวณจากข้อมูลในมือได้

แถวสุดท้ายสำคัญและมักถูกเข้าใจผิด — เช่น “จำนวนงานที่ทำเสร็จวันนี้ทั้งคลัง” ดูเหมือนคำนวณได้ แต่ข้อมูลในมือเรามีแค่งานของตัวเอง ตัวเลขนั้นจึงเป็นข้อมูลจาก server ที่ต้องเก็บ ไม่ใช่ค่าที่คำนวณเอง

ถ้าเผลอคำนวณตัวเลขระดับคลังจากรายการที่โหลดมาบางส่วน จะได้ตัวเลขที่ดูสมเหตุสมผลแต่ผิด — และไม่มีใครสังเกตจนกว่าจะเอาไปเทียบกับรายงาน

8. getter ต้องไม่มีผลข้างเคียง

// ผิด — getter ที่เปลี่ยนอะไรบางอย่าง
int get remainingCount {
  _lastCheckedAt = DateTime.now();     // เปลี่ยนสถานะ
  notifyListeners();                    // แจ้งคนอื่น — อันตรายมาก
  return _lines.where((l) => !l.done).length;
}

ทบทวนจาก D1.7 — คนอ่านโค้ดเห็น store.remainingCount แล้วคิดว่าเป็นการอ่านค่าธรรมดา ถ้ามันไปแจ้งให้คนอื่นวาดใหม่ จะเกิดการวาดวนไม่รู้จบทันที เพราะ build อ่านค่านี้แล้วทำให้เกิด build รอบใหม่

getter ควรทำอย่างเดียวคือคำนวณแล้วคืนค่า

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ตัวเลขสองที่บนหน้าจอไม่ตรงกันเก็บค่าที่คำนวณได้ไว้ซ้ำเปลี่ยนเป็น getter
ขึ้นว่า “เสร็จหมดแล้ว” ทั้งที่ยังไม่มีงานลืมเงื่อนไข isNotEmptyเพิ่มเข้าไป
รายการที่เลือกไว้แสดงข้อมูลเก่าเก็บ object แทนรหัสเก็บรหัสแล้วหาใหม่
เลือกรายการที่ถูกลบไปแล้วค้างอยู่ไม่ได้ตรวจว่ายังมีอยู่ให้ getter คืน null เองเมื่อหาไม่เจอ
ตัวเลขสรุประดับคลังไม่ตรงกับรายงานคำนวณจากข้อมูลบางส่วนใช้ตัวเลขจาก server
หน้าจอวาดวนไม่หยุดgetter เรียก notifyListenersเอาผลข้างเคียงออกจาก getter

10. แบบฝึกหัด

หน้าจอตรวจนับซีเรียลเก็บข้อมูลแบบนี้

class CountState {
  int requiredQty = 10;              // ต้องนับกี่ชิ้น
  Set<String> scannedSerials = {};   // ซีเรียลที่ยิงแล้ว
  int scannedQty = 0;                // ยิงไปกี่ชิ้น
  int remainingQty = 10;             // เหลืออีกกี่ชิ้น
  bool isComplete = false;           // ครบหรือยัง
  bool isOverScanned = false;        // ยิงเกินหรือไม่
}
  1. ระบุว่าอะไรควรเก็บจริง อะไรควรคำนวณ
  2. เขียนใหม่ให้ไม่มีข้อมูลซ้ำซ้อน
  3. ยกตัวอย่างสถานะที่เป็นไปไม่ได้ ซึ่งโค้ดเดิมยอมให้เกิด
ดูแนวคำตอบและเหตุผล

ข้อ 1

ฟิลด์เก็บหรือคำนวณเหตุผล
requiredQtyเก็บมาจากใบงาน คำนวณจากอะไรไม่ได้
scannedSerialsเก็บเป็นข้อมูลที่ผู้ใช้สร้างขึ้น
scannedQtyคำนวณคือ scannedSerials.length
remainingQtyคำนวณคือ requiredQty - scannedQty
isCompleteคำนวณคือ scannedQty == requiredQty
isOverScannedคำนวณคือ scannedQty > requiredQty
class CountState {
  CountState({required this.requiredQty});

  final int requiredQty;
  final Set<String> _scanned = <String>{};

  Set<String> get scannedSerials => Set.unmodifiable(_scanned);   // D1.7

  int get scannedQty => _scanned.length;

  /// ไม่ให้ติดลบ เพราะ "เหลือ -2" ไม่มีความหมายกับผู้ใช้
  int get remainingQty => (requiredQty - scannedQty).clamp(0, requiredQty);

  bool get isComplete => scannedQty == requiredQty;

  bool get isOverScanned => scannedQty > requiredQty;

  /// ทางเดียวที่ข้อมูลเปลี่ยนได้ จึงรักษากฎได้ครบ
  bool addSerial(String serial) => _scanned.add(serial);
}

ข้อ 3 — สถานะที่เป็นไปไม่ได้ซึ่งโค้ดเดิมยอมให้เกิด

ชุดค่าทำไมเป็นไปไม่ได้เกิดได้อย่างไร
scannedSerials มี 3 ตัว แต่ scannedQty = 5นับจากชุดเดียวกันต้องเท่ากันมี method ที่เพิ่มลง set แต่ลืมบวก scannedQty
isComplete = true พร้อม remainingQty = 4ครบแล้วต้องไม่เหลืออัปเดตตัวหนึ่งแต่ลืมอีกตัว
isComplete = true พร้อม isOverScanned = trueครบพอดีกับเกินพร้อมกันไม่ได้เขียนเงื่อนไขคนละที่ไม่ตรงกัน
remainingQty = -2เหลือติดลบไม่มีความหมายยิงเกินแล้วลบตรง ๆ

สิ่งที่ได้จากการเขียนใหม่ — ทั้งสี่ชุดค่าข้างบน เขียนออกมาไม่ได้เลย เพราะไม่มีที่ให้เก็บค่าที่ขัดกัน ทุกอย่างคำนวณจากสองฟิลด์ที่เก็บจริง

นี่คือหลักคิดเดียวกับที่ D1.10 เรียกว่า “ทำให้สถานะที่ผิดเขียนออกมาไม่ได้” และที่ 3.14 ใช้กับ sealed class — ต่างกันแค่ที่นี่ใช้ getter

ทำไม addSerial คืน bool

เพราะ Set.add คืน false เมื่อมีอยู่แล้ว ซึ่งเป็นข้อมูลที่ผู้เรียกต้องใช้เพื่อแจ้งว่ายิงซ้ำ — เป็นรูปแบบเดียวกับที่ใช้ใน 3.7 และเป็นการไม่ทิ้งข้อมูลที่ภาษาให้มาฟรี ๆ

จุดที่ควรสังเกตเรื่อง clamp

การจำกัดไม่ให้ติดลบเป็นการตัดสินใจเชิงการใช้งาน ไม่ใช่เชิงเทคนิค — ผู้ใช้ที่เห็น “เหลือ -2” จะงง ส่วน “เหลือ 0” พร้อมคำเตือนว่ายิงเกินสื่อสารได้ดีกว่า และเรายังรู้ว่าเกินอยู่ผ่าน isOverScanned

ลองต่อ: ใน lab ลองเพิ่ม field int _remainingCount เข้าไปใน PickStore แล้วอัปเดตเฉพาะใน load แต่ลืมใน markDone — จากนั้นรันเทสต์ allDone เป็นจริงเมื่อไม่มีอะไรเหลือ จะเห็นว่าล้มเหลว ซึ่งเป็นการจำลองบั๊กที่บทนี้ป้องกัน

11. สรุปท้ายบท

  • ถ้าคำนวณจากค่าอื่นได้ อย่าเก็บซ้ำ
  • ข้อมูลสองชุดที่ต้องตรงกัน จะมีวันที่ไม่ตรงกัน
  • เก็บรหัสแล้วหา object เอา ดีกว่าเก็บ object ไว้
  • แยก “ไม่มีข้อมูล” ออกจาก “ทำเสร็จหมดแล้ว”
  • ตัวเลขที่ server คำนวณ ต้องเก็บ ไม่ใช่คำนวณเอง
  • getter ต้องไม่มีผลข้างเคียง
  • เป้าหมายคือทำให้สถานะที่ผิดเขียนออกมาไม่ได้
