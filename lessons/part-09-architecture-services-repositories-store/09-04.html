Dart part + extension: แบ่ง implementationของ libraryเดียวเป็นไฟล์ตามโดเมน ทำให้ extension เข้าถึงสมาชิก private ได้ แต่ยังเป็น ApiService type/lifetime เดียวกัน

1. โครงของจริง

// api_service.dart
part 'api/receiving_api.dart';
part 'api/picking_api.dart';

// api/receiving_api.dart
part of '../api_service.dart';
extension ReceivingApi on ApiService { /* getPO, scanReceiptPart */ }

2. ข้อดี

ลดไฟล์หลัก, group endpointตาม feature, reuse private _get/_post และ migrationจาก God serviceทำได้โดยไม่เปลี่ยน call sitesมาก

3. ข้อจำกัด

ทุก part เป็น libraryเดียว จึงมี importsรวม, private boundaryไม่แยกจริง, inject/mockingราย featureยาก และ extensionเพิ่ม interface stateไม่ได้

4. Extension resolution

Extension methodถูกเลือกแบบ staticจาก import/type ไม่ใช่ virtual dispatch จึงไม่ใช่ replacementของ repository interfaceสำหรับ polymorphic fake

5. เมื่อเหมาะ

เหมาะกับ codebaseขนาดกลางที่ transportเดียวและต้องจัดกลุ่ม endpointเร็ว โดยยังไม่ต้อง local cacheหรือ implementationหลายแบบ

6. ทางย้ายต่อ

class ReceivingApi implements ReceivingRepository {
  ReceivingApi(this.client);
  final JsonClient client;
  // ย้าย methods ทีละตัวจาก extension
}

คง facadeเดิมชั่วคราวเพื่อไม่ break screens

7. แบบฝึกหัด

ต้อง fake เฉพาะ Receivingแต่ใช้ Pickingจริงใน test ควรคง extensionหรือแยก class?

เฉลย

แยก ReceivingRepository/class ทำ injectionราย feature; extensionบน singletonไม่ให้ seamที่ตรงความต้องการ

8. หลักจำ

part แบ่งไฟล์ ไม่ได้แบ่ง architecture boundary; ใช้เพื่อ organization แล้วเพิ่ม interfaceเมื่อมีเหตุผลด้าน test/implementation
