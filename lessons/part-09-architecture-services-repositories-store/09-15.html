แตก God Storeตาม cohesive state + lifetime: ไม่ใช่แบ่งทุก 300 บรรทัด แต่แยก Receiving, Tasks, Inventory, CycleCountที่มี dependenciesและ workflowของตัวเอง

1. Evidence จากของจริง

WarehouseStore ประมาณ 1,684 บรรทัด ถือ repositoriesสี่ชุด, timer, receiving/tasks/picking/cycle count/navigationและ UI callbacks ทำให้ทุก feature share notify/lifetimeและแก้ไฟล์เดียวกัน

2. Map clusters

สร้างตาราง field→methods→repository→widgets→timer แล้วหากลุ่มที่แทบไม่ cross-reference เช่น CycleCount state/methodsสามารถเป็น sliceแรก

3. Extract façade-compatible slice

class CycleCountStore extends ChangeNotifier {
  CycleCountStore(this.repository);
  final CycleCountRepository repository;
  CycleCountState state = const CycleCountIdle();
  Future<void> load(String pallet) async { /* ... */ }
}

God Store delegateชั่วคราวเพื่อคง call sites

4. Split timers by owner

task pollingอยู่ TasksStoreและเริ่ม/หยุดตาม screen/app lifecycle ไม่ให้ WarehouseStore constructorเริ่ม timerแม้ userยังไม่เปิด feature

5. Cross-slice events

หลัง receiving successต้อง refresh tasks ใช้ coordinatorเรียกสอง storesหรือ typed domain eventที่ explicit อย่าให้ stores importกันวงกลม

6. Preserve SSOT

ระหว่าง migrationอย่า copy listทั้ง God Storeและslice ให้ delegate getter/actionไป ownerใหม่จน consumerย้ายครบแล้วค่อยลบของเดิม

7. แบบฝึกหัด

ควรแตก NavigationStoreก่อนหรือ CycleCountStoreก่อน?

แนวคำตอบ

เลือก cluster dependencyน้อย/มี tests/ขอบเขตชัด เช่น CycleCount; navigationอาจพัวพันทุก flowและควรแยกหลังเข้าใจ state ownership

8. Safety plan

characterization tests → extract state/action → delegate façade → migrate widgets → remove duplicate → analyze/testทุก commit; ไม่ rewrite God Storeครั้งเดียว
