1. ปัญหาที่บทนี้แก้

Part 1–8 สร้างของมาแล้วหลายชิ้น — ApiClient, TaskRepository, TaskStore, SessionStore, หน้าจอหลายจอ ตอนนี้คำถามเปลี่ยนจาก “เขียนอย่างไร” เป็น “ของชิ้นนี้ควรอยู่ที่ไหน”

คำถามนี้ตอบผิดแล้วไม่พังทันที มันพังตอนแก้ครั้งที่ยี่สิบ ตอนที่การเปลี่ยนสีปุ่มทำให้เทสต์ของ API พัง หรือตอนที่การเพิ่มฟิลด์หนึ่งช่องต้องแก้เจ็ดไฟล์

2. คำที่ต้องรู้ก่อน

คำแปลว่า
concernเรื่องหนึ่งเรื่องที่โปรแกรมต้องรับผิดชอบ เช่น “วาดหน้าจอ” หรือ “คุยกับเซิร์ฟเวอร์”
layer (ชั้น)กลุ่มไฟล์ที่รับผิดชอบ concern เดียวกัน
couplingระดับที่ของสองชิ้นต้องรู้จักกัน ยิ่งรู้จักกันมาก ยิ่งแก้ทีละชิ้นยาก
cohesionระดับที่ของในไฟล์เดียวกันเกี่ยวข้องกันจริง ๆ
architectureข้อตกลงว่าจะแบ่งชั้นอย่างไร และใครเรียกใครได้

3. แบบจำลองในหัว: แยกตามเหตุผลที่จะเปลี่ยน

โค้ดสองก้อนควรอยู่คนละไฟล์ เมื่อ มันเปลี่ยนด้วยเหตุผลคนละอย่าง

ไม่ใช่ “แยกเพราะไฟล์ยาว” และไม่ใช่ “แยกเพราะหนังสือบอก” ลองดูเหตุผลที่ทำให้โค้ดในแอปคลังต้องเปลี่ยนจริง ๆ

ใครสั่งให้เปลี่ยนเปลี่ยนอะไรควรอยู่ชั้น
หัวหน้าคลังบอกว่าปุ่มเล็กไปขนาด สี ตำแหน่งUI
เปลี่ยนขั้นตอนงาน ต้องยืนยันสองครั้งลำดับการทำงานLogic / Store
ทีมหลังบ้านเปลี่ยนชื่อ endpointpath, ชื่อฟิลด์Data / Repository
เปลี่ยนจาก HTTP เป็น SignalRวิธีขนส่งข้อมูลInfrastructure

สี่แถวนี้มาจากคนละคน คนละเวลา ถ้าอยู่ไฟล์เดียวกัน ทุกครั้งที่คนหนึ่งขอเปลี่ยน คนอื่นก็เสี่ยงพังไปด้วย

4. บททดสอบสองข้อ

เวลาสงสัยว่าแยกดีพอหรือยัง ถามสองคำถามนี้กับโค้ดที่มีอยู่

คำถามถ้าตอบว่า “ต้องแก้/พัง” แปลว่า
ถ้า endpoint เปลี่ยนจาก quantity เป็น qty ไฟล์ UI ต้องแก้ไหมUI รู้เรื่องรูปแบบข้อมูลจากเซิร์ฟเวอร์มากเกินไป
ถ้าเปลี่ยนจาก ListView เป็น GridView เทสต์ของ repository พังไหมตรรกะข้อมูลผูกกับวิธีวาดหน้าจอ

ในสองโปรเจกต์จริงที่จะอ่านกันตลอด Part นี้ คำตอบต่างกัน — และไม่ใช่เพราะฝีมือคนเขียนต่างกัน แต่เพราะเลือกจุดสมดุลคนละจุด

5. ทิศทางของการพึ่งพา

Widget  ──เรียก──▶  Store  ──เรียก──▶  Repository  ──เรียก──▶  ApiClient  ──▶  .NET

Widget  ◀──ข้อมูล──  Store  ◀──โมเดล──  Repository  ◀──JSON──   ApiClient  ◀──  .NET

ลูกศรเรียกชี้ลงทางเดียว และห้ามชี้ย้อนกลับ แปลว่า

ทำได้ทำไม่ได้
Widget รู้จัก StoreStore รู้จัก Widget
Store รู้จัก RepositoryRepository รู้จัก Store
Repository รู้จัก PalletPallet รู้จัก http หรือ material.dart

กฎนี้ตรวจได้ด้วยตาเปล่า — ดูบรรทัด import ที่หัวไฟล์ ถ้า store มี import 'package:flutter/material.dart' แปลว่ามีอะไรผิดที่

ดูของจริงได้เลย wms_absolute_mobile/lib/features/warehouse/warehouse_store.dart เปิดมาบรรทัดที่สองเป็น import 'package:flutter/foundation.dart' ไม่ใช่ material.dart — นั่นตั้งใจ

6. ราคาของการแยก

การแยกชั้นไม่ฟรี ต้องจ่ายสามอย่าง

จ่ายอะไรรู้สึกตอนไหน
ไฟล์เยอะขึ้น ต้องเปิดหลายไฟล์กว่าจะเข้าใจงานเดียวตอนคนใหม่เข้าทีม
เพิ่มฟิลด์หนึ่งช่องต้องแก้หลายชั้นตอนเพิ่มฟีเจอร์เล็ก
ต้องตั้งชื่อและออกแบบ interfaceตอนเริ่มฟีเจอร์ใหม่

จะยอมจ่ายก็ต่อเมื่อได้อะไรกลับมา ซึ่งได้จริงสามอย่างเช่นกัน คือ ทดสอบทีละชิ้นได้, แก้ทีละชิ้นได้ และ ใช้ซ้ำได้ ถ้าฟีเจอร์นั้นไม่ต้องการทั้งสามอย่าง ก็ไม่ต้องแยก

7. สัญญาณว่ายังปนกันอยู่

  • widget เรียก jsonDecode
  • widget แปลเลข status เป็นข้อความเอง
  • ApiClient เปิด dialog
  • repository ถือ BuildContext
  • โมเดลข้อมูล import material.dart เพื่อเลือกสี
  • ทุกฟีเจอร์แก้ไฟล์เดียวกัน แล้ว merge ชนกันทุกครั้ง

8. แบบฝึกหัด

งานสี่อย่างนี้ควรอยู่ชั้นไหน และเพราะอะไร

  1. ตัดช่องว่างหัวท้ายของบาร์โค้ดที่สแกนมา
  2. timeout 15 วินาที
  3. แถวที่ผู้ใช้เลือกอยู่ตอนนี้
  4. กฎว่ารับของเกินจำนวนใน PO ไม่ได้
แนวคำตอบ

1. ขอบของการรับข้อมูล — ที่ที่ค่าจากเครื่องสแกนเข้ามา ทำที่เดียวก่อนส่งต่อ ไม่ใช่ให้ทุกที่ที่ใช้ค่าต้องจำว่าต้อง trim

2. Infrastructure ใน ApiClient — เป็นเรื่องของการขนส่ง จอไม่ควรรู้ว่ากี่วินาที

3. Presentation หรือ Store — ถ้าเลือกแล้วมีผลแค่เรื่องไฮไลต์ ให้อยู่ในจอ แต่ถ้าขั้นตอนถัดไปต้องใช้ว่าเลือกอะไร ให้อยู่ใน store

4. ทั้งสองที่ — เซิร์ฟเวอร์ต้องบังคับเพราะเป็นความจริง ส่วนแอปตรวจก่อนเพื่อไม่ให้ผู้ใช้ยิงไปเสียเที่ยว แต่ถ้าสองที่ไม่ตรงกัน เซิร์ฟเวอร์ถูกเสมอ

9. สรุป

  • แยกเพราะ “เหตุผลที่จะเปลี่ยนต่างกัน” ไม่ใช่เพราะไฟล์ยาว
  • ลูกศรเรียกชี้ทางเดียว ตรวจได้จากบรรทัด import
  • การแยกมีราคา ยอมจ่ายเมื่ออยากทดสอบ แก้ หรือใช้ซ้ำทีละชิ้น

บทหน้า: เอากฎนี้ไปจับกับโค้ดจริงหนึ่งจอ แล้วดูว่าบรรทัดไหนควรย้ายไปไหน
