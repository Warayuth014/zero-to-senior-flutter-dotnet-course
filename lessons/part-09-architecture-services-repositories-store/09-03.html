2. หน้าตาของ ApiService

class ApiService {
  static final ApiService _instance = ApiService._internal();

  factory ApiService() => _instance;

  ApiService._internal();
  ...
}

สามบรรทัดนี้คือรูปแบบที่เรียกว่า singleton อ่านทีละบรรทัด

บรรทัดทำอะไร
ApiService._internal()constructor ที่ขึ้นต้นด้วย _ แปลว่าเรียกได้เฉพาะในไฟล์นี้ ข้างนอกสร้างเองไม่ได้
static final _instanceสร้างไว้ตัวเดียว ตอนที่ถูกใช้ครั้งแรก
factory ApiService()คนเขียน ApiService() ได้เหมือนสร้างใหม่ แต่ได้ตัวเดิมกลับไปเสมอ
factory constructor คือ constructor ที่ไม่จำเป็นต้องสร้างวัตถุใหม่ — จะคืนตัวที่มีอยู่แล้วก็ได้ ต่างจาก constructor ปกติที่สร้างใหม่เสมอ

3. ปัญหาที่ singleton แก้ให้จริง

ApiService ถือของที่ควรมีชุดเดียวทั้งแอป

static String? _cachedBase;

static Future<String> _resolveBase() async {
  if (_cachedBase != null) return _cachedBase!;

  final custom = await _configService.getCustomBase();
  final isAndroid = !kIsWeb && Platform.isAndroid;

  final candidates = <String>[
    if (custom != null) custom,
    if (isAndroid) 'http://10.0.2.2:$_defaultPort',
    if (!isAndroid) 'http://localhost:$_defaultPort',
  ];

  for (final base in candidates) {
    ...ลองเปิด socket ดูว่าต่อติดไหม...
  }
}

การหา base URL ต้องลองเปิด socket จริง ซึ่งช้า ถ้าทุกจอสร้าง ApiService ของตัวเอง ทุกจอจะต้องลองใหม่ การมีตัวเดียวทำให้ _cachedBase ใช้ร่วมกันได้ — นี่คือเหตุผลที่ถูกต้อง ไม่ใช่ความขี้เกียจ

4. ApiResult: ความล้มเหลวเป็นค่า ไม่ใช่ข้อยกเว้น

class ApiResult<T> {
  final bool success;
  final T? data;
  final String? error;
  final int? statusCode;

  ApiResult.success(this.data) : success = true, error = null, statusCode = 200;
  ApiResult.error(this.error, {this.statusCode}) : success = false, data = null;

  bool get isNotFound => statusCode == 404;
}

ต่างจาก lab ของเราที่โยน ApiException ออกมา ตรงนี้คืนกล่องที่บอกว่าสำเร็จหรือไม่ ผลของการเลือกแบบนี้คือ

ได้เสีย
ลืม handle ไม่ได้ง่าย ๆ เพราะต้องอ่าน .data ผ่าน .success ก่อนdata เป็น T? เสมอ ต้องเขียน ! หรือเช็ค null ทุกที่
อ่านเส้นทางความล้มเหลวได้จากลายเซ็นเมธอดความล้มเหลวเป็น String ตัวเดียว แยกชนิดไม่ได้เหมือน ApiFailureKind (7.9)
ไม่มี exception หลุดขึ้นไปทำแอปพังความล้มเหลวเงียบได้ ถ้าคนเรียกไม่เช็ค success

9.13 จะเทียบสามแบบนี้อย่างละเอียด ตอนนี้แค่รู้ว่าเป็นทางเลือกที่ต่างกัน ไม่ใช่ผิดถูก

class _PackingScreenState extends State<PackingScreen> {

}

จอไปหยิบ ApiService มาเองจากอากาศ ไม่มีใครส่งให้ ผลตามมาสามข้อ

ผลตามมารู้สึกตอนไหน
เทสต์จอนี้โดยใส่ API ปลอมไม่ได้ ต้องแก้โค้ดจอก่อนตอนอยากเขียนเทสต์
ไม่มีที่เดียวที่บอกว่าจอนี้ต้องพึ่งอะไรบ้าง ต้องอ่านทั้งไฟล์ตอนคนใหม่อ่านโค้ด
สลับเป็น API ของ server ทดสอบเฉพาะบางจอไม่ได้ตอนแก้บั๊กที่เกิดเฉพาะที่
สังเกตว่าปัญหาทั้งสามไม่ได้มาจาก “มีตัวเดียว” แต่มาจาก “หยิบเอง” — มีตัวเดียวแต่ส่งเข้าไปทาง constructor ก็ได้ ซึ่ง 9.8 จะพูดถึง

7. แบบฝึกหัด

สมมติต้องเพิ่มความสามารถ “ถ้าเจอ 401 ให้เด้งกลับหน้าเข้าสู่ระบบทั้งแอป” ตามที่ 8.7 สอน

  1. ในโครงของ wmsapp จะใส่ตรงไหน
  2. ในโครงของ lab จะใส่ตรงไหน
แนวคำตอบ

1. ใส่ได้ที่เดียว คือใน _get/_post ของ ApiService ซึ่งดีมาก เพราะทุกคำขอผ่านที่นั่นหมด แต่มีปัญหาต่อทันทีคือ ApiService จะแจ้งใครว่าให้เด้ง? มันไม่มี BuildContext และไม่ควรมี ทางออกคือ callback แบบเดียวกับ onTokenChanged ใน 8.4 หรือ onToast ที่ wms_absolute_mobile ใช้

2. ที่เดียวกันในหลักการ คือชั้นล่างสุด แต่ lab แยกไว้ให้แล้วว่าใครตัดสินใจ — ApiClient แค่แปลง 401 เป็น ApiFailureKind.unauthorized ส่วน SessionStore.handleUnauthorized() เป็นคนตัดสินใจว่าจะออกจากระบบ

ข้อต่างที่สำคัญ: ในแบบแรก “ตรวจเจอ” กับ “ตัดสินใจ” อยู่ที่เดียวกัน ทำให้เปลี่ยนนโยบายทีหลังต้องแก้ในชั้นขนส่ง

8. สรุป

  • singleton แก้ปัญหา “ของที่ควรมีชุดเดียว” ได้จริง เช่น base URL ที่หามาแล้ว
  • ปัญหาไม่ได้อยู่ที่มีตัวเดียว แต่อยู่ที่จอหยิบเองโดยไม่มีใครส่งให้
  • ApiResult<T> ทำให้ความล้มเหลวเป็นค่าที่ต้องอ่าน แลกกับการที่ data เป็น null ได้เสมอ
