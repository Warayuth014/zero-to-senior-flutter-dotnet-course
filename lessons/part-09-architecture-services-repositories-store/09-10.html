1. หลัก

Unidirectional data flow: เหตุการณ์ไหลขึ้น ข้อมูลไหลลง และไม่มีทางลัด
            ผู้ใช้กดปุ่ม
                 │  เหตุการณ์ไหลขึ้น
                 ▼
  Widget ──────────────────▶ Store ──────▶ Repository ──▶ เซิร์ฟเวอร์
    ▲                          │
    │  ข้อมูลไหลลง             │ เปลี่ยนสถานะ
    └──────────────────────────┘  notifyListeners()

จอไม่เคยเปลี่ยนสถานะเอง มันแค่บอกว่ามีอะไรเกิดขึ้น แล้วรอดูว่า store จะบอกอะไรกลับมา

2. ไล่จริงทีละขั้น

ผู้ใช้กดปุ่ม “ล็อก” ที่แถว PLT-001

ขั้นที่ไหนเกิดอะไร
1pallet_screen_v2.dartonPressed: () => store.hold(pallet)
2pallet_store.dartเช็คว่ากำลังทำอยู่ไหม, เพิ่มลง _busyCodes, notifyListeners()
3FlutterListenableBuilder วาดใหม่ ปุ่มกลายเป็นจาง กดไม่ได้
4pallet_repository.dartPOST พร้อม Idempotency-Key
5เซิร์ฟเวอร์ล็อกจริง ตอบพาเลทที่อัปเดตแล้ว
6pallet_repository.dartแปลง JSON เป็น Pallet
7pallet_store.dartแทนที่แถวนั้นในลิสต์, เอาออกจาก _busyCodes, notifyListeners()
8Flutterวาดใหม่ แถวนั้นกลายเป็น “ล็อกแล้ว”

สังเกตว่าขั้นที่ 3 กับ 8 คือการวาดใหม่ทั้งคู่ และในทั้งสองครั้ง จอวาดจากสิ่งที่ store บอก ไม่ได้จำว่าตัวเองเพิ่งทำอะไรไป

3. ทำไมห้ามลัด

ทางลัดที่คนอยากทำที่สุดคือให้จอเปลี่ยนค่าเองเลยหลังกด เพื่อให้ตอบสนองเร็ว

// อย่าเขียนแบบนี้
onPressed: () {
  setState(() => pallet.onHold = true);   // เปลี่ยนเองเลย
  store.hold(pallet);                      // แล้วค่อยบอก store
}

ปัญหาโผล่ตอนคำสั่งล้มเหลว — จอบอกว่าล็อกแล้ว เซิร์ฟเวอร์บอกว่าไม่ได้ล็อก และไม่มีใครแก้จอกลับ ผู้ใช้เดินไปหยิบพาเลทที่คิดว่าล็อกไว้แล้ว เจอว่ามีคนอื่นเอาไปแล้ว

ในงานคลัง หน้าจอที่ตอบสนองเร็วแต่โกหก แย่กว่าหน้าจอที่ช้าแต่จริง

ถ้าอยากได้ทั้งเร็วและถูก ต้องทำแบบที่เรียกว่า optimistic update ซึ่งต้องมีการย้อนกลับเมื่อล้มเหลว และการย้อนกลับนั้นต้องอยู่ใน store ไม่ใช่ในจอ

4. สิ่งที่บังคับให้ไหลทางเดียว

กฎบังคับด้วยอะไร
store เปิด dialog เองไม่ได้ไม่ import material.dart
จอแก้ลิสต์ของ store ไม่ได้List.unmodifiable
โมเดลถูกแก้กลางทางไม่ได้ฟิลด์เป็น final ทั้งหมด ใช้ copyWith แทน
repository จำสถานะไม่ได้ประกาศเป็น const constructor ไม่มี field ที่เปลี่ยนได้

ทั้งสี่ข้อไม่ใช่ข้อตกลงในเอกสาร แต่เป็นสิ่งที่คอมไพเลอร์บังคับ — กฎที่คอมไพเลอร์บังคับไม่ได้ คือกฎที่จะถูกละเมิดในวันที่รีบ

5. เมื่อ store ต้องบอกจอให้ทำอะไร

บางเรื่องจอต้องทำจริง ๆ เช่นแสดงข้อความ สั่นเครื่อง หรือเล่นเสียง store สั่งเองไม่ได้ จึงต้องมีทางบอก สองแบบที่ใช้กันคือ

แบบหน้าตาเหมาะกับ
สถานะที่จออ่านString? actionMessage ใน storeข้อความที่ค้างอยู่ได้ เช่น แถบผิดพลาด
callbackvoid Function(String msg)? onToastเหตุการณ์ที่เกิดครั้งเดียว เช่น toast, เสียงบี๊บ

เลือกผิดแล้วจะเจออาการคลาสสิก คือ toast เด้งซ้ำทุกครั้งที่จอวาดใหม่ เพราะเอาเหตุการณ์ไปเก็บเป็นสถานะแล้วลืมล้าง

// wms_absolute_mobile เลือกแบบ callback สำหรับเหตุการณ์ครั้งเดียว
void Function(String msg, {bool err})? onToast;
void Function(bool ok)? onFlash;

6. ตรวจว่าไหลทางเดียวจริงไหม

สามคำถามที่ตอบได้เร็ว

  1. ใน widget มี setState ที่แก้ข้อมูลของงาน (ไม่ใช่ของหน้าจอ) ไหม
  2. ใน store มี import 'package:flutter/material.dart' ไหม
  3. มีที่ไหนที่แก้ค่าในโมเดลโดยตรงไหม เช่น pallet.onHold = true

ถ้าตอบว่ามีข้อใดข้อหนึ่ง แปลว่ามีทางลัดอยู่ ให้ตามไปดูว่ามันแก้ปัญหาอะไร แล้วหาทางแก้ปัญหานั้นโดยไม่ลัด

7. แบบฝึกหัด

ผู้ใช้บ่นว่ากดปุ่มล็อกแล้วต้องรอสองวินาทีกว่าแถวจะเปลี่ยน อยากให้เปลี่ยนทันที ออกแบบวิธีที่ทั้งเร็วและไม่โกหก

แนวคำตอบ

ทำ optimistic update ใน store โดยเก็บค่าเดิมไว้ก่อน

Future<void> hold(Pallet pallet) async {
  if (_busyCodes.contains(pallet.code)) return;
  _busyCodes.add(pallet.code);

  final previous = _pallets;                    // เก็บของเดิมไว้ทั้งลิสต์
  _replace(pallet.copyWith(onHold: true));      // เปลี่ยนให้เห็นทันที
  notifyListeners();

  try {
    final updated = await repository.hold(pallet.code, commandId: ...);
    _replace(updated);                          // ยึดของจริงจากเซิร์ฟเวอร์
  } on PalletFailure catch (failure) {
    _pallets = previous;                        // ล้มเหลว ย้อนกลับ
    _failure = failure;
  } finally {
    _busyCodes.remove(pallet.code);
    notifyListeners();
  }
}

สามจุดที่ต้องคิดต่อ

  • ยังไหลทางเดียวอยู่ เพราะการเปลี่ยนและการย้อนกลับอยู่ใน store ทั้งคู่ จอไม่รู้เรื่องเลย
  • ห้ามทำกับ PalletFailure ที่ไม่รู้ผล — ถ้า POST timeout เราไม่รู้ว่าเซิร์ฟเวอร์ล็อกไปแล้วหรือยัง (7.10) ย้อนกลับก็ผิด ไม่ย้อนก็ผิด ทางที่ถูกคือโหลดใหม่แล้วดูของจริง
  • ต้องเก็บทั้งลิสต์ ไม่ใช่เก็บแค่ bool เดิมของแถวนั้น เพราะระหว่างรออาจมีการโหลดใหม่ที่เปลี่ยนลิสต์ทั้งชุด

ข้อสองคือเหตุผลที่ optimistic update ไม่ควรใส่ทุกที่ — มันเหมาะกับงานที่ล้มเหลวแล้วไม่เสียหาย เช่นกดถูกใจ ไม่ใช่งานที่ผลกระทบเป็นของจริงในคลัง

8. สรุป

  • เหตุการณ์ขึ้น ข้อมูลลง จอไม่เปลี่ยนสถานะของงานเอง
  • ทางลัดที่ทำให้เร็วขึ้น แลกมาด้วยหน้าจอที่อาจโกหก
  • กฎที่คอมไพเลอร์บังคับได้ ดีกว่ากฎที่เขียนไว้ในเอกสาร
  • เหตุการณ์ครั้งเดียวใช้ callback สถานะที่ค้างอยู่ได้ใช้ field
