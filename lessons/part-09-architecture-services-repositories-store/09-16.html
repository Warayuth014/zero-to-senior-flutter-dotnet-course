3. โครงของเทสต์ที่ต้องเข้าใจก่อนทำโจทย์

void runSharedBehaviourTests(Widget Function(http.Client client) build) { ... }

group('พฤติกรรมเดียวกัน · รุ่นรวมทุกอย่างไว้ในจอ', () {
  runSharedBehaviourTests((client) => PalletScreenV1(client: client, zone: 'A1'));
});

group('พฤติกรรมเดียวกัน · รุ่นแยกชั้น', () {
  runSharedBehaviourTests((client) {
    final api = ApiClient(baseUrl: baseUrl, client: client);
    return PalletScreenV2(store: PalletStore(RemotePalletRepository(api)), zone: 'A1');
  });
});

กุญแจอยู่ที่ ทั้งสองรุ่นรับ http.Client เป็นจุดเดียวที่ของปลอมเข้าไป ทำให้เขียนเทสต์ชุดเดียวแล้วรันกับทั้งคู่ได้ — เป็นเทคนิคที่ใช้ได้กับทุก refactor ที่ต้องพิสูจน์ว่าพฤติกรรมไม่เปลี่ยน

4. โจทย์

ในโฟลเดอร์ lib/architecture_lab/ มีจอที่ยังไม่ได้แยก คือจอ “ย้ายพาเลทไปตำแหน่งใหม่” ให้เขียนเองตั้งแต่ต้นตามนี้

เขียน move_screen_v1.dart แบบรวมทุกอย่างไว้ในจอก่อน ตามพฤติกรรมนี้

สิ่งที่จอทำ
สแกนรหัสพาเลท แล้ว GET /api/WMS/mobile_pallets/{code} เพื่อดูรายละเอียด
แสดงตำแหน่งว่างที่แนะนำ จาก GET /api/WMS/mobile_locations/free?zone={zone}
สแกนรหัสตำแหน่งปลายทาง แล้วตรวจว่าอยู่ในรายการที่ว่างไหม
กดยืนยัน แล้ว POST /api/WMS/mobile_pallets/{code}/move พร้อม Idempotency-Key
สำเร็จแล้วล้างหน้าจอ พร้อมรับพาเลทใบถัดไป

แล้ว refactor เป็น move_repository.dart + move_store.dart + move_screen_v2.dart

#เกณฑ์บท
1เทสต์พฤติกรรมชุดเดียวกันผ่านทั้ง v1 และ v2 อย่างน้อย 6 ข้อ9.2

11กดยืนยันซ้ำระหว่างรอ ต้องยิงคำสั่งครั้งเดียว9.7

6. คำใบ้สำหรับข้อที่ยาก

เกณฑ์ 14 — ตรวจก่อนยิง แต่ไม่ทำให้เซิร์ฟเวอร์เป็นเพียงพิธี

กฎนี้ควรอยู่บนโมเดลหรือใน store ไม่ใช่ในจอ (9.12)

// ใน store
void scanDestination(String code) {
  final match = _freeLocations.where((l) => l.code == code).firstOrNull;
  if (match == null) {
    _failure = const MoveFailure('ตำแหน่งนี้ไม่ว่าง หรือไม่อยู่ในโซนนี้');
    notifyListeners();
    return;
  }
  _destination = match;
  _failure = null;
  notifyListeners();
}

แต่ยังต้องปล่อยให้เซิร์ฟเวอร์ปฏิเสธได้อยู่ดี เพราะรายการที่ว่างอาจเก่าไปแล้วตั้งแต่ตอนโหลด — การตรวจฝั่งแอปคือความสะดวก ไม่ใช่ความจริง (9.1 แบบฝึกหัดข้อ 4)

เกณฑ์ 10 — สแกนใบใหม่แซงใบเก่า

ใช้เลขรุ่นแบบเดียวกับ PalletStore.load แต่ระวังจุดที่ต่าง คือที่นี่ค่าที่ต้องทิ้งไม่ใช่แค่ลิสต์ แต่รวมถึงตำแหน่งปลายทางที่สแกนไว้ด้วย

เกณฑ์ 15 — เทสต์ที่ไม่มี widget

class _ScriptedMoveRepository implements MoveRepository {
  final List<Completer<PalletDetail>> _lookups = [];

  @override
  Future<PalletDetail> lookup(String code) {
    final completer = Completer<PalletDetail>();
    _lookups.add(completer);
    return completer.future;     // ค้างไว้จนกว่าเทสต์จะสั่งตอบ
  }
}

7. ข้อผิดพลาดที่พบบ่อยตอนทำ lab นี้

อาการสาเหตุวิธีแก้
เทสต์ v1 กับ v2 ต้องเขียนคนละชุดตั้ง Key ไม่เหมือนกันใช้ key เดียวกันทั้งสองรุ่น
ข้อความผิดพลาดสองรุ่นไม่ตรงกันv1 แปลจากเลข status v2 แปลจาก kindให้ v1 แปลด้วยคำเดียวกันก่อน แล้วค่อยย้าย
store พังตอนเทสต์ว่า Bad state: Future already completedตัวปลอมตอบสองครั้งตรวจว่า completeAt ชี้ index ถูก
วงหมุนค้างลืม finallyตั้ง _loading = false ใน finally เสมอ
สแกนใบใหม่แล้วปลายทางเก่ายังค้างล้างไม่ครบรวมการล้างไว้ในเมธอดเดียว

8. แบบทดสอบตัวเองก่อนจบ Part 9

  1. “แยกเพราะเหตุผลที่จะเปลี่ยนต่างกัน” หมายความว่าอย่างไร (9.1)
  2. บททดสอบสองข้อที่ใช้ตรวจว่าแยกดีพอหรือยัง คืออะไร (9.1)
  3. จอที่เก็บ Map<String, dynamic> มีปัญหาอะไร (9.2)
  4. ทำไม refactor ที่ถูกต้องต้องมีเทสต์ชุดเดิมผ่าน (9.2)
  5. singleton แก้ปัญหาอะไรได้จริง และไม่ได้แก้อะไร (9.3)
  6. ApiResult<T> ได้อะไรและเสียอะไร (9.3, 9.13)
  7. part ต่างจาก import อย่างไร (9.4)
  8. ทำไม extension บนคลาสรูปธรรมถึงสวมของปลอมไม่ได้ (9.4)
  9. อะไรที่ไม่ควรอยู่ใน repository interface (9.5)
  10. ทำไมการอ่านคำตอบต้องอยู่นอก try (9.6)
  11. ทำไม initialLoading ต้องเป็น getter (9.7)
  12. ทำไม store ไม่ควร import material.dart (9.7, 9.10)
  13. constructor injection คืออะไร ต้องใช้ library ไหม (9.8)
  14. composition root คือที่ไหน (9.8)
  15. อาการของการมีแหล่งความจริงสองที่ เป็นอย่างไร (9.9)
  16. ค่าไหนควรอยู่ในจอ ค่าไหนควรอยู่ใน store (9.9)
  17. optimistic update ห้ามใช้กับกรณีไหน (9.10)
  18. ควรยก widget ขึ้นเป็นของกลางเมื่อไหร่ (9.11)
  19. เมื่อไหร่ควรเพิ่มชั้น use case (9.12)
  20. ความล้มเหลวชนิดไหนที่ไม่ควรแปลให้ผู้ใช้ (9.13)
  21. ขั้นแรกของการแยกจอใหญ่คืออะไร (9.14)
  22. ทำไมห้ามแก้ปัญหา store ใหญ่ด้วยการแยกข้อมูลออกเป็นสองชุด (9.15)

9. สรุปท้าย Part 9

สิ่งที่ทำได้แล้ว

  • ตัดสินได้ว่าโค้ดก้อนหนึ่งควรอยู่ชั้นไหน โดยมีเหตุผลที่ตรวจสอบได้
  • อ่านสถาปัตยกรรมสามแบบออก และบอกได้ว่าแต่ละแบบแลกอะไร
  • เขียน repository interface ด้วยคำของงาน
  • เขียนตัวจริงที่แปลง JSON เป็นโมเดล และแปลความล้มเหลวที่จุดเดียว
  • เขียน store ที่เป็นเจ้าของสถานะ ทดสอบได้โดยไม่ต้องมี widget
  • ประกอบของทั้งหมดที่จุดเดียว และสลับเป็นของปลอมในเทสต์ได้
  • มองออกว่าข้อมูลถูกเก็บซ้ำตรงไหน
  • วางแผนแยกจอใหญ่และ store ใหญ่โดยไม่ทำให้พฤติกรรมเปลี่ยน

สิ่งที่ยังไม่ได้ทำและจะทำที่ไหน
