When to Add Domain Layer

Part 9: App Architecture

สารบัญบทเรียน

  1. ชั้นที่ยังไม่ได้พูดถึง
  2. หน้าตาถ้าเพิ่มเข้ามา
  3. คำถามที่ต้องตอบก่อนเพิ่ม
  4. ทางเลือกที่เบากว่าการเพิ่มชั้น
  5. ของจริงทั้งสองโปรเจกต์ไม่มีชั้นนี้
  6. กรณีที่คุ้มค่าจริง
  7. แบบฝึกหัด
  8. สรุป
ระดับ: สูงใช้เวลา: 45–60 นาทีลงมือทำ: ตัดสินใจจากโค้ดจริงว่าควรเพิ่มชั้นหรือไม่
ต้องผ่านอะไรมาก่อน: 9.5–9.11
จบบทนี้แล้วจะทำได้: ตอบได้ว่าเมื่อไหร่ควรเพิ่มชั้น domain และเมื่อไหร่มันเป็นแค่พิธีกรรม

1. ชั้นที่ยังไม่ได้พูดถึง

ตอนนี้แอปมีสี่ชั้น

Widget  →  Store  →  Repository  →  ApiClient

ในหนังสือสถาปัตยกรรมมักมีชั้นที่ห้าคั่นระหว่าง store กับ repository เรียกว่า domain layer หรือ use case

Widget  →  Store  →  UseCase  →  Repository  →  ApiClient
Use case คือคลาสที่ทำงานทางธุรกิจหนึ่งอย่างให้จบ โดยไม่รู้จักหน้าจอและไม่รู้จัก HTTP เช่น HoldPallet, ConfirmCycleCount

2. หน้าตาถ้าเพิ่มเข้ามา

class HoldPallet {
  const HoldPallet(this.pallets, this.audit);

  final PalletRepository pallets;
  final AuditRepository audit;

  Future<Pallet> call(Pallet pallet, {required String username}) async {
    if (pallet.onHold) {
      throw const PalletFailure('พาเลทนี้ถูกล็อกอยู่แล้ว');
    }
    final held = await pallets.hold(pallet.code, commandId: ...);
    await audit.record('hold', pallet.code, by: username);
    return held;
  }
}

store จะเรียกแค่ await holdPallet(pallet, username: ...) โดยไม่รู้ว่าข้างในมีสองขั้น

3. คำถามที่ต้องตอบก่อนเพิ่ม

คำถามถ้าตอบว่าใช่
งานนี้ต้องประสาน repository มากกว่าหนึ่งตัวไหมเป็นเหตุผลที่ดี
มีกฎธุรกิจที่ต้องตรวจก่อนยิง และกฎนั้นใช้ในหลายจอไหมเป็นเหตุผลที่ดี
มีลำดับหลายขั้นที่ต้องทำให้ครบ ไม่งั้นข้อมูลค้างครึ่ง ๆ ไหมเป็นเหตุผลที่ดี
มี store หลายตัวที่ต้องทำงานเดียวกันนี้ไหมเป็นเหตุผลที่ดี
เพิ่มเพราะไดอะแกรมในบทความบอกว่าต้องมีใช่ไหมไม่ใช่เหตุผล

ถ้าไม่มีข้อไหนตอบว่าใช่ ผลของการเพิ่มชั้นคือคลาสที่มีเมธอดเดียวที่เรียกต่อไปยัง repository เฉย ๆ

// ชั้นที่ไม่ได้ทำอะไร นอกจากเพิ่มไฟล์
class GetPalletsInZone {
  const GetPalletsInZone(this.repository);
  final PalletRepository repository;

  Future<List<Pallet>> call(String zone) => repository.fetchInZone(zone);
}

คลาสแบบนี้ทำให้คนอ่านต้องเปิดไฟล์เพิ่มอีกหนึ่งไฟล์ เพื่อพบว่าไม่มีอะไรอยู่ในนั้น

4. ทางเลือกที่เบากว่าการเพิ่มชั้น

ก่อนสร้างชั้นใหม่ ลองสามอย่างนี้ก่อน — ส่วนใหญ่พอ

ปัญหาทางแก้ที่เบากว่า
กฎธุรกิจกระจายอยู่หลายที่ย้ายไปเป็นเมธอดในโมเดล เช่น bool get canHold => !onHold && quantity > 0;
store สองตัวทำงานเดียวกันถามก่อนว่าทำไมถึงมีสอง — มักเป็นอาการของ 9.9
เมธอดใน store ยาวเกินไปแยกเป็นเมธอดส่วนตัวในคลาสเดิม ยังไม่ต้องมีไฟล์ใหม่

แถวแรกมีพลังมากกว่าที่คิด — กฎที่อยู่บนโมเดลเดินทางไปกับข้อมูลเสมอ ไม่มีทางที่จอไหนจะลืมตรวจ

5. ของจริงทั้งสองโปรเจกต์ไม่มีชั้นนี้

ทั้ง wmsapp และ wms_absolute_mobile ไม่มี use case layer งานที่ประสานหลายขั้นอยู่ในเมธอดของ store แทน

// wms_absolute_mobile — dispatchTask ประสานหลายอย่างในเมธอดเดียว
Future<void> dispatchTask(...) async {
  ...ตรวจสิทธิ์ → ตรวจจุดปลายทาง → เรียก tasksRepository.dispatch → อัปเดตลิสต์...
}

ตัดสินอย่างไรว่าเลือกถูก ให้ดูว่าปัญหาที่เกิดจริงคืออะไร ในโปรเจกต์นี้ปัญหาไม่ใช่ “ตรรกะกระจาย” แต่เป็น “ทุกอย่างกองอยู่ใน store ตัวเดียว” ซึ่งการเพิ่ม use case ไม่ได้แก้ — มันจะได้ store ที่บางลงแต่มีไฟล์ use case สามสิบไฟล์ที่ยังพันกันอยู่ดี

หลัก: เพิ่มชั้นเมื่อมันแก้ปัญหาที่มีอยู่จริงตอนนี้ ไม่ใช่ปัญหาที่อาจมีถ้าโปรเจกต์โตขึ้นสิบเท่า

6. กรณีที่คุ้มค่าจริง

ตัวอย่างจากงานคลังที่ควรมี use case

ปิดงานหยิบของหนึ่งรอบ:
  1. ยืนยันจำนวนที่หยิบได้จริง          → PickRepository
  2. ปล่อยพาเลทที่ล็อกไว้                → PalletRepository
  3. สร้างงานขนย้ายไปจุดแพ็ก            → TaskRepository
  4. บันทึกว่าใครทำ เมื่อไหร่            → AuditRepository

สี่ขั้นนี้ต้องเกิดครบ ใช้ในสองจอ (จอหยิบและจอหัวหน้า) และมีกฎว่าถ้าขั้นที่ 3 ล้มเหลวต้องไม่ปล่อยให้ขั้นที่ 2 ค้าง — พอมีความซับซ้อนระดับนี้ การมีคลาสที่ทดสอบได้เดี่ยว ๆ ชื่อ CompletePickRound คุ้มค่ากว่าการเขียนไว้ใน store สองตัว

สังเกตว่าตัวอย่างนี้ตอบว่า “ใช่” ถึงสี่ข้อในตาราง §3

7. แบบฝึกหัด

ทีมเสนอให้เพิ่ม use case สำหรับทุกการกระทำในแอป รวมถึง GetPalletsInZone, HoldPallet, LoadTasks เหตุผลคือ “จะได้เป็นมาตรฐานเดียวกันทั้งโปรเจกต์”

  1. ข้อดีที่อ้างนี้จริงไหม
  2. จะเสนออะไรกลับ
แนวคำตอบ

1. จริงบางส่วน — ความสม่ำเสมอมีค่าจริง คนอ่านไม่ต้องเดาว่าตรรกะอยู่ไหน และคนใหม่รู้ว่าต้องสร้างไฟล์อะไรบ้าง แต่ค่านั้นต้องเทียบกับต้นทุน คือไฟล์ที่เพิ่มขึ้นเท่าตัวและไฟล์ส่วนใหญ่จะมีบรรทัดเดียว

2. เสนอกฎที่แคบกว่าและตรวจได้

  • งานที่แตะ repository มากกว่าหนึ่งตัว ให้เป็น use case
  • งานที่แตะตัวเดียวและไม่มีกฎธุรกิจ ให้ store เรียก repository ตรง ๆ
  • ถ้าวันหนึ่งงานตัวไหนโตขึ้นจนเข้าเกณฑ์ข้อแรก ค่อยยกขึ้นเป็น use case ตอนนั้น

กฎนี้ยังสม่ำเสมอ — คนอ่านรู้ว่าถ้าเห็น use case แปลว่ามีอะไรซับซ้อนอยู่ ซึ่งเป็นข้อมูลที่มีประโยชน์กว่าการที่ทุกอย่างเป็น use case เหมือนกันหมดจนไม่บอกอะไรเลย

8. สรุป

  • เพิ่มชั้น domain เมื่อมีการประสานหลาย repository, กฎที่ใช้หลายที่ หรือลำดับที่ต้องครบ
  • ลองย้ายกฎไปไว้บนโมเดลก่อน — เบากว่าและกฎเดินทางไปกับข้อมูล
  • use case ที่แค่เรียกต่อ คือไฟล์ที่ทำให้คนอ่านเสียเวลาเปล่า
  • โปรเจกต์จริงทั้งสองตัวไม่มีชั้นนี้ และปัญหาของมันคือคนละเรื่อง

บทหน้า: เรื่องที่ทุกชั้นต้องตกลงกันให้ชัด คือความล้มเหลวเดินทางอย่างไร
