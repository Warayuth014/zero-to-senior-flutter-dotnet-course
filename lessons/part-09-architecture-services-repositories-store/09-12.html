Domain layerมีเมื่อกฎคุ้มค่า: เพิ่มเมื่อมี invariants/calculation/workflow languageที่ต้องเป็นอิสระจาก Flutter/API ไม่ใช่เพราะทุก projectต้องมีสี่ชั้น

1. Signals ว่าควรมี

  • กฎเดียวใช้หลายหน้าหรือหลาย data source
  • workflow transitionซับซ้อน
  • ต้อง test business rulesจำนวนมาก
  • DTO shapeไม่ตรงคำศัพท์ใน app
  • offline/reconciliationต้องรักษา invariants

2. Entity/value object

final class Quantity {
  Quantity._(this.value);
  final double value;
  static Quantity create(double value) {
    if (!value.isFinite || value <= 0) throw InvalidQuantity();
    return Quantity._(value);
  }
}

3. Domain service

ใช้เมื่อ ruleข้ามหลาย entitiesและไม่มี ownerธรรมชาติ เช่น allocation policy แต่อย่าเรียก class wrapperทุก methodว่า Serviceโดยไม่มี domain logic

4. Application vs domain

Domainตัดสิน “quantity valid/transition allowed”; applicationจัด “เรียก repository, loading, retry, user session”; infrastructureส่ง HTTP

5. เมื่อไม่ต้องมี

หน้า read-only mappingตรง APIและไม่มี rule อาจใช้ DTO→ViewStateผ่าน repositoryได้ ชั้นเพิ่มโดยไม่มี logicทำ navigationยากและ boilerplateสูง

6. Backend authority

Flutter domain validationช่วย UX/offlineแต่ .NETยังต้อง enforce invariantเพราะ clientถูกแก้/ข้อมูลแข่งขันได้ ให้ share contract/testsไม่ copy logicแบบหลง divergence

7. แบบฝึกหัด

สี statusควรอยู่ domain entityไหม?

เฉลย

ไม่ สีเป็น presentation mapping; domainเก็บ typed statusและ allowed transitions ส่วน UI map theme/icon/color

8. Cost check

ก่อนเพิ่ม layer ระบุ rule, consumer, testและ change pressureที่ได้ประโยชน์ หากตอบไม่ได้ให้เริ่มเรียบง่ายและรักษา boundaryไว้ก่อน
