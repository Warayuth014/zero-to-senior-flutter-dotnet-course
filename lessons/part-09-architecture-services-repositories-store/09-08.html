1. คำถามที่ยังไม่ตอบ

ตอนนี้มีของสามชิ้นที่ต้องต่อกัน

ApiClient  →  RemotePalletRepository  →  PalletStore  →  PalletScreenV2

คำถามคือ ใครเป็นคนต่อ และต่อตรงไหน คำตอบมีสองแบบใหญ่ ๆ

หยิบเองรับเข้ามา
โค้ดfinal _api = ApiService();PalletScreenV2({required this.store})
ใครรู้ว่าต้องใช้อะไรต้องอ่านทั้งไฟล์ดูที่ constructor
สลับของปลอมได้ไหมไม่ได้ได้

2. Constructor injection คืออะไร

Dependency injection คือการที่วัตถุรับของที่ตัวเองต้องใช้เข้ามา แทนที่จะสร้างหรือไปหยิบเอง เมื่อรับผ่าน constructor ก็เรียกว่า constructor injection

ไม่ต้องใช้ library อะไรเลย มันคือการเขียน constructor ให้รับพารามิเตอร์

class PalletStore extends ChangeNotifier {
  PalletStore(this.repository, {String Function(String code)? createCommandId})
    : _createCommandId = createCommandId ??
          ((code) => '$code-${DateTime.now().microsecondsSinceEpoch}');

  final PalletRepository repository;
}

สังเกตพารามิเตอร์ตัวที่สอง — createCommandId เป็นค่าที่มีค่าเริ่มต้นให้แล้ว โค้ดจริงไม่ต้องส่ง แต่เทสต์ส่งฟังก์ชันที่คืนค่าคงที่เข้าไปได้ เพื่อตรวจว่าส่ง Idempotency-Key ถูกไหม

รูปแบบที่ใช้ได้ทั่วไป: อะไรที่ทำให้เทสต์เดาไม่ได้ — เวลา, สุ่ม, ตัวจับเวลา — ให้เปิดช่องรับเข้ามาพร้อมค่าเริ่มต้น เทสต์จะได้คุมได้ โดยที่โค้ดเรียกใช้จริงไม่ต้องเปลี่ยน

3. จุดประกอบเดียวของแอป

ถ้าทุกชั้นรับของเข้ามา แปลว่ามีที่หนึ่งที่ต้องสร้างของจริงทั้งหมด ที่นั่นเรียกว่า composition root

// จุดประกอบ — ที่เดียวในแอปที่รู้ว่าตัวจริงคือใคร
final apiClient = ApiClient(baseUrl: settings.baseUrl);
final palletStore = PalletStore(RemotePalletRepository(apiClient));

runApp(MyApp(palletStore: palletStore));

ในเทสต์ จุดประกอบคือบรรทัดสองบรรทัดในไฟล์เทสต์เอง

runSharedBehaviourTests((client) {
  final api = ApiClient(baseUrl: baseUrl, client: client);
  final store = PalletStore(RemotePalletRepository(api));
  return PalletScreenV2(store: store, zone: 'A1');
});

โครงเหมือนกันเป๊ะ ต่างแค่ client — และนั่นคือทั้งหมดที่เทสต์ต้องเปลี่ยน

4. ของจริง: warehouse_shell.dart

store = WarehouseStore(
      username: widget.auth.session?.username ?? '0000',
      receivingRepository: ReceivingApi(widget.auth.client),
      tasksRepository: TasksApi(widget.auth.client),
      inventoryRepository: InventoryApi(widget.auth.client),

    ..onToast = _showToast

เก้าบรรทัดนี้คือจุดประกอบของ wms_absolute_mobile อ่านแล้วเห็นทั้งหมดว่าฟีเจอร์คลังพึ่งพาอะไรบ้าง — repository สี่ตัว, ชื่อผู้ใช้, สิทธิ์ และวิธีแจ้งข้อความสองแบบ

สิ่งที่สังเกตได้ความหมาย
repository ทั้งสี่รับ widget.auth.client ตัวเดียวกันมี ApiClient ตัวเดียวที่ถือ token — ตรงกับกฎใน 8.4
..onToast = _showToaststore บอกว่าเกิดอะไร จอตัดสินใจว่าจะแสดงอย่างไร
ประกอบใน initState ของ shellstore มีอายุเท่ากับ shell — ออกจากระบบแล้ว shell ถูกทิ้ง store ก็ไปด้วย (8.8)

5. เทียบกับ wmsapp

class _PackingScreenState extends State<PackingScreen> {
  final _api = ApiService();
  ...
}

รูปแบบนี้ปรากฏ 26 ที่ในโปรเจกต์ ผลที่ตามมามีข้อหนึ่งที่ไม่ชัดจนกว่าจะเจอเอง

สมมติต้องแก้บั๊กที่เกิดเฉพาะตอนเซิร์ฟเวอร์ตอบช้าเกิน 10 วินาที ในโครงที่รับของเข้ามา เขียนเทสต์ที่ทำให้ตอบช้าได้ใน 3 บรรทัด ในโครงที่หยิบเอง ต้องเลือกทางใดทางหนึ่งระหว่าง

  • ตั้งเซิร์ฟเวอร์จริงให้ตอบช้า แล้วทดสอบด้วยมือ
  • แก้จอให้รับ ApiService เข้ามาก่อน (ซึ่งคือการทำ injection นั่นเอง)
  • ไม่เขียนเทสต์

ทางที่สามคือทางที่เกิดขึ้นจริงเกือบทุกครั้ง

6. แล้วต้องส่งของผ่านทุกชั้นเลยไหม

ปัญหาที่คนกลัวคือ “ต้องส่ง ApiClient ลงไปสิบชั้น” ซึ่งเกิดขึ้นจริงถ้าออกแบบผิด วิธีหลีกเลี่ยงคือ ส่งของที่ชั้นนั้นใช้จริง ไม่ใช่ส่งของดิบลงไปให้ชั้นล่างประกอบเอง

แบบที่ทำให้ปวดหัวแบบที่ควรทำ
PalletScreen(apiClient: apiClient) แล้วจอสร้าง repository และ store เองPalletScreen(store: store) — จอไม่รู้จัก ApiClient เลย

ในแอปที่ใหญ่ขึ้น ยังมีเครื่องมือที่ช่วยส่งของข้ามชั้นได้โดยไม่ต้องเขียน parameter ต่อกันเป็นทอด ๆ เช่น InheritedWidget, provider หรือ riverpod ซึ่งอยู่ใน Part 27 ทั้งหมดนั้นเปลี่ยนแค่ วิธีส่ง ไม่ได้เปลี่ยนหลักที่ว่าของต้องถูกส่งเข้ามา

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เทสต์แต่ละข้อเห็นข้อมูลของข้ออื่นstore เป็น static หรือ singletonสร้างใหม่ทุกเทสต์
สร้าง store ใน build()build ถูกเรียกหลายครั้งสร้างใน initState หรือที่ชั้นบนกว่า
ลืม dispose storeไม่มีใครรับผิดชอบชัดเจนใครสร้าง คนนั้นทิ้ง
ส่ง BuildContext เข้าไปใน storeอยากให้ store เปิด dialogใช้ callback แทน (9.7 §7)

8. แบบฝึกหัด

แอปมีสองจอที่ต้องเห็นรายการพาเลทเดียวกัน คือจอค้นหาและจอสรุป ถ้าจอหนึ่งล็อกพาเลท อีกจอต้องเห็นทันที

  1. ควรสร้าง PalletStore กี่ตัว
  2. ควรสร้างที่ไหน
  3. ใครเรียก dispose
แนวคำตอบ

1. ตัวเดียว ถ้าสร้างสองตัว จะมีข้อมูลสองชุดที่ไม่ตรงกันทันทีที่ล็อกสำเร็จ — ปัญหานี้คือหัวข้อของ 9.9

2. ที่ระดับที่ครอบทั้งสองจอ ถ้าสองจออยู่ใน shell เดียวกันก็สร้างที่ shell แบบเดียวกับที่ warehouse_shell.dart ทำ

3. shell ที่สร้างมัน ไม่ใช่จอ — และนี่เป็นจุดที่ต้องระวัง เพราะ task_screen.dart ใน lab เรียก widget.store.dispose() ใน dispose ของตัวเอง ซึ่งถูกต้องเฉพาะตอนที่จอนั้นเป็นเจ้าของ store คนเดียว ถ้าเอาโครงนั้นมาใช้กับ store ที่แชร์กัน จอแรกที่ปิดจะทำให้จอที่สองพัง

กฎที่จำง่าย: ใครสร้าง คนนั้นทิ้ง — และถ้าเห็น dispose ของที่ตัวเองไม่ได้สร้าง ให้สงสัยไว้ก่อน

9. สรุป

  • รับของเข้ามาทาง constructor แทนที่จะหยิบเอง ไม่ต้องใช้ library อะไร
  • constructor คือรายการพึ่งพาที่อ่านได้ในที่เดียว
  • จุดประกอบมีที่เดียวในแอป และอีกที่ในเทสต์
  • ส่งของที่ชั้นนั้นใช้จริง ไม่ส่งของดิบลงไปให้ประกอบเอง

บทหน้า: ถ้ามี store สองตัวที่เก็บของเดียวกัน จะเกิดอะไรขึ้น
