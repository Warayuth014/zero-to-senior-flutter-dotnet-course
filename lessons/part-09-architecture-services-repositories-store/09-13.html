1. ความล้มเหลวเดินทางผ่านสี่ชั้น

เซิร์ฟเวอร์ตอบ 409 พร้อม {"detail": "พาเลทนี้ถูกล็อกโดยสมชายอยู่"}
   ↓
ApiClient         → ApiException(kind: conflict, problem: ...)     ภาษาของ HTTP
   ↓
Repository        → PalletFailure('พาเลทนี้ถูกล็อกโดยสมชายอยู่')   ภาษาของงาน
   ↓
Store             → _failure = failure                              สถานะ
   ↓
Widget            → Text(failure.message)                           สิ่งที่ผู้ใช้เห็น

คำถามหลักของบทนี้คือ แปลตรงไหน คำตอบคือชั้นที่สอง และมีเหตุผลชัดเจน

2. ทำไมไม่แปลที่ ApiClient

ApiClient รู้แค่ว่าได้ 409 มา แต่ 409 หมายถึงอะไรขึ้นกับว่ากำลังทำอะไรอยู่

ตอนกำลังทำ409 แปลว่า
ล็อกพาเลทมีคนล็อกไปก่อนแล้ว
ปิดงานขนย้ายงานนี้ถูกปิดไปแล้ว — ซึ่งอาจไม่ใช่ปัญหาเลย (4.13)
เริ่มรอบนับสต๊อกมีรอบนับที่ยังไม่ปิดค้างอยู่

ชั้นขนส่งไม่รู้บริบทนี้ หน้าที่มันคือแปลง 409 เป็น ApiFailureKind.conflict แล้วส่งต่อพร้อมข้อความที่เซิร์ฟเวอร์ให้มา จบแค่นั้น

3. ทำไมไม่แปลที่จอ

นี่คือสิ่งที่ pallet_screen_v1.dart ทำ

_error = response.statusCode >= 500
    ? 'เซิร์ฟเวอร์มีปัญหา แจ้งทีมระบบถ้ายังไม่หาย'
    : 'โหลดข้อมูลไม่สำเร็จ (${response.statusCode})';

ผลที่ตามมาสามข้อ

ปัญหารูปธรรม
ทุกจอแปลไม่เหมือนกันจอหนึ่งบอก “เชื่อมต่อไม่ได้” อีกจอบอก “โหลดข้อมูลไม่สำเร็จ (0)”
ผู้ใช้เห็นเลข status“โหลดข้อมูลไม่สำเร็จ (409)” ไม่ได้บอกว่าต้องทำอะไรต่อ
ข้อความที่เซิร์ฟเวอร์ตั้งใจส่งมาถูกทิ้ง“พาเลทนี้ถูกล็อกโดยสมชายอยู่” หายไป เหลือแค่เลข

ข้อสุดท้ายเจ็บที่สุด เพราะเซิร์ฟเวอร์เป็นฝ่ายที่รู้เรื่องธุรกิจมากที่สุด

4. การแปลใน lab

PalletFailure _translate(ApiException error) => switch (error.kind) {
  ApiFailureKind.network => const PalletFailure(
    'เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ ตรวจสัญญาณแล้วลองใหม่', canRetry: true),
  ApiFailureKind.timeout => const PalletFailure(
    'เซิร์ฟเวอร์ไม่ตอบภายในเวลาที่กำหนด', canRetry: true),
  ApiFailureKind.server => const PalletFailure(
    'เซิร์ฟเวอร์มีปัญหา แจ้งทีมระบบถ้ายังไม่หาย', canRetry: true),
  ApiFailureKind.notFound => const PalletFailure('ไม่พบข้อมูลที่ขอ'),
  // สามชนิดนี้เซิร์ฟเวอร์รู้เรื่องดีกว่าเรา จึงใช้ข้อความของมัน
  ApiFailureKind.conflict ||
  ApiFailureKind.validation ||
  ApiFailureKind.forbidden => PalletFailure(error.userMessage),
  ApiFailureKind.unauthorized => const PalletFailure('เซสชันหมดอายุ'),
  ApiFailureKind.contract => PalletFailure(error.userMessage),
};
สังเกตเหตุผล
ไม่มี default หรือ _วันที่เพิ่มชนิดใหม่ คอมไพเลอร์จะฟ้องให้มาตัดสินใจ ไม่ใช่ปล่อยให้ตกไปเป็นข้อความกลาง
canRetry ตัดสินที่นี่จอไม่ต้องรู้ว่าชนิดไหนลองใหม่ได้ แค่ดูว่าจะโชว์ปุ่มไหม
บางชนิดใช้ข้อความของเซิร์ฟเวอร์ข้อความที่เจาะจงกว่าย่อมมีประโยชน์กว่า

5. สิ่งที่ต้องไม่แปล

final items = requireList(json, 'items');    // อยู่นอก try โดยตั้งใจ

ContractException ไม่ถูกแปลเป็น PalletFailure เพราะมันไม่ใช่ปัญหาที่ผู้ใช้ทำอะไรได้ กดลองใหม่กี่ครั้งเซิร์ฟเวอร์ก็ส่งข้อมูลผิดรูปแบบเดิมกลับมา

ชนิดใครแก้ได้ควรทำอย่างไร
เน็ตหลุดผู้ใช้บอกและให้ลองใหม่
ล็อกซ้ำผู้ใช้ (ไปคุยกับสมชาย)บอกให้ชัด
ข้อมูลผิดสัญญาทีมพัฒนาปล่อยให้พังและส่งเข้าระบบเก็บ error
บั๊กในโค้ดเราทีมพัฒนาปล่อยให้พัง
การจับข้อผิดพลาดทุกอย่างแล้วแสดง “เกิดข้อผิดพลาด กรุณาลองใหม่” คือการซ่อนสองแถวล่างไว้ใต้พรม — ผู้ใช้ทำตามที่บอกแล้วไม่ได้ผล และทีมไม่เคยรู้ว่ามีปัญหา

6. สามวิธีส่งความล้มเหลวขึ้นไป

โยน exceptionApiResult<T>sealed class
ใช้ที่ไหนlab, wms_absolute_mobilewmsapplab เฉพาะการเข้าสู่ระบบ (8.2)
ลืมจัดการได้ไหมได้ แต่แอปจะพังให้เห็นได้ และเงียบไม่ได้ คอมไพเลอร์บังคับ
เส้นทางสำเร็จอ่านง่ายไหมง่ายที่สุด ไม่มี if คั่นต้องเช็ค success ก่อนทุกครั้งต้อง switch
แยกกรณีย่อยได้ไหมได้ผ่าน kindได้แค่ผ่านเลข statusได้ดีที่สุด
เขียนยาวไหมสั้นกลางยาวที่สุด

เลือกอย่างไร

  • โยน เมื่อความล้มเหลวส่วนใหญ่จัดการเหมือนกันหมด คือแสดงข้อความแล้วให้ลองใหม่ — ครอบคลุมงานส่วนใหญ่
  • sealed class เมื่อแต่ละกรณีต้องพาผู้ใช้ไปคนละทาง เช่นการเข้าสู่ระบบที่ 401 ให้พิมพ์ใหม่ ส่วน 403 ให้ไปติดต่อหัวหน้า
  • ผลลัพธ์แบบกล่อง เมื่อทีมไม่อยากให้มี exception หลุดขึ้นไปเลย และยอมรับว่าต้องเช็คทุกจุดเรียก

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ผู้ใช้เห็น ContractException ที่ items[3].quantity: ...เอา toString() ของ exception ไปแสดงตรง ๆแสดงข้อความกลาง แล้วส่งรายละเอียดเข้าระบบเก็บ log
ทุกความผิดพลาดขึ้นว่า “เกิดข้อผิดพลาด”catch (e) ครอบทุกอย่างจับเฉพาะชนิดที่จัดการได้จริง
ปุ่มลองใหม่โผล่ในกรณีที่ลองใหม่ไม่ช่วยจอเดา canRetry จากการมี errorให้ repository ตัดสินแล้วส่งมา
ข้อความผิดพลาดค้างอยู่หลังลองใหม่สำเร็จลืมล้างตอนเริ่มคำขอใหม่_failure = null ก่อน notifyListeners()

8. แบบฝึกหัด

ผู้ใช้กดล็อกพาเลท แล้วเน็ตหลุดระหว่างรอคำตอบ ตอนนี้ไม่มีใครรู้ว่าเซิร์ฟเวอร์ล็อกไปแล้วหรือยัง

  1. _translate ที่มีอยู่จัดการกรณีนี้ถูกไหม
  2. ควรแก้อย่างไร
แนวคำตอบ

1. ไม่ถูก มันแปลเป็น “เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ ตรวจสัญญาณแล้วลองใหม่” พร้อม canRetry: true ซึ่งชวนให้ผู้ใช้กดล็อกซ้ำ ทั้งที่อาจล็อกไปแล้ว

ข้อมูลที่ต้องใช้มีอยู่แล้วใน ApiException.outcomeUnknown ตั้งแต่ 7.10 แต่ _translate ทิ้งไป

2. ส่งต่อขึ้นไปด้วย

class PalletFailure implements Exception {
  const PalletFailure(this.message, {
    this.canRetry = false,
    this.outcomeUnknown = false,
  });
  ...
}

ApiFailureKind.network => PalletFailure(
  error.outcomeUnknown
      ? 'การเชื่อมต่อขาดระหว่างส่งคำสั่ง กำลังตรวจสอบสถานะล่าสุด'
      : 'เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ ตรวจสัญญาณแล้วลองใหม่',
  canRetry: !error.outcomeUnknown,
  outcomeUnknown: error.outcomeUnknown,
),

แล้วให้ store โหลดใหม่เพื่อดูความจริง แทนที่จะให้ผู้ใช้เดา — แบบเดียวกับที่ TaskStore.complete ทำใน Part 4

ประเด็นที่ควรจำ: โครงที่แยกชั้นไว้ดีแล้วก็ยังทำข้อมูลหล่นได้ ถ้าจุดแปลทิ้งสิ่งที่ชั้นล่างอุตส่าห์หามาให้ — ทุกครั้งที่เขียน _translate ให้ถามว่ากำลังทิ้งอะไรไปบ้าง

9. สรุป

  • แปลที่ repository เพราะเป็นชั้นแรกที่รู้บริบทของงาน
  • ชั้นขนส่งบอกแค่ชนิด จอแค่แสดง ไม่มีใครแปลซ้ำ
  • ความล้มเหลวที่ผู้ใช้แก้ไม่ได้ อย่าแปลงให้เป็นข้อความให้ผู้ใช้กดลองใหม่
  • เลือกวิธีส่งต่อจากลักษณะของงาน ไม่ใช่จากความชอบ
