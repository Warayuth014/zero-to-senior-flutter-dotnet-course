2. สามชั้นที่ต้องแยกให้ออก

ชั้นตอบคำถามว่าห้ามรู้เรื่อง
UIสิ่งที่มีอยู่ตอนนี้ หน้าตาเป็นอย่างไรHTTP, JSON, ชื่อฟิลด์ของเซิร์ฟเวอร์
Logicเมื่อผู้ใช้ทำแบบนี้ ต้องเกิดอะไรตามลำดับไหนปุ่มอยู่ตรงไหน สีอะไร
Dataข้อมูลมาจากไหน หน้าตาตอนอยู่บนสายเป็นอย่างไรใครจะเอาไปแสดง

3. เปิด pallet_screen_v1.dart แล้วชี้ทีละส่วน

ไฟล์นี้ยาวประมาณ 220 บรรทัด อ่านจากบนลงล่างรู้เรื่องหมด นั่นคือข้อดีของมัน ลองดูว่าข้างในมีอะไรปนกันบ้าง

class _PalletScreenV1State extends State<PalletScreenV1> {
  bool _loading = false;                        // Logic — สถานะของงาน
  String? _error;                               // Logic
  bool _canRetry = false;                       // Logic
  List<Map<String, dynamic>> _pallets = const []; // Data — ยังเป็น JSON ดิบ!
  final Set<String> _busyCodes = {};             // Logic

  static const String _baseUrl = 'http://localhost:5000';  // Infrastructure

สังเกต List<Map<String, dynamic>> — จอนี้เก็บ JSON ดิบไว้ตรง ๆ แปลว่าเวลาวาด ต้องเขียน pallet['code'] as String ในส่วนที่วาด UI ซึ่งแปลว่า ถ้าเซิร์ฟเวอร์เปลี่ยนชื่อฟิลด์ ต้องไปแก้ในโค้ดวาดหน้าจอ — ตกบททดสอบข้อแรกใน 9.1 ทันที

5. อาการที่มองไม่เห็นจากการอ่าน

ในบล็อกข้างบนมีคอมเมนต์บรรทัดหนึ่งที่ต้องอ่านให้ดี

// ไม่มีการเช็คว่าคำขอนี้ยังใหม่อยู่ไหม — กด "โหลดใหม่" รัว ๆ แล้ว
// คำตอบของคำขอเก่าที่กลับมาช้าจะทับคำตอบใหม่ได้ (4.10)
if (!mounted) return;
setState(() { _pallets = items; _loading = false; });

Part 4 สอนวิธีแก้ไปแล้ว คือใช้เลขรุ่นของคำขอ คำถามคือ ทำไมรุ่นนี้ถึงลืม คำตอบไม่ใช่เพราะคนเขียนไม่รู้ แต่เพราะเทสต์ที่จะจับเรื่องนี้ต้องคุมจังหวะการตอบของเซิร์ฟเวอร์ให้ได้ ซึ่งในรุ่นนี้ทำได้ทางเดียวคือผ่าน MockClient พร้อมกับต้องสร้าง widget ทั้งจอขึ้นมา — แพงพอที่คนส่วนใหญ่จะไม่เขียน

หลักที่ใช้ได้ทั่วไป: โค้ดที่ทดสอบยาก มักจะไม่ถูกทดสอบ และโค้ดที่ไม่ถูกทดสอบ มักจะมีบั๊กที่รู้วิธีแก้อยู่แล้ว

6. หลังแยกชั้น: บรรทัดเดียวกันไปอยู่ที่ไหน

ใน v1ย้ายไปอยู่ทำไม
_baseUrl, timeout, headerscore/api_client.dartทุกจอใช้เหมือนกัน
jsonDecode + อ่านฟิลด์pallet_repository.dartเปลี่ยนตามสัญญากับเซิร์ฟเวอร์
แปลเลข status เป็นข้อความpallet_repository.dartต้องแปลเหมือนกันทุกจอ
_loading, _error, _busyCodespallet_store.dartเป็นสถานะของงาน ไม่ใช่ของหน้าจอ
Map<String, dynamic>กลายเป็น PalletUI ควรเห็นคำศัพท์ของงาน
ListTile, Column, ปุ่มpallet_screen_v2.dartอยู่ที่เดิม เพราะเป็นเรื่องของหน้าจอจริง ๆ

7. ผลลัพธ์ที่วัดได้

เทสต์ใน architecture_test.dart แบ่งเป็นสองส่วน ส่วนแรกเจ็ดข้อรันกับทั้งสองรุ่นด้วยโค้ดชุดเดียวกัน

group('พฤติกรรมเดียวกัน · รุ่นรวมทุกอย่างไว้ในจอ', () {
  runSharedBehaviourTests((client) => PalletScreenV1(client: client, zone: 'A1'));
});

group('พฤติกรรมเดียวกัน · รุ่นแยกชั้น', () {
  runSharedBehaviourTests((client) {
    final api = ApiClient(baseUrl: baseUrl, client: client);
    final store = PalletStore(RemotePalletRepository(api));
    return PalletScreenV2(store: store, zone: 'A1');
  });
});

ผ่านทั้งคู่ แปลว่า ผู้ใช้ไม่รู้เลยว่าเราแยกชั้น ซึ่งเป็นนิยามของคำว่า refactor

ส่วนที่สองอีกหกข้อ ทดสอบ repository และ store โดยตรง ไม่สร้าง widget เลยสักตัว — และนี่คือส่วนที่รุ่น v1 เขียนไม่ได้ ไม่ใช่เพราะยาก แต่เพราะกฎอยู่ใน _PalletScreenV1State ซึ่งเป็นคลาสส่วนตัวที่เข้าถึงจากข้างนอกไม่ได้

8. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดความจริง
“v1 เขียนผิด”v1 ทำงานถูก และเร็วกว่าถ้าจอนี้จะไม่โตอีก ที่ต่างคือสิ่งที่ทำได้ตอนแก้และตอนทดสอบ
“แยกชั้นแล้วโค้ดสั้นลง”ยาวขึ้น v1 มีไฟล์เดียว v2 มีห้าไฟล์ ที่ได้คือแต่ละไฟล์เข้าใจได้ด้วยตัวเอง
“ต้องแยกทุกจอ”จอตั้งค่าที่มีสองสวิตช์ไม่ต้องมี repository และ store

9. แบบฝึกหัด

เปิด pallet_screen_v1.dart หาเมธอด _hold แล้วตอบ

  1. บรรทัดไหนบ้างที่จะต้องแก้ ถ้าเซิร์ฟเวอร์เปลี่ยนจากตอบ 200 พร้อมพาเลทที่อัปเดตแล้ว เป็นตอบ 204 ที่ไม่มีเนื้อหา
  2. ถ้าเปลี่ยนแบบเดียวกันในรุ่น v2 ต้องแก้กี่ไฟล์
แนวคำตอบ

1. ต้องแก้ในจอ ตรงที่ jsonDecode(response.body) และตรงที่แทนที่แถวในลิสต์ ซึ่งอยู่ใน setState ปนกับโค้ดวาดหน้าจอ ถ้ามีจออื่นที่ล็อกพาเลทได้ด้วย ต้องไปแก้ที่จอนั้นอีก

2. สองไฟล์ และ ไม่มีไฟล์หน้าจอ — 204 ไม่มีเนื้อหา แปลว่า repository สร้าง Pallet คืนไม่ได้อีก สัญญาต้องเปลี่ยนเป็น Future<void> hold(...) แล้ว PalletStore.hold เปลี่ยนมาอัปเดตแถวเองด้วย pallet.copyWith(onHold: true)

ข้อนี้ตอบยากกว่าที่คิด และสอนสองอย่างพร้อมกัน คือ (ก) เปลี่ยนสัญญาแล้วกระเทือนถึงคนเรียก หนีไม่พ้น แต่ (ข) มันหยุดอยู่แค่ชั้นที่ถัดไป ไม่ลามไปถึงโค้ดวาดหน้าจอ ต่างจาก v1 ที่การเปลี่ยนนี้ลงไปแก้ในกองเดียวกับ ListTile

10. สรุป

  • UI ตอบว่า “มีอะไร” Logic ตอบว่า “ทำอะไรต่อ” Data ตอบว่า “มาจากไหน”
  • จอที่เก็บ Map<String, dynamic> คือจอที่รู้เรื่องเซิร์ฟเวอร์มากเกินไป
  • สิ่งที่ทดสอบยาก จะไม่ถูกทดสอบ และจะมีบั๊ก
  • refactor ที่ถูกต้องคือเทสต์ชุดเดิมยังผ่าน
