ไฟล์หลัก: cycle-count methods ใน WarehouseStore — storeเป็น state machineฝั่ง clientที่ประสาน phaseจาก serverกับ inputการนับในเครื่อง

1. Session state

storeถือ pallet snapshot, selected mode/product, map count values, loading/submittingและ private refreshing flag clearCycleCountSession ล้าง public stateเมื่อออกหน้า แต่ปัจจุบันไม่ได้เพิ่ม generationเพื่อ invalidate lookup/refresh/confirmที่กำลังรอ จึงยังมี stale async riskต่างจาก Receiving

2. Lookup และ Start

lookupCycleCountPallet trim code, guard empty/loading, แสดง busy แล้ว apply server snapshotพร้อม feedback startCycleCount guard null/submittingและส่ง username/stationจาก snapshot Responseอาจเป็น waiting ไม่ใช่ ready จึงต้อง renderตาม phase

3. เลือก Manual Quantity

เมื่อเลือก manual mapจะถูกเติมทุก productด้วย lastCountQty ?? systemQty เพื่อให้ของที่ไม่เปลี่ยนกดยืนยันได้เร็ว นี่เป็น deliberate productivity policyแต่เสี่ยง operatorยืนยันค่าคาดเดาโดยไม่ตรวจจริง ควรมี visual acknowledgement/audit policyตามงานคลัง

4. เลือก Scan Each Item

mapเริ่มทุก productที่ 0 ทุก scan trim/uppercaseแล้วหา productบน palletและเพิ่มทีละ 1, รองรับ undoหนึ่งชิ้น Scanผิดให้ error/flashและไม่เปลี่ยนค่า เพราะ mapมี keyครบตั้งแต่เลือก mode UIจึงถือ countedAll=trueแม้ยังไม่ยิง—zeroอาจเป็นผลนับจริงแต่ควรมี explicit confirmation

5. Manual edit validation

setCycleCountQuantity ปฏิเสธค่าติดลบแต่ viewใช้ double.tryParse(...) ?? 0 ทำให้ inputชั่วคราวที่ parseไม่ได้กลายเป็นศูนย์ทันที Storeยังไม่ตรวจ NaN/infinityหรือ decimal precision Domain validationต้องอยู่ store/server ไม่อาศัย keyboard typeอย่างเดียว

6. Confirm

ยืนยันได้เมื่อ pallet phase ready, เลือก modeและไม่ submitting จากนั้นส่ง resultสำหรับทุก productโดย missing fallback 0, apply response, ล้าง mode/selection/valuesและแจ้ง returning หาก failคง inputsไว้ให้แก้/retry นี่เป็น recovery policyที่ดี แต่ timeout-after-commitต้อง lookup reconcileก่อน retry

7. Refresh และ preserve inputs

refreshCycleCount guard concurrent refresh, lookupด้วย pallet/stationและ preserveCounts: true ถ้า transitionจากไม่ readyเป็น readyจะล้าง mode/countเพื่อเริ่มรอบใหม่ แต่ถ้ายัง readyจะเก็บ inputระหว่าง refresh Failureถูกกลืนเพราะเป็น informational refreshทั้งจาก timerและ pull-to-refresh

8. Race-hardening exercise

เพิ่ม cycle-count session generationเหมือน receiving จับ palletCode+generationก่อนทุก awaitและ commitเฉพาะ snapshotที่ยัง active ทดสอบ clearระหว่าง lookup, เปลี่ยน palletระหว่าง refresh, ออกจากหน้าระหว่าง confirm และ responseเก่ามาทีหลังโดยต้องไม่เปิด sessionเดิมกลับมา
