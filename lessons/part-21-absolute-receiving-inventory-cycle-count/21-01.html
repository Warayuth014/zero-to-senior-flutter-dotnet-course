ไฟล์หลัก: lib/features/warehouse/warehouse_store.dart — runtime single source of truth ของ shell ปัจจุบัน รวมข้อมูลจาก server, navigation และ transient workflow state ไว้ใน ChangeNotifier เดียว

1. Store อยู่ตรงไหนใน graph

WarehouseShell
  └─ WarehouseStore(username, repositories...)
      ├─ ReceivingRepository
      ├─ InventoryRepository
      ├─ CycleCountRepository
      └─ TasksRepository

Views → เรียก command/getter ของ store
Store → await repository → mutate state → notifyListeners
Shell/Views → rebuild จาก state snapshot ใหม่

หน้าจอไม่สร้าง HTTP client และ repository ไม่รู้ widget lifecycle เส้นแบ่งนี้ทำให้ business workflow ทดสอบได้โดยไม่เปิด UI จริง

2. State สามประเภทอยู่ร่วมกัน

  • Server-backed: inboundOrders, receivedToday, pallets, cycle-count pallet/history
  • Derived: inbound, recvCount, filtered order lines และ lookup getters
  • Transient UI/workflow: screen, detailId, rStep, rQty, scanned pallet, selected mode และ loading/submitting flags

การแยกสามกลุ่มในใจช่วยตอบว่า refresh ควรเขียนทับอะไร และอะไรต้อง preserve ระหว่าง request

3. List identity และ mutation

store ถือ list object เดิมแล้วใช้ clear()..addAll(...) จากนั้น notify ทำให้ consumers ที่อ้าง list เดิมเห็นข้อมูลใหม่ แต่ model บางตัว เช่น InboundOrderDetail มี field mutable สำหรับ status/pallet/received quantity จึงต้อง mutate ผ่าน store เท่านั้น หาก view แก้โดยตรงจะไม่มี invariant หรือ notify ที่เชื่อถือได้

4. Navigation เป็น state machine ส่วนหนึ่ง

nav() ไม่ได้แค่เปลี่ยนชื่อหน้า มัน reset receiving/manual-task/cycle-count runtime ตามปลายทาง, notify แล้ว trigger reload สำหรับ list ที่กำลังเปิด ส่วน exitFlow() ใช้ preserveFlow: true เพื่อ pause และเสนอ Continue ภายหลัง ดังนั้น navigation มีผลต่อ domain session และต้องทดสอบเหมือน business logic

5. Load policy

loadAll() ใช้ Future.wait โหลด receiving, tasks, pallets, picks และ summary เพื่อให้ badge หน้าแรกไม่ค้างศูนย์ แต่แต่ละ method มี error policy ต่างกัน: inventory เก็บ error สำหรับ retry UI, receiving toastแล้วหยุดบางส่วน, summary/history fail-soft หลักคือข้อมูล critical กับ informational ไม่ควรมี failure boundary เดียวกันทั้งหมด

6. Side effects และ lifecycle

store ส่ง toast/flash ผ่าน callbacks ที่ shell ประกอบให้ และสร้าง timer 5 วินาทีสำหรับ task status ใน constructor ก่อน cancel ใน dispose() Store จึงไม่ใช่ pure state object; ผู้สร้างต้อง dispose เสมอและ tests ใช้ addTearDown(store.dispose) เพื่อไม่ให้ periodic timerค้าง

7. จุดแข็งและขีดจำกัดของ God Store

ข้อดีคือ trace stateง่ายและ cross-feature badgesใช้ข้อมูลเดียวกัน ข้อเสียคือไฟล์เกิน 1,500 บรรทัด, notify อาจ rebuildกว้าง, receiving/cycle/task lifecycle couplingกัน และ fakeต้องประกอบ repositoryทุกตัว แนว refactorปลอดภัยคือแยก feature storeทีละ seam โดยให้ shellถือ facade/summary และเพิ่ม characterization testsก่อนย้าย state

8. แบบฝึก SSOT audit

เลือกหนึ่ง action เช่น “ยืนยันรับเข้า” ทำตาราง state ก่อน/ระหว่าง/สำเร็จ/ล้มเหลว/ออกหน้าระหว่างรอ ระบุ server-backed, derived และ transient fields ทุกตัว จากนั้นตรวจว่าแต่ละ mutationมี notify, stale-response guard และ cleanup ที่สมมาตรหรือไม่
