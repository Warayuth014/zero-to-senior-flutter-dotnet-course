1. Phase กับ Mode คนละแกน

CycleCountPhase มาจาก serverและบอก availability/transport/readiness/returning ส่วน CycleCountMode เป็นทางเลือก UIว่าจะพิมพ์จำนวนหรือยิงทีละชิ้น Palletอาจ readyแต่ยังไม่เลือก mode และ modeไม่ควรเปลี่ยน server phaseเอง

2. Unknown phase สำคัญ

parserคืน unknown เมื่อ backendเพิ่มค่าใหม่แทน throwหรือสมมติ available UIควรแสดง safe stateและไม่เปิด destructive actionจนรู้ความหมาย พร้อม telemetryให้ทีมเพิ่ม mapping การ fallbackเป็น availableอาจเริ่มงานผิด phase

3. Product snapshot

CycleCountProduct เก็บ systemQty, lastCountQtyและ lastDiffแยกกันเพื่อแสดงฐานระบบกับผลรอบก่อน ห้าม mutate systemQtyเมื่อผู้ใช้พิมพ์จำนวนรอบนี้; current inputอยู่ WarehouseStore.cycleCountValues จึงคำนวณ diffโดยไม่ทำลาย snapshot

4. History เป็น audit read model

CycleCountHistory มี round/document/operator/timeและ resultsราย product แต่ละ resultเก็บ system/count/diff ณ ตอนนั้น ไม่ควรคำนวณ diffย้อนหลังจาก systemQtyปัจจุบันเพราะ stockอาจเปลี่ยนหลังรอบเก่า

5. Pallet snapshot

CycleCountPallet รวม location/station/phase/task document/completed rounds/current round/products/history Responseทุก commandแทน snapshotนี้ทั้งก้อน ทำให้ storeไม่ต้อง merge fieldทีละตัว แต่ต้องระวัง preserve local count inputsตอน informational refresh

6. Command DTO

CycleCountResult มีเพียง product codeกับ count qtyและ toJson ใช้ snake_caseตาม backend การไม่ส่ง systemQty/diffให้ clientตัดสินช่วยให้ serverอ่าน stock snapshotและคำนวณ authoritative diffเอง

7. Decimal และ identity

countเป็น doubleรองรับหน่วยทศนิยม แต่ scan-eachเพิ่มทีละ 1 ส่วน manualรับ decimal Product codeเป็น map keyจึงต้อง uniqueต่อ palletและ normalizeเทียบแบบ case-insensitiveตอน scan หาก backendส่ง product codeซ้ำ mapจะรวม inputsผิด ต้อง enforce contractหรือใช้ line identity

8. Model tests

ทดสอบ phaseทุกค่า/unknown/casing, null last values, historyหลายรอบ, decimal count serialization, duplicate/case-varied product codes และ snapshot equality/copy strategy จากนั้นกำหนด UI behaviorที่ปลอดภัยสำหรับ unknown phaseกับ empty products
