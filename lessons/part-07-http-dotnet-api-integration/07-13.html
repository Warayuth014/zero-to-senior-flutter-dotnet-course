1. ปัญหาที่บทนี้แก้

การค้นหาและการโหลดเพิ่ม แต่ละอย่างไม่ยาก แต่เมื่ออยู่ด้วยกันจะเกิดสถานการณ์ที่คิดไม่ถึง

0.0s  ผู้ใช้เลื่อนถึงท้าย → โหลดเพิ่มเริ่ม (คำค้นว่าง, ข้าม 20)
0.2s  ผู้ใช้พิมพ์ "PAL" → ค้นหาใหม่เริ่ม
0.7s  ค้นหาใหม่กลับมา → แสดงผล 12 รายการ
1.4s  โหลดเพิ่มกลับมา → ต่อท้ายอีก 20 รายการที่ไม่ตรงคำค้น

ผลคือผู้ใช้ค้นหา “PAL” แต่เห็นงานที่ไม่มี PAL อยู่ในรายการ และตัวเลขข้างบนบอกจำนวนที่ไม่ตรงกับสิ่งที่เห็น

อาการนี้ทำซ้ำได้ยากมาก เพราะต้องพิมพ์พอดีจังหวะที่เลื่อนถึงท้าย

3. Mental model: สองคำสั่งที่แตะข้อมูลก้อนเดียวกัน

ค้นหา      →  แทนที่ข้อมูลทั้งชุด  →  เริ่มชุดใหม่
โหลดเพิ่ม  →  ต่อท้ายข้อมูลเดิม    →  ต่อชุดเดิม
ประโยคเดียวที่ต้องจำ: การโหลดเพิ่มต้องรู้ว่ากำลังต่อ ชุดไหน — ถ้าชุดนั้นถูกแทนที่ไปแล้ว ผลที่กลับมาต้องถูกทิ้ง

5. ส่งเงื่อนไขเดิมไปทุกครั้ง

// ผิด — ทิ้งเงื่อนไขเดิม
final page = await repository.fetchOpen(search: '', skip: _tasks.length);

// ถูก — ส่งเงื่อนไขที่ใช้อยู่จริง
final page = await repository.fetchOpen(search: _query, skip: _tasks.length);

ซึ่งแปลว่าต้องเก็บ _query ไว้ และต้องเก็บ ตอนที่ผลกลับมาสำเร็จ ไม่ใช่ตอนที่เริ่มยิง

final page = await repository.fetchOpen(query: query, skip: 0);
if (generation != _generation) return;
_tasks = page.items;
_totalCount = page.totalCount;
_query = query;                  // จำเงื่อนไขที่ใช้จริง หลังจากรู้ว่าผลนี้ใช้ได้

ถ้าเก็บตอนเริ่มยิง จะเกิดกรณีที่ _query เป็นของคำขอที่ถูกทิ้งไปแล้ว แล้วการโหลดเพิ่มจะใช้เงื่อนไขผิด

6. กรองซ้ำก่อนต่อท้าย

final seenIds = {for (final task in _tasks) task.id};
_tasks = [
  ..._tasks,
  for (final task in page.items)
    if (seenIds.add(task.id)) task,
];

จำเป็นเพราะการแบ่งหน้าด้วยตำแหน่งมีจุดอ่อนตามธรรมชาติ ตามที่เห็นใน 6.10

โหลดหน้า 1 → ได้รายการที่ 1–20
มีคนเพิ่มงานใหม่ ซึ่งเรียงมาเป็นอันดับที่ 1
โหลดหน้า 2 (ข้าม 20) → ได้รายการที่ 20–39
                        └─ รายการที่ 20 ซ้ำกับที่โหลดไปแล้ว

seenIds.add() คืน false เมื่อมีอยู่แล้ว จึงใช้เป็นเงื่อนไขกรองได้ในบรรทัดเดียว

การกรองซ้ำแก้เรื่องข้อมูลซ้ำ แต่ไม่ได้แก้เรื่องข้อมูล ขาด — ถ้ามีคนลบงานออกระหว่างโหลด รายการที่ 21 จะถูกข้ามไปโดยไม่มีใครรู้ ซึ่งแก้ได้ทางเดียวคือให้ฝั่งหลังบ้านใช้ตัวชี้ที่ผูกกับรายการสุดท้ายแทนตำแหน่ง

7. debounce ลดคำขอ แต่ไม่ได้แก้ปัญหา

Timer? _debounce;

void onQueryChanged(String query) {
  _debounce?.cancel();
  _debounce = Timer(const Duration(milliseconds: 300), () => search(query));
}
debounceตัวนับรุ่น
แก้อะไรลดจำนวนคำขอกันผลเก่าทับผลใหม่
ถ้าผู้ใช้พิมพ์ช้ากว่า 300msยิงทุกครั้งอยู่ดียังกันได้
ถ้าคำขอแรกช้ากว่าคำขอสองช่วยไม่ได้เลยกันได้

เป็นข้อสรุปเดียวกับ 4.10 — debounce เป็นเรื่องประสิทธิภาพ ตัวนับรุ่นเป็นเรื่องความถูกต้อง และถ้าเลือกได้แค่อย่างเดียวต้องเลือกอย่างหลัง

11. แบบฝึกหัด

หน้าค้นหางานมีข้อกำหนดเพิ่มมาข้อหนึ่ง — ผู้ใช้ลากลงเพื่อรีเฟรชได้ โดยที่คำค้นปัจจุบันยังอยู่

  1. อธิบายว่าการรีเฟรชควรเพิ่มเลขรุ่นหรือเกาะรุ่นเดิม
  2. เขียนเมธอด refresh()
  3. ตอบว่าถ้าผู้ใช้ลากรีเฟรชขณะที่กำลังโหลดเพิ่มอยู่ ควรเกิดอะไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — เพิ่มหรือเกาะ

เพิ่ม — เพราะการรีเฟรชคือการเริ่มชุดข้อมูลใหม่ ไม่ใช่การต่อชุดเดิม

คำสั่งทำอะไรกับข้อมูลเลขรุ่น
searchแทนที่ทั้งชุดเพิ่ม
refreshแทนที่ทั้งชุดเพิ่ม
loadMoreต่อท้ายเกาะเดิม

เกณฑ์คือ ดูว่าทำอะไรกับข้อมูล ไม่ใช่ดูว่าเงื่อนไขเปลี่ยนหรือไม่

คนมักตอบว่า “เกาะเดิม เพราะคำค้นไม่เปลี่ยน” ซึ่งเป็นการดูผิดจุด — สิ่งที่สำคัญคือผลที่กลับมาจะไปแทนที่ข้อมูลทั้งหมด ดังนั้นการโหลดเพิ่มที่ค้างอยู่ต้องถูกทิ้ง

ข้อ 2 — โค้ด

Future<void> refresh() async {
  final generation = ++_generation;    // เริ่มชุดใหม่
  final query = _query;                // ใช้คำค้นเดิม
  _refreshing = true;
  _errorMessage = null;
  // ไม่ตั้ง _loading เพราะยังมีข้อมูลให้แสดงอยู่ (4.7)
  notifyListeners();

  try {
    final page = await repository.searchOpen(
      palletCode: query.isEmpty ? null : query,
      skip: 0,
      take: _pageSize,
    );
    if (generation != _generation) return;
    _tasks = page.items;               // แทนที่ทั้งชุด
    _totalCount = page.totalCount;
  } on ApiException catch (error) {
    if (generation != _generation) return;
    // ล้มเหลวตอนรีเฟรช — เก็บข้อมูลเดิมไว้ให้ทำงานต่อได้ (4.7)
    _errorMessage = error.userMessage;
  } finally {
    if (generation == _generation) {
      _refreshing = false;
      notifyListeners();
    }
  }
}

ข้อ 3 — รีเฟรชขณะกำลังโหลดเพิ่ม

ไล่ตามลำดับเวลา

0.0s  ผู้ใช้เลื่อนถึงท้าย → loadMore() เริ่ม
      จำ generation = 5, ขอ skip: 20
0.3s  ผู้ใช้ลากลงรีเฟรช → refresh() เริ่ม
      _generation กลายเป็น 6
0.9s  refresh กลับมา → 6 == 6 → แทนที่ข้อมูลทั้งชุด
      _tasks = 20 รายการแรกที่สดใหม่
1.6s  loadMore กลับมา → 5 != 6 → ทิ้งผล ✓

ถ้าไม่ทิ้ง จะเกิดสิ่งนี้แทน

1.6s  ต่อท้าย 20 รายการที่ 21–40 ของ "ข้อมูลเมื่อ 1.6 วินาทีก่อน"
      เข้ากับ 20 รายการแรกที่ "สดใหม่"
      → รายการที่ 21–40 อาจซ้ำหรือขาด เพราะมาจากคนละช่วงเวลา

ผลคือรายการที่ผู้ใช้เห็นเป็นการปนกันของข้อมูลสองช่วงเวลา ซึ่งอาจมีงานที่ถูกปิดไปแล้วปนอยู่

สิ่งที่ควรทำเพิ่ม

ทำอะไรเพราะ
กันไม่ให้ loadMore เริ่มระหว่างรีเฟรชลดโอกาสเกิด
ปลดธง _loadingMore ให้ถูกไม่งั้นตัวหมุนท้ายรายการจะค้าง
Future<void> loadMore() async {
  if (_loadingMore || _loading || _refreshing || !hasMore) return;
  ...
  } finally {
    // ปลดธงเสมอ แม้รุ่นจะเปลี่ยนไปแล้ว ไม่งั้นตัวหมุนค้าง
    _loadingMore = false;
    if (generation == _generation) notifyListeners();
  }
}

บรรทัดใน finally เป็นจุดที่ละเอียด — ธงต้องปลดเสมอ แต่การแจ้งให้วาดใหม่ควรทำเฉพาะเมื่อยังเป็นรุ่นปัจจุบัน

ถ้าเอา _loadingMore = false ไปไว้ใต้เงื่อนไขตรวจรุ่น ตัวหมุนจะค้างถาวรเมื่อผลของรุ่นเก่ากลับมา ซึ่งเป็นบั๊กเดียวกับที่ 4.10 หัวข้อ 5 เตือนไว้

บทเรียนที่ควรจำ: เมื่อมีคำสั่งหลายตัวที่แตะข้อมูลก้อนเดียวกัน ให้จัดกลุ่มตาม สิ่งที่ทำกับข้อมูล ไม่ใช่ตามชื่อคำสั่ง — คำสั่งที่แทนที่ทั้งชุดเริ่มรุ่นใหม่ คำสั่งที่ต่อท้ายเกาะรุ่นเดิม

12. สรุปท้ายบท

  • ค้นหาและรีเฟรชแทนที่ทั้งชุด จึงเริ่มรุ่นใหม่
  • โหลดเพิ่มต่อท้าย จึงเกาะรุ่นเดิม
  • เก็บเงื่อนไขที่ใช้จริงไว้ แล้วส่งไปทุกครั้งที่โหลดเพิ่ม
  • เก็บเงื่อนไขตอนที่ผลกลับมาสำเร็จ ไม่ใช่ตอนเริ่มยิง
  • กรองซ้ำด้วย id ก่อนต่อท้าย
  • debounce ลดคำขอ ตัวนับรุ่นกันความผิด — ต้องมีทั้งคู่
  • ค้นด้วยตัวอักษรน้อยเกินไปไม่มีประโยชน์ แต่ต้องบอกผู้ใช้ว่าทำไม
  • ธงต้องปลดเสมอ แต่แจ้งให้วาดใหม่เฉพาะรุ่นปัจจุบัน
