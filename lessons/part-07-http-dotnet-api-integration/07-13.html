Query string คือ contract: pagination, search, filter และ sort ต้อง encode ด้วย Uri และผูกกับ response generation เพื่อกันข้อมูลเก่าทับใหม่

1. สร้าง query

final uri = base.replace(queryParameters: {
  'page': '$page',
  'pageSize': '$pageSize',
  if (search.trim().isNotEmpty) 'search': search.trim(),
  if (status != null) 'status': status.wireValue,
  'sort': 'createdAt:desc',
});

2. Page vs offset

Page-based ใช้ง่ายแต่รายการอาจเลื่อนเมื่อข้อมูลใหม่เข้า; offset-based มีปัญหาคล้ายกัน ส่วน cursor-based เสถียรกว่าสำหรับ feed ใหญ่ แต่ server/client ต้องออกแบบร่วมกัน

3. Search debounce

ข้อความค้นหาควร debounce และเพิ่ม request generation token เมื่อ query เปลี่ยน เพื่อไม่ให้ response คำเก่าที่ช้ากว่ามาทับผลคำล่าสุด

4. Reset pagination

เมื่อ search/filter/sort เปลี่ยน ต้องกลับหน้าแรก ล้าง accumulator และยกเลิกหรือ ignore request เดิม การคง page 5 ไว้อาจทำให้ดูเหมือนไม่มีข้อมูล

5. Repeat keys

ถ้า filter หลายค่าใช้ repeated query keys หรือ comma-separated ตาม contract อย่า rely กับ Map<String,String> หากต้องส่ง key ซ้ำ; ใช้ builder ที่รองรับรายการ

6. Server validation

.NET ต้อง clamp/max pageSize, whitelist sort fields และ parameterize search; client validationช่วย UX แต่ไม่แทน server security

7. แบบฝึกหัด

ผู้ใช้พิมพ์ “entity A&B” ต่อเนื่องสามครั้ง response แรกกลับมาทีหลังสุด ควรแสดงผลใด?

เฉลย

เฉพาะ generation ล่าสุด; Uri ต้อง decode search กลับข้อความเดิม และหน้าเริ่มที่ contract กำหนด

8. Checklist

encode query, ระบุ page origin, จำกัด pageSize, reset เมื่อ filter เปลี่ยน, stable sort, stale-response guard และ test อักขระพิเศษ
