Retry ไม่ใช่ “ลองทุกอย่างอีกครั้ง”: retry เมื่อ failure ชั่วคราวและ operation ปลอดภัยต่อการทำซ้ำ หรือมี idempotency guarantee เท่านั้น

1. Safe candidates

GET health/list/detail มัก retry ได้ ส่วน POST complete/receive/issue stock อาจทำซ้ำ side effect จึงห้าม auto-retry ถ้ายังไม่มี idempotency key

2. Retryable failure

พิจารณา timeout ก่อน connect, SocketException, 408, 429 และบาง 5xx ตาม API policy ไม่ retry 400/401/403/404 แบบอัตโนมัติ

3. Exponential backoff + jitter

final delay = Duration(
  milliseconds: (300 * math.pow(2, attempt)).round()
      + random.nextInt(200),
);
await Future.delayed(delay);

jitter ลดการยิงพร้อมกันเมื่อ server กลับมา

4. Budget

กำหนด max attempts และเวลารวม เช่น 2 retry ภายใน 10 วินาที เคารพ Retry-After และหยุดเมื่อผู้ใช้ออกจากหน้า/logout

5. UX

background refresh retry เงียบได้ช่วงสั้น แต่ command ที่ผลไม่แน่นอนต้องบอกผู้ใช้ว่า “กำลังตรวจสอบผล” ไม่แสดงล้มเหลวเด็ดขาดก่อน reconcile

6. Server load

retry storm ทำ outage แย่ลง จึงควรมี backoff, jitter, circuit breaker ระดับระบบเมื่อจำเป็น และ telemetry แยก original request จาก retry attempt

7. แบบฝึกหัด

POST complete timeout หลัง 8 วินาที จะ retry อัตโนมัติไหม?

เฉลย

ไม่ เว้นแต่ส่ง idempotency key เดิมและ serverรับประกัน dedupe; ทางเลือกคือ query command status ก่อน

8. กฎตัดสินใจ

ถามสองข้อก่อน retry: “รู้ไหมว่า server ยังไม่ทำ?” และ “ทำซ้ำแล้วผลเท่าเดิมแน่ไหม?” ถ้าตอบไม่ได้ให้หยุดและ reconcile
