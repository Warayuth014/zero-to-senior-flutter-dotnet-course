1. อย่าเริ่มอ่านที่ HTTP

เริ่มจากเหตุการณ์ของผู้ใช้และผลลัพธ์ที่หน้าจอต้องแสดง แล้วจึงตาม call chain ลงไป วิธีนี้ทำให้รู้ว่า request มีไว้ตอบโจทย์ workflow ใด ไม่หลงอยู่ใน utility code

2. เส้นทางไปและกลับ

ScanScreen
  → TaskStore.submit(barcode)
  → TasksApi.complete(request)
  → ApiClient.post('/tasks/complete')
  → .NET endpoint → service → database
  ← HTTP status + JSON
  ← TaskDto → Task domain model
  ← AsyncState.success/error → widget rebuild

3. Boundary แต่ละชั้น

  • Widget รับ input และ render state
  • Store คุม loading/race/workflow
  • API class รู้ endpoint และ DTO
  • ApiClient รู้ HTTP, header, timeout และ decode
  • .NET รับ/validate DTO และคืน contract

4. ไฟล์จริง

ดู wmsapp/lib/services/api_service.dart และ wms_absolute_mobile/lib/core/api_client.dart เป็น transport boundary จากนั้นดู API ราย feature เช่น api/tasks_api.dart เพื่อเห็น endpoint-specific mapping

5. ตัวอย่าง orchestration

Future<void> load() async {
  state = const TaskState.loading(); notifyListeners();
  try {
    final page = await api.fetchTasks();
    state = TaskState.ready(page.items);
  } on ApiException catch (e) {
    state = TaskState.failed(e.userMessage);
  }
  notifyListeners();
}

6. แบ่งความรับผิดชอบ

อย่าให้ widget ต่อ URL, อ่าน status code และ cast JSON เอง เพราะจะทดสอบยากและ error policy กระจายหลายหน้า ส่วน business logic ภายใน .NET เรียนละเอียดในคอร์ส backend; บทนี้เน้น contract ที่ Flutter ต้องพึ่งพา

7. แบบฝึกหัด

เลือกปุ่มหนึ่งในแอป วาดลูกศรไป-กลับครบทุกชั้น พร้อมเขียน input, output และ failure ของแต่ละ boundary

แนวคำตอบ

เส้นทางต้องจบกลับที่ state ของ UI และแยก network failure ออกจาก contract/business failure

8. Checklist

ตอบให้ได้ว่าใครสร้าง DTO, ใครส่ง HTTP, ใคร parse JSON, ใครถือ loading/error และ endpoint ใดเป็นเจ้าของ contract
