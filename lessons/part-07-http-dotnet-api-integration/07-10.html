สองแนวทาง: คืน ApiResult<T> ทำ failure ชัดใน type; throw ApiException ทำ happy path อ่านง่าย ทั้งคู่ใช้ได้ถ้ากำหนด policy สม่ำเสมอ

1. Result type

sealed class ApiResult<T> const ApiResult();
final class ApiSuccess<T> extends ApiResult<T> {
  const ApiSuccess(this.value); final T value;
}
final class ApiFailure<T> extends ApiResult<T> {
  const ApiFailure(this.error); final ApiError error;
}

2. Exception style

try {
  final page = await api.fetchTasks();
  state = Ready(page);
} on ApiException catch (e) {
  state = Failed(e.userMessage);
}

3. เลือก Result เมื่อ

failure เป็นผลที่คาดหมายและ caller ต้อง pattern-match ทุกครั้ง เช่น validation/conflict ใน workflow หรือทีมต้องการให้ compiler บังคับ handle

4. เลือก throw เมื่อ

service method มีค่าปกติหนึ่งแบบและใช้ shared boundary แปลง exception เป็น UI state ทำให้ chain หลายชั้นไม่ต้อง unwrap ซ้ำ

5. อย่าซ้อนสองระบบ

ApiResult ที่บาง branch ยัง throw network exception ทำให้ caller ต้อง handle สองทาง ถ้าใช้ Result ควรกำหนดว่าอะไรถูก capture และอะไรเป็น programmer error

6. Generic และ stack trace

ถ้า rethrow ใช้ rethrow เพื่อรักษา stack trace ไม่ใช้ throw e; Result ควรเก็บ cause สำหรับ diagnostics โดยไม่ expose ให้ UI

7. แบบฝึกหัด

แอปมี 30 API methods และทุก Store ใช้ Loading/Error/Success เดียวกัน ควรเริ่มจากอะไร?

แนวคำตอบ

เลือก convention เดียว เช่น typed ApiException + central mapper หรือ Result + exhaustive switch แล้วเขียนตัวอย่างมาตรฐานและ tests ก่อน migrate

8. Decision rule

ความสม่ำเสมอและ typed error สำคัญกว่าชื่อ pattern; ห้ามคืน null เพื่อแทนทั้ง not-found, offline และ parse error
