1. ปัญหาที่บทนี้แก้

โค้ดที่ดูเหมือนรอบคอบแล้ว

try {
  final json = await api.getJson('/api/WMS/mobile_tasks');
  ...
} catch (e) {
  showError('เชื่อมต่อไม่ได้');
}

ข้อความเดียวนี้ถูกใช้กับสถานการณ์ที่ต่างกันสิ้นเชิง

สิ่งที่เกิดจริงผู้ใช้ควรทำแต่ได้ข้อความว่า
Wi-Fi หลุดเดินไปที่ที่สัญญาณดีเชื่อมต่อไม่ได้
เซิร์ฟเวอร์ช้ามากรอแล้วลองใหม่เชื่อมต่อไม่ได้
ที่อยู่เซิร์ฟเวอร์ตั้งผิดไปแก้ในหน้าตั้งค่าเชื่อมต่อไม่ได้
บั๊กในโค้ดเราแจ้งทีมเชื่อมต่อไม่ได้

แถวสุดท้ายอันตรายที่สุด — catch (e) เปล่า ๆ กลืนบั๊กของเราเองแล้วแสดงว่าเป็นปัญหาเครือข่าย ทำให้ไม่มีใครไปแก้ที่ต้นเหตุ

2. คำศัพท์ที่ต้องรู้ก่อน

ชนิดเกิดเมื่อ
SocketExceptionต่อไม่ถึงปลายทาง — หาที่อยู่ไม่เจอ หรือไม่มีเส้นทาง
TimeoutExceptionรอเกินเวลาที่กำหนด
ClientExceptionปัญหาระดับการส่งอื่น ๆ เช่นการเชื่อมต่อขาดกลางคัน
FormatExceptionสิ่งที่ได้กลับมาไม่ใช่ JSON
ApiExceptionเซิร์ฟเวอร์ตอบมาแล้ว แต่ตอบว่าไม่สำเร็จ

3. Mental model: ไปไม่ถึง ไม่เท่ากับ ไปถึงแล้วไม่สำเร็จ

แอป ──X──→ เซิร์ฟเวอร์        ไปไม่ถึง — รู้แน่ว่าไม่มีอะไรเกิดขึ้น
แอป ─────→ เซิร์ฟเวอร์ ──X──→  ถึงแล้ว แต่คำตอบกลับไม่ถึง — ไม่รู้ผล
แอป ─────→ เซิร์ฟเวอร์ ────→  ถึงแล้ว ตอบว่าไม่ให้ทำ — รู้ผลแน่
ประโยคเดียวที่ต้องจำ: คำถามที่สำคัญที่สุดไม่ใช่ “ล้มเหลวเพราะอะไร” แต่คือ “เซิร์ฟเวอร์ทำไปแล้วหรือยัง” — เพราะคำตอบนั้นตัดสินว่าจะลองใหม่ได้ไหม

4. แปลงเป็นชนิดของเราที่ขอบ

เปิด lib/core/api_client.dart

} on SocketException {
  // GET ไม่เปลี่ยนข้อมูล จึงรู้แน่ว่าไม่มีอะไรเกิดขึ้น
  throw const ApiException(
    'เชื่อมต่อ server ไม่ได้',
    kind: ApiFailureKind.network,
  );
} on http.ClientException {
  throw const ApiException(
    'เชื่อมต่อ server ไม่ได้',
    kind: ApiFailureKind.network,
  );
} on TimeoutException {
  throw const ApiException(
    'server ไม่ตอบภายในเวลาที่กำหนด',
    kind: ApiFailureKind.timeout,
  );
}

สามอย่างที่เกิดขึ้นตรงนี้

สิ่งที่ทำเพราะ
ดักเฉพาะชนิดที่รู้จักบั๊กของเราจะไม่ถูกกลืน (4.8)
แปลงเป็น ApiException ชนิดเดียวชั้นบนไม่ต้องรู้จัก exception ของ HTTP
ติด kind ให้ทุกทางชั้นบนตัดสินใจได้โดยไม่ต้องอ่านข้อความ

ข้อสองสำคัญกว่าที่เห็น — ถ้าปล่อยให้ SocketException ลอยขึ้นไปถึง store จะกลายเป็นว่า store ต้อง import 'dart:io' ซึ่งทำให้ทดสอบยากและผูกกับแพลตฟอร์ม

5. ตั้งเวลารอให้เหมาะกับงาน

.timeout(const Duration(seconds: 15))

ตัวเลขนี้ไม่ควรเป็นค่าเดียวกันทุกที่

งานเวลาที่เหมาะเพราะ
ตรวจว่าเซิร์ฟเวอร์ยังอยู่ไหม3–5 วินาทีต้องรู้เร็ว ผู้ใช้กำลังรอดูผล
โหลดรายการงาน10–15 วินาทียอมรอได้ แต่ไม่ควรค้างนาน
ส่งคำสั่งที่เปลี่ยนข้อมูล20–30 วินาทียิ่งหมดเวลาเร็ว ยิ่งเจอกรณี "ไม่รู้ผล" บ่อย
อัปโหลดรูปนานกว่านั้นขึ้นกับขนาดไฟล์และสัญญาณ

แถวที่สามสวนความรู้สึก — คนมักคิดว่าคำสั่งสำคัญควรหมดเวลาเร็ว ๆ เพื่อให้ผู้ใช้รู้ผลไว แต่จริง ๆ แล้วตรงกันข้าม

ตั้ง 5 วินาที  → เซิร์ฟเวอร์ใช้ 7 วินาที → แอปบอกว่าไม่รู้ผล
                  ทั้งที่งานสำเร็จเรียบร้อย
                  → ผู้ใช้ต้องไปตรวจสอบเอง หรือเสี่ยงกดซ้ำ

ทุกครั้งที่หมดเวลารอกับคำสั่งที่เปลี่ยนข้อมูล จะเกิดสถานะ “ไม่รู้ผล” ที่ต้องจัดการ — ซึ่งแพงกว่าการรออีกสิบวินาทีมาก

6. หมดเวลารอไม่ได้แปลว่าเซิร์ฟเวอร์ไม่ทำ

นี่คือความเข้าใจผิดที่ทำให้เกิดข้อมูลซ้ำมากที่สุด

แอปเลิกรอที่วินาทีที่ 15
เซิร์ฟเวอร์ยังทำงานอยู่ และทำเสร็จที่วินาทีที่ 18
  → งานถูกบันทึกแล้ว แต่แอปไม่รู้

การเลิกรอเป็นการตัดสินใจของฝั่งเรา ไม่ได้ส่งสัญญาณอะไรไปบอกเซิร์ฟเวอร์ให้หยุด

ใน lab จึงตั้งธงไว้ต่างกันตาม method ตามที่เห็นใน 7.4

// GET — ไม่เปลี่ยนอะไรอยู่แล้ว
throw const ApiException('server ไม่ตอบภายในเวลาที่กำหนด',
    kind: ApiFailureKind.timeout);

// POST — เปลี่ยนข้อมูลได้
throw const ApiException('server ไม่ตอบหลังส่งคำสั่ง',
    outcomeUnknown: true, kind: ApiFailureKind.timeout);

และกฎนี้ถูกตรึงไว้ใน api_failure.dart

/// timeout กับ network ที่ขาดกลางทางคือกรณีที่ไม่รู้ผล ซึ่งห้ามเดา (4.13)
bool get outcomeIsKnown => switch (this) {
  ApiFailureKind.network || ApiFailureKind.timeout => false,
  _ => true,
};

7. ข้อความที่บอกว่าต้องทำอะไรต่อ

ชนิดข้อความที่ดีข้อความที่ไม่ช่วย
network“ติดต่อเซิร์ฟเวอร์ไม่ได้ ตรวจสอบ Wi-Fi แล้วลองใหม่”“SocketException”
timeout“เซิร์ฟเวอร์ตอบช้า ลองใหม่อีกครั้ง”“หมดเวลา”
timeout หลังส่งคำสั่ง“ไม่ทราบผล กำลังตรวจสอบสถานะล่าสุด”“บันทึกไม่สำเร็จ”
contract“ข้อมูลจากเซิร์ฟเวอร์ไม่ถูกต้อง กรุณาแจ้งทีม”“เกิดข้อผิดพลาด”

แถวที่สามสำคัญที่สุด — “บันทึกไม่สำเร็จ” เป็นการโกหกเมื่อยังไม่รู้ผล และเป็นการโกหกที่ทำให้ผู้ใช้กดซ้ำ

ส่วนแถวสุดท้าย ข้อความควรบอกด้วยว่าไม่ใช่ความผิดของผู้ใช้ ไม่งั้นเขาจะพยายามแก้เองไปเรื่อย ๆ

8. ไม่มีอินเทอร์เน็ต ไม่เท่ากับ ไม่มีเซิร์ฟเวอร์

ในคลังหลายแห่ง เครือข่ายภายในไม่ได้ต่อออกอินเทอร์เน็ตเลย

PDA ──→ Wi-Fi ของคลัง ──→ เซิร์ฟเวอร์ WMS   ✓ ทำงานได้
                        ──X──→ อินเทอร์เน็ต   ไม่ได้ต่อ
วิธีตรวจตอบอะไรได้
ตรวจว่ามีอินเทอร์เน็ตไหมไม่ตรงคำถาม — คลังหลายที่ไม่มีอยู่แล้ว
ตรวจว่ามีการเชื่อมต่อ Wi-Fi ไหมต่อ Wi-Fi ได้ไม่ได้แปลว่าถึงเซิร์ฟเวอร์
ยิงไปที่เซิร์ฟเวอร์จริงตอบตรงคำถาม

การใช้สถานะการเชื่อมต่อของเครื่องเป็นตัวตัดสิน จะทำให้แอปบอกว่า “ออฟไลน์” ทั้งที่ใช้งานได้ปกติ — ซึ่งเป็นการปิดกั้นผู้ใช้โดยไม่มีเหตุผล

วิธีที่ถูกคือถือว่าใช้งานได้ไว้ก่อน แล้วให้ผลของคำขอจริงเป็นตัวบอก ซึ่งจะทำเต็มรูปแบบใน 7.16

9. อย่าเปลี่ยนความล้มเหลวเป็นรายการว่าง

// อันตรายมาก
try {
  return await api.fetchTasks();
} catch (e) {
  return [];      // เน็ตหลุดกลายเป็น "วันนี้ไม่มีงาน"
}
สิ่งที่ผู้ใช้เห็นสิ่งที่เกิดจริง
“วันนี้ยังไม่มีงาน”มีงาน 40 ชิ้น แต่โหลดไม่ได้

ผลคือคนหน้างานยืนรอ หรือเดินไปถามหัวหน้าว่าทำไมไม่มีงาน ทั้งที่งานอยู่ในระบบครบ

เป็นหลักเดียวกับ 4.7 — “ไม่มีข้อมูล” กับ “เอาข้อมูลมาไม่ได้” เป็นคนละสถานะ และต้องแสดงต่างกัน

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ทุกปัญหาขึ้นข้อความเดียวกันcatch (e) เปล่า ๆดักเฉพาะชนิดที่รู้จัก
บั๊กในโค้ดถูกรายงานว่าเน็ตมีปัญหาเหมือนข้างบนเหมือนข้างบน
ข้อมูลซ้ำหลังจากที่หมดเวลารอถือว่าหมดเวลารอ = ไม่สำเร็จตั้ง outcomeUnknown แล้วไปตรวจสอบ
เจอกรณี “ไม่รู้ผล” บ่อยผิดปกติตั้งเวลารอสั้นเกินไปสำหรับคำสั่งยืดเวลาสำหรับคำสั่งที่เปลี่ยนข้อมูล
แอปบอกออฟไลน์ทั้งที่ใช้ได้ใช้สถานะอินเทอร์เน็ตเป็นตัวตัดสินยิงไปที่เซิร์ฟเวอร์จริง
เน็ตหลุดแล้วขึ้นว่าไม่มีงานคืนรายการว่างเมื่อล้มเหลวแยกสถานะให้ชัด
store ต้อง import dart:ioปล่อย exception ของ HTTP ขึ้นไปแปลงเป็นชนิดของเราที่ขอบ

11. แบบฝึกหัด

ทีมตั้งเวลารอไว้ 10 วินาทีทุก endpoint แล้วพบสองอาการ

#อาการ
1ตอนช่วงเช้าที่คนใช้เยอะ มีรายงานว่า “กดปิดงานแล้วขึ้นว่าไม่สำเร็จ แต่พอกลับมาดูงานปิดไปแล้ว” สัปดาห์ละหลายครั้ง
2หน้าตั้งค่ามีปุ่มทดสอบการเชื่อมต่อ ผู้ใช้บ่นว่ากดแล้วต้องรอนานกว่าจะรู้ว่าที่อยู่ผิด
  1. อธิบายว่าทั้งสองอาการมาจากสาเหตุเดียวกันอย่างไร
  2. เสนอค่าที่ควรตั้งของแต่ละงาน พร้อมเหตุผล
  3. ตอบว่าการแก้เวลารออย่างเดียวพอไหมสำหรับอาการที่ 1
ดูแนวคำตอบและเหตุผล

ข้อ 1 — สาเหตุเดียวกัน

ทั้งสองมาจาก การใช้ค่าเดียวกับงานที่มีความต้องการตรงข้ามกัน

ปิดงานทดสอบการเชื่อมต่อ
ผู้ใช้กำลังทำอะไรทำงานจริง รอผลได้กำลังตั้งค่า อยากรู้เร็ว
หมดเวลาเร็วไปแล้วเสียหายอย่างไรเกิดสถานะไม่รู้ผลไม่เสียหาย
หมดเวลาช้าไปแล้วเสียหายอย่างไรไม่เสียหายมากผู้ใช้ยืนรอโดยไม่จำเป็น

10 วินาทีจึง สั้นไป สำหรับอย่างแรก และ ยาวไป สำหรับอย่างที่สอง

และอาการที่ 1 บอกใบ้ชัดว่าเป็นเรื่องเวลา — “ช่วงเช้าที่คนใช้เยอะ” คือช่วงที่เซิร์ฟเวอร์ช้าลง ทำให้บางคำขอเกิน 10 วินาที

ข้อ 2 — ค่าที่ควรตั้ง

งานค่าเหตุผล
ทดสอบการเชื่อมต่อ5 วินาทีต้องรู้เร็ว และไม่มีผลข้างเคียงถ้าตัดสินผิด
โหลดรายการ15 วินาทีล้มเหลวแล้วกดใหม่ได้ ไม่มีอะไรเสียหาย
ปิดงาน / คำสั่งที่เปลี่ยนข้อมูล30 วินาทีทุกครั้งที่หมดเวลา = เกิดสถานะไม่รู้ผล ซึ่งแพงกว่าการรอ
// ให้ตั้งได้ต่อคำขอ แทนที่จะเป็นค่าเดียวทั้งคลาส
Future<Map<String, dynamic>> getJson(
  String path, {
  Duration timeout = const Duration(seconds: 15),
}) async {
  ...
  .timeout(timeout);
}

ข้อ 3 — แก้เวลารออย่างเดียวพอไหม

ไม่พอ และนี่คือประเด็นหลักของแบบฝึกหัดนี้

การยืดเป็น 30 วินาทีลดความถี่ของอาการ แต่ไม่ได้กำจัดมัน — ตราบใดที่มีเวลารอ ก็ยังมีโอกาสที่เซิร์ฟเวอร์จะใช้เวลานานกว่านั้น

สิ่งที่ต้องมีเพิ่มบททำอะไร
ตั้ง outcomeUnknown ให้ถูก7.4แยก "ไม่รู้ผล" ออกจาก "ล้มเหลวแน่"
ห้ามย้อนกลับเมื่อไม่รู้ผล4.13ไปโหลดใหม่แทนการเดา
รหัสคำสั่ง4.14, 7.15ส่งซ้ำได้โดยไม่บันทึกซ้ำ
ข้อความที่บอกว่ากำลังตรวจสอบ7.7 หัวข้อ 7ไม่บอกว่าล้มเหลวทั้งที่ยังไม่รู้

สังเกตว่าอาการที่รายงานมาคือ “ขึ้นว่าไม่สำเร็จ แต่งานปิดไปแล้ว” ซึ่งชี้ว่าปัญหาจริงไม่ใช่เวลารอ แต่คือ แอปบอกว่าล้มเหลวทั้งที่ยังไม่รู้ผล

สิ่งที่เกิด:  หมดเวลารอ → แอปบอก "ไม่สำเร็จ" → ผู้ใช้เชื่อ → งานจริงปิดไปแล้ว
สิ่งที่ควรเป็น: หมดเวลารอ → แอปบอก "กำลังตรวจสอบ" → โหลดใหม่ → บอกผลจริง

ถ้าทำข้อนี้แล้ว ต่อให้เวลารอเป็น 10 วินาทีเหมือนเดิม อาการที่ผู้ใช้รายงานก็จะหายไป เพราะแอปจะไปหาความจริงมาบอกแทนที่จะเดา

บทเรียนที่ควรจำ: การปรับตัวเลขเวลารอเป็นการลดความถี่ ส่วนการจัดการสถานะ “ไม่รู้ผล” ให้ถูกคือการแก้ปัญหา — และเมื่อเจออาการแบบนี้ ให้แก้อย่างหลังก่อนเสมอ เพราะอย่างแรกไม่มีวันพอ

12. สรุปท้ายบท

  • ดักเฉพาะชนิดที่รู้จัก อย่าใช้ catch (e) เปล่า ๆ
  • แปลง exception ของ HTTP เป็นชนิดของเราที่ขอบ
  • คำถามสำคัญคือ “เซิร์ฟเวอร์ทำไปแล้วหรือยัง” ไม่ใช่ “ล้มเหลวเพราะอะไร”
  • หมดเวลารอไม่ได้แปลว่าเซิร์ฟเวอร์หยุดทำงาน
  • คำสั่งที่เปลี่ยนข้อมูลควรตั้งเวลารอนานกว่า ไม่ใช่สั้นกว่า
  • ข้อความต้องบอกว่าต้องทำอะไรต่อ และห้ามบอกว่าล้มเหลวเมื่อยังไม่รู้ผล
  • ไม่มีอินเทอร์เน็ตไม่เท่ากับเข้าเซิร์ฟเวอร์ไม่ได้
  • ห้ามเปลี่ยนความล้มเหลวเป็นรายการว่าง

บทถัดไป: 7.8 จะดูฝั่งที่คำขอสำเร็จแล้ว — และทำไมรหัส 200 ยังไม่ได้แปลว่าข้อมูลใช้ได้
