1. ปัญหาที่บทนี้แก้

HTTP มีวิธีส่งคำขอหลายแบบ และสองแบบที่ใช้บ่อยที่สุดคือ GET กับ POST

คำถามที่ดูเหมือนเป็นเรื่องของรูปแบบ แต่จริง ๆ แล้วเป็นเรื่องของความหมาย

GET  /api/WMS/mobile_tasks              "ขอดูรายการงาน"
POST /api/WMS/mobile_tasks/T-001/complete   "สั่งให้ปิดงาน T-001"

ถ้าเลือกผิด สิ่งที่ตามมาไม่ใช่แค่ผิดหลักการ

ถ้าใช้ GET สั่งให้ปิดงานผลที่เกิดจริง
เบราว์เซอร์และตัวกลางเก็บผลไว้ใช้ซ้ำกดปิดงานครั้งที่สองไม่ถึงเซิร์ฟเวอร์
ตัวกลางในเครือข่ายลองใหม่เองเมื่อล้มเหลวงานถูกปิดสองครั้ง
รหัสงานไปโผล่ใน log ของทุกตัวกลางที่ผ่านข้อมูลรั่วโดยไม่ตั้งใจ

แถวที่สองสำคัญที่สุด — ระบบเครือข่ายถือว่า GET ปลอดภัยที่จะทำซ้ำ และจะทำซ้ำให้เองโดยไม่ถามใคร

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
methodชนิดของคำขอ เช่น GET, POST
bodyข้อมูลที่ส่งไปกับคำขอ
queryข้อมูลที่ต่อท้าย URL
safeไม่เปลี่ยนแปลงอะไรที่เซิร์ฟเวอร์
idempotentทำซ้ำแล้วผลเท่ากับทำครั้งเดียว
Content-Typeบอกว่า body ที่ส่งเป็นรูปแบบอะไร

3. Mental model: ถามหรือสั่ง

"ขอดูหน่อย"     → GET   ทำกี่ครั้งก็ได้ ไม่มีอะไรเปลี่ยน
"ทำสิ่งนี้ให้ที"  → POST  ทำซ้ำอาจได้ผลซ้ำ ต้องระวัง
ประโยคเดียวที่ต้องจำ: ถามว่า “ถ้าคำขอนี้ถูกส่งซ้ำสามครั้งโดยไม่มีใครตั้งใจ จะเป็นไรไหม” — ถ้าไม่เป็นไรคือ GET ถ้าเป็นไรคือ POST

4. อ่านข้อมูลด้วย GET

เปิด lib/core/api_client.dart

Future<Map<String, dynamic>> getJson(String path) async {
  try {
    final response = await _client
        .get(Uri.parse('$baseUrl$path'), headers: _headers())
        .timeout(const Duration(seconds: 15));
    return _decode(response);
  } on SocketException {
    // GET ไม่เปลี่ยนข้อมูล จึงรู้แน่ว่าไม่มีอะไรเกิดขึ้น
    throw const ApiException('เชื่อมต่อ server ไม่ได้', kind: ApiFailureKind.network);
  }
  ...
}

คอมเมนต์บรรทัดนั้นสำคัญกว่าที่เห็น — เพราะ GET ไม่เปลี่ยนอะไร เราจึงรู้แน่ว่าเน็ตหลุดแปลว่าไม่มีอะไรเกิดขึ้น ซึ่งทำให้ลองใหม่ได้อย่างปลอดภัย

เงื่อนไขที่ต้องรักษาไว้เพื่อให้ข้อสรุปนี้จริง

ต้องไม่ทำเพราะ
ให้ GET เปลี่ยนข้อมูลข้อสรุปเรื่องลองใหม่จะไม่จริงอีกต่อไป
ให้ GET มี bodyตัวกลางบางตัวตัด body ของ GET ทิ้ง
ใส่ข้อมูลอ่อนไหวใน queryไปโผล่ใน log ของทุกตัวกลาง (7.17)

5. สั่งงานด้วย POST

Future<Map<String, dynamic>> postJson(
  String path,
  Map<String, dynamic> body, {
  Map<String, String> headers = const {},
}) async {
  try {
    final response = await _client
        .post(
          Uri.parse('$baseUrl$path'),
          headers: {..._headers(), ...headers},
          body: jsonEncode(body),
        )
        .timeout(const Duration(seconds: 15));
    return _decode(response);
  } on SocketException {
    // POST เปลี่ยนข้อมูลได้ จึงไม่รู้ว่า server ทำไปแล้วหรือยัง
    throw const ApiException(
      'การเชื่อมต่อขาดระหว่างส่งคำสั่ง',
      outcomeUnknown: true,
      kind: ApiFailureKind.network,
    );
  }
  ...
}

เทียบสองเมธอดนี้จะเห็นความต่างที่สำคัญที่สุดของบทนี้

getJsonpostJson
เน็ตหลุดแล้วรู้ผลไหมรู้ — ไม่มีอะไรเกิดขึ้นไม่รู้
outcomeUnknownไม่ตั้ง (เป็น false)true
ลองใหม่เองอัตโนมัติได้ไหมได้ไม่ได้ ถ้าไม่มีรหัสคำสั่ง

ธง outcomeUnknown นี้คือตัวเดียวกับที่ใช้ตัดสินใน 4.13 ว่าจะย้อนกลับหรือไปตรวจสอบ — และมันถูกกำหนดตั้งแต่ชั้นนี้ เพราะชั้นนี้เป็นชั้นเดียวที่รู้ว่าใช้ method อะไร

6. body ต้องเป็นข้อความ JSON ไม่ใช่ Map

// ผิด — Dart จะแปลง Map เป็นข้อความแบบของ Dart ไม่ใช่ JSON
body: {'taskId': 'T-001', 'quantity': 12}

// ได้ {taskId: T-001, quantity: 12}  ← ไม่มีเครื่องหมายคำพูด ไม่ใช่ JSON
// server ตอบ 400 หรือ 415
// ถูก
body: jsonEncode({'taskId': 'T-001', 'quantity': 12}),
headers: {'Content-Type': 'application/json'},

สองอย่างต้องมาคู่กันเสมอ — jsonEncode ทำให้เนื้อหาเป็น JSON และ Content-Type บอกเซิร์ฟเวอร์ว่าให้อ่านแบบ JSON

ถ้าขาดอย่างใดอย่างหนึ่งจะได้รหัส 415 ซึ่งแปลว่า “ส่งมาในรูปแบบที่ฉันไม่รับ”

ใน lab _headers() ใส่ Content-Type ให้ทุกคำขออยู่แล้ว จึงไม่ต้องใส่ซ้ำในแต่ละที่ที่เรียก — เป็นรูปแบบเดียวกับการรวมกฎไว้ที่เดียวใน 6.2

7. ส่งอะไรไปใน body

คำถามที่ตอบง่ายผิด — ส่ง model ที่มีอยู่แล้วไปเลยได้ไหม

// เลี่ยง
body: jsonEncode(task.toJson())
ปัญหารายละเอียด
ส่ง field ที่เซิร์ฟเวอร์ไม่ต้องการเช่น createdAt ที่เซิร์ฟเวอร์เป็นคนกำหนดเอง
เพิ่ม field ใน model แล้วสัญญาเปลี่ยนเงียบ ๆไม่มีอะไรบอกว่าคำขอเปลี่ยนไป
ไม่รู้ว่าคำขอนี้ต้องมีอะไรบ้างต้องไปอ่าน model ทั้งตัว

ทางที่ถูกคือมีชนิดของคำขอแยกต่างหาก ตามที่ทำไว้ใน 6.2

class CompleteTaskRequest {
  const CompleteTaskRequest({
    required this.taskId,
    required this.quantity,
    required this.commandId,
    this.note,
  });

  Map<String, Object?> toJson() => {
    'taskId': taskId,
    'quantity': quantity,
    'commandId': commandId,
    'note': note,
  };
}

อ่านคลาสนี้แล้วรู้ทันทีว่าคำขอนี้ต้องมีอะไร และ compiler บังคับให้ครบตั้งแต่ตอนเขียน

8. method อื่นที่จะเจอ

methodความหมายทั่วไปทำซ้ำแล้วผลเท่าเดิมไหม
GETอ่านใช่
POSTสร้างหรือสั่งงานไม่
PUTแทนที่ทั้งชิ้นใช่
PATCHแก้บางส่วนแล้วแต่ว่าแก้อะไร
DELETEลบใช่ — ลบซ้ำก็ยังไม่มีอยู่

คอลัมน์ขวาคือสิ่งที่สำคัญกว่าชื่อ — มันบอกว่าตัวกลางในเครือข่ายจะกล้าลองใหม่ให้หรือไม่

แต่ความหมายจริงต้องอ่านจากสัญญาของ endpoint นั้น ไม่ใช่เดาจากชื่อ method — บาง API ใช้ POST กับทุกอย่างรวมถึงการอ่านข้อมูล ซึ่งถ้าเป็นแบบนั้นต้องรู้ตัวว่าเสียคุณสมบัติเรื่องการลองใหม่ไปด้วย

9. คำตอบที่ไม่มีเนื้อหา

ไม่ใช่ทุกคำขอที่ได้ข้อมูลกลับมา

รหัสความหมายต้องทำอะไร
200สำเร็จ พร้อมข้อมูลอ่าน body
201สร้างสำเร็จอ่าน body หรือดูที่อยู่ของสิ่งที่สร้าง
204สำเร็จ ไม่มีเนื้อหาห้ามพยายามอ่าน body
// ใน _decode ของ lab
if (response.statusCode >= 200 && response.statusCode < 300) {
  // 204 และ 200 ที่ body ว่าง ถือว่าสำเร็จ ไม่ต้องมี JSON
  return json ?? <String, dynamic>{};
}

ถ้าเรียก jsonDecode('') จะได้ FormatException ที่หน้าตาเหมือนปัญหาสัญญา ทั้งที่จริง ๆ แล้วคำขอสำเร็จเรียบร้อย — เป็นข้อผิดพลาดที่ทำให้ไล่หาสาเหตุผิดทางได้ง่าย

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
กดปิดงานครั้งที่สองไม่มีอะไรเกิดขึ้นใช้ GET สั่งงาน แล้วผลถูกเก็บไว้ใช้ซ้ำเปลี่ยนเป็น POST
งานถูกบันทึกซ้ำโดยไม่มีใครกดซ้ำตัวกลางลองใหม่ให้เอง เพราะคิดว่าปลอดภัยใช้ POST และรหัสคำสั่ง (7.15)
รหัส 415ไม่ได้ jsonEncode หรือไม่มี Content-Typeใส่ทั้งคู่
รหัส 400 ทั้งที่ข้อมูลดูถูกส่ง Map เข้าไปตรง ๆjsonEncode ก่อน
FormatException ทั้งที่คำขอสำเร็จพยายามอ่าน body ของ 204ตรวจก่อนว่ามีเนื้อหาไหม
เซิร์ฟเวอร์บ่นว่ามี field แปลก ๆส่ง model ทั้งตัวไปทำชนิดของคำขอแยก
ค้นหาแล้วเจอผลเก่าผลของ GET ถูกเก็บไว้เป็นพฤติกรรมปกติ — ถ้าไม่ต้องการต้องบอกเซิร์ฟเวอร์

11. แบบฝึกหัด

ทีมกำลังออกแบบ endpoint สำหรับงานสี่อย่าง

#งาน
1ดูรายการงานที่ยังไม่เสร็จ
2ค้นหางานด้วยรหัสพาเลท
3ยืนยันการหยิบสินค้าหนึ่งบรรทัด
4บันทึกว่าผู้ใช้เปิดดูงานนี้แล้ว เพื่อเก็บสถิติ
  1. เลือก method และเขียน endpoint ของแต่ละงาน
  2. ระบุว่างานไหนต้องมีรหัสคำสั่ง
  3. งานที่ 4 มีจุดที่ต้องคิดเป็นพิเศษ — อธิบายว่าคืออะไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 และ 2

#method และเส้นทางต้องมีรหัสคำสั่งไหม
1GET /api/WMS/mobile_tasks?status=openไม่
2GET /api/WMS/mobile_tasks?search=PAL-0101ไม่
3POST /api/WMS/mobile_tasks/T-001/completeต้องมี
4POST /api/WMS/mobile_tasks/T-001/viewedดูข้อ 3

ข้อ 2 ใช้ GET ทั้งที่ผู้ใช้ “ทำอะไรบางอย่าง” — เพราะการค้นหาไม่ได้เปลี่ยนแปลงอะไรที่เซิร์ฟเวอร์ การค้นซ้ำสิบครั้งก็ได้ผลเหมือนเดิม

ข้อ 3 ต้องมีรหัสคำสั่งเพราะเป็นคำสั่งที่ทำซ้ำแล้วเสียหาย และเน็ตอาจหลุดตอนที่ไม่รู้ผล ตามที่วางไว้ใน 4.14

ข้อ 3 — จุดที่ต้องคิดเป็นพิเศษของงานที่ 4

งานนี้ดูเหมือนงานเล็กที่สุด แต่มีคำถามซ้อนอยู่หลายชั้น

ชั้นที่หนึ่ง — มันเปลี่ยนข้อมูลหรือเปล่า

เปลี่ยน — มันเขียนสถิติลงฐานข้อมูล จึงเป็น POST ไม่ใช่ GET

คนมักเผลอทำเป็น GET เพราะรู้สึกว่า “แค่ดู” แต่สิ่งที่ตัดสินคือ ผลที่เซิร์ฟเวอร์ ไม่ใช่เจตนาของผู้ใช้

ชั้นที่สอง — ต้องรอผลไหม

ยืนยันการหยิบ (ข้อ 3)บันทึกสถิติ (ข้อ 4)
ผู้ใช้ต้องรู้ผลไหมต้องไม่ต้อง
ล้มเหลวแล้วต้องบอกไหมต้องไม่ควรบอก
ต้องกันกดซ้ำไหมต้องไม่ต้อง
// ข้อ 4 — สั่งแล้วไม่รอ และต้องจัดการ error ในตัวเอง (4.8)
unawaited(analytics.recordTaskViewed(taskId));

ถ้าเผลอ await การเปิดดูงานจะช้าลงเพราะรอบันทึกสถิติ และถ้าบันทึกล้มเหลว ผู้ใช้จะเห็นข้อความผิดพลาดทั้งที่ไม่ได้ทำอะไรผิดเลย

ชั้นที่สาม — รหัสคำสั่งจำเป็นไหม

คำตอบคือ ไม่จำเป็น แต่ด้วยเหตุผลที่ต้องคิดให้ครบ

คำถามคำตอบ
บันทึกซ้ำแล้วเสียหายไหมสถิติเพี้ยนเล็กน้อย ไม่กระทบการทำงาน
คุ้มที่จะทำระบบกันซ้ำไหมไม่ — ต้นทุนสูงกว่าความเสียหาย
ถ้าสถิตินี้เอาไปคิดค่าตอบแทนล่ะคำตอบเปลี่ยนทันที — ต้องกันซ้ำ

แถวสุดท้ายคือประเด็นจริงของข้อนี้ — “ข้อมูลนี้เอาไปใช้ทำอะไร” เป็นคำถามที่ต้องถามก่อนตัดสินใจ ไม่ใช่คำถามที่ถามทีหลัง

สถิติที่เอาไปดูเฉย ๆ กับสถิติที่เอาไปคิดเงิน มีข้อกำหนดคนละระดับ ทั้งที่ endpoint หน้าตาเหมือนกันทุกอย่าง

ชั้นที่สี่ — ข้อมูลส่วนบุคคล

การบันทึกว่า “ใครเปิดดูอะไรเมื่อไหร่” เป็นข้อมูลที่ติดตามพฤติกรรมพนักงานได้ ซึ่งต้องมีเหตุผลรองรับและควรแจ้งให้ทราบ — ไม่ใช่เรื่องเทคนิค แต่เป็นเรื่องที่ต้องถามก่อนเขียนโค้ด

บทเรียนที่ควรจำ: การเลือก method ตัดสินจาก ผลที่เกิดกับเซิร์ฟเวอร์ ไม่ใช่จากความรู้สึกของผู้ใช้ — และคำถามว่า “ต้องกันซ้ำไหม” ตอบไม่ได้จนกว่าจะรู้ว่าข้อมูลนั้นถูกเอาไปใช้ทำอะไร

12. สรุปท้ายบท

  • เลือก method จากคำถามว่า “ถูกส่งซ้ำโดยไม่ตั้งใจแล้วเป็นไรไหม”
  • ตัวกลางในเครือข่ายลองใหม่ให้เองกับคำขอที่ถือว่าปลอดภัย
  • GET ไม่เปลี่ยนอะไร จึงรู้แน่ว่าเน็ตหลุดแปลว่าไม่มีอะไรเกิดขึ้น
  • POST เปลี่ยนข้อมูลได้ จึงต้องตั้ง outcomeUnknown เมื่อเน็ตหลุด
  • body ต้องผ่าน jsonEncode และต้องมี Content-Type คู่กัน
  • ส่งชนิดของคำขอที่แยกไว้ ไม่ส่ง model ทั้งตัว
  • 204 ไม่มีเนื้อหา ห้ามพยายามอ่าน body
  • ผลที่เกิดกับเซิร์ฟเวอร์เป็นตัวตัดสิน ไม่ใช่ความรู้สึกของผู้ใช้

บทถัดไป: 7.5 จะดูข้อมูลที่เดินทางไปกับคำขอแต่ไม่ได้อยู่ใน body — ตั้งแต่การบอกชนิดข้อมูล ไปจนถึงบัตรผ่านที่ยืนยันว่าเราเป็นใคร
