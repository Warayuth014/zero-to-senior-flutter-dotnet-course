Idempotency: ส่ง command เดิมหลายครั้งด้วย key เดิมแล้วเกิดผลทางธุรกิจเพียงครั้งเดียว และ client ได้ผลลัพธ์เดิมกลับมา

1. ทำไม Mobile WMS ต้องมี

Wi-Fi หลุดหลัง server commit, ผู้ใช้กดซ้ำ, scanner ยิงซ้ำ หรือ app resume สามารถสร้างรับ/จ่าย/ยืนยันงานซ้ำได้ หาก client ตัดสินจาก timeout อย่างเดียว

2. Key ต่อ logical command

final commandId = const Uuid().v4();
await api.completeTask(
  request,
  idempotencyKey: commandId,
); // retry ต้องใช้ commandId เดิม

3. Header หรือ body

ใช้ Idempotency-Key header หรือ commandId ใน request DTO ตามมาตรฐานทีม Key ต้องผูกผู้ใช้/endpoint/payload และมีอายุจัดเก็บ

4. .NET algorithm

  1. เริ่ม transaction และตรวจ key
  2. ถ้ามีผลเดิม คืนผลเดิม
  3. ถ้า key เดิมแต่ payload fingerprint ต่าง คืน conflict
  4. ทำ business mutation
  5. บันทึก key + response atomically แล้ว commit

5. Unique constraint

ใช้ unique index ปิด race ระหว่าง request พร้อมกัน ไม่พึ่ง check-then-insert ใน memory และกำหนด behavior เมื่อคำสั่งแรกยัง processing

6. UI duplicate guard

disable ปุ่มและ debounce scanner ยังมีประโยชน์ต่อ UX แต่ไม่ใช่ correctness guarantee เพราะ app crash/restart และหลายอุปกรณ์ยังเกิดได้

7. แบบฝึกหัด

ผู้ใช้แก้ quantity แล้วกดใหม่ ควรใช้ key เดิมหรือใหม่?

เฉลย

ใหม่ เพราะเป็น logical command/payload ใหม่; หากส่ง payload ต่างด้วย key เดิม server ควร 409 ไม่ reuse ผลอย่างเงียบ ๆ

8. Exit criteria

ทดสอบ request ซ้ำพร้อมกัน, timeout แล้ว retry, app restart, key เดิม payload ต่าง และ retention หมดอายุ
