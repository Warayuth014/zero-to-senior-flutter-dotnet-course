1. ปัญหาที่บทนี้แก้

การต่อข้อความสองอันเข้าด้วยกัน ดูเป็นเรื่องที่ผิดไม่ได้

final url = baseUrl + path;

แต่ลองดูว่าเกิดอะไรเมื่อค่าจริงมาถึง

baseUrlpathผลลัพธ์

// server เห็น search=A และพารามิเตอร์แปลก ๆ ชื่อ B 01

3. Mental model: URL เป็นโครงสร้าง ไม่ใช่ข้อความ

คิดว่าเป็นข้อความ  →  ต่อกันเอง  →  ผิดเมื่อค่าไม่เป็นอย่างที่คิด
คิดว่าเป็นโครงสร้าง →  ประกอบด้วย Uri  →  Dart จัดการ encoding ให้
ประโยคเดียวที่ต้องจำ: ถ้าเห็น '$baseUrl$path' หรือ '?search=$value' ในโค้ด แปลว่ากำลังปฏิบัติกับ URL เหมือนข้อความ ซึ่งจะผิดเมื่อค่าจริงมาถึง

4. ให้ Uri เป็นคนประกอบ

Uri buildUri(String baseUrl, String path, [Map<String, String>? query]) {
  final base = Uri.parse(baseUrl);
  final basePath = base.path.endsWith('/')
      ? base.path.substring(0, base.path.length - 1)
      : base.path;
  final suffix = path.startsWith('/') ? path : '/$path';

  return base.replace(
    path: '$basePath$suffix',
    queryParameters: query,   // Dart encode ให้เอง
  );
}

ทดสอบกับค่าที่เคยพังในหัวข้อ 1

buildUri('http://wms.local/', '/api/tasks')
// http://wms.local/api/tasks   ✓

buildUri('http://wms.local', 'api/tasks')
// http://wms.local/api/tasks   ✓

buildUri('http://wms.local/wms', '/api/tasks', {'search': 'A&B 01'})
// http://wms.local/wms/api/tasks?search=A%26B+01   ✓

บรรทัดสุดท้ายคือสิ่งที่การต่อข้อความทำไม่ได้ — & กลายเป็น %26 และช่องว่างกลายเป็น + ซึ่งเซิร์ฟเวอร์จะถอดกลับเป็น A&B 01 ได้ถูกต้อง

5. ระวัง resolve ที่ทิ้ง path เดิม

Dart มีเมธอด resolve ที่ดูเหมือนจะเหมาะกับงานนี้ แต่มีพฤติกรรมที่ทำให้พลาดง่าย

final base = Uri.parse('http://wms.local/wms');

base.resolve('/api/tasks')    // http://wms.local/api/tasks   ← /wms หายไป
base.resolve('api/tasks')     // http://wms.local/api/tasks   ← หายเหมือนกัน

เพราะ resolve ทำตามกติกาของลิงก์ในหน้าเว็บ — path ที่ขึ้นต้นด้วยขีดทับหมายถึง “จากรากของ host” ไม่ใช่ “ต่อจากที่อยู่ปัจจุบัน”

อาการที่เจอคือแอปทำงานได้ตอนที่เซิร์ฟเวอร์อยู่ที่รากของ host แล้วพังทันทีที่ย้ายไปอยู่ใต้เส้นทางย่อย ซึ่งมักเกิดตอนขึ้น production

ถ้าจะใช้ resolve ต้องเขียนเทสต์ที่ base URL มีเส้นทางย่อยเสมอ — ไม่ใช่ทดสอบแค่ http://localhost:5000 ที่ไม่มี path

6. ตกลงให้ชัดว่า base URL รวมอะไร

คำถามที่ต้องตอบครั้งเดียวแล้วยึดตลอด — base URL รวม /api แล้วหรือยัง

ทางเลือกbase URLที่ repository เขียน
ไม่รวมhttp://wms.local:5000/api/WMS/mobile_tasks
รวมhttp://wms.local:5000/api/WMS/mobile_tasks

ทั้งสองแบบใช้ได้ แต่ต้องเลือกอย่างเดียวและเขียนไว้ให้ชัด

lab เลือกแบบแรก — ดูได้จาก task_repository.dart

final json = await api.getJson('/api/WMS/mobile_tasks');

เหตุผลที่แบบแรกมักดีกว่าคือ ไม่ใช่ทุก endpoint ที่อยู่ใต้ /api — หน้าตรวจสุขภาพเซิร์ฟเวอร์อาจอยู่ที่ /health เฉย ๆ ถ้ายัด /api ไว้ใน base URL จะเรียก endpoint นั้นไม่ได้

7. ตรวจ URL ตอนที่ผู้ใช้กรอก

ในแอปคลังจริง ผู้ใช้เป็นคนกรอกที่อยู่เซิร์ฟเวอร์เอง เพราะแต่ละสาขาคนละที่

/// ตรวจและทำให้เป็นรูปแบบมาตรฐานตั้งแต่ตอนบันทึก
/// ไม่ใช่ตอนใช้งาน — ผู้ใช้จะได้รู้ทันทีว่าพิมพ์ผิด
Uri parseBaseUrl(String raw) {
  final trimmed = raw.trim();
  final uri = Uri.tryParse(trimmed);

  if (uri == null || !uri.hasScheme || uri.host.isEmpty) {
    throw const FormatException('กรุณาระบุที่อยู่ เช่น http://192.168.1.50:5000');
  }
  if (uri.scheme != 'http' && uri.scheme != 'https') {
    throw FormatException('รองรับเฉพาะ http และ https แต่ได้ ${uri.scheme}');
  }
  // ตัดขีดทับปิดท้ายทิ้งที่นี่ที่เดียว จะได้ไม่ต้องระวังทุกที่ที่ใช้
  return uri.replace(path: uri.path.replaceAll(RegExp(r'/+$'), ''));
}
ผู้ใช้พิมพ์ผลลัพธ์
http://wms.local:5000/ http://wms.local:5000
wms.local:5000ปฏิเสธ — ไม่มี scheme
ftp://wms.localปฏิเสธ — scheme ที่ไม่รองรับ

สังเกตว่าแถวสองน่าสนใจ — Uri.tryParse('wms.local:5000') ไม่คืน null เพราะมันตีความว่า wms.local คือ scheme การตรวจ host.isEmpty จึงจำเป็น

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
404 ทั้งที่ endpoint มีอยู่มีขีดทับซ้อนหรือหายไปประกอบด้วย Uri ที่จัดการขีดทับ
ค้นหาด้วยรหัสที่มี & แล้วไม่เจอต่อ query เป็นข้อความใช้ queryParameters
ค้นหาภาษาไทยแล้วได้ผลแปลกไม่ได้ encodeเหมือนข้างบน
ทำงานได้ตอน dev พังตอน productionใช้ resolve กับ base ที่มีเส้นทางย่อยประกอบ path เอง หรือทดสอบด้วย base ที่มี path
เรียก health check ไม่ได้ยัด /api ไว้ใน base URLให้ base URL เป็นแค่ที่อยู่เซิร์ฟเวอร์
ผู้ใช้กรอกที่อยู่แล้วใช้ไม่ได้ โดยไม่มีอะไรบอกไม่ได้ตรวจตอนบันทึกตรวจและทำให้เป็นมาตรฐานที่จุดบันทึก

9. แบบฝึกหัด

ผู้ใช้บันทึกที่อยู่เซิร์ฟเวอร์เป็น http://10.0.2.2:5000/wms/ และต้องเรียกสาม endpoint

งานเส้นทางquery
รายการงาน/api/WMS/mobile_taskssearch = A&B 01, page = 2
ปิดงาน/api/WMS/mobile_tasks/T-001/completeไม่มี
ตรวจสุขภาพ/healthไม่มี
  1. เขียน URL ที่ถูกต้องของทั้งสาม
  2. อธิบายว่าถ้ารหัสงานเป็น T/001 ที่มีขีดทับ จะเกิดอะไร และแก้อย่างไร
  3. ตอบว่าควรตรวจที่อยู่ตอนบันทึก หรือตอนยิงคำขอครั้งแรก
ดูแนวคำตอบและเหตุผล

ข้อ 1 — URL ที่ถูกต้อง

http://10.0.2.2:5000/wms/api/WMS/mobile_tasks?search=A%26B+01&page=2
http://10.0.2.2:5000/wms/api/WMS/mobile_tasks/T-001/complete
http://10.0.2.2:5000/wms/health

ทั้งสามต้องเก็บ /wms ไว้ — ซึ่งเป็นจุดที่ resolve จะทำหาย

และสังเกตว่าอันที่สามยังอยู่ใต้ /wms แม้จะไม่มี /api ซึ่งเป็นเหตุผลที่ base URL ไม่ควรรวม /api ไว้

ข้อ 2 — รหัสงานที่มีขีดทับ

ถ้าเอาไปต่อเข้ากับ path ตรง ๆ ขีดทับจะกลายเป็นตัวแบ่งเส้นทาง

'/api/WMS/mobile_tasks/T/001/complete'
//                      └─┬─┘
//                        server เห็นเป็นสองส่วน ไม่ใช่รหัสเดียว → 404

ทางแก้คือ encode เฉพาะส่วนที่เป็นค่า ไม่ใช่ทั้ง path

final encodedId = Uri.encodeComponent(taskId);   // T/001 → T%2F001
final path = '/api/WMS/mobile_tasks/$encodedId/complete';
ฟังก์ชันทำอะไรใช้เมื่อ
Uri.encodeComponentencode ทุกอย่างรวมขีดทับค่าที่จะไปอยู่ใน path หรือ query
Uri.encodeFullไม่ encode ขีดทับและตัวคั่นURL ทั้งอันที่ประกอบมาแล้ว

การใช้ encodeFull กับรหัสงานจะไม่แก้ปัญหา เพราะมันตั้งใจไม่แตะขีดทับ

แต่คำถามที่ควรถามต่อคือ — รหัสงานควรมีขีดทับได้หรือไม่

ทางเลือกผลที่ตามมา
encode แล้วส่งไปใช้ได้ แต่ต้องมั่นใจว่าเซิร์ฟเวอร์ decode กลับถูก
ส่งใน query แทน pathปลอดภัยกว่า แต่เปลี่ยนสัญญา
ห้ามรหัสมีขีดทับตั้งแต่ต้นทางดีที่สุดถ้าทำได้ แต่มักแก้ไม่ได้เพราะข้อมูลเก่า

ในทางปฏิบัติต้อง encode และ เขียนเทสต์ที่ใช้รหัสมีขีดทับจริง ๆ เพราะไม่งั้นจะไม่มีใครรู้ว่ามันพังจนกว่าจะเจอข้อมูลชุดนั้น

ข้อ 3 — ตรวจตอนไหน

ตอนบันทึก และเหตุผลไม่ใช่แค่เรื่องความสะดวก

ตรวจตอนบันทึกตรวจตอนยิงคำขอ
ผู้ใช้รู้ตอนไหนทันทีที่กดบันทึกตอนกดปุ่มทำงาน ซึ่งอาจเป็นวันถัดไป
ผู้ใช้อยู่ที่ไหนตอนรู้หน้าตั้งค่า ที่แก้ได้เลยกลางคลัง ที่ไม่รู้ว่าต้องไปแก้ที่ไหน
ข้อความบอกอะไรได้“กรุณาระบุที่อยู่ เช่น http://...”“เชื่อมต่อไม่ได้” — ซึ่งไม่ได้บอกว่าพิมพ์ผิด

แถวสุดท้ายสำคัญที่สุด — ที่อยู่ที่พิมพ์ผิดกับเน็ตหลุด ให้อาการเหมือนกันตอนยิงคำขอ ผู้ใช้จะไปตามช่างเรื่อง Wi-Fi ทั้งที่ปัญหาคือพิมพ์ htp://

แต่การตรวจตอนบันทึกก็ยังไม่พอ — มันตรวจได้แค่ว่ารูปแบบถูก ไม่ได้ตรวจว่าที่อยู่นั้นมีเซิร์ฟเวอร์อยู่จริง

ตรวจรูปแบบตอนบันทึก      → รู้ว่าพิมพ์ถูกรูปแบบไหม
ยิงทดสอบตอนกดปุ่มทดสอบ  → รู้ว่าที่อยู่นั้นมีเซิร์ฟเวอร์จริงไหม

สองอย่างนี้ตอบคนละคำถาม และหน้าตั้งค่าที่ดีควรมีทั้งคู่ — ซึ่งเป็นสิ่งที่ 7.16 จะทำ

10. สรุปท้ายบท

  • URL เป็นโครงสร้าง ไม่ใช่ข้อความที่ต่อกันได้
  • ประกอบด้วย Uri เพื่อให้จัดการขีดทับและ encoding ให้
  • resolve ทิ้ง path เดิมเมื่อ path ขึ้นต้นด้วยขีดทับ
  • ตกลงครั้งเดียวว่า base URL รวม /api หรือไม่
  • อย่ายัด /api ไว้ใน base URL เพราะบาง endpoint ไม่ได้อยู่ใต้นั้น
  • ตรวจและทำที่อยู่ให้เป็นมาตรฐานตอนบันทึก ไม่ใช่ตอนใช้
  • ค่าที่ไปอยู่ใน path ต้อง encodeComponent เสมอ
  • ตรวจรูปแบบกับทดสอบการเชื่อมต่อ ตอบคนละคำถาม
