1. ปัญหาที่บทนี้แก้

เซิร์ฟเวอร์ตอบมาว่าไม่สำเร็จ แล้วแอปควรทำอะไร

// คำตอบที่ทุกคนเขียนครั้งแรก
showError('ไม่สำเร็จ');

แต่ “ไม่สำเร็จ” มีหลายแบบที่ผู้ใช้ต้องทำต่างกันสิ้นเชิง

เซิร์ฟเวอร์บอกว่าผู้ใช้ต้องทำลองใหม่ช่วยไหม
ยังไม่ได้เข้าสู่ระบบเข้าสู่ระบบใหม่ไม่
ไม่มีสิทธิ์ทำสิ่งนี้ติดต่อหัวหน้าไม่
คนอื่นทำไปก่อนแล้วโหลดใหม่แล้วดูอีกทีไม่
จำนวนที่กรอกไม่ถูกต้องแก้จำนวนแล้วส่งใหม่ไม่ ถ้าไม่แก้
เซิร์ฟเวอร์มีปัญหาภายในรอสักครู่แล้วลองใหม่ช่วย

ห้าแถว มีแค่แถวเดียวที่ปุ่ม “ลองใหม่” มีความหมาย — แต่ถ้าแสดงเหมือนกันหมด ผู้ใช้จะกดลองใหม่กับทุกแถว

รหัสแปลว่า

500–599เซิร์ฟเวอร์มีปัญหา

3. Mental model: รหัสบอกกลุ่ม เนื้อหาบอกรายละเอียด

รหัส 409     →  "ขัดแย้ง" — บอกได้แค่กลุ่ม
detail       →  "งานนี้ถูกปิดโดยผู้ใช้อื่นแล้ว" — บอกว่าขัดแย้งเรื่องอะไร
ประโยคเดียวที่ต้องจำ: รหัสใช้ตัดสินว่า แอปควรทำอะไร ส่วนเนื้อหาใช้บอกผู้ใช้ว่า เกิดอะไรขึ้น — และห้ามสลับหน้าที่กัน

4. แปลงรหัสเป็นชนิดที่เดียว

เปิด lib/core/api_failure.dart

/// แปลงรหัสตอบกลับเป็นชนิดความล้มเหลว
///
/// รวมไว้ที่เดียวเพราะกฎนี้ต้องเหมือนกันทุก endpoint
ApiFailureKind failureKindForStatus(int statusCode) => switch (statusCode) {
  401 => ApiFailureKind.unauthorized,
  403 => ApiFailureKind.forbidden,
  404 => ApiFailureKind.notFound,
  409 => ApiFailureKind.conflict,
  400 || 422 => ApiFailureKind.validation,
  >= 500 => ApiFailureKind.server,
  _ => ApiFailureKind.contract,
};

สามอย่างที่ควรสังเกต

สิ่งที่เห็นเหตุผล
400 || 422 รวมเป็นชนิดเดียวทั้งคู่แปลว่า “ข้อมูลที่ส่งไปใช้ไม่ได้” และแอปทำเหมือนกัน
>= 500 ครอบทุกรหัส 5xx500, 502, 503 ล้วนแปลว่าเซิร์ฟเวอร์มีปัญหา และลองใหม่ได้เหมือนกัน
รหัสที่เหลือเป็น contractรหัสที่ไม่ควรมาถึงตรงนี้ แปลว่าสัญญาไม่ตรงกัน
test('รหัสที่ไม่ควรมาถึงตรงนี้ ถือว่าผิดสัญญา', () {
  expect(failureKindForStatus(418), ApiFailureKind.contract);
});

สังเกตว่าไม่ได้แยก 401 กับ 403 ตามที่คนมักคิดว่า “คล้ายกัน” — เพราะ 7.5 แสดงแล้วว่าสองรหัสนี้ต้องทำคนละอย่างสิ้นเชิง

5. อ่านเนื้อหาแบบไม่คาดหวังมากเกินไป

เนื้อหาที่มากับความล้มเหลวมีได้หลายรูปแบบ

รูปแบบเจอเมื่อ
ProblemDetailsASP.NET รุ่นใหม่ที่ตั้งค่าไว้
{"message": "..."}ระบบเก่าที่กำหนดรูปแบบเอง
ข้อความล้วนตัวกลางในเครือข่าย
HTMLหน้าเข้าสู่ระบบขององค์กร
ว่างเปล่าบาง endpoint ที่ไม่ได้ใส่รายละเอียด

lab จึงลองอ่านแบบดีที่สุดเท่าที่ทำได้ แล้วมีทางสำรองเสมอ

final problem = ProblemDetails.tryParse(json);
throw ApiException(
  // ข้อความสำรองเมื่อ server ไม่ได้บอกอะไรที่อ่านรู้เรื่อง
  problem?.userMessage ??
      json?['message']?.toString() ??
      'HTTP ${response.statusCode}',
  statusCode: response.statusCode,
  kind: failureKindForStatus(response.statusCode),
  problem: problem,
);

สังเกตว่า tryParse คืน null แทนที่จะโยน ตามที่เขียนไว้ใน 6.9

/// คืน null เมื่อไม่ใช่ — ไม่โยน เพราะบาง endpoint ตอบรูปแบบอื่น
/// และนั่นไม่ใช่ความผิดพลาดที่ต้องหยุดทุกอย่าง

เพราะการที่เนื้อหาไม่ตรงรูปแบบที่หวัง ไม่ควรทำให้ข้อมูลที่มีอยู่แล้ว (คือรหัสตอบกลับ) ใช้ไม่ได้ไปด้วย

6. ห้ามใช้ข้อความเป็นเงื่อนไข

นี่คือข้อผิดพลาดที่ดูไม่มีพิษภัยแต่สร้างปัญหายาว

// อันตราย
if (error.message.contains('already completed')) {
  showAsSuccess();
}
ปัญหาเกิดเมื่อ
ข้อความเปลี่ยนทีมหลังบ้านแก้คำให้อ่านง่ายขึ้น
ข้อความถูกแปลเซิร์ฟเวอร์รองรับหลายภาษา
ข้อความคล้ายกันแต่คนละเรื่อง“already completed” กับ “already cancelled”

สิ่งที่ควรขอจากฝั่งหลังบ้านคือ รหัสที่ไม่เปลี่ยน

{
  "title": "Conflict",
  "status": 409,
  "detail": "งานนี้ถูกปิดโดยผู้ใช้อื่นแล้ว",
  "errorCode": "TASK_ALREADY_COMPLETED"
}
// ตัดสินใจจากรหัส แสดงผลจากข้อความ
switch (error.problem?.errorCode) {
  case 'TASK_ALREADY_COMPLETED':
    await store.reload();              // ไม่ใช่ความผิดพลาด — แค่ช้าไป
  case 'TASK_LOCKED_BY_OTHER':
    showResultBanner(messenger, error.userMessage);
  case _:
    showResultBanner(messenger, error.userMessage, isError: true);
}
กฎง่าย ๆ — ถ้าโค้ดอ่านข้อความเพื่อตัดสินใจ แปลว่ากำลังพึ่งสิ่งที่ไม่มีใครรับประกันว่าจะไม่เปลี่ยน

7. รหัสเดียวกันอาจมาจากคนละสาเหตุ

404 เป็นตัวอย่างที่ชัดที่สุด

สาเหตุควรทำ
งาน T-001 ถูกลบไปแล้วบอกผู้ใช้ว่างานหายไป แล้วโหลดรายการใหม่
เส้นทางพิมพ์ผิดเป็นบั๊กของเรา ต้องแจ้งทีม
เซิร์ฟเวอร์ยังไม่ได้ติดตั้งรุ่นที่มี endpoint นี้บอกให้อัปเดตเซิร์ฟเวอร์

สามอย่างนี้ให้รหัสเดียวกันแต่ต้องทำคนละอย่าง และแยกไม่ได้จากรหัสอย่างเดียว

สิ่งที่ช่วยแยกได้

สัญญาณบอกอะไร
มี ProblemDetails มาด้วยเซิร์ฟเวอร์รู้จัก endpoint นี้ — น่าจะเป็นสาเหตุแรก
ได้ HTML หรือเนื้อหาว่างอาจไปไม่ถึง endpoint เลย — น่าจะเป็นสาเหตุที่สองหรือสาม
เกิดกับทุก endpointที่อยู่พื้นฐานผิด (7.2)
เกิดกับ endpoint เดียวเส้นทางนั้นผิด หรือเซิร์ฟเวอร์รุ่นเก่า

สองแถวล่างเป็นข้อมูลที่ได้จากการดูภาพรวม ไม่ใช่จากคำขอครั้งเดียว — ซึ่งเป็นเหตุผลที่ต้องบันทึกไว้ตาม 7.17

8. ให้ชั้นบนเป็นคนตัดสินว่าจะทำอะไร

ApiClient รู้แค่ว่าเกิดความล้มเหลวชนิดไหน แต่ไม่ควรตัดสินว่าจะพาผู้ใช้ไปไหน

// ผิด — ชั้นล่างสุดตัดสินใจเรื่องเส้นทาง
if (response.statusCode == 401) {
  Navigator.of(context).pushAndRemoveUntil(...);   // ApiClient ไม่ควรรู้จัก Navigator
}
ชั้นรับผิดชอบ
ApiClientแปลงรหัสเป็นชนิด
repositoryแปลงเป็นความล้มเหลวที่มีความหมายทางธุรกิจ ถ้าจำเป็น
storeตัดสินว่าสถานะควรเป็นอะไร
หน้าจอตัดสินว่าจะแสดงอะไรและพาไปไหน

เป็นหลักเดียวกับ 5.4 — ชั้นที่รู้เรื่องเส้นทางน้อยที่สุด ควรตัดสินใจเรื่องเส้นทางน้อยที่สุด

และการที่ ApiClient ไม่รู้จัก BuildContext ทำให้ทดสอบได้โดยไม่ต้องมีหน้าจอ ตาม 7.6

9. เก็บหลักฐานไว้ตามหา

/// รหัสที่ใช้ตามหาคำขอนี้ใน log ฝั่งเซิร์ฟเวอร์
final String? traceId;

เมื่อเกิดข้อผิดพลาด สิ่งที่ควรเก็บ

เก็บใช้ทำอะไร
รหัสตอบกลับรู้ว่าเป็นความล้มเหลวกลุ่มไหน
traceIdตามหาคำขอนี้ใน log ฝั่งเซิร์ฟเวอร์
endpointรู้ว่าเกิดที่ไหน
เวลาที่ใช้แยก “ปฏิเสธทันที” ออกจาก “ทำนานแล้วล้มเหลว”

และสิ่งที่ห้ามเก็บคือเนื้อหาทั้งก้อน ตามที่ 6.8 และ 7.17 บอกไว้ — เพราะ body ของงานคลังมีทั้งชื่อลูกค้าและราคา

การแสดง traceId บนหน้าจอเมื่อเกิดข้อผิดพลาด ทำให้คนหน้างานอ่านให้ทีมฟังได้ทันที แทนที่ทีมจะต้องเดาว่าเกิดตอนไหน

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ผู้ใช้กดลองใหม่กับทุกอย่างแสดงข้อความเดียวกันหมดแยกชนิดแล้วแสดงต่างกัน
ถูกเด้งออกจากระบบเมื่อไม่มีสิทธิ์เหมารวม 403 เป็น 401แยกสองรหัส
โค้ดพังหลังหลังบ้านแก้คำในข้อความใช้ข้อความเป็นเงื่อนไขขอรหัสที่ไม่เปลี่ยน
เนื้อหาผิดรูปแบบแล้วไม่ได้อะไรเลยบังคับให้เนื้อหาต้องตรงรูปแบบมีทางสำรองจากรหัสเสมอ
404 แล้วไม่รู้ว่าเป็นบั๊กหรือข้อมูลหายดูรหัสอย่างเดียวดูสัญญาณประกอบ
ApiClient ต้องรู้จักหน้าจอตัดสินใจเรื่องเส้นทางที่ชั้นล่างย้ายไปชั้นบน
ตามหาใน log ฝั่งเซิร์ฟเวอร์ไม่เจอไม่ได้เก็บ traceIdเก็บและแสดงให้ผู้ใช้เห็น

11. แบบฝึกหัด

ผู้ใช้กดปิดงาน แล้วได้คำตอบนี้

HTTP 409
{
  "type": "https://httpstatuses.io/409",
  "title": "Conflict",
  "status": 409,
  "detail": "งานนี้ถูกปิดโดยผู้ใช้อื่นแล้ว เมื่อ 14:32",
  "traceId": "00-4bf92f-a3ce929d-01"
}
  1. ระบุว่าแอปควรทำอะไรกับคำตอบนี้ และห้ามทำอะไร
  2. เขียนสิ่งที่ผู้ใช้ควรเห็นบนหน้าจอ
  3. ตอบว่าถ้าเซิร์ฟเวอร์ตอบ 409 เหมือนกันแต่ detail ว่า “งานนี้ถูกล็อกโดยผู้ใช้อื่นอยู่” จะต่างกันอย่างไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ควรทำอะไร

ต้องทำเพราะ
ย้อนการเปลี่ยนแปลงบนจอกลับเราติ๊กว่าเสร็จไว้ล่วงหน้าตาม 4.13 — แต่คนอื่นเป็นคนปิด
โหลดรายการใหม่ข้อมูลบนจอเก่าไปแล้ว อาจมีงานอื่นเปลี่ยนด้วย
แสดง detail ที่เซิร์ฟเวอร์ส่งมามันบอกเรื่องที่เราไม่รู้ — ว่าใครทำและเมื่อไหร่
เก็บ traceId ไว้เผื่อต้องตามหาทีหลัง
ห้ามทำเพราะ
ลองใหม่อัตโนมัติconflict.isRetryable เป็น false — ยิงไปกี่ครั้งก็ได้ 409 เหมือนเดิม
แสดงปุ่ม “ลองใหม่”เหตุผลเดียวกัน — เป็นการหลอกให้ผู้ใช้เสียเวลา
พาไปหน้าเข้าสู่ระบบไม่เกี่ยวกับสิทธิ์เลย
แสดงว่า “เกิดข้อผิดพลาด”ไม่มีอะไรผิดพลาด — งานถูกปิดเรียบร้อยแล้ว แค่ไม่ใช่เราที่ปิด

แถวสุดท้ายคือประเด็นสำคัญ — 409 นี้เป็น ข้อมูลใหม่ ไม่ใช่ความล้มเหลว ซึ่งเป็นข้อสรุปเดียวกับ 6.12 แบบฝึกหัดข้อ 3

ข้อ 2 — สิ่งที่ผู้ใช้ควรเห็น

┌────────────────────────────────────────┐
│ ✓ T-001  PAL-0101                      │
│   งานนี้ถูกปิดโดยผู้ใช้อื่นแล้ว เมื่อ 14:32  │
│                                        │
│ (รายการอัปเดตแล้ว)                       │
└────────────────────────────────────────┘
สิ่งที่ควรมีสิ่งที่ไม่ควรมี
ข้อความจากเซิร์ฟเวอร์ตรง ๆคำว่า “ผิดพลาด” หรือสีแดง
รายการที่อัปเดตแล้วปุ่มลองใหม่
เครื่องหมายว่างานนั้นเสร็จแล้วการย้อนกลับเงียบ ๆ โดยไม่บอกเหตุผล

เพราะผลลัพธ์สุดท้ายคือ “งานเสร็จแล้ว” ซึ่งเป็นสิ่งที่ผู้ใช้ต้องการอยู่แล้ว — แค่ไม่ได้เกิดจากการกดของเขา

ส่วน traceId ไม่ต้องแสดงในกรณีนี้ เพราะไม่มีอะไรผิดปกติให้ตามหา — เก็บไว้ใน log ก็พอ

ข้อ 3 — ถ้า detail เปลี่ยนเป็น “ถูกล็อกอยู่”

รหัสเหมือนกัน แต่ ความหมายทางธุรกิจต่างกันสิ้นเชิง

“ถูกปิดแล้ว”“ถูกล็อกอยู่”
งานจบหรือยังจบแล้วยังไม่จบ
ผู้ใช้ทำอะไรได้ไปทำงานถัดไปรอ แล้วลองใหม่ทีหลัง
ปุ่มลองใหม่มีความหมายไหมไม่มี — เมื่ออีกคนปล่อยล็อกแล้ว
ควรแสดงเป็นอะไรข้อมูลสิ่งที่ต้องรอ

และนี่คือเหตุผลว่าทำไมรหัสอย่างเดียวไม่พอ

ถ้าตัดสินจากรหัส 409 อย่างเดียว ทั้งสองกรณีจะได้การปฏิบัติเหมือนกัน ซึ่งผิดในกรณีหลัง — ผู้ใช้จะคิดว่างานเสร็จแล้วและเดินจากไป ทั้งที่ยังไม่มีใครทำ

แต่ก็ห้ามอ่าน detail เพื่อตัดสินใจ ตามหัวข้อ 6

// ห้าม — ข้อความเปลี่ยนได้
if (detail.contains('ถูกปิด')) { ... }

ทางที่ถูกคือขอให้ฝั่งหลังบ้านส่งรหัสที่ไม่เปลี่ยนมาด้วย

{
  "status": 409,
  "detail": "งานนี้ถูกล็อกโดยผู้ใช้อื่นอยู่",
  "errorCode": "TASK_LOCKED_BY_OTHER"
}
switch (error.problem?.errorCode) {
  case 'TASK_ALREADY_COMPLETED':
    await store.reload();
    showResultBanner(messenger, error.userMessage);      // ไม่ใช่ error
  case 'TASK_LOCKED_BY_OTHER':
    showRetryableBanner(messenger, error.userMessage);   // มีปุ่มลองใหม่
  case _:
    showResultBanner(messenger, error.userMessage, isError: true);
}

บทเรียนที่ควรจำ: รหัสตอบกลับบอกได้แค่ว่าเป็นความล้มเหลว กลุ่ม ไหน — เมื่อกลุ่มเดียวกันต้องทำต่างกัน ต้องขอรหัสที่ละเอียดกว่าจากฝั่งหลังบ้าน ไม่ใช่ไปอ่านข้อความเอา

12. สรุปท้ายบท

  • รหัสใช้ตัดสินว่าแอปทำอะไร เนื้อหาใช้บอกผู้ใช้ว่าเกิดอะไร
  • แปลงรหัสเป็นชนิดที่เดียว เพื่อให้กฎเหมือนกันทุก endpoint
  • รวมรหัสที่แอปทำเหมือนกันไว้เป็นชนิดเดียว
  • อ่านเนื้อหาแบบดีที่สุดเท่าที่ทำได้ และมีทางสำรองจากรหัสเสมอ
  • ห้ามใช้ข้อความเป็นเงื่อนไข — ขอรหัสที่ไม่เปลี่ยนแทน
  • รหัสเดียวกันอาจมาจากคนละสาเหตุ ต้องดูสัญญาณประกอบ
  • ชั้นบนเป็นคนตัดสินว่าจะพาผู้ใช้ไปไหน
  • ความล้มเหลวบางอย่างไม่ใช่ความผิดพลาด แต่เป็นข้อมูลใหม่
