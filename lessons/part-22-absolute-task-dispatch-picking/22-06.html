1. ทำไม AGV putaway ต้องสแกนสองค่า

palletยืนยันสิ่งของที่จะย้าย ส่วน robot pointยืนยันจุดรับจริง หากเชื่อเพียง task card ผู้ใช้อาจยืนผิดจุดหรือรถรับ palletผิดตัว จึงต้องผ่านทั้ง exact pallet matchและ backend point validationก่อนเปิดปุ่ม Send

2. Exact pallet match

dialog normalizeช่องว่าง/caseแล้วเทียบกับ palletของ task ไม่ใช้ contains เพราะ barcodeที่คล้ายกันห้ามผ่าน เมื่อ palletยังไม่ถูก ช่อง pointและการส่งงานยังถูกปิด เป็น progressive validationที่ลด requestไม่จำเป็น

3. Point validation เป็น server authority

scan point → uppercase
→ POST mobile_validate_robot_point
→ valid: เก็บ canonical point
→ invalid/error: แสดงข้อความและห้าม dispatch

clientไม่เดารูปแบบ pointจาก regex เพราะ availabilityและmappingเป็นข้อมูล operationalของ backend

4. Non-dismissible dialog

ระหว่าง flowสำคัญ dialogไม่ให้แตะพื้นหลังแล้วหายโดยบังเอิญ ผู้ใช้ยกเลิกด้วย actionชัดเจนได้ และ controllerถูก disposeตาม lifecycle ช่วยไม่ทิ้ง input stateหรือ listenerเมื่อเปิดซ้ำ

5. Async mounted guard

validationรอ network ขณะที่ผู้ใช้อาจปิด dialog callbackจึงต้องตรวจ mountedก่อน setState/show error นี่เป็นกฎทั่วไปของ StatefulWidget: หลัง await ทุกครั้ง ให้พิสูจน์ว่า context/stateยังมีชีวิต

6. TOCTOU ยังมีอยู่

pointอาจ validตอนตรวจแต่ถูกใช้งานก่อน dispatchจริง Backend dispatchจึงต้อง validateซ้ำแบบ atomicกับการจองงาน ไม่ถือว่า validation endpointเป็น authorizationหรือ reservation

7. Error UX ที่ควรแยก

“ไม่พบ point”, “pointไม่พร้อม”, network timeout และ unauthorizedควรมีข้อความ/การ retryต่างกัน ปัจจุบัน boolean/resultง่ายต่อ UIแต่สูญเสียเหตุผล Senior designควรคืน typed failureพร้อม codeที่แปลข้อความได้

8. Test contract

widget testยืนยันว่าพิมพ์ palletผิดยังเปิด pointไม่ได้, invalid pointไม่ dispatch, valid scanถูก normalizeแล้ว dispatchหนึ่งครั้ง ควรเพิ่ม close-during-request, timeout, double scanและ pointเปลี่ยนสถานะก่อน dispatch
