ไฟล์หลัก: _putawayAtScan, _returnAtScan และ _completeTask — taskที่หน้าตาคล้ายกันใช้ completion authorityคนละแบบ

1. Received putaway

เมื่อสแกน locationขั้นสุดท้าย storeเรียก mobile_putaway(pallet, location) Backendยืนยัน container/locationแล้วจึงอัปเดต task, refresh historyและไป done หาก failยังค้างที่ scanlocเพื่อแก้และ retry

2. Returning relocate

returningเป็น RELOCATEที่กลับ rack จึงใช้ mobile_complete_move(taskId, robot, destination) ไม่ใช่ mobile_putaway แม้ labelหน้า UIเรียก Putaway หลังสำเร็จนำ locationออกจาก free listเพื่อไม่ให้เลือกซ้ำใน session

3. Retrieve completion

retrieveสแกน destinationแล้วไป done จากนั้น _completeTaskตั้ง completedแบบ optimisticและยิง completeMoveแบบ unawaited ทำให้ UIตอบสนองเร็วแต่ความล้มเหลวเกิดภายหลังและต้อง reconcileอย่างระวัง

4. ความไม่สมมาตรที่ต้องจำ

FlowEndpointรอผลก่อน done
Received putawaymobile_putawayใช่
Returningmobile_complete_moveใช่
Retrievemobile_complete_moveไม่—optimistic

5. Unawaited failure edge

retrieve failureคืน statusเป็น inProgressแต่ stepยังอยู่ done ผู้ใช้อาจไม่มี scan actionให้ retry เป็นช่องว่างสำคัญ ควร awaitก่อนจบ, หรือ rollbackทั้ง status+step, หรือสร้าง explicit retry completion state

6. Free-location race

locationที่ freeตอนโหลดอาจถูกอุปกรณ์อื่นจับจองก่อน scan Backendต้องเป็นผู้ตัดสินและคืน conflict หากชนกัน Clientควร reload free locationsและรักษาค่าที่สแกนไว้ให้ผู้ใช้เข้าใจว่าเหตุใดถูกปฏิเสธ

7. Idempotent completion

timeoutหลัง backend commitทำให้ retryได้ Endpointควรตอบผลเดิมเมื่อ taskเดียวกันเสร็จที่ destinationเดียวกัน และ rejectอย่างชัดเจนเมื่อ destinationขัดกัน การพึ่งปุ่ม disabledอย่างเดียวไม่พอสำหรับ distributed system

8. Completion test matrix

ครอบคลุม success, validation conflict, timeout-after-commit, retry, duplicate tap, taskถูกปิดจากเครื่องอื่น, history refresh failure และ retrieve unawaited rollback โดย assertทั้ง server call, status, stepและสิ่งที่ผู้ใช้ทำต่อได้
