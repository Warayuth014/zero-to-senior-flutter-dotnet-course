ไฟล์หลัก: dispatchStoreIn, mobile_store_in และ C3 dispatched UI — ส่ง staged palletเข้า ASRS/ESS

1. Store In command

จาก C3 STAGED ผู้ใช้กด Store In แล้ว storeเรียก backendด้วย palletและ robot ปัจจุบัน hard-code Local-AGV Responseคืน taskCodeสำหรับ trace และ reloadทั้ง queuesกับ tasks

2. ทำไม reloadสอง projection

queuesต้องเปลี่ยน C3เป็น DISPATCHED ขณะที่ tasksอาจมี transport taskใหม่ ทั้งสองคือ projectionคนละมุมของ transactionเดียว หากโหลดสำเร็จเพียงอันเดียว UIต้องยอมรับ temporary inconsistencyและ retryอีกฝั่ง

3. ESS เป็น completion authority

หลัง dispatch UIแสดง waiting ESS ไม่ให้ผู้ใช้กด completeเอง ระบบภายนอกเคลื่อน palletและ callbackเปลี่ยน statusจริง เช่นเดียวกับ AGV task progressที่ต้องอ่านจาก WMS ไม่สร้าง animationแทน domain state

4. Hard-coded robot smell

Local-AGVผูก environment/identityไว้ใน store หากหลาย device/robotควรได้จาก configurationหรือ server assignmentและส่ง stable identifier ไม่ใช้ display nameที่อาจเปลี่ยน

5. Dispatch idempotency

Store In timeoutหลังสร้าง taskอาจสร้างซ้ำ Backendควร enforceหนึ่ง active store-inต่อ staged palletและคืน taskCodeเดิม Clientใช้ taskCodeแสดงผล/ติดตามแทนอนุมานจาก laneเพียงอย่างเดียว

6. Concurrent Remove vs Store In

สอง operatorอาจกดคนละ actionพร้อมกัน Backendต้อง transitionจาก STAGEDแบบ compare-and-set มีผู้ชนะหนึ่งคำสั่ง ส่วนผู้แพ้ได้ conflictพร้อม current stateแล้ว reload

7. Polling และ stale response

timerโหลด queuesทุก 5 วินาทีขณะอยู่ Picking หาก pollเก่าเริ่มก่อน dispatchแต่จบทีหลัง อาจคืน STAGEDมาทับ DISPATCHEDชั่วคราว ควรใช้ request generation/versionหรือ cancel stale fetch

8. Store-In tests

ทดสอบ staged→dispatched, taskCode, hard-coded/configured robot, remove race, duplicate/timeout, queues successแต่ tasks fail, ESS callbackและ out-of-order poll เพื่อรับรองว่า UIไม่สร้าง taskซ้ำ
