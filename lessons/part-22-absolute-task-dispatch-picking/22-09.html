1. Withdraw ไม่ได้ย้ายของทันที

ผู้ใช้เลือก pallet, จำนวนและ destination แล้ว backendสร้างงาน RELOCATE/PENDING ผลลัพธ์คือ queue countใหม่ ส่วน physical stockยังอยู่ที่เดิมจน taskถูก dispatchและ complete

2. Candidate filter

pickerแสดงเฉพาะ palletสถานะ STOREDและ quantityมากกว่า 0 เพื่อไม่เสนอ receiving/staged stock การสแกน exact codeใช้ผลเดียวได้ทันที ส่วนหลายผลยังให้ผู้ใช้เลือกเพื่อเลี่ยง ambiguity

3. Quantity invariant

1 ≤ requested quantity ≤ pallet on-hand

เลือก palletแล้วค่าเริ่มต้นเป็นเต็มจำนวน QtyStepper clampช่วงให้ แต่ backendยังต้องตรวจ stockปัจจุบันเพราะ on-handอาจเปลี่ยนหลัง snapshot

4. Destination selection

destinationมาจาก fixed operational definitions การเปลี่ยน destinationเคลียร์ conveyor/active picking selectionใน store ป้องกัน contextของ laneเก่าค้างมาปนกับ withdrawใหม่

5. Submit transaction

pickingSubmittingกันการกดซ้ำ เรียก withdraw, reload destination queues, เคลียร์ pallet/qtyแล้วนำไปหน้า dispatch ลำดับนี้ทำให้ผู้ใช้เห็น taskที่เพิ่งสร้างและเลือก carrierต่อได้

6. Global busy coupling

withdrawแชร์ booleanกับ picking/store-in actions ทำให้ operationคนละชนิด blockกันโดยไม่บอก task ID โครงสร้างที่โตควรใช้ command stateแยก เช่น AsyncAction<WithdrawKey> เพื่อแสดง loading/errorเฉพาะ card

7. Timeout และ duplicate request

หาก responseหายหลังสร้าง relocation clientอาจส่งซ้ำและได้สองงาน APIควรรับ idempotency keyหรือ enforceหนึ่ง open relocationต่อ pallet+destination+quantity พร้อมให้ client reload queueก่อน retry

8. Layout และ behavior tests

withdraw layout testยืนยัน scannerคงที่ขณะที่ list scrollและ selected flowพอดีจอ ควรเพิ่ม stale stock, invalid quantity, no destination, timeout/duplicate, queue refresh failureและ navigationหลัง success
