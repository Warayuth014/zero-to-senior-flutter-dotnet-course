ไฟล์หลัก: WarehouseStore.dispatchTask และ DispatchView — AGVกับ Forklift share pending task แต่ completion authorityต่างกัน

1. Dispatch queue

DispatchViewแบ่ง pendingDispatch เป็นงานรอมอบหมายและ dispatched/inProgress/executingเป็นงานกำลังทำ Cardแสดง task type, pallet/product/route และสอง actions Automatic AGV/Forklift ส่วน statusจริงหลังมอบหมายมาจาก server polling

2. Guard identity ก่อน command

storeปฏิเสธ taskที่ไม่มี server IDเพราะ event display IDไม่ใช่ keyสำหรับ mutation สำหรับ AGV putawayยังต้องมี scanned palletและ source pointก่อนส่ง ส่วน retrieve/return dispatch AGVได้โดยใช้ routeที่ taskมีอยู่

3. Forklift branch

dispatch(mode=FORKLIFT, robot=username)
→ backend persists HANDLE
→ local status=dispatched, step=0
→ putaway/return target=Any Available Location
→ task appears in My Tasks

physical completionเกิดภายหลังจาก guided scansบน PDA

4. AGV branch

optimistic executing / serverStatus=AGV
→ dispatch(mode=AGV, pallet/source pointถ้าจำเป็น)
→ backend/ESS assigns rack/robot
→ reload tasks
→ ESS TaskStatusCallBack เป็นผู้ปิดงานจริง

PDAไม่สร้าง progressเปอร์เซ็นต์ปลอมและไม่เรียก completeMoveแทน ESS

5. Failure rollback

AGV failureคืน statusเป็น pendingและ serverStatus PENDING; manual failureคง pending แต่ codeตั้ง t.mode ก่อน requestและไม่ได้ revertทั้งสอง branch ทำให้ badge/filterที่ดู modeอาจเห็น assignmentชั่วคราวผิดจน reload Senior fixควร commit modeหลัง successหรือ snapshot/rollbackทุก optimistic field

6. Busy state coupling

dispatchใช้ recvSubmitting ซึ่งชื่อมาจาก Receivingและถูกใช้ใน pick confirmationด้วย ทำให้ actionคนละ feature blockกันแบบซ่อน coupling ควรแยก operation stateต่อ command/task ID ไม่ใช้ global booleanก้อนเดียวใน God Store

7. Retry/idempotency

double tapถูกกันใน process แต่ timeoutหลัง backend persist HANDLE/AGVอาจทำให้ client rollbackแล้วส่งซ้ำ Endpointต้องตรวจ task current statusและ idempotentlyคืน assignmentเดิมหรือ conflictที่ใช้ reload reconcileได้

8. Dispatch tests

ทดสอบ missing ID, manual success/fail/timeout, AGVทุก task type, required scans, duplicate tap, optimistic fields/rollbackและ external ESS status change ระหว่าง request ยืนยันว่า server snapshotล่าสุดชนะและไม่มี taskถูก assignสอง carrier
