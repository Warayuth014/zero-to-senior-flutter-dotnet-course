ไฟล์หลัก: TaskRunView, WarehouseStore.openTask และ taskScan — manual task เป็น state machine ที่ขับด้วย metadata

1. รับงานก่อนเริ่มวิ่ง step

taskที่ HANDLE/dispatched เมื่อเปิดจะเปลี่ยนเป็น inProgressและเริ่ม step 0 ส่วน taskที่ทำค้างเก็บ stepเดิมไว้ การเข้า detailจึงไม่ควร resetงานทุกครั้ง และ navigation stateต้องถือ active taskให้กลับมาทำต่อได้

2. View render จาก runSteps

TaskRunViewเลือก runSteps[task.type] แล้วแสดง FlowStepsกับ panelตาม key ทำให้ putaway/retrieve/returningใช้ shellเดียวกัน แต่แต่ละ flowมีจำนวนและชนิด inputต่างกัน

3. Expected barcode

StepDef.expect
→ task.barcodeFor(expect)
→ normalize(trim + uppercase)
→ compare exact
→ success: step++
→ mismatch: error, stepเดิม

destinationใช้ scanned codeบันทึกไว้ใน taskเพื่อส่ง completeMoveภายหลัง

4. Instruction step ไม่ใช่ scan step

detail, suggestและdeliverเป็นคำแนะนำ/confirmation จึงใช้ปุ่ม Next ขณะที่ scanpallet, scanlocและscandestต้องรับหลักฐานหน้างาน อย่าทำ Nextข้าม scanเพื่อความสะดวก เพราะจะทำลาย traceability

5. Location picker เป็นตัวช่วย ไม่ใช่ bypass

putawayโหลด free locationsมาให้ค้นและแตะเติมช่องได้ แต่ยังเข้าทาง confirmเดียวกับการสแกน รายการ scrollแยกจาก scannerเพื่อรักษาปุ่ม/ช่อง inputให้เห็นบน PDAจอเล็ก

6. Back และ bottom navigation

ออกจากหน้า runไม่ควรลบ runtime step งาน manualต้องกลับมา resumeได้ Flow navigation testตรวจทั้ง pause/resume, backและ bottom navigation เพื่อกัน regressionที่เปลี่ยน tabแล้ว active taskหาย

7. Runtime state ไม่ใช่ durable state

stepและ scanned destinationอยู่ใน memoryและถูก preserveตอน reload แต่ปิดแอป/refresh browserแล้วยังหาย ถ้าธุรกิจต้อง resumeข้าม session ควร persist checkpointฝั่ง serverหรือ local storeที่ผูก user+task version พร้อมตรวจ task statusใหม่

8. State-machine tests

ทดสอบทุก transition, barcodeผิด, scanซ้ำ, free-location stale, navigation resume, reloadระหว่าง stepและ taskถูก cancelจากอุปกรณ์อื่น ห้าม assertเพียงหน้าจอสุดท้ายเพราะ bugมักเกิดที่ transitionกลางทาง
