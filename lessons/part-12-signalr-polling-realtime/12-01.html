Polling กับ pushแก้คนละข้อจำกัด: pollingเรียบง่ายและคืน snapshot authoritative; SignalRลด latency/requestsแต่ eventอาจขาด ซ้ำ หรือมาผิดลำดับ จึงมักใช้ pushเป็น invalidationแล้ว HTTP reconcile

1. Polling

clientเรียก APIทุก interval ข้อดี debugง่าย, ใช้ HTTP contractเดิม, recoverจาก eventที่พลาด ข้อเสีย latencyสูงสุดเท่า interval, battery/network costและโหลด serverแม้ข้อมูลไม่เปลี่ยน

2. Push realtime

serverส่ง eventผ่าน persistent connectionเมื่อข้อมูลเปลี่ยน ข้อดีตอบสนองเร็วและลด empty polls แต่ต้องดู connection lifecycle, reconnect, ordering, duplicatesและ authorization

3. Cost model

poll requests/minute = devices × 60 / intervalSeconds
500 devices ที่ 5s = 6,000 requests/minute

ปรับ intervalตามความสดที่ธุรกิจต้องการ ไม่ใช้ 1 วินาทีเพราะ “ดู realtime”

4. Hybrid pattern

โหลด snapshotด้วย HTTPตอนเข้า → SignalR eventบอก entity/versionที่เปลี่ยน → patchอย่างปลอดภัยหรือ debounce refresh → periodic slow reconciliationเป็น safety net

5. Source of truth

eventเป็น notification/factที่เกิดแล้ว ไม่จำเป็นต้องมี stateเต็ม Server snapshot/versionเป็น authorityเมื่อ reconnectหรือสงสัย divergence

6. ของจริง

wmsapp ใช้ SignalRกับ Putaway/Sorting ขณะที่ WarehouseStore อีกแอปมี Timer 5 วินาทีโหลดเฉพาะข้อมูลของ screenปัจจุบัน

7. แบบฝึกหัด

สถานะ taskต้องเปลี่ยนภายใน 2 วินาทีแต่ networkหลุดเป็นช่วง ควรเลือกอะไร?

แนวคำตอบ

SignalRเพื่อ latency + reconnect snapshot/slow pollingเพื่อความถูกต้อง พร้อมแสดง stale/offline status

8. Decision checklist

freshness SLA, device count, event rate, battery/network, snapshot endpoint, ordering/versionและ behaviorตอน disconnected
