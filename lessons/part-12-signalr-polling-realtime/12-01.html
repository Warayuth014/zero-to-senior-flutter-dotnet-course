1. ปัญหา

ทุกอย่างที่ผ่านมาในคอร์สนี้ ข้อมูลเปลี่ยนเพราะผู้ใช้กดอะไรบางอย่าง — กดโหลดใหม่ กดยืนยัน สแกนบาร์โค้ด

แต่ในคลังจริง สิ่งที่เปลี่ยนส่วนใหญ่ไม่ได้เกิดจากคนที่ถือเครื่องอยู่

เกิดอะไรขึ้นใครทำคนถือ PDA ต้องรู้ไหม
รถ AGV ส่งพาเลทถึงจุดปลายทางแล้วหุ่นยนต์ต้องรู้ทันที
คนอื่นล็อกพาเลทที่เรากำลังจะหยิบเพื่อนร่วมงานต้องรู้ก่อนเดินไป
จุดคัดแยกเต็มสายพานต้องรู้ก่อนส่งของไปเพิ่ม
มีงานใหม่เข้าคิวระบบรู้ช้าหน่อยได้

คำถามของ Part นี้คือ แอปจะรู้ได้อย่างไร และมีสองคำตอบ

2. สองวิธี

ถามซ้ำเป็นระยะ (polling)เรียลไทม์ (SignalR)
ใครเริ่มแอปถามเซิร์ฟเวอร์บอก
ช้าแค่ไหนครึ่งหนึ่งของช่วงเวลาที่ตั้งไว้ โดยเฉลี่ยเกือบทันที
จำนวนคำขอคงที่ ไม่ว่าจะมีอะไรเปลี่ยนหรือไม่เท่ากับจำนวนสิ่งที่เปลี่ยนจริง
ความซับซ้อนตัวจับเวลาหนึ่งตัวการเชื่อมต่อค้าง สถานะ การต่อใหม่ การรั่ว
ทำงานตอนเน็ตกระตุกครั้งที่ล้มเหลวก็แค่รอครั้งหน้าต้องจัดการการหลุดและช่วงที่ขาดหาย
ทดสอบง่ายยาก ต้องจำลองการหลุด
ข้อที่คนมักลืม: เรียลไทม์ไม่ได้แทนที่ HTTP — มันบอกว่า “มีอะไรเปลี่ยน” แต่ตอนเปิดจอครั้งแรกยังต้องถามว่า “ตอนนี้เป็นอย่างไร” อยู่ดี 12.10 จะพูดเรื่องนี้ทั้งบท

3. คิดเป็นตัวเลข

สมมติคลังมี PDA 20 เครื่อง ใช้งาน 8 ชั่วโมงต่อวัน

ช่วงเวลาถามซ้ำคำขอต่อเครื่องต่อวันรวม 20 เครื่องช้าโดยเฉลี่ย
1 วินาที28,800576,0000.5 วินาที
5 วินาที5,760115,2002.5 วินาที
15 วินาที1,92038,4007.5 วินาที
60 วินาที4809,60030 วินาที

สังเกตว่าการทำให้เร็วขึ้นสองเท่า ต้องจ่ายด้วยคำขอสองเท่าเสมอ ส่วนเรียลไทม์ตัดความสัมพันธ์นี้ทิ้ง — เร็วเกือบทันทีโดยที่จำนวนข้อความเท่ากับจำนวนสิ่งที่เปลี่ยนจริง ซึ่งในคลังอาจเป็นแค่ไม่กี่ร้อยครั้งต่อวัน

แต่ต้องนับต้นทุนอีกด้านด้วย

ต้นทุนของเรียลไทม์รายละเอียด
การเชื่อมต่อค้างไว้ตลอดกินแบตกว่าคำขอเป็นครั้ง ๆ เพราะวิทยุไม่ได้พัก
เซิร์ฟเวอร์ต้องถือ 20 การเชื่อมต่อไว้ใช้หน่วยความจำต่อเนื่อง
โค้ดที่ต้องเขียนเพิ่มทั้ง Part นี้คือโค้ดนั้น

4. เกณฑ์ตัดสิน

ใช้เรียลไทม์เมื่อใช้ถามซ้ำเมื่อ
ช้าไปห้าวินาทีแล้วผู้ใช้ทำผิดช้าไปหนึ่งนาทีก็ไม่เป็นไร
สิ่งที่เปลี่ยนเกิดขึ้นน้อยครั้งแต่สำคัญมากข้อมูลเปลี่ยนตลอดเวลาอยู่แล้ว
ผู้ใช้จ้องหน้าจอนั้นรอเปิดดูเป็นครั้งคราว
มีคนหลายคนแก้ข้อมูลชุดเดียวกันข้อมูลของใครของมัน

แถวแรกคือเกณฑ์ที่แม่นที่สุด ลองใช้กับตัวอย่างจริง

ฟีเจอร์ช้าไป 5 วินาทีแล้วเกิดอะไรควรใช้
จุดคัดแยกเต็มส่งของไปเพิ่ม ของตกพื้นเรียลไทม์
พาเลทถูกล็อกโดยคนอื่นเดินไปถึงแล้วพบว่าหายไปเรียลไทม์
จำนวนงานที่เสร็จวันนี้ตัวเลขบนหน้าแรกช้าไปนิดหน่อยถามซ้ำ
รายการงานค้างเห็นงานใหม่ช้าไปหน่อยถามซ้ำก็พอ

5. ของจริง: สองโปรเจกต์เลือกคนละทาง

// wmsapp — เรียลไทม์ สำหรับ putaway และ sorting
_connection!.on('StationDispatched', _onStationDispatched);
_connection!.on('PalletArrived', _onPalletArrived);
_connection!.on('StationFull', _on(_stationFull));
// wms_absolute_mobile — ถามซ้ำทุก 5 วินาที
_taskRefreshTimer = Timer.periodic(
  const Duration(seconds: 5),
  (_) => _refreshTaskStatus(),
);

ทั้งคู่สมเหตุสมผลกับสิ่งที่ตัวเองทำ — wmsapp ดูแลจุดคัดแยกที่เต็มแล้วของตกทันที ส่วน wms_absolute_mobile ดูรายการงานที่ช้าไปห้าวินาทีไม่เป็นไร

และสิ่งที่ wms_absolute_mobile ทำได้ดีคือไม่ได้ถามทุกอย่างทุกครั้ง

void _refreshTaskStatus() {
  if (screen == 'agv' || screen == 'dispatch' || screen == 'tasks') {
    unawaited(loadTasks());
  }
  if (screen == 'agv') unawaited(loadAgvHistory());
  if (screen == 'tasks') unawaited(loadForkliftHistory());
  if (screen == 'picking') unawaited(loadPicks());
}

ตัวจับเวลาเดินตลอด แต่ยิงคำขอเฉพาะข้อมูลของจอที่ผู้ใช้กำลังดูอยู่ ผู้ใช้ที่อยู่หน้าแรกจึงไม่กินเน็ตเลย — เป็นการลดต้นทุนที่ได้ผลมากโดยเขียนเพิ่มไม่กี่บรรทัด

สิ่งที่ยังขาดในโค้ดนั้น: ตัวจับเวลาเดินต่อแม้แอปอยู่พื้นหลัง — PDA ที่ถูกวางไว้บนโต๊ะโดยแอปยังเปิดอยู่ ยังยิงคำขอทุกห้าวินาทีทั้งวัน ทางแก้คือหยุดตอน paused แบบเดียวกับที่ 10.8 ใช้ WidgetsBindingObserver

6. ทำทั้งสองอย่าง

คำตอบที่ใช้จริงมักไม่ใช่เลือกอย่างใดอย่างหนึ่ง แต่เป็น

เรียลไทม์ทำงานอยู่   → ไม่ต้องถามซ้ำเลย
เรียลไทม์หลุด        → ถามซ้ำแทน
เรียลไทม์กลับมา      → หยุดถามซ้ำ + โหลดใหม่หนึ่งครั้งเพื่ออุดช่วงที่ขาด

lab ของ Part นี้ทำแบบนี้ และเทสต์บังคับพฤติกรรมทั้งสามบรรทัดไว้

test('หลุดแล้วเริ่มถามซ้ำ ต่อกลับได้แล้วหยุด', () {
  fakeAsync((async) {
    ...
    expect(store.isPolling, isFalse, reason: 'ต่อได้อยู่ ไม่ต้องถามซ้ำ');

    inner.simulateDrop();
    async.flushMicrotasks();
    expect(store.isPolling, isTrue);
    ...
  });
});

เหตุผลที่ต้องมีทางสำรองคือ เรียลไทม์เป็นสิ่งที่หลุดได้ และมันหลุดเงียบ — ต่างจาก HTTP ที่ล้มเหลวแล้วรู้ทันทีจากคำตอบที่ไม่มา การเชื่อมต่อที่หลุดจะดูเหมือน “ไม่มีอะไรเกิดขึ้น” ซึ่งแยกไม่ออกจาก “ทุกอย่างปกติ”

7. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ทำเรียลไทม์ทั้งแอปทั้งที่ต้องการแค่จอเดียวคิดว่าเรียลไทม์ดีกว่าเสมอตัดสินทีละฟีเจอร์
แบตหมดเร็วถามซ้ำถี่เกินความจำเป็นตั้งช่วงเวลาจากความเสียหายที่เกิดถ้าช้า
ถามซ้ำทั้งที่ผู้ใช้ไม่ได้ดูจอนั้นตัวจับเวลาไม่รู้ว่าใครดูอะไรอยู่ถามเฉพาะของจอปัจจุบัน
ทำเรียลไทม์แล้วเลิกโหลดผ่าน HTTPคิดว่าเหตุการณ์พอยังต้องโหลดตอนเปิดจอและตอนต่อกลับ (12.10)
เรียลไทม์หลุดแล้วหน้าจอค้างข้อมูลเก่าเงียบ ๆไม่มีทางสำรองถามซ้ำเมื่อหลุด (12.11)

8. แบบฝึกหัด

หัวหน้าขอให้หน้าจอ “งานค้างของฉัน” อัปเดตทันทีเมื่อมีงานใหม่ ตอนนี้ใช้ถามซ้ำทุก 5 วินาที

  1. ควรเปลี่ยนเป็นเรียลไทม์ไหม
  2. มีทางอื่นไหม
แนวคำตอบ

1. ต้องถามก่อนว่า “ทันที” ของหัวหน้าคือเท่าไหร่ และช้าไปแล้วเกิดอะไร

ถ้าคำตอบคือควรทำ
“พนักงานยืนรออยู่ไม่มีงานทำ”เรียลไทม์คุ้ม — เวลาที่เสียคือค่าแรง
“อยากให้ดูทันสมัย”ไม่คุ้ม — จ่ายความซับซ้อนทั้ง Part นี้เพื่อความรู้สึก
“ห้าวินาทีมันนานไป”ลองลดเป็นสองวินาทีก่อน วัดผลจริงแล้วค่อยตัดสิน

2. ทางที่มักได้ผลกว่าและถูกกว่า

  • ถามทันทีเมื่อผู้ใช้กลับมาที่จอ — ผู้ใช้ที่เพิ่งปิดงานเสร็จแล้วกลับมาหน้ารายการ จะเห็นของใหม่ทันที ซึ่งเป็นจังหวะที่เขาสนใจจริง (10.8)
  • ถามทันทีหลังผู้ใช้ทำอะไรเสร็จ — ปิดงานแล้วโหลดใหม่เลย ไม่ต้องรอตัวจับเวลา
  • ถามถี่ขึ้นเฉพาะตอนที่จอนั้นเปิดอยู่และหน้าจอติด — เร็วขึ้นโดยไม่เพิ่มต้นทุนตอนที่ไม่มีใครดู

สามข้อนี้รวมกันมักทำให้ผู้ใช้รู้สึกว่า “ทันที” โดยไม่ต้องมีการเชื่อมต่อค้างเลย เพราะความรู้สึกว่าเร็วมาจากการอัปเดตตรงจังหวะที่ผู้ใช้สนใจ ไม่ได้มาจากการอัปเดตบ่อย

ถ้าทำครบสามข้อแล้วยังไม่พอ ค่อยไปเรียลไทม์ — และตอนนั้นจะรู้ชัดว่าจ่ายไปเพื่ออะไร

9. สรุป

  • ถามซ้ำจ่ายคำขอคงที่ เรียลไทม์จ่ายการเชื่อมต่อค้างและความซับซ้อน
  • เกณฑ์ที่แม่นที่สุดคือ “ช้าไปห้าวินาทีแล้วเกิดความเสียหายอะไร”
  • ถามเฉพาะข้อมูลของจอที่ผู้ใช้ดูอยู่ ลดต้นทุนได้มากโดยเขียนไม่กี่บรรทัด
  • เรียลไทม์ไม่แทนที่ HTTP
  • เรียลไทม์หลุดเงียบ จึงต้องมีทางสำรองเสมอ
