Dashboard ไม่ใช่ fetchทุก feature: ใช้ summary projectionเฉพาะหน้า Homeและ deep linkไป feature โดยไม่ duplicate source of truth

1. Information hierarchy

แสดง open receiving, pending/manual tasks, inventory alerts, cycle count phase, completed todayและ connection/session status เฉพาะตัวเลขที่นำไป actionได้ ไม่ยัดข้อมูลทุก endpointลงจอเล็ก

2. Summary contract

GET /api/WMS/mobile_dashboard
→ { receivingOpen, tasksPending, tasksWorking,
    inventoryAlerts, cycleCountPending, completedToday,
    generatedAt }

aggregateฝั่ง serverลด N requestsและให้ countsมาจาก snapshotใกล้กัน

3. Staleness

แสดง last updated, pull refreshและ refreshตอนกลับ foreground/หลัง mutationสำคัญ ไม่ต้อง poll dashboardขณะ userอยู่ featureอื่น Countsเป็น informationalหากไม่ใช่ command precondition

4. Card navigation

แต่ละ cardมี semantic label, permission guardและเปิด featureพร้อม filter/context เช่น pending tasks ไม่ให้ Homeแก้ feature selectionผ่าน public fields

5. Partial failure

ถ้า backend aggregateเดียวล้มแสดง stale snapshot+retry หากยังเรียกหลาย endpointsให้ card failแยกและอย่าสรุป nullเป็น 0 เพราะทำให้ผู้ใช้เชื่อว่าไม่มีงาน

6. Layout

compactใช้ 2-column metricsตามพื้นที่และ action list; wideเพิ่ม detail ไม่ hard-code heightจน text scale overflow Loadingใช้ skeletonที่รักษาขนาดและไม่สลับ card order

7. Tests

repository parse, store refresh/stale, widget loading/error/zero/large counts, permissions, tap navigation, Thai/English/text scaleและ mutationแล้ว summary invalidate

8. Acceptance

ผู้ใช้เปิดแอปแล้วรู้ “มีอะไรต้องทำ” ภายในไม่กี่วินาที, countทุกตัวมีนิยาม/source/time, tapไปยังรายการที่สอดคล้องและ connection failureไม่ถูกแสดงเป็นงานศูนย์
