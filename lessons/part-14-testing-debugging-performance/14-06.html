ทดสอบ Store ผ่าน state ที่สังเกตได้: ให้ fake repository ควบคุม I/O แล้ว assert loading/data/error, notification และ race behavior ไม่เรียก private method หรือพึ่ง widget

1. ตัวอย่าง WarehouseStore

wms_absolute_mobile inject receiving/tasks/inventory/cycle-count repositories เข้า WarehouseStore extends ChangeNotifier ทำให้ flow_navigation_test.dart เปิด line, advance, back และตรวจการล้าง state ได้ใน pure test

2. สังเกต notifications

var notifications = 0;
store.addListener(() => notifications++);
await store.load();
expect(store.loading, isFalse);
expect(store.items, hasLength(2));
expect(notifications, greaterThanOrEqualTo(2));

อย่าล็อกจำนวน exact หาก contract ไม่กำหนด เพราะ batch/refactor อาจลด notification โดย behavior เท่าเดิม

3. Loading transition

final pending = Completer<List<Task>>();
repo.nextFetch = pending.future;
final operation = store.load();
expect(store.loading, isTrue);
pending.complete([task]);
await operation;
expect(store.loading, isFalse);

4. Error และข้อมูลเดิม

กำหนด policy ว่า refresh ล้มแล้วคงข้อมูลเดิมพร้อม banner หรือ clear list Test ต้องยืนยันทั้ง error type, loading reset และ state เดิม ไม่เพียง expect ว่า future throw

5. Async race

สร้าง Completer สองตัว: request B เริ่มทีหลังแต่จบก่อน แล้ว A จบทีหลัง ตรวจว่า generation/cancel logic ไม่ให้ A ทับ B นี่จับ bug ที่ happy-path test ไม่เห็น

6. Dispose

ใช้ addTearDown(store.dispose) ทุก test และพิสูจน์ timer/subscription ถูกหยุด ห้าม notify หลัง dispose Store ที่เริ่ม polling ใน constructor ทำ test ยาก—แยก start() หรือ inject scheduler

7. Business navigation state

ตัวอย่างจริงตรวจว่า Back ลด step ก่อน, exit เก็บ resumable draft และ bottom navigation ล้าง receiving state นี่คือ logic ที่เหมาะกับ Store test เพราะไม่ต้อง render UI แต่ครอบคลุม workflow สำคัญ

8. Store test matrix

initial, success, empty, failure, retry, double-submit, stale response, dispose mid-flight, navigation reset/resume และ notification หลังทุก public command โดย fixture แต่ละ test แยกขาดจากกัน
