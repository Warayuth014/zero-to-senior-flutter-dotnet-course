Read concurrency: refresh สองครั้งอาจตอบกลับไม่เรียงตามเวลาที่ส่ง รุ่นเก่าจึงต้องไม่มีสิทธิ์ทับ state จาก request รุ่นใหม่

1. Generation token

final generation = ++_requestGeneration;
final result = await repository.fetchOpen();
if (generation != _requestGeneration) return;

ทุก load ได้เลขรุ่น เมื่อ response กลับ Store commit เฉพาะรุ่นล่าสุด หลักนี้แก้ stale response โดยไม่ต้อง cancel transport จริง

2. Initial load

เมื่อ list ยังว่างให้แสดง progress เต็มหน้า เพราะไม่มีข้อมูลก่อนหน้าให้ทำงาน แต่ต้องมี error view พร้อม retry หากอ่านครั้งแรกไม่สำเร็จ

3. Refresh

เมื่อมี task อยู่แล้ว refresh ไม่ควรลบ list แล้วกระพริบ spinner เต็มหน้า เก็บ snapshot เดิม แสดง progress บางๆ และให้ operator อ่านงานต่อได้

4. Error กับ stale data

ถ้า refresh ล้มเหลว รายการเดิมไม่เท่ากับข้อมูลล่าสุด UI จึงแสดง banner ว่า reload ไม่สำเร็จ แทนการซ่อน error หรือแทน list ด้วยหน้าว่าง ต้องสื่อว่าข้อมูลอาจ stale

5. finally ที่มี guard

request รุ่นเก่าห้ามตั้ง _loading=false ขณะที่รุ่นใหม่ยังรอ จึงตรวจ generation ใน finally ด้วย Guard เฉพาะ assignment result แต่ลืม loading คือ race ที่พบบ่อย

6. Cancellation ต่างจาก ignore

generation token ไม่หยุด bandwidth หรือ server work เพียงไม่ commit ผลเก่า ถ้าค้นหาถี่ควร debounce/cancel client เพิ่ม แต่ยังต้องมี last-write policy ป้องกัน callback ที่หลุดมา

7. Test race

สร้าง Completer สองตัว เรียก load สองครั้ง ให้คำตอบครั้งที่สองกลับก่อนแล้วครั้งแรกกลับทีหลัง สุดท้าย Store ต้องถือรายการของครั้งที่สอง

8. Checkpoint

อธิบายให้ได้ว่าทำไม request generation ถูกตรวจทั้งหลัง await, catch และ finally ถ้าขาดจุดใด state รุ่นเก่าอาจทับ data/error/loading รุ่นใหม่
