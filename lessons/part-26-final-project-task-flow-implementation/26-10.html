Reconciliation: เมื่อผล mutation ไม่แน่นอน เป้าหมายไม่ใช่เดาว่า success/error แต่คือกลับไปหา source of truth ด้วย read ที่ปลอดภัย

1. Timeout path

POST complete → timeout (outcome unknown)
GET open tasks → TASK-001 หาย
สรุป: ไม่อยู่ในงานค้างแล้วและไม่ส่ง command ใหม่

2. ถ้ายังพบ task

การยังพบ task ไม่พิสูจน์ว่า command ไม่เคยเกิดเสมอ อาจเป็น read replica lag หรือ workflow เปลี่ยน state อื่น Lab แสดงข้อความให้ตรวจสอบก่อนสั่งซ้ำ ไม่ประกาศ failure แบบมั่นใจเกินหลักฐาน

3. Preserve warning

ระหว่าง reload Store เก็บข้อความ “กำลังตรวจสอบสถานะล่าสุด” เพื่อไม่ให้ spinner ดูเหมือน action ปกติ เมื่อ read จบจึงแปลงเป็น success-like reconciliation หรือ unresolved warning

4. Reconcile endpoint ที่ดีกว่า

production ควร query command status ด้วย idempotency key หรือคืน operation resource เช่น GET /commands/{id} แทนอนุมานจาก task list โดยเฉพาะเมื่อ list มี filter/pagination

5. Offline queue

หากต้อง queue command ข้าม app restart ให้ persist commandId, payload hash, createdAt และ state pending/sent/confirmed/failed แล้ว replay key เดิม Part offline-first จะขยายเรื่องนี้ภายหลัง

6. UX language

ใช้ “ยังยืนยันผลไม่ได้” ต่างจาก “ไม่สำเร็จ” และบอก action ต่อไป เช่น โหลดสถานะ/สแกนตรวจ หลีกเลี่ยง toast สั้นที่หายก่อน operator อ่าน

7. Observability

แสดง correlation ID เมื่อมี response และ log command ID แบบไม่รั่ว token เพื่อให้ support จับคู่ client intent กับ server audit ได้

8. Exercise

ทำ fake repository ที่ complete โยน unknown outcome แล้ว fetch คืน list ว่าง Test ต้องได้ tasks ว่าง, error null และ action message ว่าตรวจสอบซ้ำแล้ว จากนั้นทำกรณี fetch ยังมี task และอธิบาย UI ที่เหมาะสม
