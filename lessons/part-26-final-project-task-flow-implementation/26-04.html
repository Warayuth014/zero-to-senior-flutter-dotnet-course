API exception และ outcome unknown

Part 26: Final Project Implementation I: Production Task Flow

Mutation ambiguity: timeout ของ GET แปลว่าโหลดไม่สำเร็จ แต่ timeout ของ POST ไม่ได้แปลว่า server ไม่ทำงาน เพราะ response อาจหายหลัง commit แล้ว

1. Error taxonomy

ApiException เก็บ statusCode และ outcomeUnknown เพื่อให้ชั้นบนตัดสินใจตามชนิด operation ได้ ข้อความอย่างเดียวไม่พอและการ parse string error เปราะมาก

2. Known failure

HTTP 400/404 ที่มี response ชัดคือ server ตอบกลับแล้ว Client รู้ว่า request รอบนั้นไม่เกิดผลตามที่ขอ จึงแสดง validation/not-found และให้ผู้ใช้แก้ input ได้

3. Unknown outcome

Socket หลุดหรือ timeout ระหว่าง POST อาจเกิดก่อน server รับ, ระหว่างประมวลผล หรือหลัง commit ก่อน response ถึง client จึงตั้ง outcomeUnknown: true และห้าม retry แบบสร้าง command ใหม่ทันที

4. GET ต่างจาก POST

GET timeout → state เดิม + retry read ได้
POST timeout → reconcile หรือ replay command ID เดิม

การเหมารวม network error เป็น “ลองใหม่” คือสาเหตุของรับสินค้า/ตัด stock ซ้ำในระบบธุรกิจ

5. Web และ mobile exceptions

mobile อาจได้ SocketException ส่วน web client มักโยน http.ClientException ApiClient จึงแปลทั้งคู่เป็นศัพท์ของแอปเพื่อไม่ให้ store ผูกกับ platform exception

6. Status code ยังสำคัญ

เก็บ status สำหรับ policy เช่น 401 ให้ session controller logout, 409 ให้แสดง conflict และ 422 แสดง field validation แต่ UI ไม่ควรเดาจาก raw body ทุกหน้า

7. ขอบเขตของ lab

lab ถือ network failure ของ POST เป็น unknown อย่าง conservative ระบบจริงอาจรู้ละเอียดขึ้นจาก transport instrumentation แต่ห้ามลดความไม่แน่นอนโดยไม่มีหลักฐาน

8. แบบฝึกหัด

เขียนตาราง HTTP 400, 401, 409, 500, connect failure และ response timeout ว่า complete task ควร retry, reconcile, logout หรือหยุดอย่างไร พร้อมเหตุผลเรื่อง side effect
