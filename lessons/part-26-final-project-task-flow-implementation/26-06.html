Completion result และ idempotency contract

Part 26: Final Project Implementation I: Production Task Flow

Idempotency contract: ปุ่ม disabled ป้องกัน double tap ใน process เดียว แต่ command identity ป้องกันการส่งซ้ำข้าม timeout, restart และหลาย proxy hop

1. Command identity

Store สร้าง commandId ต่อ user intent แล้ว repository ส่งเป็น Idempotency-Key Backend จำผลตาม key และคืนผลเดิมเมื่อ replay แทนประมวลผลใหม่

2. Scope ของ key

key ควร unique ภายใน operation/tenant/user ตาม policy Lab ปฏิเสธ key เดิมที่เปลี่ยน task id แต่ Backend production ต้องบันทึก request fingerprint ทั้ง route/body ด้วย เพื่อปฏิเสธ payload ต่างกันที่ละเอียดกว่านั้น

3. Response ที่ typed

TaskCompletion(id: responseId,
  alreadyCompleted: alreadyCompleted,
  correlationId: correlationId)

repository ตรวจ id ตรง request, boolean เป็นชนิดจริงและ correlation ไม่ว่างก่อนคืน store

4. alreadyCompleted กับ replayed

alreadyCompleted หมายถึง task ถูกปิดก่อน command นี้ ส่วน replayed หมายถึง key นี้เคยได้ผลแล้ว ทั้งสองเรื่องต่างกันและช่วย audit/debug คนละแบบ

5. อายุข้อมูล idempotency

production store ต้องมี retention ที่ยาวกว่าหน้าต่าง retry และ cleanup policy หากลบเร็วเกิน replay อาจสร้าง side effect ใหม่ หากไม่ลบเลย storage โตไม่จำกัด

6. DB transaction

การเปลี่ยน task และบันทึก idempotency result ต้องอยู่ transaction เดียวกัน มิฉะนั้น crash ระหว่างสองขั้นทำให้ task เปลี่ยนแต่ไม่มีหลักฐานสำหรับ replay In-memory lock ของ lab แสดง atomic intention แต่ไม่แทน database transaction

7. Client retry rule

retry mutation ได้เมื่อ replay key เดิมและ backend รับรอง semantics นี้ การสร้าง key ใหม่ทุก retry ทำให้กลไกไม่มีประโยชน์

8. แบบฝึกหัด

ออกแบบ schema IdempotentCommands(Key, Operation, RequestHash, StatusCode, ResponseJson, CreatedAt) และอธิบาย unique constraint/transaction ที่ต้องใช้ใน .NET + EF Core
