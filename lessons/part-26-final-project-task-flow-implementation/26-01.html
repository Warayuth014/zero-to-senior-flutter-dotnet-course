Milestone contract และ Definition of Done

Part 26: Final Project Implementation I: Production Task Flow

Milestone 1: เราจะเปลี่ยน task vertical slice ใน labs/flutter_wms_companion จาก demo happy path ให้เป็น baseline ที่บอกได้ว่าคำสั่งถูกส่งกี่ครั้ง ผลลัพธ์เชื่อถือได้แค่ไหน และมี test พิสูจน์พฤติกรรมสำคัญ

1. ทำไมเริ่มจาก slice เล็ก

Final Project เต็มระบบมี auth, inventory, receiving และ realtime แต่ถ้าแต่ละ feature ยังไม่มีมาตรฐานเรื่อง contract, mutation และ test การเพิ่มหน้าจอจะคูณความเสี่ยง เราจึงทำหนึ่งเส้นทางให้ครบก่อน: TaskScreen → TaskStore → TaskRepository → JsonApi → .NET แล้วใช้เป็นแม่แบบของ feature ถัดไป

2. User outcome

ผู้ปฏิบัติงานต้องเห็นงานค้าง โหลดใหม่ได้ ยืนยันก่อนปิดงาน กด task เดิมซ้ำระหว่าง request ไม่ได้ และเมื่อเครือข่ายขาดหลังส่งคำสั่ง แอปต้องตรวจสถานะล่าสุดแทนการเดาว่าล้มเหลว

3. Acceptance scenarios

Given งาน TASK-001 ยังเปิด
When ผู้ใช้ยืนยันปิดงาน
Then server รับ command เดียวและงานหายจากรายการ

Given request complete หมดเวลา
When server อาจรับคำสั่งไปแล้ว
Then client reload งานล่าสุดก่อนอนุญาตให้ตัดสินใจซ้ำ

4. Quality attributes

  • Contract เสียต้อง fail ที่ repository ไม่ปล่อย model ครึ่งๆ กลางๆ ถึง UI
  • Loading ครั้งแรก, refresh และ action ต้องไม่ใช้ boolean เดียวกัน
  • Command ต้องมี identity สำหรับ retry อย่างปลอดภัย
  • Error ต้องบอกต่างกันระหว่าง “ไม่สำเร็จแน่” กับ “ยังไม่รู้ผล”

5. Definition of Done

flutter analyze, unit tests, widget test และ dotnet build ต้องผ่าน ผู้เรียนต้องอธิบาย trace พร้อม failure path ได้ และลอง replay idempotency key เดิมแล้วไม่มี side effect รอบสอง

6. สิ่งที่ยังไม่อ้างว่า production-ready

lab ใช้ in-memory dictionary ไม่มีฐานข้อมูลหรือ distributed idempotency store, ไม่มี JWT จริงและไม่มี telemetry backend ดังนั้นมันคือ production-style learning baseline ไม่ใช่ระบบพร้อม deploy คลังจริง

7. ไฟล์ที่จะเปลี่ยน

อ่าน core/json_api.dart, core/api_client.dart, feature tasks ทั้ง model/repository/store/screen, tests สี่ชุด และ WmsMobileApi/Program.cs ทุกไฟล์มีหน้าที่อยู่ใน trace เดียว

8. Checkpoint

ก่อนเดินต่อ ให้วาด sequence diagram happy path และ timeout path ด้วยตัวเอง ถ้ายังไม่รู้ว่า layer ใดตัดสินว่า response เสียหรือ task ยังเปิด ให้กลับมาแก้ boundary ก่อนเพิ่ม feature
