1. ปัญหาที่บทนี้แก้

คนหน้างานสแกนของเข้ารายการไป 12 บรรทัด แล้วเกิดเหตุการณ์เหล่านี้ตามลำดับ

เกิดอะไร12 บรรทัดควรยังอยู่ไหม
เปิดกล่องยืนยันขึ้นมาแล้วปิดอยู่
สลับไปแท็บอื่นแล้วกลับมาอยู่
ย่อแอปไปเปิดแอปอื่น แล้วกลับมาอยู่
กดปุ่ม “พักไว้ก่อน”อยู่ แต่ต้องรู้ว่ายังไม่เสร็จ
กดปุ่ม “ยกเลิกใบนี้”ไม่อยู่
ระบบปิดแอปเพราะหน่วยความจำไม่พอควรอยู่ แต่ส่วนใหญ่ไม่อยู่
ออกจากระบบไม่ควรให้คนถัดไปเห็น

เจ็ดเหตุการณ์ คำตอบไม่เหมือนกัน — และถ้าไม่ได้ตัดสินไว้ล่วงหน้า คำตอบจะกลายเป็น “แล้วแต่ว่า widget ตัวไหนบังเอิญถูกทำลายก่อน” ซึ่งเป็นสิ่งที่อธิบายให้ผู้ใช้ฟังไม่ได้

ประโยคเดียวที่ต้องจำ: ก่อนเขียนโค้ดเก็บอะไรสักอย่าง ให้ตอบก่อนว่ามันอยู่ชั้นไหน — เพราะแต่ละชั้นมีคำตอบเรื่อง “เมื่อไหร่ควรหาย” ที่ต่างกันโดยสิ้นเชิง
ชั้นเก็บที่ไหนหายเมื่อ
ของ UIState ของ widgetwidget ถูกทำลาย — และไม่เป็นไร
ร่างงานstore หรือเครื่องผู้ใช้ยืนยันว่าจะทิ้ง หรือส่งสำเร็จ
ข้อมูลจากเซิร์ฟเวอร์storeโหลดใหม่ทับ หรือออกจากระบบ
ผู้ใช้/การตั้งค่าเครื่องออกจากระบบ หรือผู้ใช้เปลี่ยนเอง

5. พัก กับ ยกเลิก คือคนละเรื่อง

นี่คือสิ่งที่ TaskOutcome ใน 5.3 ออกแบบไว้ให้แยกได้

class TaskPaused extends TaskOutcome {
  const TaskPaused(this.draft);
  final NavTask draft;        // พาร่างกลับไปด้วย
}

class TaskCancelled extends TaskOutcome {
  const TaskCancelled();      // ไม่มีอะไรกลับไป
}

ฝั่งที่รับทำต่างกันชัดเจน

case TaskPaused(draft: final draft):
  setState(() {
    _tasks = [
      for (final item in _tasks) item.id == draft.id ? draft : item,
    ];
    _pausedIds.add(draft.id);     // เก็บร่าง แต่ทำเครื่องหมายว่ายังไม่เสร็จ
  });

case TaskCancelled():
  showResultBanner(messenger, 'ยกเลิกการแก้ไข ${task.id}');
  // ไม่แตะข้อมูลเลย
พักไว้ก่อนยกเลิก
ร่างเก็บทิ้ง
ผู้ใช้ตั้งใจจะกลับมาทำต่อไม่เอาแล้ว
งานฝั่งเซิร์ฟเวอร์ยังเปิดอยู่ยังเปิดอยู่เหมือนกัน

แถวล่างสำคัญ — ทั้งสองกรณีไม่ได้แตะข้อมูลฝั่งเซิร์ฟเวอร์เลย เพราะไม่เคยส่งอะไรไป งานยังคงเปิดค้างอยู่ทั้งคู่ ต่างกันแค่ว่าฝั่งแอปเก็บสิ่งที่ทำไว้หรือไม่

ถ้าธุรกิจต้องการให้ “พักไว้ก่อน” หมายถึงการจองงานนั้นไว้ไม่ให้คนอื่นหยิบ นั่นเป็นการกระทำที่ต้องส่งไปเซิร์ฟเวอร์ ซึ่งเป็นคนละเรื่องกับการเก็บร่างในเครื่อง

6. เปิดกล่องโต้ตอบไม่ควรทำให้อะไรหาย

เมื่อเปิด showDialog หรือแผ่นด้านล่าง หน้าจอเดิม ไม่ได้ถูกทำลาย มันแค่ถูกทับ

┌──────────────────┐
│  ┌────────────┐  │
│  │ ยืนยันไหม?  │  │  ← route ใหม่ทับอยู่
│  └────────────┘  │
│ หน้ารายละเอียด    │  ← State ยังอยู่ครบ
└──────────────────┘

จึงไม่ต้องทำอะไรพิเศษเพื่อรักษาร่างระหว่างเปิดกล่อง — เป็นเรื่องเดียวกับ 5.1 หัวข้อ 3

สิ่งที่ต้องระวังคือทางกลับกัน — อย่าให้กล่องโต้ตอบแก้ข้อมูลจริงก่อนที่ผู้ใช้จะยืนยัน

// ผิด — แก้ไปแล้วตั้งแต่ยังไม่ตอบ
showDialog(builder: (ctx) => AlertDialog(
  content: TextField(onChanged: (v) => store.updateNote(v)),
));
// ถูก — กล่องถือร่างของตัวเอง แล้วคืนค่าตอนกดยืนยัน
final note = await showDialog<String>(...);
if (note != null) store.updateNote(note);

7. ย่อแอปแล้วกลับมา ไม่เหมือนระบบปิดแอป

ย่อแอปไว้ระบบปิดแอป
เกิดเมื่อผู้ใช้กดปุ่มโฮมระบบต้องการหน่วยความจำคืน
ข้อมูลใน Stateยังอยู่หายหมด
ข้อมูลใน storeยังอยู่หายหมด
ผู้ใช้รู้ตัวไหมรู้ไม่รู้เลย

คอลัมน์ขวาเป็นสิ่งที่คนพัฒนามักไม่เคยเจอ เพราะเครื่องพัฒนามีหน่วยความจำเหลือเฟือ แต่บน PDA ที่รันหลายแอปพร้อมกันทั้งกะ มันเกิดจริง

อาการที่ผู้ใช้เห็นคือ “วางเครื่องไว้ไปกินข้าว กลับมาแล้วงานที่สแกนไว้หายหมด” ซึ่งฟังดูเหมือนแอปพัง ทั้งที่ระบบทำถูกต้องตามที่ควร

ทางเดียวที่รอดคือเก็บลงเครื่อง — ซึ่งจะทำจริงใน Part 12 แต่ต้องตัดสินใจตั้งแต่ตอนออกแบบว่าอะไรคุ้มที่จะเก็บ

คุ้มเก็บไม่คุ้มเก็บ
สิ่งที่ต้องเดินไปสแกนใหม่ตำแหน่งที่เลื่อนในรายการ
จำนวนที่นับด้วยมือช่องที่กำลังโฟกัส
รหัสคำสั่งที่สร้างไว้แล้ว (4.14)ข้อมูลที่โหลดใหม่ได้ง่าย

8. ออกจากระบบต้องล้างของคนเก่า

ต่อจาก 5.4 หัวข้อ 7 — ร่างที่ค้างอยู่คือข้อมูลที่ต้องคิดเป็นพิเศษ

ผู้ใช้ A สแกนค้างไว้ 18 บรรทัด → ออกจากระบบ
ผู้ใช้ B ล็อกอินด้วยเครื่องเดียวกัน
  → ต้องไม่เห็น 18 บรรทัดนั้น
  → แต่ A ต้องได้มันคืนเมื่อกลับมา

ทางแก้คือผูกร่างไว้กับเจ้าของ

await draftStorage.save(userId: session.userId, draft: draft);

สิ่งที่ต้องล้างทันทีเมื่อออกจากระบบ กับสิ่งที่เก็บไว้ได้ ต่างกัน

ล้างทันทีเก็บไว้ได้ (ผูกกับผู้ใช้)
tokenร่างงานที่ยังไม่ได้ส่ง
ข้อมูลใน store ทั้งหมดรหัสคำสั่งที่ยังค้าง
ชื่อและข้อมูลส่วนตัวการตั้งค่าที่ไม่อ่อนไหว เช่นขนาดตัวอักษร

9. เกณฑ์ตัดสินที่ใช้ได้ทุกครั้ง

เมื่อไม่แน่ใจว่าข้อมูลชิ้นหนึ่งควรอยู่รอดแค่ไหน ให้ถามสามข้อ

คำถามถ้าตอบว่าแปลว่า
ถ้ามันหาย ผู้ใช้ต้องทำอะไรใหม่กดสองสามครั้งอยู่ใน State ก็พอ
เดินไปสแกนใหม่ทั้งหมดต้องเก็บลงเครื่อง
คนอื่นเห็นแล้วเสียหายไหมไม่เก็บข้ามการออกจากระบบได้
ใช่ต้องล้างเมื่อออกจากระบบ
เซิร์ฟเวอร์รู้เรื่องนี้หรือยังรู้แล้วโหลดใหม่ได้ ไม่ต้องเก็บ
ยังไม่รู้เราคือที่เดียวที่มีข้อมูลนี้ — ต้องรับผิดชอบ

ข้อสุดท้ายคือข้อที่สำคัญที่สุด — ทุกอย่างที่ยังไม่ได้ส่งไปถึงเซิร์ฟเวอร์ มีสำเนาอยู่ที่เดียวในโลกคือในเครื่องนั้น ถ้ามันหาย ไม่มีใครกู้คืนได้เลย

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
เปิดกล่องยืนยันแล้วสิ่งที่กรอกหายให้กล่องแก้ข้อมูลจริงระหว่างพิมพ์ให้กล่องถือร่างของตัวเองแล้วคืนค่า
สลับแท็บแล้วสิ่งที่กรอกหายสร้างแท็บใหม่ทุกครั้งIndexedStack หรือย้ายไป store (5.6)
วางเครื่องไว้แล้วกลับมา งานหายระบบปิดแอปเก็บร่างลงเครื่อง
ล็อกอินคนใหม่แล้วเห็นงานของคนเก่าร่างไม่ได้ผูกกับผู้ใช้เก็บพร้อมรหัสผู้ใช้
“พักไว้ก่อน” กับ “ยกเลิก” ได้ผลเหมือนกันผลลัพธ์เป็น boolแยกเป็นคนละกรณี (5.3)
กดพักแล้วคนอื่นหยิบงานไปทำเข้าใจว่าพักคือการจองถ้าต้องจอง ต้องส่งไปเซิร์ฟเวอร์
ไม่รู้ว่าข้อมูลไหนควรอยู่ตรงไหนไม่เคยแยกชั้นใช้ตารางในหัวข้อ 3

11. แบบฝึกหัด

หน้าจอนับสต๊อกหนึ่งหน้า มีข้อมูลหกอย่าง

ข้อมูลรายละเอียด
ตำแหน่งที่เลื่อนในรายการรายการมี 80 บรรทัด
ยอดที่นับได้แต่ละบรรทัดนับไปแล้ว 53 บรรทัด
ยอดตั้งต้นจากระบบโหลดมาจากเซิร์ฟเวอร์
รหัสใบนับได้มาตอนเริ่มงาน
ชื่อผู้นับมาจากการล็อกอิน
คำค้นที่พิมพ์ในช่องค้นหาใช้กรองรายการ
  1. จัดแต่ละอย่างลงชั้นตามตารางหัวข้อ 3
  2. ตอบว่าอะไรต้องเก็บลงเครื่อง และอะไรไม่ต้อง
  3. ผู้ใช้นับไป 53 บรรทัด แล้วระบบปิดแอป — เขียนว่าตอนเปิดกลับมาควรเกิดอะไรตามลำดับ
ดูแนวคำตอบและเหตุผล

ข้อ 1 — จัดชั้น

ข้อมูลชั้นเก็บที่
ตำแหน่งที่เลื่อนของ UIState
คำค้นของ UIState
ยอดที่นับได้ร่างงานstore + เครื่อง
รหัสใบนับร่างงานstore + เครื่อง
ยอดตั้งต้นข้อมูลจากเซิร์ฟเวอร์store
ชื่อผู้นับผู้ใช้session

จุดที่คนมักจัดผิดคือ รหัสใบนับ — ดูเหมือนข้อมูลจากเซิร์ฟเวอร์เพราะได้มาจากเซิร์ฟเวอร์ แต่มันคือสิ่งที่ผูกยอดที่นับไว้เข้ากับใบงานนั้น ถ้ามันหาย ยอด 53 บรรทัดที่เหลืออยู่จะไม่รู้ว่าเป็นของใบไหน จึงต้องเก็บคู่กันไปเสมอ

ข้อ 2 — อะไรต้องเก็บลงเครื่อง

เก็บไม่เก็บ

รหัสผู้ใช้ที่เป็นเจ้าของยอดตั้งต้น
เวลาที่บันทึกล่าสุดชื่อผู้นับ

เหตุผลที่ ไม่เก็บยอดตั้งต้น ทั้งที่มันอยู่บนจอเหมือนกัน — เพราะโหลดใหม่ได้ และการโหลดใหม่ยัง ดีกว่า ด้วย เนื่องจากอาจมีคนแก้ยอดตั้งต้นระหว่างที่แอปปิดอยู่ ตามเกณฑ์ข้อสามในหัวข้อ 9 — เซิร์ฟเวอร์รู้เรื่องนี้อยู่แล้ว จึงไม่ใช่ความรับผิดชอบของเรา

ส่วนยอดที่นับได้ เซิร์ฟเวอร์ไม่รู้เลย เพราะยังไม่เคยส่งไป — เครื่องนี้คือที่เดียวในโลกที่มีข้อมูลนั้น

ข้อ 3 — เปิดกลับมาหลังระบบปิดแอป

1. เปิดแอป → ตรวจว่ายังล็อกอินอยู่ไหม
     ยังอยู่ → ไปข้อ 2
     ไม่อยู่ → ให้ล็อกอินก่อน แล้วค่อยไปข้อ 2

2. ค้นหาร่างที่ค้างไว้ ของผู้ใช้คนนี้เท่านั้น
     ไม่มี → เข้าหน้าหลักตามปกติ จบ

3. โหลดใบนับนั้นใหม่จากเซิร์ฟเวอร์ (ยอดตั้งต้นล่าสุด)
     ใบถูกปิดไปแล้ว → บอกผู้ใช้ ทิ้งร่าง จบ
     ใบยังเปิดอยู่   → ไปข้อ 4

4. รวมยอดที่นับไว้เข้ากับยอดตั้งต้นที่โหลดใหม่
     ยึดยอดที่ผู้ใช้นับไว้เสมอ ไม่ให้ข้อมูลใหม่ทับ

5. แสดงให้ผู้ใช้เห็นก่อนทำต่อ
     "พบการนับค้างไว้ 53 จาก 80 บรรทัด เมื่อ 14:32"
     [ทำต่อ]  [เริ่มใหม่]

6. ถ้าเลือกทำต่อ → เข้าหน้านับ เลื่อนไปบรรทัดถัดไปที่ยังไม่ได้นับ

ขั้นทำไมต้องมี
ข้อ 2 กรองด้วยผู้ใช้ไม่ให้คนกะถัดไปเจองานของคนกะก่อน (5.4)
ข้อ 3 โหลดใหม่ยอดตั้งต้นอาจเปลี่ยน และใบอาจถูกปิดไปแล้ว
ข้อ 4 รวมโดยยึดของผู้ใช้เป็นการรวมแบบเดียวกับ 4.16 หัวข้อ 7
ข้อ 5 ถามก่อนอย่าพาเข้าหน้านับเงียบ ๆ — ผู้ใช้ไม่รู้ว่าแอปเคยปิด จะงงว่าทำไมมีตัวเลขอยู่แล้ว

ทำไมข้อ 5 สำคัญกว่าที่คิด

ผู้ใช้ไม่รู้ว่าระบบปิดแอปไป เขาแค่กดเปิดแอปตามปกติ ถ้าเจอหน้านับที่มีตัวเลขอยู่แล้ว 53 บรรทัด เขาจะไม่แน่ใจว่าตัวเลขนั้นเชื่อได้ไหม หรือใครเป็นคนนับ

การบอกว่า “พบการนับค้างไว้ เมื่อ 14:32” ทำสองอย่าง — ยืนยันว่าเป็นงานของเขาเอง และให้เขาตัดสินใจได้เองว่าจะเชื่อหรือเริ่มใหม่

หลักที่ได้: การกู้ข้อมูลคืนโดยไม่บอก แย่กว่าการกู้คืนแล้วบอก เพราะข้อมูลที่โผล่มาเองโดยไม่มีคำอธิบาย ทำให้ผู้ใช้เริ่มไม่เชื่อสิ่งที่จออื่นแสดงด้วย ซึ่งเป็นหลักเดียวกับ 4.13 หัวข้อ 11 เรื่องห้ามย้อนกลับเงียบ ๆ

12. สรุปท้ายบท

  • แยกข้อมูลเป็นสี่ชั้นตามอายุ แล้วตัดสินเรื่องการเก็บจากชั้น
  • ของ UI หายได้ ร่างงานหายไม่ได้
  • “พัก” กับ “ยกเลิก” ต่างกันที่ร่าง ไม่ใช่ที่เซิร์ฟเวอร์
  • เปิดกล่องโต้ตอบไม่ทำลายหน้าเดิม แต่กล่องต้องไม่แก้ข้อมูลจริงก่อนยืนยัน
  • ย่อแอปกับระบบปิดแอปให้ผลต่างกันสิ้นเชิง และผู้ใช้ไม่รู้ตัวในกรณีหลัง
  • ร่างต้องผูกกับเจ้าของ ไม่งั้นคนถัดไปที่ใช้เครื่องจะเห็น
  • ทุกอย่างที่ยังไม่ถึงเซิร์ฟเวอร์ มีสำเนาอยู่ที่เดียวคือในเครื่องนั้น
  • กู้ข้อมูลคืนแล้วต้องบอกผู้ใช้เสมอ
