1. ปัญหาที่บทนี้แก้

ทุกอย่างที่ทำมาตั้งแต่ Part 1 อยู่บนหน้าจอเดียว แต่แอปจริงมีหลายหน้า

รายการงาน → แตะบรรทัด → รายละเอียดงาน → กดย้อนกลับ → รายการงาน

คำถามที่ต้องตอบให้ได้ก่อนเขียนโค้ด

คำถามทำไมสำคัญ
ตอนอยู่หน้ารายละเอียด หน้ารายการหายไปไหนถ้ามันถูกทำลาย ตำแหน่งที่เลื่อนไว้จะหาย
กดย้อนกลับแล้วหน้ารายการถูกสร้างใหม่ไหมถ้าใช่ ต้องโหลดข้อมูลใหม่ทุกครั้ง
ผลจากหน้ารายละเอียดกลับมาถึงหน้ารายการได้อย่างไรถ้าไม่รู้ จะไปเขียน callback ซ้อนกันหลายชั้นโดยไม่จำเป็น

3. Mental model: กองกระดาษ

            ┌──────────────────┐
            │ รายละเอียดงาน     │  ← บนสุด คือหน้าที่ผู้ใช้เห็น
            ├──────────────────┤
            │ หน้าหลัก          │  ← ยังอยู่ ไม่ได้ถูกทำลาย
            └──────────────────┘

push  = วางใบใหม่ทับ
pop   = หยิบใบบนสุดออก แล้วใบข้างล่างโผล่มา
ประโยคเดียวที่ต้องจำ: หน้าที่อยู่ข้างล่างไม่ได้หายไป มันแค่ถูกบัง — State ของมันยังอยู่ครบ ตำแหน่งที่เลื่อนไว้ก็ยังอยู่

นี่คือคำตอบของสองคำถามแรกในหัวข้อ 1 — กดย้อนกลับแล้วหน้าเดิมไม่ได้ถูกสร้างใหม่ มันแค่โผล่กลับมา

4. เปิดหน้าใหม่

เปิด lib/nav_basics/nav_basics_app.dart

await Navigator.of(context).push<TaskOutcome>(
  MaterialPageRoute<TaskOutcome>(
    builder: (_) => TaskDetailScreen(task: task),
  ),
);
ส่วนหน้าที่
Navigator.of(context)หา Navigator ที่ใกล้ที่สุด โดยเดินขึ้นจาก context (1.10)
MaterialPageRouteสร้างหน้าใหม่พร้อมท่าเลื่อนเข้าแบบ Material (5.2)
builderฟังก์ชันที่สร้าง widget ของหน้านั้น
<TaskOutcome>บอกว่าหน้านี้จะคืนค่าชนิดอะไรกลับมา (5.3)

Navigator มาจากไหน — MaterialApp สร้างให้อัตโนมัติหนึ่งตัว จึงใช้ได้เลยโดยไม่ต้องประกาศเอง

5. push คืน Future

จุดที่ทำให้ Flutter ต่างจากที่หลายคนคุ้นเคย — push คืน Future ที่จะเสร็จเมื่อหน้านั้นถูกปิด

final outcome = await Navigator.of(context).push<TaskOutcome>(...);
// บรรทัดนี้ทำงานตอนที่ผู้ใช้ปิดหน้ารายละเอียดแล้ว
// ซึ่งอาจเป็นสามวินาที หรือสามนาทีหลังจากนั้น

แปลว่านี่คือ async gap ขนาดใหญ่ที่สุดที่จะเจอ — ทุกอย่างใน 4.9 ใช้กับตรงนี้เต็ม ๆ

Future<void> _openTask(NavTask task) async {
  // หยิบไว้ก่อน await เพราะหลังจากนี้หน้าจออาจถูกปิดไปแล้ว (4.9)
  final messenger = ScaffoldMessenger.of(context);

  final outcome = await Navigator.of(context).push<TaskOutcome>(...);
  if (!mounted) return;
  ...
}

6. ปิดหน้าและส่งค่ากลับ

// ใน TaskDetailScreen
void _save() => Navigator.of(context).pop(TaskSaved(_draft));

ค่าที่ใส่ใน pop คือค่าที่ await push ฝั่งโน้นจะได้รับ

หน้ารายการ                    หน้ารายละเอียด
    │
    ├── push ────────────────→ เปิดขึ้นมา
    │   (รออยู่)                    │
    │                              ├── ผู้ใช้แก้จำนวน
    │                              │
    │   ←──────────── pop(TaskSaved(...))
    │
    └── outcome = TaskSaved(...)

7. ปุ่มย้อนกลับก็คือ pop

สิ่งที่คนใหม่มักเข้าใจผิด — คิดว่าปุ่มย้อนกลับเป็นคนละกลไกกับ pop

ผู้ใช้ทำอะไรเกิดอะไรขึ้นค่าที่ส่งกลับ
กดปุ่มลูกศรบน AppBarpop()null
กดปุ่มย้อนกลับของเครื่องpop()null
ปัดจากขอบจอ (iOS)pop()null
กดปุ่มบันทึกที่เราทำเองpop(TaskSaved(...))ค่าที่ส่ง

สามทางแรกให้ null ทั้งหมด ซึ่งเป็นเหตุผลที่ต้องจัดการกรณี null เสมอ — เรื่องนี้ลงลึกใน 5.3

บน PDA บางรุ่นมีปุ่มย้อนกลับแบบฮาร์ดแวร์ที่กดโดนง่ายขณะถือเครื่อง — การถือว่า “ผู้ใช้คงไม่กดย้อนกลับกลางทาง” จึงผิดเสมอ

8. เมธอดอื่นที่ควรรู้จัก

เมธอดทำอะไรใช้เมื่อ
pushวางทับเปิดหน้าใหม่ตามปกติ
popเอาบนสุดออกปิดหน้าปัจจุบัน
pushReplacementแทนที่บนสุดเข้าสู่ระบบสำเร็จ (5.4)
pushAndRemoveUntilวางใหม่แล้วล้างที่เหลือออกจากระบบ (5.4)
maybePopขอปิด โดยเคารพ PopScopeปุ่มย้อนกลับที่เราทำเอง (5.5)
canPopถามว่ามีอะไรให้ปิดไหมตัดสินว่าจะแสดงปุ่มย้อนกลับหรือไม่

pop() ตอนที่เหลือหน้าเดียวจะทำให้แอปปิดหรือได้จอดำ ดังนั้นถ้าไม่แน่ใจให้ถาม canPop() ก่อน

9. pop ให้ถูก Navigator

ปัญหาที่เจอทันทีที่เริ่มใช้กล่องโต้ตอบ

showDialog(
  context: context,
  builder: (dialogContext) => AlertDialog(
    actions: [
      TextButton(
        // ถูก — ปิดกล่อง
        onPressed: () => Navigator.of(dialogContext).pop(false),
        child: const Text('แก้ต่อ'),
      ),
    ],
  ),
)

กล่องโต้ตอบเป็น route หนึ่งเหมือนกัน จึงมี context ของตัวเอง ถ้าเผลอใช้ context ของหน้าจอ อาจไปปิดหน้าจอทั้งหน้าแทนที่จะปิดแค่กล่อง

กฎง่าย ๆ — ใช้ context ที่ builder ตัวนั้นให้มา ซึ่งเป็นกฎเดียวกับที่เรียนใน 4.9 หัวข้อ 5 เรื่อง dialogContext.mounted

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Navigator operation requested with a context that does not include a Navigatorใช้ context ที่อยู่เหนือ MaterialAppใช้ context ที่อยู่ใต้ MaterialApp เช่นใน Builder
ปิดกล่องแล้วหน้าจอปิดตามไปด้วยใช้ context ผิดตัวใน popใช้ dialogContext
Looking up a deactivated widget's ancestorใช้ context หลัง await pushตรวจ mounted หรือหยิบไว้ก่อน (4.9)
กดย้อนกลับแล้วข้อมูลไม่อัปเดตไม่ได้ await ผลของ pushawait แล้วจัดการผล (5.3)
กดปุ่มเปิดหน้ารัว ๆ แล้วได้หลายหน้าซ้อนกันไม่กันการกดซ้ำปิดปุ่มระหว่างเปิด หรือเช็กว่ากำลังเปิดอยู่
แอปปิดตัวเองเมื่อกดย้อนกลับpop ตอนเหลือหน้าเดียวตรวจ canPop() ก่อน

11. แบบฝึกหัด

โค้ดนี้อยู่ในหน้ารายการงาน

void _openTask(NavTask task) {
  Navigator.of(context).push(
    MaterialPageRoute(builder: (_) => TaskDetailScreen(task: task)),
  );
  ScaffoldMessenger.of(context).showSnackBar(
    SnackBar(content: Text('เปิดงาน ${task.id} แล้ว')),
  );
  setState(() => _lastOpenedId = task.id);
}
  1. อธิบายว่าข้อความจะขึ้นตอนไหน และทำไมนั่นไม่ใช่สิ่งที่ตั้งใจ
  2. ถ้าอยากให้ข้อความขึ้นตอนผู้ใช้ปิดหน้ารายละเอียด ต้องแก้อย่างไร
  3. หลังแก้แล้ว มีปัญหาอะไรเพิ่มขึ้นที่ต้องรับมือ
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ข้อความขึ้นตอนไหน

ขึ้น ทันที พร้อมกับที่หน้ารายละเอียดกำลังเลื่อนเข้ามา

เพราะไม่มี await โค้ดจึงไม่ได้รอ — push คืน Future แต่เมื่อไม่รอ บรรทัดถัดไปทำงานต่อทันที

_openTask() เรียก
  ├─ push        → เริ่มเปิดหน้าใหม่
  ├─ showSnackBar → ขึ้นทันที บนหน้าที่กำลังจะถูกบัง
  └─ setState     → ทำงานทันที

ผลคือผู้ใช้จะเห็นข้อความแวบหนึ่งขณะหน้าเลื่อนเข้า แล้วมันก็หายไปกับหน้าที่ถูกบัง

ข้อ 2 — แก้อย่างไร

Future<void> _openTask(NavTask task) async {
  final messenger = ScaffoldMessenger.of(context);   // หยิบก่อน await

  await Navigator.of(context).push(
    MaterialPageRoute(builder: (_) => TaskDetailScreen(task: task)),
  );
  if (!mounted) return;

  messenger.showSnackBar(
    SnackBar(content: Text('ปิดงาน ${task.id} แล้ว')),
  );
  setState(() => _lastOpenedId = task.id);
}

สามอย่างที่เปลี่ยน — เติม async/await, หยิบ messenger ไว้ก่อน, และตรวจ mounted หลัง await

ข้อ 3 — ปัญหาใหม่ที่ตามมา

ปัญหาทำไมเพิ่งโผล่รับมืออย่างไร
หน้ารายการอาจถูกปิดไปแล้วตอนไม่ await โค้ดจบทันที ไม่มีช่องให้อะไรเปลี่ยนif (!mounted) return;
ผู้ใช้อาจกดเปิดรัว ๆ ได้หลายหน้าซ้อนฟังก์ชันกลายเป็น async จึงเรียกซ้อนกันได้ธงกันการกดซ้ำ (4.14)
ไม่รู้ว่าผู้ใช้ปิดหน้าด้วยเหตุผลอะไรตอนนี้เริ่มสนใจผลแล้วรับค่าที่ pop กลับมา (5.3)

ทำไมต้องหยิบ messenger ไว้ก่อน ทั้งที่มี if (!mounted) return; แล้ว

ในโค้ดนี้ตรวจ mounted ก็เพียงพอแล้วจริง ๆ แต่การหยิบไว้ก่อนมีข้อดีที่ต่างออกไป — มันทำให้ ยังแสดงข้อความได้แม้หน้ารายการถูกปิดไป ซึ่งบางครั้งเป็นสิ่งที่ต้องการ เช่นข้อความ “บันทึกสำเร็จ” ที่ควรเห็นแม้ผู้ใช้จะเปลี่ยนหน้าไปแล้ว

ทั้งสองแบบถูก แต่ให้พฤติกรรมต่างกัน จึงต้องเลือกอย่างตั้งใจ — จะกลับมาเรื่องนี้ใน 5.10

ลองต่อ: ใน test/nav_basics_test.dart มีเทสต์ 'กดย้อนกลับโดยไม่ได้แก้อะไร ต้องไม่มีข้อความใด ๆ' ซึ่งใช้ tester.pageBack() จำลองการกดย้อนกลับ ลองอ่านดูว่ามันตรวจอะไร

12. สรุปท้ายบท

  • Navigator เก็บหน้าจอเป็นกอง เอาออกได้ทีละใบบนสุด
  • หน้าที่อยู่ข้างล่างไม่ถูกทำลาย State ยังอยู่ครบ
  • push คืน Future ที่เสร็จเมื่อหน้านั้นถูกปิด — เป็น async gap ที่ยาวที่สุดในแอป
  • ค่าที่ใส่ใน pop คือค่าที่ฝั่งที่ await จะได้รับ
  • ปุ่มย้อนกลับทุกแบบคือ pop() ที่ให้ null
  • ปิด route ด้วย context ที่ builder ตัวนั้นให้มา
  • หลัง await push ต้องตรวจ mounted เสมอ
