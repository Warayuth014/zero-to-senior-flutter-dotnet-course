SnackBar/toast/flash เป็น transient feedback ไม่ใช่ durable state เลือกช่องทางตามความสำคัญและความเร็ว: scanผลทันทีใช้ flash/haptic+status, actionทั่วไปใช้ SnackBar, errorที่ต้องตัดสินใช้ panel/dialog

1. ScaffoldMessenger

final messenger = ScaffoldMessenger.of(context);
messenger
  ..hideCurrentSnackBar()
  ..showSnackBar(const SnackBar(content: Text('บันทึกแล้ว')));

Messengerทำให้ SnackBarอยู่ข้าม Scaffold routeบางกรณีได้ แต่ contextต้องอยู่ใต้ messenger

2. Queue policy

scanถี่ไม่ควร queue SnackBarสิบอัน ใช้ replaceable status/flash ส่วน errorสำคัญอาจ queue/history แยก latest transientจาก audit log

3. Absolute feedback

Shellรับ onToast/onFlashจาก store, timerยกเลิกของเดิมก่อนตั้งใหม่, flashเขียว/แดง+hapticและ cancel timersใน dispose ทำให้ feedbackครอบทุก screenใน shell

4. One-shot event

อย่าเก็บ message persistentใน stateจน rebuild/navigationเล่นซ้ำ ใช้ event ID/consume callbackหรือ clear timerอย่างมี owner

5. Accessibility

สีไม่พอ ต้อง text/icon/semantics live regionตามความเหมาะสม durationอ่านทันและมีทางดู errorเต็ม ไม่ flashรุนแรงเมื่อ reduce motion

6. Context safety

หลัง awaitตรวจ mounted ใช้ ScaffoldMessenger.maybeOfใน reusable sheetเมื่ออาจไม่มี messenger และไม่ให้ storeถือ context

7. แบบฝึกหัด

แจ้ง duplicate scanอย่างไรโดยไม่ขัด throughput?

เฉลย

amber/red flash+haptic pattern+status textแทน modal, ไม่เพิ่ม count, คืน focusเดิม และมี recent scans/historyถ้าต้องตรวจ ไม่ queue SnackBarทุกครั้ง

8. จุดพลาด

อย่าแสดง successก่อน server commit และอย่าใช้ toastเป็นแหล่งเดียวของข้อมูลที่ต้องย้อนดู เพราะหายตามเวลา
