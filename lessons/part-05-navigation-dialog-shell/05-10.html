1. ปัญหาที่บทนี้แก้

ผู้ใช้กดปุ่ม แล้วอะไรบางอย่างเกิดขึ้น — เขาจะรู้ได้อย่างไรว่าสำเร็จ

คำตอบง่าย ๆ คือแสดงข้อความ แต่พอทำจริงจะเจอคำถามที่ตอบยากกว่านั้น

คำถามทำไมตอบยาก
ข้อความควรอยู่นานแค่ไหนสั้นไปไม่ทันอ่าน ยาวไปบังปุ่ม
สแกน 200 ครั้งจะขึ้นข้อความ 200 อันไหมถ้าใช่ ผู้ใช้จะรอดูข้อความมากกว่าทำงาน
เปลี่ยนหน้าไปแล้ว ข้อความควรตามไปไหมบางกรณีควร บางกรณีไม่ควร
ข้อผิดพลาดที่ต้องแก้ ควรใช้ช่องทางเดียวกันไหมข้อความที่หายไปเอง แจ้งเรื่องที่ต้องจัดการไม่ได้

3. Mental model: เลือกตามว่าต้องทำอะไรต่อ

ผู้ใช้ต้องทำอะไรต่อไหม?
    │
    ├─ ไม่ต้อง แค่รับรู้        → ข้อความสั้น ๆ ที่หายไปเอง
    ├─ ต้องรู้ทันทีขณะทำงานเร็ว → สี + เสียง + สั่น
    └─ ต้องตัดสินใจหรือแก้ไข   → แถบที่ค้างอยู่ หรือกล่องโต้ตอบ
ประโยคเดียวที่ต้องจำ: ข้อความที่หายไปเอง เหมาะกับเรื่องที่ถ้าพลาดไม่เห็นก็ไม่เป็นไร — ถ้าพลาดแล้วเป็นเรื่อง ต้องใช้อย่างอื่น

6. อย่าให้ข้อความต่อคิว

ScaffoldMessenger จะเก็บข้อความที่ยังไม่ได้แสดงไว้ในคิว แล้วแสดงทีละอันจนหมด

สแกนผิด 5 ครั้งใน 3 วินาที
  → คิวมี 5 อัน × อันละ 3 วินาที = ผู้ใช้ต้องรอ 15 วินาที
  → ข้อความอันสุดท้ายขึ้นตอนที่ผู้ใช้สแกนไปอีก 8 ชิ้นแล้ว

ผลคือข้อความที่เห็น ไม่ตรงกับสิ่งที่เพิ่งทำ ซึ่งแย่กว่าไม่มีข้อความเลย

เมธอดทำอะไรใช้เมื่อ
clearSnackBars()ล้างทั้งอันที่แสดงอยู่และคิวต้องการให้เห็นเฉพาะอันล่าสุด
hideCurrentSnackBar()ซ่อนอันปัจจุบัน แต่คิวยังอยู่แทบไม่ค่อยได้ใช้

สำหรับงานที่เกิดถี่ ควรใช้ clearSnackBars() เสมอ — เพราะสิ่งที่ผู้ใช้ต้องรู้คือผลของครั้งล่าสุด ไม่ใช่ประวัติของทุกครั้ง

7. งานสแกนต้องใช้คนละแบบ

บน PDA การสแกนเกิดทุกสองสามวินาที ซึ่งเร็วเกินกว่าที่ข้อความแบบเลื่อนขึ้นมาจะทัน

ข้อความเลื่อนขึ้นมาสี + เสียง + สั่น
ต้องมองจอไหมต้องไม่ต้อง
รู้ผลเร็วแค่ไหนรอเลื่อนขึ้นมาทันที
ทำซ้ำถี่ ๆ ได้ไหมไม่ได้ ต่อคิวได้

คนหน้างานมองของในมือ ไม่ได้มองจอตลอดเวลา — เสียงและการสั่นจึงเป็นช่องทางหลัก ส่วนจอเป็นช่องทางรอง

สแกนสำเร็จ  → สั่นสั้น + เสียงสูง + แถบเขียวแวบหนึ่ง + ตัวเลขบนจอเพิ่ม
สแกนซ้ำ     → สั่นสองครั้ง + เสียงต่ำ + แถบเหลือง + ข้อความค้างบนจอ
รูปแบบผิด   → สั่นยาว + เสียงเตือน + แถบแดง + ข้อความค้างบนจอ

สังเกตว่าสองกรณีหลังมี ข้อความค้างอยู่บนจอ ไม่ใช่ข้อความที่หายไปเอง เพราะผู้ใช้อาจไม่ได้มองตอนที่มันเกิด — เขาต้องหันมามองแล้วยังเห็นอยู่

หลักที่ได้ — ช่องทางที่ไม่ต้องมองจอ ใช้บอกว่ามีอะไรเกิดขึ้น ส่วนจอใช้บอกว่าเกิดอะไร และสิ่งที่ต้องแก้ต้องอยู่บนจอจนกว่าจะแก้เสร็จ

เรื่องนี้ต่อกับ 3.10 ที่ออกแบบการตอบสนองของการสแกนไว้แล้ว

8. ข้อความไม่ใช่ที่เก็บข้อมูล

กับดักที่พบบ่อยเมื่อระบบเริ่มโต

// ผิด — ข้อมูลที่ต้องย้อนดูได้ อยู่ในข้อความที่หายไปใน 3 วินาที
showResultBanner(messenger, 'บันทึกใบรับเข้าเลขที่ RC-2481 แล้ว');

เลขที่ใบรับเข้าคือข้อมูลที่ผู้ใช้อาจต้องจดหรือใช้อ้างอิงทีหลัง แต่มันหายไปแล้วและไม่มีที่ไหนให้ดูอีก

ข้อมูลควรอยู่ที่
“บันทึกแล้ว”ข้อความชั่วคราว — พอ
เลขที่ใบรับเข้าบนหน้าจอ หรือในรายการประวัติ
รายการที่บันทึกไม่สำเร็จที่ที่ยังอยู่จนกว่าจะจัดการ

เป็นหลักเดียวกับ 4.12 หัวข้อ 10 — เหตุการณ์กับสถานะเป็นคนละอย่าง ข้อความคือเหตุการณ์ ส่วนเลขที่ใบคือสถานะ

9. อย่าแจ้งสำเร็จก่อนที่มันจะสำเร็จ

// ผิด

แต่มีข้อยกเว้นที่ตั้งใจ — เมื่อใช้ optimistic UI ตาม 4.13 การเปลี่ยนหน้าจอทันทีเป็นสิ่งที่ตั้งใจ แต่ ต้องไม่ประกาศว่าสำเร็จ

สิ่งที่ทำได้ทันทีสิ่งที่ต้องรอ
ติ๊กเครื่องหมายถูกให้เห็นข้อความว่า “บันทึกสำเร็จ”
ปิดปุ่มไม่ให้กดซ้ำเลขที่เอกสารที่เซิร์ฟเวอร์ออกให้

ใน lab ข้อความ “บันทึก T-001 แล้ว” ขึ้นหลังจากที่หน้ารายละเอียดปิดและส่งผลกลับมาแล้ว จึงไม่ใช่การประกาศล่วงหน้า

อาการสาเหตุวิธีแก้

Looking up a deactivated widget's ancestorเรียก ScaffoldMessenger.of(context) หลัง awaitหยิบไว้ก่อน await
ข้อความไปโผล่บนหน้าจอที่ไม่เกี่ยวหยิบ messenger ไว้แล้วผู้ใช้เปลี่ยนหน้าตรวจ mounted ถ้าไม่ต้องการให้ตามไป
ข้อความเด้งซ้ำเมื่อกลับเข้าหน้าจอเก็บข้อความไว้เป็นสถานะอ่านแล้วเคลียร์ (4.12)
สแกนแล้วไม่รู้ว่าติดหรือไม่ใช้ข้อความอย่างเดียวเพิ่มสี เสียง และการสั่น

บอกว่าสำเร็จแล้วเปลี่ยนเป็นล้มเหลวแจ้งก่อนได้ผลจริงรอผลก่อนประกาศ
ผู้ใช้ไม่รู้ว่าต้องทำอะไรต่อข้อความบอกแค่ว่าผิดพลาดบอกทางออกด้วย

12. แบบฝึกหัด

หน้าสแกนรับเข้าหนึ่งหน้า มีเหตุการณ์ห้าแบบ

เหตุการณ์ความถี่
สแกนสำเร็จทุก 2–3 วินาที
สแกนซ้ำรหัสเดิมทุกไม่กี่นาที
สแกนของที่ไม่อยู่ในใบนี้นาน ๆ ครั้ง
ส่งใบทั้งใบสำเร็จ ได้เลขที่ RC-2481ครั้งเดียวตอนจบ
ส่งไม่สำเร็จเพราะเน็ตหลุดนาน ๆ ครั้ง
  1. เลือกช่องทางแจ้งผลของแต่ละเหตุการณ์
  2. เขียนข้อความที่จะแสดง
  3. ตอบว่าเหตุการณ์ไหนที่ห้ามใช้ข้อความแบบหายไปเอง และเพราะอะไร
ดูแนวคำตอบและเหตุผล

ข้อ 1 และ 2 — ช่องทางและข้อความ

เหตุการณ์ช่องทางสิ่งที่แสดง
สแกนสำเร็จสั่นสั้น + เสียงสูง + ตัวเลขบนจอเพิ่มไม่มีข้อความ — แค่ “12 / 40” เปลี่ยนเป็น “13 / 40”
สแกนซ้ำสั่นสองครั้ง + เสียงต่ำ + แถบเหลืองค้าง“PAL-0102 สแกนไปแล้ว (บรรทัดที่ 7)”
ของไม่อยู่ในใบสั่นยาว + เสียงเตือน + แถบแดงค้าง“SKU-9931 ไม่อยู่ในใบรับเข้านี้ ตรวจสอบก่อนสแกน”
ส่งใบสำเร็จเปลี่ยนหน้าจอ + ข้อความชั่วคราวหน้าสรุปแสดง “RC-2481” ตัวใหญ่ พร้อมข้อความ “ส่งใบรับเข้าแล้ว”
ส่งไม่สำเร็จแถบค้าง + ปุ่มลองใหม่“ส่งไม่สำเร็จ เน็ตไม่ตอบสนอง — ข้อมูล 40 บรรทัดยังอยู่ครบ [ส่งอีกครั้ง]”

เหตุผลของแถวแรก — สแกนสำเร็จเกิดทุก 2–3 วินาที ถ้าแสดงข้อความทุกครั้งจะได้คิวยาวและผู้ใช้ต้องรอ สิ่งที่เขาต้องการรู้จริง ๆ คือ “นับไปกี่ชิ้นแล้ว” ซึ่งตัวเลขบนจอบอกได้ดีกว่าข้อความ

เหตุผลของแถวที่สี่ — การส่งใบสำเร็จคือจุดจบของงานทั้งชิ้น สมควรได้หน้าจอของตัวเอง ไม่ใช่ข้อความแวบเดียว

ข้อ 3 — เหตุการณ์ที่ห้ามใช้ข้อความแบบหายไปเอง

สามแบบ โดยเหตุผลต่างกัน

หนึ่ง — สแกนซ้ำ และ ของไม่อยู่ในใบ

เพราะ ผู้ใช้อาจไม่ได้มองจอตอนที่มันเกิด เขาก้มดูของในมือ ยิงบาร์โค้ด แล้วหันไปหยิบชิ้นถัดไป กว่าจะหันกลับมามองจอ ข้อความก็หายไปแล้ว

ผลคือเขาไม่รู้ว่าชิ้นนั้นไม่ได้ถูกนับ แล้วจะพบทีหลังว่ายอดไม่ตรง โดยไม่รู้ว่าตกหล่นตรงไหน

ข้อความจึงต้องค้างอยู่จนกว่าจะสแกนชิ้นถัดไปสำเร็จ — ซึ่งเป็นการยืนยันว่าเขาเห็นและจัดการแล้ว

สอง — เลขที่ RC-2481

เพราะมันคือ ข้อมูล ไม่ใช่การแจ้งเตือน ตามหัวข้อ 8

ผู้ใช้ต้องจดเลขนี้ลงในเอกสารกระดาษ
  → เงยหน้าดูจอ → ข้อความหายไปแล้ว
  → ต้องกลับไปหาในประวัติ หรือถามหัวหน้า

เลขที่เอกสารต้องอยู่บนหน้าจอจนกว่าผู้ใช้จะกดออกเอง และต้องหาเจอในประวัติได้ด้วย

สาม — ส่งไม่สำเร็จ

เพราะ มันยังไม่จบ — มีงานค้างที่ต้องจัดการ ข้อความที่หายไปเองแปลว่า “รับทราบแล้วนะ” ซึ่งไม่จริง

ถ้าใช้ข้อความชั่วคราวผลที่เกิด
ผู้ใช้ไม่ทันเห็นคิดว่าส่งสำเร็จ เดินไปทำงานถัดไป
เห็นแต่ยังไม่ทันกดข้อความหาย ไม่มีปุ่มให้กดอีก
ข้อมูล 40 บรรทัดยังอยู่แต่ไม่มีอะไรบอกว่ายังอยู่ — เขาอาจเริ่มสแกนใหม่ทั้งใบ

เกณฑ์เดียวที่ใช้ตัดสินได้ทั้งสามข้อ

ถามว่าถ้าตอบว่าใช่
ถ้าผู้ใช้ไม่เห็นข้อความนี้ จะเกิดความเสียหายไหมห้ามใช้ข้อความที่หายไปเอง
ข้อความนี้มีข้อมูลที่ต้องใช้ทีหลังไหมห้ามใช้ข้อความที่หายไปเอง
มีอะไรที่ผู้ใช้ต้องทำต่อไหมห้ามใช้ข้อความที่หายไปเอง

เมื่อใช้เกณฑ์นี้แล้ว จะพบว่าข้อความแบบหายไปเองเหมาะกับกรณีที่แคบกว่าที่คิดมาก — คือ เรื่องที่เกิดขึ้นแล้ว จบแล้ว และพลาดไม่เห็นก็ไม่เป็นไร เท่านั้น

13. สรุปท้ายบท

  • เลือกช่องทางจากคำถามว่าผู้ใช้ต้องทำอะไรต่อ
  • ส่งผ่าน ScaffoldMessengerState ไม่ใช่ BuildContext เพื่อให้เรียกได้หลัง await
  • ล้างคิวก่อนแสดงอันใหม่ ไม่งั้นข้อความจะไม่ตรงกับสิ่งที่เพิ่งทำ
  • งานสแกนต้องใช้สี เสียง และการสั่น เพราะผู้ใช้ไม่ได้มองจอตลอด
  • สิ่งที่ต้องแก้ ต้องค้างอยู่บนจอจนกว่าจะแก้เสร็จ
  • ข้อความไม่ใช่ที่เก็บข้อมูล — เลขที่เอกสารต้องอยู่ที่อื่น
  • อย่าประกาศว่าสำเร็จก่อนที่มันจะสำเร็จจริง
  • ข้อความควรบอกสิ่งที่ทำ ผลที่ได้ และสิ่งที่ต้องทำต่อ
