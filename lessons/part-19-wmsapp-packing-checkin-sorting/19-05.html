1. เซิร์ฟเวอร์ปิดกล่องให้เอง

คอมเมนต์ในฝั่ง API อธิบายไว้

/// สแกน Part (เพิ่ม scanned qty) — ส่ง serialNumbers ได้ (optional)
/// Auto-finalize เมื่อทุก Detail ใน Pack เป็น DONE — response จะมี
/// packFinalized=true + trackingId + palletReleased
Future<ApiResult<PackingOrderResponse>> scanPackPart({...})
ฟิลด์ในคำตอบบอกอะไร
packFinalizedกล่องนี้แพ็กครบแล้วและถูกปิด
trackingIdเลขติดตามที่เพิ่งสร้าง
palletReleasedพาเลทว่างแล้ว (กล่องสุดท้ายบนพาเลท)

สามฟิลด์นี้มีค่าเฉพาะเมื่อสแกนชิ้นสุดท้าย — คำขอเดียวกันจึงตอบได้สองแบบ

packFinalized: json['packFinalized'] ?? false,
trackingId: json['trackingId'],
palletReleased: json['palletReleased'] ?? false,

ค่าเริ่มต้นเป็น false ทั้งคู่ — เป็นค่าเริ่มต้นแบบเข้มงวดตามที่ 17.9 อธิบาย

ถ้าเดาผิดผล
เซิร์ฟเวอร์ปิดกล่องแล้วแต่ไม่ส่งฟิลด์มาแอปคิดว่ายังไม่ปิด → ผู้ใช้อยู่หน้าสินค้าที่แพ็กครบแล้ว

ผู้ใช้จะเห็นว่าทุกอย่างครบแต่ไม่มีอะไรเกิดขึ้น — น่ารำคาญแต่ไม่ทำให้ข้อมูลเสีย

ต่างจาก condition ?? 'FG' ใน 17.9 ที่เดาผิดแล้วของเสียผ่านไปเป็นของดี — ที่นี่เดาผิดแล้วผู้ใช้แค่ติดขัด

แอปจึงสร้างขึ้นเองจากข้อมูลที่มี

ฟิลด์มาจากเชื่อได้แค่ไหน
packingIdเซิร์ฟเวอร์เชื่อได้
trackingIdเซิร์ฟเวอร์เชื่อได้
palletShippedเซิร์ฟเวอร์เชื่อได้
status: 'DONE'แอปเขียนเองสมเหตุสมผล — packFinalized แปลว่าปิดแล้ว
completedAt: DateTime.now()เวลาของเครื่องอาจไม่ตรงกับเซิร์ฟเวอร์
messageแอปเขียนเองสรุปจาก palletReleased
DateTime.now() ตรงนี้ต่างจากกรณีที่ 16.8 เตือน
ที่นั่นเป็นค่าเริ่มต้นเมื่ออ่านค่าไม่ได้ — ทำให้ข้อมูลผิดโดยไม่มีใครรู้
ที่นี่เป็นเวลาที่แอปบันทึกไว้เพื่อแสดงบนหน้าจอทันที ไม่ได้ส่งกลับไปเซิร์ฟเวอร์
ความเสี่ยงคือถ้านาฬิกาเครื่องผิด ผู้ใช้จะเห็นเวลาที่ไม่ตรงกับที่ระบบบันทึก — ซึ่งเป็นเรื่องเล็กเมื่อเทียบกับการเรียงลำดับผิดใน 16.8

ทางที่ตรงกว่าคือให้เซิร์ฟเวอร์ส่งเวลามาด้วย

completedAt: DateTime.tryParse(json['completedAt'] ?? '') ?? DateTime.now(),

ซึ่ง ConfirmPackResponse.fromJson ก็ทำแบบนั้นอยู่แล้ว — แต่เส้นทางนี้ไม่ได้ผ่าน fromJson

4. การยืนยันหลายรายการในรอบเดียว

Future<void> _confirmCollectedPack() async {
  final order = _orderResp;
  if (order == null) return;

  // Part มี S/N → ต้องสแกนครบ remaining ถึงจะ pack ได้
  // Part ไม่มี S/N → กรอกจำนวนเท่าไหร่ก็ pack เท่านั้น (pack บางส่วนได้)
  final readyParts = order.parts
      .where((part) =>
          !part.isDone &&
          part.remaining > 0 &&
          (part.serialRequire
              ? _collectedCountFor(part) == part.remaining
              : _collectedCountFor(part) > 0))
      .toList();

  if (readyParts.isEmpty) {
    showWarningSnackbar(context,
        'กรุณาสแกน S/N หรือระบุจำนวนอย่างน้อย 1 รายการก่อนยืนยัน');
    _serialScanFocus.requestFocus();
    return;
  }

  for (final part in readyParts) {
    await _confirmPart(part, _collectedCountFor(part));
    if (!mounted || _state != _PackState.orderParts) return;
  }
}

เงื่อนไขคัดกรองมีสามข้อ

เงื่อนไขกันอะไร
!part.isDoneสินค้าที่แพ็กครบแล้ว
part.remaining > 0ตาข่ายชั้นสอง เผื่อ isDone ไม่ตรง
กฎตามชนิดสินค้าของที่ยังไม่พร้อม

กฎข้อสามคือหัวใจ

part.serialRequire
    ? _collectedCountFor(part) == part.remaining    // ต้องครบเท่านั้น
    : _collectedCountFor(part) > 0                  // มีเท่าไรก็ได้
สินค้าแพ็กบางส่วนได้ไหมทำไม
มี S/Nไม่ได้ต้องรู้ว่าชิ้นไหนบ้างอยู่ในกล่อง
ไม่มี S/Nได้นับจำนวนอย่างเดียว แบ่งหลายรอบได้
เทียบกับ 17.10 ที่พบว่า LoadToBasketScreen ปล่อยให้โหลดบางส่วนได้แม้สินค้ามี S/N
ที่นั่นปุ่ม “ถัดไป” ตรวจแค่ว่ามี S/N อย่างน้อยหนึ่งตัว
ที่นี่เข้มกว่าและถูกกว่า — และคอมเมนต์สองบรรทัดอธิบายเหตุผลไว้ให้ด้วย

การวนยืนยันทีละรายการมีข้อดีข้อเสีย

วนทีละรายการ (packing)ส่งทีเดียว (picking, 18.14)
จำนวนคำขอเท่ากับจำนวนรายการ1
รู้ว่ารายการไหนล้มเหลวรู้ไม่รู้
ล้มเหลวกลางทางรายการก่อนหน้าถูกบันทึกแล้วไม่มีอะไรถูกบันทึก
เวลาที่ผู้ใช้รอนานกว่าสั้นกว่า

แถวที่สามเป็นทั้งข้อดีและข้อเสีย — งานที่ทำไปแล้วไม่เสีย แต่ระบบอยู่ในสถานะกลางทาง

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
คำขอหนึ่งตอบได้แบบเดียวscanPackPart ตอบสองแบบตาม packFinalized
แอปไม่ควรสร้างข้อมูลขึ้นเองได้ ถ้าไม่ส่งกลับเซิร์ฟเวอร์และมีข้อมูลพอ
วนเรียก API ทีละรายการเป็นการออกแบบที่แย่รู้ว่ารายการไหนล้มเหลว ซึ่งส่งทีเดียวไม่รู้
วนต่อไปเมื่อรายการหนึ่งล้มเหลวดีกว่าหยุดถ้าเป็นปัญหาเน็ต รายการที่เหลือก็จะล้มเหลวเหมือนกัน
ล้างข้อมูลทั้งหมดหลังยืนยันต้องล้างเฉพาะรายการที่ยืนยันไป

8. แบบฝึกหัด

ผู้ใช้แจ้งว่า “กดยืนยันทีเดียวหลายรายการ แล้วเน็ตสะดุด ขึ้น error สามรอบติด กดปิดจนงง แล้วไม่รู้ว่าอันไหนสำเร็จบ้าง”

  1. ไล่ว่าเกิดอะไรขึ้นทีละขั้น
  2. ผู้ใช้ต้องการรู้อะไร
  3. ออกแบบทางแก้ที่ครบ
แนวคำตอบ

ข้อ 1 — ไล่ทีละขั้น

ผู้ใช้สแกนครบ 5 รายการ แล้วกดยืนยัน
  ▼
_confirmCollectedPack → readyParts มี 5 ตัว
  ▼
วนรอบที่ 1: _confirmPart(A) → สำเร็จ → _orderResp อัปเดต
วนรอบที่ 2: _confirmPart(B) → สำเร็จ
วนรอบที่ 3: _confirmPart(C) → เน็ตสะดุด → กล่อง error
              ผู้ใช้กดปิด → return (ไม่บอกว่าล้มเหลว)
              การวนทำต่อ
วนรอบที่ 4: _confirmPart(D) → เน็ตยังสะดุด → กล่อง error อีก
วนรอบที่ 5: _confirmPart(E) → กล่อง error อีก
  ▼
ผู้ใช้กดปิดกล่องสามครั้ง แล้วเห็นรายการที่ A, B เปลี่ยนเป็นครบ
                             ส่วน C, D, E ยังไม่ครบ

ข้อมูลที่ต้องการอยู่บนหน้าจอแล้ว — แต่ผู้ใช้ต้องอ่านรายการทั้งหมดเพื่อหาว่าอันไหนไม่ผ่าน

และมีปัญหาซ้อน: _confirmPart ที่ล้มเหลวไม่ล้าง _collectedSerials ของรายการนั้น (เพราะ return ก่อนถึงบรรทัดล้าง) ซึ่งถูกต้อง — S/N ที่สแกนไว้ยังอยู่ให้กดซ้ำได้

ข้อ 2 — ผู้ใช้ต้องการรู้อะไร

คำถามของผู้ใช้ตอบได้จาก

แถวที่สามสำคัญที่สุด — 7.10 เรียกว่าคำสั่งที่ไม่รู้ผล และเป็นสิ่งที่ผู้ใช้กลัวที่สุด

ที่นี่โชคดีที่ scanPackPart เพิ่ม scannedQty ตามที่ส่งไป ถ้าส่งซ้ำจะเกินและเซิร์ฟเวอร์น่าจะปฏิเสธ — แต่ต้องยืนยันกับทีมหลังบ้าน ไม่ใช่เดา

ข้อ 3 — ทางแก้ที่ครบ

Future<void> _confirmCollectedPack() async {
  final order = _orderResp;
  if (order == null) return;

  final readyParts = order.parts.where((part) => ...).toList();
  if (readyParts.isEmpty) { ... return; }

  final failed = <String>[];
  var doneCount = 0;

  for (final part in readyParts) {
    final ok = await _confirmPart(part, _collectedCountFor(part), silent: true);
    if (!mounted || _state != _PackState.orderParts) return;

    if (ok) {
      doneCount++;
      continue;
    }

    failed.add(part.partId);
    // เน็ตมีปัญหา รายการที่เหลือก็จะล้มเหลวเหมือนกัน — หยุดดีกว่ากดปิดหลายรอบ
    break;
  }

  if (failed.isEmpty) return;

  await showDialog<void>(
    context: context,
    builder: (ctx) => AlertDialog(
      title: const Text('ยืนยันไม่ครบ'),
      content: Column(
        mainAxisSize: MainAxisSize.min,
        crossAxisAlignment: CrossAxisAlignment.start,
        children: [
          Text('สำเร็จ $doneCount จาก ${readyParts.length} รายการ'),
          const SizedBox(height: 8),
          Text('ยังไม่ได้บันทึก: ${failed.join(", ")} '
               'และอีก ${readyParts.length - doneCount - failed.length} รายการ'),
          const SizedBox(height: 12),
          Text(
            'S/N ที่สแกนไว้ยังอยู่ — กดยืนยันซ้ำได้เมื่อสัญญาณกลับมา',
            style: TextStyle(fontSize: 13, color: AppTheme.textGrey(ctx)),
          ),
        ],
      ),
      actions: [
        ElevatedButton(
          onPressed: () => Navigator.pop(ctx),
          child: const Text('เข้าใจแล้ว'),
        ),
      ],
    ),
  );
}
เปลี่ยนอะไรได้อะไร
silent: true ไม่ให้ _confirmPart เด้งกล่องเองไม่ต้องกดปิดหลายรอบ
break เมื่อล้มเหลวไม่ยิงซ้ำทั้งที่รู้ว่าจะล้ม
กล่องเดียวตอนจบสรุปครบในที่เดียว
บอกว่า S/N ยังอยู่ตอบคำถาม “ต้องสแกนใหม่ไหม”

สิ่งที่ยังไม่ได้แก้และต้องคุยกับทีม .NET — คำถาม “กดซ้ำแล้วของจะซ้ำไหม”
ถ้า scanPackPart เพิ่ม scannedQty แบบสะสม การส่งซ้ำจะทำให้เกิน
ถ้าเซิร์ฟเวอร์ตรวจว่า S/N นั้นถูกสแกนไปแล้ว จะปฏิเสธเอง ซึ่งปลอดภัย
ต้องรู้คำตอบก่อนถึงจะเขียนข้อความที่ถูกได้ — ถ้าปลอดภัยให้บอก “กดซ้ำได้เลย” ถ้าไม่ ให้บอก “ตรวจรายการก่อนกดซ้ำ”

9. สรุป

  • scanPackPart ตอบสองแบบ — ปกติ หรือปิดกล่องพร้อมเลขติดตาม
  • สามฟิลด์ที่บอกการปิดกล่องมีค่าเริ่มต้นแบบเข้มงวด เดาผิดแล้วผู้ใช้แค่ติดขัด
  • แอปประกอบ ConfirmPackResponse ขึ้นเองเพราะคำตอบเป็นคนละคลาส
  • DateTime.now() ที่นี่ปลอดภัยกว่าใน 16.8 เพราะไม่ได้ส่งกลับเซิร์ฟเวอร์
  • ล้างเฉพาะสินค้าที่ยืนยันไป ไม่ล้างทั้งหมด — จำเป็นเพราะวนหลายรายการ
  • กฎแพ็กบางส่วน: มี S/N ต้องครบ ไม่มี S/N ได้เท่าที่กรอก
  • วนยืนยันทีละรายการ ทำให้รู้ว่าอันไหนล้มเหลว แต่ระบบอยู่กลางทางได้
  • _confirmPart ไม่คืนผลลัพธ์ ทำให้ลูปวนต่อทั้งที่ล้มเหลว
  • ข้อความในหน้าสรุปบอกสถานการณ์ ทำให้ผู้ใช้เลือกปุ่มถูกโดยไม่ต้องคิด
