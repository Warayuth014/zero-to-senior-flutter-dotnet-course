อย่าอ่าน giant screen จากบรรทัดแรกถึงท้าย: PackingScreen มีมากกว่า 2,000 บรรทัด ให้สร้างแผนที่ state, commands, derived values และ render branches ก่อนอ่าน widget detail

1. Start from enum

_PackState มี scanPallet, packList, orderList, orderParts และ success ค้น switch ที่ render แต่ละ state และ method ที่ assign state เพื่อได้ transition graph ก่อน

2. Group state by role

Infrastructure: API/controllers/focus; remote snapshots: pallet/pack/order/confirm; navigation context: current IDs/state; draft input: selectedPart, serial/qty maps และ expanded rows แยกกลุ่มแล้ว ownership ชัดขึ้น

3. Find command methods

rg -n "Future<void> _|_state =|_api\." packing_screen.dart

เริ่มที่ scan/open/confirm/refresh/reset แล้วค่อยตามไป model และ API อย่าเริ่มจากสี/spacing 1,000 บรรทัดกลางไฟล์

4. Mark pure calculations

_collectedCountFor, _currentPart, remaining และ allDone ควรเป็น pure logic ที่ย้ายออกมาทดสอบได้ ส่วน focus/dialog/snackbar เป็น presentation side effect

5. Pair state with reset

ทุก draft field ต้องตอบว่า reset เมื่อเปิด order, ย้อนกลับ, pack finalized และ reset all ตรงไหน หากหาไม่เจอจะเกิด serial/qty จาก order ก่อนรั่วเข้า request ใหม่

6. Identify duplicate UI

scanner cards, serial tables, status chips และ selection logic คล้าย PickingScreen มาก เป็นสัญญาณให้สกัด shared behavior แต่ต้องเริ่มจาก tests เพื่อไม่เปลี่ยน scanner focus/validation โดยไม่ตั้งใจ

7. Read async hazards

วงกลมทุก await แล้วตรวจ mounted, stale response, loading overlap, sequential mutations และ timeout ambiguity โดยเฉพาะ _confirmCollectedPack ยิงหลาย part ทีละ request

8. Safe reading output

ก่อนแก้ giant screen ต้องมี state graph, data ownership table, API list, reset matrix และ characterization tests อย่างน้อย happy/error/back/retry จากนั้น refactor ทีละ seam ไม่ rewrite ทั้งไฟล์
