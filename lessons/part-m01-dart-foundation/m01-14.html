Exception, Result และ error boundary

Part -1: Dart Foundation for Flutter

Exception เหมาะกับ failure ที่ตัด flow ปกติ ส่วน Result ทำ failure เป็นข้อมูลที่ caller ต้องเปิดดู สองโปรเจกต์ใช้คนละแนวและเราต้องอ่านข้อแลกเปลี่ยนให้ออก

1. throw, catch, finally และ stack trace

try {
  final task = await repository.load(id);
  show(task);
} on ApiException catch (error, stackTrace) {
  log(error.message, stackTrace: stackTrace);
  showError(error.message);
} finally {
  setLoading(false);
}

จับเฉพาะ error ที่ชั้นนี้แปลงเป็นการตัดสินใจได้ finally เหมาะคืน loading/resource หาก rethrow ใช้ rethrow เพื่อรักษา stack เดิม ไม่ใช้ throw error โดยไม่จำเป็น

2. Typed exception

class ApiException implements Exception {
  const ApiException(this.message, {this.statusCode});
  final String message;
  final int? statusCode;
}

wms_absolute_mobile/core/api_client.dart ใช้แนวนี้: client decode และ throw; repository ปล่อยหรือแปลง; screen/store catch ที่ boundary ของ user action ข้อดีคือ happy path ตรง ข้อเสียคือ caller ต้องรู้ว่า operation throw อะไร

3. Result type

class ApiResult<T> {
  ApiResult.success(this.data) : success = true, error = null;
  ApiResult.error(this.error) : success = false, data = null;
  final bool success;
  final T? data;
  final String? error;
}

wmsapp/services/api_service.dart ใช้แนวนี้ ทุก call site ตรวจ success ข้อดีคือ failure เห็นใน return type ข้อเสียของโครง bool+nullable คือ compiler ยังยอมให้เขียน data! ผิด branch ได้ Sealed success/failure จะบังคับได้มากกว่า

4. Error boundary ตามชั้น

  1. transport แยก timeout/socket/non-2xx/malformed body
  2. repository แปลง payload เป็น domain หรือโยน contract error
  3. store/action แปลง failure เป็น state และตัดสิน retry/rollback
  4. widget แสดงข้อความ/action โดยไม่ parse exception string

อย่า catch ทุกอย่างแล้วคืน list ว่าง เพราะผู้ใช้จะแยก “ไม่มีงาน” จาก “server ล่ม” ไม่ได้

5. ไม่เปิดข้อมูลลับ

ข้อความ UI ควร actionable แต่ไม่แสดง token, password, SQL หรือ stack trace เก็บ technical context ใน log ที่เหมาะสมและ sanitize request header/body ก่อน log

6. แบบฝึกหัด

ออกแบบ load tasks ให้แยก success-empty, 401, timeout และ malformed JSON แล้วบอกแต่ละกรณี UI ทำอะไร

แนวคำตอบ
  • empty: แสดง empty state
  • 401: clear session/ไป login
  • timeout: error พร้อม Retry โดยไม่ทำรายการซ้ำ
  • malformed: generic contract error + log correlation detail

7. จุดพลาด

อย่าผสม Result และ exception แบบไร้กติกาจน caller ต้องทั้งตรวจ bool และ try/catch เลือก policy ต่อ boundary แล้ว document ว่า failure ใดเป็น data และ failure ใด throw

8. สรุป

Failure ที่ดีต้องรักษาสาเหตุ, มี owner ที่แปลงเป็น state, ไม่ถูกกลืนเป็นข้อมูลปกติ และไม่เปิดความลับต่อผู้ใช้
