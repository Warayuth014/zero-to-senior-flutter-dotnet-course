Sound null safety แยก “มีค่า T” จาก “อาจไม่มี T?” ตั้งแต่ type system เป้าหมายไม่ใช่กำจัด null แต่ทำให้ทุก absence ถูกออกแบบและตรวจใกล้จุดกำเนิด

1. เครื่องมือหลัก

String? serial;
final display = serial?.trim().isNotEmpty == true ? serial! : 'ไม่มี Serial';
final quantity = int.tryParse(raw) ?? 0;

void submit(String? barcode) {
  if (barcode == null || barcode.trim().isEmpty) return;
  print(barcode.toUpperCase()); // promoted เป็น String
}
  • ?. เรียกเมื่อไม่ null
  • ?? ใช้ fallback เมื่อ null
  • ??= assign เมื่อเดิม null
  • ! assertion ว่าไม่ null—ผิดแล้วพัง runtime

2. Promotion และเหตุที่บางครั้ง promote ไม่ได้

local final variable promote ได้ง่าย ส่วน mutable field อาจถูกเปลี่ยนระหว่างตรวจและใช้ โดยเฉพาะมี getter override/async boundary ให้ copy เป็น local:

final session = auth.session;
if (session == null) return;
useToken(session.token);

นี่ชัดกว่ากระจาย auth.session! หลายจุดและบันทึก snapshot ที่กำลังใช้งาน

3. Nullable ไม่เท่ากับ error

T? เหมาะเมื่อ “ไม่พบ/ยังไม่มี” เป็นผลปกติ เช่น suggested pallet ไม่มี แต่ถ้าการขาดค่านั้นแปลว่า payload เสียหรือ request ล้มเหลว ให้คืน Result/throw typed exception ไม่ควรคืน null แล้วทำให้ caller เดาสาเหตุ

4. Required + nullable

Widget buildRow({required String? subtitle}) { /* ... */ }

ความหมายคือ caller ต้องตัดสินใจส่ง argument แต่ value อาจ null ใช้ได้เมื่อ “explicit absence” สำคัญ หากไม่มีเหตุผลมักควรเป็น String subtitle หรือ optional parameter ที่มี default

5. ตัวอย่างจริง

  • ConnectionProfile.fromJson(Object? raw) คืน null เมื่อ saved row เสียเพื่อไม่ให้หนึ่งแถวทำลายทุก profile
  • AuthRepository.session? แทนสถานะก่อน/หลัง login
  • ApiResult<T> มี data? และ error? แต่ constructor พยายามรักษาว่าควรมีอย่างใดอย่างหนึ่ง—บท architecture จะปรับให้ type บังคับ invariant ได้แข็งขึ้น

6. หลีกเลี่ยง null cascade

ถ้า DTO ทุก field nullable แล้ว UI ต้อง ?. ?? '' ทุกบรรทัด แปลว่า boundary ไม่ได้ทำงาน แยก required/optional ตาม contract, validate required fields ใน parser และใช้ default เฉพาะค่าที่ domain ยอมรับจริง

7. แบบฝึกหัด

API คืน palletId ที่อาจไม่พบ ออกแบบ signature และ UI ทั้งกรณีไม่พบกับ payload ผิด

แนวคำตอบ

Future<Pallet?> findPallet(String id) ใช้ null สำหรับ 404 ที่เป็นผลปกติ; malformed JSON/500 ให้ throw ApiException หรือคืน failure result UI จึงแยก “ไม่พบ pallet” จาก “ระบบผิดพลาด” ได้

8. จุดพลาด

! ไม่ได้แก้ null มันเพียงสั่ง compiler ให้เชื่อเรา ใช้หลัง invariant ที่พิสูจน์ได้ใกล้ ๆ เท่านั้น ถ้าใช้เพราะ “น่าจะมี” ให้เปลี่ยน flow/type
