1. ปัญหาที่บทนี้แก้

null แปลว่า “ไม่มีค่า” ซึ่งเป็นสถานะที่เกิดขึ้นจริงตลอดเวลาในงานคลัง — พาเลทที่ยังไม่ถูกจัดเก็บยังไม่มีช่องเก็บ ผู้ใช้ที่ยังไม่ล็อกอินยังไม่มีชื่อ สินค้าที่ยังไม่ตรวจยังไม่มีผลตรวจ

ในภาษาเก่า ๆ ปัญหาคือ ทุกตัวแปรเป็น null ได้หมด โดยไม่มีอะไรเตือน จึงเกิดข้อผิดพลาดที่เรียกว่า null pointer ซึ่งเป็นสาเหตุของแอปพังอันดับหนึ่งมานานหลายสิบปี

Dart แก้ปัญหานี้ด้วยการแยกให้ชัดตั้งแต่ชนิด: String คือ “มีข้อความแน่นอน” ส่วน String? คือ “อาจมีหรือไม่มีก็ได้” และบังคับให้เราตรวจก่อนใช้เสมอ

5. Type promotion: วิธีที่ถูกต้องที่สุด

final location = target.location;   // ชนิด String?
if (location != null) {
  print(location.toUpperCase());    // ตรงนี้เป็น String แล้ว ไม่ต้องใส่ ! เลย
}

หลังผ่าน if Dart รู้เองว่าในบล็อกนั้นค่าไม่ใช่ null แน่นอน จึงยอมให้เรียก method ได้ตามปกติ นี่คือทางที่ควรใช้เป็นค่าเริ่มต้นเสมอ เพราะมันปลอดภัยโดยไม่มีต้นทุนอะไรเลย

แต่บางครั้ง promotion ทำงานไม่ได้ และเป็นจุดที่คนใหม่งงมาก

class ScanBox {
  String? code;   // field ที่เปลี่ยนค่าได้
}

final box = ScanBox()..code = 'PAL-1003';
if (box.code != null) {
  // box.code.toUpperCase();   // error! ทั้งที่เพิ่งตรวจไปเอง
  final local = box.code!;      // ดึงลงตัวแปร local ก่อน
  print(local.toUpperCase());   // แล้วค่อยใช้
}

เหตุผล: box.code เป็น field ที่เปลี่ยนค่าได้ ระหว่างบรรทัดที่ตรวจกับบรรทัดที่ใช้ อาจมีโค้ดอื่นเปลี่ยนมันเป็น null ได้ Dart จึงไม่กล้ารับประกัน

วิธีแก้ที่ดีที่สุด: คัดลอกลงตัวแปร final ในเครื่องก่อนเสมอ เพราะตัวแปร local ที่เป็น final ไม่มีใครแก้ได้ Dart จึง promote ให้

final code = box.code;      // สำเนาที่ไม่มีใครแก้ได้
if (code == null) return;
print(code.toUpperCase());  // ปลอดภัยและไม่ต้องใช้ ! เลย

6. เมื่อไหร่ที่ห้ามใช้ !

String? empty;
print(empty!.length);   // TypeError: Null check operator used on a null value
! ไม่ได้ทำให้ค่าไม่เป็น null — มันแค่สั่งให้ Dart หยุดเตือน ถ้าเราคิดผิด โปรแกรมจะพังตอนผู้ใช้กำลังใช้งานอยู่ ซึ่งแย่กว่าการเจอ error ตอน compile มาก
สถานการณ์ใช้ ! ได้ไหม
เพิ่งตรวจในบรรทัดก่อนหน้า และค่าเป็น field ที่เปลี่ยนได้ได้ แต่ควรคัดลอกลง local แทน
“น่าจะมีค่านะ” / “ปกติมันไม่ null หรอก”ห้ามเด็ดขาด
ใส่เพื่อให้ analyzer หยุดขึ้นเส้นแดงห้ามเด็ดขาด
ค่ามาจาก API ที่เราควบคุมไม่ได้ห้าม — ต้องตรวจจริง

ถ้าพบว่าตัวเองอยากใช้ ! บ่อย ๆ แสดงว่าปัญหาอยู่ที่การออกแบบชนิด ไม่ใช่ที่ตัวโค้ดตรงนั้น ให้ย้อนไปถามว่า “ค่านี้ควรเป็น nullable จริงหรือเปล่า”

8. nullable ไม่ใช่ทางเดียวในการบอกว่า “ไม่มี”

เมื่อฟังก์ชันคืน null ผู้เรียกจะไม่รู้ว่าเพราะอะไร ให้แยกสองกรณีนี้ออกจากกันตั้งแต่ออกแบบ

สถานการณ์ควรทำอย่างไรเหตุผล
ค้นหาแล้วไม่พบ — เป็นผลลัพธ์ปกติคืน T?ผู้เรียกแค่ต้องแสดง “ไม่พบข้อมูล”
เชื่อมต่อไม่ได้ / ข้อมูลเสีย — เป็นความผิดปกติโยน exception หรือคืนผลลัพธ์ที่บอกเหตุผลผู้เรียกต้องแสดงข้อความและให้ลองใหม่ได้

ถ้าใช้ null กับทั้งสองกรณี หน้าจอจะแสดง “ไม่พบพาเลท” ทั้งที่จริง ๆ แล้วเน็ตหลุด ซึ่งทำให้พนักงานเดินไปหาของผิดที่ เรื่องนี้จะกลับมาอีกครั้งใน D1.14 และ Part 7

Null check operator used on a null valueใช้ ! กับค่าที่เป็น null จริงเปลี่ยนไปตรวจด้วย if แล้วใช้ promotion
The property 'length' can't be unconditionally accessedใช้ค่า nullable โดยยังไม่ตรวจใช้ ?. หรือตรวจด้วย if ก่อน
ตรวจ != null แล้วยัง error อยู่เป็น field ที่เปลี่ยนได้ จึง promote ไม่ได้คัดลอกลงตัวแปร final ในเครื่องก่อน
โค้ดเต็มไปด้วย ?. และ ?? '' ทุกบรรทัดปล่อยให้ทุก field ของ model เป็น nullableตรวจข้อมูลที่ชั้นแปลง JSON แล้วให้ model มีค่าแน่นอน (D1.19)
แสดง “ไม่พบข้อมูล” ทั้งที่เน็ตหลุดใช้ null แทนทั้ง “ไม่พบ” และ “ผิดพลาด”แยกสองกรณีตามตารางหัวข้อ 8
ใช้ late ทุกที่เพื่อเลี่ยง ?ย้าย error ไป runtime แทนที่จะแก้จริงยอมรับว่าค่าอาจไม่มี แล้วใช้ nullable (ทบทวน D1.3)

10. แบบฝึกหัด

ระบบต้องแสดงข้อมูลผู้รับผิดชอบพาเลทบนหน้าจอ โดยมีเงื่อนไขดังนี้

  1. พาเลทอาจยังไม่มีผู้รับผิดชอบ
  2. ถ้ามี ให้แสดงชื่อเป็นตัวพิมพ์ใหญ่
  3. ถ้าไม่มี ให้แสดง รอมอบหมาย
  4. ถ้ามีแต่เป็นข้อความว่างหรือมีแต่ช่องว่าง ให้ถือว่าไม่มี

จงเขียนฟังก์ชัน ownerLabel โดย ห้ามใช้เครื่องหมาย ! เลย

ดูแนวคำตอบและเหตุผล
String ownerLabel(String? owner) {
  final name = owner?.trim();
  if (name == null || name.isEmpty) return 'รอมอบหมาย';
  return name.toUpperCase();
}

void main() {
  for (final input in <String?>[null, '', '   ', 'somchai', ' malee ']) {
    print('${input == null ? 'null' : '"$input"'} -> ${ownerLabel(input)}');
  }
}
null -> รอมอบหมาย
"" -> รอมอบหมาย
"   " -> รอมอบหมาย
"somchai" -> SOMCHAI
" malee " -> MALEE

ทำไมเขียน owner?.trim() ก่อน: เพราะมันรวมสองงานไว้ในบรรทัดเดียว — ถ้าเป็น null ก็ได้ null ต่อไป ถ้ามีค่าก็ตัดช่องว่างให้เลย จากนั้นเหลือเงื่อนไขเดียวที่ต้องตรวจ

ทำไมต้องเก็บลงตัวแปร name: เพราะเมื่อเป็นตัวแปร final ในเครื่องแล้ว Dart จะ promote ให้หลัง if ทำให้บรรทัดสุดท้ายเรียก toUpperCase() ได้โดยไม่ต้องใช้ ! — ถ้าเขียน owner?.trim() ซ้ำในบรรทัดล่าง จะ promote ไม่ได้และต้องพึ่ง ! ทันที

บทเรียนที่สำคัญที่สุด: การเขียนโดยไม่ใช้ ! ได้เลย ไม่ใช่เพราะเก่ง แต่เพราะจัด ลำดับ การตรวจให้ถูก — ตรวจให้เสร็จก่อน แล้วค่อยใช้ ในโค้ดจริงถ้าคุณต้องใช้ ! ให้ลองจัดลำดับใหม่ก่อนเสมอ

ลองต่อ: เปลี่ยนโจทย์เป็น “ถ้าไม่มีผู้รับผิดชอบและพาเลทอยู่ในโซนเร่งด่วน ให้แสดง ต้องมอบหมายด่วน” แล้วสังเกตว่าคุณต้องรับ parameter เพิ่มโดยที่โครงเดิมยังใช้ได้

11. สรุปท้ายบท

  • T คือมีค่าแน่นอน ส่วน T? คืออาจไม่มี — Dart บังคับให้ตรวจก่อนใช้
  • ?? ใส่ค่าสำรอง, ?. เรียกต่อเมื่อมีค่า, ??= ใส่เมื่อยังว่าง
  • ตรวจด้วย if แล้วให้ Dart promote ให้ คือทางที่ปลอดภัยที่สุด
  • field ที่เปลี่ยนค่าได้ promote ไม่ได้ ให้คัดลอกลงตัวแปร final ในเครื่องก่อน
  • ! ไม่ได้แก้ปัญหา แค่ปิดปาก compiler — ใช้เมื่อพิสูจน์ได้จริงเท่านั้น
  • อย่าใช้ค่าวิเศษอย่าง -1 หรือ '' แทน “ไม่มีค่า”
  • แยก “ไม่พบข้อมูล” ออกจาก “ระบบผิดพลาด” ตั้งแต่ออกแบบ
