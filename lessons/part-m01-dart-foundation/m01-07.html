1. ปัญหาที่บทนี้แก้

ใน D1.6 เราเขียน method receive ที่ปฏิเสธจำนวนติดลบ แต่กฎนั้นยังหลบเลี่ยงได้ง่ายมาก

pallet.receive(-5);      // ถูกปฏิเสธ ตามที่ตั้งใจ
pallet.quantity = -5;    // ผ่านฉลุย! กฎที่เขียนไว้ไร้ความหมาย

ถ้าใครก็แก้ field ได้โดยตรง กฎทั้งหมดที่เราเขียนใน method ก็เป็นแค่ข้อเสนอแนะ บทนี้คือวิธีทำให้กฎเป็นกฎจริง ๆ

3. Mental model: เคาน์เตอร์รับของ

คิดถึงห้องเก็บของที่มีเคาน์เตอร์กั้น

  • ของในห้อง = field ที่ขึ้นต้นด้วย _ — คนนอกเข้าไปหยิบเองไม่ได้
  • ช่องยื่นของเข้า = method ที่ตรวจของก่อนรับ
  • ช่องดูรายการ = getter ที่ให้ดูได้แต่แก้ไม่ได้

ประโยชน์ที่แท้จริงไม่ใช่ “ความลับ” แต่คือ ทุกการเปลี่ยนแปลงต้องผ่านจุดที่เราตรวจสอบได้ เมื่อเกิดข้อมูลผิด เรารู้ทันทีว่าต้องไปดูโค้ดตรงไหน

ประโยคเดียวที่ต้องจำ: ยิ่งมีทางเข้าถึงข้อมูลน้อย ยิ่งหาสาเหตุของบั๊กได้เร็ว

4. underscore = private ต่อ “ไฟล์” ไม่ใช่ต่อ class

class ScanSession {
  final List<String> _scanned = <String>[];   // คนนอกไฟล์นี้มองไม่เห็นเลย
  bool _closed = false;
}
จุดที่ต่างจากภาษาอื่นอย่าง C# หรือ Java: ใน Dart _ ทำให้ private ต่อ ไฟล์ (เรียกว่า library) ไม่ใช่ต่อ class ดังนั้นสอง class ที่อยู่ไฟล์เดียวกันจะเห็นของ private ของกันและกัน — ตั้งใจออกแบบมาแบบนี้ และเราจะใช้ประโยชน์จากมันใน D1.18

5. Getter: ทางอ่านที่ปลอดภัย

int get count => _scanned.length;
bool get isEmpty => _scanned.isEmpty;
List<String> get scanned => List.unmodifiable(_scanned);

เรียกใช้เหมือน field ไม่ต้องใส่วงเล็บ

print(session.count);     // ไม่ใช่ session.count()
print(session.isEmpty);

สังเกต scanned ที่คืน List.unmodifiable — ถ้าคืน _scanned ตรง ๆ คนนอกจะ add เข้ามาได้ทันที ซึ่งข้ามกฎทั้งหมดที่เราเขียนไว้ใน method add

6. เมื่อไหร่ควรใช้ getter แทนการเก็บ field

กฎง่าย ๆ: ถ้าคำนวณจากค่าอื่นได้ อย่าเก็บซ้ำ

เก็บเป็น fieldคำนวณด้วย getter
ตัวอย่างint _count = 0;int get count => _scanned.length;
ความเสี่ยงลืมอัปเดตแล้วค่าไม่ตรงกับความจริงไม่มีทางไม่ตรง เพราะคำนวณสด
ความเร็วเร็วกว่าเล็กน้อยช้ากว่าเล็กน้อย (แทบไม่รู้สึก)
ควรเลือกเมื่อคำนวณแพงมากจริง ๆ และวัดแล้วเกือบทุกกรณี
สิ่งที่ getter ไม่ควรทำ: อย่าให้ getter มีผลข้างเคียง เช่น ยิง API เปลี่ยนค่าอื่น หรือโยน error แบบไม่คาดคิด เพราะคนอ่านโค้ดเห็น session.count แล้วคิดว่าเป็นการอ่านค่าธรรมดา ถ้างานหนักหรือเป็นงานที่ต้องรอ ให้ทำเป็น method ที่มีวงเล็บเพื่อส่งสัญญาณว่า “นี่มีค่าใช้จ่าย”

7. Setter: ทางเขียนที่มีเงื่อนไข

bool get closed => _closed;

set closed(bool value) {
  if (_closed && !value) {
    throw StateError('ปิดรอบไปแล้ว เปิดซ้ำไม่ได้');
  }
  _closed = value;
}

ใช้งานเหมือนกำหนดค่าให้ field ปกติ แต่มีการตรวจสอบซ่อนอยู่

session.closed = true;    // ผ่าน setter จึงตรวจกฎให้อัตโนมัติ

ในทางปฏิบัติ setter ถูกใช้น้อยกว่า method ที่ตั้งชื่อชัด ๆ เพราะการเปลี่ยนสถานะสำคัญมักมีความหมายมากกว่าแค่ “ใส่ค่า” เช่น closeSession() อ่านแล้วเข้าใจกว่า closed = true แต่ควรรู้จักไว้เพราะจะเจอในโค้ดของคนอื่น

8. รวมร่าง: class ที่ปกป้องกฎของตัวเองได้

void add(String code) {
  if (_closed) {
    throw StateError('รอบนี้ปิดแล้ว สแกนเพิ่มไม่ได้');
  }
  final normalized = code.trim().toUpperCase();
  if (normalized.isEmpty || _scanned.contains(normalized)) return;
  _scanned.add(normalized);
}

ลองไล่ผลลัพธ์จาก lab: เราสแกน 4 ครั้งด้วย 'pal-1001', ' PAL-1001 ', 'PAL-1002' และ ' ' แต่ได้ผลเพียง 2 รายการ

scanned = [PAL-1001, PAL-1002]
count   = 2

เพราะ add จัดรูปแบบข้อความ ตัดตัวซ้ำ และปฏิเสธค่าว่างให้ทั้งหมด — โดยที่คนเรียกไม่ต้องรู้กฎเหล่านี้เลย นี่คือหน้าตาของ class ที่ออกแบบดี

9. Extension: เพิ่มมุมมองโดยไม่แก้ต้นฉบับ

บางครั้งเราอยากเพิ่มความสะดวกให้ชนิดที่มีอยู่แล้ว โดยไม่อยากไปแก้ class ต้นทาง (หรือแก้ไม่ได้เพราะเป็นของ Dart เอง)

extension ScanSessionSummary on ScanSession {
  String get summary => '$operator สแกนแล้ว $count รายการ';
}

print(session.summary);   // สมชาย สแกนแล้ว 2 รายการ

extension เพิ่มได้เฉพาะ getter และ method — เพิ่ม field ใหม่ไม่ได้ ซึ่งเป็นข้อจำกัดที่ดี เพราะมันบังคับให้ส่วนที่เพิ่มเข้ามาเป็นเพียง “มุมมองใหม่ของข้อมูลเดิม” ไม่ใช่สถานะที่ซ่อนอยู่

10. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
คนนอก add เข้า list ของเราได้ ทั้งที่เป็น private fieldgetter คืน list ตัวจริงออกไปคืน List.unmodifiable(...) หรือสำเนา [..._list]
Unsupported operation: Cannot add to an unmodifiable listเผลอเรียก add บน list ที่เราตั้งใจล็อกไว้เรียกผ่าน method ของ class แทน — นั่นคือเจตนาของโค้ด
ค่า count ไม่ตรงกับจำนวนรายการจริงเก็บ _count เป็น field แล้วลืมอัปเดตบางเส้นทางเปลี่ยนเป็น getter ที่คำนวณจาก _scanned.length
เรียก session.count() แล้ว errorgetter ไม่ต้องใส่วงเล็บเขียน session.count
class อื่นในไฟล์เดียวกันแก้ _field ได้เข้าใจว่า _ เป็น private ต่อ classถ้าอยากกันจริง ให้แยกคนละไฟล์ (D1.18)
getter ทำงานช้าหรือค้างใส่งานหนัก/งานเครือข่ายไว้ใน getterย้ายไปเป็น method ที่คืน Future (D1.15)

11. แบบฝึกหัด

ปรับปรุง StorageBin จาก D1.6 ให้ปกป้องกฎของตัวเองได้จริง

  1. ทำให้คนนอกแก้ used ตรง ๆ ไม่ได้
  2. เปิดให้อ่านจำนวนที่ใช้ไป จำนวนที่เหลือ และสถานะเต็มหรือยัง
  3. ห้ามเก็บ “จำนวนที่เหลือ” เป็น field
  4. เพิ่ม method take(int amount) ที่ปฏิเสธเมื่อของไม่พอ
ดูแนวคำตอบและเหตุผล
class StorageBin {
  StorageBin({required this.code, required this.capacity});

  final String code;
  final int capacity;
  int _used = 0;

  int get used => _used;
  int get remaining => capacity - _used;   // คำนวณสด ไม่เก็บซ้ำ
  bool get isFull => remaining == 0;

  bool put(int amount) {
    if (amount <= 0 || amount > remaining) return false;
    _used += amount;
    return true;
  }

  bool take(int amount) {
    if (amount <= 0 || amount > _used) return false;
    _used -= amount;
    return true;
  }

  @override
  String toString() => '$code [$_used/$capacity]';
}

ทำไม remaining ต้องเป็น getter: ถ้าเก็บเป็น field เราจะต้องจำอัปเดตมันทั้งใน put และ take วันหนึ่งจะมี method ที่สามที่ลืมอัปเดต แล้วเกิดสถานะที่ used + remaining != capacity ซึ่งเป็นไปไม่ได้ในโลกจริงแต่เป็นไปได้ในโค้ด — บั๊กแบบนี้หาสาเหตุยากมากเพราะเลขดูสมเหตุสมผลจนกว่าจะเอามาบวกกัน

ทำไม put เช็คด้วย remaining: อ่านแล้วตรงกับภาษาคนว่า “ใส่ได้ไม่เกินที่เหลือ” ชัดกว่าการเขียน _used + amount > capacity

ลองต่อ: ลองเรียก bin.used = 99 ดู — analyzer จะปฏิเสธทันทีเพราะ getter อย่างเดียวไม่มี setter นั่นคือเป้าหมายของบทนี้

12. สรุปท้ายบท

  • _ ทำให้ชื่อเป็น private ต่อไฟล์ ไม่ใช่ต่อ class
  • ทุกการเปลี่ยนข้อมูลควรผ่าน method ที่ตรวจกฎได้ที่เดียว
  • getter คืนค่าที่คำนวณสด และไม่ควรมีผลข้างเคียง
  • อย่าเก็บค่าที่คำนวณจากค่าอื่นได้ ให้ใช้ getter แทน
  • คืน collection ออกนอก class ให้คืนแบบแก้ไม่ได้เสมอ
  • extension เพิ่มมุมมองใหม่ได้โดยไม่แตะต้นฉบับ
