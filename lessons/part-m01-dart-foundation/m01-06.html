1. ปัญหาที่บทนี้แก้

ตอนนี้ถ้าจะเก็บข้อมูลพาเลทหนึ่งใบ เราต้องใช้ตัวแปรสามตัวลอย ๆ

final code = 'PAL-1001';
final location = 'A-01-02';
var quantity = 12;

พอมีสองใบก็ต้องเป็นหกตัวแปร และไม่มีอะไรผูกไว้ว่าสามตัวไหนเป็นของใบเดียวกัน เมื่อส่งเข้าฟังก์ชันก็ต้องส่งทีละสามค่าและมีโอกาสสลับกัน

class คือวิธีบอก Dart ว่า “ข้อมูลชุดนี้กับพฤติกรรมชุดนี้อยู่ด้วยกัน” แล้วเรียกมันเป็นสิ่งเดียว

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมายเปรียบเทียบ
classแบบพิมพ์เขียวแบบแปลนบ้าน
object / instanceของจริงที่สร้างจากแบบบ้านที่สร้างเสร็จแล้วหนึ่งหลัง
fieldข้อมูลที่ object เก็บไว้สีบ้าน จำนวนห้อง
methodสิ่งที่ object ทำได้เปิดไฟ ปิดประตู
constructorขั้นตอนสร้าง objectวันที่สร้างบ้านเสร็จและส่งมอบ
thisตัว object ที่กำลังทำงานอยู่“บ้านหลังนี้”
แบบแปลนเขียนครั้งเดียว แต่สร้างบ้านจากแบบเดียวกันได้ไม่จำกัด — class เขียนครั้งเดียว สร้าง object ได้ไม่จำกัดเช่นกัน

3. Mental model: แบบพิมพ์เขียวกับของจริง

class Pallet {              // แบบพิมพ์เขียว เขียนครั้งเดียว
  Pallet({
    required this.code,
    required this.location,
    this.quantity = 0,
  });

  final String code;        // field: ข้อมูลที่ทุกใบต้องมี
  final String location;
  int quantity;             // ไม่ใส่ final เพราะจำนวนเปลี่ยนได้

  void receive(int amount) {   // method: สิ่งที่พาเลททำได้
    if (amount <= 0) return;
    quantity += amount;
  }
}

final a = Pallet(code: 'PAL-1001', location: 'A-01-02', quantity: 10); // ของจริงใบที่ 1
final b = Pallet(code: 'PAL-1002', location: 'B-03-01');              // ของจริงใบที่ 2

this.code ในวงเล็บ constructor เป็นทางลัดที่แปลว่า “รับค่าเข้ามาแล้วเก็บลง field ชื่อ code ให้เลย” ถ้าไม่มีทางลัดนี้เราต้องเขียนยาวกว่านี้สองเท่า

@override
String toString() => 'Pallet($code @ $location, $quantity ชิ้น)';

@override คือป้ายบอก Dart ว่า “ตั้งใจเขียนทับของที่มีอยู่แล้ว” ถ้าสะกดชื่อผิด Dart จะเตือนทันที ถ้าไม่เขียนทับ print(a) จะได้ข้อความไร้ประโยชน์อย่าง Instance of 'Pallet'

5. Constructor สามแบบและใช้ตอนไหน

แบบหน้าตาใช้เมื่อ
constructor หลักPallet({required this.code, ...})ทางเข้าปกติ มีข้อมูลครบอยู่แล้ว
named constructorPallet.empty(String code)ทางเข้าเพิ่มเติมที่มีความหมายต่างออกไป
factory constructorfactory Pallet.fromScan(String raw)ต้องตัดสินใจหรือแปลงข้อมูลก่อนว่าจะสร้าง object แบบไหน
// named: เรียกต่อไปยัง constructor หลักด้วย : this(...)
Pallet.empty(String code) : this(code: code, location: 'ยังไม่จัดเก็บ');

// factory: มีตรรกะได้ และเลือกได้ว่าจะคืนอะไร
factory Pallet.fromScan(String rawText) {
  final parts = rawText.split('|');
  if (parts.length < 3) {
    return Pallet.empty(parts.first);   // ข้อมูลไม่ครบ
  }
  return Pallet(
    code: parts[0],
    location: parts[1],
    quantity: int.tryParse(parts[2]) ?? 0,
  );
}

ความต่างที่สำคัญ: constructor ปกติ ต้อง สร้าง object ใหม่เสมอ ส่วน factory จะคืน object ที่มีอยู่แล้ว คืน object ชนิดลูก หรือเลือกเส้นทางตามข้อมูลก็ได้ — จึงเหมาะกับการ “แปลงข้อมูลดิบเป็นสิ่งของ” ซึ่งเราจะใช้หนักมากตอนแปลง JSON จาก API ใน D1.19

6. Method: พฤติกรรมที่ปกป้องข้อมูลของตัวเอง

void receive(int amount) {
  if (amount <= 0) return;   // ปฏิเสธค่าที่ไม่สมเหตุสมผล
  quantity += amount;
}

ประโยชน์คือกฎ “จำนวนที่รับต้องมากกว่าศูนย์” ถูกเก็บไว้ ที่เดียว ใครเรียกก็ได้กฎเดียวกัน ต่างจากการเขียน a.quantity += x กระจายทั่วโปรแกรม ซึ่งวันหนึ่งจะมีจุดที่ลืมตรวจ

นี่คือแก่นของการออกแบบ class ที่ดี: ข้อมูลกับกฎที่คุ้มครองข้อมูลนั้นต้องอยู่ด้วยกัน เราจะขยายเรื่องนี้ต่อใน D1.7

7. object สองตัวที่ค่าเท่ากัน ยังเป็นคนละตัว

final a = Pallet(code: 'PAL-1001', location: 'A-01-02', quantity: 15);
final c = Pallet(code: 'PAL-1001', location: 'A-01-02', quantity: 15);

print(a == c);              // false
print(a.code == c.code);    // true
เข้าใจผิดที่พบบ่อย: == บน class ที่เราเขียนเองจะเทียบว่า “เป็นวัตถุชิ้นเดียวกันหรือเปล่า” ไม่ใช่ “ข้อมูลเหมือนกันหรือเปล่า” — จึงได้ false ทั้งที่ค่าทุกตัวตรงกัน อาการนี้ทำให้ค้นของใน List ไม่เจอทั้งที่มั่นใจว่ามี

มีสามทางแก้ ซึ่งจะเรียนตามลำดับในบทถัด ๆ ไป

ทางแก้เรียนที่เหมาะกับ
เทียบด้วย field ที่เป็นรหัส เช่น a.code == c.codeใช้ได้ตั้งแต่วันนี้กรณีง่ายที่มีรหัสไม่ซ้ำอยู่แล้ว
ใช้ record ซึ่งเทียบด้วยค่าให้เองD1.12ข้อมูลชั่วคราวที่ไม่ต้องมี method
ให้เครื่องมือสร้างโค้ดเทียบค่าให้ (freezed)Part 30model จริงในแอปที่ต้องเทียบบ่อย

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
The parameter 'code' can't have a value of 'null'ลืม required หน้า named parameter ที่ไม่มีค่าเริ่มต้นเติม required หรือใส่ค่าเริ่มต้น
'quantity' can't be used as a setter because it's finalประกาศ field เป็น final แล้วพยายามแก้ทีหลังตัดสินใจว่าค่านี้เปลี่ยนได้จริงไหม ถ้าใช่ให้เอา final ออก
print(object) ได้ Instance of 'Pallet'ยังไม่ได้เขียน toString()เขียน @override String toString()
== คืน false ทั้งที่ค่าเท่ากันDart เทียบด้วยตัวตน ไม่ใช่ค่าเทียบด้วย field ที่เป็นรหัส หรือใช้เครื่องมือใน Part 30
เขียน Pallet.fromScan เป็น constructor ปกติแล้วมี if ข้างในconstructor ปกติเลือกไม่ได้ว่าจะคืนอะไรเติมคำว่า factory นำหน้า

9. แบบฝึกหัด

สร้าง class StorageBin ที่

  1. เก็บรหัสช่อง (String) และความจุสูงสุด (int) ซึ่งทั้งคู่เปลี่ยนไม่ได้หลังสร้าง
  2. เก็บจำนวนที่วางอยู่จริง ซึ่งเปลี่ยนได้ เริ่มต้นที่ 0
  3. มี method put(int amount) ที่ปฏิเสธถ้าใส่แล้วเกินความจุ และคืน bool ว่าใส่สำเร็จหรือไม่
  4. มี named constructor StorageBin.small(String code) ที่กำหนดความจุเป็น 10
  5. พิมพ์ออกมาอ่านได้ว่า A-01-02 [3/10]
ดูแนวคำตอบและเหตุผล
class StorageBin {
  StorageBin({required this.code, required this.capacity});

  StorageBin.small(String code) : this(code: code, capacity: 10);

  final String code;
  final int capacity;
  int used = 0;

  bool put(int amount) {
    if (amount <= 0) return false;
    if (used + amount > capacity) return false;
    used += amount;
    return true;
  }

  @override
  String toString() => '$code [$used/$capacity]';
}

void main() {
  final bin = StorageBin.small('A-01-02');
  print(bin.put(3));    // true
  print(bin.put(9));    // false เพราะจะเกิน 10
  print(bin);           // A-01-02 [3/10]
}

ทำไม put ต้องคืน bool: เพราะคนเรียกต้องรู้ผลเพื่อไปแสดงข้อความให้ผู้ใช้ ถ้าเขียนเป็น void แล้วเงียบ ๆ ไม่ทำอะไร ผู้ใช้จะกดแล้วไม่เกิดอะไรขึ้นโดยไม่รู้สาเหตุ ซึ่งเป็นบั๊กที่หาสาเหตุยากมากในงานจริง

ทำไม capacity เป็น final แต่ used ไม่เป็น: ความจุของช่องเก็บเป็นคุณสมบัติทางกายภาพที่ไม่เปลี่ยน ส่วนจำนวนที่วางอยู่คือสถานะที่เปลี่ยนตลอดวัน — ตรงกับหลักจาก D1.3 ว่าเริ่มจากล็อกไว้ก่อน แล้วผ่อนเฉพาะที่ต้องเปลี่ยนจริง

ลองต่อ: เพิ่ม getter isFull ที่คืน used >= capacity — แล้วสังเกตว่าเราไม่ควรเก็บ isFull เป็น field เพราะมันคำนวณจากค่าอื่นได้ (เหตุผลเต็ม ๆ อยู่ใน D1.7)

10. สรุปท้ายบท

  • class คือแบบพิมพ์เขียว object คือของจริงที่สร้างจากแบบนั้น
  • field เก็บข้อมูล method คือสิ่งที่ object ทำได้ และทั้งสองควรอยู่ด้วยกัน
  • this.x ใน constructor คือทางลัดของ “รับค่าแล้วเก็บลง field”
  • named constructor เพิ่มทางเข้าที่สื่อความหมาย ส่วน factory ใช้เมื่อต้องตัดสินใจก่อนสร้าง
  • == เทียบตัวตน ไม่ได้เทียบค่า

บทถัดไป: D1.7 จะตอบคำถามที่ค้างจากบทนี้ว่า จะกันไม่ให้คนนอกแก้ข้อมูลข้าม method ของเราได้อย่างไร ด้วย private field และ getter
