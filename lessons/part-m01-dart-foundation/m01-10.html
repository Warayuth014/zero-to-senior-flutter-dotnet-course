Extension method ที่ใช้แยก API ตามโดเมน

Part -1: Dart Foundation for Flutter

Extension method เพิ่ม API ที่เรียกเหมือน member โดยไม่แก้ class ต้นฉบับ ใน wmsapp ใช้แบ่ง ApiService ตามโดเมน 9 ชุด แต่ state/dependency ยังคงเป็นของ object เดิม

1. รูปแบบพื้นฐาน

extension BarcodeText on String {
  String get normalizedBarcode => trim().toUpperCase();
  bool get looksLikePallet => normalizedBarcode.startsWith('PAL-');
}

final code = input.normalizedBarcode;

extension ถูก resolve แบบ static จาก type ที่ compiler เห็น ไม่ได้แก้ String จริงและไม่มี runtime polymorphism แบบ virtual method

2. โครงจริงของ wmsapp

// api_service.dart
part 'api/receiving_api.dart';
part 'api/picking_api.dart';

// api/picking_api.dart
part of '../api_service.dart';
extension PickingApi on ApiService {
  Future<ApiResult<List<PickOrderListItem>>> getPickOrdersList() async {
    final response = await _get('/picking/orders-list');
    // parse แล้วคืน typed result
  }
}

เพราะไฟล์เป็น part ของ library เดียว extension จึงเรียก private _get/_post ได้ ผลคือ call site ใช้ ApiService().getPickOrdersList() แต่ไฟล์แยกตามโดเมน

3. ข้อดีและต้นทุนของแบบนี้

  • ดี: ลดไฟล์ ApiService ยักษ์, ชื่อ method discover ได้จาก object เดียว, reuse transport/error handling
  • ต้นทุน: ทุกโดเมนยังผูก singleton เดียว, extension เก็บ instance state ของตัวเองไม่ได้, mock เฉพาะ Picking ยากกว่า inject PickingRepository

จึงเป็น organization technique ไม่ใช่ dependency boundary โดยอัตโนมัติ

4. Extension กับ nullable และ generic

extension NullableString on String? {
  bool get isBlank => this == null || this!.trim().isEmpty;
}

extension FirstOrNull<T> on Iterable<T> {
  T? get firstOrNull => isEmpty ? null : first;
}

อย่าใส่ business rule สำคัญใน extension ทั่วไปจน owner หาย เช่น String.completePicking() ไม่สมเหตุผล เพราะ String ไม่ใช่เจ้าของ workflow

5. Name conflict และ import

ถ้า extension หลายตัวมี member ชื่อเดียวและมองเห็นพร้อมกัน compiler อาจเลือกไม่ได้ แก้ด้วย import show/hide, ตั้งชื่อไม่ชน หรือเรียก explicit extension override เช่น BarcodeText(raw).normalizedBarcode

6. Decision guide

  1. utility ที่เป็นธรรมชาติของ type และไม่มี state → extension
  2. ต้อง inject/mock หรือมี lifecycle → service/repository class
  3. ต้องเป็น polymorphic behavior → interface + implementation
  4. ต้องแชร์ private member ข้ามไฟล์ → ทบทวน library/part และ coupling ก่อน

7. แบบฝึกหัด

เปิด extension ReceivingApi แล้วจำแนกแต่ละ method: transport, contract parsing, business rule หรือ UI concern ถ้าพบสองอย่างหลังให้อธิบายว่าควรย้ายไปที่ใด

แนวตรวจคำตอบ

extension ควรสร้าง request และแปลง response เป็น model; workflow rule อยู่ store/use case; ข้อความ/สีอยู่ presentation หาก parser ซ้ำมากให้ย้ายเข้า model/parser helper

8. จุดพลาด

ไฟล์แยกไม่เท่ากับ architecture แยก ถ้าทุก extension ใช้ singleton/private transport เดียวกัน test seam และ ownership ยังอยู่จุดเดียว
