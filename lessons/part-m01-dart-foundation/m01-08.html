1. ปัญหาที่บทนี้แก้

ในคลังมีงานหลายชนิด: จัดเก็บ หยิบออก ตรวจนับ ทั้งสามมีสิ่งที่เหมือนกัน (มีรหัสงาน มีชื่อ ต้องรายงานผล) และมีสิ่งที่ต่างกัน (ขั้นตอนการทำงาน) ถ้าเขียนเป็นสาม class ที่ไม่เกี่ยวข้องกันเลย เราจะคัดลอกโค้ดส่วนที่เหมือนกันสามรอบ และไม่สามารถเก็บทั้งสามชนิดไว้ใน list เดียวกันได้

บทนี้คือเครื่องมือสามอย่างสำหรับจัดการความสัมพันธ์แบบนี้

2. คำศัพท์ที่ต้องรู้ก่อน

คำความหมาย
inheritance / สืบทอดclass ลูกได้ทั้งข้อมูลและพฤติกรรมของแม่มาใช้ต่อ
abstract classแบบพิมพ์เขียวที่ยังไม่สมบูรณ์ สร้าง object ตรง ๆ ไม่ได้
interface / สัญญารายการว่า “ต้องมี method อะไรบ้าง” โดยไม่ให้โค้ดมาด้วย
mixinก้อนความสามารถที่แปะให้ class ไหนก็ได้
overrideลูกเขียนทับพฤติกรรมของแม่
polymorphismเรียกชื่อ method เดียวกัน แต่ได้พฤติกรรมต่างกันตามชนิดจริง
superอ้างถึงส่วนที่เป็นของแม่

3. Mental model: เปรียบเทียบสามคำด้วยประโยคเดียว

คำประโยคที่ใช้จำได้โค้ดของแม่มาด้วยไหมมีได้กี่ตัว
extends“ฉันเป็นชนิดหนึ่งของสิ่งนั้น”ได้แม่ได้ตัวเดียว
implements“ฉันทำได้ตามสัญญานั้น”ไม่ได้ ต้องเขียนเองทั้งหมดกี่สัญญาก็ได้
with“ฉันมีความสามารถก้อนนั้นแถมมา”ได้กี่ก้อนก็ได้
วิธีตัดสินใจแบบเร็ว: ถ้าประโยค “ลูกเป็นชนิดหนึ่งของแม่” ฟังแล้วเป็นจริงในโลกจริง ให้ใช้ extends; ถ้าแค่ต้องการให้สลับตัวกันได้ ใช้ implements; ถ้าเป็นความสามารถเสริมที่หลาย class ต้องการเหมือนกัน ใช้ with

4. extends: แม่-ลูกที่แชร์โค้ดกัน

abstract class WarehouseTask {
  WarehouseTask(this.id);

  final String id;

  String get title;   // ไม่มีตัว = ลูกต้องเขียนเอง
  String run();       // ไม่มีตัว = ลูกต้องเขียนเอง

  String describe() => '[$id] $title -> ${run()}';   // แชร์ให้ลูกทุกตัว
}

class PutawayTask extends WarehouseTask {
  PutawayTask(super.id, this.location);

  final String location;

  @override
  String get title => 'จัดเก็บเข้าช่อง';

  @override
  String run() => 'นำพาเลทไปที่ $location';
}

abstract แปลว่าอะไร: แปลว่า “แบบนี้ยังไม่สมบูรณ์ สร้างของจริงจากมันตรง ๆ ไม่ได้” — เขียน WarehouseTask('T-01') จะ error ทันที ต้องสร้างจากลูกเท่านั้น สมเหตุสมผลเพราะ “งานในคลัง” แบบลอย ๆ ที่ไม่ระบุว่างานอะไร ไม่มีอยู่จริง

super.id คืออะไร: เป็นทางลัดที่แปลว่า “รับค่ามาแล้วส่งต่อให้ constructor ของแม่” ประหยัดกว่าการเขียน PutawayTask(String id, this.location) : super(id);

5. Polymorphism: ประโยชน์ที่แท้จริงของ extends

Set-Location .\labs\flutter_wms_companion
dart run tool/dart_foundation/d1_08_inheritance.dart
final tasks = <WarehouseTask>[
  PutawayTask('T-01', 'A-01-02'),
  PickTask('T-02', 5),
  CountTask('T-03', 30),
];

for (final task in tasks) {
  print(task.describe());   // เรียกชื่อเดียว ได้ผลต่างกันตามชนิดจริง
}
[T-01] จัดเก็บเข้าช่อง -> นำพาเลทไปที่ A-01-02
[T-02] หยิบสินค้า -> หยิบ 5 ชิ้นออกจากช่องเก็บ
[T-03] ตรวจนับ -> นับให้ครบ 30 ชิ้น

นี่คือหัวใจของบทนี้ — โค้ดที่วน for ไม่รู้จักงานทั้งสามชนิดเลย มันรู้แค่ว่า “ทุกตัวใน list นี้เป็น WarehouseTask ซึ่งเรียก describe() ได้” เมื่อเพิ่มงานชนิดที่สี่ในอนาคต โค้ดตรงนี้ไม่ต้องแก้แม้แต่บรรทัดเดียว

6. implements: สัญญาที่ไม่แถมโค้ดมาด้วย

abstract interface class Printable {
  String toReceipt();
}

class CountTask extends WarehouseTask implements Printable {
  // ...
  @override
  String toReceipt() => 'ใบตรวจนับ $id เวลา $stamp';
}

ต่างจาก extends ตรงที่ implements ไม่ได้อะไรมาให้เลย — ต้องเขียนทุก method ที่สัญญาระบุไว้เองทั้งหมด แลกกับความยืดหยุ่นสองอย่าง

  1. class หนึ่งทำสัญญาได้หลายอันพร้อมกัน (แต่มีแม่ได้แค่ตัวเดียว)
  2. ผู้ใช้สัญญาไม่ผูกกับ class ตัวใดตัวหนึ่ง — สลับตัวจริงได้

ข้อสองนี้สำคัญมากในงานจริง เพราะมันคือวิธีที่เราจะเขียนเทสต์ได้โดยไม่ต้องต่อ server จริง: ประกาศสัญญาว่า “ต้องดึงรายการงานได้” แล้วสลับระหว่างตัวที่ยิง API จริงกับตัวที่คืนข้อมูลปลอม (จะทำจริงใน Part 9 และ Part 14)

ข้อจำกัดที่ต้องรู้: ถ้า Printable ไม่ใช่แม่ของ WarehouseTask การเขียน if (task is Printable) task.toReceipt() จะไม่ผ่าน analyzer เพราะ Dart เลื่อนชนิดให้เฉพาะเมื่อชนิดใหม่เป็นลูกของชนิดเดิม ทางออกที่อ่านง่ายที่สุดคือใช้ whereType
for (final printable in tasks.whereType<Printable>()) {
  print(printable.toReceipt());
}

7. mixin: ความสามารถที่แปะข้ามสายพันธุ์ได้

mixin Timestamped {
  final DateTime createdAt = DateTime(2026, 1, 1, 9, 0);
  String get stamp => '${createdAt.hour}:${createdAt.minute}';
}

class CountTask extends WarehouseTask with Timestamped implements Printable {
  // ได้ createdAt และ stamp มาใช้ทันที
}

อ่านบรรทัดประกาศจากซ้ายไปขวาได้เป็นประโยค: “CountTask เป็นชนิดหนึ่งของ WarehouseTask มีความสามารถ Timestamped แถมมา และรับปากว่าทำตามสัญญา Printable ได้”

เหตุผลที่ต้องมี mixin ทั้งที่มี extends อยู่แล้ว: เพราะ class มีแม่ได้ตัวเดียว ถ้าความสามารถ “บันทึกเวลาสร้าง” ต้องใช้ทั้งในงานคลังและในใบสั่งซื้อซึ่งคนละสายพันธุ์กัน การยัดมันไว้ในแม่ร่วมจะทำให้ลำดับชั้นบิดเบี้ยว mixin แก้ปัญหานี้พอดี

ใน Flutter เราจะเจอ mixin บ่อยมาก โดยเฉพาะเวลาต้องการให้หน้าจอรับรู้เหตุการณ์บางอย่าง เช่นแอปถูกย่อลงพื้นหลัง

8. ตารางตัดสินใจ

สถานการณ์ใช้เหตุผล
งานหลายชนิดที่มีขั้นตอนร่วมกันabstract class + extendsแชร์โค้ดส่วนกลางได้จริง
ต้องสลับระหว่างของจริงกับของปลอมตอนเทสต์implementsผู้ใช้ไม่ผูกกับตัวใดตัวหนึ่ง
ความสามารถเดียวกันที่ class คนละสายต้องใช้mixin + withข้ามข้อจำกัดแม่ตัวเดียวได้
แค่อยากเรียกใช้ความสามารถของอีก classเก็บเป็น field ธรรมดาเรียบง่ายที่สุดและยืดหยุ่นที่สุด
คำแนะนำที่ใช้ได้ทั้งอาชีพ: ทางเลือกสุดท้ายในตารางคือทางที่ควรลองก่อนเสมอ ถ้าเก็บอีก object ไว้เป็น field แล้วเรียกใช้ได้ ก็ไม่ต้องสืบทอดอะไรเลย ลำดับชั้นที่ลึกเกินสองชั้นมักเป็นสัญญาณว่าออกแบบผิดตั้งแต่ต้น

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
Missing concrete implementation of 'X.run'ลูกยังไม่ได้เขียน method ที่แม่บังคับไว้เพิ่ม method พร้อม @override
X can't be instantiated because it's abstractพยายามสร้าง object จาก abstract classสร้างจาก class ลูกแทน
The method 'toReceipt' isn't defined for the type 'WarehouseTask'คาดว่า is จะเลื่อนชนิดให้ แต่ชนิดใหม่ไม่ใช่ลูกใช้ whereType<T>() หรือ cast อย่างชัดเจน
Classes can only extend other classesใช้ extends กับสองตัวเลือกแม่ตัวเดียว ที่เหลือใช้ implements หรือ with
เขียนทับ method แล้วพฤติกรรมไม่เปลี่ยนสะกดชื่อ method ผิดใส่ @override เสมอ เพื่อให้ analyzer จับให้
สืบทอดเพียงเพื่อยืม method สองสามตัวใช้ inheritance ผิดจุดประสงค์เก็บอีก object เป็น field แล้วเรียกใช้แทน

10. แบบฝึกหัด

ออกแบบระบบอ่านบาร์โค้ดที่ต้องทำงานได้สองแบบ

  1. ตอนใช้งานจริง อ่านจากเครื่องสแกนของ PDA
  2. ตอนทดสอบ ต้องป้อนบาร์โค้ดที่เรากำหนดเองได้ โดยไม่ต้องมีเครื่องจริง

จงเขียนโครงว่าควรใช้ extends, implements หรือ with พร้อมเหตุผล และเขียนฟังก์ชันที่รับตัวอ่านบาร์โค้ดเข้าไปใช้งานได้ทั้งสองแบบ

ดูแนวคำตอบและเหตุผล
// สัญญา: สนใจแค่ว่า "อ่านบาร์โค้ดถัดไปได้"
abstract interface class BarcodeSource {
  String? readNext();
}

class HardwareScanner implements BarcodeSource {
  @override
  String? readNext() => null;   // ของจริงจะคุยกับอุปกรณ์
}

class FakeScanner implements BarcodeSource {
  FakeScanner(this._queue);
  final List<String> _queue;

  @override
  String? readNext() => _queue.isEmpty ? null : _queue.removeAt(0);
}

// โค้ดงานจริงพึ่งพา "สัญญา" ไม่ใช่ตัวใดตัวหนึ่ง
int countScans(BarcodeSource source) {
  var count = 0;
  while (source.readNext() != null) {
    count++;
  }
  return count;
}

void main() {
  print(countScans(FakeScanner(['PAL-1001', 'PAL-1002'])));   // 2
}

ทำไมต้อง implements ไม่ใช่ extends: เพราะเครื่องสแกนจริงกับตัวปลอมไม่มีโค้ดอะไรที่แชร์กันได้เลย — ตัวหนึ่งคุยกับฮาร์ดแวร์ อีกตัวอ่านจาก list ในหน่วยความจำ สิ่งเดียวที่เหมือนกันคือ “สัญญา” ว่าเรียก readNext() ได้ ซึ่งตรงกับความหมายของ implements พอดี

ทำไมไม่ใช้ mixin: mixin มีไว้แจกโค้ดที่ทำงานได้จริง แต่ที่นี่เราไม่มีโค้ดจะแจก มีแต่ข้อกำหนด

สิ่งที่ควรสังเกตที่สุด: countScans เขียนครั้งเดียวแล้วใช้ได้ทั้งของจริงและของปลอม นี่คือเหตุผลที่ทีมซอฟต์แวร์ยอมลงทุนสร้าง interface — ไม่ใช่เพื่อความสวยงาม แต่เพื่อให้เทสต์รันได้บนเครื่องที่ไม่มีอุปกรณ์

ลองต่อ: เพิ่ม mixin Counting ที่นับจำนวนครั้งที่ readNext ถูกเรียก แล้วแปะให้ FakeScanner เท่านั้น

11. สรุปท้ายบท

  • extends = เป็นชนิดหนึ่งของ ได้โค้ดแม่มาด้วย มีแม่ได้ตัวเดียว
  • implements = รับปากว่าทำได้ ต้องเขียนเองทั้งหมด ทำได้หลายสัญญา
  • with = แปะความสามารถเสริม ข้ามสายพันธุ์ได้
  • abstract = แบบที่ยังไม่สมบูรณ์ สร้าง object ตรง ๆ ไม่ได้
  • ประโยชน์หลักคือเขียนโค้ดที่ทำงานกับ “ชนิดแม่” แล้วรองรับลูกใหม่ได้โดยไม่ต้องแก้
  • ถ้าเก็บเป็น field ธรรมดาแล้วจบ ก็ไม่ต้องสืบทอดอะไรเลย
