1. ปัญหาที่บทนี้แก้

สมมติเราเขียนช่องรับบาร์โค้ดขึ้นมาหนึ่งตัว มันมีหน้าที่ตัดช่องว่าง แปลงเป็นตัวพิมพ์ใหญ่ และตรวจว่าไม่ว่าง แต่คำถามคือ เมื่ออ่านสำเร็จแล้วจะทำอะไรต่อ

ปัญหาคือคำตอบต่างกันไปตามหน้าจอ — หน้ารับเข้าจะบันทึกลงรายการ หน้าหยิบของจะยิงไปหา server หน้าตรวจนับจะแค่เพิ่มตัวเลข ถ้าเราเขียนโค้ดเหล่านั้นลงไปในช่องรับบาร์โค้ดโดยตรง มันจะใช้ได้แค่หน้าจอเดียว

callback คือคำตอบ: ช่องรับบาร์โค้ดไม่ต้องรู้ว่าจะทำอะไรต่อ มันแค่รับ “ฟังก์ชันที่จะเรียกเมื่อสแกนสำเร็จ” มาจากผู้ใช้งาน

function typeชนิดของฟังก์ชัน เช่น void Function(String)

closureฟังก์ชันที่จำตัวแปรรอบตัวไว้ได้ (จาก D1.4)

3. Mental model: ทิ้งเบอร์ไว้ให้โทรกลับ

เวลาส่งของซ่อม เราไม่ยืนรอที่ร้าน แต่ทิ้งเบอร์โทรไว้แล้วกลับบ้าน ร้านเป็นคนโทรกลับเมื่อซ่อมเสร็จ

ในชีวิตจริงในโค้ด
เบอร์โทรที่เราให้ไว้ฟังก์ชันที่เราส่งเข้าไป
ร้านเก็บเบอร์ไว้class เก็บ callback ไว้ใน field
ร้านโทรกลับเมื่อเสร็จclass เรียก callback เมื่อถึงเงื่อนไข
ร้านไม่รู้ว่าเราจะทำอะไรต่อclass ไม่ต้องรู้ตรรกะของผู้ใช้งาน
ประโยคเดียวที่ต้องจำ: ผู้ที่รู้ “ว่าเกิดอะไรขึ้น” กับผู้ที่รู้ “ว่าต้องทำอะไรต่อ” มักไม่ใช่คนเดียวกัน callback คือสะพานเชื่อมสองฝ่ายนี้

4. อ่านชนิดของฟังก์ชันให้ออก

ชนิดอ่านว่า
void Function()ไม่รับอะไร ไม่คืนอะไร
void Function(String code)รับข้อความหนึ่งตัว ไม่คืนอะไร
String? Function(int value)รับจำนวนเต็ม คืนข้อความหรือ null
Future<void> Function(String)รับข้อความ แล้วทำงานที่ต้องรอ (D1.15)

อ่านจากซ้ายไปขวา: ส่วนหน้าสุดคือสิ่งที่คืน คำว่า Function คือตัวชนิด และในวงเล็บคือสิ่งที่รับ ชื่อ parameter ในวงเล็บใส่ไว้เพื่อให้อ่านง่ายเท่านั้น จะไม่ใส่ก็ได้

5. class ที่รับ callback

class ScanField {
  ScanField({
    required this.onSubmitted,
    this.onError,               // ไม่บังคับ
  });

  final void Function(String code) onSubmitted;
  final void Function(String message)? onError;

  void simulateScan(String raw) {
    final code = raw.trim().toUpperCase();
    if (code.isEmpty) {
      onError?.call('บาร์โค้ดว่าง');   // ถ้าไม่มีคนฟัง ก็ไม่ต้องเรียก
      return;
    }
    onSubmitted(code);
  }
}

onError?.call(...) คือรูปแบบที่ต้องจำ — เครื่องหมาย ? แปลว่า “ถ้า callback นี้เป็น null ให้ข้ามไปเลย” จึงไม่พังเมื่อผู้ใช้ไม่ได้ส่งมา เขียน onError!(...) ไม่ได้เพราะจะพังทันทีที่ไม่มีคนฟัง

6. typedef: ตั้งชื่อเล่นให้ชนิดที่ยาว

typedef QuantityValidator = String? Function(int value);

String? notNegative(int value) => value < 0 ? 'จำนวนติดลบไม่ได้' : null;

final QuantityValidator validate = notNegative;
print(validate(-2));   // จำนวนติดลบไม่ได้

ประโยชน์ไม่ใช่แค่ประหยัดตัวอักษร แต่คือการตั้งชื่อที่สื่อความหมาย — QuantityValidator บอกเจตนาชัดกว่า String? Function(int) และเมื่อจะเพิ่ม parameter ในอนาคตก็แก้ที่เดียว

Flutter ตั้งชื่อเล่นแบบนี้ไว้ให้เราหลายตัวแล้ว ที่จะเจอบ่อยคือ VoidCallback (คือ void Function()) และ ValueChanged<T> (คือ void Function(T))

7. กับดักที่สำคัญที่สุดของบทนี้

void logIt(String code) => print('  logIt: $code');

// ถูก — ส่งตัวฟังก์ชันไปให้เรียกทีหลัง
ScanField(onSubmitted: logIt);

// ถูก — ห่อไว้ในฟังก์ชันใหม่ เมื่อต้องส่ง argument เพิ่มเอง
ScanField(onSubmitted: (code) => logIt(code));

// ผิด — เรียกทันที แล้วเอา "ผลลัพธ์" ไปใส่แทนที่จะใส่ฟังก์ชัน
ScanField(onSubmitted: logIt('PAL-1'));
อาการที่จะเจอเมื่อเขียนผิดแบบที่สาม: ในโค้ด Flutter จริง คุณจะเห็นปุ่มทำงานเองตั้งแต่หน้าจอเปิดขึ้นมา และกดแล้วไม่มีอะไรเกิดขึ้น เพราะคุณส่ง “ผลลัพธ์ของการเรียก” ไปแทนที่จะส่ง “ตัวฟังก์ชัน” — เป็นบั๊กที่คนใหม่เจอกันแทบทุกคน
เขียนแบบความหมายเมื่อไหร่ที่ฟังก์ชันทำงาน
logItตัวฟังก์ชันเมื่อผู้รับตัดสินใจเรียก
() => logIt(x)ฟังก์ชันใหม่ที่ห่อการเรียกไว้เมื่อผู้รับตัดสินใจเรียก
logIt(x)ผลลัพธ์จากการเรียกทันทีที่บรรทัดนี้ถูกอ่าน

8. closure ทำให้ callback มีประโยชน์จริง

var received = 0;

final counter = ScanField(
  onSubmitted: (_) {
    received++;                  // แก้ตัวแปรที่อยู่นอกฟังก์ชันได้
    print('  สแกนสะสม $received รายการ');
  },
);
counter.simulateScan('PAL-1001');   // สแกนสะสม 1 รายการ
counter.simulateScan('PAL-1002');   // สแกนสะสม 2 รายการ

ตัว ScanField ไม่รู้จักตัวแปร received เลยแม้แต่น้อย แต่ callback ที่เราส่งเข้าไปจำมันไว้ได้ ทำให้ผู้ใช้งานเก็บสถานะของตัวเองได้อย่างอิสระ นี่คือเหตุผลที่ callback ทรงพลังกว่าการส่งข้อมูลกลับด้วยค่า return ธรรมดา

ชื่อ _ ที่ใช้แทนชื่อ parameter หมายถึง “มีค่าส่งมา แต่ฉันไม่ได้ใช้” เป็นธรรมเนียมที่ช่วยให้คนอ่านรู้ว่าไม่ได้ลืม

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
callback ทำงานทันทีที่สร้าง objectใส่วงเล็บตอนส่งส่งชื่อเปล่า หรือห่อด้วย () => f(x)
The argument type 'void' can't be assigned to ...ส่งผลลัพธ์แทนตัวฟังก์ชันถอดวงเล็บออก
Null check operator used on a null valueเรียก onError!(...) ทั้งที่ไม่มีคนส่งมาใช้ onError?.call(...)
ประกาศชนิดเป็น Function เฉย ๆ แล้วส่งอะไรก็ผ่านชนิดกว้างเกิน ไม่ตรวจจำนวน/ชนิด argumentระบุให้ครบ เช่น void Function(String)
callback ที่เป็นงานรอผลแล้ว error หายไปเงียบ ๆผู้เรียกไม่ได้รอผลและไม่ได้ดักข้อผิดพลาดประกาศชนิดเป็น Future<void> Function(...) แล้วให้ผู้เรียกจัดการ (D1.15)
callback ยาวหลายสิบบรรทัดจนอ่าน stack trace ไม่ออกเขียนตรรกะทั้งหมดไว้ในฟังก์ชันนิรนามแยกเป็น method ที่มีชื่อ แล้วส่งชื่อนั้นเข้าไป

10. แบบฝึกหัด

สร้าง class QuantityInput ที่

  1. รับ callback onAccepted ที่ถูกเรียกพร้อมจำนวน เมื่อค่าที่กรอกถูกต้อง
  2. รับ callback onRejected แบบไม่บังคับ ที่ถูกเรียกพร้อมเหตุผล เมื่อค่าไม่ถูกต้อง
  3. รับ validator จากภายนอกได้ เพื่อให้แต่ละหน้าจอกำหนดกฎของตัวเองได้
  4. มี method submit(String raw) ที่ทำงานทั้งหมดนี้
ดูแนวคำตอบและเหตุผล
typedef QuantityValidator = String? Function(int value);

class QuantityInput {
  QuantityInput({
    required this.onAccepted,
    this.onRejected,
    this.validator,
  });

  final void Function(int quantity) onAccepted;
  final void Function(String reason)? onRejected;
  final QuantityValidator? validator;

  void submit(String raw) {
    final value = int.tryParse(raw.trim());
    if (value == null) {
      onRejected?.call('กรุณากรอกตัวเลข');
      return;
    }
    final error = validator?.call(value);
    if (error != null) {
      onRejected?.call(error);
      return;
    }
    onAccepted(value);
  }
}

void main() {
  var total = 0;

  final input = QuantityInput(
    onAccepted: (quantity) {
      total += quantity;
      print('รับ $quantity ชิ้น (รวม $total)');
    },
    onRejected: (reason) => print('ปฏิเสธ: $reason'),
    validator: (value) => value > 50 ? 'เกิน 50 ชิ้นต่อครั้ง' : null,
  );

  input.submit('12');     // รับ 12 ชิ้น (รวม 12)
  input.submit('abc');    // ปฏิเสธ: กรุณากรอกตัวเลข
  input.submit('99');     // ปฏิเสธ: เกิน 50 ชิ้นต่อครั้ง
  input.submit('8');      // รับ 8 ชิ้น (รวม 20)
}

ทำไม validator ต้องรับจากภายนอก: เพราะกฎ “ไม่เกิน 50 ชิ้น” เป็นกฎของหน้าจอนั้น ไม่ใช่กฎของช่องกรอกตัวเลข ถ้าเขียนฝังไว้ข้างใน หน้าจออื่นที่มีเพดานต่างกันจะใช้ class นี้ไม่ได้ — สังเกตว่า QuantityInput รู้แค่ ขั้นตอน (แปลง → ตรวจ → แจ้งผล) ส่วน กฎ มาจากข้างนอกทั้งหมด

ทำไม onAccepted บังคับ แต่ onRejected ไม่บังคับ: เพราะถ้าไม่มีใครสนใจผลสำเร็จ ก็ไม่มีเหตุผลที่จะใช้ class นี้ตั้งแต่แรก ส่วนการแจ้งข้อผิดพลาดเป็นสิ่งที่บางหน้าจออาจไม่ต้องการ การใช้ required จึงเป็นการสื่อสารว่าอะไรคือแก่นและอะไรคือส่วนเสริม

ลองต่อ: ลองส่ง validator เป็น null แล้วสังเกตว่า validator?.call(value) คืน null ซึ่งแปลว่า “ไม่มีข้อผิดพลาด” พอดี — เป็นตัวอย่างที่ดีว่าการออกแบบให้ null มีความหมายเดียวกันทั้งสองกรณีช่วยลดจำนวน if ลงได้

11. สรุปท้ายบท

  • callback คือฟังก์ชันที่เราส่งให้คนอื่นเรียกทีหลัง
  • ผู้ที่รู้ว่า “เกิดอะไรขึ้น” ส่งข่าวให้ผู้ที่รู้ว่า “ต้องทำอะไรต่อ”
  • อ่านชนิดฟังก์ชันจากซ้าย: คืนอะไร → Function → รับอะไร
  • f คือตัวฟังก์ชัน, f() คือการเรียก — ต่างกันแค่วงเล็บแต่คนละความหมาย
  • callback ที่ไม่บังคับให้เรียกด้วย ?.call(...) เสมอ
  • closure ทำให้ callback เข้าถึงสถานะของผู้เรียกได้
