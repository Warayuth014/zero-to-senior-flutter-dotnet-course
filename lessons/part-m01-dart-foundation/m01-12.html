1. ปัญหาที่บทนี้แก้

ฟังก์ชันคืนค่าได้ค่าเดียว แต่บ่อยครั้งเราอยากได้สองค่าพร้อมกัน เช่น “แกะบาร์โค้ดแล้วได้ทั้งรหัสและจำนวน” หรือ “ตรวจข้อมูลแล้วได้ทั้งผลผ่าน/ไม่ผ่านและเหตุผล”

ทางออกที่มีมาก่อนหน้านี้ล้วนมีข้อเสีย

วิธีข้อเสีย
สร้าง class ใหม่ทุกครั้งเยอะเกินไปสำหรับค่าที่ใช้แค่ในสองบรรทัด
คืน Listเสียชนิด ทุกตัวกลายเป็นชนิดร่วมที่กว้างที่สุด
คืน Mapสะกด key ผิดได้ และไม่มีอะไรตรวจให้
ใช้ parameter แบบส่งค่ากลับอ่านยาก และ Dart ไม่รองรับตรง ๆ

record แก้ปัญหานี้ได้ตรงจุด และ pattern matching ทำให้แกะค่าออกมาใช้ได้สะดวก

3. Mental model: กล่องพัสดุที่ไม่ต้องตั้งชื่อ

record คือกล่องที่มัดของหลายชิ้นไว้ด้วยกันชั่วคราว — ใช้เสร็จก็แกะทิ้ง ต่างจาก class ซึ่งเป็นสิ่งของที่มีชื่อ มีกฎ และอยู่ในระบบไปนาน

recordclass
ประกาศล่วงหน้าไม่ต้องต้อง
ใส่ method / กฎได้ไม่ได้ได้
เทียบด้วยค่าได้เลยต้องเขียนเพิ่ม
เหมาะกับผลลัพธ์ชั่วคราวในฟังก์ชันเดียวสิ่งของในระบบที่มีชื่อและกฎ
เกณฑ์ตัดสิน: ถ้าค่านั้นต้องเดินทางข้ามหลายไฟล์ ต้องมี validation หรือมีชื่อที่คนในทีมเรียกกัน ให้ทำเป็น class — ถ้าเป็นแค่ “ค่าสองตัวที่คืนพร้อมกัน” ใช้ record

4. record แบบตำแหน่งและแบบมีชื่อ

// แบบตำแหน่ง: เหมาะกับ 2 ค่าที่ชนิดต่างกันชัดเจน
(String code, int quantity) parseScan(String raw) {
  final parts = raw.split('|');
  return (parts.first, int.tryParse(parts.last) ?? 0);
}

// แบบมีชื่อ: อ่านออกทันทีว่าค่าไหนคืออะไร
({bool ok, String message}) validate(int quantity) {
  if (quantity <= 0) return (ok: false, message: 'จำนวนต้องมากกว่า 0');
  if (quantity > 99) return (ok: false, message: 'เกินขีดจำกัดต่อรอบ');
  return (ok: true, message: 'ผ่าน');
}

5. record เทียบด้วยค่า ไม่ใช่ตัวตน

print((1, 'A') == (1, 'A'));   // true

ทบทวนจาก D1.6: class ที่เราเขียนเองจะได้ false ในกรณีเดียวกัน เพราะเทียบตัวตน ส่วน record เทียบทีละค่าให้อัตโนมัติ นี่คือเหตุผลที่ record เหมาะกับการเป็นผลลัพธ์ที่ต้องเอาไปเปรียบเทียบหรือใส่ใน Set

สำหรับ record แบบมีชื่อ ลำดับที่เขียนไม่สำคัญ แต่ชื่อสำคัญ — (ok: true, message: 'x') เท่ากับ (message: 'x', ok: true)

6. Pattern matching: ตรวจรูปร่างพร้อมแกะค่า

ต่อยอดจาก switch ใน D1.10 — คราวนี้ไม่ได้เทียบแค่ค่า แต่เทียบ “รูปร่าง” ของข้อมูลได้ด้วย

sealed class ScanEvent {}
class ScanOk extends ScanEvent { ScanOk(this.code, this.quantity); ... }
class ScanFailed extends ScanEvent { ScanFailed(this.reason); ... }
class ScanIgnored extends ScanEvent {}

String describe(ScanEvent event) => switch (event) {
  ScanOk(code: final c, quantity: final q) when q > 10 =>
    'สแกน $c จำนวนมาก ($q ชิ้น) ต้องยืนยันอีกครั้ง',
  ScanOk(code: final c, quantity: final q) => 'สแกน $c จำนวน $q ชิ้น',
  ScanFailed(reason: final r) => 'ล้มเหลว: $r',
  ScanIgnored() => 'ข้ามรายการนี้',
};

สังเกตสามอย่างที่เกิดขึ้นพร้อมกันในบรรทัดเดียว: ตรวจว่าเป็นชนิดไหน, ดึง field ออกมาเป็นตัวแปร, และตรวจเงื่อนไขเพิ่มด้วย when

sealed สำคัญตรงไหน: มันบอก Dart ว่าลูกของ ScanEvent มีเท่าที่ประกาศไว้ในไฟล์นี้เท่านั้น analyzer จึงตรวจได้ว่า switch ครอบคลุมครบไหม — ให้ผลเหมือน enum แต่แต่ละกรณีพกข้อมูลต่างกันได้ ซึ่ง enum ทำไม่ได้

เมื่อไหร่ใช้ enumเมื่อไหร่ใช้ sealed class
ทุกกรณีมีข้อมูลเหมือนกันหรือไม่มีเลยแต่ละกรณีพกข้อมูลคนละชุด
เช่น สถานะ pending/done/cancelledเช่น สำเร็จ(พร้อมข้อมูล) / ล้มเหลว(พร้อมเหตุผล)

7. pattern แบบอื่นที่ใช้บ่อย

// map pattern: ตรวจว่ามี key และชนิดตรง แล้วแกะค่าเลย
final raw = <String, Object?>{'code': 'PAL-1003', 'qty': 7};
if (raw case {'code': final String c, 'qty': final int q}) {
  print('$c จำนวน $q');
}

// ช่วงค่าและค่าที่เหลือ
String classify(int quantity) => switch (quantity) {
  0 => 'ไม่มีของ',
  < 100 => 'ปกติ',
  _ => 'ต้องขออนุมัติ',
};

if (x case pattern) ใช้เมื่อสนใจรูปแบบเดียว ไม่ต้องเขียน switch เต็มรูป — จะมีประโยชน์มากตอนแกะ JSON ใน D1.19

_ คือ pattern ที่จับได้ทุกอย่าง ใช้เป็นกรณีสุดท้าย แต่ระวังตามที่เตือนไว้ใน D1.10 ว่ามันปิดการตรวจสอบความครบถ้วน

ลำดับสำคัญ: switch เทียบจากบนลงล่างและหยุดที่กรณีแรกที่ตรง ดังนั้นกรณีที่แคบกว่า (มี when) ต้องอยู่ก่อนกรณีที่กว้างกว่าเสมอ ถ้าสลับกัน กรณีแคบจะไม่มีวันถูกใช้เลย

8. pattern ไม่ได้แทน validation

pattern ตรวจได้ว่า “ข้อมูลรูปร่างถูก” แต่ไม่ได้ตรวจว่า “ข้อมูลสมเหตุสมผล”

pattern ตรวจได้ต้องเขียนตรวจเอง
มี key ชื่อ quantity ไหมจำนวนติดลบหรือเปล่า
เป็น int หรือเปล่าเกินจำนวนคงเหลือไหม
เป็นชนิด ScanOk ไหมสถานะเปลี่ยนตามลำดับที่ถูกต้องไหม

อย่าให้ parser ที่ดูเรียบร้อยหลอกเราว่าข้อมูลผ่านการตรวจแล้ว — กฎทางธุรกิจยังต้องเขียนแยกเสมอ

9. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
The type 'ScanEvent' is not exhaustively matchedยังไม่ครอบคลุมลูกทุกตัวของ sealed classเพิ่มกรณีที่ขาด
บางกรณีใน switch ไม่เคยทำงานเลยเขียนกรณีกว้างไว้ก่อนกรณีแคบย้ายกรณีที่มี when ขึ้นไปข้างบน
ไม่รู้ว่า result.$2 คืออะไรใช้ record แบบตำแหน่งกับค่าหลายตัวเปลี่ยนเป็น record แบบมีชื่อ
record โตขึ้นเรื่อย ๆ จนมี 5–6 ค่าใช้ record แทนสิ่งที่ควรเป็น classตั้งชื่อให้มันแล้วสร้างเป็น class
if (x case ...) ไม่เข้าเงื่อนไขทั้งที่ข้อมูลดูถูกชนิดใน pattern ไม่ตรง เช่นข้อมูลเป็น String แต่เขียน final intตรวจชนิดจริงด้วย runtimeType ก่อน
ผ่าน pattern แล้วแต่ข้อมูลยังผิดเชิงธุรกิจเข้าใจว่า pattern ตรวจให้ทุกอย่างเขียนกฎธุรกิจตรวจเพิ่มหลัง pattern

10. แบบฝึกหัด

เขียนฟังก์ชัน parseQuantity ที่รับค่าซึ่งอาจมาในหลายรูปแบบจาก API

  1. ถ้าเป็น int ที่ไม่ติดลบ ให้คืนเลขนั้น
  2. ถ้าเป็นข้อความที่แปลงเป็นเลขไม่ติดลบได้ ให้คืนเลขนั้น
  3. ถ้าเป็น null ให้คืน 0
  4. กรณีอื่นให้โยน FormatException พร้อมบอกค่าที่ได้รับ
ดูแนวคำตอบและเหตุผล
int parseQuantity(Object? raw) => switch (raw) {
  null => 0,
  final int n when n >= 0 => n,
  final String s when (int.tryParse(s) ?? -1) >= 0 => int.parse(s),
  _ => throw FormatException('จำนวนไม่ถูกต้อง: $raw'),
};

void main() {
  for (final input in <Object?>[12, '8', null, -3, 'มาก', 4.5]) {
    try {
      print('$input -> ${parseQuantity(input)}');
    } on FormatException catch (error) {
      print('$input -> ${error.message}');
    }
  }
}
12 -> 12
8 -> 8
null -> 0
-3 -> จำนวนไม่ถูกต้อง: -3
มาก -> จำนวนไม่ถูกต้อง: มาก
4.5 -> จำนวนไม่ถูกต้อง: 4.5

ทำไม null ต้องอยู่บนสุด: เพราะถ้าอยู่ล่างกว่า _ มันจะไม่มีวันถูกใช้ และในกรณีนี้ null เป็นค่าที่เจาะจงที่สุด จึงควรอยู่ก่อนทุกอย่าง

จุดที่น่าสังเกตที่สุด: -3 เป็น int จริง แต่ไม่ผ่าน when n >= 0 จึงตกลงไปที่กรณีสุดท้ายและถูกปฏิเสธ — นี่คือความต่างระหว่าง “ตรวจรูปร่าง” (เป็น int ไหม) กับ “ตรวจความสมเหตุสมผล” (ติดลบหรือเปล่า) ตามที่อธิบายไว้ในหัวข้อ 8 และ pattern จัดการทั้งสองอย่างได้ในบรรทัดเดียวเพราะมี when

ข้อควรระวังในคำตอบนี้: 4.5 เป็น double ซึ่งถูกปฏิเสธ ถ้า API ของคุณส่งทศนิยมมาจริงแล้วต้องการปัดลง ต้องเพิ่มกรณี final double d when d >= 0 => d.toInt() — ประเด็นคือคุณต้อง ตัดสินใจ ว่าจะรับหรือปฏิเสธ ไม่ใช่ปล่อยให้มันพังโดยไม่ตั้งใจ

ลองต่อ: ลบบรรทัด _ => throw ... ออกแล้วรัน flutter analyze — จะได้ error เพราะ Object? มีค่าที่เป็นไปได้ไม่จำกัด จึงต้องมีกรณีปิดท้ายเสมอ ต่างจาก enum และ sealed class ที่ปิดชุดค่าไว้แล้ว

11. สรุปท้ายบท

  • record คือกลุ่มค่าชั่วคราวที่ไม่ต้องประกาศ class ล่วงหน้า
  • แบบมีชื่ออ่านง่ายกว่าเสมอเมื่อมีตั้งแต่สามค่าขึ้นไป
  • record เทียบด้วยค่า ต่างจาก class ที่เทียบด้วยตัวตน
  • pattern ตรวจชนิดและรูปร่างพร้อมแกะค่าออกมาในขั้นตอนเดียว
  • sealed class ให้การตรวจครบถ้วนแบบ enum แต่แต่ละกรณีพกข้อมูลต่างกันได้
  • กรณีที่แคบกว่าต้องเขียนไว้ก่อนกรณีที่กว้างกว่า
  • pattern ไม่ได้ตรวจกฎทางธุรกิจให้ ต้องเขียนเพิ่มเสมอ
