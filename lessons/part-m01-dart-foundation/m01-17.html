1. ปัญหาที่บทนี้แก้

ใน D1.15 เราเรียนว่า await ทำให้โปรแกรมไปทำอย่างอื่นได้ระหว่างรอ แต่มีคำเตือนค้างไว้ว่ามันช่วยได้เฉพาะงานที่ “รอ” จริง ๆ

ถ้างานนั้นคือการคำนวณล้วน ๆ เช่นแกะข้อมูล 5 เมกะไบต์ หรือประมวลผลรูปถ่าย ก็ไม่มีอะไรให้รอ — โปรแกรมต้องใช้ CPU ทำงานจริงจนกว่าจะเสร็จ ระหว่างนั้นหน้าจอจะค้างสนิท ผู้ใช้กดอะไรก็ไม่ตอบสนอง

3. Mental model: พนักงานคนเดียวกับคิวงาน

ให้คิดว่าโปรแกรม Dart มีพนักงานหนึ่งคนที่ทำงานตามคิว

ประเภทงานสิ่งที่เกิดขึ้นผลกับหน้าจอ
รอเน็ต (I/O)พนักงานฝากงานไว้กับระบบ แล้วไปทำงานอื่นในคิวต่อยังลื่น
คำนวณหนัก (CPU)พนักงานติดอยู่กับงานนั้น คิวที่เหลือรอทั้งหมดค้าง

ทางแก้คือ จ้างพนักงานอีกคนที่นั่งอีกห้อง — นั่นคือ isolate อีกตัว มันมีโต๊ะและของใช้ของตัวเองแยกกันสิ้นเชิง สื่อสารกันได้ทางเดียวคือส่งเอกสารข้ามห้อง

ประโยคเดียวที่ต้องจำ: await แก้ปัญหา “รอ” ส่วน isolate แก้ปัญหา “ยุ่ง” — ใช้ผิดตัวจะไม่ช่วยอะไรเลย

  1. ในกรณีที่สอง ข้อความ tick พิมพ์ออกมาได้ระหว่างที่งานหนักยังทำอยู่ — นั่นคือหลักฐานว่า isolate หลักยังว่าง ถ้าเป็นแอปจริง หน้าจอจะยังเลื่อนได้และปุ่มยังกดได้
  2. เวลารวมกลับ นานขึ้นเล็กน้อย (1221ms เทียบกับ 1124ms) เพราะการเปิด isolate ใหม่และคัดลอกข้อมูลมีต้นทุน

ข้อสองคือประเด็นหลักของบทนี้: isolate ไม่ได้ทำให้เร็วขึ้น มันทำให้ ส่วนอื่นไม่ถูกบล็อก ซึ่งคนละเรื่องกัน

5. วิธีใช้ที่ง่ายที่สุด

import 'dart:isolate';

final result = await Isolate.run(() => heavySum(rounds));

Isolate.run ทำสามอย่างให้อัตโนมัติ: เปิด isolate ใหม่, รันฟังก์ชันที่ให้ไป, ส่งผลกลับมาแล้วปิด isolate นั้น — เขียนบรรทัดเดียวจบ

ใน Flutter มีตัวช่วยชื่อ compute ที่ทำสิ่งเดียวกันและมีมานานกว่า จะเจอทั้งสองแบบในโค้ดจริง

6. ข้อจำกัดที่ต้องรู้: ไม่แชร์หน่วยความจำ

var counter = 0;

await Isolate.run(() {
  var localCopy = 0;
  localCopy += 100;
  return localCopy;      // ต้องส่งค่ากลับผ่าน return เท่านั้น
});

print(counter);   // ยังเป็น 0 — ไม่ถูกแก้ข้ามฝั่ง

นี่เป็นข้อจำกัดที่ตั้งใจออกแบบมา เพราะการให้สองพื้นที่แก้ข้อมูลก้อนเดียวกันพร้อมกันคือต้นเหตุของบั๊กที่หายากที่สุดในวงการซอฟต์แวร์ Dart ตัดปัญหานี้ทิ้งด้วยการบังคับให้คัดลอกข้อมูลข้ามฝั่ง

ส่งข้ามได้ส่งข้ามไม่ได้
ตัวเลข ข้อความ boolสิ่งที่ผูกกับหน้าจอ
List, Map, Set ของค่าธรรมดาการเชื่อมต่อเครือข่ายที่เปิดอยู่
object ธรรมดาที่สร้างจาก class ของเราสิ่งที่ผูกกับอุปกรณ์ เช่นตัวควบคุมกล้อง
ฟังก์ชันที่ส่งเข้า isolate ต้องไม่ไปอ้างอิงสิ่งที่ส่งข้ามไม่ได้ ถ้าเผลอ closure ไปจับตัวแปรที่ผูกกับหน้าจอ จะเกิดข้อผิดพลาดตอนรัน — วิธีที่ปลอดภัยคือให้ฟังก์ชันนั้นรับเฉพาะข้อมูลดิบและคืนเฉพาะข้อมูลดิบ

7. ตัดสินใจอย่างไรว่าควรใช้หรือไม่

อย่ารีบใช้ isolate เป็นทางแก้แรก ให้ไล่ตามลำดับนี้

  1. วัดก่อน — หน้าจอกระตุกตรงไหนจริง ๆ อย่าเดา
  2. ลดปริมาณข้อมูล — ขอ API ให้แบ่งหน้า หรือส่งเฉพาะ field ที่ใช้ มักได้ผลมากที่สุดและถูกที่สุด
  3. ทำเท่าที่จำเป็น — แสดงรายการแบบโหลดทีละส่วนแทนที่จะสร้างทุกแถวพร้อมกัน
  4. ถ้ายังหนักอยู่ จึงย้ายส่วนที่คำนวณล้วน ๆ ไป isolate
สถานการณ์ควรใช้ isolate ไหมเหตุผล
เรียก API แล้วรอผลไม่เวลาส่วนใหญ่คือรอ ไม่ได้ใช้ CPU
แกะ JSON รายการงาน 50 แถวไม่เร็วเกินกว่าจะรู้สึก การย้ายกลับช้าลง
แกะ JSON สต็อก 50,000 แถวใช่ ถ้าวัดแล้วกระตุกจริงเป็นการคำนวณล้วนที่กินเวลานาน
ย่อรูปก่อนอัปโหลดใช่ประมวลผลภาพกิน CPU สูงมาก
คำนวณสรุปยอดทั้งคลังบนเครื่องใช่งานหนักที่ไม่ควรบล็อกหน้าจอ

สำหรับ PDA ที่เป็นเป้าหมายของคอร์สนี้ ข้อควรระวังเพิ่มคือ ต้องวัดบนเครื่องจริง เพราะ CPU ของ PDA ช้ากว่าคอมพิวเตอร์ที่ใช้พัฒนามาก งานที่ใช้ 100ms บนเดสก์ท็อปอาจใช้ 800ms บน PDA ซึ่งข้ามเส้นจาก “ไม่รู้สึก” เป็น “ค้างชัดเจน”

8. ข้อผิดพลาดที่พบบ่อย

อาการสาเหตุวิธีแก้
ใส่ async แล้วหน้าจอยังค้างงานนั้นเป็น CPU-bound ไม่ใช่การรอย้ายไป Isolate.run
ย้ายไป isolate แล้วช้าลงงานเล็กเกินไป ต้นทุนการเปิดและคัดลอกมากกว่างานเองทำตรง ๆ ไปเลย
ข้อผิดพลาดเรื่องส่งข้อมูลข้าม isolate ไม่ได้ฟังก์ชันไปจับสิ่งที่ผูกกับหน้าจอหรืออุปกรณ์ให้ฟังก์ชันรับและคืนเฉพาะข้อมูลดิบ
แก้ตัวแปรใน isolate แล้วฝั่งเดิมไม่เปลี่ยนเข้าใจว่าแชร์หน่วยความจำกันส่งผลกลับผ่าน return
เปิด isolate ทุกครั้งที่มีข้อมูลเข้ามาเรียกถี่เกินไปรวมงานเป็นก้อนใหญ่ หรือแก้ที่ต้นเหตุคือปริมาณข้อมูล
ใช้ isolate แล้วยังกระตุกอยู่ต้นเหตุจริงคือการวาดหน้าจอ ไม่ใช่การคำนวณกลับไปวัดใหม่ตามลำดับในหัวข้อ 7

9. แบบฝึกหัด

หน้าจอรายการสินค้าคงคลังกระตุกอย่างชัดเจนหลังจากที่ API เริ่มส่งข้อมูลก้อนละ 5 เมกะไบต์

  1. เรียงลำดับขั้นตอนที่คุณจะทำเพื่อหาสาเหตุและแก้ไข
  2. อธิบายว่าทำไมการย้ายการเรียก API ไป isolate จึงไม่ช่วย
  3. เขียนโครงโค้ดของขั้นตอนสุดท้าย ถ้าปรากฏว่าต้นเหตุคือการแกะ JSON จริง
ดูแนวคำตอบและเหตุผล

ข้อ 1 — ลำดับที่ถูกต้อง

  1. วัดก่อน แยกให้ออกว่าเวลาหมดไปกับอะไร: รอเน็ต, แกะ JSON, สร้าง object, หรือวาดหน้าจอ — ถ้าข้ามขั้นนี้ไป มีโอกาสสูงที่จะแก้ผิดจุด
  2. ลดข้อมูลที่ต้นทาง ขอให้ API แบ่งหน้าหรือส่งเฉพาะ field ที่หน้าจอใช้จริง ข้อมูล 5 MB สำหรับรายการที่ผู้ใช้เห็นทีละ 20 แถวนั้นมากเกินไปตั้งแต่แรก
  3. วาดเท่าที่เห็น ใช้รายการแบบสร้างทีละแถวเมื่อเลื่อนถึง
  4. ย้ายการแกะข้อมูลไป isolate ถ้าขั้น 1 ยืนยันว่านั่นคือคอขวดจริง
  5. วัดซ้ำบน PDA จริง ไม่ใช่บนเครื่องพัฒนา

ข้อ 2 — ทำไมย้าย API call ไม่ช่วย

เพราะระหว่างรอเน็ต isolate หลักว่างอยู่แล้ว ไม่ได้ทำอะไรเลย การย้ายไปทำอีกห้องจึงไม่เปลี่ยนอะไร นอกจากเพิ่มต้นทุนการเปิด isolate — ส่วนที่กิน CPU จริงคือขั้นตอน หลัง ได้ข้อมูลมาแล้ว คือการแปลงข้อความ 5 MB เป็น object

// ฟังก์ชันนี้ต้องเป็นการคำนวณล้วน ๆ ไม่แตะหน้าจอหรือเครือข่าย
List<Map<String, Object?>> parseInventory(String body) {
  final rows = jsonDecode(body) as List<Object?>;
  return rows.whereType<Map<String, Object?>>().toList();
}

Future<void> load() async {
  final body = await api.fetchInventoryBody();      // รอเน็ต: ทำตรงนี้ได้
  final rows = await Isolate.run(() => parseInventory(body));  // คำนวณ: ย้ายออก
  render(rows);
}

จุดที่คนมักตอบผิด: หลายคนย้ายทั้งฟังก์ชัน load เข้า isolate ซึ่งจะเจอปัญหาทันทีเพราะการเชื่อมต่อเครือข่ายและการอัปเดตหน้าจอส่งข้ามไม่ได้ หลักคือ แยกส่วนที่คำนวณล้วนออกมาเป็นฟังก์ชันเดี่ยว ๆ ก่อน แล้วค่อยย้ายเฉพาะส่วนนั้น ซึ่งเป็นการออกแบบที่ดีอยู่แล้วแม้ไม่ใช้ isolate เพราะทำให้เขียนเทสต์ได้ง่ายด้วย

ลองต่อ: วัดเวลาของ parseInventory ด้วย Stopwatch กับข้อมูล 100 แถว เทียบกับ 50,000 แถว แล้วดูว่าเส้นแบ่งที่ควรเริ่มใช้ isolate อยู่ตรงไหนบนเครื่องของคุณ

10. สรุปท้ายบท

  • await แก้ปัญหางานที่ต้อง “รอ” ส่วน isolate แก้ปัญหางานที่ “ยุ่ง”
  • isolate ไม่ได้ทำให้เร็วขึ้น แต่ทำให้ส่วนอื่นไม่ถูกบล็อก
  • Isolate.run คือวิธีที่ง่ายที่สุดสำหรับงานครั้งเดียว
  • isolate ไม่แชร์หน่วยความจำ ต้องส่งข้อมูลด้วยการคัดลอก
  • อย่าใช้เป็นทางแก้แรก — วัด ลดข้อมูล วาดเท่าที่เห็น แล้วค่อยพิจารณา
  • ต้องวัดบนเครื่องจริง โดยเฉพาะ PDA ที่ CPU ช้ากว่าเครื่องพัฒนามาก
