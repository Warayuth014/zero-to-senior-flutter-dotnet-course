4. ความต่างที่แท้จริงระหว่างสองโดเมน

ถ้าดูแค่ตัวเลข จะสรุปว่า picking เขียนแย่กว่า — แต่ดูงานที่ทำก่อน

putawaypicking
ผู้ใช้ทำอะไรสแกนพาเลท เลือกปลายทาง กดยืนยันสแกนพาเลทต้นทาง → เลือกของทีละชิ้น → สแกน S/N → สแกนพาเลทปลายทาง → ยืนยัน → ตัดสินใจว่าจะทำอะไรต่อ
ขั้นตอน25
สถานะที่ต้องจำระหว่างทางพาเลท + ปลายทาง + ต้องพันฟิล์มไหมของที่เลือก + S/N ต่อชิ้น + จำนวนต่อชิ้น + พาเลทปลายทาง + ผลลัพธ์ล่าสุด
เรียลไทม์มี — 4 เหตุการณ์ไม่มี
จำนวนสถานี3 + 6ไม่มีแนวคิดสถานี
ข้อสรุปที่สำคัญ: putaway แตกไฟล์ได้เยอะเพราะสิ่งที่ซ้ำคือหน้าตา — สถานี 9 แห่งใช้การ์ดแบบเดียวกัน แผ่นเลื่อนแบบเดียวกัน ตัวเลือกปลายทางแบบเดียวกัน
picking แตกได้น้อยเพราะสิ่งที่ซับซ้อนคือลำดับและเงื่อนไข ซึ่งแตกเป็น widget ไม่ได้
ทั้งสองแตกถูกทิศทั้งคู่ — ความต่างมาจากธรรมชาติของงาน ไม่ใช่ความขยัน

แต่ 18.11 จะแสดงว่า picking มีสิ่งที่ ScanPartScreen ไม่มี และมันสำคัญกว่าจำนวนไฟล์

8. เรียลไทม์ที่มีเฉพาะ putaway

final _signalR = SignalRService();

@override
void initState() {
  super.initState();
  _signalR.addStationDispatchedListener(_handleStationDispatched);
  _signalR.addPalletArrivedListener(_handlePalletArrived);
  _signalR.addPalletReturnedListener(_handlePalletReturned);
  _signalR.addLabelingCompletedListener(_handleLabelingCompleted);
  _initSignalR();
  _loadStationStatus();
}
เหตุการณ์เกิดเมื่อ
StationDispatchedมีคนสั่ง putaway ที่สถานีหนึ่ง
PalletArrivedหุ่นยนต์เอาพาเลทมาถึงสถานี
PalletReturnedหุ่นยนต์รับพาเลทกลับไป
LabelingCompletedติดฉลากเสร็จ

ทั้งสี่เป็นเหตุการณ์ที่ผู้ใช้ไม่ได้เป็นคนทำ — หุ่นยนต์ทำ หรือคนอื่นที่สถานีอื่นทำ

ตรงกับหลักที่ 12.1 สอน — ใช้เรียลไทม์เมื่อข้อมูลเปลี่ยนโดยที่ผู้ใช้ไม่ได้กด
picking ไม่มีเรียลไทม์เพราะทุกอย่างเกิดจากการกระทำของผู้ใช้เอง ยกเว้นสถานะ WAITING ที่รอหุ่นยนต์ — ซึ่ง 18.9 จะเจอว่าตรงนั้นใช้การกดรีเฟรชเองแทน

ข้อ 1

จอทำนายเหตุผล

ข้อสังเกตตีความ

บรรทัดสุดท้ายน่าสนใจ — StationInfo ถูกใช้จาก unload_screen.dart ด้วย (17.11)

// unload_screen.dart
import '../putaway/shared/putaway_shared_widgets.dart';

โดเมน unload import ของจากโดเมน putaway — แปลว่า shared/ นั้นไม่ได้ shared แค่ในโดเมนตัวเอง

นี่เป็นสัญญาณที่ต้องสังเกต — เมื่อโดเมน A ต้อง import จาก โดเมน B/shared/ แปลว่าของชิ้นนั้นไม่ใช่ของ B แต่เป็นของกลางของทั้งแอป
ที่ถูกคือย้ายไปที่ lib/widgets/ หรือ lib/models/common/ ซึ่งมีอยู่แล้ว
ผลของการไม่ย้าย: ถ้าวันหนึ่งลบโดเมน putaway ทิ้ง โดเมน unload จะพังตามโดยไม่มีใครคาดคิด

ข้อสรุป: การมี shared/ เป็นข้อดี แต่ต้องดูด้วยว่าใครใช้บ้าง — shared ที่ถูกใช้ข้ามโดเมนคือของกลางที่วางผิดที่

11. สรุป

  • putaway 26 ไฟล์ เฉลี่ย 91 บรรทัด — picking 15 ไฟล์ เฉลี่ย 232
  • putaway มี shared/ 49% ส่วน picking ไม่มีเลย
  • putaway แตกได้เยอะเพราะสิ่งที่ซ้ำคือหน้าตา (9 สถานีใช้ของเดียวกัน)
  • picking แตกได้น้อยเพราะสิ่งที่ซับซ้อนคือลำดับและเงื่อนไข ซึ่งแตกเป็น widget ไม่ได้
  • ชื่อโฟลเดอร์ widget ของ picking ตรงกับขั้นตอนของ flow ทั้งห้าขั้น
  • putaway มี SignalR 4 เหตุการณ์ ทั้งหมดเป็นสิ่งที่หุ่นยนต์หรือคนอื่นทำ
  • picking ไม่มีเรียลไทม์เพราะทุกอย่างเกิดจากผู้ใช้เอง
  • StationInfo ใน putaway/shared/ ถูก import จากโดเมน unload — ของกลางที่วางผิดที่
