Confirm pick คือ inventory transaction: ยอดถูกหักจาก source และเพิ่มที่ destination พร้อมอัปเดต order จึงต้อง atomic, idempotent และตรวจ serial/quantity จากฐานข้อมูลล่าสุด

1. Build selected items

วน palletItems แล้วใช้ serial count หรือ qty map; รายการที่ qty≤0 ถูกข้าม สำหรับ serial item ส่ง serialNumbers ที่เลือก ส่วน non-serial ส่ง empty list ให้ backendตรวจ SerialRequire เอง

2. Confirm payload

POST /picking/confirm-pick
{ pickOrderId, sourcePalletId, destPalletId,
  items: [{ partId, qty, serialNumbers }],
  operatorId }

payload ปัจจุบันไม่มี lineId/lot/condition จึงกำกวมเมื่อ partId ซ้ำหลาย inventory lines

3. Client validation

ต้องมีอย่างน้อยหนึ่ง item; qty ไม่เกิน suggested; serial ไม่ซ้ำ อยู่ใน available list และไม่เกิน suggested แต่เป็น UX guard เท่านั้น ไม่ใช่ security/inventory guarantee

4. Atomic backend rules

ตรวจ source ownership/location, destination eligibility/capacity, order remaining, serial membership/uniqueness และ concurrency version ใน transaction เดียว หากบาง item ไม่ผ่านต้องกำหนดชัดว่า reject ทั้งชุดหรือ partial result

5. Response dimensions

ConfirmPickResponse มี isPickOrderComplete, sourcePalletEmpty, sourcePickDone, pickOrderStatus, remainingItems และ message แต่ UI ปัจจุบันใช้หลัก ๆ complete/remaining และไม่ได้ใช้ source flags ตัดสิน transitionครบถ้วน

6. After-pick state

success banner แยก order complete กับรอบนี้สำเร็จ และ remaining card filter qty>0 ผู้ใช้เลือกกลับ scan source หรือส่ง destination ไป PACK ข้อมูลนี้ควร reload authoritative order ก่อน action ถัดไป

7. Retry ambiguity

timeout หลัง commit อาจทำให้ผู้ใช้กดยืนยันซ้ำ ต้องส่ง idempotency key/operationId และ backendคืน response เดิม หรือ client query operation/order state ก่อน retry

8. Confirm tests

ทดสอบ nonserial/serial/mixed, part หลาย lot, concurrent stock change, duplicate command, destination full, partial failure policy, source empty และ order complete โดย assert ยอด source+dest และ order เปลี่ยนสอดคล้องกัน
