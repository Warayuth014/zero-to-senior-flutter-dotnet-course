ส่ง destination ไป PACK คือ handoff สุดท้าย: action นี้ปิดช่วง Picking และเปิดช่วง Packing จึงต้องอิง order readiness ไม่ใช่เพียงมี destPalletId

1. Send endpoint

POST /picking/send-to-pack/{palletId}

sendToPack คืน dynamic map และ UI อ่าน message เมื่อสำเร็จ ควรมี typed response ที่ระบุ pallet status/location และ order handoff

2. Current UI behavior

afterPick แสดงปุ่มส่ง PACK เมื่อ _destPalletId != null ทั้งกรณี order complete และยังมี remaining items ดังนั้น client ไม่ได้บังคับ readiness จาก isPickOrderComplete

3. Business decision

ถ้าห้ามส่งก่อนครบ ปุ่มต้อง enable เฉพาะ complete และ backend reject เสมอ; ถ้าอนุญาต partial shipment ต้องมี explicit partial handoff, order split และ audit ไม่ควรเกิดจากปุ่มเดียวที่ความหมายคลุมเครือ

4. Success transition

เมื่อ API สำเร็จ UI แสดง message, clear destination แล้วกลับ scanSource แต่ถ้า order complete ควรพิจารณากลับ orders list แทน เพื่อไม่เปิดรับ source ใหม่ของงานที่ปิดแล้ว

5. End-to-end trace

WAITING → PICKING
source pallets → confirm-pick(s) → order complete
destination pallet → send-to-pack → ZONE_PACK
→ Packing flow

แต่ละลูกศรต้องมี server status/version และ actor ที่ตรวจย้อนหลังได้

6. Observability

log correlationId, pickOrderId, source/dest pallets, station, operator, item/serial counts และ outcome โดยไม่ log token Metrics สำคัญคือ pick cycle time, conflict/retry, shortage และ premature pack rejection

7. Refactor roadmap

เพิ่ม typed station/picking DTO, line identity, immutable workflow controller, typed domain errors, unified return coordinator, request generation guard, idempotency key และ explicit pack readiness ตามลำดับความเสี่ยง

8. Capstone

สร้าง integration scenario order ที่ใช้ source 2 pallets และ destination เดิม: รอบแรก remaining, คืน source, รอบสอง complete, ส่ง PACK จากนั้นจำลอง timeout/duplicate/conflict และพิสูจน์ว่า inventory รวม, serial ownership และ order status ถูกต้องเพียงครั้งเดียว
