Destination pallet เป็น inventory owner หลัง confirm: ต้องไม่ใช่ source และอาจเป็น pallet เดิมของ order เพื่อรวมสินค้าหลาย source รอบ

1. Enter destination state

เมื่อมีรายการ pick อย่างน้อยหนึ่งรายการและยังไม่มี dest, state เปลี่ยนเป็น scanDest, clear input แล้ว request focus หลัง frame หากมี _destPalletId จากรอบก่อนจะ confirm ต่อ pallet เดิมทันที

2. Suggested destination

getSuggestedDestPallet() รับ pickOrderId เพื่อหา pallet ที่เหมาะกับ order ปัจจุบัน

GET /picking/suggest-dest-pallets
  ?pickOrderId={encodedOrderId}

API เลือกรายการแรกและคืน Dart record (palletId, continued) หรือ null

3. Continued semantics

continued=true หมายถึง order นี้มี destination pallet เดิม ให้ใช้ต่อ; false คือ pallet ว่าง Type=NULL+AVAILABLE UI แสดง label/chip ต่างกันเพื่อไม่ให้ผู้ใช้คิดว่าเป็นคำแนะนำชนิดเดียวกัน

4. Suggestion is optional

ผู้ใช้แตะ chip เพื่อเติม controller แล้วต้องยืนยันเอง การโหลด suggestion fail ถูกแปลงเป็นไม่มี suggestionโดยไม่แสดงเหตุผล จึงควรแยก no candidate จาก network/error

5. Source ≠ destination

_scanDestAndConfirm reject เมื่อ destId เท่ากับ source pallet ปัจจุบัน นี่เป็น local invariant สำคัญ แต่ server ต้องตรวจซ้ำและควร normalize IDs แบบเดียวกัน

6. Stale suggestion

ระหว่างแนะนำกับ confirm pallet ว่างอาจถูกอุปกรณ์อื่นจอง หรือ continued pallet อาจไป PACK แล้ว Backend ต้อง reserve/validate atomically และตอบ conflict ที่ทำให้ client reload suggestion

7. Persist across sources

หลัง confirm destination ID ยังอยู่ เมื่อกลับ scan source รอบถัดไปจึงข้าม scanDest และเติม pallet เดิม แต่ต้องตรวจว่า order/pallet ยังเปิดรับและ capacity พอก่อนทุก confirm

8. Destination tests

ทดสอบ no suggestion, continued/new, refresh, source=dest, suggestion ถูกแย่ง, dest capacity เต็ม, order เปลี่ยน และการใช้ dest เดิมกับ source รอบสองโดย backend ยังเป็นผู้ตัดสินสุดท้าย
