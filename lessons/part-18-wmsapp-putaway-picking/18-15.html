1. สถานะที่เกิดจากความล้มเหลว

if (!result.success) {
  setState(() {
    _returnPalletId = palletId;
    _state = _PickState.returnSource;

}

สถานะเดียวใน enum ที่เข้าได้เฉพาะเมื่อคำขอล้มเหลว

สถานะเข้าจาก
pickViewเปิดจอ หรือสแกนต้นทางสำเร็จ
scanDestกดยืนยันโดยยังไม่มีปลายทาง

การมีสถานะสำหรับความล้มเหลวเป็นการตัดสินใจที่ดี — แทนที่จะแสดงกล่อง error แล้วให้ผู้ใช้ยืนงงว่าทำอะไรต่อ จอพาไปหน้าที่มีทางออกให้
18.9 ทำสิ่งเดียวกันด้วย preview และ 17.7 ทำด้วย palletError — สามที่ในสองโดเมนที่ใช้แนวคิดเดียวกัน

4. ทางออกที่ไม่ควรมีในบางกรณี

เมื่อรู้สาเหตุจริงแล้ว จะเห็นว่าปุ่มสองใบไม่เหมาะกับทุกกรณี

สาเหตุส่งพาเลทกลับเหมาะไหม
ไม่มีของที่ต้องหยิบเหมาะ — พาเลทนี้ไม่มีงาน ส่งกลับได้
พาเลทถูกคนอื่นจองไม่เหมาะ — คนอื่นกำลังใช้อยู่

เน็ตหลุดอันตราย

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
ข้อความตายตัวปลอดภัยกว่าข้อความจากเซิร์ฟเวอร์ที่นี่ทำให้ผู้ใช้ตัดสินใจผิด
คำขอล้มเหลวมีสาเหตุเดียวอย่างน้อยห้าสาเหตุ
ทางออกที่มีปุ่มคือทางออกทั้งหมดปุ่มย้อนกลับก็เป็นทางออกแต่มองไม่เห็น
ชื่อคลาสไม่สำคัญเท่าโค้ดข้างในชื่อที่ไม่ตรงทำให้คนอ่านเข้าใจผิด
ไอคอนกับสีเลือกแยกกันได้ต้องสื่อความหมายเดียวกัน

8. แบบฝึกหัด

ผู้ใช้แจ้งว่า “สแกนพาเลทแล้วขึ้นว่าไม่มีของ พอกดส่งกลับ ASRS แล้วมารู้ทีหลังว่าของยังอยู่บนพาเลท”

  1. ไล่ว่าเกิดได้อย่างไร ทีละขั้น
  2. จุดไหนที่ถ้าแก้แล้วจะหยุดเหตุการณ์นี้ได้
  3. เรียงลำดับการแก้ตามผลกระทบ
แนวคำตอบ

ข้อ 1 — ไล่ทีละขั้น

1. ผู้ใช้สแกน PAL-042
2. _scanSourcePallet() ยิง assignPickStation
3. คำขอล้มเหลว (สาเหตุอะไรก็ได้ — เน็ต, สถานีไม่ว่าง, คนอื่นจอง)
4. เข้าสถานะ returnSource โดยไม่เก็บ result.error
5. การ์ดแสดง "ไม่มีสินค้าที่ต้อง Pick บน Pallet นี้"    ← ข้อความเดา
6. ผู้ใช้อ่านแล้วเชื่อ
7. กด "ส่งกลับ ASRS"
8. returnPallet สำเร็จ → พาเลทถูกส่งกลับพร้อมของที่ยังไม่ได้หยิบ

สังเกตว่าทุกขั้นทำงานถูกตามที่โค้ดเขียนไว้ — ไม่มีบั๊กในความหมายของโค้ดที่ทำงานผิด

สิ่งที่ผิดคือขั้นที่ 5 บอกข้อมูลที่ไม่จริง แล้วผู้ใช้ตัดสินใจจากข้อมูลนั้น

ข้อ 2 — จุดที่หยุดได้

ขั้นแก้อย่างไรหยุดได้ไหม
3–4แยกความล้มเหลวจากเน็ตออกก่อนเข้าสถานะนี้หยุดได้บางกรณี
5แสดง result.error แทนข้อความเดาหยุดได้ทุกกรณี
7เพิ่มกล่องยืนยันที่บอกว่า AMR จะมารับทันทีหยุดได้บางส่วน
7แสดงปุ่มเฉพาะเมื่อเซิร์ฟเวอร์บอกว่าส่งได้หยุดได้ทุกกรณี

สองจุดที่หยุดได้ทุกกรณี — จุดที่ 5 แก้ฝั่งแอปอย่างเดียว จุดสุดท้ายต้องแก้ทั้งสองฝั่ง

ข้อ 3 — เรียงลำดับ

ลำดับแก้อะไรต้นทุนผล
1เก็บ result.error แล้วแสดงในการ์ด~15 บรรทัด ฝั่งแอปผู้ใช้เห็นสาเหตุจริง
2เพิ่มปุ่ม “สแกนใบอื่น”~15 บรรทัดมีทางออกที่ถูกให้เลือก
3เพิ่มกล่องยืนยันก่อนส่ง (18.14)~10 บรรทัดมีจังหวะให้คิด
4แยกความล้มเหลวจากเน็ตต้องเพิ่ม kind ใน ApiResultกันกรณีที่อันตรายที่สุด
5ให้เซิร์ฟเวอร์คืน canReturnต้องแก้ .NETถูกที่สุด

สามข้อแรกรวมกันใช้เวลาไม่ถึงครึ่งวันและแก้ปัญหาได้เกือบทั้งหมด — ควรทำก่อน

ข้อสรุปที่ใหญ่กว่าเคสนี้
ความเสียหายในเคสนี้ไม่ได้เกิดจากโค้ดที่ทำงานผิด แต่เกิดจากข้อความที่บอกสิ่งที่แอปไม่รู้
ข้อความตายตัวที่เขียนไว้ตอนที่มีสาเหตุเดียว จะกลายเป็นข้อมูลเท็จทันทีที่มีสาเหตุที่สอง
วิธีตรวจ: ทุกครั้งที่เขียนข้อความอธิบายสาเหตุ ให้ถามว่า “แอปรู้จริงหรือเปล่าว่าสาเหตุคือนี่” ถ้าไม่รู้ ต้องเอาข้อมูลจากที่ที่รู้ หรือไม่ก็บอกว่าไม่รู้

9. สรุป

  • returnSource เป็นสถานะเดียวที่เข้าได้เฉพาะเมื่อคำขอล้มเหลว
  • การมีสถานะสำหรับความล้มเหลวดีกว่าแสดงกล่อง error แล้วปล่อยผู้ใช้
  • แบนเนอร์ปลายทางยังแสดงอยู่ — ผู้ใช้รู้ว่าพาเลทปลายทางยังไม่หาย
  • การ์ดเขียนสาเหตุไว้ตายตัว ทั้งที่ล้มเหลวได้อย่างน้อยห้าสาเหตุ
  • result.error มีข้อความจริงอยู่แล้วแต่ถูกทิ้ง
  • เน็ตหลุดแล้วผู้ใช้ถูกบอกว่าพาเลทไม่มีของ ซึ่งนำไปสู่คำสั่งที่ผิด
  • ทางออกจริงมีสามทาง แต่เห็นบนจอสองทาง
  • ชื่อคลาสสื่อว่าเป็นการ์ดข้อมูล แต่ที่จริงคือคำอธิบายความล้มเหลว
  • ข้อความที่บอกสิ่งที่แอปไม่รู้ กลายเป็นข้อมูลเท็จทันทีที่มีสาเหตุที่สอง
