switch บน enumif ซ้อนกัน

เทียบกับสิ่งที่ 18.3 และ 18.5 พบ — ที่นั่นใช้ isPW ? A : B และ _ => 'Prework' ซึ่งทำให้ค่าที่ไม่รู้จักตกไปที่ทางเลือกหนึ่งเงียบ ๆ
ที่นี่ไม่มีทางเกิดเพราะ enum มีสมาชิกจำกัดและคอมไพเลอร์รู้ว่ามีกี่ตัว

5. ปุ่มย้อนกลับที่รู้ว่าอยู่สถานะไหน

void _handleBack() {
  switch (_state) {
    case _PickState.scanDest:
      setState(() => _state = _PickState.pickView);    // กลับไปแก้ของที่เลือก
      break;
    case _PickState.afterPick:
      break;                                            // ← ไม่ให้ย้อน
    case _PickState.returnSource:
      _goToScanSource();                                // ไปสแกนใบใหม่
      break;
    case _PickState.scanSource:
    case _PickState.pickView:
      Navigator.pop(context);                           // ออกจากจอ
      break;
  }
}
return PopScope(
  canPop: _state == _PickState.pickView &&
      _assignment == widget.initialAssignment,
  onPopInvokedWithResult: (didPop, _) {
    if (!didPop) _handleBack();
  },
  child: Scaffold(...),
);
สถานะกดย้อนกลับแล้วเหตุผล
scanDestกลับไป pickViewยังไม่ได้ยืนยัน แก้ของที่เลือกได้

scanSourceออกจากจอยังไม่ได้เริ่มอะไร
pickViewออกจากจอดูเงื่อนไข canPop เพิ่ม

_state == _PickState.pickView && _assignment == widget.initialAssignment

รูปแบบเดียวกับที่ 18.10 ใช้ใน initState และเป็นสิ่งที่ต้องทำทุกครั้งที่โฟกัสไปยังช่องที่เพิ่งโผล่

8. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
ไฟล์ใหญ่แปลว่าอ่านยากเสมอที่นี่ใหญ่แต่มีโครงชัดกว่า ScanPartScreen
enum เป็นแค่เรื่องความเรียบร้อยทำให้สถานะที่ขัดแย้งกันสร้างไม่ได้

9. แบบฝึกหัด

เทียบ PickItemsScreen กับ ScanPartScreen แล้วตอบ

  1. ถ้าจะเพิ่มสถานะที่หก (เช่น confirmingWithSupervisor) แต่ละจอต้องแก้อะไร
  2. ปัญหาที่ 17.5 พบใน ScanPartScreen ข้อไหนบ้างที่ไม่เกิดที่นี่ และเพราะอะไร
  3. ปัญหาข้อไหนที่ยังเกิดทั้งสองจอ
แนวคำตอบ

ข้อ 1 — เพิ่มสถานะที่หก

PickItemsScreenScanPartScreen
ประกาศสถานะเพิ่มสมาชิกใน enum 1 บรรทัดเพิ่มฟิลด์ใหม่ หรือคิดเงื่อนไขใหม่จากฟิลด์เดิม
หา build ที่ต้องแก้คอมไพเลอร์บอกต้องอ่าน build() ทั้งหมดเอง
ปุ่มย้อนกลับคอมไพเลอร์บอก (switch ใน _handleBack)ต้องหาเอง
ตรวจว่าไม่ชนกับสถานะอื่นไม่ต้อง — เป็นไปไม่ได้ต้องไล่ทุกเงื่อนไข
เสี่ยงพลาดต่ำสูง

สองแถวกลางคือประโยชน์ที่จับต้องได้ที่สุด — เพิ่มสมาชิก enum แล้วรัน flutter analyze จะได้รายการจุดที่ต้องแก้ครบ

error: The type '_PickState' is not exhaustively matched by the switch cases
  since it doesn't match '_PickState.confirmingWithSupervisor'.

ข้อความนี้ปรากฏสองที่ (ใน build และ _handleBack) ซึ่งคือทุกที่ที่ต้องแก้จริง

ข้อ 2 — ปัญหาที่ไม่เกิดที่นี่

ปัญหาใน 17.5เกิดที่นี่ไหมเพราะ
สองสถานะมีค่าพร้อมกันไม่enum ถือค่าได้ทีละแบบ
จำนวนเก็บสองที่ต้องซิงก์เองไม่_pickedCountFor() คำนวณจากแหล่งที่ถูกต้อง
ไม่มีทางยกเลิกการเลือกสินค้าไม่มีแบนเนอร์ “ดูทั้งหมด” ที่ล้าง _selectedPartIds
โหมดที่ซ่อนอยู่ ต้องอ่าน build เพื่อรู้ไม่อยู่บรรทัดที่ 23

สี่ข้อจากรายการของ 17.5 ไม่เกิดที่นี่ — และสามข้อแรกเป็นผลโดยตรงจากข้อสุดท้าย

ข้อสรุปที่สำคัญที่สุด

สี่ข้อที่ยังเกิดทั้งสองจอ ล้วนมีรากอยู่นอกจอ — ที่ชั้น ApiResult และที่การตัดสินใจว่าสถานะจะอยู่ฝั่งไหน

ส่วนสี่ข้อที่หายไป ล้วนมีรากอยู่ในจอ — และแก้ได้ด้วยการเปลี่ยนวิธีถือสถานะ

บทเรียนที่ใช้ได้กับทุกโปรเจกต์: การใช้ enum แทนฟิลด์ bool/nullable หลายตัว แก้ปัญหาได้ทั้งกลุ่มในครั้งเดียว — ไม่ใช่เพราะเขียนสวยกว่า แต่เพราะทำให้สถานะที่ผิดสร้างไม่ได้
แต่มันแก้ได้เฉพาะปัญหาที่เกิดในจอ ปัญหาที่รากอยู่ชั้นล่างต้องแก้ที่ชั้นล่าง — ซึ่ง Part 23 จะทำ

10. สรุป

  • enum _PickState ห้าสมาชิกคือความต่างที่ใหญ่ที่สุดจาก ScanPartScreen
  • ฟิลด์เดียวถือค่าได้ทีละแบบ — สถานะที่ขัดแย้งกันสร้างไม่ได้
  • switch บน enum ทำให้คอมไพเลอร์ตรวจว่าครบทุกกรณี
  • ชื่อโฟลเดอร์ widget ตรงกับสมาชิกของ enum ทั้งห้า
  • สถานะจริง 12 ตัว และ _pickedCountFor() คำนวณจำนวนแทนการเก็บซ้ำ
  • สแกนพาเลทต้นทางไม่สำเร็จ → พาไปสถานะที่มีทางออกให้ ไม่ใช่แค่แสดง error
  • _handleBack() ตัดสินตามสถานะ และ afterPick ย้อนกลับไม่ได้
  • canPop ตรวจว่ายังเป็นพาเลทเดิม แต่ไม่ตรวจว่ามี S/N ค้าง
  • ข้ามสถานะ scanDest ได้เมื่อรู้ปลายทางแล้ว
  • ปัญหาที่รากอยู่ในจอหายไปด้วย enum ปัญหาที่รากอยู่ชั้นล่างยังอยู่
