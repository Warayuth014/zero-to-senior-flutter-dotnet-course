เป้าหมาย Part 20: อ่านแกนกลางของ wms_absolute_mobile จากการเปิดแอปจนถึง shell หลัง login ให้เห็นว่า configuration, HTTP, session, connection profile และ UI lifecycle ส่งต่อ state กันอย่างไร ก่อนลงรายละเอียด workflow คลังใน Part 21–22

1. เริ่มอ่านจาก composition root

เปิด lib/main.dart ก่อน เพราะไฟล์นี้ตอบว่า object ใดอยู่ยาวเท่าแอป: AppLanguageController และ ConnectionController เป็น singleton, ส่วน ApiClient ถูกสร้างหนึ่งตัวแล้วส่งเข้า AuthRepository จากนั้น repository เดิมถูกส่งต่อจาก LoginScreen ไป WarehouseShell จึงรักษา Bearer token ตัวเดียวกันไว้ได้

main
  ├─ load language + connection profiles
  └─ WmsApp
      └─ AuthRepository(ApiClient)
          ├─ LoginScreen
          └─ WarehouseShell
              ├─ WarehouseStore
              └─ ReceivingApi / TasksApi / InventoryApi / CycleCountApi

2. แผนที่โฟลเดอร์

  • lib/core: config, HTTP client, ภาษา, theme และ connection state ที่หลาย feature ใช้ร่วมกัน
  • lib/features/auth: session, repository และหน้า login
  • lib/features/settings: editor สำหรับ server profiles
  • lib/features/warehouse: shell, store, models, screens และ operational UI
  • lib/api: adapters ที่แปลง method ของ store เป็น HTTP contract
  • lib/widgets: widget ระดับแอป เช่นแถบสถานะ PDA
  • test: contract, state และ widget tests ที่ใช้ยืนยัน design intention

3. เส้นทาง login ถึง API

LoginScreen._submit()
  → AuthRepository.login(username, password)
  → ApiClient.post('/api/Authenticate/login', absolute: true)
  → parse token/expiration
  → client.authToken = token
  → Navigator.pushReplacement(WarehouseShell)

หลังเข้า shell, API adapters ทุกตัวรับ widget.auth.client ตัวเดิม จึงแนบ token เดิมโดยไม่ต้องส่ง token ผ่านทุก method นี่คือ shared transport state แบบง่าย แต่ทำให้ logout และการเปลี่ยน server ต้องคิดเป็นเหตุการณ์ระดับ session ไม่ใช่แค่เปลี่ยนหน้าจอ

4. ใครเป็นเจ้าของ state

StateOwnerอายุ
ภาษาAppLanguageControllerข้ามการเปิดแอปด้วย preferences
profiles/server statusConnectionControllerข้ามการเปิดแอป; status อยู่ใน memory
token/sessionAuthRepository + ApiClientเฉพาะ process ปัจจุบัน
warehouse workflowWarehouseStoreตั้งแต่เข้า shell ถึง logout
form/dialogState ของ widget นั้นจน widget dispose

5. เส้นทาง configuration ถึง request

ConnectionProfile ทำหน้าที่ model และ validation, ConnectionController เลือก active profile และ persist, ส่วน AppConfig.apiBaseUrl อ่าน active URL ใหม่ทุกครั้งที่สร้าง request ดังนั้นการสลับ profile มีผลกับ request ถัดไปทันที โดยไม่สร้าง ApiClient ใหม่ ลำดับ precedence คือ compile-time override → active profile → http://localhost:6191

6. เส้นทาง connection test แยกจาก business API

ConnectionProbe ใช้ client ของตัวเองยิง /api/WMS/mobile_health ไปยัง URL draft ได้ จึงกด Test ก่อน Save/Use ได้ และไม่ได้แนบ token โดยไม่จำเป็น มันไม่เชื่อแค่ HTTP 200 แต่ตรวจ JSON ว่า service == "WMS" และ ok == true เพราะ Blazor fallback อาจคืนหน้า HTML พร้อม 200 แม้ base path ผิด

7. Reading order ที่ลดการเดา

  1. main.dart เพื่อหา composition และ startup ordering
  2. app_config.dart → connection_*.dart เพื่อเข้าใจ URL
  3. api_client.dart → auth_repository.dart → login_screen.dart เพื่อ trace login
  4. warehouse_shell.dart เพื่อดู lifecycle และการประกอบ adapters/store
  5. อ่าน test คู่กับ production file เพื่อจับ invariant ที่ comment ไม่ได้บอก

8. แบบฝึก trace ก่อนลงลึก
