1. ไฟล์ทั้งไฟล์ 26 บรรทัด

import 'connection_controller.dart';
import 'connection_profile.dart';

/// Static configuration for the PDA app.
class AppConfig {
  /// Port the WMS backend (Kestrel) listens on — see appsettings.json.
  static const int backendPort = defaultServerPort;

  /// Base URL of the WMS backend — see [resolveBaseUrl] for the order it is
  /// worked out in.
  ///
  /// `ApiClient` calls this getter on every request rather than caching it, so
  /// switching profiles redirects the whole app immediately — no client is
  /// rebuilt and the bearer token on the live client survives untouched.
  static String get apiBaseUrl =>
      resolveBaseUrl(ConnectionController.instance.activeBaseUrl);

  /// PDA endpoints live on the shared WMS controller (api/WMS/mobile_*). Auth
  /// uses the shared /api/Authenticate/login (called with absolute path).
  static const String apiPrefix = '/api/WMS';

  /// Shown in the status bar. Will become a per-device setting later.
  // static const String deviceName = 'PDA-07';

  static const String appTitle = 'ACETEC WMS v3';
}

ไฟล์เล็กที่สุดในโปรเจกต์ แต่มีอยู่บรรทัดหนึ่งที่ตัดสินสถาปัตยกรรม

2. บรรทัดที่สำคัญ: get ไม่ใช่ const

เทียบสองแบบ

// แบบที่เห็นบ่อย (และแบบที่ wmsapp ทำ)
static const String apiBaseUrl = 'http://192.168.1.194:6191';

// แบบที่ไฟล์นี้ทำ
static String get apiBaseUrl =>
    resolveBaseUrl(ConnectionController.instance.activeBaseUrl);
constget
ค่าถูกคิดเมื่อไรตอนคอมไพล์ ครั้งเดียวทุกครั้งที่อ่าน
เปลี่ยนระหว่างแอปทำงานไม่ได้ได้
ค่าใช้จ่ายศูนย์เรียกฟังก์ชันหนึ่งครั้ง

ผลของการเลือก get อยู่ในคอมเมนต์

“ApiClient เรียก getter นี้ทุกคำขอแทนที่จะจำค่าไว้ ทำให้การสลับโปรไฟล์เปลี่ยนปลายทางทั้งแอปทันที — ไม่ต้องสร้าง client ใหม่ และ bearer token บน client ตัวเดิมยังอยู่ครบ”

3. ทำไม “ไม่ต้องสร้าง client ใหม่” ถึงสำคัญ

ย้อนไปดู 20.2 — ApiClient ถูกสร้างครั้งเดียวใน main()

runApp(WmsApp(auth: AuthRepository(ApiClient())));

และ token เก็บอยู่บนตัว client

class ApiClient {
  String? authToken;   // ตั้งตอนล็อกอินสำเร็จ
}

ทีนี้ลองคิดว่าถ้า apiBaseUrl เป็น const จะสลับเซิร์ฟเวอร์อย่างไร

// ต้องสร้าง client ใหม่ทั้งตัว
final newClient = ApiClient();       // ← authToken เป็น null แล้ว
ทางเลือกผลที่ตามมา
สร้าง client ใหม่token หาย ผู้ใช้ต้องล็อกอินใหม่
สร้างใหม่แล้วก๊อป tokenต้องจำว่ามีอะไรต้องก๊อปบ้าง — ลืมง่ายเมื่อเพิ่มฟิลด์
ให้ที่อยู่เป็น getterไม่ต้องแตะ client เลย
รูปแบบที่ควรจำ
เมื่อมีค่าที่เปลี่ยนได้ระหว่างทำงาน ให้ค้นค่าตอนใช้ อย่าฉีดค่าเข้าไปเก็บไว้ในของที่มีอายุยาว
เพราะของที่มีอายุยาวจะเริ่ม “ถือค่าที่ตกยุคแล้ว” และคุณจะต้องไล่ซิงก์มันตลอดไป

แต่ควรพูดถึงราคาที่จ่ายด้วย

สิ่งที่แลกมารายละเอียด
AppConfig ผูกกับ ConnectionControllerไฟล์ที่ควรเป็นค่าคงที่ล้วน กลับ import singleton เข้ามา
เทสต์ต้องรีเซ็ต controllerจึงมี debugReset() ให้ (20.11)
ที่อยู่เปลี่ยนกลางคำขอชุดหนึ่งได้ถ้าสลับโปรไฟล์ระหว่างที่มีคำขอค้างอยู่

แถวสุดท้ายเป็นความเสี่ยงจริง แต่เล็ก — การสลับโปรไฟล์เป็นการกระทำที่คนตั้งใจทำ ไม่ได้เกิดเอง

4. รากของ API มีสามอัน

static const String apiPrefix = '/api/WMS';

คอมเมนต์ในไฟล์ connection_profile.dart บอกไว้ชัดว่าแอปยิงสามราก

รากใช้ทำอะไรเรียกอย่างไร
/api/WMSทุกอย่างของพีดีเอpost('/mobile_xxx', ...)
/api/Authenticateล็อกอินpost('/api/Authenticate/login', ..., absolute: true)
/api/dataตารางข้อมูลที่เว็บใช้ร่วมกันabsolute: true

นี่คือเหตุผลที่ apiPrefix เป็น const ในขณะที่ apiBaseUrl เป็น get

เส้นแบ่งที่ชัด
  • ที่อยู่เครื่อง — ผู้ใช้แก้ได้ เพราะแต่ละไซต์คนละเครื่อง
  • เส้นทางของ API — ผู้ใช้แก้ไม่ได้ เพราะถูกกำหนดโดยโค้ดฝั่ง .NET
คอมเมนต์ใน normalizeBasePath เขียนไว้ตรง ๆ ว่า “มันไม่ใช่ราก /api ของแอป — แอปยิงสามรากต่างกัน ส่วนนั้นจึงให้ผู้ใช้แก้ไม่ได้”

5. resolveBaseUrl — ลำดับความสำคัญสามชั้น

/// Resolves the address the app talks to. First match wins:
///   1. `--dart-define=WMS_API_BASE_URL` (a build pinned to one server)
///   2. [activeBaseUrl], the profile the operator picked (null before load)
///   3. the built-in default, only until a profile has been seeded
String resolveBaseUrl(String? activeBaseUrl) {
  if (_baseUrlOverride.isNotEmpty) return _baseUrlOverride;
  if (activeBaseUrl != null && activeBaseUrl.isNotEmpty) return activeBaseUrl;
  return 'http://$defaultServerHost:$defaultServerPort';
}

สามบรรทัด อ่านจบใน 10 วินาที และมีเอกสารบอกลำดับไว้ข้างบน

ชั้นที่ 1 — --dart-define

const String _baseUrlOverride = String.fromEnvironment('WMS_API_BASE_URL');
flutter run --dart-define=WMS_API_BASE_URL=http://192.168.1.50:6191

String.fromEnvironment อ่านค่าที่ส่งตอนคอมไพล์ ไม่ใช่ตอนทำงาน — ถ้าไม่ส่งจะได้สตริงว่าง

ชั้นที่ 2 — โปรไฟล์ที่ผู้ใช้เลือก

มาจาก ConnectionController ที่โหลดใน main() (20.11)

ชั้นที่ 3 — ค่าฝังมา

const String defaultServerHost = 'localhost';
const int defaultServerPort = 6191;

คอมเมนต์บอกว่านี่คือ “ที่เดียวที่ที่อยู่เริ่มต้นอยู่” — ทั้ง seedConnectionProfile() และค่าตกกลับของ AppConfig อ่านจากตรงนี้ ย้ายเซิร์ฟเวอร์แล้วแก้บรรทัดเดียว

และเห็นได้ใน AppConfig เอง

static const int backendPort = defaultServerPort;   // ไม่ใช่ 6191 ที่พิมพ์ซ้ำ

6. สองคอมเมนต์ที่บอกประวัติ

คอมเมนต์ที่บอกว่า “เคยมีทางที่สอง แล้วเอาออก”

/// One path for every platform. There used to be a `kIsWeb` branch deriving the
/// host from the page URL, but a saved profile does that job better and on
/// every platform, so keeping a second mechanism only meant Chrome behaved
/// differently from the handheld for no gain.

คอมเมนต์ที่บอกว่า “เคยมีสองที่ แล้วรวมเป็นที่เดียว”

/// Lives here rather than in `AppConfig` so the *same* answer serves both the
/// requests (`AppConfig.apiBaseUrl`) and the status probe. When each resolved
/// its own way, a `--dart-define` build sent requests to one server while the
/// header dot reported on another.
บั๊กที่บรรยายในคอมเมนต์นี้คือบั๊กที่หลอกคนที่สุดแบบหนึ่ง
จุดเขียว “เชื่อมต่อแล้ว” ขึ้นสวยงาม แต่คำขอจริงไปคนละเครื่อง
ผู้ใช้จะรายงานว่า “แอปบอกว่าต่อได้แต่ทำอะไรไม่ได้เลย” — และคนแก้จะไล่หาที่ผิดฝั่ง
กฎที่ได้จากบั๊กนี้
ตัวบ่งชี้สถานะต้องถามคำถามเดียวกับที่งานจริงถาม
ถ้าจุดสถานะคำนวณที่อยู่เอง มันกำลังทดสอบสิ่งที่ไม่มีใครใช้
ใช้กับทุกเรื่อง — จอแสดงสิทธิ์ต้องอ่านตัวแปรเดียวกับที่ปุ่มใช้ตัดสิน จอแสดงคิวต้องนับจากคิวเดียวกับที่คนงานหยิบ

7. บรรทัดที่ถูกคอมเมนต์ทิ้งไว้

/// Shown in the status bar. Will become a per-device setting later.
// static const String deviceName = 'PDA-07';

โค้ดที่ถูกปิดไว้พร้อมคำอธิบายว่าจะกลับมาทำ

มุมที่ยอมรับได้มุมที่ไม่ควร
บอกว่าเคยมีฟีเจอร์นี้และตั้งใจจะมีอีกไม่รู้ว่า “later” คือเมื่อไร
มีคอมเมนต์อธิบาย ไม่ใช่โค้ดตายเปล่า ๆgit เก็บประวัติให้อยู่แล้ว ลบทิ้งได้

ในโปรเจกต์นี้ยอมรับได้เพราะมีบรรทัดเดียวและมีคำอธิบาย — ถ้าเป็นบล็อก 40 บรรทัด ควรลบแล้วเปิด issue แทน

8. ข้อผิดพลาดที่พบบ่อย

ผิดอาการถูก
const สำหรับค่าที่ผู้ใช้เปลี่ยนได้สลับแล้วไม่มีผลจนกว่าจะปิดแอปใช้ getter
ให้ผู้ใช้แก้ราก /api404 ทุกเส้นทางให้แก้แค่ที่อยู่เครื่อง
จุดสถานะคำนวณที่อยู่แยกจากคำขอเขียวแต่ใช้ไม่ได้ฟังก์ชันเดียวตอบทั้งคู่
พิมพ์พอร์ตซ้ำหลายที่ย้ายเซิร์ฟเวอร์แล้วลืมแก้ที่หนึ่งค่าคงที่ตัวเดียว
เก็บ token ใน client แล้วสร้าง client ใหม่ถูกเด้งออกโดยไม่มีเหตุผลอย่าสร้างใหม่ ให้ที่อยู่เป็น getter

9. แบบฝึกหัด

  1. ผู้ใช้ตั้ง Base Path เป็น /api — เขียน URL เต็มที่แอปจะยิงออกไป และอธิบายว่าทำไม validateConnectionInput ถึงห้ามไว้
  2. ถ้าจะเพิ่มการเก็บ deviceName ต่อเครื่องจริง ๆ ควรเก็บที่ไหน และทำไมไม่ควรอยู่ใน AppConfig
แนวคำตอบ

ข้อ 1

baseUrl  = 'http://192.168.1.50:6191' + normalizeBasePath('/api')
         = 'http://192.168.1.50:6191/api'

URL เต็ม  = baseUrl + apiPrefix + path
         = 'http://192.168.1.50:6191/api' + '/api/WMS' + '/mobile_receiving_list'
         = http://192.168.1.50:6191/api/api/WMS/mobile_receiving_list
                                    ~~~~~~~~ ซ้ำ

404 ทุกเส้น และข้อความในตัวตรวจก็เขียนไว้ตรงตัว

'Leave this empty — the app already adds /api itself. Filling it in here '
'makes every address /api/.../api/... and nothing will work.'
สังเกตว่าคอมเมนต์เหนือกฎนี้อธิบายว่าทำไมคนถึงพลาด
“Easy mistake: the field looks like the place the API root belongs.”
ช่องชื่อ Base Path ดูเหมือนที่ที่ควรใส่ราก API — การตรวจที่ดีจึงไม่ใช่แค่ห้าม แต่บอกว่าควรใส่อะไรแทน

ข้อ 2

ควรอยู่ใน ConnectionController หรือคอนโทรลเลอร์คล้าย ๆ กันที่อ่าน/เขียน SharedPreferences

เหตุผลอธิบาย
ค่าต่างกันต่อเครื่องAppConfig เก็บสิ่งที่เหมือนกันทุกเครื่อง
ต้องอ่านจากดิสก์AppConfig ไม่มี load() และไม่ควรมี
ต้องแจ้งเมื่อเปลี่ยนแถบสถานะต้องวาดใหม่ — ต้องเป็น ChangeNotifier

ทางที่ตรงที่สุดคือเพิ่มลงในโปรไฟล์ที่มีอยู่แล้ว — เพิ่มฟิลด์ deviceName ใน ConnectionProfile พร้อม toJson/fromJson แล้วเปิดช่องในแผ่นตั้งค่า

// fromJson รองรับข้อมูลเก่าที่ไม่มีฟิลด์นี้อยู่แล้ว
deviceName: raw['deviceName']?.toString() ?? '',

ได้ของแถมคือสลับโปรไฟล์แล้วชื่อเครื่องเปลี่ยนตาม ซึ่งสมเหตุสมผลถ้าพีดีเอเครื่องเดียวใช้ทดสอบหลายไซต์

แต่ถามก่อนทำ — “ชื่อเครื่อง” เป็นสมบัติของเครื่อง หรือของการเชื่อมต่อ
ถ้าเป็นของเครื่อง การผูกไว้กับโปรไฟล์แปลว่าต้องพิมพ์ซ้ำทุกโปรไฟล์
ไม่มีคำตอบถูกจากโค้ด — ต้องถามคนใช้ว่าพีดีเอหนึ่งเครื่องยิงหลายเซิร์ฟเวอร์จริงหรือไม่
นี่คือคำถามที่ต้องถามก่อนเขียน ไม่ใช่หลังเขียน

10. สรุป

  • apiBaseUrl เป็น get ไม่ใช่ const — สลับโปรไฟล์แล้วมีผลทันทีโดยไม่แตะ client และ token ไม่หาย
  • ค่าที่เปลี่ยนได้ระหว่างทำงาน ให้ค้นตอนใช้ อย่าฝากไว้กับของที่อายุยาว
  • apiPrefix เป็น const เพราะเส้นทาง API ผู้ใช้แก้ไม่ได้ — แอปยิงสามราก
  • resolveBaseUrl สามชั้น: --dart-define → โปรไฟล์ → ค่าฝังมา
  • ที่อยู่เริ่มต้นอยู่ที่เดียว — defaultServerHost/defaultServerPort
  • ฟังก์ชันเดียวตอบทั้งคำขอและจุดสถานะ เพราะเคยแยกกันแล้วเจอบั๊ก “เขียวแต่ใช้ไม่ได้”
  • คอมเมนต์ในไฟล์นี้บันทึกทางที่เคยลองแล้วเอาออก ไม่ใช่แค่บอกว่าโค้ดทำอะไร
