Scan PO เป็น read-before-write gate: normalize input, โหลดเอกสาร/รายการ, แสดง status แล้วอนุญาตเข้า ScanPartเฉพาะ POที่ยังไม่ RECEIVED

1. State

TextEditingController _poController
POResponse? _po
bool _loadingPo
ApiService _api

dispose controllerถูกต้องและไม่มี FocusNodeเฉพาะ

2. Search command

poId = text.trim().toUpperCase();
setState(() { loading = true; po = null; });
result = await api.getPO(poId);

clear POเดิมก่อน responseป้องกันผู้ใช้กดเริ่มจากข้อมูลเก่าระหว่าง load

3. Endpoint

GET /api/receiving/po/{poId}
→ POResponse(po, supplier, status, items, pendingLines)

path segmentควร encodeด้วย Uriหาก IDมีอักขระพิเศษ ไม่ต่อ stringโดยสมมติรูปแบบเสมอ

4. Error path

empty inputเปิด error dialog; API failureหยุด loadingและแสดง result.error ปัจจุบันใช้ result.error! จึง assume errorไม่ null ควร typed failure/fallbackแน่นอน

5. Start receiving

เมื่อมี POและ statusไม่ใช่ RECEIVED push ScanPartScreenพร้อม snapshot PO หลัง routeกลับเรียก _reloadPO()เพื่อดึง qty/statusล่าสุดจาก server

6. Stale search

ถ้าผู้ใช้ค้น Aแล้ว Bก่อน Aจบ response Aอาจทับ B ต้อง disable/serializeหรือใช้ generationผูก poIdกับ response Mounted guardป้องกัน disposeแต่ไม่ป้องกัน out-of-order

7. UI extraction

PoSearchCardเป็น input/loading action, PoStepIndicatorเป็น flow context จึง test wiringแยกจาก parent orchestrationได้ แต่ source of truthของ queryยังอยู่ parent controller

8. Tests

trim/uppercase, empty, 404, loading, A/B race, RECEIVEDไม่มี start, active PO pushถูก, reloadหลังกลับและ dispose mid-request โดย assert APIเรียกด้วย PO IDจริง
