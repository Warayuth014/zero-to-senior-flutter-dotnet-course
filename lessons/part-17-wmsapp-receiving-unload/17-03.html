2. ค้นหา PO

Future<void> _scanPO() async {
  final poId = _poController.text.trim().toUpperCase();
  if (poId.isEmpty) {
    showErrorDialog(context, message: 'กรุณาใส่ PO ID');
    return;
  }

  setState(() {
    _loadingPo = true;
    _po = null;                  // ← ล้างผลเก่าก่อน
  });

  final result = await _api.getPO(poId);

  if (!mounted) return;

  if (!result.success) {
    setState(() => _loadingPo = false);
    showErrorDialog(context, message: result.error!);
    return;
  }

  setState(() {
    _po = result.data!;
    _loadingPo = false;
  });
}
รายละเอียดทำไมสำคัญบท
trim()เครื่องสแกนบางรุ่นเติมช่องว่างท้าย3.6
toUpperCase()รหัสในระบบเป็นตัวใหญ่ ผู้ใช้พิมพ์เล็กก็ยังหาเจอ3.6
ตรวจว่างก่อนยิงไม่เสียเวลารอเพื่อจะได้ข้อความว่ากรอกไม่ครบ3.7
_po = null ก่อนยิงผู้ใช้ไม่เห็นข้อมูล PO เก่าคู่กับตัวหมุน4.10
if (!mounted) returnจอถูกปิดระหว่างรอได้จริง4.13

ห้าข้อครบ ซึ่งไม่ใช่เรื่องปกติในโค้ดที่เขียนเร็ว

บรรทัด _po = null สำคัญกว่าที่เห็น — ถ้าไม่ล้าง ผู้ใช้ที่ค้นหา PO ใหม่จะเห็นข้อมูลของ PO เก่าค้างอยู่ระหว่างรอ
ในคลังที่ผู้ใช้กดเริ่มรับสินค้าอย่างรวดเร็ว จังหวะนั้นอาจกลายเป็นการเริ่มรับผิดใบ ซึ่งเป็นความผิดพลาดที่แก้ยากมาก

ตรงนี้ปลอดภัยกว่าเพราะ Navigator.push ทำงานทันที ไม่มีช่วงรอให้กดซ้ำ

แต่ _reloadPO() ที่ตามมาไม่มีตัวหมุนบอก — ผู้ใช้กลับมาเห็นข้อมูลเก่าอยู่ครู่หนึ่งแล้วเปลี่ยนเอง

Future<void> _reloadPO() async {
  if (_po == null) return;
  final result = await _api.getPO(_po!.poId);
  if (!mounted) return;
  if (result.success) {
    setState(() => _po = result.data!);
  }
  // ล้มเหลว → เงียบ ข้อมูลค้างเก่า
}

รูปแบบ “ล้มเหลวแล้วเงียบ” เดียวกับ 17.2 — และที่นี่ร้ายกว่า เพราะจำนวนที่รับไปแล้วบนหน้าจอจะไม่ตรงกับความจริง แล้วผู้ใช้อาจตัดสินใจจากตัวเลขนั้น

เอาปุ่มออกแทนที่จะปิดปุ่มปุ่มที่กดไม่ได้ทำให้ผู้ใช้พยายามกดแล้วสงสัยว่าพัง

ต่างจากกรณีใน 17.2 ที่ยังควรให้กดได้ — ที่นั่นข้อมูลอาจไม่ทันสมัย ที่นี่สถานะเป็นข้อเท็จจริงที่เพิ่งดึงมา

หลักที่แยกสองกรณี: เอาปุ่มออกได้ เมื่อเรารู้แน่ว่าทำไม่ได้ และผู้ใช้เห็นเหตุผลบนจอ
ต้องปล่อยให้กดได้ เมื่อเราแค่เดาจากข้อมูลที่อาจเก่า

เงื่อนไข != 'RECEIVED' เขียนแบบตรวจว่าไม่เท่ากับค่าเดียว ซึ่งแปลว่าสถานะอื่นทั้งหมด — OPEN, PARTIAL, และสถานะใหม่ที่ฝั่ง .NET อาจเพิ่มมา — จะได้ปุ่มหมด

ในที่นี้ถูกต้อง เพราะ “ยังไม่ครบ” คือทุกอย่างที่ไม่ใช่ครบ แต่ถ้าวันหนึ่งมีสถานะ CANCELLED ผู้ใช้จะยังกดเริ่มรับใบที่ถูกยกเลิกได้

5. ตัวชี้ขั้นตอน

const PoStepIndicator(),

เป็น const แปลว่าไม่รับค่าอะไรเลย — แสดงขั้นตอนคงที่เหมือนกันตลอด ไม่ได้บอกว่าตอนนี้อยู่ขั้นไหน

แบบคงที่ (ตอนนี้)แบบที่รู้ขั้นตอน
ประโยชน์ผู้ใช้ใหม่รู้ว่า flow มีกี่ขั้นรู้ด้วยว่าอยู่ขั้นไหน

ใช้ const ได้ได้ — ไม่สร้างใหม่ตอน rebuildไม่ได้

สำหรับ flow ที่มีสองขั้นและผู้ใช้ทำทุกวัน แบบคงที่พอ — และการเป็น const ทำให้ Flutter ข้ามการสร้างใหม่ทุกครั้งที่ build ทำงาน ซึ่งในจอนี้เกิดทุกครั้งที่พิมพ์

ตรงกับที่ 1.14 สอนว่าใส่ const ให้ widget ที่ไม่เปลี่ยน — ในจอนี้มีการใช้ const ถูกที่หลายจุด รวมถึงกล่องข้อความ “รับสินค้าครบแล้ว” ที่ทั้งก้อนเป็น const Row

7. แบบฝึกหัด

ผู้ใช้แจ้งว่า “ยิงบาร์โค้ด PO แล้วบางทีขึ้นใบเก่า ต้องยิงใหม่อีกรอบ”

  1. อธิบายว่าเกิดได้อย่างไร
  2. เขียนโค้ดแก้ที่ครอบคลุมทุกกรณี ไม่ใช่แค่กันกดซ้ำ
  3. จะทดสอบว่าแก้ได้จริงอย่างไร ในเมื่อเทสต์ของโปรเจกต์นี้ยังเขียนไม่ได้
แนวคำตอบ

ข้อ 1

t=0.0s  ยิง PO-A → _scanPO() เรียก getPO('PO-A')
t=0.5s  ผู้ใช้เห็นว่ายังไม่ขึ้น ยิง PO-B → _scanPO() เรียก getPO('PO-B')
t=2.0s  คำตอบของ PO-B กลับมาก่อน → setState(_po = PO-B)   ← ถูกต้อง
t=3.5s  คำตอบของ PO-A กลับมาทีหลัง → setState(_po = PO-A)  ← ทับของใหม่

คำขอที่ยิงก่อนไม่จำเป็นต้องกลับมาก่อน — เส้นทางเครือข่ายต่างกัน เซิร์ฟเวอร์ประมวลผลนานไม่เท่ากัน

ผู้ใช้จึงเห็น “ใบเก่า” ซึ่งที่จริงคือใบที่ยิงก่อนหน้า

ข้อ 2 — แก้ให้ครอบคลุม

การกันกดซ้ำ (if (_loadingPo) return;) แก้ได้เฉพาะเคสนี้ แต่ไม่แก้กรณีที่ผู้ใช้กดยกเลิกแล้วยิงใหม่ ทางที่ครอบคลุมกว่าคือทิ้งคำตอบที่ล้าสมัย

int _requestSeq = 0;

Future<void> _scanPO() async {
  final poId = _poController.text.trim().toUpperCase();
  if (poId.isEmpty) {
    showErrorDialog(context, message: 'กรุณาใส่ PO ID');
    return;
  }

  final seq = ++_requestSeq;        // จองหมายเลขของคำขอนี้
  setState(() {
    _loadingPo = true;
    _po = null;
  });

  final result = await _api.getPO(poId);

  if (!mounted) return;
  // มีคำขอใหม่กว่าเกิดขึ้นแล้ว — คำตอบนี้ล้าสมัย ทิ้งไปเงียบ ๆ
  if (seq != _requestSeq) return;

  if (!result.success) {
    setState(() => _loadingPo = false);
    showErrorDialog(context, message: result.error!);
    return;
  }

  setState(() {
    _po = result.data!;
    _loadingPo = false;
  });
}

รูปแบบนี้ตรงกับที่ 12.9 ใช้กับเหตุการณ์ที่มาไม่เรียงลำดับ — ให้แต่ละคำขอมีหมายเลข แล้วยอมรับเฉพาะคำตอบของหมายเลขล่าสุด

ครอบคลุมกรณีกันกดซ้ำอย่างเดียวใช้หมายเลข
ยิงซ้ำระหว่างรอได้ได้
ยิงใบใหม่ระหว่างรอใบเก่าได้ (แต่ผู้ใช้ยิงไม่ได้เลย)ได้ และยิงใบใหม่ได้ทันที
คำตอบมาสลับลำดับไม่ได้ได้

ควรใช้ทั้งสองอย่าง — หมายเลขกันผลลัพธ์ผิด ส่วนการกันกดซ้ำลดคำขอที่ไม่จำเป็น

ข้อ 3 — ทดสอบอย่างไร

16.6 อธิบายว่าจอเทสต์ไม่ได้เพราะ ApiService() เป็น singleton แต่ตรรกะนี้ทดสอบได้ถ้าดึงออกมา

// แยกตัวกันคำตอบล้าสมัยออกมาเป็นของที่ทดสอบได้
class LatestOnly {
  int _seq = 0;

  /// คืน token สำหรับคำขอใหม่
  int begin() => ++_seq;

  /// คำตอบของ token นี้ยังใช้ได้ไหม
  bool isCurrent(int token) => token == _seq;
}
test('คำตอบของคำขอเก่าต้องถูกทิ้ง', () {
  final gate = LatestOnly();
  final first = gate.begin();
  final second = gate.begin();

  expect(gate.isCurrent(first), isFalse);
  expect(gate.isCurrent(second), isTrue);
});

ส่วนการทดสอบด้วยมือบนเครื่องจริง ทำได้โดยจำลองเน็ตช้าตามที่ 15.11 แนะนำ แล้วยิงสองใบติดกัน

ข้อสังเกตที่สำคัญกว่าคำตอบ: อาการที่ผู้ใช้แจ้งคือ “ขึ้นใบเก่า” ซึ่งฟังเหมือนปัญหาแคช แต่ที่จริงเป็นเรื่องลำดับของคำตอบ — คำอธิบายของผู้ใช้บอกสิ่งที่เห็น ไม่ใช่สาเหตุ และการเชื่อคำอธิบายนั้นตรง ๆ จะพาไปหาแคชที่ไม่มีอยู่จริง

8. สรุป

  • จอ 166 บรรทัด state สี่ตัว และสถานะที่เป็นไปได้จริงมีสามชุด
  • ล้าง _po = null ก่อนยิง — กันผู้ใช้กดต่อจากข้อมูลผิดใบ
  • ทำครบทั้ง trim, toUpperCase, ตรวจว่าง, ตรวจ mounted
  • ปุ่มถูกปิดตอนโหลด แต่ช่องข้อความยังรับการสแกนได้ — คำขอซ้อนกันได้
  • คำตอบที่กลับมาทีหลังชนะเสมอ แม้จะเป็นคำขอที่ยิงก่อน
  • แก้ด้วยหมายเลขคำขอ ดีกว่ากันกดซ้ำอย่างเดียว
  • _reloadPO() ล้มเหลวแล้วเงียบ ทำให้ตัวเลขบนจอไม่ตรงกับความจริง
  • เอาปุ่มออกเมื่อรู้แน่ ปล่อยให้กดได้เมื่อแค่เดาจากข้อมูลที่อาจเก่า
