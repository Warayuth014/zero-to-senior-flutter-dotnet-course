Progress ต้องมาจาก line identity: จำนวน part card หรือจำนวนครั้งที่ scan ไม่เท่ากับจำนวนงานสำเร็จ ให้คำนวณจาก session items และ confirmed line IDs เท่านั้น

1. Scan pallet

trim palletId, reject ค่าว่าง, lock ระหว่าง request แล้วเรียก POST /unload/open-session พร้อม operatorId หาก scan pallet ใหม่ต้องถามยืนยันเมื่อ session เดิมยังมีงาน pending

2. Build progress

totalCount = session.items.length
confirmedCount = items.where(
  (x) => status[x.lineId] == 'CONFIRMED'
).length
allConfirmed = totalCount > 0 && confirmedCount == totalCount

นิยาม empty session แยกจาก completed เพื่อไม่แสดงสำเร็จทั้งที่ไม่มีข้อมูล

3. Scan part

ค้นหา item ที่ partId ตรงและยัง PENDING ถ้ามีหนึ่งรายการเลือกได้ทันที ถ้ามีหลาย lot ให้แสดงตัวเลือกที่มี lot, condition และ qty เพื่อยืนยัน identity ก่อนกรอกจำนวน/serial

4. Serial item

serial ที่ scan ต้องอยู่ใน item.serialNumbers, ไม่ซ้ำใน local set และจำนวนต้องตรงยอดที่จะ unload การใช้ Set ช่วย duplicate lookup แต่ควรเก็บ List เพิ่มหากลำดับ scan มีความหมายต่อ audit/UI

5. Non-serial item

parse qty แบบปลอดภัย ตรวจ finite/integer ตามหน่วยธุรกิจ, มากกว่า 0 และไม่เกินยอด line ปัจจุบัน ข้อความผิดควรระบุค่าที่รับได้ ไม่ใช่เพียง “invalid quantity”

6. Confirm unload

POST /unload/confirm-unload
{
  "sessionId": session.sessionId,
  "palletId": session.pallet.id,
  "partId": item.partId,
  "lineId": item.lineId,
  "operatorId": operatorId,
  "serialNumbers": serials,
  "qtyUnloaded": qty
}

7. Return pallet

return-pallet-to-asis เป็น transition ปิดงานที่มีผลต่อ inventory ต้องยืนยัน allConfirmed ตามกติกา, ป้องกันกดซ้ำ และใช้ผลจาก API เป็นหลัก การหน่วงเวลา 5 วินาทีใน UI ไม่ใช่หลักฐานว่า backend ทำงานเสร็จ ควรใช้ status/polling หรือ operation result

8. Concurrency tests

จำลองสองเครื่องเปิด pallet เดียวกัน, line ถูก confirm จากอีกเครื่อง, partial unload สร้าง line ใหม่, session หมดอายุ และ return pallet ชนกับ confirm โดยคาดหวัง conflict ที่ refresh แล้วทำต่อได้
