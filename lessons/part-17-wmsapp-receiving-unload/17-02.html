ReceivingMenu เป็น dashboardเล็ก: มีสอง card—เริ่มรับเอกสารและรายการค้างผูก pallet—พร้อม badgeที่นับจาก server ไม่ใช่ local cache

1. Inputs

ReceivingMenuScreenรับ userId/fullNameจาก HomeScreen ใช้ fullNameใน AppBarและส่งทั้งคู่ต่อ routeลูก ไม่มี session lookupซ้ำในเมนู

2. Pending count

initState() → _loadPendingCount()
→ getPendingPalletLines()
→ count = result.data!.length

failureถูกละเลยและ countคง 0 จึงแยกไม่ได้ว่าไม่มีค้างหรือโหลดล้ม

3. Refresh on return

await Navigator.push(...ScanPoScreen...);
_loadPendingCount();

ทำเหมือนกันกับ PendingPalletScreen จึงสะท้อนรายการใหม่หลังรับ/assign แต่ควรเช็ก mounted/generationและมี loading/error state

4. Card semantics

ReceivingMenuCardรับ icon/title/subtitle/color/badge/onTap เมื่อ pending>0ใช้ dangerและ badge count; เมื่อ 0ใช้ textGrey เป็น presentation componentที่ไม่รู้ API

5. Route A

“รับเอกสาร” push ScanPoScreen(userId, fullName) แล้ว workflowภายในเลือก POและรับสินค้า

6. Route B

“ค้างการผูก Pallet” push PendingPalletScreen เพื่อแก้รายการที่ receiptสำเร็จแต่ palletยังไม่ผูก เมนูจึงเป็น recovery entry point ไม่ใช่แค่ navigation

7. Race

ถ้ากลับ routeเร็วแล้ว refreshหลายครั้ง responseเก่าอาจทับใหม่ แม้เป็น countอย่างเดียวควรใช้ single-flight/generation และแสดง retryเมื่อโหลดล้มแทน count 0หลอก

8. Tests

0/positive badge, API failure, refreshหลังทั้ง routes, disposeระหว่าง load, double tapไม่ pushซ้ำ และ constructorส่ง user identityถูก โดย fake ReceivingRepositoryแทน singleton
