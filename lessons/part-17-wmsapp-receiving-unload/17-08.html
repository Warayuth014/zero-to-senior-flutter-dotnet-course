6. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง

7. แบบฝึกหัด

หัวหน้ากะบอกว่า “ของค้าง 40 รายการจาก PO เดียวกัน จะลงพาเลทเดียวกันหมด แต่ต้องมานั่งกด 40 รอบ”

  1. ทำไมทำเป็นชุดไม่ได้ในตอนนี้ ทั้งที่ API รองรับ
  2. ออกแบบวิธีที่ผู้ใช้เลือกหลายรายการแล้วผูกครั้งเดียว
  3. ต้องระวังอะไรที่ต่างจากการผูกทีละรายการ
แนวคำตอบ

ข้อ 3 — ต้องระวังอะไร

เรื่องทำไมต่างจากทีละรายการ
สภาพต้องตรงกันทุกรายการผูกทีละอันตรวจได้จากรายการนั้น แต่ 40 รายการอาจมีทั้ง FG และ PW ปน
สำเร็จบางส่วนเซิร์ฟเวอร์อาจผูกได้ 37 จาก 40 แล้วผู้ใช้ต้องรู้ว่าอีก 3 คืออะไร
เวลาที่ใช้คำขอเดียวแต่ทำงานหนักกว่า — timeout 10 วินาทีอาจไม่พอ
ยกเลิกกลางคันผู้ใช้กดย้อนกลับตอนกำลังผูก 40 รายการ ต้องรู้ว่าผูกไปแล้วกี่อัน

ข้อแรกกันได้ตั้งแต่ตอนเลือก

ถ้าเป็นแบบที่สองและแอปไม่อ่าน ผู้ใช้จะเห็น “สำเร็จ” แล้วเดินจากไป ทั้งที่ยังมีของค้าง 3 รายการ — ซึ่งแย่กว่าการผูกทีละอันมาก เพราะการผูกทีละอันไม่มีทางเข้าใจผิดแบบนี้

ข้อสรุปที่สำคัญ: การทำงานเป็นชุดประหยัดเวลาผู้ใช้ แต่ทำให้ “สำเร็จบางส่วน” เป็นสถานะที่ต้องออกแบบ ก่อนเขียนโค้ดต้องรู้ก่อนว่าเซิร์ฟเวอร์ทำแบบไหน — ไม่ใช่เดา

8. สรุป

  • จอนี้มีอยู่เพราะกรณีสำเร็จครึ่งทางใน 17.7 และแสดงของค้างทั้งคลัง
  • จัดกลุ่มตาม PO ด้วย putIfAbsent แต่คำนวณใน build() ทุกครั้ง
  • มี RefreshIndicator ซึ่ง ReceivingMenuScreen ยังไม่มี
  • แยกสถานะโหลด/ว่าง/มีข้อมูล แต่ยังไม่แยกสถานะโหลดไม่สำเร็จ
  • StatefulBuilder ให้กล่องมีสถานะของตัวเองโดยไม่วาดจอใหม่ทั้งจอ
  • ปิดครบสามทางเข้า: ปุ่มยืนยัน ปุ่มยกเลิก และ onSubmitted
  • ความจำพาเลทมีเฉพาะใน ScanPartScreen — ผู้ใช้ที่นี่ต้องสแกนซ้ำทุกรายการ
  • จัดการ context สองตัวได้ครบ รวมถึงตรวจ dlgCtx.mounted
  • API รับหลายรายการได้แต่แอปส่งทีละหนึ่งเสมอ

บทหน้า: โมเดลและ API ของ receiving ทั้งชุด และฟิลด์ที่จะพังถ้าฝั่ง .NET เปลี่ยน
