2. สองระดับของการบอกผู้ใช้

สังเกตว่าด่าน 3 กับด่านอื่นบอกผู้ใช้คนละแบบ

ด่านวิธีบอกต้องกดปิดไหม
3 สแกนซ้ำแถบลอย + ไฮไลต์แถวที่ซ้ำไม่ต้อง
1, 2, 4กล่องข้อความกลางจอต้อง

เป็นการตัดสินใจที่ถูก — การสแกนซ้ำเกิดบ่อยมากในคลัง (ผู้ใช้ยิงสองครั้งเพราะไม่แน่ใจว่าติดหรือยัง) ถ้าเด้งกล่องทุกครั้งจะทำงานไม่ได้เลย

void _showScanStatus(String message, {_ScanStatusTone tone = _ScanStatusTone.success}) {
  _scanStatusTimer?.cancel();          // ยกเลิกตัวเก่าก่อนเสมอ
  setState(() {
    _scanStatusMessage = message;
    _scanStatusTone = tone;
  });
  _scanStatusTimer = Timer(const Duration(seconds: 5), _hideScanStatus);
}

_scanStatusTimer?.cancel() บรรทัดแรกป้องกันปัญหาที่เจอบ่อย — ถ้าไม่ยกเลิก ตัวจับเวลาของข้อความก่อนหน้าจะมาปิดข้อความใหม่ก่อนเวลา

t=0s   สแกนตัวที่ 1 สำเร็จ → ข้อความขึ้น, ตั้งเวลา A ปิดที่ t=5
t=1s   สแกนตัวที่ 2 สำเร็จ → ข้อความใหม่, ตั้งเวลา B ปิดที่ t=6
t=5s   ถ้าไม่ยกเลิก A → A ปิดข้อความของตัวที่ 2 ทั้งที่เพิ่งขึ้นได้ 4 วินาที

และตัวจับเวลาถูกยกเลิกใน dispose() ด้วย — ครบตามที่ 12.8 สอน

มีอีกเมธอดที่น่าสนใจ

void _holdScanStatus() {
  _scanStatusTimer?.cancel();
  _scanStatusTimer = null;
}

ค้างข้อความไว้ไม่ให้หายเอง ใช้ตอนที่ต้องการให้ผู้ใช้อ่านจนกว่าจะทำอย่างอื่น

3. เลื่อนไปหาแถวที่ซ้ำ

void _markScannedSerial(String serialNo, {bool duplicate = false}) {
  setState(() {
    _highlightedSerial = serialNo;
    _highlightedSerialDuplicate = duplicate;
  });

  WidgetsBinding.instance.addPostFrameCallback((_) {
    final index = _serialNumbers.indexOf(serialNo);
    if (index < 0 || !_serialListController.hasClients) return;

    final target = (index * _serialRowHeight)
        .clamp(0.0, _serialListController.position.maxScrollExtent)
        .toDouble();
    _serialListController.animateTo(
      target,
      duration: const Duration(milliseconds: 220),
      curve: Curves.easeOut,
    );
  });
}

ผู้ใช้ที่สแกนซ้ำจะเห็นรายการเลื่อนไปหาแถวที่ซ้ำและแถวนั้นถูกไฮไลต์ — บอกได้ทันทีว่าซ้ำกับอันไหน

รายละเอียดทำไมจำเป็น
addPostFrameCallbackต้องรอให้ setState วาดเสร็จก่อน ไม่งั้น maxScrollExtent ยังเป็นค่าเก่า
hasClientsถ้ารายการยังไม่ถูกวาด ScrollController ยังไม่ผูกกับอะไร — เรียก position จะพัง
clampตำแหน่งที่คำนวณอาจเกินความยาวจริง
คูณด้วย _serialRowHeightคำนวณตำแหน่งจากความสูงคงที่ต่อแถว

บรรทัดสุดท้ายทำงานได้เพราะทุกแถวสูงเท่ากันจริง — ค่าคงที่ _serialRowHeight = 42 ถูกใช้ทั้งตอนวาดและตอนคำนวณตำแหน่ง

หลังเซิร์ฟเวอร์ตอบว่า S/N ถูกต้อง ยังมีการตรวจอีกชั้น

เซิร์ฟเวอร์ตอบว่า “S/N นี้มีอยู่จริง” แต่ไม่ได้บอกว่าตรงกับล็อตที่ผู้ใช้กำลังรับ — แอปจึงต้องเทียบเอง

สถานการณ์เซิร์ฟเวอร์ตอบแอปตัดสิน
S/N ของล็อตที่กำลังรับสำเร็จ + lineId ตรงรับ
S/N ของล็อตอื่นใน PO เดียวกันสำเร็จ + lineId ไม่ตรงปฏิเสธ
S/N ที่ไม่มีในระบบล้มเหลวปฏิเสธ

แถวกลางคือกรณีที่เกิดจริงในคลัง — ผู้ใช้หยิบกล่องผิดล็อตมาสแกน ถ้าไม่มีด่านนี้ ของจะถูกบันทึกเข้าล็อตผิด และเป็นความผิดพลาดที่แก้ยากมากเพราะระบบเชื่อว่าถูกแล้ว

ข้อความที่บอกผู้ใช้ทำได้ดีมาก

'S/N "SN-4471" ไม่ตรงกับ Lot "LOT-A" ที่กำลังรับ (จริงๆ อยู่ Lot "LOT-B")'
ข้อความบอกผู้ใช้ทำอะไรต่อได้
ตัวที่สแกนคืออะไรยืนยันว่าอ่านถูกตัว
กำลังรับล็อตไหนอยู่รู้ว่าตัวเองอยู่ตรงไหน
ของจริงอยู่ล็อตไหนรู้ว่าต้องไปหยิบกล่องไหนมาแทน

แถวสุดท้ายคือสิ่งที่ทำให้ข้อความนี้ต่างจาก “S/N ไม่ถูกต้อง” — ผู้ใช้ไม่ต้องเดินไปถามใคร

สังเกต ?? "ไม่ทราบ" ด้วย — เซิร์ฟเวอร์อาจไม่ส่ง lotNumber มา ข้อความก็ยังอ่านได้ไม่พังกลางประโยค

6. จำนวนสูงสุดที่คำนวณสองแบบ

final maxQty = item.qtyRemaining > 0 ? item.qtyRemaining : item.qtyOrdered;

บรรทัดนี้ปรากฏสองที่ — ใน _addSerial และใน _confirmPart

qtyRemainingใช้ค่าไหนทำไม
> 0qtyRemainingรับไปแล้วบางส่วน เหลือเท่านี้
0qtyOrderedถือว่ายังไม่เคยรับ ใช้จำนวนสั่งเต็ม

แถวที่สองน่าสงสัย — qtyRemaining == 0 ควรแปลว่ารับครบแล้ว ไม่ใช่ยังไม่เคยรับ

ย้อนไปดูโมเดล

qtyRemaining: json['qtyRemaining'] ?? 0,

ถ้าฝั่ง .NET ไม่ส่ง qtyRemaining มา จะได้ 0 — และโค้ดนี้ตีความว่า “ยังไม่เคยรับ” แล้วอนุญาตให้รับเต็มจำนวน

สถานการณ์qtyRemainingmaxQty ที่ได้ถูกไหม
สั่ง 10 รับแล้ว 466ถูก
สั่ง 10 รับครบ 10010ผิด — รับซ้ำได้อีก 10
เซิร์ฟเวอร์ไม่ส่งค่ามา010ตั้งใจให้เป็นแบบนี้

แถวกลางไม่เกิดในทางปฏิบัติ เพราะรายการที่รับครบจะมี status == 'RECEIVED' และถูกกรองออกจากรายการที่แสดง

final pendingItems = _currentPo.items
    .where((item) => item.status != 'RECEIVED')
    .toList();

แต่การป้องกันอยู่ที่การกรองในหน้าจอ ไม่ใช่ที่การคำนวณจำนวน — ถ้าวันหนึ่งมีทางเข้าที่ข้ามการกรอง (เช่นสแกน Part โดยตรงซึ่ง _scanPartId ทำอยู่แล้ว) ตัวเลขจะผิด

ตรวจสอบจริง: _scanPartId() สร้าง POItem เองด้วย orElse เมื่อหาไม่เจอใน _currentPo.items
orElse: () => POItem(
  ...
  qtyOrdered: lot.qtyOrdered,
  qtyReceived: lot.qtyReceived,
  qtyRemaining: lot.qtyOrdered - lot.qtyReceived,   // ← คำนวณเอง ปลอดภัย
  status: 'PENDING',
  ...

ตรงนี้คำนวณ qtyRemaining เองจากผลต่าง จึงไม่พึ่งค่าที่เซิร์ฟเวอร์ส่ง — เป็นการป้องกันที่ทำไว้แล้วโดยไม่ได้เขียนคอมเมนต์อธิบาย

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
ลำดับของการตรวจไม่สำคัญตรวจในเครื่องก่อนยิงเน็ต ทำให้ flow ใช้ได้จริง
ทุกความผิดพลาดควรเด้งกล่องสแกนซ้ำเกิดบ่อยเกินกว่าจะเด้งได้
เซิร์ฟเวอร์บอกว่า S/N ถูก แปลว่ารับได้ต้องเทียบ lineId กับล็อตที่กำลังรับ
ส่งรายการเดิมเข้าไปได้เลยต้องคัดลอก ไม่งั้นถูกล้างกลางทาง
qtyRemaining == 0 แปลว่ารับครบโค้ดนี้ตีความว่ายังไม่เคยรับ
ตัวจับเวลาตัวใหม่ทับตัวเก่าเองต้อง cancel() เอง

8. แบบฝึกหัด

ผู้ใช้แจ้งว่า “สแกน S/N ครบ 5 ตัวแล้ว กดยืนยัน ขึ้นว่าจำนวนไม่ตรง แต่นับดูก็ 5 ตัว”

  1. ไล่ว่าเงื่อนไขไหนที่ปฏิเสธ และเป็นไปได้อย่างไร
  2. ถ้าเป็นบั๊กจริง จะแก้ที่ไหน
  3. ข้อความปฏิเสธควรเขียนใหม่ว่าอย่างไร
แนวคำตอบ

ข้อ 1 — ไล่เงื่อนไข

serialNumbers = _serialPartId == poItem.partId && _serialNumbers.length == qty
    ? List<String>.of(_serialNumbers)
    : null;

มีสองทางที่จะได้ null

ทางเกิดเมื่อผู้ใช้เห็นอะไร
_serialPartId != poItem.partIdS/N ที่สแกนไว้เป็นของสินค้าคนละตัวนับดูก็ 5 ตัว — ตรงกับที่แจ้ง
_serialNumbers.length != qtyจำนวนไม่ตรงจริงนับแล้วต้องไม่ตรง

เนื่องจากผู้ใช้บอกว่านับได้ 5 ตัว ทางแรกน่าสงสัยกว่า

เกิดได้จากสถานะที่ 17.5 ข้อ 2 อธิบายไว้

ผู้ใช้สแกน Part A → _scanningItem = A, _serialPartId = 'A'
  → สแกน S/N ของ A ไป 5 ตัว
    → กดปุ่ม "ผูก" ที่รายการค้าง → _pendingLine มีค่า
      → ผูกพาเลทเสร็จ กลับมาโหมด A
        → _scanningItem ยังเป็น A แต่ _currentPo ถูกโหลดใหม่
          → poItem ที่ส่งเข้า _confirmPart อาจเป็นตัวใหม่ที่ partId ต่าง

แต่ยังมีอีกทางที่ตรงกว่า

ผู้ใช้สแกน Part A → สแกน S/N 5 ตัว
  → เปลี่ยนใจ ลบ S/N จนหมด → _clearSerialScan() → _serialPartId = null
    → สแกน Part B → _serialPartId = 'B'
      → สแกน S/N ของ B ไป 5 ตัว
        → กดยืนยัน → ตรงหมด ไม่มีปัญหา

ทางนี้ไม่เกิดปัญหา แสดงว่าต้องมีเส้นทางที่ _scanningItem เปลี่ยนโดย _serialPartId ไม่เปลี่ยน หรือกลับกัน

ไล่ดูว่ามีที่ไหนตั้ง _scanningItem บ้าง — เจอที่เดียวคือ _scanPartId() ซึ่งตั้งทั้งสองตัวพร้อมกัน

setState(() {
  _scanningItem = resolvedItem;
  _serialPartId = partId;          // ตั้งพร้อมกัน
  ...
});

สังเกตว่า partId ที่ตั้งคือค่าที่ผู้ใช้สแกนมา ส่วน resolvedItem.partId อาจต่างกันได้ ถ้ามาจาก orElse

orElse: () => POItem(
  id: lot.id,
  partId: partId,        // ← ตรงกัน ในกรณีนี้
  ...

ตรงกัน แต่กรณีที่หาเจอใน _currentPo.items

final resolvedItem = _currentPo.items.firstWhere((i) => i.id == lot.id, orElse: ...);

เทียบด้วย id ไม่ใช่ partId — ถ้าฝั่ง .NET มีข้อมูลที่ id เดียวกันแต่ partId ต่าง (เช่นรหัสสินค้าถูกแก้) resolvedItem.partId จะไม่เท่ากับ partId ที่สแกน แล้วเงื่อนไขจะปฏิเสธ

ข้อ 2 — แก้ที่ไหน

แก้ให้ทั้งสองที่อ้างค่าเดียวกัน

setState(() {
  _scanningItem = resolvedItem;
  _serialPartId = resolvedItem.partId;   // ← ใช้ค่าจากตัวที่จะใช้ยืนยันจริง
  ...
});

แต่วิธีที่ปิดปัญหาถาวรคือเลิกเก็บ _serialPartId แยก แล้วเก็บ S/N ไว้ในโหมดเดียวกับสินค้าตามที่ 17.5 ข้อ 3 เสนอ

class Scanning extends ScanMode {
  Scanning(this.item);
  final POItem item;
  final List<String> serials = [];    // ผูกกับ item เสมอ ไม่มีทางไม่ตรง
}

เมื่อ S/N อยู่ในวัตถุเดียวกับสินค้า ไม่มีทางที่จะเป็นของคนละตัวได้เลย

ข้อ 3 — ข้อความที่ควรเป็น

ปัจจุบัน

'จำนวน S/N (5) ไม่ตรงกับจำนวนรับ (5)'    // ← อ่านแล้วงงมาก

ผู้ใช้เห็นตัวเลขเท่ากันแต่ถูกบอกว่าไม่ตรง ซึ่งทำให้เชื่อว่าแอปพัง

ต้องแยกสองสาเหตุออกจากกัน

if (_serialPartId != poItem.partId) {
  showErrorDialog(
    context,
    message: 'S/N ที่สแกนไว้เป็นของ "$_serialPartId" '
        'แต่กำลังยืนยัน "${poItem.partId}" — กรุณาสแกน S/N ใหม่',
  );
  return;
}
if (_serialNumbers.length != qty) {
  showErrorDialog(
    context,
    message: 'สแกน S/N ไว้ ${_serialNumbers.length} ตัว '
        'แต่จำนวนที่จะรับคือ $qty',
  );
  return;
}

หลักที่ใช้: ข้อความที่รวมสองสาเหตุเข้าด้วยกันจะอธิบายได้ดีแค่สาเหตุเดียว — ถ้าเงื่อนไขมีสองส่วน ข้อความก็ต้องมีสองแบบ

และข้อความแรกมีค่ามากที่สุด เพราะบอกได้ว่าระบบสับสนระหว่างสินค้าสองตัว ซึ่งเป็นข้อมูลที่ผู้ใช้เอาไปแจ้งทีมได้ ต่างจาก “ไม่ตรง” ที่ไม่บอกอะไรเลย

9. สรุป

  • _addSerial() มีห้าด่าน สามด่านแรกตรวจในเครื่อง ด่านที่แพงที่สุดอยู่ท้าย
  • การสแกนซ้ำใช้แถบลอยไม่ใช่กล่อง เพราะเกิดบ่อยเกินกว่าจะให้กดปิดทุกครั้ง
  • _scanStatusTimer?.cancel() ก่อนตั้งตัวใหม่เสมอ ไม่งั้นตัวเก่าปิดข้อความใหม่
  • การเลื่อนไปหาแถวที่ซ้ำต้องอยู่ใน addPostFrameCallback และตรวจ hasClients
  • มีด่านที่หก — เทียบ lineId เพราะเซิร์ฟเวอร์ตอบว่า S/N มีจริงแต่ไม่บอกว่าตรงล็อต
  • ข้อความบอกด้วยว่าของจริงอยู่ล็อตไหน ผู้ใช้จึงไปหยิบถูก
  • _confirmPart ตรวจซ้ำอีกชั้นว่า S/N เป็นของสินค้าตัวที่กำลังยืนยัน
  • List<String>.of() คัดลอกก่อนส่ง ไม่งั้นรายการถูกล้างกลางทาง
  • ข้อความที่รวมสองสาเหตุจะอธิบายได้ดีแค่สาเหตุเดียว
