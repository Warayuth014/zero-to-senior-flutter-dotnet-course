1. Part นี้อ่านอะไร

Part 16 ทำแผนที่ทั้งโปรเจกต์ Part นี้ลงลึกที่สองโดเมนแรก — Receiving (รับสินค้าจากผู้ขาย) และ Unload (ถ่ายของจากพาเลทลงตะกร้า)

สองโดเมนนี้ถูกจับมาไว้ Part เดียวกันเพราะเป็นขาเข้าทั้งคู่ — ของเข้าคลังผ่าน Receiving แล้วถูกถ่ายลงตะกร้าผ่าน Unload ก่อนจะไปสู่การจัดเก็บ

สิบเอ็ด endpoint สำหรับ 5,392 บรรทัด — สัดส่วนนี้บอกว่าโค้ดส่วนใหญ่ไม่ได้ใช้คุยกับเซิร์ฟเวอร์ แต่ใช้จัดการสถานะบนหน้าจอ

สังเกตแถวที่ 2 กับ 3 — เป็น path เดียวกันแต่ส่งพารามิเตอร์ต่างกัน

// ส่งแค่ partId → ถามว่ามีกี่ condition/lot ให้เลือก
Uri(path: '/receiving/validate-serial', queryParameters: {'partId': partId})

// ส่ง partId + serialNo → ถามว่า S/N นี้ถูกต้องไหม
Uri(path: '/receiving/validate-serial',
    queryParameters: {'partId': partId, 'serialNo': serialNo})

endpoint เดียวทำสองงานที่ต่างกันตามพารามิเตอร์ที่ส่งมา — ประหยัดฝั่งเซิร์ฟเวอร์ แต่ชื่อ validate-serial ไม่ได้บอกว่าเรียกโดยไม่มี serial ก็ได้ ต้องอ่านโค้ดฝั่งแอปถึงจะรู้

6. รูปแบบที่ซ้ำกันทั้งสองโดเมน

ทุกจอในสองโดเมนนี้เดินตามโครงเดียวกัน

class _XxxScreenState extends State<XxxScreen> {
  final _api = ApiService();               // 1. เชื่อมต่อ
  final _xxxController = TextEditingController();   // 2. ช่องสแกน
  final _xxxFocus = FocusNode();

  bool _loading = false;                   // 3. สถานะ
  SomeModel? _data;

  @override
  void initState() {
    super.initState();
    _load();                               // 4. โหลดตอนเปิด
  }

  Future<void> _load() async {
    setState(() => _loading = true);
    final result = await _api.something();
    if (!mounted) return;                  // 5. ตรวจก่อน setState
    setState(() => _loading = false);
    if (!result.success) {
      showErrorDialog(context, message: result.error!);
      return;
    }
    setState(() => _data = result.data);
  }

  @override
  void dispose() {                         // 6. คืนทรัพยากร
    _xxxController.dispose();
    _xxxFocus.dispose();
    super.dispose();
  }
}

หกขั้นนี้ตรงกับที่ Part 4 สอนทุกข้อ อ่านจอแรกเข้าใจแล้วจะอ่านจอที่เหลือได้เร็ว

สิ่งที่ต่างกันในแต่ละจอคือสิ่งที่อยู่ระหว่างขั้น 3 กับ 4 — จำนวน state ที่ถือ

8. แบบฝึกหัด

ยังไม่ต้องเปิดไฟล์ ใช้ข้อมูลในบทนี้ตอบ

  1. ถ้าผู้ใช้แจ้งว่า “สแกน Part แล้วเด้งถามว่าจะรับอันไหน แต่กดยกเลิกแล้วสแกนใหม่ไม่ได้” จะเปิดไฟล์ไหน และคาดว่าสาเหตุอยู่ที่ไหน
  2. ทำไม UnloadSessionSheet ถึงมีไฟล์ย่อยรวมกันมากกว่าตัวเอง แต่ ScanPartScreen กลับกัน
แนวคำตอบ

ข้อ 1

scan_part_screen.dart — และคาดว่าสาเหตุคือสถานะค้าง

อาการ “กดยกเลิกแล้วสแกนใหม่ไม่ได้” แปลว่ามีฟิลด์บางตัวถูกตั้งค่าไว้ตอนเริ่มสแกน แล้วไม่ถูกล้างเมื่อผู้ใช้ยกเลิก

จาก 27 ฟิลด์ ตัวที่น่าสงสัยคือตัวที่ควบคุมว่าช่องสแกนใช้ได้หรือไม่ — 17.5 จะเจอว่าเป็น _scanningItem และช่อง Part ถูกปิดด้วย enabled: _scanningItem == null

วิธีเข้าเร็วที่สุดคือค้นคำว่า enabled: ในไฟล์นั้น แล้วดูว่าเงื่อนไขขึ้นกับฟิลด์ไหน จากนั้นค้นว่าฟิลด์นั้นถูกตั้งค่าและถูกล้างที่ไหนบ้าง

คำอธิบายที่น่าจะถูกที่สุดคือความซับซ้อนของกฎ ไม่ใช่ความขยันของคนเขียน

Unload มีกฎเดียว: ของบนพาเลทมีอะไรบ้าง ยืนยันทีละรายการจนครบ

Receiving มีกฎซ้อนกันหลายชั้น: Part → เลือก Condition → เลือก Lot → สแกน S/N หรือกรอกจำนวน → เลือกพาเลท → บันทึก → อาจล้มเหลวครึ่งทาง → ต้องตามเก็บ

ตรรกะที่ซ้อนกันแบบนี้แตกออกเป็น widget ไม่ได้ เพราะมันไม่ใช่ส่วนที่วาดหน้าจอ — ต้องแตกออกเป็นชั้นที่ถือสถานะ ซึ่งโปรเจกต์นี้ยังไม่มี

ข้อสรุปที่ใช้ได้ทั่วไป: ถ้าจอหนึ่งแตกไฟล์ไปแล้วแต่ยังใหญ่อยู่ แปลว่าสิ่งที่เหลือไม่ใช่ UI — และการแตกเป็น widget เพิ่มจะไม่ช่วย ต้องย้ายตรรกะออกไปที่ store ตามที่ 9.7 สอน ซึ่ง Part 23 จะทำจริง

9. สรุป

  • Receiving + Unload = 28 ไฟล์ 5,392 บรรทัด คิดเป็น 24% ของโปรเจกต์
  • Receiving มีสามจอหลัก จอสุดท้ายยาว 1,727 บรรทัด
  • Unload ใช้ bottom sheet เป็นหัวใจของ flow ไม่ใช่จอ
  • สิบเอ็ด endpoint สำหรับ 5,392 บรรทัด — โค้ดส่วนใหญ่จัดการสถานะบนจอ
  • /receiving/validate-serial ทำสองงานตามพารามิเตอร์ที่ส่ง
  • ทุกจอเดินตามโครงหกขั้นเดียวกัน สิ่งที่ต่างคือจำนวน state ที่ถือ
  • จำนวนฟิลด์ใน State ทำนายความยากได้แม่นกว่าจำนวนบรรทัด
  • Part เดียวมีหลาย Condition และหลาย Lot คือต้นเหตุของความซับซ้อนทั้งหมด
