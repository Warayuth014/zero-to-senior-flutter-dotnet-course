Inbound มีสองการเปลี่ยน ownership: Receiving ยืนยันของจาก POเข้า WMSและผูก pallet; Unloadเปิด palletจาก ASRSแล้วแยก Part/Lotออกก่อน Load to Basket ทุก commandต้องรักษา line/lot/serial identity

1. Receiving route

Home → ReceivingMenu
  → ScanPo → ScanPart
  → PendingPallet (แก้ partial assignment)

Homeส่ง userId/fullName; Receiving menu refresh pending countทุกครั้งที่ routeลูกกลับ

2. Receiving data flow

PO ID → POResponse
Part ID → PartLinesResponse
→ choose condition + lot
→ validate serial(s) / manual qty
→ scanReceiptPart(..., palletId)
→ ReceiptLineResponse

3. Unload route

Home → UnloadMenu
  → UnloadScreen → UnloadSessionSheet
  → LoadToBasketScreen

Unloadและ Basketเป็นคนละ endpoint/state แม้หน้าต่อกันทางธุรกิจ

4. Identity keys

poIdระบุเอกสาร, lineIdระบุ Part+condition+lot, partIdอย่างเดียวไม่พอ, serialNoระบุชิ้น, palletId/basketIdระบุ container และ sessionIdผูก unload operation

5. Source ownership

Screen Stateถือ controllers/focus/loading/selections, ApiService extensionsประกอบ transport, models parse DTO และ serverเป็น authorityของ qty/status/assignment หลัง commandสำเร็จ flowที่ดี reload authoritative snapshotแทน patchซับซ้อนเอง

6. Partial success

Receiving APIอาจบันทึกรับสำเร็จแต่ผูก palletล้ม โดยคืน palletError Screenต้องเก็บ lineไว้ pendingและห้าม resend receiptทั้งก้อน นี่เป็น outcomeแบบ “success + follow-up required” ไม่ใช่ boolean errorธรรมดา

7. Failure boundaries

POไม่พบ, condition/lotไม่ตรง, serialซ้ำ/ผิด line, qtyเกิน, pallet typeขัดกัน, unload partial remainder, session staleและ basket loadซ้ำ แต่ละจุดควรมี typed outcome/idempotency ไม่ใช้ข้อความเป็น control flow

8. Trace rule

ทุก actionให้จด stateก่อน → API method/path/payload → response DTO → stateหลัง → focus/navigation → retry semantics โดยเฉพาะ “serverทำสำเร็จแต่ clientไม่เห็น response”
