Model คือขอบเขตความจริงของแอป: อ่าน JSON ให้ได้ไม่พอ ต้องรู้ว่า field ใดเป็น identity, field ใด nullable และ fallback แบบใดอาจซ่อนข้อมูลเสียจาก backend

1. Receiving API surface

ReceivingApi มี 6 งานหลัก: อ่าน PO, อ่าน part lines, validate serial, scan receipt, assign pallet และอ่าน pending pallet lines หน้าจอควรเรียกผ่าน service นี้แทนประกอบ URL เอง

2. POResponse

POResponse รวม header, items และ pendingLines จึงเป็น snapshot ของ receiving document ณ เวลาหนึ่ง วันที่ parse ไม่ได้ถูก fallback เป็น DateTime.now() ในโค้ดจริง ซึ่งทำให้ข้อมูลเสียดูเหมือนข้อมูลใหม่ ควรพิจารณา nullable หรือ parse error ที่สังเกตได้

3. POItem identity

POItem.id ใช้แทน line/lot identity ส่วน partId คือรหัสสินค้า หนึ่ง part อาจมีหลาย lot หรือ condition จึงห้ามใช้ partId เป็น key เดี่ยวเมื่อเลือกบรรทัดรับสินค้า

4. PartLinesResponse

โครงสร้าง PartLinesResponse → PartLine(condition) → PartLot(id, lot, qty) อธิบายเหตุผลที่ UI ต้องให้เลือก condition และ lot ก่อนจะได้ lineId ที่แน่นอนสำหรับการรับ

5. Serial validation result

ValidateSerialResponse ส่ง lineId, poId, condition และ lot กลับมา Client ต้องเทียบ lineId กับ item ที่กำลังรับ ไม่ควรเชื่อเพียงว่า serial มีอยู่ เพราะ serial อาจเป็นของอีก lot หรืออีก PO

6. Receipt response

ReceiptLineResponse มี palletId, palletError, autoClosed, poStatus และ closeMessage จึงแทนผลหลายมิติ: receipt สำเร็จหรือไม่, assignment สำเร็จหรือไม่ และ PO ปิดแล้วหรือยัง

7. Endpoint contracts

GET  /receiving/po/{poId}
GET  /receiving/validate-serial?partId=...&serialNo=...
POST /receiving/scan-part
POST /receiving/assign-pallet
GET  /receiving/pending-pallet-lines

query ต้อง encode ค่า, JSON key ต้องตรง DTO และ error response ควรแปลงเป็น domain exception ที่ UI เข้าใจ

8. Contract hardening

เพิ่ม fixture tests สำหรับ missing/null/wrong type, unknown status, invalid date, empty serial list และ palletError พร้อมแยก transport DTO ออกจาก domain model เพื่อให้ API เปลี่ยนโดยไม่กระจายผลไปทุก widget
