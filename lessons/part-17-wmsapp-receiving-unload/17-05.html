2. เครื่องสถานะที่ซ่อนอยู่

ไม่มีที่ไหนในโค้ดเขียนว่าจอนี้มีกี่โหมด แต่อ่านจาก build() แล้วประกอบได้

บรรทัดเดียวนี้แบ่งจอเป็นสองโลก

┌─ โหมด A: สแกนของ (_pendingLine == null) ─────────────┐
│                                                       │
│  A1  ว่าง            _scanningItem == null            │
│      → ช่อง Part เปิด รอสแกน                          │
│                                                       │
│  A2  เลือกของแล้ว    _scanningItem != null            │
│      ├─ A2a ต้องมี S/N  → ช่อง S/N + รายการที่สแกน    │
│      └─ A2b ไม่ต้อง     → ช่องกรอกจำนวน               │
│                                                       │
└───────────────────────────────────────────────────────┘
                          │
                  ผูกพาเลทไม่สำเร็จ
                          ▼
┌─ โหมด B: ผูกพาเลท (_pendingLine != null) ────────────┐
│      → ช่อง Part ถูกซ่อน แสดงช่องพาเลทแทน            │
│      → ออกจากจอไม่ได้ (PopScope)                     │
└───────────────────────────────────────────────────────┘

เส้นทางปกติของผู้ใช้

A1 → สแกน Part → [เลือก condition] → [เลือก lot] → A2
A2 → สแกน S/N ครบ / กรอกจำนวน → กดยืนยัน
   → popup ให้สแกนพาเลท → บันทึก
   → สำเร็จ: กลับไป A1
   → พาเลทไม่ผ่าน: ไปอยู่ใน _resumedPendingLines (ยังอยู่ A1)

สังเกตว่าโหมด B ไม่ได้ถูกเข้าจากเส้นทางปกติ — เข้าได้จากการกด “ผูก” ที่รายการค้างเท่านั้น

ฟิลด์ที่คุมโหมดค่าไหนหมายถึงอะไร
_pendingLineไม่ใช่ null = อยู่โหมด B
_scanningItemไม่ใช่ null = เลือกของแล้ว รอกรอกจำนวน/S/N
_scanningItem!.serialRequiretrue = A2a, false = A2b

6. ทรัพยากรที่ไม่ถูกคืน

@override
void dispose() {
  _scanStatusTimer?.cancel();
  _partController.dispose();
  _partFocus.dispose();
  _qtyController.dispose();
  _manualQtyController.dispose();
  _serialController.dispose();

แต่ละตัวไม่ใหญ่ แต่ TextEditingController เป็น ChangeNotifier ที่อาจถือผู้ฟังไว้ และ FocusNode ลงทะเบียนกับระบบโฟกัส — การไม่คืนทำให้ทั้งสองอย่างค้างจนกว่าจอจะถูกปิด

แก้ได้ด้วยการคืนหลังกล่องปิด

Future<String?> _pickPallet({String? defaultPalletId}) async {
  final controller = TextEditingController(text: defaultPalletId ?? '');
  final focusNode = FocusNode();
  try {
    return await showModalBottomSheet<String>(...);
  } finally {
    controller.dispose();
    focusNode.dispose();
  }
}

finally รับประกันว่าคืนแน่ ไม่ว่ากล่องจะปิดด้วยการกดยืนยัน กดยกเลิก หรือปัดลง

รูปแบบนี้เจอสามที่ในโดเมนที่เรากำลังอ่าน — _pickPallet ที่นี่, _openAssignDialog ใน 17.8, และ _showBasketDialog ใน 17.10 รวมแปดวัตถุที่ไม่ถูกคืน
คนเขียนรู้เรื่อง dispose ดี — เก้าตัวในจอนี้ถูกคืนครบ สิ่งที่พลาดคือตัวที่สร้างในเมธอด ซึ่งอยู่นอกสายตาของ dispose()

7. ข้อผิดพลาดที่พบบ่อย

เข้าใจผิดที่จริง
27 ฟิลด์คือสถานะ 27 อย่างเป็นสถานะจริง 16 ที่เหลือเป็นทรัพยากรและค่าคงที่
ปิดช่องสแกนแล้วผู้ใช้ยกเลิกได้เสมอที่นี่ยกเลิกได้เฉพาะเมื่อมี S/N ให้ลบ
จำนวนที่ส่งมาจากแหล่งเดียวเก็บสองที่และซิงก์ด้วยมือ
ความจำพาเลทใช้ได้กับของทุกชิ้นต้องสภาพตรงกันเท่านั้น
dispose() ครบแล้วแปลว่าไม่รั่วตัวที่สร้างในเมธอดไม่อยู่ในนั้น

8. แบบฝึกหัด

เขียนเครื่องสถานะของจอนี้ออกมาให้ครบ แล้วหาสถานะที่ไม่ควรเกิดได้

    _pendingLine = line;          // ← ตั้ง _pendingLine โดยไม่ล้าง _scanningItem
    _resumedPendingLines.remove(line);
  });
  _palletFocus.requestFocus();
}

เมธอดนี้ตั้ง _pendingLine โดยไม่แตะ _scanningItem เลย

ผู้ใช้ที่จะเข้าถึงได้ต้องกดปุ่ม “ผูก” ที่รายการค้าง ซึ่งถูกป้องกันไว้ด้วย

ResumedPendingList(
  lines: _resumedPendingLines,
  canAssign: _pendingLine == null,    // ← กันไว้แล้ว แต่กันแค่ _pendingLine
  ...

canAssign ตรวจแค่ _pendingLine ไม่ได้ตรวจ _scanningItem

ผู้ใช้สแกน Part → _scanningItem มีค่า (โหมด A2)
  → รายการค้างยังแสดงอยู่และปุ่ม "ผูก" ยังกดได้ (canAssign = true)
    → ผู้ใช้กดผูก → _pendingLine มีค่า
      → ทั้งสองตัวมีค่าพร้อมกัน ← สถานะที่ไม่ควรเกิด

ผลที่ตามมา: ผู้ใช้ผูกพาเลทเสร็จ กลับมาโหมด A แต่ _scanningItem ยังค้าง ช่อง Part ยังปิดอยู่ และ _serialNumbers ที่สแกนไว้ก่อนหน้ายังอยู่ — ถ้าผู้ใช้สแกน S/N ต่อ จะกลายเป็นของชิ้นเดิมที่อาจไม่ได้ตั้งใจ

ข้อ 3 — ทำให้สร้างไม่ได้

วิธีที่เร็วที่สุดคือแก้เงื่อนไข

canAssign: _pendingLine == null && _scanningItem == null,

แก้ได้ แต่เป็นการอุดรูทีละรู — ถ้ามีทางเข้าใหม่ก็ต้องจำเพิ่มเงื่อนไขอีก

วิธีที่ทำให้สถานะผิดสร้างไม่ได้เลยคือรวมสองฟิลด์เป็นชนิดเดียวตามที่ 6.13 สอน

sealed class ScanMode {}

/// ว่าง รอสแกน Part
class Idle extends ScanMode {
  const Idle();
}

/// เลือกของแล้ว กำลังกรอกจำนวนหรือสแกน S/N
class Scanning extends ScanMode {
  Scanning(this.item);
  final POItem item;
  final List<String> serials = [];

  int get qty => item.serialRequire ? serials.length : manualQty;
  int manualQty = 0;
}

/// กำลังผูกพาเลทให้รายการที่ค้าง
class AssigningPallet extends ScanMode {
  AssigningPallet(this.line);
  final ReceiptLineResponse line;
}
ScanMode _mode = const Idle();

ตอนนี้สองสถานะพร้อมกันเป็นไปไม่ได้ เพราะฟิลด์มีตัวเดียวและถือค่าได้ทีละแบบ

และ build() เขียนได้แบบที่คอมไพเลอร์ตรวจว่าครบทุกกรณี

switch (_mode) {
  Idle() => _buildScanPartSection(enabled: true),
  Scanning(:final item) => item.serialRequire
      ? _buildSerialSection(item)
      : _buildManualQtySection(item),
  AssigningPallet(:final line) => _buildPalletSection(line),
}

เพิ่มโหมดใหม่วันหลัง คอมไพเลอร์จะบอกทันทีว่ามีที่ไหนยังไม่ได้จัดการ — ต่างจากตอนนี้ที่ต้องหาเองว่ามีเงื่อนไข != null อยู่กี่ที่

ข้อสังเกตที่สำคัญที่สุด: บั๊กนี้ยังไม่มีใครแจ้ง เพราะผู้ใช้ต้องกดในลำดับที่ไม่ปกติถึงจะเจอ — แต่มันเป็นบั๊กที่โครงสร้างของโค้ดเปิดช่องไว้ ไม่ใช่ความผิดพลาดของคนเขียน
วิธีอุดรูทีละรูจะได้ผลจนกว่าจะมีคนเพิ่มทางเข้าใหม่ ส่วนวิธีที่สองปิดช่องถาวร

9. สรุป

  • 27 ฟิลด์แบ่งได้ 8 กลุ่ม และเป็นสถานะจริงแค่ 16
  • จอมีสามโหมด: ว่าง / เลือกของแล้ว / ผูกพาเลท ซึ่งไม่มีที่ไหนเขียนไว้
  • _pendingLine คุมโหมดใหญ่ _scanningItem คุมโหมดย่อย
  • ช่อง Part ถูกปิดสองชั้น — ทั้งที่ widget และที่เมธอด
  • ผู้ใช้ที่เลือกผิดของและยังไม่สแกน S/N จะไม่มีทางยกเลิก
  • จำนวนถูกเก็บสองที่และซิงก์ด้วยมือทุกจุดที่แตะ _serialNumbers
  • ความจำพาเลทถูกล้างเมื่อล้มเหลว และตรวจสภาพสินค้าก่อนใช้
  • ตัวควบคุมที่สร้างใน _pickPallet ไม่ถูกคืน — สะสมทั้งกะ
  • _pendingLine และ _scanningItem มีค่าพร้อมกันได้ ซึ่งไม่ควรเกิด
